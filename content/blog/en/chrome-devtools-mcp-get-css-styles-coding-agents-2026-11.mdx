Anyone who has asked a coding agent to "fix the button spacing" knows the pattern. The agent edits the obvious rule, reports success, and nothing changes on screen, because a more specific selector three files away wins the cascade. The agent read the source; it never saw what the browser actually applied.

The Chrome DevTools team's November 2026 update targets exactly that gap. The DevTools MCP server, the piece that lets agents drive a real Chrome instance, now includes a `get_css_styles` tool. For a selected element it returns matched rules, inherited rules, declarations that were overridden, pseudo-elements, `@keyframes`, and other at-rules, with pagination for large results. In short, the agent gets the Styles pane instead of guessing at it.

## Why source-only CSS reasoning fails

CSS is one of the few places where reading the code is genuinely not enough to know the outcome. The final value of a property depends on:

- selector specificity and source order across every stylesheet loaded,
- cascade layers (`@layer`) and their declaration order,
- `!important`, inheritance, and custom properties resolved at runtime,
- media and container queries evaluated against the current viewport,
- styles injected by third-party scripts or component libraries.

A model looking at one component file sees a small fraction of that. Here is a typical trap:

```css
/* components/button.css */
.btn-primary {
  padding: 12px 24px;
}

/* vendor/theme.css, loaded later */
.card .actions button {
  padding: 4px 8px;
}
```

The agent edits `.btn-primary`, but the descendant selector in the theme has higher specificity (0,2,1 versus 0,1,0) and wins. With `get_css_styles`, the agent sees the `.btn-primary` declaration marked as overridden and the winning rule with its file and location. The right fix, whether that's adjusting a layer, scoping the theme, or raising specificity deliberately, becomes a decision it can actually reason about.

## Setting it up with Claude Code

The DevTools MCP server runs through `npx`. Adding it to Claude Code is a one-liner:

```bash
claude mcp add chrome-devtools -- npx chrome-devtools-mcp@latest --isolated
```

The `--isolated` flag starts Chrome with a temporary profile that is discarded afterwards. We recommend it as the default: an agent driving your everyday browser profile has access to every logged-in session you have.

A prompt that uses the new tool well is specific about the element and the expected outcome:

```text
Open http://localhost:3000/pricing.
Take a snapshot and find the "Start trial" button in the Pro card.
Use get_css_styles on it and tell me which rule determines its padding,
which rules are overridden, and from which files they come.
Do not edit any files yet.
```

Asking for diagnosis before edits matters. Agents tend to jump straight to writing CSS; forcing a read of the computed cascade first leads to smaller, better-targeted diffs.

## Where it fits in a frontend workflow

We see three practical uses.

**1. Debugging "my change does nothing".** This is the highest-value case. The agent can confirm whether its rule is applied, overridden, or not matched at all, which are three very different problems.

**2. Design system migrations.** When moving from a legacy stylesheet to Tailwind or a token-based system, the agent can inspect a component on the old page, list the effective values, and verify the new implementation produces the same ones. That's a much tighter loop than eyeballing screenshots.

**3. Reviewing agent-generated UI.** After an agent builds a component, a second pass with `get_css_styles` can flag hardcoded values that should be tokens, or rules that are dead because something else always wins.

## Limits worth keeping in mind

The tool's skill documentation tells agents to treat the output as authoritative and complete. For the element and page state at that moment, that's reasonable. But "that moment" carries a lot of assumptions:

- **Viewport and state.** Results reflect the current window size, color scheme, and interaction state. A bug that only happens at 375px wide, in dark mode, or on `:hover` won't appear unless the agent sets up that state first. Ask for it explicitly.
- **Dynamic styles.** Styles toggled by JavaScript after an interaction need the interaction to happen before inspection.
- **Authoritative for the browser, not for intent.** The tool tells you what wins, not what should win. Deciding whether to fix the theme or the component is still an architectural choice.
- **Large pages.** Pagination exists because results can be big. On heavy pages, costs in tokens add up quickly; inspect specific elements rather than sweeping the page.

There's also a security angle. An agent with a live browser can read whatever that browser can reach. Keep it pointed at local or staging environments, use the isolated profile, and avoid giving it sessions for production admin tools.

## Our take

Most AI coding tools have been strong at logic and weak at layout, partly because layout correctness lives in the browser, not in the repository. Giving agents structured access to the cascade is a meaningful step toward closing that gap, and it costs very little to adopt if you already use MCP.

For teams we work with, we'd suggest a simple rule: for any CSS bug, the agent must call `get_css_styles` on the affected element before editing. It adds a few seconds per task and removes an entire class of "fixed it, nothing changed" loops.
