GitHub Universe 2026 ran October 28–29 in San Francisco, and Copilot dominated the agenda. The individual features matter less than the shift in scope. Copilot is no longer framed as something that suggests code in your editor. It is framed as something that takes an issue, coordinates several agents, and brings a pull request to a mergeable state.

This summary draws on GitHub's own blog and several event recaps. The recaps disagree on which features are in preview versus GA, and on how pricing works, so check github.blog/changelog before making adoption decisions.

## What was announced

**Copilot app.** A new application built for agent-driven delivery. GitHub describes it as connecting agents and tools across projects so developers direct the work instead of managing every handoff.

**Copilot Projects (public preview).** You group repositories, design mocks, Slack threads, and meeting notes into one project, and Copilot runs as many agents as it needs in parallel to return deliverables such as pull requests. The work is split across agents rather than handed to one model end to end.

**Copilot Fusion.** The model routing and coordination layer previously previewed as HydraFusion. Some outlets report it as GA; others still call it a preview.

**Agent Merge and shared Automations.** Agent Merge sits in the pull request merge box and can fix failing CI or resolve merge conflicts. Copilot Automations can now be shared across a team and assigned to recurring work like issue triage and code review.

**Copilot code review Max (public preview) and Connectors.** code review Max sends the review to several agents backed by different model providers and merges their output into a single review. Connectors are GitHub-verified MCP servers that make tools like Slack and Sentry available across Copilot clients.

GitHub also said agents now open more than 40% of pull requests.

## What the 40% figure implies

When agents open a large share of pull requests, the constraint moves from writing code to reviewing and merging it. We made this point in October in [more AI code, same output](/blog/ai-agents-more-code-same-output-review-bottleneck-2026-10): if generation goes up and the review process stays the same, you either get a growing queue of open PRs or a lot of lightly reviewed merges.

Agent Merge pushes further in that direction. If an agent fixes CI and resolves conflicts, someone still has to own the state of the branch right before it merges. Decide who that is before you turn the feature on.

## Repository guardrails to set up first

Enabling agent features is a settings change on GitHub. Keeping them safe is the repository's job. These are the items we check first, both internally and on client projects.

### 1. Lock required checks and human review in a ruleset

Agent Merge can make CI pass. Whether its fix is correct is a separate question. Use a branch ruleset to require status checks and at least one approval. Requiring approval after the most recent push catches the case where an agent adds commits after a human approved.

### 2. Use CODEOWNERS for areas agents should not change unsupervised

```text
# .github/CODEOWNERS
# Auth, billing, and infra always need the owning team's review
/src/auth/            @your-org/security-team
/src/billing/         @your-org/payments-team
/infra/               @your-org/platform-team
/.github/workflows/   @your-org/platform-team
```

`.github/workflows/` deserves special attention. If an agent "fixes" CI by editing the workflow itself, the check no longer means anything.

### 3. Label agent-authored pull requests

Reviewers read differently when they know an agent wrote the change. This workflow adds a label when the PR author is in a configured list of bot accounts. Set the list to match the agents you actually use.

```yaml
# .github/workflows/label-agent-pr.yml
name: Label agent-authored PRs
on:
  pull_request_target:
    types: [opened]

permissions:
  pull-requests: write

jobs:
  label:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/github-script@<full-commit-sha> # v7.x
        env:
          AGENT_LOGINS: ${{ vars.AGENT_LOGINS }} # e.g. "copilot[bot],other-agent[bot]"
        with:
          script: |
            const agents = (process.env.AGENT_LOGINS || "").split(",").map(s => s.trim());
            const author = context.payload.pull_request.user.login;
            if (agents.includes(author)) {
              await github.rest.issues.addLabels({
                ...context.repo,
                issue_number: context.payload.pull_request.number,
                labels: ["agent-authored"],
              });
            }
```

`pull_request_target` is safe here because the job never checks out or runs code from the PR. Keep it limited to labeling.

### 4. Start Connectors (MCP) with minimal scopes

Connecting Slack or Sentry gives agents better context. It also adds more paths for outside text to be read as instructions. Start with read-only scopes and keep an inventory of which connectors are enabled in which repositories.

## Where code review Max fits

Reviewing with several models is a sensible way to reduce single-model blind spots. We still recommend treating it as a first pass before a human reads the diff, not as a replacement for that human. Models are good at local bugs and style issues. Whether the change matches the spec, or makes sense for the domain, is still a human call.

Decide up front whether agent review comments must be resolved before merging. Otherwise the same debate happens on every PR.

## Our take

GitHub has moved from "agents write code" to "agents run the delivery flow." The tooling is compelling, but the results depend on repository discipline.

- Teams with required checks, approval rules, and CODEOWNERS already in place can safely give agents more scope.
- In repositories with thin test coverage, Agent Merge will optimize for green CI rather than correct behavior.
- Licensing and AI credit billing are changing, so measure usage from the first pilot.

## Takeaways

- Most of Copilot Projects, Agent Merge, code review Max, and Connectors are in preview. Confirm availability in the changelog before rolling them out to production repositories.
- Review your rulesets (required checks, approval after the last push) and CODEOWNERS first.
- Make agent-authored PRs visible so reviewers can adjust how they read them.
- Start MCP connectors read-only and keep an inventory.

Before agent-opened PRs approach half of your total, write down who is accountable for the state of a branch at merge time. That is the most useful preparation right now.
