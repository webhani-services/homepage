Most cloud credential leaks used to end in crypto mining. The economics have shifted. According to a report published on November 2 by Google Threat Intelligence Group (GTIG) and Mandiant, attackers now prefer to turn stolen cloud identities into access to hosted LLMs, and a resale market has formed around it. In one case they describe, a single actor made more than 500,000 model calls in under eight hours, leaving the victim with close to $1 million in token costs. Other incidents ran above $100,000 per day.

The numbers are striking, but the structural change matters more for engineering teams. LLMjacking is no longer an opportunistic side effect of a leaked key. It is a supply chain with specialists.

## How the market is organized

The report separates two roles:

- **Intrusion crews** obtain credentials. The dominant entry points are the usual ones: IAM access keys, service account key files, GitHub personal access tokens, and live session tokens.
- **"LLM Mixers"** pool those credentials behind open-source API gateways and custom relays, meter the traffic, and resell model access to their own customers. Because each request is routed through a pool of stolen keys, the origin of any individual call is hard to trace.

Two details from the coverage stand out to us:

1. **Several victims had never enabled LLM services.** The attackers enabled model access themselves using the stolen identity. "We don't use Bedrock / Vertex AI" is not a defense; it is a blind spot.
2. **AI gateways are now targets.** One incident reportedly involved a vulnerability in a self-hosted LiteLLM gateway that let ordinary virtual keys be escalated to admin. Whatever the exact CVE details turn out to be, the lesson is general: a gateway that holds provider keys for the whole company is a high-value asset and needs the same patching discipline as your identity provider.

## Why this is different from a normal key leak

A leaked database password exposes data. A leaked cloud identity with model access exposes your **budget**, and it does so at a rate humans don't notice in time. LLM inference is one of the few cloud services where an attacker can generate six-figure charges in a day without provisioning anything visible like instances or clusters. Cost anomaly detection that runs once a day is too slow.

It also changes who needs to care. Teams that run no AI features at all are still exposed, because the attacker only needs a principal with permission to enable and invoke models.

## Controls we recommend

None of these are new ideas. What's new is the priority.

### 1. Deny model invocation where it isn't needed

On AWS, the cleanest control is a Service Control Policy on organizational units that have no business running inference. It blocks the stolen-credential path even if a principal has `AdministratorAccess`.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyBedrockOutsideAIWorkloads",
      "Effect": "Deny",
      "Action": [
        "bedrock:InvokeModel",
        "bedrock:InvokeModelWithResponseStream",
        "bedrock:PutFoundationModelEntitlement",
        "aws-marketplace:Subscribe"
      ],
      "Resource": "*"
    }
  ]
}
```

Attach it to OUs like "legacy", "data-platform", or "sandbox", and keep a dedicated AI workload account (or OU) where invocation is allowed. The `aws-marketplace:Subscribe` line matters because third-party model access is often gated by a Marketplace subscription. Test in a non-production OU first; SCPs affect every principal in scope.

On Google Cloud, the equivalent is restricting which projects can enable the Vertex AI API (via organization policy on allowed services) rather than relying on per-project IAM.

### 2. Remove long-lived keys from CI

GitHub PATs and static cloud keys in CI secrets are among the most common sources in the report. If your pipelines still use `AWS_ACCESS_KEY_ID`, move to OIDC federation so that nothing long-lived exists to steal:

```yaml
permissions:
  id-token: write
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/gha-deploy
          aws-region: ap-northeast-1
```

Scope the role's trust policy to a specific repository and branch, and make sure the deploy role has no Bedrock permissions unless deployment genuinely needs them.

### 3. Scan for leaked secrets, including history

Keys leaked months ago are still valid if nobody rotated them. Run a scan across full git history, not only the working tree:

```bash
gitleaks git . --redact --report-path gitleaks-report.json
```

Every hit should be rotated, not just deleted from the repository. Deleting a committed key does nothing to the copies already harvested.

### 4. Alert on spend in hours, not days

Set budgets per AI account with alerts at low thresholds, and route them to a channel someone actually watches. Provider-side controls help too: per-key spend limits and rate limits on your LLM gateway turn a $1M incident into a capped one. If you run LiteLLM or a similar proxy, configure per-key budgets and keep the admin/master key out of application environments entirely.

### 5. Treat the AI gateway as tier-0 infrastructure

- Patch it on the same cadence as your SSO and secrets manager.
- Don't expose its admin API to the internet.
- Log key creation and privilege changes, and alert on them.

## What we'd check this week

If you only have an hour:

- List which accounts/projects have model access enabled. Anything unexpected is either shadow AI or an attacker.
- Confirm a budget alert exists for every account that can invoke models.
- Search CI configuration for static cloud keys and GitHub PATs.
- Check the version of any self-hosted LLM gateway against its security advisories.

## Takeaway

LLMjacking has moved from incident to industry, with separate roles for credential theft and resale. The practical response is unglamorous: deny inference where it isn't used, eliminate long-lived credentials, and make cost alerts fast enough to matter. At webhani we now treat "can this identity invoke a model?" as a standard question in cloud security reviews, alongside "can it read production data?" Both answers should be deliberate.
