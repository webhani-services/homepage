The Next.js team shipped its pre-announced security release on November 3. The fixed versions are **16.4.5 (Active LTS)** and **15.5.29 (Maintenance LTS)**. Most issues are rated medium, but one high-severity bug matters a lot if you run a multi-tenant SaaS.

This summary is based on the official Next.js blog post and secondary coverage found through search. Sources disagree on the exact count and on CVE/GHSA identifiers, so use the official post on nextjs.org/blog as the authoritative list.

## What was fixed

| Severity | Issue | Most likely to affect |
| --- | --- | --- |
| High | Cross-tenant cache disclosure | Apps combining `unstable_cache` with `use cache` |
| Medium | Cache poisoning on self-hosted deployments | A specific dynamic route shape with a blocking fallback |
| Medium | Response injection and disclosure via stale compressed response framing | Deployments behind reverse proxies that pipeline HTTP/1.1 |
| Medium | Cookie values readable through the `x-middleware-set-cookie` header | Only when attacker JavaScript already runs on the same origin |
| Medium | SVG rejection bypass in Image Optimization | Caused by AVIF misclassification |

### High: cross-tenant cache disclosure

In apps that combine `unstable_cache` and `use cache`, one tenant's cached data could be served to another tenant. For any SaaS that varies data by signed-in user or tenant, that is a direct data leak.

### Medium: self-hosted cache poisoning

According to the official post, this needs a narrow set of conditions: a prerenderable dynamic parameter requested with a value not generated at build time, deeper parameters that are never prerendered, a blocking fallback shell, and a layout that reads a shallower parameter inside a Suspense boundary. If you run `next start` on your own Node.js servers or containers rather than on Vercel, compare this against your actual route tree.

### Medium: response framing

Stale framing on compressed responses can let one response bleed into another request. Behind a reverse proxy that pipelines HTTP/1.1 upstream, this can lead to responses being delivered to the wrong client. Self-hosted setups behind Nginx or an internal load balancer should check this first.

## Upgrading

Start by checking the version that actually resolves in your lockfile, not the range in `package.json`.

```bash
# See the resolved version
npm ls next

# Active LTS line
npm install next@16.4.5

# Maintenance LTS line (if you are still on 15.x)
npm install next@15.5.29
```

Our own site runs on Next.js 16, so it is in scope too. The upgrade is simple, but do not skip these steps:

1. Review the lockfile diff and make sure nothing besides `next` moved unexpectedly.
2. Rebuild container images and confirm a cached layer is not still installing the old version.
3. After deploying, confirm the version that is actually running in production.

The last step gets skipped more often than you would think. CI builds with the new version while production keeps running last week's image.

## The real lesson: put the tenant in the cache key yourself

Patching fixes this bug. The more durable lesson is a design rule: do not rely on the framework to infer cache isolation from request context.

`use cache` builds the cache key from the function's arguments and the values it closes over. If you pass the tenant ID as an explicit argument instead of reading it from cookies or headers inside the function, the key is always scoped per tenant.

```tsx
// lib/data.ts
// Avoid: tenant resolved implicitly inside the cached function
export async function getDashboardImplicit() {
  "use cache";
  const tenantId = await resolveTenantFromSomewhere(); // may not be part of the key
  return db.dashboard.findMany({ where: { tenantId } });
}

// Prefer: tenant ID is an argument, so it is always part of the key
export async function getDashboard(tenantId: string) {
  "use cache";
  return db.dashboard.findMany({ where: { tenantId } });
}
```

The same applies to existing `unstable_cache` calls. Put the tenant in both the key parts and the tags.

```ts
import { unstable_cache } from "next/cache";

export function getInvoices(tenantId: string) {
  return unstable_cache(
    async () => db.invoice.findMany({ where: { tenantId } }),
    ["invoices", tenantId],
    { tags: [`tenant:${tenantId}:invoices`], revalidate: 300 },
  )();
}
```

Also look for half-finished migrations where the same data is cached by both mechanisms. The high-severity bug lives in exactly that combination, and mixed caching layers are hard to reason about even without a bug.

## Other hardening

- **Image Optimization:** if you do not need SVG, leave `images.dangerouslyAllowSVG` disabled. If you optimize user-uploaded images, keep the allowed remote patterns as narrow as possible.
- **Reverse proxies:** check whether anything pipelines HTTP/1.1 to your Next.js upstream. Most setups do not, but custom proxies and old configs are worth a look.
- **CSP:** the cookie exposure assumes attacker JavaScript is already running on your origin. A Content Security Policy that blocks XSS is what keeps this class of issue contained.

Better Auth, an authentication library often used with Next.js, also shipped 1.7.16 on November 3 with fixes for 12 security issues. If you use both, update them together.

## Takeaways

- Upgrade `next` to 16.4.5 or 15.5.29, and verify the version running in production.
- In multi-tenant apps, pass the tenant ID explicitly as a cached function argument or key part. Do not depend on implicit isolation.
- If you self-host, compare your route structure and proxy configuration against the conditions above.
- With security releases now arriving almost monthly, treat patching as routine maintenance with a written procedure, not a one-off event.
