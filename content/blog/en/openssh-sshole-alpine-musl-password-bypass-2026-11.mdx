On November 5, Alpine Linux and the OpenSSH project published advisories for a password authentication bypass in sshd. It is tracked as CVE-2026-123158, nicknamed "sshole", and carries a CVSS 3.1 base score of 8.1 (High).

The uncomfortable part is who gets hit: **accounts that were never supposed to accept a password at all**. Key-only users and accounts with a locked password are exactly the targets.

## The conditions

Based on the published advisories, a host is exposed when all of these hold:

- sshd is **OpenSSH built against musl libc without PAM**. Alpine's stock `openssh-server` package matches.
- `PasswordAuthentication` is enabled. Upstream's default is `yes`.
- The target account has no usable password.

Under those conditions, an attacker who sends an oversized, crafted password can log into an account that should be unreachable by password. Analyses so far report that Dropbear and other non-OpenSSH servers are not affected.

OpenSSH 10.6p2, released November 5, contains the fix, and Alpine shipped patched packages for edge and every stable branch back to 3.16. As of November 6, public reproductions exist, but no confirmed in-the-wild exploitation has been reported and the CVE is not in CISA's KEV catalog. With a working reproduction already public, though, plan on that changing soon.

## Step one: find every Alpine sshd

Debian, Ubuntu, and RHEL use glibc and fall outside these conditions, so the real work is scoping. In our client engagements, Alpine sshd instances tend to hide in places nobody lists in the asset inventory:

- Small bastion VMs or containers
- SFTP drop points and Git mirrors used by CI
- "SSH-able" dev containers in a `docker compose` file
- Vendor appliances that happen to run Alpine internally

On a host, this check tells you what you are dealing with:

```bash
#!/bin/sh
# Quick exposure check for CVE-2026-123158
set -eu

[ -f /etc/alpine-release ] && echo "distro: alpine $(cat /etc/alpine-release)"

if ldd "$(command -v sshd)" 2>/dev/null | grep -q musl; then
  echo "libc: musl"
fi

# Effective configuration, with Include'd drop-ins resolved
sshd -T 2>/dev/null | grep -Ei '^(passwordauthentication|usepam) '

sshd -V 2>&1 | head -1 || ssh -V 2>&1
```

Use `sshd -T` instead of grepping `sshd_config`. Drop-in files pulled in via `Include` often override what the main file says, and `-T` shows the values the daemon will actually use.

For images, sweep what you have locally or in your registry:

```bash
for img in $(docker images --format '{{.Repository}}:{{.Tag}}' | grep -v '<none>'); do
  if docker run --rm --entrypoint sh "$img" -c \
      'test -f /etc/alpine-release && apk info -e openssh-server' >/dev/null 2>&1; then
    echo "CANDIDATE: $img"
  fi
done
```

In production, an SBOM-based scanner such as Trivy or Grype queried by CVE ID is more reliable. Vulnerability databases take time to pick up new CVEs, so run direct checks like this one alongside the scanner until they catch up.

## Remediation

### 1. Upgrade and restart

```bash
apk update
apk upgrade openssh-server openssh
rc-service sshd restart   # OpenRC
```

Alpine's advisory spells this out, and it is easy to miss: **upgrading the package does not replace the running daemon**. Restart it, then verify the process start time is after the upgrade:

```bash
ps -o pid,lstart,args -C sshd 2>/dev/null || ps -ef | grep '[s]shd'
```

### 2. If you cannot patch today

Disabling password authentication closes this path:

```text
# /etc/ssh/sshd_config.d/00-disable-password.conf
PasswordAuthentication no
KbdInteractiveAuthentication no
```

The `00-` prefix matters. For most keywords, sshd uses the **first** value it encounters, so a `no` in a later file loses to an earlier `yes`. Validate with `sshd -t`, confirm the effective value with `sshd -T`, then reload.

### 3. Rebuild images instead of patching containers

For containers, don't run `apk upgrade` inside them. Rebuild from an updated base and redeploy:

```dockerfile
FROM alpine:3.24
RUN apk add --no-cache --upgrade openssh-server
COPY sshd_config.d/ /etc/ssh/sshd_config.d/
```

`--upgrade` pulls the latest package even when the build reuses a stale cached base layer.

## Check the logs

Successful password authentication against an account with no password is this bug's signature. In an environment that does not use password logins at all, any hit here is suspicious:

```bash
grep -E 'Accepted password for' /var/log/messages /var/log/auth.log 2>/dev/null
```

If you find one, treat the host as compromised: rotate the keys it holds and rebuild it rather than cleaning it in place.

## Our take

The bug matters, but the bigger lesson is about assumptions. "We only use keys" is often a statement about **habit, not configuration**. We regularly find hosts where nobody logs in with a password, yet `PasswordAuthentication` still sits at its default of `yes`.

What we recommend to clients:

- Set `PasswordAuthentication no` explicitly on every SSH endpoint. Don't leave unused features enabled.
- Assert the `sshd -T` output in CI or configuration management rather than trusting the config file.
- Where possible, move bastion access to SSM Session Manager, IAP, or similar, so the SSH port isn't exposed at all.
- Question every container image that ships an sshd.

Patching takes an afternoon. Knowing where all your SSH entry points are is what makes the next advisory an afternoon too.
