Python 3.15 was released on October 9, a little over a week after its planned date, following an extra release candidate. Plenty has been written about lazy imports and the new `frozendict`. This post covers the other three headline items that tend to get over-read: the JIT compiler, the new `abi3t` stable ABI, and free-threading.

Numbers and compatibility details below come from the CPython release notes as quoted by secondary coverage, and from trade press. Sources disagree on exact benchmark figures, so treat any speedup as a starting hypothesis for your own measurement.

## The JIT: modest, still experimental

The JIT compiler in 3.15 is still labeled experimental. Reported gains are in single-digit to low-double-digit percentages: roughly 8–9% mean improvement over the interpreter on x86-64 Linux in one account, about 7–8% geometric mean in another, and 12–13% on Apple silicon. Those are averages across a benchmark suite. Individual workloads can be faster, unchanged, or slower.

For a typical web backend, that range matters less than where time actually goes. A request handler that spends most of its time waiting on a database, a cache, or an upstream HTTP call is not CPU-bound in the interpreter, so a faster interpreter loop barely moves p95 latency. The JIT helps most with tight pure-Python loops: parsing, serialization written in Python, template rendering, data transformation.

Two cautions:

- A July 2026 newsletter reported that the JIT disables itself once threads start, which would make it a poor match for a threaded server or free-threaded build. We did not find confirmation that this changed in the final release, so check it against your own setup rather than assuming either way.
- An experimental feature has no stability promise. If you enable it in production, you want a one-switch way to turn it off.

If you want to evaluate it, you need an interpreter built with JIT support, and enabling is typically controlled by an environment variable. Check the 3.15 documentation for the exact build flag and variable name. A comparison harness is straightforward:

```python
# bench_endpoint.py: run the same CPU-bound handler under both configurations
import time
import statistics

def handler(payload: dict) -> dict:
    # Stand-in for real work: replace with your serialization / transform path
    return {k: str(v).upper() for k, v in payload.items()}

payload = {f"key{i}": i for i in range(200)}

def run(n: int = 20_000) -> float:
    start = time.perf_counter()
    for _ in range(n):
        handler(payload)
    return time.perf_counter() - start

samples = [run() for _ in range(7)]
print(f"median {statistics.median(samples):.3f}s  min {min(samples):.3f}s")
```

Run it twice, once with the JIT enabled and once without, on the same machine. A micro-benchmark like this tells you the ceiling. Then repeat with a replay of real traffic against your application, because that is the number that matters.

## abi3t: the quiet change with the biggest packaging impact

Free-threaded builds of Python could not use the existing stable ABI (`abi3`) wheels, which meant native extension authors had to ship a separate wheel per Python version for free-threaded interpreters. 3.15 adds `abi3t`, a stable ABI for free-threaded builds, so one wheel can work across versions.

The catch, per the release notes as reported: build tooling has not caught up. setuptools, meson-python, scikit-build-core, and Maturin were listed as not yet supporting it. That has a practical consequence for you as a consumer rather than a maintainer. Even if your own code is pure Python, a dependency with a native extension (a database driver, a crypto library, a numerics package) may have no free-threaded wheel for 3.15 yet. In that case `pip` either falls back to building from source or fails.

Before planning a free-threaded rollout, audit it:

```bash
# Create a clean environment on the target interpreter and see what actually resolves
python3.15t -m venv .venv-ft
. .venv-ft/bin/activate
pip install --only-binary=:all: -r requirements.txt
```

`--only-binary=:all:` makes the install fail loudly for any package that would need a source build. The failures are your real list of blockers. The `t` suffix on the interpreter name is the common convention for free-threaded builds, but confirm what your installer provides.

## Free-threading: supported, not a default recommendation

Free-threading stopped being experimental in 3.14, and in 3.15 the official macOS installers reportedly enable it by default. That is a signal about maturity, not a signal that you should switch your servers.

What free-threading changes for a web service: CPU-bound work in threads can use multiple cores in one process, which could reduce the number of worker processes and the memory duplicated across them. What it does not change: if you already run several worker processes behind Gunicorn or Uvicorn, you already use your cores. The gain is largest for services that hold large in-memory state they cannot cheaply share across processes.

The risks are the ones you would expect. Thread-safety bugs that the GIL used to mask become visible, and extension modules that are not thread-safe can misbehave. Single-thread performance on free-threaded builds has historically been somewhat lower than on the regular build, so measure it.

## Our recommendation

1. **Upgrade to 3.15 for the ordinary reasons**: lazy imports, UTF-8 as the default encoding, the new types, a supported version. Do this on the regular (GIL) build.
2. **Treat the JIT as an experiment** and benchmark it on CPU-bound paths only. Do not enable it fleet-wide because of an average figure.
3. **Run the `--only-binary` audit now** to learn how far your dependency tree is from free-threaded readiness. It costs ten minutes and informs a decision for next year.
4. **Defer free-threaded production** unless you have a specific multi-core-in-one-process problem and the test coverage to find concurrency bugs.

A new Python release rewards boring adoption: move to the supported version, keep the defaults, and spend your experimentation budget where measurement shows a bottleneck.
