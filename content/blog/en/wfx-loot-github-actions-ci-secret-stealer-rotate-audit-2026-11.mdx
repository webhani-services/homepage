Starting around November 10, 2026, a threat actor used thousands of hijacked GitHub accounts to push a credential-stealing script into repositories at scale. Security vendors track it as "wfx" or "wfx-loot." Figures differ between sources. Aikido reports roughly 4,837 compromised accounts opening probe pull requests across about 61,000 repositories, with the payload actually executing in a little under two thousand of them. Treat those numbers as approximate.

The detail that matters for engineering teams is not the scale. It is that, according to the write-ups from Endor Labs and others, the campaign does not exploit a bug in GitHub Actions. It relies on stolen account credentials and tokens, then uses the permissions those accounts already have. Your workflow files are the delivery mechanism, and your CI secrets are the target.

## What the stealer reportedly does

Based on public analyses, the sequence looks like this:

1. A hijacked account opens a probe pull request against repositories it can reach, to learn whether it has enough write access to inject a workflow.
2. Where it does, a workflow runs a shell script inside GitHub Actions, where repository secrets, cloud credentials, package registry tokens and AI provider API keys tend to live.
3. The script exfiltrates what it finds, and reportedly deletes the workflow runs that would reveal it.
4. It then establishes persistence on the cloud side: registering new federated credentials on Azure applications and modifying AWS role trust policies.

Step 4 is why "rotate your secrets" is an incomplete response. A rotated token does nothing about a trust policy that now lets an attacker's principal assume your role.

## Triage: what to check first

If you maintain repositories with CI that touches cloud accounts, work through these in order.

**1. Look for workflows you did not write.** Search recent history for workflow files added or changed by unfamiliar commits, including on non-default branches.

```bash
# Workflow changes in the last 30 days, with author
git log --since="30 days ago" --all \
  --format='%h %an %ad %s' --date=short \
  -- .github/workflows/

# Anything referencing the campaign's markers
git grep -n -i "wfx" $(git rev-list --all --since="30 days ago") -- .github 2>/dev/null | head
```

**2. Audit cloud-side trust, not just keys.** For AWS, list roles whose trust policy allows a principal you do not recognize, or an OIDC subject you did not configure. CloudTrail events for `UpdateAssumeRolePolicy` are a good starting filter.

```bash
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=EventName,AttributeValue=UpdateAssumeRolePolicy \
  --start-time "$(date -u -d '30 days ago' +%FT%TZ)" \
  --query 'Events[].{time:EventTime,user:Username,res:Resources[0].ResourceName}'
```

On the macOS shell, replace the `date` call with `date -u -v-30d +%FT%TZ`.

For Azure, review federated identity credentials on app registrations. The reporting mentions entries with a `wfx-ci-` prefix, but do not rely on the name: review every credential you cannot account for.

**3. Rotate, in the right order.** Remove the unrecognized trust or federated credentials first, then rotate the secrets. Rotating first leaves a window in which the attacker can mint fresh credentials through the backdoor.

**4. Check the humans.** Force a review of who has write access, revoke stale personal access tokens and OAuth app grants, and confirm two-factor authentication is enforced for the organization. The accounts in this campaign were reportedly taken over through credential stuffing, phishing or infostealer logs, not through GitHub itself.

## Hardening that limits the blast radius

None of these is new advice, but this campaign is a good test of whether you actually applied it.

**Use OIDC federation instead of long-lived cloud keys, and constrain the subject.** A trust policy that accepts any workflow in the repository is only slightly better than a static key. Pin it to the branch or environment:

```json
{
  "Condition": {
    "StringEquals": {
      "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
      "token.actions.githubusercontent.com:sub": "repo:your-org/your-repo:environment:production"
    }
  }
}
```

Combined with a protected `production` environment that requires reviewer approval, a malicious workflow on a feature branch cannot obtain production credentials.

**Set minimal default permissions.** In each workflow, or at the organization level:

```yaml
permissions:
  contents: read
```

**Gate who can change workflows.** Use CODEOWNERS on `.github/workflows/` and require review from a small group. Branch protection and rulesets should apply to administrators too.

**Pin third-party actions to full commit SHAs**, and keep secrets out of jobs that run on untrusted pull request events.

**Alert on the cloud side.** Create alerts for trust policy updates and new federated credentials. These are low-volume events, so the alerts are cheap and the signal is strong.

## Our take

Two lessons stand out for the teams we work with.

First, CI is a credential store with a public-facing trigger surface. Most organizations review application code carefully and workflow files casually, yet a workflow is arbitrary code with access to your most privileged secrets.

Second, incident response for CI compromise has to include cloud identity audit, not just token rotation. If your runbook says "rotate secrets" and stops there, add a step for trust policies, federated credentials, and any new principals created during the exposure window.

AI provider API keys are also on the target list. If your pipelines or coding agents hold them, apply the same scoping and rotation discipline you use for cloud keys.

## Takeaways

- The campaign abuses stolen credentials, not a GitHub Actions vulnerability, so account hygiene and token scope are the first line of defense.
- Audit workflow history and cloud trust relationships, then remove backdoors before rotating secrets.
- Constrain OIDC subjects to environments, enforce reviews on workflow changes, and alert on trust policy changes.

Details are still evolving and counts vary by vendor, so check the current advisories from Aikido, Endor Labs and GitHub before closing out your own review.
