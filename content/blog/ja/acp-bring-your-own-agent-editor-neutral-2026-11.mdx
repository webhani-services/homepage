Android Studio の Rabbit 2 系のリリースノートに、「Bring Your Own Agent」という機能が載っています。Agents メニューから外部のコーディングエージェントを選び、手持ちのサブスクリプションやAPIキーでサインインすると、IDE が別プロセスとしてそのエージェントを起動する仕組みです。リリースノートで名前が挙がっているのは Claude Agent、OpenAI Codex、Google の Antigravity などです。接続したエージェントは、ビルド診断、SDK ツール、ターミナル実行、エミュレータ管理といった IDE の機能を使えます。

導入前に確認しておきたい点があります。公式のリリースノートでは Rabbit 2 は Canary 扱いですが、二次情報には安定版として紹介する記事もあります。実際にインストールするチャンネルは自分で確認してください。

Android 向けの話に見えますが、多くのチームにとって重要なのは、その下で使われている Agent Client Protocol（ACP）という仕組みのほうです。

## ACP とは何か、MCP との違い

どちらも AI 周辺の JSON-RPC 系プロトコルなので混同されがちですが、つなぐ対象が違います。

| プロトコル | つなぐ対象 | 答える問い |
| --- | --- | --- |
| MCP | エージェント ↔ ツール・データ | 「エージェントは何を呼び出せるか」 |
| ACP | エディタ ↔ エージェント | 「エディタはエージェントをどう動かし、作業をどう見せるか」 |

MCP はデータベースや課題管理ツール、ブラウザへのアクセスをエージェントに与えます。ACP はその手前、つまり人間が使うエディタとエージェントプロセスの間の層です。プロンプトの送信、進捗のストリーミング、ファイル編集のレビュー表示、危険な操作の前の許可確認などを担います。

共通プロトコルがなければ、エディタとエージェントの組み合わせごとに個別の連携が必要になり、N 個のエディタと M 個のエージェントで N×M 通りになります。共通化すれば N+M で済み、組み合わせはユーザーが選べます。

## Android 以外でも意味がある理由

私たちが支援するチームでは、コストや品質、コンプライアンスの理由でエージェントを一つに決めることがよくあります。ところが実際には、メンバーの半分が VS Code、4分の1が JetBrains 系、残りが Neovim や Zed ということも珍しくありません。エージェントが特定ベンダーのプラグインでしか使えないと、標準化は不均一にしか徹底されません。

エディタ非依存のプロトコルがあると、判断の置き場所が変わります。

- **エージェントの選定はチームの方針になる。** どの IDE を入れたかという偶然に左右されなくなります。
- **エディタの選択は個人の好みのままでよい。** 管理側が思う以上に、開発者はここにこだわります。
- **乗り換えコストが下がる。** エージェントの切り替えがワークフローの移行ではなく、設定変更で済みます。

ただし、プロトコルが標準化するのは会話の部分だけです。能力の差は残ります。Android Studio の統合でエージェントが何をできるかは IDE が何を公開しているかで決まり、エージェントの動きをどこまでユーザーに見せるかもエディタ側の判断です。

## ACP 風のセッションのイメージ

ACP は JSON-RPC をベースにしており、一般的な構成ではエディタがエージェントをサブプロセスとして起動し、標準入出力でやり取りします。正確なメソッド名やスキーマは仕様書で定義されているため、以下は交換の形を示すための例であり、そのまま使えるクライアントではありません。

```ts
// イメージ用のコードです。実際のメソッド名は ACP の仕様を確認してください。
import { spawn } from "node:child_process";

const agent = spawn("my-agent", ["--acp"], { stdio: ["pipe", "pipe", "inherit"] });

let nextId = 1;
function send(method: string, params: unknown) {
  const msg = { jsonrpc: "2.0", id: nextId++, method, params };
  agent.stdin.write(JSON.stringify(msg) + "\n");
}

agent.stdout.on("data", (chunk) => {
  for (const line of chunk.toString().split("\n").filter(Boolean)) {
    const message = JSON.parse(line);
    // エディタ側の責務: ストリーミングされる進捗の表示、
    // 提案されたファイル編集の差分表示、
    // コマンド実行やプロジェクト外への書き込み前のユーザー確認。
    console.log("agent ->", message);
  }
});

send("initialize", { clientCapabilities: { fileEdits: true } });
```

ポイントは役割分担です。エージェントは推論して操作を提案し、エディタは差分表示、許可の確認、作業ディレクトリといった画面まわりを持ちます。この分担があるから、一つのエージェントを複数のエディタで動かせます。

## 運用上の実務的なポイント

**エージェントへの指示は、エディタの設定に置かない。** 規約をリポジトリ内のファイル（`AGENTS.md` など）に書いておけば、IDE ではなくプロジェクトに付いてきます。特定プラグインの設定画面に埋もれた指示は持ち運べません。

**統合ごとに権限モデルを確認する。** 同じエージェントでも、ホストのエディタが何を許すかによって挙動が変わります。新しいエディタで有効にする前に、確認なしで実行できる操作、書き込める範囲、ネットワークアクセスの制限を確かめてください。信頼できない指示ファイルのリスクについては、[AGENTS.md の乗っ取り](/blog/agents-md-hijack-coding-agents-untrusted-instructions-2026-10)の記事で触れました。新しいホストがエージェントを起動する場合も同じ注意が必要です。

**別インスタンスは別の状態を持つ。** Android Studio は、ターミナルで動いているエージェントにアタッチするのではなく、専用のエージェントプロセスを起動します。セッション履歴やメモリ、保存前のコンテキストは引き継がれません。ターミナルと IDE を行き来するなら、文脈を伝え直す前提で使ってください。

**個人はサブスクリプション、チームは管理されたキーで。** 開発者ごとの API キーが IDE の設定に散らばると、ローテーションも監査も難しくなります。利用状況のレポートが必要な組織では、中央のゲートウェイやエンタープライズプランを経由させるのが現実的です。

## webhani の見解

エディタとエージェントの間を標準化するのは妥当な設計だと考えています。言語サーバーが成功したのと同じ理由で、エディタと言語ツールを独立して進化させられるからです。大手ベンダーの IDE が採用したことは、単独のプラグイン発表よりも強いシグナルです。

一方で、ACP がどこでも同じように動くことを前提にしたチームのワークフローは、まだ組まないほうがよいと思います。プロトコルは若く、ホストごとの対応にもばらつきがあり、今回の Android Studio の機能自体も安定版かどうかの表記が揺れています。現時点では次の進め方が堅実です。

1. チームの主力エージェントを一つ決め、文書化する。
2. 規約はエディタ固有の設定ではなく、リポジトリのファイルに置く。
3. ACP 経由の利用は、まず一つのエディタで少人数に試してから広げる。
4. 各ホストがエージェントに何を公開するかを確認し、セキュリティ基準の一部として記録する。

エディタが混在するチームでのエージェント選定やガードレール設計は、私たちが日常的に支援している領域です。
