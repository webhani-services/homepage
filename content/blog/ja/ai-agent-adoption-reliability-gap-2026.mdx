Temporalが実施した2026年度の開発者調査には興味深い数字が並んでいます。AI coding agentを「毎日以上の頻度で使用する」と回答した開発者・リーダーの割合は、前年の47.3%から80.8%へと1年で70.8%も増加しました。544名のエンジニアを対象にした米英両国の調査で見える大きなトレンドです。

しかし同じ報告書には、もう一つ重要な記述があります。「AIエージェントをより頻繁に使いたくない理由は何か」という問いに対し、35.7%の回答者が「タスクのStateを追跡できない」と答えました。続いて、Agent動作のDebug困難さ（意味的には正しく見えるが実は間違っている出力の検出）、それにAgent実行のコスト予測不可能性が主要な課題として挙げられています。

つまり、採用急増の裏側では、正反対の傾向が起きているのです。使いこなせたチームと、そうでないチームの間に、信頼性の格差が急速に広がっています。

## State追跡：なぜ失敗は常に途中で起きるのか

マルチステップなタスクをagentに任せるとき、最初のステップは完璧でも、3つ目のステップで何か予期しない状況に遭遇する可能性があります。その時、agentを再度起動すればいいのかも知れません。でも、もし5ステップ目で失敗したら。9ステップなら。

多くのチームの現状は、失敗時に「最初からやり直す」です。これは外部API呼び出しのコストを再度支払うことを意味し、実システムへの操作がダブル実行されるリスクもあります。

webhaniが推奨するアプローチは、各ステップの完了時点でStateをファイルまたは軽量なログに記録する、チェックポイント方式です。

```typescript
// agentの各ステップ完了後に状態を保存
interface TaskCheckpoint {
  stepId: string;
  status: "pending" | "in_progress" | "completed" | "failed";
  result?: unknown;
  timestamp: number;
  agentContext?: Record<string, unknown>;
}

async function executeTaskWithCheckpoint(
  taskId: string,
  steps: Array<{ id: string; action: () => Promise<unknown> }>
) {
  const checkpointFile = `./checkpoints/${taskId}.json`;
  let checkpoint = loadCheckpoint(checkpointFile) || { taskId, steps: [] };

  for (const step of steps) {
    const existing = checkpoint.steps.find((s) => s.stepId === step.id);
    if (existing?.status === "completed") {
      console.log(`Step ${step.id} already completed, skipping.`);
      continue;
    }

    try {
      checkpoint.steps.push({
        stepId: step.id,
        status: "in_progress",
        timestamp: Date.now(),
      });
      saveCheckpoint(checkpointFile, checkpoint);

      const result = await step.action();

      checkpoint.steps = checkpoint.steps.map((s) =>
        s.stepId === step.id
          ? {
              ...s,
              status: "completed",
              result,
              timestamp: Date.now(),
            }
          : s
      );
      saveCheckpoint(checkpointFile, checkpoint);
    } catch (err) {
      checkpoint.steps = checkpoint.steps.map((s) =>
        s.stepId === step.id ? { ...s, status: "failed" } : s
      );
      saveCheckpoint(checkpointFile, checkpoint);
      throw err; // 失敗したら上位層で処理
    }
  }

  return checkpoint;
}
```

このパターンでは、エラーからの再開が自動的になります。失敗したステップだけが再実行され、完了済みのステップは明示的にスキップされます。実システムへの冪等性も確保しやすくなります。

## Agent動作のDebug：構造化ログなしでは盲目状態

AIエージェントの失敗は、一般的なアプリケーションエラーと質が異なります。HTTP 500エラーは「何かが壊れた」という信号ですが、agentが間違った判断を下した場合、返却された値は正しく形成されたJSON・正しいHTTPステータスコードで、一見すると「成功」に見えます。

これを検出するには、agentの「考えたプロセス」そのものをログとして記録する必要があります。

```typescript
// Agentの各決定ステップを構造化ログに記録
interface AgentDecisionLog {
  taskId: string;
  stepNumber: number;
  decision: string;
  reasoning: string;
  toolSelected: string;
  toolArguments: Record<string, unknown>;
  toolResult: unknown;
  expectedOutcome: string;
  actualOutcome: string;
  match: boolean; // 予期した結果と実際の結果が一致したか
  timestamp: number;
}

async function logAgentDecision(
  taskId: string,
  stepNumber: number,
  decision: string,
  reasoning: string,
  tool: { name: string; args: Record<string, unknown> },
  result: unknown,
  expectedOutcome: string
) {
  const actual = String(result);
  const match = actual.includes(expectedOutcome.substring(0, 20)); // 簡易判定

  const log: AgentDecisionLog = {
    taskId,
    stepNumber,
    decision,
    reasoning,
    toolSelected: tool.name,
    toolArguments: tool.args,
    toolResult: result,
    expectedOutcome,
    actualOutcome: actual,
    match,
    timestamp: Date.now(),
  };

  // Append to task-specific log, never delete it
  fs.appendFileSync(
    `./agent-logs/${taskId}.jsonl`,
    JSON.stringify(log) + "\n"
  );

  if (!match) {
    // Mismatch detected: alert immediately, don't wait for task completion
    await notifySlack(
      `Agent decision mismatch in task ${taskId} step ${stepNumber}: ` +
        `expected "${expectedOutcome}" but got "${actual}"`
    );
  }
}
```

このパターンでは、各agentの判断が記録され、予期した結果と実際の結果のズレが即座に検出されます。タスク完了後の監査も可能になり、「なぜこのagentはこの判断を下したのか」という問いに後追いで答えられるようになります。ログの削除もagentプロセス外で厳密に管理できます。

## Cost制御：予測不可能な請求を回避する

Agentは、単発のLLM呼び出しと比較して、トークンやAPI呼び出し数が飛躍的に増加することがあります。Tool使用を繰り返すループが想定以上に長く続いたり、Retry Loopが暴走したり、あるいは見た目では無害な判断が背後で多数のAPI呼び出しを誘発したりします。

結果、月末の請求書を見て驚く、ということになります。

webhaniが採用しているのは、Agent実行前に予算を決め、超過したら即座に中止する仕組みです。

```typescript
// Agent実行のコスト上限を設定・監視
interface CostBudget {
  taskId: string;
  maxSpendUSD: number;
  currentSpendUSD: number;
  tokensUsed: { input: number; output: number };
}

const COST_PER_INPUT_TOKEN = 0.000003; // Claude Haiku相当
const COST_PER_OUTPUT_TOKEN = 0.000015;

async function executeAgentWithCostGuard(
  taskId: string,
  maxBudgetUSD: number,
  agentFn: () => Promise<unknown>
) {
  const budget: CostBudget = {
    taskId,
    maxSpendUSD: maxBudgetUSD,
    currentSpendUSD: 0,
    tokensUsed: { input: 0, output: 0 },
  };

  try {
    // Agentを実行
    // （実装では、LLMの各呼び出しの直後に以下を実行）
    const result = await agentFn();

    // 仮の使用量データ（実際にはLLMレスポンスから取得）
    budget.tokensUsed.input += 2500;
    budget.tokensUsed.output += 1200;

    const spend =
      budget.tokensUsed.input * COST_PER_INPUT_TOKEN +
      budget.tokensUsed.output * COST_PER_OUTPUT_TOKEN;

    budget.currentSpendUSD = spend;

    if (spend > budget.maxSpendUSD) {
      throw new Error(
        `Cost guard exceeded: $${spend.toFixed(4)} > $${maxBudgetUSD}`
      );
    }

    return result;
  } catch (err) {
    // コスト超過で中止した場合、ログに記録
    console.error(`Agent ${taskId} stopped:`, err.message);
    await recordCostExceeded(budget);
    throw err;
  }
}

async function recordCostExceeded(budget: CostBudget) {
  fs.appendFileSync(
    "./cost-overruns.log",
    `${new Date().toISOString()} - Task ${budget.taskId}: ` +
      `$${budget.currentSpendUSD.toFixed(4)} (limit: $${budget.maxSpendUSD})\n`
  );
}
```

このパターンでは、agentの暴走が予算超過で自動的に止まります。月単位の想定コストの10倍というような悲劇を避けられます。

## 信頼性格差はなぜ広がるのか

Temporalの調査が示唆しているのは、AI agentが「試して見る」段階から「依存する」段階へ移行しているということです。試験的な使用なら、State管理も甘く、Debugも事後的で、コストもまぁいいか、という姿勢で済みます。

ですが、実際のCIパイプラインに組み込んだり、複数チームで共用するagent infrastructureを構築したりするとき、これら3つの問題は必然的に表面化します。

成熟したチームとそうでないチームの差は、「agentの精度」ではなく、「agentを本番環境で使う準備ができているか」なのです。

採用率80%を超えたいま、重要なのは、agentの能力そのものではなく、agentをどう運用するかです。State checkpoint、structured logging、cost guard——これらはどれも単純な実装ですが、導入するだけで信頼性の格差を埋める武器になります。
