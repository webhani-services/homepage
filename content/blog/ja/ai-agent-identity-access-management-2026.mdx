## 「誰が」ではなく「どのエージェントが」

Webサービスのアクセス制御を設計するとき、これまでは「人間のユーザー」と「サービスアカウント」の2種類を想定していれば概ね足りました。しかし2026年現在、この前提は崩れつつあります。

業務システムに組み込まれた自律的なAIエージェントが、人間の承認を都度待たずにAPIを呼び出し、データベースを操作し、他のエージェントにタスクを委譲する。こうした構成が一般的になった結果、企業内の非人間アイデンティティ(サービスアカウント、ワークロード、そしてAIエージェント)の数は人間のアカウント数の約50倍に達しているという調査もあります。本稿では、この「エージェントID管理」という新しい課題を、Webhaniが顧客システムを設計する際の視点で整理します。

## 従来のIAMモデルが機能しない理由

従来のID・アクセス管理(IAM)は、次のような前提の上に成り立っていました。

- アイデンティティは長期間安定している(社員のアカウントは年単位で存続する)
- 権限の委譲は明示的で、経路が追跡しやすい
- 「誰が」「いつ」操作したかを1つのアイデンティティに紐づけられる

AIエージェントはこの前提のいずれも崩します。エージェントは数秒から数時間の短命なライフサイクルで生成・破棄されることがあり、あるエージェントが別のエージェントにタスクを委譲し、そのエージェントがさらに別のツールを呼び出す、という多段の委譲が発生します。結果として「誰の権限で、何が実行されたか」を追跡すること自体が難しくなります。

## 2026年に定着しつつある4つのアーキテクチャパターン

現在のエージェントセキュリティの実装では、大きく4つのパターンが使われています。

```text
1. User-delegated(ユーザー委任型)
   エージェントが明示的なユーザーの同意のもとで、そのユーザーとして振る舞う

2. Autonomous(自律型)
   エージェント自身が独自のアイデンティティを持ち、標準的な認可の対象となる

3. Hybrid orchestrated(ハイブリッド編成型)
   1つのエージェントが他のエージェントにタスクを委譲する

4. Scoped impersonation(範囲限定なりすまし型)
   エージェントが特定のスコープに限定してユーザーを代行する
```

どのパターンを選ぶかは、エージェントが何を代行するか、どこまでの権限を持たせるかによって変わります。重要なのは、これらを混在させたまま設計すると、監査時にどの操作がどの権限モデルで実行されたのか判別できなくなる点です。

## 実装時に押さえるべきポイント

Webhaniが顧客のエージェント統合を設計する際、次の点を最初に確認します。

### 1. エージェントを「第一級のアイデンティティ」として扱う

エージェント専用のサービスアカウントを人間のアカウントの延長として扱うのではなく、独自のライフサイクル・権限スコープ・監査ログを持つ主体として定義します。

```yaml
# 概念的な例: エージェント用アイデンティティの最小構成
agent_identity:
  id: "agent-invoice-processor-01"
  type: "autonomous"
  scope:
    - "read:invoices"
    - "write:payment-status"
  lifespan: "ephemeral"      # セッション終了時に失効
  delegated_by: null          # 自律型なので委任元なし
  audit_trail: true
```

### 2. 委任の連鎖を可視化する

エージェントAがエージェントBにタスクを委譲する場合、その委譲関係をログに残さなければ、後からインシデントを追跡できません。委譲のたびに「誰が、誰に、何の権限を、いつまで」渡したのかを記録する設計が必須です。

### 3. スコープは最小権限、かつ有効期限つきで

人間のAPIキーであれば「とりあえず広めの権限を与えて後で絞る」運用が許容される場面もありますが、エージェントは人間より高頻度・高速に操作を実行するため、過剰な権限のリスクは相対的に大きくなります。短命なトークンとタスク単位のスコープを組み合わせるのが基本方針です。

## Webhaniの見解

エージェントID管理は、まだベンダーごとに実装パターンが分かれている発展途上の領域です。Microsoft Entra Agent IDのような大手プラットフォームのネイティブ機能から、Aembitのような専業ベンダーのIAMブローカーまで、選択肢は増えています。しかし共通する原則は変わりません。「エージェントを人間の延長として扱わない」「委任の連鎖を追跡可能にする」「権限を短命かつ最小に保つ」という3点です。

新しいベンダー製品を導入する前に、まず自社のエージェント運用がどのアーキテクチャパターンに該当するのかを整理することを、Webhaniでは推奨しています。パターンが曖昧なまま製品を選定すると、後から権限モデルの作り直しが必要になるケースが少なくありません。

## まとめ

AIエージェントの導入が進むほど、「誰が操作したか」を追跡する仕組みの重要性は増していきます。エージェントIDの設計は、後付けで直せる部分と、最初に決めておかないと手戻りが大きい部分が混在する領域です。Webhaniでは、エージェント統合を検討する顧客に対し、機能実装と同時にID・アクセス管理の設計を最初のフェーズに組み込むことを提案しています。
