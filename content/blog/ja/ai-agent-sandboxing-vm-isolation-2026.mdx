## 無人で書かれるコードの割合が増えている

Sonarの2026 State of Code Developer Surveyによると、回答者がコミットしたコードのうちAI生成・AI支援によるものは42%に達し、チームは2027年までにこの割合が65%まで上がると見込んでいます。この数字が示しているのは、多くのエンジニアリングチームがすでに肌で感じている変化です。エージェントはもはや1行を補完するだけの存在ではなく、関数を書き、それを支えるために依存パッケージをインストールし、テストスイートを実行し、繰り返し改善する — その大部分を、人間が途中の一つひとつを読まないまま行っています。

この変化こそが、クラウドネイティブ基盤のプロバイダーを、エージェントの実行を単純なコンテナではなくVMレベルの隔離で包む方向へ押しているものです。CIジョブやビルドパイプラインには十年間十分だった境界が、なぜエージェントには急に不十分になったのか、具体的に見ていく価値があります。

## コンテナは既知で静的なワークロードを前提にしている

標準的なコンテナのセキュリティモデルは、事情をよく理解した上で能動的に適応していくプロセスを止めるようには本質的に作られていません。コンテナの隔離（Namespace、cgroups、共有カーネル）はコストと密度に優れ、作者が想定した通りに振る舞うワークロードを封じ込めるのには向いています。しかし、ドキュメントを読み、設定ミスに気づき、想定された範囲外の何かをインストールしてみようと「判断する」プロセスに対する堅牢な境界として設計されたことは一度もありません。

これは自律的なコーディングエージェントが本質的に行うことの正確な描写です。明示的に指示されていないコマンドを実行し、事前承認されていないパッケージをインストールし、自分の置かれた状況を把握するためにファイルを読む — これらはまさに、そのエージェントを有用にしている振る舞いでもあります。壊れたビルドから自力で抜け出せる適応力と、「コンテナの境界を信頼する」という前提を以前より弱くしているものは、同じ性質から来ています。

## VMレベルの隔離が実際に加えるもの

現在進んでいる変化は、特定のエージェントへの不信感の話ではなく、ワークロードが自力でできることの範囲に隔離境界を合わせる話です。VMレベルの境界（実際のHypervisorに支えられたSandbox、あるいはFirecrackerのようなmicroVM方式）は次のものをもたらします。

- **ワークロードごとに独立したKernel** — コンテナ隔離が本来完全に塞ぐことを意図していなかった、共有Kernel経由の脱出経路を閉じます。
- **ワークロードの振る舞いに依存しないResourceとNetworkの境界** — コンテナのcgroups制限はKernelによって強制されるとはいえ協調的な性質を持ちますが、VMの境界はワークロードが行儀よく振る舞うことを前提にしなくても保たれます。
- **Sandbox内で止まる影響範囲** — これはエージェントの行動（パッケージのインストール、シェルコマンド、ファイル書き込み）が動的であり、CIジョブのステップのように事前に宣言されるのではなく事後にしか全容が分からない、という点で特に重要です。

## 実際の設定はこう見える

エージェント駆動のコード生成やビルドステップを運用しているクライアントに現時点で推奨するパターンです。

```yaml
# エージェント実行ステップに対する概念的なサンドボックスポリシー
sandbox:
  isolation: microvm       # Hypervisorに支えられた隔離、共有Kernelではない
  network:
    egress: allowlist      # パッケージレジストリのみ許可、任意の外向き通信は不可
  filesystem:
    scope: ephemeral        # タスク終了後にワークスペースを破棄
  resource_limits:
    cpu: "2"
    memory: "4Gi"
    timeout: "15m"
  audit:
    log_commands: true
    log_network: true
```

上記のYAMLはあくまで例示であり、特定製品の仕様ではありません。重要なのはポリシーの形です。厳格な送信許可リスト、一時的なファイルシステム、明確なリソース上限、コマンド・ネットワークの完全なログ記録 — これらはインシデントの後に追加するものではなく、最初から必要なものとして前提にすべきです。CNCFがCertified Kubernetes AI Conformance Programに向けて進めている取り組みも同じ方向を指しています。AI/MLワークロード、そして今後増えていくエージェント型ワークロードをクラスタ基盤の中でどう動かすべきかを標準化し、各チームが独自の境界をその場しのぎで作る状態から脱却しようとしています。

## 実際のチームにとっての意味

多くのエンジニアリング組織にとって実務上の問いは、エージェントにパッケージのインストールやシェルコマンドの実行を許すかどうかではありません — その能力こそがエージェントの価値の大部分だからです。問いは、そうした行動がどこで許されるべきか、そしてミスや本当に悪意あるパッケージがそこからどこまで到達しうるか、という点です。

具体的な推奨事項をいくつか挙げます。

1. **本番の認証情報を保持する基盤の中でエージェント駆動のビルドを絶対に実行しない**：エージェントのSandboxとデプロイパイプラインのSecretsが同じ境界を共有しているなら、そのSandboxは無意味になっています。
2. **Taskレベルだけでなく、コマンドとネットワークのレベルでログを取る**：「エージェントがビルドを実行した」は事後には役に立ちません。「エージェントが `pip install X` を実行し、その後Yへ3回の送信通信を行った」であれば意味があります。
3. **パッケージのインストールを日常的な作業ではなく、エージェントが行う中で最もリスクの高い行為として扱う**：エージェントが未レビューの依存関係をインストールして持ち込むサプライチェーンの問題は、人間が持ち込んだ場合と機能的に同一であり、同じレビューゲートが必要です。

## Webhaniの見解

コンテナの隔離は、振る舞いがおおむね事前に分かっているワークロードのために作られたものです。エージェント型のワークロードは、その前提を設計上崩します。エージェントの価値とはまさに、直前に見つけたものに基づいて次に何を実行するかを自分で判断できることにあるからです。決定論的なCIジョブ向けに作られたのと同じ隔離モデルでエージェントを包む基盤は、その種の適応力に対して元々耐えるように設計されていない境界を信頼していることになります。

エージェント向けのVMレベルSandboxへの現在の動きは、任意のハードニング策としてではなく、エージェントが自らの依存関係をインストールしたり、明示的にスクリプト化されていないコマンドを実行したりするあらゆる環境における基本構成として扱うべきだと考えます。エージェント型コーディングの利便性は本物です。同時に、それが隔離境界に求められる「止められるべきもの」の中身を変えてしまっているのも事実です。
