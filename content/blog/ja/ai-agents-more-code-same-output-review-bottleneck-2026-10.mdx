今週、700社超を対象にAIコーディングエージェント導入前後を比較した調査が話題になっています。私たちが確認できたのは二次情報のみで（一次の論文には環境上アクセスできませんでした）、数値は目安として見てください。報道によると、commitは約20%、PRは約23%増えた一方、Jiraのissue/epic解決率はほとんど変わっていません。別の報告では、導入企業の一部でPRのマージ時間が約5割伸びたとも言われています。データは2026年3月までとのことです。

個々の数字を保証はできませんが、傾向自体はお客様のプロジェクトで見ているものと一致します。エージェントによって「書く」コストは下がり、そのコストは別の場所に移ります。

## コストはどこへ移るのか

変更は、誰かが理解し、検証し、マージして初めて「届いた」ことになります。エージェントは変更の流入量を増やしますが、承認できる人の数は増やしません。結果として次のことが起こります。

1. **レビュー待ちが増える。** レビュアー1人あたりのPRが増え、1本あたりのサイズも手書きより大きくなりがちです。
2. **負荷の中でレビューの質が下がる。** 流し読みになり、「テストが通っているから」で承認されます。
3. **手戻りが増える。** 一見もっともらしいが要件を取り違えたコードが、修正PRとして戻ってきます。PR数は増えても、issueは閉じません。

commitやPRの数で成果を測ると、これらはすべて「進捗」に見えます。issueの解決数で測ると、何も進んでいないように見えます。

## 測る対象を変える

プロセスを変える前に、追う指標を変えます。リポジトリごとに、Gitホストから次の4つを取ることをお勧めします。

- PRのopenからmergeまでの時間（中央値と90パーセンタイル）
- PRのサイズ（変更行数、変更ファイル数）
- レビュー待ち時間（openから最初のレビューまで）
- 再修正率（先行PRの修正として出されたPRの割合）

GitHub CLIを使えば、最小限のスクリプトでベースラインが取れます。

```bash
gh pr list --state merged --limit 200 \
  --json number,createdAt,mergedAt,additions,deletions \
  | jq -r '.[] |
      [.number,
       ((.mergedAt|fromdateiso8601) - (.createdAt|fromdateiso8601))/3600,
       (.additions + .deletions)] | @csv'
```

エージェント導入前と導入後で比較し、マージまでの時間の中央値とPRサイズの両方が伸びていれば、上記のパターンに当てはまります。

## 効果のある調整

**PRサイズに上限を設ける（エージェントにも）。** `CLAUDE.md`や`AGENTS.md`などの指示に、1PR1関心事、変更は数百行以内を目安、超える場合は分割、と書きます。レビュー容量を増やす施策として、最も低コストです。

**レビューの補助資料をエージェントに書かせる。** 意図、重要なファイル、リスクのある箇所を明記したPR説明を作らせます。見るべき場所が分かっていれば、レビュアーが変更を再発見する時間が減ります。

**機械的なチェックは人のレビューから外す。** 型チェック、lint、フォーマット、依存関係ポリシー、シークレットスキャンはCIの仕事です。人の注意は、設計、要件との整合、セキュリティ上重要な箇所に使います。

```yaml
# .github/workflows/pr-checks.yml (抜粋)
jobs:
  checks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run lint
      - run: npx tsc --noEmit
      - run: npm test -- --coverage
```

**着手前にissueと紐付ける。** 手戻りは、レビューで拾うより防ぐ方が安く済みます。受け入れ条件のあるissueを必須にし、そのテキストをエージェントへのタスクとして渡します。曖昧な指示からは、もっともらしいがずれた変更が出てきます。

**レビュー時間を明示的に確保する。** エージェントを導入するなら、会議と同じようにレビューの時間をカレンダーに取ります。そうしないと、真っ先に後回しになります。

## やらないほうがよいこと

別のエージェントに最初のエージェントのPRを承認させるのは、null checkの漏れなどを拾う助けにはなりますが、要件を理解した人間の代わりにはなりません。私たちは自動レビューを、人間が見るリストを短くするフィルターとして扱い、承認者とはしていません。

また「エンジニア1人あたりのPR数を3割増やす」といった目標も置きません。調査が示唆する「出荷価値につながっていない行動」を、そのまま評価することになるからです。

## まとめ

コーディングエージェントの導入は、生成容量への投資です。次にぶつかる制約は、多くのチームでレビューと統合の容量です。commit数ではなくマージ時間と解決率を測り、PRを小さく保ち、機械的なチェックをCIに寄せ、レビュアーの時間を意図的に確保してください。ベースラインの計測やリポジトリ向けのエージェント指示の調整が必要でしたら、私たちが日常的にお手伝いしている領域ですので、お気軽にご相談ください。
