## 「テストスクリプトなしでバグを見つける」という話題

ここ数か月、クライアントから同じような質問を何度か受けています。「AIエージェントがテストスクリプトなしでアプリを勝手にクリックしてバグを見つけるデモを見た。自分たちのPlaywrightスイートの代わりにこれを使うべきか」というものです。

結論から言うと、「代わりに」ではありません。ただ、このカテゴリー自体は本物で、何を置き換え何を置き換えないのかを整理しておく価値はあります。過剰な期待も、逆に頭ごなしの否定も、どちらも避けたいところです。

自律探索型テストエージェントとは、事前に書かれたスクリプトに従うのではなく、Webやデスクトップアプリケーションを自分で操作しながら探索するAIエージェントです。ボタンをクリックし、フォームに入力し、リンクをたどり、状態遷移を発生させながら、アプリケーションの構造を自分なりに理解していきます。「必須項目が空のままモーダルがアニメーション中に送信ボタンを押したらどうなるか」といったテストケースは誰も書いていません。エージェントが自分でそのパスを見つけたのです。

これは既存のスクリプトテストとは根本的に動作モードが違います。何が本当に新しいのかを具体的に見ていきます。

## PlaywrightやCypressのスクリプトと何が構造的に違うのか

どんなに丁寧に書かれたE2Eスクリプトでも、決まった経路をたどります。`/checkout`に遷移し、フィールドAを入力し、ボタンBをクリックし、Cをアサートする。この経路はスクリプトの作者が事前に決めたものです。入力が同じなら手順もアサーションも毎回同じ、つまり決定的（deterministic）です。これはリグレッションのゲートとして必要な性質そのものです。

一方、探索型エージェントは次のような動きをします。

```
loop:
  現在のページ状態を観察する（DOM / アクセシビリティツリー / スクリーンショット）
  可能なアクションを推測する（クリック可能な要素、フォームフィールド、ナビゲーション）
  「既視感があるか」「意味がありそうか」でアクションに優先順位をつける
  アクションを選んで実行する
  新しい状態を記録し、異常（エラー、コンソール警告、レイアウト崩れ、行き止まり）をメモする
  アプリの内部マップを更新する
```

固定スクリプトは存在せず、「テスト」はエージェントが持つアプリケーションのモデルから実行時に生成されます。しかもこのモデルは、エージェントが探索する枝によって毎回変わります。これはPlaywrightのspecを書くQAエンジニアというより、バグバッシュ中の人間の探索的テスターに近い動き方です。エージェントはテスト計画を高速実行しているのではなく、その場でテスト計画そのものを組み立てています。だからこそ、誰も書き留めなかった経路――二重送信によるレース条件、ブラウザバック後の孤立した状態、絵文字を受け付けてしまう数値フィールドが後段の計算を壊すケースなど――に偶然たどり着くことができます。

## どこで本当に役立つのか

最も強い使いどころは「カバレッジの証明」ではなく「カバレッジの発見」です。具体的には次の3つです。

- **新規または変化の速いUI。** 機能をリリースしたばかりでテスト作成のバックログが追いついていない状況。誰かがスクリプトを書く時間ができるまで自動カバレッジゼロで出荷するより、ステージング環境への探索パスを走らせれば、当日中に明らかな不具合を洗い出せます。
- **不慣れなコードベース。** テストの履歴がほとんど残っていないクライアントのレガシーアプリを引き継いだとき、探索エージェントを数時間走らせるだけで、人間が手作業でクリックして回るより早く「どこが脆いか」の初期マップが得られます。
- **誰も書き留めなかったエッジケース。** スクリプトテストは作者が想定した範囲しかチェックしません。「送信を素早く二回クリックしたらどうなるか」「フロー途中でビューポートをリサイズしたらどうなるか」を試すエージェントは、そもそも計画に載らなかった種類のバグを拾い上げます。

共通しているのは、いずれも「何をテストすべきかを決める」ことがボトルネックになっている状況だという点です。

## 決定的なテストの代わりにはならない部分

デモではあまり触れられない部分なので、はっきり書いておきます。

**コンプライアンス・監査のエビデンス。** 「ユーザーがXをしたときシステムが正確にYを行うことを、この日付で検証した」という証拠が規制当局や監査人に必要な場合、決まったアサーションを持つバージョン管理された決定的テストが必要です。毎回異なる経路をたどる設計のエージェントの探索ログでは代替できません。

**ビジネスロジックに紐づく精密なリグレッションアサーション。** 「請求書の合計が、明細の合計＋税金－割引にセントの単位まで一致しているか」は、正しさの定義を明示的に与えない限り、探索エージェントが確実にチェックできる項目ではありません。探索エージェントはページがエラーを吐いた、あるいは見た目が明らかに崩れたことに気づくのは得意ですが、特定の数値出力が特定の期待値と一致するかを確認するのはかなり苦手です。

**CIゲートに必要な決定的な再現性。** CIゲートは毎回同じ基準で高速かつ予測可能にpass/failを返す必要があります。実行のたびに経路が変わるエージェントは、安定したグリーン/レッドのシグナルを返せませんし、マージをブロックするゲートには許されない遅さや非決定性を持ち込みます。

要するに、探索エージェントは問題を「見つける」のは得意ですが、正しさを「証明する」ためのシステム・オブ・レコードとしては、現時点では力不足です。この二つを混同することが、導入後に躓く原因になります。

## 現実的な統合パターン

我々が推奨するのは、この2つのレイヤーを分離し、それぞれの得意分野に専念させるパターンです。

1. **決定的なスイート（Playwright、Vitestなど）をCIゲートの本体として維持する。** すべてのPRで実行され、マージをブロックし、アサーションは既知のビジネス要件に直接対応します。探索型エージェントを導入しても、ここには一切手を加えません。
2. **探索エージェントは別枠の非ブロッキングな発見ジョブとして走らせる。** 夜間バッチや、リリース前にステージング環境に対して実行するイメージです。
3. **見つかった問題は「信頼」ではなく「トリアージ」する。** エージェントが検出したものはすべて再現手順つきのチケットになり、人間がレビューしてから対応します。再現性が確認できたものは、スクリプト化されたリグレッションテストの候補となり、決定的スイートに組み込むことで同じバグが静かに再発するのを防ぎます。

パイプラインの配線イメージはこうなります。

```yaml
# .github/workflows/ci.yml — ブロッキングゲート、変更なし
on: [pull_request]
jobs:
  test:
    steps:
      - run: npm run test:unit
      - run: npx playwright test   # 決定的、マージにはパス必須

# .github/workflows/nightly-discovery.yml — 別枠、非ブロッキング
on:
  schedule:
    - cron: "0 3 * * *"
jobs:
  explore:
    steps:
      - run: deploy-to-staging
      - run: run-exploratory-agent --target https://staging.example.com
      - run: create-tickets-from-findings --require-human-review
```

発見ジョブはマージをブロックしません。バックログに知見を供給し、人間がレビューして再現性が確認されたものだけが、時間をかけて決定的スイートに昇格していきます。探索エージェントは、既存のテストを置き換えるのではなく、新しいテストケースの供給源になるわけです。

## はっきり言っておきたいリスク

**「カバレッジ完全」という誤った安心感。** エージェントの探索レポートは、数十ページを訪問し、数百のインタラクションを記録したように見え、一見すると網羅的に見えます。しかし、あなたが本当に気にしているビジネスクリティカルな経路を一度も通過していない可能性があります。「エージェントが2時間探索して何も見つからなかった」ことと「決済フローが正しく動作する」ことは同じ主張ではなく、同一視するとギャップに気づかないまま進んでしまいます。

**非決定性によるバグ再現の難しさ。** エージェントが動的に生成した経路上でバグを踏んだ場合、開発者がデバッグするためにその経路を後から正確に再現するには、エージェント側の丁寧なセッション・アクションログが必要です。それがなければ、「昨夜エージェントがバグを見つけた」は再現不能なバグ報告になり、報告がない状態より扱いにくくなります。

**エージェントの検出結果は人間のレビューを経てから信頼する。** エージェントは、意図されたローディング状態やアニメーション、標準的でないが正しいUIパターンを不具合と誤判定することがあります。トリアージ工程を挟まずにエージェントの検出結果をそのままチケットキューに流し込むと、数週間でツールへの信頼が失われます。

## webhaniとしての見解

既存のQAプロセスに新しいツールを導入するときと同じアドバイスになりますが、置き換えではなく「追加」として試すことを勧めます。まずステージング環境を一つ選び、探索エージェントを数週間、夜間ジョブとして走らせてください。そして2つを計測します。既存のスイートと手動QAが見逃していた、本当に新しい再現可能な問題をいくつ見つけたか。そして、その結果をトリアージするために自分たちのチームがどれだけの工数を割いたか。シグナル対ノイズ比が見合うようならリリースチェックリストに組み込み、見合わないなら数週間のバックグラウンドジョブを失っただけで、CIゲートには何の影響もありません。

このカテゴリーは注目に値し、適切な使いどころでは導入する価値もあります。ただし、それは「何を見落としているか分からないものを見つける」ためのツールであり、「すでに真であるべきことを証明する」ための代替手段ではありません。
