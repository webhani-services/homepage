## 使っているが、信じていない

Sonarが発表した2026年のState of Code Developer Surveyによると、回答者がコミットしたコードのうち42%がAI生成またはAI支援によるものでした。一方で、AIコーディングツールの出力を信頼していると答えた開発者は29%に過ぎません。数字だけを見ると矛盾しているように感じますが、現場の感覚としては違和感がありません。「使わざるを得ないが、目を離せない」というのが実態に近いはずです。

この記事では、この「利用率と信頼度の乖離」がなぜ生まれるのか、そしてWebhaniが顧客のAI導入支援で実際に組んでいるレビュー体制について、具体的な仕組みとあわせて紹介します。

## なぜギャップが生まれるのか

原因は技術的な精度の問題だけではありません。むしろ運用上の3つの要因が大きいと考えています。

1. **生成速度とレビュー速度の非対称性**: AIはコードを瞬時に生成しますが、人間のレビュアーが内容を理解して妥当性を判断する速度は変わりません。生成量が増えるほど、レビューが追いつかなくなります。
2. **「動く」と「正しい」の混同**: AIが生成したコードはテストを通過することが多く、一見問題なく見えます。しかし、要件の解釈違いや境界条件の見落としは、テストが通っていても残ります。
3. **説明責任の所在の曖昧さ**: AIが書いたコードに不具合が出たとき、「なぜこの実装になったのか」を説明できる人が誰もいない状態が起きがちです。

## 実務的なレビュー体制の設計

Webhaniでは、AI支援コードのレビューを「通常のPRレビューの延長」として扱うのではなく、専用のチェックポイントを追加することを勧めています。

### 1. 生成コードにはコンテキストを添付させる

PRの説明欄に、AIへの指示内容と、AIが採用しなかった選択肢を残すルールを設けます。

```text
## AI生成コードの場合、PR descriptionに以下を含める

- 使用したツール/モデル (例: Claude Code, GitHub Copilot)
- 与えたプロンプトの要旨
- 生成された実装のうち、人間が手直しした箇所
- レビュアーが特に確認すべき懸念点（あれば）
```

これにより、レビュアーは「何が自動生成され、何が人間の判断で修正されたか」を切り分けて確認できます。

### 2. 境界条件とエラーハンドリングを優先的にレビューする

AIは典型的なユースケース(happy path)の実装は得意ですが、業務固有の例外処理や境界条件は見落としがちです。レビューの優先順位を明確にするため、以下のようなチェックリストを使います。

```text
□ 空配列・null・undefinedの入力は考慮されているか
□ 外部APIのタイムアウト・エラーレスポンスは処理されているか
□ 権限チェックが実装から漏れていないか
□ ビジネスロジックが要件と1対1で対応しているか(過不足がないか)
```

### 3. 「なぜこの実装か」を説明できる状態を保つ

コードの提出者（AIを使った人間）が、実装の意図を自分の言葉で説明できることを、レビュー通過の条件にします。AIが生成したコードをそのまま貼り付けただけの状態では、障害対応時に誰も原因を追えなくなるリスクがあります。

## 信頼度を上げるための計測

Webhaniでは、レビュー体制の効果を感覚ではなく数値で追うことを推奨しています。具体的には次の指標を継続的に記録します。

- AI支援コードのPRにおける、レビュー後の修正コミット数（多いほど生成品質に課題がある可能性）
- AI支援コードに起因する本番障害の件数と、非AI支援コードとの比較
- レビューにかかる平均時間（AI支援コードとそうでないコードの差）

これらの指標を3〜6ヶ月単位で追うことで、「どのような種類のタスクならAIに任せて問題ないか」という判断基準がチーム内に蓄積されていきます。

## まとめ

AI生成コードの利用率が上がる一方で信頼度が伸び悩んでいるのは、AIの性能の問題というより、レビュー体制がAI時代に最適化されていないことが大きな要因です。生成速度に見合ったレビューの仕組みを整え、境界条件や説明責任を明示的にチェックポイント化することで、このギャップは着実に縮められます。Webhaniでは、こうしたレビュー体制の設計から導入支援まで、顧客のAIコーディング活用を伴走しています。
