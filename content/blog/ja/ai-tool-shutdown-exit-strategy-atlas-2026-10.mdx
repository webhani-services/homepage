2026年7月、OpenAI は ChatGPT Atlas ブラウザの終了を発表しました。報道によると提供終了は8月9日で、公開から1年足らずでした。機能は ChatGPT のデスクトップアプリに統合され、利用者にはデータ移行の案内が出されました。報道では、OpenAI の製品ラインの整理という文脈でも語られています。

これは一社だけの話ではありません。AI プロダクトは数か月単位で登場し、統合され、終了していきます。チームの習慣やスクリプト、顧客向け機能がそうしたプロダクトの上に乗っているなら、問うべきは「使っているものが変わるかどうか」ではなく、「変わったときにどれだけコストがかかるか」です。

## 本当の依存はどこにあるか

ロックインというとモデル API を思い浮かべがちですが、実際の案件で痛みが出るのは別の場所です。

- **業務フローへの依存。** 担当者が特定ツールの UI やショートカットに頼っていて、作業そのものの手順書がありません。
- **データへの依存。** 会話履歴、保存したプロンプト、メモリ、カスタム指示が、プロダクトの中にしかありません。
- **連携への依存。** 社内スクリプトが、ドキュメントのない（またはベータの）エンドポイントを呼んでいます。
- **知識への依存。** そのツールが無かった頃に「良い出力」がどういうものだったのか、誰も説明できません。

モデルの差し替えは多くの場合、いちばん簡単なケースです。プロダクトの終了は、残り4つに直撃します。

## 依存台帳を持つ

お客様には、利用中の AI プロダクトを短い台帳にまとめることをお勧めしています。リポジトリ内の YAML ファイルで十分です。

```yaml
- name: browser-agent-tool
  owner: platform-team
  used_for: "競合の価格チェック（週次）"
  maturity: beta            # ga | beta | preview
  data_held: [history, saved-tasks]
  export_path: "手動コピーのみ"
  replacement: "playwright スクリプト + 任意の LLM API"
  last_reviewed: 2026-10-26
```

重要なのは `maturity`、`export_path`、`replacement` の3項目です。`export_path` が「手動コピーのみ」で `maturity` が beta なら、リスクが目に見える形で順位付けできます。`replacement` が埋められないなら、そこが最初に取り組む対象です。

## コードとツールの間にインターフェースを置く

コードから呼ぶものは、ベンダーを自前のインターフェースで包みます。抽象化のための抽象化ではなく、ベンダーが機能を終了した日に、変更が1ファイルで済むようにするためです。

```ts
export interface PageReader {
  fetchText(url: string, signal?: AbortSignal): Promise<string>;
}

export class PlaywrightReader implements PageReader {
  async fetchText(url: string, signal?: AbortSignal) {
    // ブラウザを起動し、遷移して、表示テキストを返す
    throw new Error("implement with your browser automation of choice");
  }
}

// 呼び出し側は PageReader にだけ依存し、ベンダー SDK には依存しない
export async function priceSnapshot(reader: PageReader, url: string) {
  const text = await reader.fetchText(url);
  return { url, length: text.length, capturedAt: new Date().toISOString() };
}
```

呼び出し側が見るのは `PageReader` だけです。ベンダーのエージェントで実装するか、ヘッドレスブラウザか、テストのフィクスチャかは実装の詳細です。

## ツールではなく、作業そのものを書き残す

最も役に立つ成果物は、平易な言葉の手順書です。入力は何か、どんな手順か、正しい結果とは何か、そして例を3つ。これがあれば、ツールの乗り換えは設定変更と例の再実行で済みます。なければ、障害の最中に自分たちの業務をリバースエンジニアリングすることになります。

## 四半期ごとの見直し

台帳の各項目について、四半期に一度、次を確認します。

1. そのプロダクトはベンダーのロードマップに残っているか。噂ではなく公式発表で確認します。
2. 今日、データをエクスポートできるか。実際に試します。
3. 代替手段は今も動くか。保存した例で実行します。
4. ベータのまま重要になったものはないか。サポートされた経路に移すか、リスクを文書で受容します。

## webhani の推奨

探索目的なら、新しい AI プロダクトは自由に使って構いません。週次業務や顧客向けフローの一部になった時点で、もう少し厳しくします。インターフェースを前に置き、エクスポート経路を確保し、作業を文書にしておきます。かかるのは最初の数時間だけです。その結果、終了のお知らせが「障害」ではなく「チケット」になります。
