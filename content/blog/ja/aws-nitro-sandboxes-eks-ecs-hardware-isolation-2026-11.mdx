2026年11月9日、AWS は Nitro Sandboxes を発表しました。EKS の Pod、ECS の Task、EC2 のワークロードを、それぞれ専用カーネルを持つハードウェア分離の VM 内で実行できます。発表と二次情報によると、AWS が Nitro Enclaves として長年運用してきた分離技術を再利用しており、商用リージョンのほとんどの Nitro ベース EC2 インスタンスで利用でき、追加料金はありません。

コンテナはホストのカーネルを共有します。これが密度と起動速度の源泉である一方、カーネルの脆弱性やコンテナエスケープがワークロード間の境界を越えうる理由でもあります。Nitro Sandboxes は、その境界を VM レベルまで下げつつ、自前で microVM 基盤を運用する必要をなくします。

## 何が変わるのか

サンドボックスなしの場合、同じノード上の 2 つの Pod を分けているのは、Namespace、cgroup、seccomp、そして Admission ポリシーです。Pod ごとに VM があれば、コンテナからエスケープしても到達するのはその VM のゲストカーネルであり、ノードのカーネルや隣の Pod ではありません。

AWS の説明では、起動の速さを優先するモードと、暗号学的な Attestation に対応する Confidential モードの 2 種類があります。ただし Attestation は、誰かが検証して初めて意味を持ちます。報道では、Attested な測定値を検証する Verifier や、検証後にのみシークレットを渡す KMS ポリシーを自分で用意する必要があるとされています。それが整うまでは、「Confidential」を「検証済み」と同一視しないでください。

## 誰にとって重要か

**マルチテナント基盤。** 顧客のコードを実行する、あるいはテナント間でクラスターを共有する場合、カーネル共有は分離設計で最も弱い部分です。従来の選択肢は、テナントごとのノードプール(コストが高い)か、Kata Containers や gVisor の自前運用でした。

**AI エージェント・コード実行系。** モデルが生成したコード、ビルドツール、ブラウザを動かすエージェントは典型的な適用先です。エージェントの VM レベル分離については当ブログの過去記事でも触れました。AWS 上であれば、その選択肢がマネージド機能として使えるようになります。

**コンプライアンス要件のあるワークロード。** 異なるデータ区分を扱うワークロードをどう分離しているかを監査で問われたとき、VM 境界はポリシーの束より説明しやすい答えです。

信頼できる自社コードだけを動かす単一テナントの内部サービスでは、追加の境界から得られるものは小さめです。まずはパッチ適用と最小権限に労力を使うほうが効果的です。

## Kata Containers との比較

発表時の報道では Kata Containers と比較されています。実務で効く違いは次のとおりです。

| | Nitro Sandboxes | Kata Containers |
|---|---|---|
| 運用 | AWS(マネージド) | 自社 |
| 仮想化バックエンド | Nitro のみ | 複数(QEMU、Cloud Hypervisor、Firecracker) |
| 可搬性 | AWS のみ | 任意のクラウド/ベアメタル |
| Attestation | 組み込み(Confidential モード)、Verifier が必要 | バックエンドとハードウェア次第 |

マルチクラウドやオンプレが一部にある場合、Kata なら環境をまたいで単一の分離モデルを保てます。AWS のみであれば、マネージドのほうがプラットフォームエンジニアリングの一層分を減らせます。どちらも合理的な選択で、問うべきはロックインのコストを意識的に判断したかどうかです。

## まだ分かっていないこと

報じられた範囲では、ベンチマーク値、起動時間、インスタンスあたりの密度は示されていません。レイテンシに敏感なワークロードやビンパッキングが重要なワークロードでは、これらの数値が採用可否を決めます。実装が軽量でも、Pod ごとの VM にはメモリオーバーヘッドとコールドスタートのコストが伴います。

また、対象外のインスタンスタイプや Attestation の仕組みの詳細も、確認できた報道では明確ではありません。移行を計画する前に、AWS のドキュメントで最新の一覧を確認してください。

## 私たちならこう評価します

全面展開ではなく、範囲を絞ったパイロットを勧めます。

1. **分離が重要なワークロードを 1 種類選ぶ。** エージェントのランナー、ビルド実行基盤、テナント向けジョブなどです。
2. **計測する。** 現状と比べて、Pod の起動時間(p50/p95)、Pod あたりのメモリオーバーヘッド、ノードあたりの Pod 数を測ります。
3. **運用互換性を確認する。** サイドカー、CSI ボリューム、GPU、ホストネットワーク、eBPF ベースのツール、ノードレベルの監視エージェントは、Pod が独自カーネルを持つと挙動が変わることがあります。依存しているものを一つずつ試します。
4. **Attestation の方針を決める。** Confidential モードを使うなら、誰が測定値を検証し、成功時に何を渡すのかを定義します。
5. **ほかの統制は維持する。** VM 境界は、Service Account 用の最小権限 IAM ロール、ネットワークポリシー、Egress 制限の代わりにはなりません。広すぎる IAM ロールを持つサンドボックス内の Pod は、正規の認証情報で被害を出せます。

Kubernetes 側では、専用のノードプールと、サンドボックス対象のワークロードを選ぶ `RuntimeClass` 相当のセレクターを用意しておくと、Namespace 単位で段階的に移行できます。正確なリソース名は、変更の可能性があるため AWS のドキュメントに従ってください。

## まとめ

- Nitro Sandboxes は、Pod/Task 単位の VM 分離を AWS のマネージド機能として提供します。AWS によれば追加料金はありません。
- マルチテナント基盤、信頼できないコードやモデル生成コード、コンプライアンス上の分離で特に効果があります。
- 性能データと Attestation の詳細が未公開のため、採用前にパイロットと計測が必要です。
- IAM のスコープ設定、ネットワークポリシー、パッチ適用を置き換えるものではなく、補完するものです。
