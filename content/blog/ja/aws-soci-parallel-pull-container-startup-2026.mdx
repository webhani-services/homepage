## 見落とされがちなボトルネック

Autoscalingの遅延を見積もるとき、多くの人はスケジューラの判断やreadiness probe、JITのウォームアップに注目します。しかし実際には、モデルの重みや大きなML依存関係をバンドルしたコンテナイメージでは、Imageのpullとunpackだけで起動時間全体の75%以上を占めることが珍しくありません。5〜10GB級の推論用Imageをコールドノードで動かすと、コンテナプロセスが立ち上がるまでに数分かかることもあります。

AWSのSeekable OCI（SOCI）Snapshotterは、以前からlazy loadingでこの問題の一部に対処してきました。Image全体をダウンロードし終える前に、実際に使うLayerだけを先にPullしてコンテナを起動できる仕組みです。今回のParallel Pullモードは、その先の部分に踏み込んだ改善です。しかも今回は、アンパック処理そのものをcontainerd本体にアップストリームコントリビュートしているため、恩恵はEKSに限定されません。

## Parallel Pullモードで何が変わったか

SOCIはImageのLayer内容をIndex化しておくことで、Layer全体をダウンロードしなくてもどのファイルがどのChunkにあるかをSnapshotterが把握できる仕組みです。Parallel Pullモードは、このIndexを土台に2つの並列化を行います。

1. **Chunkの並列ダウンロード** — 単一コネクションでLayerを順番にPullするのではなく、複数のChunkを別々のコネクションで同時にダウンロードします。
2. **並列アンパック** — これまでダウンロード後に直列で行っていた展開・ファイルシステムへの書き込みを、残りのダウンロードと並行して進めます。

アンパック処理の部分はcontainerdのコア機能としてアップストリームにマージされたため、AWS専用パッチではありません。リリースされたバージョンにこの機能が入れば、SOCIを使っているEKSユーザーに限らず、containerdベースのランタイム全般が恩恵を受けます。

これらを組み合わせることで、AWSはモデルファイルを含む大容量コンテナで起動時間を約60%短縮できたと報告しています。Imageサイズが大きいほど効果が大きいカテゴリなので、まさに刺さる場面です。

## EKSでの有効化

SOCIはクラスタ単位ではなくノードグループ単位で有効化できます。これは実務上ありがたいポイントで、大容量Imageを実際に動かすノードグループ（推論用、バッチML用など）だけを対象にPilot導入し、他には影響を与えずに検証できます。

```hcl
# 例: EKS Managed Node GroupでSOCI Snapshotterを有効化する（Terraform）
resource "aws_eks_node_group" "inference" {
  cluster_name    = aws_eks_cluster.this.name
  node_group_name = "inference-gpu"
  node_role_arn   = aws_iam_role.node.arn
  subnet_ids      = var.subnet_ids

  launch_template {
    id      = aws_launch_template.soci_enabled.id
    version = "$Latest"
  }
}

# Launch TemplateのBootstrap User Dataでフラグを指定:
# --local-disk-max-images 50 --soci-snapshotter-enabled true
```

Bootstrapフラグの正確な名称はEKS最適化AMIのリリースによって変わることがあるため、上記はあくまで変更の「形」として捉え、本番投入前に最新のEKS AMIドキュメントを必ず確認してください。

## 効くケース・効かないケース

以下のようなワークロードでは明確な効果が見込めます。

- **スパイクの大きい推論ワークロード**：Pod数をゼロ近くからスケールさせる構成で、Pullの待ち時間を回避するためだけに常時ウォームな状態を維持するコストを避けたい場合。
- **CI/CD環境**：ジョブごとに短命なPodを立ち上げる構成では、Pullの高速化がそのままパイプライン時間の短縮になります。
- **大きく変更頻度の低いベースImage**（CUDA、PyTorch、モデルの重みを同梱したImageなど）：同じレジストリから何度もPullされるほど、Index化のコストが償却されます。

逆に、頻繁に更新される小さなアプリケーションImage（100MB程度のNode.jsサービスなど）ではPull時間自体がボトルネックになっていないため、Chunk並列ダウンロードによるCPU・ネットワークの追加負荷に見合うメリットは薄いでしょう。

## 導入前に確認すべきこと

- **レジストリの対応状況**：Lazy LoadingとParallel Pullの恩恵を受けるには、`soci` CLIやビルドパイプラインでSOCI Index付きのImageを作成・変換しておく必要があります。Index無しの通常のOCI Imageでは、普通のPullにフォールバックします。
- **Pull中のネットワーク・CPU余裕**：Chunkの並列ダウンロードと並列アンパックは、Pull中のノードで同時に使うネットワーク帯域とCPUを増やします。ネットワークが逼迫しがちなノードタイプでは、この分効果が相殺される可能性があります。
- **自社Imageでのベンチマーク**：約60%という数字はAWSが大容量AI/MLイメージで計測した値であり、汎用的なWebアプリImageで同じ比率が出るとは限りません。実際のワークロードで前後を計測することをお勧めします。

## webhaniの見解

EKS上でGPU・推論ワークロードを動かしている顧客にとって、これは労力の割にリターンが大きい変更です。Pullの待ち時間を隠すためだけに余分なPodをウォームに保つ必要がなくなるため、Autoscalingの余裕分のコストを直接削減できます。まずは1つのノードグループで実際のImageを使ってPod Ready時間を計測し、数値が確認できたら他の推論用ノードにも展開していくアプローチをお勧めします。

長期的にはむしろ、アンパック処理がcontainerd本体に入ったという事実の方が重要なシグナルです。今後数回のリリースサイクルで、Parallel Pull的な挙動はAWS固有の機能ではなく、コンテナプラットフォーム全般の標準的な期待値になっていくはずです。EKSを使っていない場合でも、動向を追っておく価値はあります。
