Coding Agent に「ボタンの余白を直して」と頼んだことがある方なら、このパターンに覚えがあるはずです。Agent はそれらしいルールを編集して「修正しました」と報告しますが、画面は何も変わりません。別ファイルにある、より詳細度の高いセレクタが Cascade で勝っているからです。Agent が読んだのはソースコードであって、ブラウザが実際に適用したスタイルではありません。

Chrome DevTools チームの 2026 年 11 月のアップデートは、まさにこのギャップを狙ったものです。Agent が実際の Chrome を操作するための DevTools MCP Server に、`get_css_styles` ツールが追加されました。選択した要素について、マッチしたルール、継承されたルール、上書きされた宣言、疑似要素、`@keyframes` などの at-rule を返し、結果が大きい場合はページネーションにも対応しています。要するに、Agent が推測ではなく Styles ペインそのものを見られるようになったということです。

## なぜソースだけでは CSS を判断できないのか

CSS は、コードを読むだけでは結果がわからない数少ない領域です。プロパティの最終的な値は次の要素で決まります。

- 読み込まれたすべてのスタイルシートにまたがるセレクタの詳細度とソース順
- Cascade Layer (`@layer`) とその宣言順
- `!important`、継承、実行時に解決されるカスタムプロパティ
- 現在のビューポートで評価される Media Query / Container Query
- サードパーティのスクリプトや UI ライブラリが注入するスタイル

1 つの Component ファイルだけを見ている Model には、そのごく一部しか見えません。よくある罠の例です。

```css
/* components/button.css */
.btn-primary {
  padding: 12px 24px;
}

/* vendor/theme.css（後から読み込まれる） */
.card .actions button {
  padding: 4px 8px;
}
```

Agent は `.btn-primary` を編集しますが、テーマ側の子孫セレクタのほうが詳細度が高く (0,2,1 対 0,1,0)、こちらが勝ちます。`get_css_styles` を使えば、`.btn-primary` の宣言が「上書き済み」として表示され、勝っているルールとそのファイル・位置もわかります。Layer を調整するのか、テーマのスコープを絞るのか、意図的に詳細度を上げるのか。正しい修正方針を、Agent が根拠をもって判断できるようになります。

## Claude Code での設定

DevTools MCP Server は `npx` で起動します。Claude Code への追加は 1 行で済みます。

```bash
claude mcp add chrome-devtools -- npx chrome-devtools-mcp@latest --isolated
```

`--isolated` を付けると、終了時に破棄される一時プロファイルで Chrome が起動します。これをデフォルトにすることをおすすめします。普段使いのプロファイルを Agent に操作させると、ログイン済みのすべてのセッションにアクセスできてしまうからです。

新しいツールをうまく使うプロンプトは、対象要素と期待する結果を具体的に指定します。

```text
http://localhost:3000/pricing を開いてください。
スナップショットを取り、Pro カードの「Start trial」ボタンを見つけてください。
そのボタンに get_css_styles を使い、padding を決めているルール、
上書きされているルール、それぞれの定義ファイルを教えてください。
まだファイルは編集しないでください。
```

編集の前に診断させることが重要です。Agent はすぐ CSS を書き始める傾向があります。先に Cascade の結果を読ませると、差分が小さく、的確になります。

## Frontend ワークフローでの使いどころ

実務で効果が大きいのは次の 3 つだと考えています。

**1. 「変更しても何も変わらない」のデバッグ。** 最も価値の高いケースです。自分のルールが適用されているのか、上書きされているのか、そもそもマッチしていないのか。これらはまったく別の問題ですが、Agent が区別できるようになります。

**2. Design System の移行。** レガシーなスタイルシートから Tailwind やトークンベースの仕組みへ移行するとき、旧ページの Component を調べて実効値を一覧にし、新しい実装が同じ値になるかを検証できます。スクリーンショットを目で比べるより、ずっと精度の高いループです。

**3. Agent が作った UI のレビュー。** Agent が Component を作ったあと、`get_css_styles` でもう一度確認すれば、トークンにすべきハードコード値や、常に他のルールに負けている死んだルールを洗い出せます。

## 押さえておきたい限界

ツールの Skill ドキュメントでは、出力を「権威ある完全な情報」として扱うよう Agent に指示しています。その瞬間の要素とページ状態に関しては妥当です。ただ、「その瞬間」には多くの前提が含まれます。

- **ビューポートと状態。** 結果は現在のウィンドウ幅、カラースキーム、操作状態を反映したものです。375px 幅やダークモード、`:hover` 時にだけ起きる不具合は、Agent がその状態を作らない限り現れません。明示的に指示しましょう。
- **動的なスタイル。** 操作後に JavaScript で切り替わるスタイルは、その操作を行ってから調べる必要があります。
- **ブラウザにとっては正しいが、意図までは示さない。** ツールが教えてくれるのは「何が勝っているか」であって「何が勝つべきか」ではありません。テーマ側を直すか Component 側を直すかは、依然として設計判断です。
- **大きなページ。** ページネーションがあるのは結果が大きくなりうるからです。重いページではトークン消費もかさむので、ページ全体ではなく特定の要素に絞って調べるのが現実的です。

セキュリティ面の注意もあります。ブラウザを操作できる Agent は、そのブラウザが到達できるものすべてを読めます。対象はローカルやステージング環境に限定し、isolated プロファイルを使い、本番の管理画面のセッションは渡さないようにしてください。

## webhani の見解

多くの AI Coding ツールはロジックには強い一方、レイアウトには弱いままでした。レイアウトの正しさがリポジトリではなくブラウザの中にあることが、その一因です。Cascade への構造化されたアクセスを Agent に与えることは、このギャップを埋める意味のある一歩であり、すでに MCP を使っているチームなら導入コストもほとんどかかりません。

私たちが支援しているチームには、シンプルなルールを提案しています。CSS のバグについては、編集前に必ず対象要素で `get_css_styles` を呼ぶこと。1 タスクあたり数秒増えるだけで、「直したはずなのに変わらない」というループを丸ごとなくせます。
