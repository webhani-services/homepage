Claude Code のリリースノートは、対話的な使い勝手に関する内容が中心になりがちです。11 月第 1 週に公開された 2.1.319 は、むしろ「誰も画面を見ていない実行」にとって意味のあるリリースです。二次情報(dev.classmethod.jp、ai-tldr.dev など)によると、`permissions.denyInsteadOfPrompting` 設定の追加、ターミナルセッションでの MCP タスクのバックグラウンド化、LLM Gateway 配下や `claude -p` における auto mode の挙動変更が含まれています。正確な仕様は公式 changelog が正ですので、以下の細部は導入前にご確認ください。

どれも派手な変更ではありませんが、CI、cron、定期実行エージェントから Claude Code を動かしているチームには効いてくる内容です。

## ヘッドレス実行における権限プロンプトの問題

対話セッションでは、権限プロンプトは機能の一部です。エージェントがコマンドを実行しようとし、人間が確認して許可または拒否します。ところがヘッドレス実行では、同じプロンプトが次の二方向のリスクになります。

- 誰も答えないプロンプトで **ハングし**、タイムアウトまで CI の時間を消費する。
- ハングを避けるために広い allow-list や権限スキップのフラグを付け、**エージェントの権限が意図せず広がる**。

実際には両方とも頻繁に起きます。ハングに悩んだチームが権限を緩めて「解決」し、結果として誰も想定していない権限を持つ無人エージェントが出来上がります。

`denyInsteadOfPrompting` は第三の選択肢です。許可されていない操作はその場で拒否され、エージェントは別の手段を探すか、「実行できなかった」と報告します。失敗が隠れたり高くついたりせず、見える形で安く済みます。

## 無人実行向けの最小構成

おすすめは、ジョブに必要なものだけを明示的に allow し、それ以外は拒否という構成です。プロジェクトの設定ファイルは次のような形になります。

```json
{
  "permissions": {
    "allow": [
      "Read",
      "Bash(npm run lint)",
      "Bash(npm run test:unit)",
      "Bash(git diff:*)"
    ],
    "deny": [
      "Bash(git push:*)",
      "Bash(curl:*)"
    ],
    "denyInsteadOfPrompting": true
  }
}
```

キーの正確な配置は、お使いのバージョンの設定ドキュメントで確認してください。ここで伝えたいのはポリシーの形であり、このスニペットの構文そのものではありません。CI のワークフローでは、拒否が「ジョブの停止」ではなくトランスクリプト上の記録として残ります。

```yaml
- name: Automated lint triage
  run: |
    claude -p "Run the linter, fix trivial violations, summarize anything else." \
      --output-format json > result.json
```

ゼロ以外の終了コードは、リトライで潰すノイズではなく、読むべきシグナルとして扱いましょう。

## 終了コードの変更は見た目以上に重要

今回のリリースでは、`claude -p` の auto mode で「安全確認が利用できないために拒否された」場合、終了コードが 0 ではなく 1 になるよう変わったと報じられています。「プロセスが終わったか」だけを見ていたラッパースクリプトは、エージェントがブロックされた実行を成功として報告していたことになります。

`claude -p` を呼び出し、終了コードで分岐しているスクリプトは棚卸ししてください。これまで主要タスクを黙って拒否しながら green になっていたジョブが、正しく red になります。望ましい挙動ですが、アップグレード翌朝の当番担当者は驚くかもしれません。CI ではバージョンを固定し、意図的にアップグレードし、新たに失敗するジョブはリグレッションではなく発見だと捉えるのがよいでしょう。

## Gateway 配下での auto mode

社内の LLM Gateway 経由でモデルを呼び出すチームは、テレメトリや実験的 beta を無効化していることが多いです。報道によれば、2.1.319 ではこうした環境で auto mode が組み込み classifier にフォールバックしなくなり、サーバー側チェックを明示的に制御する環境変数(`CLAUDE_CODE_AUTO_MODE_SERVER`)が用意されています。managed settings で実験的 beta を無効化している場合は、サーバー側のフラグも意図的に設定する必要があるとのことです。

Gateway 構成の場合は、アップグレード後にステージング用プロジェクトで auto mode を試し、`/status` で設定どおりの挙動になっているかを確認してください。従来のフォールバックがまだ効いていると決めつけないことが大切です。安全性に関わる classifier の挙動変更は、本番に入る前に捕まえたいところです。

## MCP タスクのバックグラウンド実行

ターミナルセッションでは、時間のかかる MCP ツール呼び出しをバックグラウンドタスクとして実行し、完了時に結果が Claude に渡されるようになりました。呼び出しをブロックさせたい場合に無効化する環境変数も用意されています。これは MCP 仕様のタスク機構と対応しており、以前の非同期エージェントに関する記事でも取り上げました。

MCP サーバーを作る側にとっては、インデックス再構築、レポート生成、マイグレーションの dry-run といった長い処理を、長いタイムアウト付きのブロッキング呼び出しではなく、きちんとしたタスクとして実装する動機になります。エージェントを運用する側にとっては、遅いツールの実行中もセッションが作業を続けられる一方、**モデルが次の処理に進んだ後で副作用が完了しうる**ことを意味します。状態を変更するツールは、結果の再読み取りが冪等であるようにし、監査ログには最初の呼び出しだけでなくタスク ID も記録してください。

## webhani の推奨

1. **無人ジョブにはすべて deny-on-miss を採用する。** allow-list は空から始め、ジョブが実際に必要とするものだけを追加します。
2. **`claude -p` を包むスクリプトの終了コード処理を棚卸しする。** 1 は「ブロックまたは失敗」であり、green になるまでリトライする対象ではありません。
3. **バージョンを固定し、段階的にアップグレードする。** 100 件を超える変更(大半は権限・サンドボックス関連を含む修正)がある版は、自動更新ではなく読んでから上げる価値があります。
4. **Gateway 構成はアップグレード後に再検証する。** auto mode の状態と関連の環境変数を明示的に確認します。
5. **状態を変更するツールを公開しているなら MCP タスク ID をログに残す。** バックグラウンド完了を追跡できるようにします。

共通するテーマは、エージェントの安全設計が「人ごと」ではなく「実行ごと」に設定されるようになっていることです。キーボードの前にいるエンジニアに適したポリシーは、cron ジョブには大抵合いません。2.1.319 はその違いを表現する手段を少し増やしてくれました。CI や社内プラットフォームで AI コーディングエージェントのガードレールを設計される際は、トレードオフの整理からご相談いただけます。
