Claude CodeをCIや定期バッチで動かしていると、よく出会う問題が2つあります。1つは、権限プロンプトに誰も答えずジョブが止まり続けること。もう1つは、エージェントが実際には何もしていないのにジョブが「成功」で終わることです。

11月6日に出た v2.1.319 には、この2つに関わる変更が入っています。以下の内容は複数のサードパーティの解説記事(classmethod、DEV Communityなど)にもとづいています。設定名や細かな挙動は、適用前に公式のchangelogとドキュメントで確認してください。

## 報じられている主な変更

- **MCPタスクのバックグラウンド化。** MCPサーバーがツール呼び出しを「タスク」として実行すると、Claude Codeはそれをすぐバックグラウンドに回し、完了時に結果をClaudeへ返します。待機させる、または無効化するための環境変数も用意されています。サブエージェントからのMCP呼び出しはタスク化されません。
- **権限プロンプトを拒否として扱う設定。** `permissions.denyInsteadOfPrompting` が追加され、プロンプトを待つ代わりにその呼び出しを拒否してターンを続行できるようになったとされています。
- **ゲートウェイ配下のauto mode。** テレメトリや機能フラグがオフの環境(LLMゲートウェイ経由を含む)では、サーバー側で判定できない呼び出しは確認または拒否になり、ローカルの分類器にフォールバックしなくなりました。`CLAUDE_CODE_AUTO_MODE_SERVER=0` で従来の挙動に戻せます。Bedrock、Vertex、Foundryは対象外です。
- **`claude -p` の終了コード。** auto modeがアクションを拒否した場合、これまでの 0 ではなく 1 で終了するようになりました。

個々の変更は小さく見えますが、まとめると無人実行の前提がかなり変わります。

## 「止まる」問題: プロンプトを拒否に変える

ヘッドレス実行で一番困るのは、許可されていない操作に当たってプロンプトが出たまま、タイムアウトまで何も起きないケースです。拒否として扱えば、エージェントは別の手段を探すか、できなかったことを報告して終了します。

CI用の設定は、許可リストを明示し、それ以外は拒否する形にするのが基本です。

```json
{
  "permissions": {
    "allow": [
      "Read",
      "Edit",
      "Bash(npm run lint)",
      "Bash(npm run test:*)",
      "Bash(git diff:*)"
    ],
    "deny": [
      "Bash(git push:*)",
      "Bash(curl:*)",
      "Read(./.env*)"
    ],
    "denyInsteadOfPrompting": true
  }
}
```

この設定はCI専用のファイルとして分け、開発者のローカル設定とは混ぜないことをおすすめします。ローカルでは確認してほしい操作でも、CIでは拒否して構わない、という場面が多いからです。

## 「黙って成功する」問題: 終了コードを使う

`claude -p` がauto modeの拒否で 1 を返すようになったことで、CIのステップは「エージェントがやり切れなかった」ことを検知できます。ただし、すぐに失敗扱いにするより、まず理由を残す設計にしたほうが運用しやすいです。

```yaml
# .github/workflows/claude-maintenance.yml(抜粋)
- name: Run Claude Code
  id: claude
  run: |
    set +e
    claude -p "依存パッケージのlint警告を修正し、テストが通ることを確認してください" \
      --output-format json > claude-result.json
    echo "exit_code=$?" >> "$GITHUB_OUTPUT"

- name: Report refusal or failure
  if: steps.claude.outputs.exit_code != '0'
  run: |
    echo "::warning::Claude Code exited with ${{ steps.claude.outputs.exit_code }}"
    jq -r '.result // "no result"' claude-result.json | head -50
    exit 1

- name: Upload transcript
  if: always()
  uses: actions/upload-artifact@v4
  with:
    name: claude-result
    path: claude-result.json
```

以前のバージョンで「終了コード 0 なら成功」と書いていたパイプラインは、今回の変更で初めて失敗するかもしれません。それはこれまで見えていなかった拒否が表に出てきただけなので、許可リストの見直しのきっかけとして扱うのがよいでしょう。

## ゲートウェイ配下のチームは要確認

社内のLLMゲートウェイを経由してClaude Codeを使っている組織は、今回の変更の影響を受けやすい層です。ローカル分類器へのフォールバックがなくなったため、これまで自動で通っていた操作が確認や拒否に変わる可能性があります。

対応としては、次のどちらかを選ぶことになります。

1. **許可リストを広げる。** よく使うコマンドを `allow` に明示します。何が許可されているかが設定ファイルに残るので、監査の観点ではこちらが望ましいです。
2. **`CLAUDE_CODE_AUTO_MODE_SERVER=0` で従来の挙動に戻す。** 移行期間の一時的な手段として使い、期限を決めておきます。

私たちは基本的に1を推奨しています。自動判定に任せる範囲が広いほど、何が許可されたのかを後から説明しにくくなるためです。

## MCPタスクのバックグラウンド化で気をつけること

長時間かかるMCPツール(ビルド、データ取得、外部APIのポーリングなど)がバックグラウンドで動くことで、エージェントは待ち時間に他の作業を進められます。一方で、設計上の注意点も増えます。

- **冪等性。** 結果が遅れて届く前提になるため、同じタスクが再実行されても安全なツールにしておきます。
- **stdioサーバーの寿命。** stdioで動くMCPサーバーはClaude Codeの終了とともにプロセスが止まるため、メモリ上のタスク状態は失われる可能性があります。長いタスクは状態を外部(ファイルやDB)に保存します。
- **CIでの扱い。** ジョブの最後でバックグラウンドタスクが未完了のまま終わると、結果を取りこぼします。CIでは待機させる設定にするか、タスクの完了を確認してから終了するプロンプトにしておくのが安全です。

## webhaniの見解

今回の変更は、Claude Codeが「人が横で見ている対話ツール」から「無人で動くワーカー」としての用途を強く意識し始めていることを示しています。無人実行で大事なのは、止まらないことと、失敗を正しく失敗として報告することの2点です。2.1.319はその両方に手当てをしています。

チームとしてやっておきたいことをまとめます。

1. CI専用の権限設定ファイルを用意し、許可リストと拒否設定を明示する
2. `claude -p` の終了コードと出力をCIで記録し、拒否の理由を追えるようにする
3. ゲートウェイ配下の環境では、許可リストを先に整備してから更新する
4. 長時間のMCPツールは冪等にし、状態を外部に持たせる

Claude Codeは更新頻度が高いため、こうした変更を個人の設定で吸収するのではなく、チームの設定として管理しておくことが安定運用の前提になります。
