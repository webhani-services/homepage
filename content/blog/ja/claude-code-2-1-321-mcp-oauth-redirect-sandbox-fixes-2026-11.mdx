Claude Code 2.1.321 の話題は、Fable 5.2 がデフォルトの Fable モデルになり、1M context window を備えた点に集まりがちです。コスト試算には重要ですが、モデル移行については別記事で扱いました。ここでは、目立たないほうの変更、つまり権限とセキュリティの修正を取り上げます。

先にお断りします。以下のセキュリティ関連の内容は、リリースを要約した日本語の解説記事(labmemo.com)1 件に基づくもので、公式 changelog の文言ではありません。公式 changelog で確認できたのはモデル変更です。修正内容の正確な表現は、公式の changelog で確認してください。

## 修正されたとされる内容

この要約で目を引くのは次の 2 点です。

1. **MCP サーバーの OAuth リダイレクト問題**。特定の条件下で、ユーザーが認可したのとは別のホストに refresh token などの秘密情報が送られる可能性があった。
2. **read-only の Bash コマンドが、権限確認なしで sandbox の外で実行され得た問題**。

二次情報だけでは発動条件を確認できないため、推測は避けます。代わりに、この 2 つが触れている境界はエージェントと MCP を使うどのチームにも共通なので、問題の種類として整理します。

## OAuth リダイレクトの問題が重要な理由

OAuth で認証する MCP サーバーは、開発者のマシン上に refresh token を保持します。refresh token は有効期間が長く、スコープも 1 つのタスクに必要な範囲より広いことが少なくありません。リダイレクトで誤ったホストに送られた場合、被害は現在のセッションに留まらず、失効させるまで有効なままです。

これは古典的な OAuth の open redirect と同じ失敗パターンですが、今回は README の URL を貼るだけで入れられるツールの内部で起きています。信頼の判断はインストール時に一度だけ行われ、その後は無人で動き続けます。

したがって問うべきは「この脆弱性の影響を受けたか」よりも、「自社のノート PC に資格情報を持つ MCP サーバーが何台あり、誰が承認したのか」です。

## read-only Bash の問題が重要な理由

エージェントの権限システムは分類に依存しています。読み取り専用なら実行し、書き込みなら確認する、という仕組みです。この分類に穴があれば、利便性の仕組みがそのまま迂回経路になります。今回報告されたのは、read-only と分類されたコマンドが、確認なしに sandbox の外で動き得たという点です。

ここから得られる教訓は一般的です。「read-only」をそれ単体でセキュリティ境界として扱わないでください。境界は sandbox であり、分類器はその上に載った使い勝手のための層です。

## 今日からできる棚卸し

まず一覧を作ります。プロジェクト単位の MCP サーバーは `.mcp.json` に、ユーザー単位のものは Claude Code の設定にあります。プロジェクトファイルを走査する例です。

```bash
# ~/work 配下の全リポジトリで宣言されている MCP サーバーを列挙
find ~/work -name ".mcp.json" -not -path "*/node_modules/*" -print0 \
  | xargs -0 -I{} sh -c 'echo "== {}"; jq -r ".mcpServers | to_entries[] | \"\(.key)\t\(.value.url // .value.command)\"" "{}"'
```

各サーバーについて、保守元、OAuth の利用有無、要求しているスコープ、トークンの保存場所の 4 点を記録します。1 行で答えられない項目は、レビュー対象に入れます。

結果に応じて次の対応を取ります。

- **まず更新する**。チーム全体を 2.1.321 以降にします。Homebrew 経由では stable チャネルや cask の反映が約 1 週間遅れることがあるとの情報もあるため、`claude --version` で実際に確認してください。
- **重要度の高いサーバーは再認可する**。ソースホスティング、クラウドコンソール、チケット管理に接続した MCP サーバーは、プロバイダー側で既存の許可を取り消し、更新後に認可し直します。誤った宛先に渡った可能性のある refresh token が無効になります。
- **スコープを絞る**。再認可は、より少ないスコープを要求し直す最も手軽な機会です。エージェントの用途の大半は read-only スコープで足ります。
- **sandbox を有効のままにする**。ビルドを通すために無効化している人がいれば、理由を確認し、パスや権限の根本原因を直します。

## あわせて見直したい運用ポリシー

更新で塞がるのは今回の穴だけです。次の穴に備えて、次の見直しをおすすめします。

| 対策 | 理由 |
| --- | --- |
| リポジトリごとに MCP サーバーを allowlist 化し、PR でレビューする | `.mcp.json` の変更が差分として見える |
| 自社でホストするか、契約のあるベンダーのサーバーを優先する | OAuth フローに責任を持つ相手がいる |
| プロバイダーが対応していれば短寿命の資格情報を使う | 漏れても自然に失効する |
| エージェント用の ID を人の ID と分ける | 失効させても人がロックアウトされない |

どれも特定のベンダーに限った話ではありません。CI のサービスアカウントに適用している最小権限の考え方を、新しい種類のクライアントにも当てはめるだけです。

## webhani の見解

モデルのデフォルト変更とセキュリティ修正が同じリリースに入っていると、見出しだけ読んで済ませがちです。私たちは、修正のほうを先に読むことをおすすめします。モデル変更は設定で戻せますが、漏れた refresh token は失効作業をしない限り元に戻りません。

webhani 自身の対応は小さく済みます。更新し、利用中の OAuth 系サーバーを数件再認可し、MCP の棚卸しを四半期のアクセスレビューに加えます。本番に近いシステムに対してエージェントを動かしているチームなら、同じ 1 時間をかける価値があります。

## まとめ

- 公式の 2.1.321 changelog で修正内容を確認し、第三者の要約は手がかりとして扱う。
- MCP サーバー、特に OAuth を使うものを棚卸しし、保守元・スコープ・トークン保存先を記録する。
- 更新したうえで、重要なサーバーの許可を取り消して再発行する。
- セキュリティ境界は sandbox であり、read-only 判定は使い勝手のための層と考える。
- `.mcp.json` の変更はコードレビューの対象にする。
