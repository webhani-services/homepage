公式リリースノートをミラーしているサードパーティのチェンジログによると、Claude Code 2.1.329 では「リスクのある操作の確認」が削除され、従来は確認が挟まっていたステップが自動で実行されるようになったとのことです。同リリースでは、スケジュール済みタスク、`/loop` の wakeup、fork を一覧できる `/tasks` ビューも追加されたと報じられています。確認できたのは二次情報のみですので、詳細は公式 changelog でご確認ください。

細部がどうであれ、方向性は明確です。対話的な確認は弱い統制として扱われ、安全性の負担は設定側へ移りつつあります。チームのガードレールが settings にあるのか、それとも担当者の反射神経だけに頼っているのか、見直すよい機会です。

## 確認プロンプトが弱い統制である理由

確認ダイアログが機能するのは、読む人が内容を理解し、注意を払っている場合だけです。1日に40回確認を求められれば、41回目は読まずに承認してしまいます。悪意ではなく慣れが原因です。

また、無人実行ではプロンプトは何の役にも立ちません。スケジュールタスク、`/loop`、CI ジョブには、クリックする人がいません。破壊的なコマンドを止める役目をプロンプトに任せているパイプラインは、すでに無防備です。

つまり、プロンプトの廃止自体が退行とは限りません。他に境界を強制する仕組みがない場合にだけ問題になります。

## 境界の置き場所:settings

Claude Code は settings ファイルから権限ルールを読み込みます。このルールは決定的で、許可されたコマンドは実行され、拒否されたものは人の判断なしに拒否されます。取り返しのつかない操作に求めたい性質です。

プロジェクトの `.claude/settings.json` は、次のような形から始めるのが無難です。

```json
{
  "permissions": {
    "allow": [
      "Bash(npm run test:*)",
      "Bash(npm run lint)",
      "Bash(git diff:*)",
      "Bash(git status)"
    ],
    "deny": [
      "Bash(git push --force:*)",
      "Bash(rm -rf:*)",
      "Bash(curl:*)",
      "Read(./.env)",
      "Read(./.env.*)"
    ]
  }
}
```

ポイントは2つあります。allow は狭く始め、実際の必要に応じて広げること。そして `deny` を最重要とみなすこと。モデルがどう判断しても絶対に起こしてはならない操作の一覧だからです。

ルールの正確な構文はバージョンによって変わる可能性があるため、利用中のバージョンのドキュメントで確認してください。

## パターンで表せない確認は Hook で

「このマイグレーションは本番テーブルに触れる」といった判断は、パターンルールでは表現できません。その場合は `PreToolUse` hook で実行直前の呼び出しを検査し、非ゼロの終了コードでブロックします。最小のスケッチです。

```bash
#!/usr/bin/env bash
# .claude/hooks/block-prod-db.sh
# stdin から tool call の JSON を読み、本番向けなら拒否する
input="$(cat)"
if echo "$input" | grep -qE 'prod(uction)?[-_.]?(db|database|cluster)'; then
  echo "Blocked: command references a production database" >&2
  exit 2
fi
```

この正規表現が網羅的でないのは承知の上です。重要なのは、誰も見ていないセッションを含め、毎回必ずチェックが走ることです。

## 導入時のチェックリスト

このバージョンへ上げる場合の手順です。

1. 2.1.329 の公式リリースノートを読み、どの操作の確認がなくなったかを正確に把握する
2. force push、再帰削除、secrets ファイル、外向きネットワークツールに対する明示的な `deny` ルールを `.claude/settings.json` にコミットする
3. CI やスケジュール実行でブロックすべきものを settings か hook に移す(これらは元々、人がいない経路です)
4. まず使い捨てブランチで新バージョンを動かし、確認なしで何が実行されるかを観察する
5. ツール呼び出しをログに残す。Claude Code のテレメトリを既にエクスポートしているなら、拒否された呼び出しにアラートを付け、成功だけでなく試行も見えるようにする

## webhani の見解

今回の変更を「Claude Code が危うくなった」と読むのは適切ではないと考えます。むしろ、安全をダイアログに任せるのをやめるきっかけです。制限をバージョン管理された settings に書いているチームは、ほとんど影響を受けません。開発者の目視に頼ってきたチームは、アップグレードを機に制限を明文化すべきでしょう。

簡単な確認方法があります。開発者を全員スクリプトに置き換えても、現在の設定は `main` への force push を止められるでしょうか。答えが「誰かがクリックするかどうか」に依存するなら、アップグレード前に直しておくべきです。
