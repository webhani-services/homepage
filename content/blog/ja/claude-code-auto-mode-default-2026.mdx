## Auto Mode が変えたもの

2026年8月14日、Anthropic は Claude Code の権限管理を大きく変えました。Pro、Max、Team サブスクリプションユーザーに対し、Auto Mode がデフォルトになったのです。

これまで Claude Code は、ファイル読み込み、コマンド実行、Git操作といったアクション一つ一つに対して人間の確認を求めていました。開発速度を優先するなら確認をスキップできましたが、そこには安全性のトレードオフがありました。

Auto Mode では、Anthropic が構築した分類器が各アクションを事前に審査し、安全と判定したものは自動承認します。人間が毎回ダイアログボックスに答える手間がなくなり、一方で検証の層が間に入ります。さらに、この分類処理は追加の token 費用を発生させなくなりました。

## 何が起きたのか、実務的に

Auto Mode の導入は、3つの層での変化をもたらします。

**1つ目は、開発のリズムの変化です。** これまで「ファイルを読む」→「確認」→「次のコマンド」という段階的なやりとりが、ほぼ中断なく進むようになります。特に小さな、繰り返し的なアクション（ファイル検索、ログ確認、テスト実行など）が連鎖する場面では、確認ダイアログの消失による加速が顕著です。

Webhani のクライアント案件では、レガシーコードベースの調査フェーズに Claude Code を使うことが増えました。古いシステムを理解するには、複数ファイルの読み込み、grep による検索、簡単なスクリプト実行が次々と必要になります。従来は、これらが権限プロンプトで細切れになっていました。Auto Mode では、分類器が「これは読み取りと検索であり、副作用がない」と判断し、作業がスムーズに進みます。

**2つ目は、権限ゲートの再定義です。** 完全な自動承認ではなく、「ホワイトリスト型の分類」という仕組みです。Git push や npm パッケージ削除といった破壊的なアクションは、依然として人間の確認が入ります。Anthropic の分類器がどのアクションを「安全」と見なすかは、完全に透明ではありませんが、意図は明確です。一般的な開発作業の 90% は自動で流れ、重大な操作だけは人間が判断する設計です。

**3つ目は、AI による設定操作の拡大です。** 従来「Claude Code は読み込みと書き込みが主」という使い方でしたが、Auto Mode では、設定ファイル（`.env` の読み込み、`next.config.ts` の編集）や環境構築の一連（Docker volume のリセット、キャッシュ削除）を、より気軽に AI に任せられるようになります。

## コンサルティング業務への実務的な影響

Webhani は複数のクライアント案件で Claude Code を活用しています。Auto Mode 導入で、その使い方と監視の仕方が変わりました。

### スピード面での利得

既存ベースコードの分析が加速します。あるクライアントの Web アプリケーション改修では、数千ファイルのレポジトリを、Claude Code に「このシステムの全体像を図示してくれ」と投げた際、従来なら権限確認で 20 分待つような操作が、ほぼシームレスに進むようになりました。

初期調査から実装提案までの時間短縮は、特に時間単価で課金する案件の利幅を改善します。

### 監視上の注意点

加速化は同時に、新たな監視負荷をもたらします。以前は、「何をされるのか」を権限プロンプトで確認する機会がありました。Auto Mode では、その検査が AI 分類器に移行し、人間は事後的に「何が行われたか」をレビューする体制に切り替わります。

Webhani のプロセスでは、次の施策を入れています。

1. **セッション開始時に明確な指示を与える** — Claude Code に指定する「ロール」と「禁止事項」を明確にします。例えば「本番環境に関連するコマンド（npm run deploy など）は絶対に実行しないこと」と事前に伝えます。

2. **自動承認されたアクションのログを定期的に確認** — Auto Mode でも、Claude Code は操作履歴を記録します。1日の終わりに「実は何が自動で実行されたか」を眼を通す習慣をつけます。

3. **クライアント案件では明示的に制限する** — クライアントの開発環境によっては、自動承認対象をさらに狭く設定できます。「git push は常に確認」「npm install も確認」といった案件固有のポリシーを実装します。

## Auto Mode でもカバーされない領域

重要な点として、Auto Mode の導入 = 人間による監視の廃止ではありません。分類器は、次のような領域では判定を保留します。

- **外部 API 呼び出しの妥当性判定**：API キーを使う操作は実行されますが、「その API 呼び出しが業務上正当か」まで分類器は判定しません。クライアントの SaaS 課金体系に影響する操作は、人間レビューが不可欠です。

- **複雑なビジネスロジック検証**：コード生成は自動で進みますが、「生成されたロジックがビジネス要件に合致しているか」は、開発者が確認する必要があります。Auto Mode は、テクニカルな権限チェックであり、ビジネスロジック検証ではありません。

- **セキュリティ敏感な設定の変更**：データベース接続文字列の編集や、認証設定の変更は、たとえ技術的に「安全な書き込み」でも、慎重に扱う必要があります。

## 実装面での具体例

Auto Mode 下での作業パターンの一例を示します。

```text
セッション指示:
「このレポジトリの README.md を読み込み、プロジェクト構造を把握した上で、
不足している API ドキュメントを提案してください。
ファイルの編集は提案の前に確認を求めてください。
Git への push は絶対に実行しないでください。」
```

このように明示的に指示を与えると、Claude Code は：
- README 読み込み（自動）
- 複数ファイルの型定義確認（自動）
- 提案の提示（出力）

までは自動で進み、「ドキュメント案を生成した、確認しますか？」という段階で人間の判定を待ちます。Git push のような重大操作は、指示がなくても自動承認対象外です。

## Webhani の推奨方針

クライアント開発において、Auto Mode を活用しながらリスクを管理するには、次のアプローチを採用しています。

1. **タスクの性質に応じた権限設定** — データ分析・調査フェーズではより広い自動承認を許容し、本番反映前の最終段階では制限を強化します。

2. **複数人レビューの導入** — 単独の開発者が Claude Code のセッションを管理するのではなく、別の開発者が定期的に操作ログをサンプルレビューするプロセスを入れます。

3. **クライアントへの透明性** — 「AI が何を自動実行しているか」をクライアントに説明し、合意を得ておく。特に規制業界では、監査対応が必要になります。

## まとめ

Claude Code の Auto Mode デフォルト化は、開発スピードの向上と、操作の民主化をもたらします。同時に、監視体制の「形式」が変わり、権限ゲートから事後ログレビューへとシフトします。

AI コーディングツールが成熟するほど、人間の役割はテクニカルゲート（「実行させるか」の確認）から、ビジネスロジックと品質の最終確認へ移行します。Webhani では、クライアント案件ごとにこのバランスを設計し、「速さ」と「確実性」の両立を実現する体制を整えています。
