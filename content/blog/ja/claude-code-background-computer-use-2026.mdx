Computer Use — AI モデルが API 呼び出しではなく、実際のデスクトップをクリック・入力・操作する機能 — には、これまで一つの実用上の制約がありました。画面を占有してしまうことです。タスクを開始するとマウスを明け渡し、完了を待つしかありませんでした。2026年9月初旬、Anthropic は Claude Cowork と Claude Code に「バックグラウンド Computer Use」を追加し、macOS の Pro / Max プランユーザーに限りこの制約を取り除きました。

新しいモデルや新しい能力の話ではありません。スケジューリングと UX の変更であり、実はこの種の変更こそがチームの日々の作業を実際に変えることが多いです。

## 何が変わったのか

これまでの Computer Use は、Claude が操作している間、自分の PC が使えなくなる — 自分の PC をリモート操作されているのとほぼ同じ体験でした。バックグラウンド実行では、Claude がバックグラウンドウィンドウでアプリを開いて操作し、ユーザーはフォアグラウンドで入力・閲覧・作業を続けられます。タスクの途中でマウスやキーボードを奪うことはなく、ユーザーが入力中であれば一時停止します。フルスクリーンが本当に必要な場合のみ許可を求めますが、その場合もセッションごとに一度だけです。

設定は Settings → General → Computer use にあり、デフォルトはオフのオプトイン方式です。

## エージェント型ワークフローのどこに効くか

webhani では、エージェント型ツールを「何を自動化するか」だけでなく「人間のクリティカルパスから何を取り除くか」という観点で評価しています。バックグラウンド Computer Use が狙うのは、API が存在しないタスクという明確な隙間です。社内の管理画面、レガシーな業務システム、手動 QA 用のモバイルシミュレータなど、クライアント環境でよく見られるこの種の作業は、これまで人がずっと画面をクリックし続ける必要がありました。

現実的な使い方はこうです。開発者が「この社内 CRM を操作して、前四半期のアカウント一覧を CSV にエクスポートして」とバックグラウンドタスクを開始し、そのままフォアグラウンドでフィーチャーブランチの実装を続ける。二つのタスクが画面のフォーカスを奪い合いません。

## 権限設定の考え方（概念例）

Claude Code の `settings.json` は、ツールアクセスに対して allow/deny の権限モデルをすでに採用しています。自律的・バックグラウンド実行可能なツールを有効化する際も、包括的な許可ではなく、同様に明示的でスコープを絞った承認を経るべきです。

```json
{
  "permissions": {
    "allow": [
      "ComputerUse(app:internal-crm)"
    ],
    "deny": [
      "ComputerUse(app:*)"
    ]
  }
}
```

これはあくまで概念例です。この種のインターフェースは変化が速いため、設定前に必ず Anthropic の最新ドキュメントで正確なキー名を確認してください。

## リスクの考慮点

バックグラウンド自動化は、利便性以上に監督の重要性を高めます。クライアント環境で有効化する前に、少なくとも次の3点は徹底すべきです。

- **権限を絞る**：デスクトップ全体ではなく、特定のアプリケーションにアクセスを限定する。
- **専用プロファイルまたは専用マシンを使う**：本番環境の認証情報や関係のない機密セッションを持つ環境とは分離する。
- **実行後は毎回ログを確認する**：バックグラウンドタスクは「投げっぱなし」になりやすいものです。人による確認なしに長時間放置しないことが重要です。

## クライアントチームにとっての実務的なユースケース

- 開発者がコーディングを続けながら、ローカルファイルから競合調査をまとめる
- 自動テストでは検知しにくい UX の不具合を見つけるため、モバイルシミュレータで手動 QA パスを実行する
- API を持たない社内ダッシュボードや業務システムを操作する（法務・医療・金融系クライアントでよく見られるケース）

## webhani からの推奨

これは既存 API を置き換えるものではなく、API が存在しない反復的なデスクトップ作業に絞って使うべきツールだと考えています。スクリプト化や SDK 経由で実行できるタスクであれば、そちらのほうが信頼性・監査性の面で依然として優れています。バックグラウンド Computer Use が価値を発揮するのは、そうした代替手段が存在しない場面に限られます。

まずはリスクの低い単一のワークフローをサンドボックス環境で試し、1週間ほどログを観察してから、適用範囲を広げるかどうかを検討することをお勧めします。

## まとめ

バックグラウンド Computer Use は能力面の飛躍というより UX 面の変更ですが、機能が実際に使われるかどうかを決めるのは、多くの場合こうした UX の変更です。エージェント型開発を行うチームにとっては、API を持たないエンタープライズツールという現実的な隙間を埋める機能であり、デスクトップレベルのアクセス権を持つ他のツールと同じ水準のスコープ管理を伴って導入する限り、価値のあるアップデートだと言えます。
