## 無声のコスト増加：気付かれずに積み重なるキャッシングバグ

2026年8月19日、Claude Codeはバージョン2.1.237をリリースしました。重要な修正は、再利用されるべきコンテキストが各API呼び出しで再送信されるという潜在的なプロンプトキャッシュのバグです。技術的には単純なものですが、運用上の影響は無視できません。このバグは、明らかな失敗をトリガーすることなく、数週間のAgent セッションにわたって静かに複合化します。

具体的に考えてみましょう。あなたのチームがCI/CDパイプラインでClaude Codeを永続的なdev assistantとして実行しているとします。大規模なプロジェクトコンテキスト（システムプロンプト、ツール定義、参照ファイル）があります。キャッシングなしの素朴なセットアップでは、各Agentターンでこのコンテキストを送信することになります：

- システムプロンプト + 指示：8 KB
- ツール定義（Bash、ファイル読み込み、grep、編集）：15 KB
- コンテキストにピン留めされた参照ファイル（プロジェクト構造、命名規則、アーキテクチャドキュメント）：25 KB
- このターンの実際の会話履歴：5 KB
- 合計：53 KB/ターン

典型的なマルチステップAgentタスク（たとえば、5～6のAgentターンにわたり8～12のツール呼び出しを含むコードレビュー）では、タスクあたり約300 KBの冗長コンテキスト伝送と、同じシステムプロンプトおよびツール定義の再処理コストが発生します。1ヶ月間のCI実行（約50回のコードレビュー実行）では、プロジェクトあたり毎月約15 MBの不要な伝送になります。

プロンプトキャッシュが正常に機能する場合、最初のターンは安定したコンテキスト48 KBを送信し、APIがそれをキャッシュします（通常のトークン価格の約25%の価格で請求されます）。後続のターンはそのキャッシュを再利用し、小さな会話履歴デルタのみを支払います。節約は複合化します：キャッシュ有効時は、15 MBは約2 MBの伝送トークンになり、計算コストも同様に削減されます。

キャッシングバグは、チームが知らずに完全な非キャッシュ価格を支払っていることを意味していました。5つのプロジェクトでAgent支援コードレビューを定期的に実行しているチームの場合、月次のコスト差は現実的です：プロジェクトサイズとAgent頻度によっては$200～$800の範囲です。さらに重要なことに、高速な反復の場合：Agentタスクが予想より長くかかっているならば、破損したキャッシュは2分のタスクを4分のタスクに静かに変えるかもしれません。APIはキャッシュすべきコンテキストを再処理しているからです。

## 修正が持続可能なAgentワークフローにもたらすもの

直接的な教訓は、プロンプトキャッシングは無料の最適化ではなく、agentic ワークフローをスケールで経済的に実行可能にするための基礎的な前提だということです。Claude Codeを長時間実行するdev assistantとして、またはCI/CDにAgent呼び出しを埋め込んで実行している場合、キャッシング正確性は直接的に以下に影響します：

**コスト予測可能性。** Agentで支援されたコードレビューに$500/月を予算化するチームは、キャッシングの完全な利益を得ているかどうかを知る必要があります。バグがあった場合、実際のコストはより高く、スケールアップは苦痛で非線形な曲線になるでしょう。

**レイテンシの一貫性。** システムプロンプト、ツール定義、および参照コンテキストに依存するAgentタスクは、APIがその安定したコンテンツの再処理をスキップするため、キャッシュヒットから恩恵を受けます。キャッシングが静かに破損すると、ユーザーはより遅い完了を見て、それをモデルの低速度またはネットワークラグではなく構成の問題に起因すると考えるかもしれません。

**コンテキストウィンドウの経済性。** agentic ワークフローでは、Agentの動作を導くために、システムコンテキストに参照資料（アーキテクチャガイド、命名規則、セキュリティポリシー）をピン留めすることがよくあります。キャッシングで、最初のヒット後にキャッシュされるため、より多くのこの参照資料を余裕を持たせることができます。正しいキャッシングなしでは、同じ資料は反復に高コストがかかり、チームはそれを削除するようになり、結果としてAgentの出力品質が低下します。

v2.1.237の修正はこれらの前提を復元します。しかし、より深い教訓は、キャッシュの正確性は破損するまで見えなくなるため、セットアップで明示的に検証する価値があるということです。

## 簡潔出力スタイル：長時間セッションでシグナルをノイズから分離

同じリリースで、「Concise」（簡潔）という新しい出力スタイルオプションが導入されました。これは異なる痛点に対応しています：冗長なAgent出力です。

デフォルトでは、Claude CodeのAgent モードはコード変更と共に完全な説明的なプロースを返します。これはInteractive セッションで便利です。推論を理解したいときです。しかし、terminal-heavy ワークフロー（ヘッドレスCI環境でAgentを実行する、Agentログをバルクでレビューする、または監査目的でトランスクリプトを保管する）では、その冗長性は実際の仕事成果（コード変更、ツール呼び出し、下した決定）を曖昧にするノイズを作り出します。

Concise モードは説明的なナラティブをストリップします。説明的出力なしで作業出力を削除しません。典型的な冗長なAgent ターンは次のようになります：

```
失敗したテストを分析して修正を実装します。まずエラーメッセージを調査して何が起こっているかを理解し、次に関連するコードセクションを見て、最後に根本原因に対応しながら副作用を引き起こさない的を絞った修正を書きます。

[... 8ファイル読み込み、2回のgrep ...]

問題はイベントリスナークリーンアップの競合状態です。現在のコードはコンポーネントを破壊する前の購読を解除していないため、アンマウント後にステイルコールバックが発火します。useEffect戻り値にクリーンアップステップを追加します。

[... 編集 ...]

修正は最小限で外科的です：クリーンアップ関数に2行追加されるだけです。これにより、リスナーはコンポーネントがアンマウントされる前に削除されます。
```

Concise モードでは、同じターンは次のようになります：

```
エラーを検査 → 解放でレース条件を検出 → 修正を適用（useEffect戻り値ハンドラ）。
```

CIログで20ステップのAgentタスクをスキャンしてパターンやデバッグを探している場合、違いは顕著です。Verbose モードは40～50 KBのプロースを生成します；Concise モードは2～3 KBのシグナルを生成します。コード変更自体は同一です。ナレーションのみが変わります。

これはいくつかのシナリオで有用です：

- **CIログ：** パイプラインでのAgentの実行は、実際のdiffを埋めない、よりスキャン可能でクリーンなトランスクリプトを生成します。
- **監査証跡：** コンプライアンスまたは学習目的でのAgentセッションの長期保存は、ノイズの削減から利益を得ます。
- **並行Agentの調整：** 複数のAgentが関連タスクで作業しており、プロースを読むことなく高度な決定を追跡する必要がある場合、Concise出力はコンテキストスイッチを削減します。
- **モデルコスト：** プローストークンが少ないほど、同じ作業出力に対するAPI コストが低下します。

トレードオフは、Agent が決定を下した理由を理解するのに価値がある推論の説明を失うことです。チームは、Verbose 説明を必要とするAgentタスク（Interactive 問題解決、デバッグ、アーキテクチャ決定）対 Concise 出力で対応できるタスク（日常的なリファクター、テスト追加、コード生成）を考慮深く決定する必要があります。

## Webhani の推奨：キャッシュフレンドリーなワークフロー構造

キャッシング修正と簡潔な出力の両方をうまく機能させるために、Agentコンテキストの設定方法に小さな構造的投資をお勧めします。

まず、安定したコンテキスト（システムプロンプト、ツール定義、参照資料）をターン固有コンテンツ（会話履歴、現在のPR diff）から分離します。これによりキャッシング境界が明示されます：

```yaml
# claude-code 設定（.claude/CLAUDE.md）
## プロジェクト構成
name: webhani-project
version: 1

## 安定したコンテキスト（最初のターン後にキャッシュ）
system_context: |
  あなたは、Webhani Inc.のAIコーディングアシスタントです。
  当社のコードベースはNext.js 16、React 19、TypeScript、およびTailwind CSSを使用しています。
  
  ### 命名規則
  - コンポーネント：PascalCase、プレフィックス Area（AreaHero、AreaServices）
  - フック：camelCase、プレフィックス use（useScrollReveal）
  - ファイル：非コンポーネントの場合はケバブケース

  ### Commitスタイル
  - 形式："feat: description"または"fix: description"
  - 共著者："Co-Authored-By: Claude Code <noreply@anthropic.com>"

reference_files:
  - src/lib/constants.ts      # i18n ロケールとグローバル定数
  - docs/architecture.md       # システム設計概要
  - .github/CODEOWNERS        # レビュールーティングの所有権ルール

## 出力設定
output_style: "concise"  # Interactive セッションの場合は"verbose"を使用
log_level: "info"        # CIでデバッグ出力を抑制
```

この構造により、以下が確保されます：
- システムコンテキストブロックは10 KB未満で保たれ、最初のAPI呼び出し後にキャッシュされます。
- 参照ファイル（定数、アーキテクチャドキュメント）はピン留めされてキャッシュされ、ターンごとに再送信されません。
- 出力スタイルは環境に合わせて調整されます（CIではConcise、Interactive開発ではVerbose）。

次に、キャッシングが正常に機能していることを確認します。Agent初期化に小さなチェックを追加します：

```typescript
// プロンプトキャッシングが有効化されているか確認
const client = new Anthropic({
  apiKey: process.env.ANTHROPIC_API_KEY,
});

const response = await client.messages.create({
  model: "claude-opus-5",
  max_tokens: 100,
  system: [
    {
      type: "text",
      text: "あなたは有益なアシスタントです。",
      cache_control: { type: "ephemeral" }  // 明示的なキャッシュ制御
    }
  ],
  messages: [
    { role: "user", content: "こんにちは" }
  ]
});

// キャッシュパフォーマンスの使用状況を確認
console.log("キャッシュ作成トークン:", response.usage.cache_creation_input_tokens);
console.log("キャッシュ読み込みトークン:", response.usage.cache_read_input_tokens);
console.log("通常の入力トークン:", response.usage.input_tokens);
```

後続の呼び出しで`cache_read_input_tokens`がゼロの場合、キャッシングが正常に機能していません。これはv2.1.237バグをキャッチしたはずのカナリアです。

第3に、タスクごとにConciseまたはVerboseが適切かどうかを決定します。決定マトリックス：

| タスク | モード | 理由 |
|--------|--------|------|
| Interactive デバッグ | Verbose | 決定を理解するために完全な推論が必要 |
| 日常的なコード生成 | Concise | シグナルノイズ；出力はコード |
| セキュリティレビュー | Verbose | 脅威分析を理解する必要 |
| CI自動リファクター | Concise | ノイズ削減；人間が後でdiffをレビュー |
| アーキテクチャ変更 | Verbose | 決定根拠を理解する必要 |

## まとめ

- **キャッシングバグは複合化するまで見えなくなります。** CIまたは永続的なassistantとしてagent 支援ワークフローを実行している場合は、プロンプトキャッシングが機能しているかどうかを監査します。トークン使用量フィールドを使用してキャッシュヒットが発生しているかどうかを確認します。
- **安定したコンテキストは明示的で、会話履歴から分離されるべきです。** CLAUDE.md またはシステムプロンプトを構造化し、システムの指示、ツール定義、参照資料がキャッシング用に明確にマークされていることを確認します。これによりターンが小さくなり、コスト予測可能性が実現します。
- **簡潔出力が普遍的に良いわけではありません。これはオプションです。** CIログ、監査証跡、日常的なコード生成にConcise モードを使用します。推論を見たいInteractive 問題解決、アーキテクチャ決定、デバッグにVerbose モードを使用します。
- **キャッシュの正確性はあなたが測定できるコスト制御レバーです。** キャッシングが機能しているかどうかに可視性がない場合、考えるより多くを支払っています。Agent セットアップにキャッシュヒット率をログするチェックを追加し、ドロップする場合にアラートを送ります。
