## Coding Assistantではなく運用Releaseのような変更履歴

Anthropicの最新Claude Code Releaseには、構造化されたフィードバックDraft生成、組み込みのコスト最適化ツール、そしてPluginおよびSessionのSafeguard強化という3つの機能が追加されました。派手なModel性能の向上ではありません。これはツールが「実験段階」を終え、他のInfrastructureが依存する本物のInfrastructureになったときに初めて出てくる、地味だが重要な機能群です。

これこそが本質です。Claude Codeは「Chat窓付きの賢い補完」から、半自律的に動作し、チームのAPI Budgetを消費し、PluginやBackground Sessionを通じて編集対象のFile以外にも影響を及ぼすAgentへと静かに変わってきました。webhaniではこの1年近く、Claude CodeをClient のCI Pipelineや社内開発Workflowに組み込んできましたが、繰り返し見えてくるパターンは同じです。ツールの成熟がGovernanceの整備を追い越してしまうのです。今回のReleaseはAnthropicがそのGapの一部を埋めたものであり、残りはAgentを導入するチーム側の責任です。

## なぜ従来のメンタルモデルが通用しないのか

Claude Codeを「賢いAutocomplete」として捉えているなら、評価軸はCode品質だけで済みます。しかし、CIで常駐するDev AssistantとしてClaude Codeを実行したり、Pluginを組み込んだ複数のBackground Sessionを並行運用したりする段階になると、他のInfrastructureであれば当然統制が必要な3つの性質を、暗黙のうちにAgentへ与えていることになります。

- **人間が1回ごとに承認しなくても消費できるBudget。** Turnごとに複数のTool呼び出しをループするAgent Sessionでは、単発のChat応答とは比較にならないスピードでコストが積み上がります。
- **実システムへの書き込み権限。** Editorで開いているFileだけでなく、付与したPluginとPermissionが許す範囲すべてに及びます。
- **Session間で持続するState。** 履歴、環境Context内のCredential、キャッシュされたTool結果など、何か問題が起きたときに監査証跡が必要になる種類のStateです。

コスト最適化ツールやSession Safeguardが実装されたのは、Anthropicがこの3つの性質を製品の一等市民として扱い始めたからです。導入するチームも同じ姿勢を取るべきです。

## 最小限で効果の高いGovernance Framework

大がかりなProcessは不要です。Client案件でよく見る失敗パターンをカバーするには、以下の3点で十分です。

**1. Session単位で紐づけたBudget Alert。** CI Job内の暴走Loopと、チーム全体でのじわじわとしたコスト増加は別の問題であり、それぞれ異なる検知方法が必要です。

```typescript
// scripts/agent-spend-guard.ts
import Anthropic from "@anthropic-ai/sdk";

const SESSION_BUDGET_USD = 5;    // CI Jobごと
const DAILY_BUDGET_USD = 150;    // チーム全体で1日あたり

async function trackSpend(usage: Anthropic.Usage, sessionId: string) {
  const inputCost = usage.input_tokens * 0.000003;
  const outputCost = usage.output_tokens * 0.000015;
  const sessionTotal = await incrementSessionSpend(sessionId, inputCost + outputCost);

  if (sessionTotal > SESSION_BUDGET_USD) {
    await killSession(sessionId, "session budget exceeded");
  }

  const dailyTotal = await getDailySpend();
  if (dailyTotal > DAILY_BUDGET_USD * 0.8) {
    await notifySlack(`Agent spend at ${Math.round((dailyTotal / DAILY_BUDGET_USD) * 100)}% of daily budget`);
  }
}
```

意図的に地味な実装にしています。目指しているのは洗練されたFinOps Dashboardではなく、暴走LoopがInvoiceの高額な1行になる前に発動するCircuit Breakerです。

**2. Dependency Reviewと同じ姿勢で行うPlugin Allowlist化。** Claude Code Pluginは、機能的にはTool呼び出し権限を持つ third-party Packageです。npm Dependencyに対して行うのと同じ規律、つまりVersion固定、更新時のDiff Review、そして各Pluginが触れる範囲のScope限定を推奨します。

```yaml
# .claude/settings.json (抜粋)
{
  "permissions": {
    "allow": [
      "Bash(npm run test:*)",
      "Edit(src/**)",
      "Read(**)"
    ],
    "deny": [
      "Bash(curl:*)",
      "Bash(rm -rf:*)",
      "Edit(.env*)"
    ]
  },
  "plugins": {
    "allowlist": ["internal-lint-fixer@1.2.0"],
    "requireApprovalForNew": true
  }
}
```

ここではAllow ListよりDeny Listの方が重要です。実際に見てきたIncidentの多くは、Pluginが特殊な動作をしたからではなく、誰も制限すべきと思っていなかったToolにAgentが手を伸ばしたことが原因でした。

**3. Session終了後も残るAudit Trail。** Background Sessionが数時間後に再開されたり、別のEngineerに引き継がれたりするとき、これから何をするかだけでなく、これまで何をしたかの記録が必要です。Tool呼び出しとその引数は、Agent自身のContextの外にあるStoreへLogし、混乱したSessionや不正なSessionが自らの履歴を消せないようにします。

## Verbose と Concise、厳格Modeと利便性のバランス

コストツールとSafeguardには実際のTrade-offが伴います。Permission Scopeを厳しくし、Budget Guardを絞るほど、正当な処理でもAgentがApproval待ちで止まる頻度が増えます。webhaniの目安は、Deploy Script・Secret・Infrastructure as Codeに触れるものは厳格Mode、日常的なRefactorやTest生成のように失敗しても「CI Runの失敗」程度で済むものは寛容Mode、という切り分けです。

| Context | Permission Mode | Budget Guard |
|---|---|---|
| 内部Utilityのrefactor | 寛容 | Soft Alertのみ |
| CI起点のCode Review | 寛容 | Session単位のCap |
| Deploy / IaC Fileの編集 | 厳格Allowlist | Hard Stop + 人間の承認 |
| Plugin駆動の自動化 | 明示的Allowlist | Plugin単位のCap |

## まとめ

- **Claude Codeがコストツールと強化されたSafeguardを出荷したこと自体が重要なSignalです。** これはツールが無人Infrastructureとして使われている実態をAnthropicが認め、それに合わせて開発していることの証拠です。
- **Budget GuardはSession単位でScopeすべきです。** チーム全体の集計だけでは、月次請求で驚く前に暴走Loopを止めることができません。
- **PluginはDependencyとして扱ってください。** Version固定、Default Deny、新規Tool Access付与前のReviewが基本です。
- **Permissionの厳格さはBlast Radiusに合わせてください。** Deploy ScriptとSecretはHard Stopに値しますが、日常的なCode生成に同じ摩擦は不要です。
