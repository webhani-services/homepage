2026年10月16日に公開されたClaude Code 2.1.302では、fork subagentが`claude -p`、Agent SDK、デスクトップアプリ、VS Code拡張でも既定で有効になりました。リリースノートを紹介する二次情報(公式changelogを一行ずつ突き合わせたわけではありません)によると、対話型ターミナルでは以前のバージョンですでに切り替わっていたため、今回の影響を受けるのは主にスクリプト、CI、自社ツールからClaude Codeを呼び出している方です。

ターミナルUIだけを使っている場合、ほとんど変化はありません。一方で`claude -p`やAgent SDKを組み込んだパイプラインがある場合は、委任された作業の挙動がコストと情報露出の両面で変わるため、確認しておく価値があります。

## forkと通常のsubagentの違い

通常のsubagentは新しいコンテキストから始まります。親がプロンプトを書き、子はそのプロンプトと自分で読んだファイルをもとに作業し、要約を返します。子が何を知っているかは親が決めます。

forkは親の会話履歴全体を引き継ぎます。親に戻るのはforkの最終結果だけなので、途中のツール呼び出しで親のコンテキストが埋まることもありません。たとえば作業の途中で「このテストがflakyな理由を調べて」と頼めば、子はリポジトリ構成、失敗ログ、ここまでの判断をすでに把握しているため、再説明が不要になります。

その代わり、設計上のトレードオフがあります。

| | 通常のsubagent | fork |
|---|---|---|
| 初期コンテキスト | 親が書いたプロンプト | 親の履歴すべて |
| プロンプトの質への依存 | 高い | 低い |
| 開始時のトークンコスト | 小さい | 親の履歴に比例 |
| 子が見られる情報 | 渡された/自分で読んだもの | 親が見たものすべて |
| 返却される内容 | 要約 | 最終結果のみ |

## アップグレード前に確認したいこと

### 1. 委任ごとの開始コスト

forkは親と同じ大きさのコンテキストで始まります。共有プレフィックスが温まっていればプロンプトキャッシュが効きますが、長いセッションの終盤で複数のforkに分岐するヘッドレスジョブでは、大きなプレフィックスを何度も支払うことになり得ます。キャッシュが吸収してくれると仮定せず、アップグレード前後で1回の実行あたりのトークン使用量を計測してください。2.1.302では`/config`にidle compactionの切り替えも追加されているため、[prompt cache TTLとidle compactionの記事](/blog/claude-code-idle-compaction-prompt-cache-ttl-2026)も参考になります。

### 2. 子から何が見えるか

ここは意識的に判断すべき点です。forkは親がすでに見たファイル内容やツール出力を参照できます。対話セッションでは望ましい挙動ですが、自動化ジョブでは、親が冒頭で`.env`や顧客データのエクスポート、機密を含むログを読んでいた場合、forkもそれをすべて持った状態で動きます。「この子にはdiffだけ渡す」という緩い隔離としてsubagentを使っていたなら、forkはその境界を静かに取り払います。

本当に隔離が必要な処理では、subagentの種類に頼らないでください。セッション全体が読める範囲を絞り、ジョブごとに認証情報のスコープを分け、機密を読む処理を委任を行うセッションから切り離すのが確実です。

### 3. ヘッドレス実行の権限モード

同じリリースで、権限モードを指定しない`claude -p`やSDKセッションの既定も変わっています。サードパーティプロバイダー利用時、テレメトリ無効時、新規インストール時は、default modeで開始されます。`--permission-mode auto`を明示すればauto modeは維持されます。暗黙のモードに依存して動いていたジョブが承認待ちで止まる可能性があり、ヘッドレスでは応答できません。スクリプトでは必ず明示してください。

```bash
claude -p "Run the test suite and summarize failures" \
  --permission-mode auto \
  --output-format json
```

### 4. オプトアウト

`CLAUDE_CODE_FORK_SUBAGENT=0`でforkを無効化できます。リリース内容を紹介する情報によれば、`claude mcp serve`は常にforkを提供しないため、MCP経由でClaude Codeを公開しているサーバーは影響を受けません。

```bash
# 隔離されたsubagentに依存するパイプラインの挙動を固定する
export CLAUDE_CODE_FORK_SUBAGENT=0
```

既存の自動化ではまず`0`で固定し、効果を測定してからジョブ単位でforkを有効にする進め方をおすすめします。

## 現実的な移行手順

1. `claude -p`やAgent SDKを呼び出している箇所(CI、定期実行、社内Bot)を**洗い出す**。
2. 各所で`CLAUDE_CODE_FORK_SUBAGENT=0`と明示的な`--permission-mode`を**固定**し、アップグレードで挙動が変わらない状態にする。
3. CLIを**アップグレード**し、出力に他の変化がないことを確認する。
4. リスクの低いジョブ1つで**forkを試す**。固定した基準とトークン使用量・結果品質を比較する。
5. ジョブごとに**判断**する。共有コンテキストが活きる調査系はfork向き。機密に触れるジョブや信頼できない入力を扱うジョブは向きません。

## forkが向くケース

再説明のコストが、コンテキストを持ち運ぶコストを上回る作業に向いています。たとえば、再現したばかりの不具合の調査、同じ出発点からの別実装の並列検証、セッションで行った変更のレビューパスなどです。逆に、子の役割が意図的に狭く、親の履歴がノイズか機密ばかりの場合には不向きです。

## まとめ

- 影響を受けるのは主にヘッドレス、SDK、デスクトップ、VS Code利用者で、ターミナルはすでに切り替わっていました。
- forkは、プロンプト作成の手間と引き換えに、コンテキストサイズと隔離性を差し出します。
- 非対話の呼び出しでは権限モードを必ず明示してください。
- アップグレード時は`CLAUDE_CODE_FORK_SUBAGENT=0`で固定し、forkは意図して採用します。
- subagentの種類はセキュリティ境界ではなく、利便性の仕組みとして扱ってください。
