チームでClaude Codeを使っているなら、ワークフローの土台になっているツールはほぼ毎日変わっています。リリース追跡サイトのhavopticは、10月9日時点の最新をv2.1.296とし、直近30日で25回のリリースがあったと集計しています。これはAnthropic公式のchangelogではなくサードパーティの集計なので、数字は目安として扱ってください。ただ、更新頻度が高いこと自体は確かで、多くのチームがまだ答えを出していない問いが浮かびます。新しいバージョンへいつ、誰の判断で全員が移行するのか、という問いです。

## 10月前半に何が変わったか

10月のビルドをまとめているトラッカーによると、変更はバグ修正にとどまりません。報告されている項目は次のとおりです(利用前に公式changelogで確認してください)。

- デフォルトモデルの変更。v2.1.293でHaiku系モデルがデフォルトになったと報告されています。
- マーケットプレイスから直接プラグインをインストールできるようになった(v2.1.292)。
- サブエージェントが費やす労力の制御、続いて使用モデルの選択ができるようになった。
- 失敗したフックの扱いの変更。失敗時にブロックするオプションが追加された(v2.1.295)。
- プラグインがツールのより深い挙動を変更できるようになった(v2.1.287)。

いずれも、チームが依存しているものに触れます。コスト、出力品質、セキュリティ体制、そして自分たちで作ったガードレールです。デフォルトモデルが変われば請求額も、見かける間違いの種類も変わります。失敗時にブロックするようになったフックは、以前は素通りしていたパイプラインを止めることがあります。

## 現場でよく見る失敗パターン

導入支援の現場では、同じ4つの問題によく出会います。

1. **気づかない挙動のドリフト。** 誰かが更新してデフォルトモデルが変わり、その人の結果がチームの他メンバーと比較できなくなる。
2. **特定バージョンの挙動に依存したガードレール。** ある終了コードの挙動を前提に書いたフックが、更新後に静かに間違ったものになる。
3. **審査されないプラグイン。** マーケットプレイスからのインストールは、コード実行の判断です。npmの依存パッケージと同じ審査に値します。
4. **コストの想定外。** モデルやサブエージェントの既定値が、1タスクで消費するトークン量を左右する。

## 軽量な運用方針

大げさな委員会は要りません。次の4つで、リスクの大半をカバーできます。

**1. プロジェクト設定でモデルを明示的に固定する。** デフォルトを継承しないでください。リポジトリにコミットした共有の `.claude/settings.json` があれば、選択をレビューできます。

```json
{
  "model": "claude-sonnet-5-5",
  "permissions": {
    "deny": ["Bash(rm -rf:*)", "Read(./.env)"]
  }
}
```

キー名やモデルIDは、最新の設定ドキュメントで確認してください。過去に変更された例があります。重要なのは、決めるのが各自のノートPCではなくリポジトリだという点です。

**2. 更新サイクルを決める。** 一例として、担当者(持ち回りでも可)が週1回更新し、リリースノートを読み、リポジトリのフックに対する短いスモークテストを実行して、新しいベースラインを告知します。他のメンバーは次の告知までそのベースラインに留まります。規制の厳しい環境では、自動更新に任せず、ブートストラップスクリプトでインストールするバージョンを固定してください。

**3. 更新のたびにガードレールのスモークテストを行う。** 動くところを見たことがないフックは、信頼できません。保護用のフックごとに既知の危険な入力を与え、呼び出しがブロックされることを検証する小さなスクリプトを用意します。

```bash
#!/usr/bin/env bash
# scripts/check-claude-guardrails.sh
set -euo pipefail

echo '{"tool_name":"Bash","tool_input":{"command":"rm -rf /tmp/x"}}' \
  | .claude/hooks/block-destructive.sh && {
    echo "FAIL: destructive command was not blocked"; exit 1; }
echo "OK: destructive command blocked"
```

ローカルだけでなくCIでも実行してください。フックを「失敗時に止まる」設計にする方法は、以前の記事で扱っています。

**4. プラグインは依存パッケージとして扱う。** 利用するマーケットプレイスを許可リストで管理し、インストール前にプラグインのフックとコマンドを読み、承認済みの一覧をリポジトリに記録します。フックを登録するプラグインは、ツール呼び出しのたびにユーザー権限で動きます。

## コストと品質は、推測せず測る

デフォルトモデルやサブエージェントの設定が変わったときは、変更前後の簡単な比較で十分です。代表的な3タスク(バグ修正、リファクタリング、テスト作成)を旧設定と新設定で実行し、所要時間、トークン使用量、テストに通るかを比べます。小さく高速なモデルは、探索や検索を担うサブエージェントには適していることが多い一方、設計や、セキュリティに関わる編集には向かないことが多いです。この組み合わせは、継承ではなく意図して決める価値があります。

## webhaniの推奨

- モデルと権限ルールを固定するプロジェクト設定ファイルをコミットする。
- 週次の「ベースライン担当」を決め、ベースラインのバージョンをチームのドキュメントに載せる。
- ガードレールのスモークテストをCIに追加する。
- プラグインはサードパーティコードとしてレビューし、承認済みリストをバージョン管理する。
- リリースノートに「default」とあれば、コストと挙動に影響すると考えて検証する。

リリースサイクルが速いのは、多くの面で良いことです。不具合がすぐ直ります。代償として、チームの開発ツールが「動く依存関係」になります。アプリケーションの依存関係に行っているのと同じバージョン固定とレビューをツールにも適用すれば、わずかな手間で想定外の大半を防げます。
