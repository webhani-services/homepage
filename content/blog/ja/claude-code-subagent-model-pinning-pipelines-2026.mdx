AI コーディングを1つのセッションで使う段階から、探索担当・実装担当・レビュー担当といったサブエージェントのパイプラインへ移行すると、新しい問いが生まれます。各ステップでどのモデルを動かすのか、そして誰がそれを決めるのか、という問いです。

Claude Code 2.1.290 から 2.1.296 を扱った週次のまとめ(2026年10月11日の週)によると、サブエージェントに関する新しい制御が追加されています。パイプライン内のすべてのサブエージェントを1つのモデルに固定するワークフロー単位の設定や、Agent ツールの effort 制御などです。執筆時点では、設定名の詳細を公式のチェンジログで確認できなかったため、具体的なオプション名に依存する前に Claude Code のリリースノートを確認してください。この記事で扱うのは、機能の背後にある設計上の問いであり、構文に関係なく成り立つ内容です。

## ステップごとのモデル選択が重要な理由

複数ステップのエージェントワークフローでは、モデルは3つの観点に影響する変数です。

**コスト。** 探索(grep、ファイル読み込み、要約)は量が多く、小さなモデルでも十分なことが多い作業です。複雑なロジックの実装やレビューには、より強いモデルが効きます。すべてを最大のモデルで動かすのは簡単ですが高くつき、すべてを最小のモデルで動かすと安い代わりに手戻りが増えます。

**再現性。** サブエージェントが親セッションのモデルを暗黙に継承する場合、同じワークフローでも、誰が起動したか、何を選択していたかによって結果が変わります。そうなると失敗の再現が難しくなり、プロンプト変更の評価も困難になります。

**レビュー可能性。** パイプラインの挙動がバージョン管理されたファイルで定義されていれば、プルリクエストの差分に「レビュー担当のエージェントが別のモデルで動くようになった」と現れます。開発者のローカル選択に依存していると、その変更は見えません。

## 定義ファイルで固定する

Claude Code のサブエージェントは YAML フロントマター付きの Markdown ファイルで定義され、ドキュメント化されているフロントマターには `model` フィールドがあります。ここで固定するのが最も明示的な方法です。

```markdown
---
name: code-explorer
description: Read-only codebase search. Use for locating files and call sites.
tools: Read, Grep, Glob
model: haiku
---

You search the repository and report file paths and short excerpts.
Do not propose changes. Do not read files outside the repository root.
```

```markdown
---
name: change-reviewer
description: Reviews a diff for correctness and security issues.
tools: Read, Grep, Glob, Bash
model: opus
---

Review the staged diff. Report only issues you can point to by file and line.
Separate confirmed defects from suspicions.
```

量が多く安価に済ませたい役割は小さなモデルに、判断が重い役割は大きなモデルに固定しています。この割り当ては、適用先のプロンプトの隣、つまりリポジトリの中にあります。

## 単一モデルへの固定が向いている場面

ワークフロー単位の固定(パイプライン内の全サブエージェントで1つのモデル)は、別のトレードオフです。ステップごとの最適化を手放す代わりに、予測可能性を得ます。次の3つの場面で選択肢になります。

1. **プロンプトやワークフローの変更を評価するとき。** モデルを固定すれば、出力の違いがモデルのばらつきではなく、自分たちの変更に由来すると言えます。
2. **規制や監査のある環境。** ある変更をどのモデルが処理したか説明する必要がある場合、複数が混在するより、固定された1つの値のほうが文書化しやすくなります。
3. **インシデントの再現。** 自動実行が悪い結果を出したとき、同じ条件で再実行したくなります。

日常の開発では、役割ごとの固定のほうが、コストと品質のバランスは通常良くなります。

## 固定を監査可能にする軽量な方法

どの仕組みを使うにしても、固定されていないエージェントが紛れ込まないよう検査を追加しておきます。CI の小さなスクリプトで、すべてのエージェント定義が model を宣言していることを強制できます。

```ts
// scripts/check-agent-models.ts
import { readdirSync, readFileSync } from "node:fs";
import { join } from "node:path";

const dir = ".claude/agents";
const missing: string[] = [];

for (const file of readdirSync(dir).filter((f) => f.endsWith(".md"))) {
  const text = readFileSync(join(dir, file), "utf8");
  const frontmatter = text.match(/^---\n([\s\S]*?)\n---/)?.[1] ?? "";
  if (!/^model:\s*\S+/m.test(frontmatter)) missing.push(file);
}

if (missing.length > 0) {
  console.error(`Agents without an explicit model: ${missing.join(", ")}`);
  process.exit(1);
}
```

Lint と同じジョブで実行してください。コストは数行、得られるのは「このエージェントはどのモデルで動くのか」という問いに、常にリポジトリ内で答えられる状態です。

## あわせて押さえたい権限まわりの修正

同じまとめには、Bash の deny / ask ルールがスキップされるケースの修正や、UNC パスのファイル読み込みに関する権限バイパスの修正も挙げられています。サブエージェントの権限は、それ自体を別途レビューすべきだという注意喚起です。サブエージェントに `Bash` を渡すときは、許可するコマンドを他の権限付与と同じように扱い、allowlist を狭く保ち、読み取り専用のエージェントは読み取り専用のままにします。権限面については、以前のサブエージェントの権限制御に関する記事でより詳しく扱いました。

## webhani の推奨

- **まず役割を定義し、その後にモデルを割り当てる。** 探索・実装・レビューは求められるものが違います。モデルを選ぶ前に書き出してください。
- **バージョン管理の中で明示的に固定する。** 再現したいものについては、親セッションからの継承に頼らないこと。
- **小さくする前に測る。** ある役割を小さなモデルへ移し、過去のタスクの固定セットで実行して、コストだけでなく結果も比較します。
- **CI でチェックする。** モデルを宣言せずに新しいエージェントを追加できないようにします。
- **オプション名は最新のリリースノートで確認する。** チーム向けドキュメントに書き込む前に必ず確認してください。

モデル選択は、コストと品質に実質的な影響を持つ設定上の判断です。それをコードと同じように、宣言し、レビューし、テストすることが、エージェントパイプラインをチームで保守できるものにします。
