10月21日、AnthropicはスタンドアロンのエージェントアプリClaude Duetのリサーチプレビューを開始しました。対象は米国のウェイトリストに登録したProおよびMaxの契約者です。報道によると、Duetは連携したアカウントを数時間おきに確認し、プロンプトを待たずに作業を進め、送信・支払い・署名・削除の前には必ず承認を求めます。また、パスワードやログイントークンを直接は参照しないとされています。

私たちはまだDuetを使っておらず、製品の詳細は二次情報に基づくため、仕様は暫定的なものとして扱ってください。注目したいのは設計の形です。先に動くエージェントでは、安全性の問題が変わります。各ターンを人が見ているわけではないので、重要な統制は「出力をレビューする」から「副作用を関所で止める」へ移ります。お客様向けにエージェントを作るなら、同じ構造が必要になります。以下にその一例を示します。

## 先に動くエージェントは何が違うのか

チャット型のアシスタントは受け身です。ユーザーがメッセージを送り、回答を読み、次の行動を決めます。すべての行動が構造上、人を経由します。

先に動くエージェントはこれが逆になります。スケジュールやイベントで起動し、受信箱やカレンダーを読み、自分で「これをやるべきだ」と判断します。ここから次のことが起きます。

- **信頼できない入力が無人のまま届く**：午前3時にエージェントが読むメールに、エージェント宛ての指示が紛れているかもしれません。誰も気づきません。
- **誤りが誰にも見られないまま積み重なる**：午前9時の誤った操作が、正午の誤った計画の入力になります。
- **承認疲れが最大のリスクになる**：何でも確認してくるエージェントでは、人は中身を読まずに「承認」を押すようになります。

報じられているDuetの方式は、会話ではなく「アクション」を分類しています。読み取りは自由で、影響の大きい少数の動詞だけが人の承認を必要とします。

## リスク階層つきのアクションポリシー

最も単純で有効な実装は、エージェントが呼べるすべてのツールを階層に対応づけるポリシー表を作り、モデルの外側で強制することです。

```ts
type Tier = "auto" | "approve" | "deny";

interface ToolPolicy {
  tier: Tier;
  // 呼び出し時に評価する任意のガード（支出上限など）
  guard?: (args: Record<string, unknown>) => boolean;
}

const policy: Record<string, ToolPolicy> = {
  "calendar.read":   { tier: "auto" },
  "mail.search":     { tier: "auto" },
  "mail.draft":      { tier: "auto" },
  "mail.send":       { tier: "approve" },
  "payments.charge": { tier: "approve", guard: (a) => Number(a.amount) <= 50_000 },
  "docs.sign":       { tier: "approve" },
  "files.delete":    { tier: "approve" },
  "shell.exec":      { tier: "deny" },
};
```

重要なのは、このポリシーがシステムプロンプトではなくランタイムにあることです。プロンプトは言いくるめられますが、ルックアップ表は言いくるめられません。未知のツールは`deny`が既定です。

## 承認キュー

呼び出しが`approve`階層に入ったとき、エージェントはブロックせず、リクエストを保留して他の作業に進むべきです。

```ts
interface PendingAction {
  id: string;            // 冪等キー（リトライしても同じ値）
  tool: string;
  args: Record<string, unknown>;
  reason: string;        // エージェント自身が述べた理由
  sourceRefs: string[];  // きっかけになったメッセージIDやドキュメントURL
  createdAt: string;
  expiresAt: string;
}

async function dispatch(call: ToolCall, ctx: AgentContext) {
  const rule = policy[call.tool];
  if (!rule || rule.tier === "deny") throw new PolicyError(call.tool);
  if (rule.guard && !rule.guard(call.args)) throw new PolicyError(call.tool);

  if (rule.tier === "auto") return execute(call);

  const pending: PendingAction = {
    id: ctx.idempotencyKey(call),
    tool: call.tool,
    args: call.args,
    reason: call.reason,
    sourceRefs: ctx.currentSources(),
    createdAt: new Date().toISOString(),
    expiresAt: addHours(new Date(), 24).toISOString(),
  };
  await approvalQueue.put(pending);
  return { status: "awaiting_approval", id: pending.id };
}
```

ポイントは3つあります。

**冪等キー**：タイムアウト後にリトライしたエージェントが、同じメールを2回送ってはいけません。キーは試行ではなく「意図」から導出します。

**ソース参照**：承認者には、エージェントが「なぜ」動きたいのか、どのメッセージがきっかけなのかを見せます。これは注入された指示への最良の防御です。「見知らぬ送信者からのメールをきっかけに、新しい宛先へ請求書を送る」という申請なら、モデルが見逃したものを人が見つけられます。

**有効期限**：古い承認は危険です。一晩で状況が変わっていたら、昨日の状態で出した承認を今日実行してはいけません。

## 認証情報は共有せず、スコープを絞る

AnthropicはDuetがパスワードやログイントークンを直接は参照しないと説明しています。同じ性質を目指せます。モデルには秘密情報を見せず、ツール実行側が、範囲を絞った短命の認証情報を持つ構成です。メールのエージェントなら、読み取りと下書き作成ができるトークンと、送信スコープを承認経路でしか使わない仕組みに分けます。「下書き」と「送信」を認証情報の段階で分ければ、プロンプトを乗っ取られても関所を迂回できません。

## 承認疲れへの対策

すべての操作にクリックが必要なら、関所は飾りになります。有効な工夫は次のとおりです。

- **意図ごとにまとめる**：3件の返信を別々に聞くのではなく、「送信予定の返信3件」を差分つきで見せます。
- **変更点を見せる**：カレンダーの変更なら、旧時刻と新時刻を並べて表示します。
- **レビュー後に常設ルールを許可する**：「この社内配信リストへの返信は常に承認」は、人が選んだ後なら妥当です。取り消せて、記録が残る形にします。
- **拒否率を計測する**：承認者の拒否が1%未満なら、エージェントが優秀か、誰も読んでいないかのどちらかです。抜き取りで監査してください。

## 事後のためのログ

提案されたアクション、承認、拒否、実行のすべてを、きっかけになったソースとともに追記専用のログに残します。先に動くシステムで問題が起きたとき、問いはいつも「何を見て、なぜそれを指示だと思ったのか」です。ログがなければ答えられません。

## webhaniの推奨

スケジュールで動くエージェントを依頼されたら、次の順で進めます。

1. 最初の2週間は読み取り専用で動かし、「実行していたはずの操作」をレビューする。
2. 階層表をコードに置き、未知のツールは拒否を既定にする。
3. 承認にソース参照を持たせ、期限を設ける。
4. 秘密情報をモデルのコンテキストに入れず、認証情報はアクション単位で絞る。
5. 承認率と拒否率をヘルスメトリクスとして追う。

Duetはリサーチプレビューであり、Anthropic自身も制約があると説明しています。それでも「読み取りは自由、副作用は関所を通す」というパターンはベンダーを問わず有効です。最初の無人実行の前に組み込んでください。最初のインシデントの後では遅いのです。
