## Fable 5.1とMythos 5.1が届いた

2026年9月1日、AnthropicはClaude Fable 5.1とClaude Mythos 5.1を発表しました。両者は同一のモデルをベースにしており、Fable 5.1は本番運用向けの安全対策を備えた一般提供版、Mythos 5.1はサイバーセキュリティやライフサイエンス領域の審査済み組織向けに、制約を緩めた形で提供される版という位置づけです（参考: [Anthropic公式発表](https://www.anthropic.com/claude-fable-and-mythos-5-1)）。

今回の発表で実務上インパクトが大きいのは、新機能の追加そのものよりも「Cache Read料金の75%値下げ」と「エージェント型タスクでのベンチマーク向上」です。本稿ではこの2点を中心に、webhaniの視点で実務への影響を整理します。

## Cache Readとは何か、なぜ75%値下げが効くのか

Claudeを含む多くのLLM APIには「プロンプトキャッシュ」という仕組みがあります。長いシステムプロンプトや繰り返し参照するコンテキスト（コードベースの一部、ドキュメント、過去の会話履歴など）を一度サーバー側にキャッシュしておき、次回以降のリクエストではキャッシュヒット分を通常より安い単価で読み出す、という仕組みです。

今回の発表によると、Cache Readの単価は100万トークンあたり1ドルから0.25ドルへ、75%引き下げられました。これにより、典型的なタスクで約25%、複雑なエージェント型ワークフローでは最大45%のコスト削減が見込めるとされています（参考: [VentureBeat](https://venturebeat.com/technology/anthropics-claude-fable-5-1-and-mythos-5-1-arrive-with-a-75-cost-reduction-for-fable-cache-reads), [gHacks](https://www.ghacks.net/2026/09/03/anthropic-releases-claude-fable-5-1-and-cuts-cached-token-pricing-by-75/)）。

エージェント型のコーディングツール（Claude Codeのようなツール）は、1回のタスクの中で同じコードベースやシステムプロンプトを何度も参照します。ツールの実行結果をコンテキストに積み上げながら、何十回ものAPI呼び出しを繰り返す構造上、キャッシュヒット率が高くなりやすく、Cache Read単価の値下げの恩恵を最も受けやすいユースケースです。

## プロンプトキャッシュの基本パターン

Anthropicが公式に文書化しているプロンプトキャッシュの使い方を、TypeScriptで示します。長い静的コンテキスト（コーディング規約やコードベースの説明など）に `cache_control` を付与するだけで、以降のリクエストで再利用されます。

```typescript
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

const CODEBASE_CONTEXT = `
# プロジェクトのコーディング規約
- コンポーネント名はArea接頭辞を使う
- 翻訳キーはuseTranslationsフックでアクセスする
...(長いドキュメント)
`;

async function askAboutCode(question: string) {
  const response = await client.messages.create({
    model: "claude-fable-5-1",
    max_tokens: 1024,
    system: [
      {
        type: "text",
        text: CODEBASE_CONTEXT,
        cache_control: { type: "ephemeral" },
      },
    ],
    messages: [{ role: "user", content: question }],
  });
  return response;
}
```

`cache_control` を付けた部分は、同一内容であれば以降のリクエストでキャッシュから読み込まれます。エージェント型のワークフローでは、この「静的な部分」と「都度変わる部分」を意識して切り分けることが、コスト最適化の第一歩です。

## 簡易的なコスト試算

たとえば1日1,000回のAPI呼び出しがあり、そのうち平均8,000トークン分がキャッシュヒットするワークフローを考えます。

- 値下げ前: 8,000トークン × 1,000回 × $1/1,000,000 = $8/日
- 値下げ後: 8,000トークン × 1,000回 × $0.25/1,000,000 = $2/日

単純計算でCache Read分のコストが4分の1になります。実際のワークフローでは非キャッシュ部分のトークンも課金対象になるため削減率はここまで単純ではありませんが、キャッシュヒット率が高いワークフローほど恩恵が大きいことがわかります。

## ベンチマークが示すエージェント型コーディングの進化

Anthropicが公開したベンチマークによると、Fable 5.1はTerminal-Bench-Scienceで52.6%を記録し、Fable 5の24.7%から倍以上に向上しました。またCursorBench 3.2の agentic coding評価では73.4%を記録し、複雑なタスクにおいて自己検証（生成したコードや実行結果を自分で確認し修正する）に強みがあるとされています（参考: [MarkTechPost](https://www.marktechpost.com/2026/09/01/anthropic-releases-claude-fable-5-1-and-claude-mythos-5-1-52-6-on-terminal-bench-science-and-75-cheaper-cache-reads/)）。

ベンチマークの数値自体を鵜呑みにするのではなく、「自己検証能力の向上」という方向性に注目すべきです。エージェントが自分の出力を疑い、テストを実行し、失敗したら修正する、というループを回せるかどうかは、実務でエージェントに任せられるタスクの範囲を左右します。

## webhaniの実務での見立て

顧客プロジェクトでAIコーディングエージェントを運用する立場から、いくつか実務上のポイントを挙げます。

1. **キャッシュ設計を最初から意識する**：システムプロンプトやコードベースの説明を「変わらない部分」として切り出し、`cache_control` を付与する設計を、エージェント構築の初期段階で組み込むべきです。
2. **ベンチマークより自社ワークロードでの検証を優先する**：公開ベンチマークはあくまで目安です。実際のコードベースやタスクでA/Bテストを行い、コストと品質のバランスを確認することを推奨します。
3. **モデル移行時の互換性確認を忘れない**：モデルの切り替えには、出力フォーマットやツール呼び出しの挙動に微妙な差異が出ることがあります。本番投入前に既存のエージェントフローで回帰テストを行うべきです。

## まとめ

Claude Fable 5.1のCache Read値下げは、単なる価格改定ではなく、エージェント型コーディングというユースケースそのものへの最適化と捉えるべきです。同時にベンチマークの向上は、エージェントに任せられる作業範囲が着実に広がっていることを示しています。webhaniでは、こうしたモデルの進化を踏まえたコスト設計とエージェント運用の支援を継続していきます。
