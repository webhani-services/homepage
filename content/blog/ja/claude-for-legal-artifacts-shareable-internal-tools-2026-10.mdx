2026年10月28日、Anthropic は Claude for Legal に、すぐ使える Artifacts のギャラリーを追加しました。報道によると、Artifacts はトラッカーやダッシュボードのようなインタラクティブなツールで、チームが自分たちの文書につなぎ込み、そのまま共有できます。Anthropic が用意したテンプレートは、cite check、jurisdiction matrix、matter board、playbook deviation、regulatory scan、tabular review の6種類です。これに加えて、法律事務所、ベンダー、非営利団体が作ったものも並んでいます。

話題の中心は法務ですが、多くのエンジニアリングチームにとって興味深いのは「届け方」の部分です。LLM がチャットで答えるだけでなく、同僚が再利用できる小さな状態付きのインターフェースを生成する。このパターンは法務以外にも当てはまります。

## 仕事の単位が変わった点

これまで「LLM を繰り返しの作業に使う」といえば、保存したプロンプトや専用アシスタントのことでした。出力はテキストです。常に並び替えられた表、ステータスを追跡するボード、毎回同じルールで走るチェッカーが欲しければ、誰かが本物のアプリケーションを作る必要がありました。

Artifacts はこの境界を動かします。インターフェース、その裏のロジック、サンプルデータがひとまとめで提供され、チームは自分たちのデータソースをつなぐだけで調整できます。Claude for Legal は5月の登場以降、60を超えるコネクタが追加されたと報じられており、この「自分の文書をつなぐ」工程を現実的なものにしています。

ソフトウェアチームから見ると、スプレッドシートと本格的な社内アプリの中間に新しい層ができた、ということです。作るのが安く、共有も簡単なので、だからこそルールが必要になります。

## 向いているケースと向いていないケース

共有可能な Artifact が合うのは、次のような場面だと考えています。

- **チェックリストが安定しているレビュー業務。** playbook deviation のようなビューは、実質的に「ルール × 文書」の表です。構造はあまり変わらず、中身だけが変わります。
- **少人数チームのステータスボード。** 5人で使う案件ボードやリリーストラッカーに、独立したサービスは割に合いません。
- **本格開発の前の探索。** 本当に必要な機能を知るために、先に Artifact で試すのは速い方法です。

一方で、監査に耐える保証、厳格なデータ保持ルール、トランザクション整合性、LLM セッションから到達させたくないシステムとの連携が必要な場合は不向きです。その場合は Artifact をプロトタイプとして扱い、置き換える前提で進めてください。

もう一点、ギャラリーを解説した二次情報では、テンプレートは実際のクライアント案件ではテストされておらず、精度も測定されていないと指摘されています。これはどの領域にも通じる注意点です。見た目の整ったインターフェースは、モデル呼び出しの実力以上に出力を権威的に見せてしまいます。

## 展開前に決めておきたいガバナンス

発表では、組織の内外への共有と、チーム間のエシカルウォールを支える設定に触れられています。法務以外でも、同等の問いが生じます。

1. **組織外への共有は誰ができるか。** 既定ではオフにして、チーム単位で有効化します。
2. **Artifact はどのコネクタを使えるか。** 文書ストアにつないだトラッカーは、そのストアの機密度を引き継ぎます。OAuth のスコープをレビューするのと同じ感覚でコネクタを確認してください。
3. **作成者が異動・退職したら誰が所有するか。** 所有者がいないと、共有ツールのルールは更新されなくなります。
4. **出力が正しいとどう確認するか。** 正解が分かっている小さなサンプルを用意し、モデルや Artifact が変わるたびに再実行します。

4 を具体化する軽い方法として、Artifact の説明の隣に回帰チェックを置いておく例を挙げます。

```ts
// artifact-checks.ts: 既知の入力と期待する指摘
type Check = { input: string; mustFlag: string[]; mustNotFlag: string[] };

export const checks: Check[] = [
  {
    input: "fixtures/nda-missing-termination.txt",
    mustFlag: ["termination clause missing"],
    mustNotFlag: ["governing law missing"],
  },
];

export function evaluate(check: Check, findings: string[]) {
  const missed = check.mustFlag.filter((f) => !findings.includes(f));
  const spurious = check.mustNotFlag.filter((f) => findings.includes(f));
  return { ok: missed.length === 0 && spurious.length === 0, missed, spurious };
}
```

あえて単純にしています。目的は、モデル更新後に「挙動は変わったか」を誰かの気づきに頼らず、実行可能な形で答えられるようにすることです。

## webhani の推奨

顧客にこのパターンを勧めるなら、次の順序をお勧めします。

1. 繰り返しが多く、チェックリストが明確なレビューまたは追跡業務を1つ選ぶ。
2. サンプルデータと、期待出力の小さなチェック付きで Artifact として作る。
3. 共有はパイロットチームに限定し、使用するコネクタを文書化する。
4. 1か月後に、継続・本格アプリへの格上げ・廃止のいずれかを決める。

最も重要なのは 4 です。手軽に共有できるツールのリスクは、派手に壊れることではなく、誰も決めないまま静かに業務の基盤になってしまうことにあります。

法務向けギャラリーは、汎用 LLM クライアントが「質問に答える」から「小さな共有ツールをホストする」方向へ向かうことを示す良い予告編です。コネクタのレビュー、所有者の明確化、出力のテストが習慣になっているチームは安全に採用できます。まだの場合は、その習慣づくりが先です。
