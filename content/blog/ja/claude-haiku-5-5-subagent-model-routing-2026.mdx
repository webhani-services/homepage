2026年10月初旬、AnthropicがClaude Haiku 5.5をリリースしました。5.5ファミリーの中で最も高速かつ低コストなモデルとされ、要約・分類・データベースクエリ生成のような大量処理や、Opus 5.5・Sonnet 5.5の下で動くサブエージェント用途を想定していると報じられています。大きなコンテキストウィンドウや調整可能なeffortレベルについての情報もありますが、これらは二次情報で、媒体によって記述が異なります。仕様や価格は、必ずAnthropic公式のドキュメントで確認してください。

モデルの細部よりも重要なのは、このモデルが投げかける設計上の問いです。エージェントのワークフローの中で、本当に最強のモデルが必要なステップはどれでしょうか。

## よくある失敗: すべてを1つのモデルで処理する

エージェントを単一のモデルに接続したまま運用しているチームは少なくありません。動作はしますが、最もコストのかかる構成でもあります。典型的なコーディングエージェントやサポートエージェントは、トークンの大半を難しくないステップに使っています。

- ファイルを読んで関連があるか判断する
- 受信したリクエストを分類する
- ツールの出力をメインのコンテキストに戻す前に要約する
- テキストから構造化データを抽出する

一方、モジュールの再設計方針を決めるプランナーは性質が異なり、手持ちで最も強いモデルが効きます。ルーティングの目的は、トリアージ作業にプランナー相当のコストを払い続けないことです。

## シンプルなルーティング層

最初からフレームワークは不要です。タスク種別からモデルを引く関数があれば十分で、価格やモデル品質が変わったときの変更箇所も1か所に集まります。

```typescript
type TaskKind = "classify" | "summarize" | "extract" | "plan" | "review";

const MODEL_BY_TASK: Record<TaskKind, string> = {
  classify: "claude-haiku-5-5",
  summarize: "claude-haiku-5-5",
  extract: "claude-haiku-5-5",
  plan: "claude-opus-5-5",
  review: "claude-sonnet-5-5",
};

export function pickModel(kind: TaskKind): string {
  return MODEL_BY_TASK[kind];
}
```

マッピングは呼び出し箇所に散らさず、設定として管理します。たとえば長文の `summarize` で品質が足りないと分かった場合も、1行の変更で済みます。

## 推測ではなくエスカレーションで対応する

静的なルーティングには弱点があります。「簡単なはず」のタスクが実は難しいことがあるためです。小さいモデルで始め、シグナルが出たら上位モデルに切り替える方式のほうが堅実です。

```typescript
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

async function classifyTicket(text: string) {
  const small = await client.messages.create({
    model: "claude-haiku-5-5",
    max_tokens: 200,
    messages: [
      {
        role: "user",
        content: `Classify this ticket as "bug", "feature", or "question". If unsure, answer "unsure".\n\n${text}`,
      },
    ],
  });

  const first = small.content[0];
  const label = first.type === "text" ? first.text.trim().toLowerCase() : "unsure";

  if (label !== "unsure") return label;

  // 判断が曖昧なケースだけ大きいモデルに回す
  const large = await client.messages.create({
    model: "claude-sonnet-5-5",
    max_tokens: 200,
    messages: [
      {
        role: "user",
        content: `Classify this ticket as "bug", "feature", or "question".\n\n${text}`,
      },
    ],
  });
  const second = large.content[0];
  return second.type === "text" ? second.text.trim().toLowerCase() : "unsure";
}
```

小型モデルに「unsure」と答える逃げ道を与えるのは、安価で効果的な方法です。指示が1行増えるだけで、境界ケースでの自信満々の誤答を減らせます。

## サブエージェント: 削減効果が最も大きい場所

Claude Codeのようなツールでは、メインのエージェントが独自のコンテキストを持つサブエージェントに作業を委譲できます。リポジトリを検索して結果を報告する探索系のサブエージェントは、大量のテキストを読み、短い答えを返します。入力トークンが多く、出力が少なく、推論の深さは浅い、というこの性質は小型モデルと相性が良好です。

私たちの運用ルールは次のとおりです。読み取りが中心で判断の軽い作業は小型モデルに委譲し、判断が重いステップはメインのエージェントに残します。サブエージェントの出力が、マイグレーション計画やセキュリティ上重要な変更のように、後戻りしにくい判断に使われる場合は、上位モデルで検証します。

## 切り替える前に測定する

ルーティングは品質が保てて初めて意味があります。あるステップを小型モデルに移す前に、次の手順を踏みます。

1. 本番またはステージングのログから、そのステップの実データを50〜100件集める。
2. 両方のモデルで実行し、正解ラベルと比較するか、明文化した評価基準で上位モデルに採点させる。
3. 平均スコアだけでなく不一致率も追う。95%正しくても、最も価値の高いケースで外すモデルは許容できない場合があります。
4. 品質と並べて、タスクあたりのコストとレイテンシも記録する。

新しいモデルが出たら再実行してください。小型モデルは急速に改善するため、半年前に評価で落ちたステップが今は通ることがあります。

## webhaniの推奨

- エージェントの各ステップを「読み取り中心」「判断中心」「整形中心」に分類する。
- 分類・抽出・要約から小型モデルへ移す。最も安全に効果が出ます。
- 固定の振り分けに頼らず、「unsure」によるエスカレーション経路を用意する。
- モデル名は設定に持たせ、リクエストごとに使用モデルをログに残して、コストを帰属できるようにする。
- ベンダーのベンチマークは仮説として扱い、自社データで検証する。

すでにエージェントワークフローを運用しているチームでは、ボリュームが大きいほど、単一モデル構成とルーティング構成のコスト差が効いてきます。差が小さい場合でも、小さなステップのレイテンシ改善によって、全体の体感速度が上がることがよくあります。
