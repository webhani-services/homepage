Anthropicは2026年9月22日、5.5ファミリー最初のモデルとしてClaude Opus 5.5をリリースしました。報道の多くはベンチマークと価格に焦点を当てていますが、すでに本番でAPIを呼んでいるチームにとって重要なのは、リリースノートに書かれた別の点です。報じられている内容によると、このモデルのadaptive thinkingは常時有効で、thinkingを無効にしようとするリクエストはエラーになります。

変更履歴の一行にすぎませんが、リクエストパラメータをハードコードしているコードベースでは実害が出ます。この記事では、モデルIDを変える前に確認すべき点と、次のモデル変更を退屈な作業にするための呼び出し側の構造を整理します。

なお、以下の内容は必ずAnthropic公式ドキュメントで裏取りしてください。価格など、二次情報の間で数値が食い違っている項目がありました。

## 何が変わったと報じられているか

ローンチ時の記事とリリースノートから、連携作業に関係する点は次のとおりです。

- Adaptive thinkingは常時有効。リクエストごとにモデルが推論量を決め、オフにはできない
- デフォルトで100万トークンのコンテキストウィンドウ、最大12.8万トークンの出力
- Anthropicは、一般的なワークロードでOpus 5より約40%低コストで、出力も高速だと説明している

最初の点が前提を崩します。オートコンプリート、分類、短いチャット応答のような低レイテンシが求められる経路では、thinkingを無効にしているアプリケーションが少なくありません。その設定を拒否するモデルに対しては、品質が少し落ちるのではなく、リクエスト自体が失敗します。

## これはモデルの問題ではなく連携設計の問題

モデルのアップグレードは、IDを差し替えて評価セットを回し、リリースするだけの設定変更として扱われがちです。パラメータがモデル間で共通であればそれで済みます。モデルごとにパラメータの扱いが違うと、それでは足りなくなります。

今回の失敗は大きな音を立てるタイプで、これはむしろ良い方です。拒否されたリクエストはすぐログに現れます。同時に確認しておきたい、より静かなリスクもあります。

- **レイテンシ特性の変化**: adaptive thinkingでは、難しいプロンプトの初回トークンまでの時間が、以前のモデルで測った値より長くなることがあります。旧モデル向けに調整したタイムアウトでは厳しすぎる可能性があります。
- **トークン消費の変化**: thinkingトークンは出力として課金されます。thinkingなしでは安かったプロンプトが、トークン単価が下がっていても高くなることがあります。
- **出力長の前提**: 出力長でパースや切り詰めをしている場合、出力上限の拡大やデフォルトの冗長さの違いで挙動が変わることがあります。

## モデル固有のパラメータを1か所に閉じ込める

最も簡単な対策は、リクエストオブジェクトをあちこちで組み立てるのをやめ、小さなCapabilityテーブルとビルダー関数を1つ置くことです。

```ts
type ModelProfile = {
  id: string;
  supportsDisabledThinking: boolean;
  defaultMaxTokens: number;
  timeoutMs: number;
};

const PROFILES: Record<string, ModelProfile> = {
  "claude-opus-5-5": {
    id: "claude-opus-5-5",
    supportsDisabledThinking: false,
    defaultMaxTokens: 8192,
    timeoutMs: 120_000,
  },
  "claude-sonnet-5": {
    id: "claude-sonnet-5",
    supportsDisabledThinking: true,
    defaultMaxTokens: 4096,
    timeoutMs: 60_000,
  },
};

type Intent = { fast: boolean; maxTokens?: number };

export function buildRequest(model: string, intent: Intent) {
  const profile = PROFILES[model];
  if (!profile) throw new Error(`Unknown model profile: ${model}`);

  const request: Record<string, unknown> = {
    model: profile.id,
    max_tokens: intent.maxTokens ?? profile.defaultMaxTokens,
  };

  // モデルが許可している場合のみ「thinkingなし」を指定する
  if (intent.fast && profile.supportsDisabledThinking) {
    request.thinking = { type: "disabled" };
  }

  return { request, timeoutMs: profile.timeoutMs };
}
```

呼び出し側は「これは高速経路」という意図を渡し、その意図をパラメータで表現できるかどうかはプロファイルが決めます。高速経路でthinkingを無効にできないなら、必要なのはパラメータの修正ではなくルーティングの判断です。この間接層の目的は、その判断を見える形にすることにあります。

高速経路は、小型のモデルに置いておくのが通常の答えです。推論が効かない経路で上位モデルのコストを払うより、5.5ファミリーの軽量モデルやSonnetクラスのほうが適しています。このパターンは[エージェントワークフローのモデルルーティング](/blog/claude-haiku-5-5-subagent-model-routing-2026)の記事でも触れています。

## 影響範囲を抑える移行手順

1. **まずthinking関連の設定をgrepする**: SDKのラッパー、社内ゲートウェイ、テストフィクスチャも含め、設定箇所をすべて洗い出します。ラッパーが知らないうちに設定していることがよくあります。
2. **両モデルで評価セットを回す**: 品質だけでなく、レイテンシのパーセンタイルとリクエストあたりの総トークン数も記録します。コストの答えは価格表ではなくトークン数に出ます。
3. **切り替え前にシャドートラフィックを流す**: 実リクエストの一部を新モデルにも送り、レスポンスは捨てます。見るのは品質ではなく、エラーとテールレイテンシです。
4. **タイムアウトは意図して上げる**: 推測ではなく、新モデルで測ったp99に余裕を足して決めます。
5. **全体ではなくルート単位で切り替える**: 推論負荷の高いルートから移し、低レイテンシが必要なルートはデータが揃うまで旧モデルに残します。
6. **ロールバックは設定値1つで**: モデルIDを環境変数やフラグに置いておけば、ロールバックにデプロイは要りません。

## 何を測るか

ローンチ記事の品質に関する主張は、ベンダー側のタスクで測られたものです。自分たちのワークロードは別物なので、次の4点を自分たちの環境で測ってください。

- 自社の評価セットでのタスク成功率
- ルートごとのp50・p99レイテンシ
- thinkingを含むリクエストあたりの出力トークン数
- シャドートラフィック中のエラー種別ごとのエラー率

成功したタスクあたりのコストが下がっていれば、アップグレードは見合っています。トークン単価だけが下がっている場合は、そうとは限りません。

## webhaniの見解

Opus 5.5は、推論品質がボトルネックになるルート、つまり複数ファイルにまたがるコード変更、多段階の分析、長時間動くエージェントタスクの有力な候補です。新しい上位モデルが出たからといって、低レイテンシが必要で複雑さの低いルートまで移す必要はありません。

より大きな教訓は構造面にあります。モデル固有の挙動はこれからも変わり続け、リリースのたびにこうした制約が付いてくるでしょう。Capabilityテーブルとリクエストビルダーは半日で作れ、次回の移行を1ファイルの差分に変えてくれます。
