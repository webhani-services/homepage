## 2週間で3つの Flagship Model が出た

2026年7月だけで、業界の主要 Player が揃って新しい Model を出しました。7月8日に xAI が Grok 4.5 を、7月9日に OpenAI が GPT-5.6 系（内部コード名 Sol・Terra・Luna）を General Availability にし、ChatGPT の Default Model に据えました。同じ日に Meta も初の有料 Model である Muse Spark 1.1 を出しています。そして7月24日、Anthropic が Claude Opus 5 を発表しました。Artificial Analysis の Intelligence Index で Score 61、Agentic Index で Score 55.3 を取り、両方で首位に立っています。価格は $5 / $25（Input/Output、100万 Token あたり）で、これは Claude Fable 5 の半額です。

Client やチームから「結局どれを使えばいいのか」という質問が急に増えました。この記事では Benchmark の数字そのものより、実際に Coding Workflow に組み込むときにどう考えるべきかを書きます。

## Leaderboard の順位を信用しすぎない

Intelligence Index や Agentic Index は、幅広い Task の平均的な性能を表す指標です。有用ではありますが、これはあなたのチームが日常書いている Code の分布を反映していません。たとえば以下のようなチームがあったとします。

- 既存の Django Monolith に機能追加する Backend チーム
- React + TypeScript の Frontend で複雑な State 管理を扱うチーム
- Terraform で Infra を書く Platform チーム

これら3チームにとって「良い Model」は全く別物です。Agentic Index は Multi-step Tool Use のベンチマークですが、あなたの CI 環境、あなたの Code Style、あなたの Repository の慣習まではモデリングしていません。Grok 4.5 が「Cursor で訓練された Coding Model」だと Positioning されているのも、それがある種の Workflow に最適化されているというだけで、あなたの Workflow に最適とは限らないという意味です。

実務的な対策は単純です。自分たちの実際の Ticket や過去の PR から、10〜30件程度の小さな内部 Eval Set を作ることです。理想は次のような構成です。

1. 過去にマージされた実際の PR の Diff（Bug Fix、機能追加、Refactoring を混ぜる）
2. その PR が解決した Issue の説明文
3. 期待される Output の評価基準（Test が通るか、既存の Code Style に沿っているか、Review Comment の数）

この Eval Set に対して候補の Model（Opus 5、GPT-5.6、Grok 4.5）を同じ Prompt・同じ Tool 定義で走らせ、Pass率と Review 工数を比較します。Leaderboard の順位より、この小さな Eval のほうがあなたのチームにとって遥かに強いシグナルです。

## Opus 5 の値下げが変える Workflow

Opus 5 が Fable 5 の半額になったことは、単なる Cost 削減以上の意味を持ちます。Agentic Coding では1つの Task に対して複数回の Tool Call、複数の Sub-agent を並行して走らせることが増えています。同じ予算で今までの2倍の Tool Call・並行 Agent 数が使えるようになったということです。

具体的な Workflow 例を挙げます。今まで1つの PR に対して1つの Review Agent しか走らせていなかったチームが、同じ予算で以下のような構成に切り替えられます。

- Agent A: Logic の正しさと Edge Case を確認
- Agent B: Security 観点（Injection、権限周り）を確認
- Agent C: 既存 Code Style との整合性、命名規則を確認
- Agent D: Test Coverage の Gap を確認

これらを PR ごとに並行実行し、結果を1つの Summary に集約する構成です。以前は Cost 的に「1つの汎用 Review Agent に全部見てもらう」しか選べなかったチームが、専門化した複数 Agent を並行稼働できるようになります。もちろん、これは「並行数を増やせば品質が上がる」という単純な話ではありません。並行 Agent が増えるほど Noise（重複した指摘、優先度の低い指摘）も増えるので、集約 Step の設計が重要になります。

## Anthropic の品質劣化事件が教えてくれること

今回のニュースの中で、実務上いちばん重要なのは Opus 5 のスコアではなく、Anthropic が公表した内部調査の結果だと考えています。2026年3月から4月にかけて、以下の3つの変更が Claude の出力品質を劣化させていたことが確認されました。

1. Claude Code の Default Reasoning Effort レベルの引き下げ
2. Cache 最適化に関する Bug
3. System Prompt の改訂

3つとも Version Up ではなく、静かな Config 変更でした。つまり、あなたのチームが「同じ Model」を使い続けているつもりでも、Provider 側の Default 設定変更によって Production の Agent 挙動が劣化することがある、ということです。これは Model 選定の話より一段深刻です。どの Model を選んでも、この種のリスクからは逃れられません。

実務上の対策は次の3つです。

**Reasoning Effort を明示的に固定する。** Default に任せず、必ず明示的な Parameter として指定します。

```python
# 悪い例: Default に依存している
response = client.messages.create(
    model="claude-opus-5",
    messages=[...],
)

# 良い例: Reasoning Effort を明示的に固定
response = client.messages.create(
    model="claude-opus-5",
    reasoning_effort="high",  # Default 変更の影響を受けない
    messages=[...],
)
```

**小さな Regression Eval Suite を定期的に再実行する。** 前述の内部 Eval Set を、Model や Provider 側の Config が変わっていなくても、週次か Sprint 単位で再実行します。目的は新しい Model の評価ではなく、「昨日まで動いていた Production Agent が今日も同じ品質か」を継続的に確認することです。

```yaml
# .github/workflows/agent-regression.yml
name: Agent Regression Check
on:
  schedule:
    - cron: "0 3 * * 1" # 毎週月曜
  workflow_dispatch:

jobs:
  eval:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run internal eval set against production agent config
        run: npm run eval:agent -- --suite=internal-30 --threshold=0.85
      - name: Alert on regression
        if: failure()
        run: npm run notify:slack -- "Agent regression detected"
```

**自分の Code は何も変えていないのに挙動が変わったら疑う。** Reasoning Effort、System Prompt、Cache 挙動は Provider 側で静かに変わり得ます。Version 番号が同じでも、Output の傾向（Verbosity、Tool 呼び出し回数、Error Handling の丁寧さ)が変わったら、まず Provider 側の変更を疑う癖をつけます。

## まとめ

- Intelligence Index や Agentic Index の順位は参考程度に留め、実際の PR や Ticket ベースの小さな内部 Eval Set で候補 Model を比較する。
- Opus 5 の値下げは、並行 Review Agent や Sub-agent を増やす形で Workflow に還元できる。ただし並行数を増やすほど Summary/集約 の設計が重要になる。
- Model の品質は固定された性質ではない。Reasoning Effort・System Prompt・Cache 挙動は Provider 側の Config 変更で静かに劣化し得る。Reasoning Effort は明示的に Pin し、Default に任せない。
- 小さな Regression Eval Suite を定期的に(Model が変わっていなくても)再実行し、Production Agent の挙動 Drift を監視する。
- Opus 5・GPT-5.6・Grok 4.5 のどれを採用するかは、Leaderboard ではなく自分たちの Workflow に対する実測データで決める。
