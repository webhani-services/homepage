## 性能も上がって値段も下がった、という珍しいリリース

2026年7月24日、AnthropicがClaude Opus 5をリリースしました。数日のうちにArtificial AnalysisのIntelligence Index（スコア61）で首位に立ち、私たちの仕事に直結する指標であるAgentic Index（55.3）でも首位を獲得しています。ただ、実務の判断に効いてくるのはむしろ価格の方です。Input Token 100万あたり$5、Output Token 100万あたり$25 — もう一つのFlagshipであるClaude Fable 5のおよそ半額です。

この組み合わせは珍しいです。通常、新しいFrontier Modelは性能が上がる代わりに価格は据え置きか、むしろ上がります。今回は性能が上がって価格が下がりました。あわせて思い出しておきたいのが、そのFable 5自身が2026年6月に米国の輸出規制の対象となり、約3週間にわたってオフライン状態だったという経緯です。7月1日に再開されましたが、この期間をFable 5だけに依存して乗り切ったチームであれば、単一Vendor・単一Modelへの依存がどれだけ実務上のリスクになるか、身をもって理解しているはずです。

この記事では、「Opus 5に今すぐ乗り換えるべきか、それをどう判断すればよいか」という、私たちが顧客からよく聞かれる問いに答えます。

## Agentic Indexの首位が意味すること

一般的なIntelligence Benchmarkは、単一Turnでの推論精度に近いものを測ります。難しい問題を与えて、答えの正しさを採点する、という形です。これはコーディング能力とある程度相関しますが、実際にAgenticなコーディングワークフローを壊す原因とは少しズレています。

Agentic Indexが測っているのは、私たちが本当に気にしていることに近い部分です。複数Stepのタスクをどれだけ計画的にこなせるか、Toolを正しく呼び出せるか、Toolの失敗やTestの失敗から立て直せるか、長いSessionの中で計画が破綻せずに一貫していられるか。実務でエンジニアの時間を食う失敗は、「構文を知らなかった」ではなく、たとえば次のようなものです。

- Agentが不正な引数でToolを呼び出し、そのまま自己修正できない
- Testを実際には実行していないのに、タスク完了と申告する
- 30回ほどTool呼び出しを重ねた後、Session序盤の制約を忘れる
- 失敗したアプローチを別のやり方に切り替えず、そのまま繰り返す

Agentic Indexで首位に立つModelは、原理的にはこうした失敗に強いはずです。これは、数学Benchmarkでの0.5ポイントの改善よりも、CIに組み込まれたコーディングAgentにとってずっと意味のある差です。

## 本当に問うべきは「アップグレードすべきか」ではない

Opus 5がFable 5より性能も良く、価格も安いとなると、「全部乗り換えよう」という反応になりがちです。ここは踏みとどまるべきです。問題はOpus 5が良いModelかどうかではありません — Artificial Analysisの数字がそれを裏付けています。問題は、あなたが実際に動かしている個々のワークロードにとって適切なModelかどうかです。「Flagship」は「あらゆるタスクの正解」を意味しません。Agenticなコーディング作業の多く— Lintの修正、Changelogの生成、単純なRefactorなど — はそもそもFlagship級の推論力を必要とせず、安くなったからといってそこに回すのは、より小さなModelで済むタスクに余計なコストをかけているだけかもしれません。

以下は、Agent ConfigにおけるModel選定ロジックを、意図的に汎用的な形で示した例です。「最新のModelを選んだから」ではなく、判断基準を明示的かつTest可能にすることが目的です。

```typescript
type ModelId = "claude-opus-5" | "claude-fable-5" | "claude-haiku-5";

interface ModelPricing {
  inputPer1M: number;  // USD / 100万 Input Token
  outputPer1M: number; // USD / 100万 Output Token
}

// あくまで例示。実際のPriceは必ずProviderの最新情報で確認してください。
const PRICING: Record<ModelId, ModelPricing> = {
  "claude-opus-5":  { inputPer1M: 5,    outputPer1M: 25 },
  "claude-fable-5": { inputPer1M: 10,   outputPer1M: 50 },
  "claude-haiku-5": { inputPer1M: 0.8,  outputPer1M: 4 },
};

function estimateCost(model: ModelId, inputTokens: number, outputTokens: number): number {
  const p = PRICING[model];
  return (inputTokens / 1_000_000) * p.inputPer1M + (outputTokens / 1_000_000) * p.outputPer1M;
}

interface TaskProfile {
  requiresMultiStepToolUse: boolean;
  estimatedToolCalls: number;
  riskIfWrong: "low" | "medium" | "high"; // 例: 認証・決済まわりのコードなら high
}

function pickModel(task: TaskProfile): ModelId {
  // 影響範囲が大きい、またはTool Chainが長い場合は、最良のAgentic性能に投資する
  if (task.riskIfWrong === "high" || task.estimatedToolCalls > 8) {
    return "claude-opus-5";
  }
  // 中程度の複雑さ: opus-5と中位Modelを決め打ちせずA/B Testで比較する価値がある
  if (task.requiresMultiStepToolUse) {
    return "claude-opus-5";
  }
  // 低リスク・低複雑度: 小型Modelで十分なことが多い
  return "claude-haiku-5";
}
```

このコード例で重要なのは具体的な数字ではありません（本稿の価格はすべて執筆時点のスナップショットであり、読む頃には古くなっている前提です）。重要なのはパターンの方です。判断軸は「どのModelが最近出たか」ではなく、タスクのリスクとTool呼び出しの深さです。

## 顧客に移行を相談されたときの進め方

既存のFlagshipから新しいModelへの乗り換えを相談されたとき、Webhaniでは発表がどれだけ華々しくても、毎回同じ4Stepで整理します。

**1. 本番に反映する前に、自社のEvalを必ず走らせる。** 公開Benchmarkが示すのは、Artificial Analysisのタスクに対する性能であって、あなたのCodebase、Test Suite、社内APIに対する性能ではありません。自社Backlogから代表的なチケットを20〜50件ほど固定Setとして用意し、旧Modelと新Modelの両方を、実際に使っているAgent基盤の上で走らせて比較します。「もっともらしいコードが出たか」ではなく、Pass率・完了までのTool呼び出し回数・人間によるReview時間を比較してください。

**2. Tokenの価格ではなく、タスク全体のCostで見る。** Token単価が安くても、新Modelが同じ結果に到達するのに必要なTool呼び出しやRetryが増えるなら、タスク全体のCostは安くならない場合があります。単価だけでなく、呼び出し回数を掛け合わせて見積もってください。

**3. 段階的にRolloutする。** リリース初日に全Trafficを切り替えないこと。まずは重要度の低いタスクの一部を新Modelにルーティングし、1〜2週間ほど失敗率とCostを観察してから拡大します。これはBenchmarkには現れないリリース直後の不安定さからも身を守れます。

**4. 単一Modelへの依存をArchitectureに埋め込まない。** ここで思い出すべき具体例が、Fable 5の6月の輸出規制による3週間の停止です。どのModelを選ぶにせよ、Model IDを差し替えるだけで済むよう、Agent Configを十分に抽象化しておくべきです。上のコード例の`ModelId`は、まさにこの判断を一箇所にまとめるために存在しています。

## まとめ

- Opus 5がAgentic Indexで首位というのは、特にTool使用型のコーディングAgentにとって意味があります。実務のコストを食う失敗を捉える指標として、一般的なIntelligence Scoreより実態に近いです。
- 既存Flagshipより安くて性能も良いという事実だけでは、一斉移行の理由にはなりません。Model Tierはリリース日ではなくタスクのリスクに合わせて選ぶべきです。
- Model選定はデータドリブンで差し替え可能なConfigとして組むこと。上のコード例は完成形ではなく、出発点のパターンです。
- 本番ワークロードを切り替える前に、必ず自社のタスクでEvalすること。公開Benchmarkでの首位は「調べるべき合図」であって「移行の指示」ではありません。
- 単一Flagshipへの依存は運用上のリスクとして扱うこと。Fable 5の今年6月の停止は仮説ではなく、実際に起きたケースです。
