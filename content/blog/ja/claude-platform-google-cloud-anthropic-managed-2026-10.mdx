Anthropic が、自社運用の Claude API を Google Cloud 経由で提供開始したと発表しました。認証は Google Cloud IAM、請求は Google Cloud の請求書に集約され、既存のコミットメントから消化されます。発表によれば、Claude Opus 5.5 の Fast mode もこの経路で利用できるとのことです。Claude は以前から Google-managed の提供形態で GCP 上でも使えたため、論点は「GCP で Claude が使えるか」ではなく「2 つの経路のどちらが自社の制約に合うか」になります。

なお、Fast mode の対応状況や料金などは二次情報で食い違いが見られます。以下は判断の枠組みとして読み、具体的な数値は Anthropic と Google の最新ドキュメントで確認してください。

## 2 つの経路の違い

実務上の違いは、「誰が運用するか」と「使える機能の範囲」です。

| | Google-managed | Anthropic-managed |
|---|---|---|
| API の運用主体 | Google | Anthropic |
| データ処理者 | Google | Anthropic（Anthropic の規約に基づく） |
| 認証 | Google Cloud IAM | Google Cloud IAM |
| 課金 | Google Cloud | Google Cloud（コミットメントに充当） |
| 新機能の反映 | Google の統合スケジュールに依存 | Anthropic のプラットフォームに追随 |

コンプライアンス審査で「データ処理者は Google のみ承認」となっている場合は、Google-managed が引き続き安全な選択です。一方、「ハイパースケーラー経由だと新機能の反映が遅い」ことが障壁だった場合は、Anthropic-managed で解消できます。しかも請求は Google Cloud 内に収まるため、別途調達プロセスを回す必要もありません。

## 運用面で何が楽になるか

お客様の LLM 導入で詰まりやすいのは、モデルの品質よりも調達・キー管理・コスト按分です。モデル API が既に運用中のクラウドアカウントの内側に入ると、次の 3 点が単純になります。

- **長期 API キーが不要になる。** Service Account で認証でき、手動ローテーションが要りません。`.env` から秘密情報が 1 つ消えるだけでもセキュリティ上の改善です。
- **請求と予算が一本化される。** GCP には既にラベル・予算・アラートの運用があります。LLM の費用が、誰も管理していない SaaS 契約ではなく、通常のクラウド費用として見えるようになります。
- **監査証跡を流用できる。** IAM ポリシーと Audit Log が他のサービスと同じ形で効きます。

逆に、レート制限・リージョン・利用可能なモデルは経路によって異なります。本番ワークロードを載せる前に必ず確認してください。

## アプリケーションをポータブルに保つ

よくある失敗は、アプリケーションコードを特定プロバイダのクライアントに直接依存させることです。薄い境界を 1 枚置くだけで、経路の選択を後から変更できます。

```typescript
// llm/client.ts
export interface ChatRequest {
  system: string;
  userMessage: string;
  maxTokens: number;
}

export interface LlmClient {
  complete(req: ChatRequest): Promise<string>;
}

export type Route = "anthropic-direct" | "gcp-anthropic-managed" | "gcp-google-managed";

export function createLlmClient(route: Route): LlmClient {
  switch (route) {
    case "anthropic-direct":
      return new AnthropicDirectClient();
    case "gcp-anthropic-managed":
      return new GcpAnthropicManagedClient();
    case "gcp-google-managed":
      return new GcpGoogleManagedClient();
  }
}
```

認証・モデル ID・エラーのマッピングは各実装が持ち、アプリケーション側は `LlmClient` だけに依存します。経路はコード変更ではなく設定で選びます。

```typescript
const client = createLlmClient(
  (process.env.LLM_ROUTE as Route) ?? "anthropic-direct",
);
```

落とし穴になりやすいのがモデル ID です。同じモデルでも経路によって ID が異なることがあるため、文字列リテラルを散らさず、1 か所の表にまとめます。

```typescript
const MODEL_IDS: Record<Route, Record<"fast" | "balanced", string>> = {
  "anthropic-direct": { fast: "claude-haiku-5-5", balanced: "claude-sonnet-5-5" },
  // 各プロバイダのドキュメントを見て埋める（経路ごとに ID が異なる場合がある）
  "gcp-anthropic-managed": { fast: "", balanced: "" },
  "gcp-google-managed": { fast: "", balanced: "" },
};
```

## 経路選択のチェックリスト

経路を決める前に、次の 5 点を確認します。

1. 自社および顧客との契約上、データ処理者はどの法人である必要があるか。
2. Anthropic のプラットフォームには出ているが、もう一方の経路にはまだない機能が必要か。
3. 必要なモデルとリージョンは、ロードマップ上ではなく今日その経路で使えるか。
4. リトライを含めた想定トラフィックが Quota とレート制限に収まるか。
5. ラベルやプロジェクト単位で、プロダクトごとの LLM 費用を按分できるか。

1 と 2 が衝突する場合、それが本当の意思決定であり、技術ではなくビジネス上の判断になります。

## webhani の推奨

すでに GCP を使っているチームは、上記のインターフェースを置いたうえで Anthropic-managed 経路の PoC を短期間で回し、現在の構成とレイテンシ・コストを比較して判断するのがよいと考えます。結果に関わらず抽象化は残してください。今年はこの領域の提供形態が数か月おきに変わっており、設定で切り替えられる経路は安価な保険になります。
