Anthropic は 2026 年 9 月 28 日に Claude Sonnet 5.5 を公開しました。発表時の報道によると、Sonnet 5 より応答が 30% 以上高速で、一般的なタスクでは最大 30% 低コストになる一方、単価は入力 $2 / 出力 $10(100 万トークンあたり)のままです。安くなる理由は単価ではなく、同じ仕事に使うトークン数が減ることにあります。

その約 1 週間後(10 月 7 日)、複数のトラッカーが Sonnet 5.5 のキャッシュ読み取りが $0.20 から $0.10(100 万トークンあたり)に下がったと報じました。ただし、執筆時点で Anthropic 公式の料金ページでは確認できていません。見積もりに使う前に、公式ページで確認してください。以下の考え方は、どちらの数字でも変わりません。

## 入力単価よりキャッシュ読み取りが効く理由

単発のリクエストなら、見るべきは入力単価です。しかしエージェントのループでは、入力単価はほとんど効きません。毎ターン、システムプロンプト、ツール定義、これまでの会話全体が再送されるからです。Prompt Caching を使うと、そのほぼ全てが「新規入力」ではなく、キャッシュ読み取りまたは書き込みとして課金されます。

60k トークンのコンテキストで 40 ターン動くコーディングエージェントを例にします。

- ターンごとの新規入力:数千トークン(新しいツール結果)
- ターンごとのキャッシュ読み取り:約 55〜60k トークン
- ターンごとの出力:数百〜数千トークン

40 ターンで、キャッシュ読み取りは合計約 230 万トークンです。$0.20/M なら $0.46、$0.10/M なら $0.23 になります。新規入力(約 12 万トークン、$2/M)は $0.24 です。つまり入力側で最大の項目はキャッシュ読み取りで、これを半額にする影響は、入力の標準単価を動かすより大きくなります。

同じ理由で、タスクあたりのコストはキャッシュをどれだけ温かく保てるかに左右されます。

## キャッシュを壊す典型例

キャッシュはプレフィックス一致で動きます。プロンプトの前方が 1 か所でも変わると、それ以降は全て無効になります。クライアントコードでよく見る原因は次のとおりです。

```ts
// 悪い例:システムプロンプトの先頭に毎回変わる時刻を入れている
const system = `Current time: ${new Date().toISOString()}\n${basePrompt}`;

// 良い例:変わらない部分を先頭に置き、変動する情報は後ろに回す
const system = [
  { type: "text", text: basePrompt, cache_control: { type: "ephemeral" } },
];
const messages = [
  { role: "user", content: `Current time: ${new Date().toISOString()}\n${task}` },
];
```

ほかにも、次のようなケースがあります。

- ツール定義の順序がターンごとに変わる(順序の保証がない Map から組み立てているなど)
- 履歴の途中を削って短くしている(末尾への追記だけにするべきです)
- セッション途中でモデルを切り替え、キャッシュが新規になる
- ターンの間隔がキャッシュの有効期間を超えて失効する

各レスポンスの usage フィールドをログに残せば、全入力トークンに対するキャッシュ読み取りの比率で、キャッシュが効いているかをすぐ確認できます。長時間動くエージェントなら、最初の数ターン後は 90% を超えるのが目安です。届かない場合は、変動しているプレフィックスを探してください。

## もう一つの変数:effort

出力トークン(thinking を含む)は出力単価で課金され、これは入力単価の 5 倍です。参照した資料の一つは、Claude アプリと Claude Code の既定が medium effort であり、この設定が請求額に与える影響は他の多くの選択より大きいと指摘しています。

チームでの使い分けの一例です。

| タスク | effort | 備考 |
|---|---|---|
| リネーム、小さなリファクタ、整形 | Low | 出力が短く、推論を増やしてもコストが増えるだけ |
| テスト付きの機能開発 | Medium | 多くのセッションの既定 |
| 競合状態のデバッグ、設計レビュー | High | 結果が変わる場面でだけ推論にコストをかける |

CI のレビューボットや定期実行のエージェントでは、既定値に頼らず effort を明示してください。モデルや既定値が変わっても、支出が知らないうちに変わることを防げます。

## トークナイザーについて

5.5 ファミリーに関する報道では、新しいトークナイザーが同じテキストでやや多くのトークンを使う場合があるとされています。Sonnet 5 と 5.5 を比べるときは、トークン単位ではなく、自社のワークロードで完了したタスク単位で比較してください。代表的なタスクを 20〜30 件、両方のモデルで実行し、請求トークンを種別(新規入力、キャッシュ書き込み、キャッシュ読み取り、出力)ごとに記録するのが確実です。

## webhani の推奨

1. 月次の合計だけでなく、タスクごとにキャッシュ読み取り・書き込み・新規入力・出力のトークンを記録する。
2. プロンプトのプレフィックスに変動する内容がないか監査する。時刻、リクエスト ID、ユーザー固有の情報はキャッシュ対象ブロックの後ろに置く。
3. effort はワークロードの種類ごとに決め、バージョン管理された設定に残す。
4. 価格変更は、アーキテクチャを見直す理由ではなく、再計測する理由として扱う。キャッシュ読み取りの値下げが効くのは長いコンテキストのエージェントで、短くステートレスな呼び出しではあまり変わりません。
5. 契約や見積もりに入れる前に、価格は必ず公式の料金ページで確認する。

モデルのリリースは今後も数週間おきに続きます。コストを予測可能に保てるのは、トークンの行き先を把握し、一度に一つの変数だけを変えられるチームです。
