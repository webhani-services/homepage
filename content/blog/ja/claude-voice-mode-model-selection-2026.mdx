## 小さなトグルだが、設計上の意味は大きい

Anthropicは今週、ClaudeのVoice ModeをアップデートしOpus・Sonnet・Haikuの中からModelを選べるようにしました。これまでは全てのVoice Sessionが1つの固定Modelを経由していましたが、今後はText Chatで最後に使ったModelがデフォルトとなり、そのModelの中でも最も高速なVariantが選ばれます。

一見すると設定メニューの変更に過ぎません。しかし実務的には、Voiceプロダクトを作る人なら明示的に判断しなければならないTrade-offを浮き彫りにします。VoiceはText ChatよりもはるかにLatencyの余裕が小さい一方で、複雑な依頼に対しては本格的な推論力もユーザーは期待します。これまではこのTrade-offがProvider側で固定されていましたが、今はSessionごと、プロダクトごとに選べる判断になりました。

## なぜVoiceでは事情が変わるのか

Text Chatなら数秒の「考え中」は許容されます。Voiceはそうはいきません。1〜2秒を超えるTurn-takingの遅延は、それだけで壊れているように感じられます。人が音声会話に期待するリズムは、打ち込んだメッセージに期待するリズムよりもずっと速いためです。だからこそVoice Assistantは歴史的に、浅い推論というコストを払ってでも、最も小さく速いModelをデフォルトにしてきました。

問題は、Voiceのユースケースの多くが実際には浅くないという点です。「今日の天気は」なら速くて安価なModelで十分ですが、「この未解決の請求書紛争をどう立て直すか一緒に整理してほしい」となると話は別です。両方を同じModelに通すと、簡単な依頼にはCapacityを無駄にし、難しい依頼にはユーザーを苛立たせることになります。

Anthropicの今回のアップデートのように、SessionごとにModelを変えられ、かつ既に使っていたModelの最速Variantがデフォルトになる仕組みは、Text Agentが既に実践している「タスクの複雑さにModelの能力を合わせる」設計をVoiceインターフェースにも広げる一歩と言えます。

## 設計パターンとしての応用

この考え方はClaude自身のVoice Modeに限りません。Anthropic APIの上にVoiceプロダクトを構築する場合、同じ階層化パターンを明示的に実装できます。まず入力を安価に分類し、その複雑さに合ったModel階層にルーティングします。

```ts
type ModelTier = "haiku" | "sonnet" | "opus";

const MODEL_IDS: Record<ModelTier, string> = {
  haiku: "claude-haiku-4-5",
  sonnet: "claude-sonnet-5",
  opus: "claude-opus-5",
};

// 実際の（Latencyに敏感な）応答生成の前に、
// 安価で高速な分類パスでTierを決める
async function pickTier(utterance: string): Promise<ModelTier> {
  const wordCount = utterance.trim().split(/\s+/).length;
  const looksMultiStep = /\b(then|after that|compare|why)\b/i.test(utterance);

  if (wordCount < 8 && !looksMultiStep) return "haiku";
  if (looksMultiStep || wordCount > 25) return "opus";
  return "sonnet";
}

async function respondToVoiceTurn(utterance: string) {
  const tier = await pickTier(utterance);
  return anthropic.messages.create({
    model: MODEL_IDS[tier],
    max_tokens: 512,
    messages: [{ role: "user", content: utterance }],
  });
}
```

これはあえて単純化した例です。実運用のRouterであれば現在の発話だけでなく会話履歴も加味し、速いTierの応答が曖昧・不完全に見える場合は上位Tierへフォールバックする設計になるでしょう。ここで伝えたいのは形そのものです。Tierの判定は安価かつ高速に行い、Latencyの予算は効果のある場所にだけ使う、という発想です。

## 気をつけたいポイント

Voiceプロダクトにモデル切り替えを導入する際、見落としがちな点がいくつかあります。

- **人格の揺れ**：Model Tierが違えば言い回しも変わります。プロダクトに固有のペルソナがある場合は、System PromptとTone指示をTierに依存しない形にし、開発時に使っている1つのTierだけでなく3つ全てで人格が保たれるかテストしてください。
- **会話途中でのTier切り替え**：同一Session内でTurnごとにTierを変えると、応答スタイルの変化が目立つことがあります。Session単位でTierを固定するか、切り替えを許容するかを事前に決めておくべきです。
- **本当のボトルネックはLatency**：難しい質問のために選んだ上位Modelも、結局はLatency予算内に収まる必要があります。各Tierの実際のRound-trip Timeを、自社のNetworkとTTSパイプラインで計測してください。カタログ上のTier間の速度差が、そのままプロダクトの体感Latencyに反映されるとは限りません。

## まとめ

Voice ModeでのModel選択は小さな機能ですが、伝えているメッセージは大きいものです。Voice AIは、Text Agentが既に実践しているRoutingパターンに追いついてきています。ClaudeのAPIの上にVoiceプロダクトを構築するなら、実務的な次の一手は「どのModelを使うか」をグローバルな単一設定として扱うのをやめ、実際のタスクの複雑さと計測済みのLatency予算に応じたTurnごとのRouting判断として扱うことです。Webhaniでは、Text Agent設計で採用してきたこの階層化の考え方を、Voiceインターフェースの設計にもそのまま適用しています。
