## 脆弱性のない大規模流出

2026年8月17〜18日ごろ、"TheHatman" と名乗る攻撃者が、複数のFortune 500企業のMicrosoft Azure/Entra IDテナントから窃取したとされる従業員データベースを販売していることが明らかになりました。McDonald'sの約170万件を含む、Vodafone、Gap Inc、HCL Technologies、InterContinental Hotels Group、Kyndryl、Tata Consultancy Services、Hexaware Technologies、Wyndham Hotelsなど、対象企業は多岐にわたり、合計で360万件を超える記録が確認されています。流出したデータには氏名、従業員ID、電話番号、住所、社用メールアドレス、役職、マネージャーの割り当て、グループメンバーシップに加え、サービスアカウントとGlobal Administratorの一覧まで含まれていました。

この件で最も注目すべきは件数の多さではありません。セキュリティ研究者が調査した結果、Azureや Entra ID自体にゼロデイや脆弱性は見つからなかったという点です。データは2026年7月31日ごろから収集され始めたとみられていますが、その手口は特別なものではなく、盗まれた正規の認証情報とそこに紐づく正当なアクセス権限を悪用しただけでした。

これは今のクラウド侵害事例に共通するパターンです。基盤インフラは堅牢だったのに、その周りを守るID管理層が突破された、という構図です。

## なぜIDが最大の攻撃対象になるのか

AzureのようなクラウドPlatformは、テナント分離やAt-rest暗号化、基盤へのパッチ適用に莫大なエンジニアリングリソースを投じています。そのおかげでPlatform自体への侵害は実際まれです。攻撃対象が限定的で、監視も厳重だからです。一方で認証情報はまったく事情が異なります。従業員一人ひとり、サービスアカウント一つひとつ、CI Pipeline一本一本が鍵を持っており、それが盗まれれば警報も鳴らずに正面玄関を通り抜けられてしまいます。

ディレクトリ同期用のアカウント、古いスクリプトに残された使いかけのAPI Token、フィッシングで奪われた管理者セッション — どれも攻撃者に正規のオペレーターと同じ視界を与えてしまいます。ディレクトリデータそのものが機密というより、それが「地図」になる点が厄介です。どのアカウントが強い権限を持ち、誰が誰を管理し、どのサービスアカウントが何にアクセスできるか。この地図があれば、一つの認証情報漏洩がラテラルムーブメントの実行計画に変わります。

ここで学ぶべきは「Azureが危険」ということではなく、Identityと認証情報の衛生管理が、今やPlatform自体よりもセキュリティを左右する要素になっているのに、多くの組織がネットワークやインフラ制御への投資に比べてここへの投資を怠っている、という点です。

## 実践例: Global Administratorの棚卸し

まず、侵害されたときに最も被害が大きいアカウントから着手します。Entra IDのGlobal Administrator権限は、少人数に限定し、内容を把握し、定期的にレビューすべきものです。インシデントが起きてから初めて存在に気づく、という状態は避けなければなりません。Microsoft Graph PowerShell SDKでの棚卸し例です。

```powershell
# 読み取り専用の監査に必要な最小限のScopeで接続
Connect-MgGraph -Scopes "RoleManagement.Read.Directory","User.Read.All"

# Global Administratorロールの定義を取得
$role = Get-MgDirectoryRole -Filter "displayName eq 'Global Administrator'"

# 現在のメンバー一覧を取得
Get-MgDirectoryRoleMember -DirectoryRoleId $role.Id | ForEach-Object {
    $user = Get-MgUser -UserId $_.Id -Property DisplayName,UserPrincipalName,AccountEnabled
    [PSCustomObject]@{
        Name    = $user.DisplayName
        UPN     = $user.UserPrincipalName
        Enabled = $user.AccountEnabled
    }
} | Format-Table -AutoSize
```

これを最低でも四半期に一度は実行し、見覚えのない名前が出てきたら「たまたまだろう」と流さず、インシデントとして扱ってください。あわせて、Graph APIに強い権限を持つサービスアカウントとApp Registrationも棚卸ししましょう。これらはMFAがかかっていないことが多く、人のアカウントほど注視されないため、攻撃者にとって格好の標的になります。

## 今回のような事例を遅らせたはずの実践的コントロール

以下はどれも特別なToolを必要とせず、Entra ID P1/P2ライセンスや他のIDプロバイダーの同等プランで利用可能です。

- **フィッシング耐性のあるMFA。** Push通知型MFAやSMSコードは、プロンプト爆撃やSIMスワップで突破されえます。Global Administrator、サービスアカウントのオーナー、本番環境への書き込み権限を持つメンバーなど、特権アカウントはFIDO2セキュリティキーやPasskeyへ移行しましょう。Entra IDのAuthentication Methodsポリシーで標準対応しています。

- **Conditional Accessをデフォルト拒否のスタンスにする。** MFAを要求するだけでなく、デバイスの準拠状態、アクセス元、サインインリスクでアクセス範囲を絞ります。管理者ロール向けの最小ポリシー例です。

  ```text
  Policy: "管理者ロールにはCompliant Device + フィッシング耐性MFAを要求"
  Assignments:
    Users: Directory roles → Global Administrator, Privileged Role Administrator
    Cloud apps: All cloud apps
  Conditions:
    Sign-in risk: Medium以上 → ブロック
  Access controls:
    Grant: Compliant Deviceであることを要求
           AND Authentication strength = フィッシング耐性MFAを要求
  Session:
    Sign-in frequency: 4時間
  ```

- **Session Tokenの有効期限を短縮する。** 長寿命のRefresh Tokenこそが、盗まれた認証情報一つを数時間ではなく数週間にわたって「使える」ものにしてしまう原因です。特権セッションのSign-in Frequencyを短縮し、Continuous Access Evaluationを有効化して、権限を剥奪したら次のToken更新を待たずに即座に反映されるようにします。

- **異常サインインとImpossible Travelの検知。** Entra ID Protectionは、見慣れない場所や匿名化されたIP、物理的にありえない移動パターンからのサインインを自動でフラグ付けします。ただし、これはRisk-based Conditional Accessポリシーがログ記録だけでなく、実際にアクションを取るよう設定されている場合に限られます。

- **定期的な最小権限のIAMレビュー。** ロールの割り当ては時間とともに積み上がる一方で、なかなか剥奪されません。四半期ごとのAccess Review（Entra IDには標準機能があります）で、退職した契約社員がサブスクリプションにContributor権限を持ったままになっている、といったケースを発見できます。

- **CI Pipelineへのシークレットスキャン導入。** 「認証情報の盗難」の多くは、フィッシングされたログインではなく、Repositoryにコミットされた Tokenから始まります。Secret Scanning（GitHub Advanced Security、GitLab Secret Detection、あるいはPipelineに組み込むGitleaksなど）を有効化し、検出したシークレットは削除するだけでなく「漏洩済み」として即座にRotationしてください。

- **サービスアカウントの実効的なRotation周期を設ける。** サービスアカウントの認証情報は、それが作られたProjectよりも長生きしがちです。棚卸しし、オーナーを割り当て、「誰かが思い出したとき」ではなく固定周期（目安として90日）でRotationしましょう。

## webhaniがクライアント案件で確認するチェックリスト

クライアントのクラウド環境をオンボーディングする際、おおむね次の順序で確認しています。

1. Global Administratorおよび特権ロールの一覧を取得し、人事記録と突き合わせて確認する
2. サービスアカウントとApp Registrationを棚卸しし、それぞれにオーナーを割り当てる
3. まず特権アカウントからフィッシング耐性MFAを有効化し、その後範囲を広げる
4. サインインリスクとデバイス準拠状態に基づくConditional Accessポリシーを有効化する
5. 特権ロールのSessionとRefresh Tokenの有効期限を短縮する
6. CI Pipelineにシークレットスキャンが未導入なら追加する
7. 定期的なAccess Reviewをスケジュール化する（特権ロールは最低でも四半期ごと）

どれも地味な作業で、セキュリティベンダーの売り込みが必要なものでもありません。依存パッケージのアップデートと同じで、地味で後回しにされがちですが、侵害リスクを下げる上で最も投資対効果の高い作業です。

## まとめ

2026年8月中旬に明らかになったFortune 500企業のディレクトリデータ流出は、Azureに穴があったから起きたのではありません。人とマシン、両方の認証情報が盗まれ、設計どおりに — つまりディレクトリデータの読み取りに — 使われた結果でした。ここが厄介なところです。この種の攻撃を止めるコントロールは、決して新しいものでも秘密のものでもなく、Conditional Access、フィッシング耐性MFA、特権アカウントの棚卸し、Pipelineでのシークレット管理です。今回のようなキャンペーンで実害を受けるのは、たいていIdentity関連のコントロールを「あれば良いもの」程度にしか扱ってこなかった組織です。
