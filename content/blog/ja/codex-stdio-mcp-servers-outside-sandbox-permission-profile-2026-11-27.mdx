コーディングエージェントの Sandbox が守るのは、通常、エージェントが実行するコマンド(シェル呼び出し、テスト実行、ファイル編集)です。では、エージェントが起動する MCP サーバーはどうなっているのでしょうか。OpenAI の Codex の設定ドキュメントと、それを分析したガイドによると、`config.toml` で設定した stdio MCP サーバーの起動コマンドはデフォルトでは Sandbox されず、コマンド用のネットワークプロキシも MCP サーバーへの接続には適用されません。理由として挙げられているのは、各サーバーが必要とするファイルやネットワークサービスを Codex が確実には推測できない、という点です。

これは設計判断として理解できます。ただ同時に、「エージェントは Sandbox されている」というチーム内の安全の説明が、サードパーティのコードが動くまさにその場所で穴を持つことになります。この記事が扱うのはその隙間です。Codex に限った話ではなく、ローカル MCP をサポートする多くのエージェントハーネスに、何らかの形で存在します。

設定キー名やプロキシの挙動はバージョンによって異なり、一部はコミュニティの解説記事に基づいています。コピーする前に、必ず最新の公式設定リファレンスで確認してください。

## stdio MCP サーバーが特別な理由

stdio MCP サーバーは、エージェントが起動し、標準入出力で通信するローカルプロセスです。ファイルシステムサーバー、データベースクライアント、CLI のラッパーなどが典型例です。セキュリティ上重要な性質が3つあります。

- **ユーザーの権限で動く。** 起動部分が Sandbox の外にあれば、サーバーは `~/.ssh` やクラウドの認証情報など、アカウントが読めるものすべてを読めます。
- **多くはサードパーティのコード**で、`npx` や `uvx` でその場でインストールされます。つまり、今日動くコードが昨日と同じとは限りません。
- **ネットワークアクセスが別系統。** シェルコマンドに適用されるドメイン許可リストが、サーバーの外向き接続に自動で適用されるわけではありません。

言い換えると、エージェントのシェルを厳しく制限しても、すぐ隣のプロセスにあるツールサーバーが広い権限を持ったままでありうる、ということです。

## 現在のガイダンスが示していること

公式の記載とコミュニティの分析をまとめると次のとおりです。

1. stdio MCP サーバーは、ラップしない限り Sandbox の外で起動される。
2. ネットワークプロキシとドメインルールは Sandbox 内のコマンドに適用され、Web 検索、コネクタ、MCP サーバーの通信には適用されない。
3. ドメイン許可リストは、プロキシが有効なときだけ機能する。
4. 管理された `requirements.toml` により、承認ポリシーや Sandbox モード、MCP の許可リストといった管理者レベルの制限を強制でき、開発者が勝手にフルアクセスを選べないようにできる。

## 隙間を塞ぐ: プロファイルの中でサーバーを起動する

Codex には、名前付きの権限プロファイルのもとでコマンドを実行する仕組みがあり、これを stdio MCP サーバーの起動ラッパーとして使えます。設定の形はおおよそ次のとおりです(キー名は例示です。最新のリファレンスを確認してください)。

```toml
# ~/.codex/config.toml
[mcp_servers.docs-search]
command = "codex"
args = [
  "sandbox", "--permission-profile", "mcp-readonly", "--",
  "node", "/opt/mcp/docs-search/server.js",
]
```

そして、そのサーバーが正当に必要とするものだけに合わせたプロファイルです。

```toml
[permissions.mcp-readonly]
# プロジェクトは読み取りのみ、書き込みはサーバー自身のデータディレクトリだけ
# サーバーが本当に必要としない限りネットワークは無効
```

構文よりも原則が重要です。**すべての MCP サーバーに、実際の役割から導いたプロファイルを与える**ことです。ドキュメント検索サーバーに必要なのは、1つのディレクトリへの読み取りと、せいぜい1つのドメインです。ホームディレクトリやインターネット全体は必要ありません。

## MCP サーバーのレビューチェックリスト

エージェントの設定にあるサーバーごとに、次を確認します。

| 確認項目 | 望ましい答え |
| --- | --- |
| コードの出所とバージョン固定は? | 固定バージョンまたはベンダリング。`latest` は不可 |
| 読み書きできるパスは? | 名前の付いた最小限の集合 |
| 必要なネットワーク宛先は? | 短いリスト、または無し |
| 渡している認証情報は? | 環境変数の継承ではなく、スコープを絞って明示的に渡したトークン |
| 設定を変更できるのは誰か? | 共有環境では管理ポリシー |

バージョン固定は、思われている以上に重要です。固定していない `npx some-mcp-server` は、エージェントが起動するたびに自分の権限で実行されるサプライチェーン依存です。今年はパッケージ侵害のインシデントが相次いでおり、これは現実的な露出だと考えるべきです。

## 認証情報の衛生管理とセットで

サーバーを Sandbox すれば、侵害された場合や誤動作した場合に届く範囲は限定できます。しかし最も強力な対策は、持たせるべきでない認証情報を渡さないことです。サーバーに必要なトークンだけを渡し、可能なら読み取り専用にスコープを絞り、長期有効なものはエージェントが継承する環境に置かないでください。エージェントがシークレットをコミットしてしまった最近のインシデントは、同じ「過剰な環境権限」の問題が git 側にも現れることを示しています。

## webhani の推奨

1. **MCP サーバーを棚卸しする。** 開発者のマシンや共有設定にある stdio サーバーを、プラグイン経由で追加されたものも含めてすべて列挙します。
2. **固定してレビューする。** 浮動バージョンの起動コマンドを、固定バージョンに置き換えます。
3. **機微なデータに触れるものをラップする。** データベース、クラウドアカウント、ソースリポジトリにアクセスするサーバーから始めます。
4. **チーム設定には管理ポリシーを使う。** 安全なデフォルトを、各開発者が覚えて選ぶ必要がないようにします。
5. **境界をテストする。** プロファイル下でサーバーを動かし、禁止パスの読み取りや許可されていないホストへの接続が実際に失敗することを確認します。

エージェントの Sandbox の強さは、起動されるプロセスのうち最も弱いものに左右されます。MCP サーバーは最も見落としやすい部分ですが、気付いてしまえば最も安く直せる部分でもあります。
