## 「高品質か、低コストか」を選ばせないリリース

多くのモデルリリースは、品質とコストのトレードオフをユーザーに突きつけます。品質を取るなら高いモデルを、コストを抑えるなら劣ったモデルを、という具合です。ところが2026年9月10日にリリースされたDeepSeekのV4.1 Flashは、このトレードオフ自体を無効化しました。officechaiやBenchmark集計サイトのllm-stats.comの報道によれば、V4.1 Flashは同社の上位モデルであるV4 Proに対して、AgenticおよびCoding系のBenchmarkの多くで同等かそれ以上の成績を出しています — DeepSWE v1.1ではV4 Proの62.7に対して74.2、Terminal-Bench 2.1では87.9に対して90.6という具合です。一方でHLEのような知識系Benchmark（42.7に対して36.8）では劣っており、これは「Flash」がAgentic用途やTool呼び出しの高速処理に最適化された派生モデルであることと整合しています。

実運用の観点でより興味深いのはPricingです。Off-peak時間帯ではUncached Input Tokenが100万Tokenあたり$0.15、Output Tokenが$0.60です。Yotta Labsの記事によれば、平日UTC 01:00〜04:00および06:00〜10:00のPeak時間帯はこの両方が倍額になります。単純にハードコードして忘れられるような固定単価ではなく、時間帯に応じて変動する実際のコスト構造だということです。

## 注目すべきはV4 Proの実質的な引退

2026年9月14日UTC 04:00以降、DeepSeekは`deepseek-v4-pro`宛のAPI Requestをすべて自動的にV4.1 Flashへルーティングし、Flashの価格で処理するようになりました。これはV4.1 Proがリリースされるまで続きます。`v4-pro`をModel文字列としてハードコードしている既存のIntegrationはそのまま動き続けますが、気づかないうちに異なるLatencyや出力特性を持つ別のModelを叩くようになります。多くのチームにとってこれは純粋なアップグレード — 同等以上のBenchmarkで低コスト — ですが、「Model文字列」がProviderとの安定した契約ではないことを思い出させる出来事でもあります。出力のFormatやLatency Budgetに厳密なEvalを組んでいるチームは、Version番号だけでは分からないこの種の入れ替わりに注意が必要です。

## Providerを問わず持つべきPattern

DeepSeekを使うかどうかに関わらず、このPeak/Off-peakのPricingとMiddle-tierの引退劇は同じ課題を示しています。Model選定をBuild時の定数ではなく、実行時の判断として扱うべきだということです。最小限の実装イメージは次のようになります。

```ts
type TaskProfile = "lint-fix" | "multi-file-refactor" | "spec-review";

interface ModelChoice {
  model: string;
  maxOutputTokens: number;
}

function pickModel(task: TaskProfile, utcHour: number): ModelChoice {
  const isPeak = (utcHour >= 1 && utcHour < 4) || (utcHour >= 6 && utcHour < 10);

  if (task === "lint-fix") {
    return { model: "deepseek-v4.1-flash", maxOutputTokens: 512 };
  }

  if (task === "multi-file-refactor" && !isPeak) {
    return { model: "deepseek-v4.1-flash", maxOutputTokens: 4096 };
  }

  // Peak時間帯の複雑なTaskや、Flashの知識面の弱さが効いてくるTaskは
  // より推論力の高いModelにFallbackする
  return { model: "claude-opus-5", maxOutputTokens: 4096 };
}
```

これはDeepSeek固有のTipsではありません。後述するGloo Codeのような Agentic Coding製品が標準機能として組み込み始めているのと同じ形のLogicです。PricingとCapabilityの両方が時間帯やTaskによって変動する以上、Model文字列を1つ固定してしまうと、コストか品質のどちらかで損をすることになります。

## 評価するチームへのPoint

1. **Provider評価は一度きりで終わらせない**：2026年8月にIntegrationを組んだV4 ProのUserは、Codeを1行も変えないまま別のModelを使う状態になっています。テスト済みのModel Versionだけでなく、稼働中のEndpointに対して定期的にEvalを回すべきです。
2. **「安い」と「このTaskには十分安い」を区別する**：V4.1 FlashのKnowledge Benchmarkのギャップは実在します。RefactorやTest生成を行うCoding Agentであればほとんど問題になりませんが、Open DomainのQuestionに答えるSupport Botでは効いてくる可能性があります。
3. **Routing Layerは機能ごとではなく一度だけ作る**：上記のようなRouterはひとつの共有Moduleに収まる程度の規模です。ここを省略するチームは、すべてFrontier Modelに寄せて払いすぎるか、逆に推論力が必要なTaskにも安いModelを使って品質を落とすかのどちらかに陥りがちです。

## Webhaniの見解

DeepSeek V4.1 Flashは、LLM市場全体で見えつつあるより大きな流れを示す1つのデータポイントです。「1つのModel、1つの価格」という前提は、実際のチームの使い方にはもう合っていません。クライアントのDefault Model選定を支援するConsultingの現場では、最近は決まって同じ結論に至ります — 1つのModelを選ぶのではなく、Routing方針を選び、それを月次で見直すべきだ、と。Modelの変化のスピードは、たいていのチームの調達サイクルよりずっと速いのです。
