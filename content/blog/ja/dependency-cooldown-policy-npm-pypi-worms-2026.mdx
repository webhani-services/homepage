今年起きた複数のパッケージ侵害には共通のパターンがあります。広く使われているパッケージの悪意あるバージョンが公開され、短時間だけ配布され、その後に取り下げられる、という流れです。Mini Shai-Hulud ワームについては、悪意あるリリースが隔離されるまで約12〜36時間公開されていたと報じられています(Arctic Wolf による)。RapidFort が挙げる他の事例には、PyPI の LiteLLM 1.82.7 / 1.82.8 の侵害や、GitLab のアドバイザリで扱われている npm の axios 1.14.1 / 0.30.4 があります。

ここから導かれる対策は、拍子抜けするほど単純です。**公開されたその日のバージョンをインストールしない**。クールダウンポリシーは、新しいリリースの採用を数日遅らせ、コミュニティ、レジストリ、セキュリティベンダーが不審なバージョンに気づく時間を確保します。他の対策の代わりにはなりませんが、安価で、まさにこの種の攻撃に効きます。

## クールダウンが効くもの・効かないもの

効果があるもの:

- メンテナーアカウントが乗っ取られ、悪意あるバージョンが公開されて数時間〜数日で検知されるケース
- 新しく公開されたバージョンを経由して広がるワーム型の攻撃
- 公開直後に報告される、typosquat や悪意ある新リリース

効果がないもの:

- 数週間にわたって検知されない悪意あるコード
- 緊急で必要なセキュリティ修正(セキュリティ更新には明示的なバイパスが必要です)
- ビルドツールや CI シークレットの侵害。これは別の攻撃経路です

クールダウンの長さは自社のリスク許容度で決めます。アプリケーションの依存関係では7日が一般的な出発点です。セキュリティパッチは短く、メジャーバージョンは長くする、という使い分けも妥当です。

## Dependabot

Dependabot は `dependabot.yml` の `cooldown` ブロックに対応しています。

```yaml
version: 2
updates:
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "weekly"
    cooldown:
      default-days: 7
      semver-major-days: 14
      semver-minor-days: 7
      semver-patch-days: 3
```

この設定でセキュリティ更新が遅れることはなく、望ましい挙動です。オプション名は変遷しているので、最新の Dependabot ドキュメントで確認してください。

## pnpm

pnpm には、閾値より新しいバージョンの解決を拒否する `minimumReleaseAge`(分単位)があります。

```yaml
# pnpm-workspace.yaml
minimumReleaseAge: 10080   # 7日(分換算)
minimumReleaseAgeExclude:
  - "@your-org/*"          # 自社パッケージは即時にインストール可能
```

自社組織のパッケージは除外リストに入れておくと、社内リリースがブロックされません。

## npm

npm には、自信を持って勧められる恒久的な同等設定はありませんが、指定日時時点のバージョンを解決する `--before` があります。

```bash
# 公開から7日以上経ったバージョンだけをインストール
npm install --before="$(date -u -d '7 days ago' +%Y-%m-%dT%H:%M:%SZ)"
```

`date -d` は GNU の構文です。macOS では `date -u -v-7d +%Y-%m-%dT%H:%M:%SZ` を使います。主にロックファイルなしでクリーンインストールする CI ジョブで有用ですが、そもそもその運用は避けたいところです。ロックファイルをコミットして `npm ci` を使えば、新バージョンは自分たちの更新 PR を通じてのみ入ってくるため、Dependabot のクールダウンがそこをカバーします。

## uv(Python)

uv には、指定時刻より後にアップロードされた配布物を無視する `exclude-newer` があります。

```toml
# pyproject.toml
[tool.uv]
exclude-newer = "2026-10-15T00:00:00Z"
```

絶対時刻は再現性の面で優れていますが、更新が必要です。週次のジョブで日付を進めて PR を自動作成すれば、レビュー付きのローリングなクールダウンになります。相対期間が使えるかは、お使いのバージョンの uv ドキュメントで確認してください。

## バイパス手順を明文化する

バイパスのないクールダウンは、本物のセキュリティパッチを遅らせたときに、それ自体が事故の原因になります。手順を書き残しておきます。

1. 悪用が確認された CVE や、依存パッケージの修正版が出た場合は、クールダウン外で手動更新する
2. 担当者はリポジトリだけでなく、公開されたパッケージの changelog と diff を読む
3. 例外は PR の説明に記録する

## 穴を埋める対策と組み合わせる

クールダウンは一層にすぎません。次と組み合わせてください。

- **ロックファイルのコミットと強制**(`npm ci`、`pnpm install --frozen-lockfile`、`uv sync --locked`)
- **インストールスクリプトの既定無効化**(ツールが対応していれば)。本当に必要なパッケージだけ許可リストに入れる
- **短命でスコープの絞られた CI 認証情報**。インストール工程が侵害されても、長期シークレットを読めないようにする
- **PR での新規依存の監視**。ワームは推移的依存の追加として入ってくることが多いためです

## 推奨

まず Dependabot と pnpm に7日間のクールダウンを入れ、セキュリティ更新は対象外のままにして、バイパス手順を文書化してください。設定は半日ほどで済み、今年の事例の背景にある「公開され、インストールされ、その後に取り下げられる」パターンへの露出を、かなり減らせます。
