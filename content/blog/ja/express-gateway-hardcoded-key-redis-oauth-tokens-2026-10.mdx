CVE-2026-107177 は、バージョン 1.16.11 までの Express Gateway に影響します。SentinelOne の脆弱性データベースのエントリ（NVD 公開日は 2026年10月7日と記載）によると、原因はハードコードされた既定の暗号鍵です。ゲートウェイの Redis を読み取れる攻撃者は、保存されている OAuth トークンの秘密情報を復号でき、ゲートウェイ経由で認証された任意のユーザーになりすませます。

修正版のリリースやベンダーのアドバイザリは、こちらでは確認できていません。バージョン番号に基づいて対応する前に、プロジェクトのリポジトリと NVD のレコードをご確認ください。確実に言えるのは、この失敗パターンがありふれていて、このゲートウェイを使っていなくても点検する価値があるということです。

## 見た目以上に深刻な理由

「攻撃者が Redis を読める」は、すでに手遅れの前提に聞こえます。しかし実際には、想像より低いハードルで成立します。

- 認証なしで内部ネットワークに公開されている Redis。
- RDB などのバックアップやスナップショットが、保護の弱い場所にコピーされている。
- デバッグ中に `KEYS *` や `MONITOR` の出力がチケットに貼られる。
- 共有クラスタ上の隣接ワークロードやサイドカーが侵害される。

保存時の暗号化は、こうした事故を「全面侵害」から「暗号文の漏えい」に抑えるためのものです。ハードコードされた既定の鍵はその保護を無効にします。鍵がすべてのインストールで同一なので、ソースやパッケージを読んだ人は、鍵を上書きしていないあらゆる環境のデータを復号できます。

## 一般化したパターン

これは Express Gateway 固有の話ではありません。構図は次のとおりです。

1. ライブラリがデータ暗号化のために秘密鍵を必要とする。
2. クイックスタートが動くように、利便性のため既定値を同梱する。
3. 本番環境がクイックスタートの設定をそのままコピーし、変更されない。

同じ形は、JWT の既定署名シークレット、セッションシークレット、管理者の既定パスワードにも現れます。対策は常に、危険な状態を「起こりにくく」するのではなく「起こせなく」することです。

## 自社スタックの点検方法

### 1. 使われ続けている既定値を探す

設定ファイルや環境変数から、ドキュメントの例と一致する値を探します。

```bash
# リポジトリ履歴やサンプル設定に現れるシークレットを探す
git grep -nE "(secret|key|password)\s*[:=]\s*['\"][A-Za-z0-9+/=_-]{8,}['\"]" -- \
  ':!*.lock' ':!node_modules'

# デプロイ済みの設定を、パッケージ同梱のサンプルと比較する
diff <(jq -S . config/gateway.config.yml.sample 2>/dev/null) \
     <(jq -S . deployed/gateway.config.json)
```

本番の値がドキュメントやサンプルの値と一致していたら、公開されているものとして扱います。

### 2. 本物の鍵がなければ起動を失敗させる

データを暗号化するサービスを自分で保守しているなら、既定値を同梱しないでください。早い段階で失敗させます。

```ts
export function loadEncryptionKey(): Buffer {
  const raw = process.env.TOKEN_ENCRYPTION_KEY;
  if (!raw) {
    throw new Error("TOKEN_ENCRYPTION_KEY is required (32 bytes, base64)");
  }
  const key = Buffer.from(raw, "base64");
  if (key.length !== 32) {
    throw new Error("TOKEN_ENCRYPTION_KEY must decode to exactly 32 bytes");
  }
  return key;
}

// 生成例: node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
```

起動しないサービスは5分間だけ面倒です。公開された鍵で起動するサービスは、何年も負債になります。

### 3. Redis に置くものを減らす

プロトコルが許すなら、復号可能な秘密情報ではなくトークンのハッシュを保存します。復号可能な値を保存せざるを得ない場合は、TTL を短く設定します。

### 4. Redis 自体を固める

- 認証を必須にし、ACL でアプリケーションごとに必要なコマンドとキープレフィックスだけを許可する。
- ホストをまたぐ接続には TLS を有効にする。
- Redis をルーティング可能なネットワークに置かず、バックアップを取得できる人を制限する。

### 5. ローテーションを前提にする

鍵はいずれ漏れると考えてください。暗号文ごとに鍵 ID を持たせ、新しい鍵の導入、移行期間中の旧鍵での復号、旧鍵の廃止ができるようにします。ローテーションにダウンタイムやコード変更が必要だと、本当に必要なときに実行できません。

## Express Gateway を運用している場合

プロジェクトから修正版を確認できるまでは、既定の鍵を使っていた環境は漏えい済みとみなすのが安全です。

1. 設定で、一意でランダムな暗号鍵を指定する。
2. ゲートウェイが保存している OAuth トークンとクライアントシークレットを失効させ、再発行する。以前保存された値は読み取られた可能性があるためです。
3. 既定の鍵を使っていた期間の Redis アクセスログとネットワーク露出を確認する。
4. 上記のとおり Redis へのアクセスを制限する。

見落とされがちなのは 2 です。鍵を変えても守れるのは今後のデータだけで、すでに読み取り可能だった秘密情報は守れません。

## まとめ

この CVE は、システム内の暗号化されたストアごとに次を問い直す機会です。鍵はどこから来るのか。環境ごとに一意か。書き直しなしでローテーションできるか。もし答えのどれかが「既定値を使っている」なら、今週中に直すべき指摘事項です。
