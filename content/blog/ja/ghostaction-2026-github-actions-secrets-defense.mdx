GhostActionが最初に報告されたのは2025年9月です。GitGuardianが、数百のリポジトリに不正なワークフローが push され、リポジトリのシークレットが攻撃者のサーバーに送られていたと報告しました。セキュリティ研究者によると、2026年8月下旬から9月にかけて第2波がありました。GitGuardianはこの期間に772の公開リポジトリと2,577件のシークレットが標的になったと集計しており、別の記事では新しい亜種がAnthropic、OpenAI、OpenRouterといったAIプロバイダーのAPIキーも探すとされています。数値は情報源によって異なるため、目安として読んでください。

数字よりも重要なのは仕組みです。単純で、今後も使い回されます。この記事では、その仕組みと、リポジトリ側で何を変えるべきかを説明します。

## 攻撃の仕組み

GitHub Actions自体の脆弱性を突くものではありません。攻撃者はメンテナーの認証情報を手に入れたうえで、次の3つを行います。

1. 既存のワークフローファイルが参照しているシークレット名を列挙する
2. もっともらしい名前の新しいワークフローを push する（2025年のキャンペーンでは「Add GitHub Actions Security workflow」のようなタイトルが使われました）
3. ワークフローが push をトリガーに実行され、各シークレットを名前で読み出して外部のエンドポイントに送信する

見落とされがちなのは1です。ワークフローファイルには、どのシークレットが存在するかがそのまま書かれています。書き込み権限があれば、値を見なくても名前を列挙できます。不正なワークフローはその名前を参照するだけで、値は GitHub が実行時に注入してくれます。

根本原因は、盗まれた認証情報で得られた書き込み権限です。漏洩した Personal Access Token、侵害された開発者のマシン、ディスク上のトークンを読み取った悪意あるパッケージなどが入り口になります。ワークフローは持ち出しの経路にすぎません。

## 対策1: ワークフローの変更をレビュー対象にする

書き込み権限のあるアカウントが、シークレットを扱えるブランチへワークフローを直接 push できるなら、トークン1つ盗まれた時点で終わりです。この経路を塞ぎます。

- デフォルトブランチを保護し、管理者を含めて Pull Request のレビューを必須にする
- ワークフローのディレクトリに `CODEOWNERS` を設定し、特定チームの承認を必要にする

```text
# .github/CODEOWNERS
/.github/workflows/  @your-org/platform-security
```

なお、フィーチャーブランチに push されたワークフローは、`push` イベントではそのブランチ上のファイルで実行されます。次の対策が重要になるのはこのためです。

## 対策2: すべてのブランチにシークレットを渡さない

リポジトリレベルのシークレットは、リポジトリ内のどのワークフローからも読めます。Environment のシークレットなら制限をかけられます。

- 本番の認証情報を GitHub Environment に移す
- その Environment を保護されたブランチやタグに限定する
- その Environment へのデプロイにレビュアーの承認を必須にする

こうすると、任意のブランチ上のワークフローは本番のシークレットを読めません。読もうとした時点で承認ゲートに止まり、人の目に触れます。

## 対策3: 長期シークレットをOIDCに置き換える

最も効果的なのは、盗む価値のあるシークレットそのものを減らすことです。クラウドへのアクセスには OpenID Connect を使い、ジョブが実行時に短命なトークンを認証情報に交換するようにします。

```yaml
permissions:
  id-token: write
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/gha-deploy
          aws-region: ap-northeast-1
```

IAM ロールの信頼ポリシーは、リポジトリ、Environment、ブランチで絞り込みます。別ブランチやフォークから盗まれたワークフローでは、そのロールを引き受けられなくなります。信頼ポリシーの詳細は[GitHub Actions OIDCとAWS](/blog/github-actions-oidc-aws-keyless-2026)の記事で扱っています。

OIDC に対応していないサードパーティAPI（現時点では多くの LLM プロバイダーが該当します）では、静的なキーを持つことになります。これらは最もリスクの高いシークレットとして扱ってください。プロジェクトごとに専用のキーを発行し、プロバイダー側で利用上限を設定し、リポジトリ全体ではなく Environment スコープのシークレットに置きます。

## 対策4: トークンの権限は最小から始める

組織レベルで、デフォルトの `GITHUB_TOKEN` 権限を読み取り専用にし、書き込みが必要なジョブにだけ個別に付与します。

```yaml
permissions:
  contents: read
```

不正なワークフローが他のシークレットを送信するのは止められませんが、組み込みトークンが持ち出された場合にできることを限定できます。

## 対策5: 外向き通信を制限し、監視する

これらのキャンペーンでの持ち出しは、単一のアドレスへの平文HTTPだったと報じられています。ランナーの外向き通信を制限すれば、これはブロックされたリクエストとアラートに変わります。セルフホストランナーをegress許可リストの内側に置けば実現しやすく、GitHubホストランナーでも外向き接続を記録する監視エージェントが使えます。詳しくは[GitHub Actionsのegressファイアウォール](/blog/github-actions-egress-firewall-2026)をご覧ください。

あわせて、push protection 付きの Secret Scanning を有効にし、Pull Request を経由せずに作られたワークフローファイルが組織の監査ログに現れていないか確認してください。

## 不正なワークフローを見つけたら

シークレットのローテーションは必要ですが、それだけでは足りません。GitGuardianは、侵害された GitHub の認証情報自体も失効させるよう勧めています。そうしないと、攻撃者は新しいシークレットに対して同じ手口を繰り返せるためです。

1. 侵害されたアカウントの Personal Access Token、SSH鍵、OAuth アプリの許可を失効させ、セッションを破棄する
2. 不正なワークフローを削除し、全ブランチに同じファイルが残っていないか確認する
3. ワークフローが参照していたシークレットをすべてローテーションする。クラウドとパッケージレジストリの認証情報を最優先にする
4. push から削除までの間の監査ログと、プロバイダー側の利用履歴を確認する
5. 関連リポジトリの git 履歴を検索する。亜種のなかには、Actions のシークレットだけでなく履歴内の認証情報も走査するものがあると報じられています

## チェックリスト

- 必須レビュー付きのデフォルトブランチ保護
- `.github/workflows/` への `CODEOWNERS`
- ブランチ制限と承認付きの Environment に置いた本番シークレット
- リポジトリ・Environment・ブランチで絞ったクラウド向けOIDC
- デフォルトを読み取り専用にした `GITHUB_TOKEN`
- 利用上限付きでプロジェクトごとに分けた LLM APIキー
- push protection 付きの Secret Scanning
- ランナーの egress 監視

どれも目新しい助言ではありません。それがポイントです。この種のキャンペーンは、基本対策が一部しか入っていないリポジトリで成功します。上から順に整えていけば、トークン1つを盗んだ攻撃者が得られる価値の大半を取り除けます。
