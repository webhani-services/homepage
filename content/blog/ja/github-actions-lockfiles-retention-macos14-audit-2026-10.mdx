GitHub の10月の changelog には、CI の管理者がまとめて確認しておきたい Actions の変更が3つあります。劇的なものではありませんが、いずれもパイプラインやコンプライアンス上の前提を静かに壊す可能性があります。以下の内容は、検索結果で要約された GitHub の changelog に基づいています。日付や詳細の一部はサードパーティのインデックス経由で得たものなので、対応する前に github.blog/changelog で確認してください。

## 1. ワークフロー依存関係の lockfile（パブリックプレビュー、10月14日）

`uses: some-org/some-action@v3` はタグを指していますが、タグは動かせます。弱点はよく知られており、2025年のタグ書き換えインシデント以降は、アクションをコミット SHA 全体で固定するのが標準的な助言になりました。有効ですが、手作業での維持は面倒で、ネストした依存（アクションが別のアクションを呼ぶ場合）は見えにくいという問題があります。

GitHub は、ワークフロー依存関係の lockfile を Enterprise Cloud、Team、Free プラン向けにパブリックプレビューとして公開しました。changelog の索引にある説明では、タグやブランチが後から動いても、ロックしたコミットのままで実行され、`gh actions-lock` 拡張機能が lockfile を管理するとのことです。

私たち自身のリポジトリ全体ではまだ試していないため、以下は推奨ではなく評価計画としてお読みください。

- まずリスクの低いリポジトリ1つで試し、生成された lockfile を Pull Request で確認する。
- 再利用可能ワークフローや composite action の扱いを確認する。見えない推移的依存が潜むのはそこです。
- lockfile の更新担当を決める。Dependabot や Renovate が管理しない場合、「タグが黙って動く」問題を「誰もロックを更新しない」問題に置き換えるだけになりかねません。
- 当面は SHA 固定を続ける。ネストした参照まで lockfile がカバーすると確認できるまで、両者は代替ではなく補完関係です。

今日から適用できる最低ラインは次のとおりです。

```yaml
steps:
  - uses: actions/checkout@<full-commit-sha>  # v5.x.y
    with:
      persist-credentials: false
```

SHA の横に人が読めるバージョンをコメントで添えておくと、レビューが現実的になります。

## 2. 保持期間がチェック・ワークフロー実行・ステータスにも適用（10月1日）

これまでリポジトリの保持期間設定が管理していたのは、アーティファクトとログでした。changelog によれば、10月1日からは、チェック、ワークフロー実行、ステータスにも適用されます。Organization や Enterprise の上限は引き続き有効で、パブリックリポジトリの最大保持期間は90日です。

実務上の影響は次のとおりです。

- **監査証跡が短くなる。** 「このコミットは CI を通過した」という証拠が Actions の実行やステータスチェックである場合、その証拠は保持期間に従って失効します。数か月前の変更をサンプリングする SOC 2 や ISO 27001 の監査があるチームは、何を提出できるか確認してください。
- **デバッグ履歴が減る。** 不安定なテストの四半期分の成功率を比較するには、GitHub 上にもう残っていないデータが必要になるかもしれません。
- **過去の実行を参照するツール**（ダッシュボード、DORA 指標の収集、コストレポート）で欠損が出る可能性があります。

対応としては、次のようにします。

```bash
# リポジトリの現在の保持設定を確認する
gh api repos/OWNER/REPO/actions/permissions/artifact-and-log-retention
```

このエンドポイント名は私たちが未確認ですので、お使いのプランの REST ドキュメントで確認してください。そのうえでリポジトリごとに判断します。監査期間に合わせて保持期間を設定するか、必要なもの（実行メタデータ、テストレポート、SBOM）を自分たちが管理するストレージへ定期的にエクスポートするかです。設定は誰かが変更できてしまうため、コンプライアンス用の証跡にはエクスポートのほうが堅牢です。

## 3. macOS 14 ランナーは11月2日に終了

macOS 14 ランナーイメージは2026年11月2日に終了予定で、あと6日です。また、10月15日には Xcode 27 ランナーイメージが一般提供になりました。

`macos-14` を指定しているジョブは、終了の適用方法によって、動かなくなるか別イメージに振り替えられます。今のうちに洗い出してください。

```bash
grep -rn "macos-14" .github/workflows
```

`macos-15` 以降へ移行します（イメージが入れ替わることを許容するなら `macos-latest` も選択肢です）。iOS や macOS のビルドでは、Xcode のバージョン変更をまずブランチで検証してください。ランナー移行では、そのまますんなり通るよりも、シミュレーターや SDK の差異が表面化することのほうが多いものです。

## 関連する補足：許可リストのホスト

10月22日付けの changelog では、Actions の Blob ストレージ向けの meta API エンドポイントが更新されました。二次情報によると、セルフホストランナーのためにホスト単位で許可リストを管理している組織は、新しいホストを追加しないと、ジョブサマリーやログが途切れる可能性があります。ランナーが外向き通信の許可リストの内側にある場合は、今週中に meta API の出力とファイアウォールのルールを突き合わせてください。

## webhani のチェックリスト

1. 11月2日までに `macos-14` を検索して移行する。
2. 保持期間の設定を確認し、延長するか、証跡をエクスポートするかを決める。
3. ランナーに外向き通信の許可リストを使っているなら、meta API から更新する。
4. lockfile は1つのリポジトリで試験運用し、その間も SHA 固定は維持する。
5. この4項目は一度きりのチケットにせず、CI 管理者の四半期レビューに組み込む。この種のプラットフォーム変更は、こちらでは制御できないスケジュールでやってきます。

CI の設定は本番インフラです。デプロイ対象のサービスと同じ水準で、変更を追跡するべきです。
