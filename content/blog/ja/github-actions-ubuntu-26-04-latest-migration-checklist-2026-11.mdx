GitHub の changelog によると、`ubuntu-latest` ラベルは Ubuntu 24.04 から Ubuntu 26.04 へ、2026 年 10 月 19 日から 11 月 19 日にかけて段階的に切り替えられます。期限まであと 2 日です。`runs-on: ubuntu-latest` を使っているワークフローは、すでに新しいイメージで動いているジョブがあるかもしれません。

この変更は「お知らせ」であり、それ自体でジョブが失敗することはありません。問題が出るのは後からです。昨日まで通っていたジョブが、ツールの欠落やライブラリのバージョン違いで落ちる、という形で現れます。本記事では、そうしたケースを意図的に見つけるための手順を紹介します。

## なぜ見落としやすいのか

動くラベルは、固定していない依存関係です。多くのチームは `ubuntu-latest` を「とりあえず動くもの」として扱ってきましたし、これまではそれで問題ありませんでした。しかし OS のメジャーアップグレードでは、システムパッケージ、コンパイラ、Python や OpenSSL のバージョン、プリインストールされるソフトウェアが変わります。GitHub の runner-images プロジェクトは各イメージの収録ツールを公開しており、26.04 では保守上の理由によるツールの削除も議論されていました。

削除リストは固定情報ではなく、最新のイメージ README で確認すべきものとして扱ってください。調査時に見つけた情報では Julia や Mercurial などが挙がっていましたが、これはリリース前の議論に基づくもので、最終的なイメージと一致するとは限りません。

## ステップ 1：動くラベルの使用箇所を洗い出す

```bash
# 動くラベルを使っているワークフロー
grep -rn "ubuntu-latest" .github/workflows/

# Reusable Workflow や Composite Action にも潜んでいる
grep -rn "runs-on" .github/ | grep -v "ubuntu-24.04"
```

他のリポジトリから呼び出している Reusable Workflow は、それぞれの `runs-on` を持っています。こちら側では修正できませんが、結果の変化として影響が現れます。

## ステップ 2：明示的なラベルでテストを走らせる

`ubuntu-latest` でテストするのは避けてください。ロールアウト中はどちらのイメージにも解決され得ます。再現性のため、明示的なラベルを使います。

```yaml
jobs:
  test:
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-24.04, ubuntu-26.04]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-node@v6
        with:
          node-version: 24
      - run: npm ci
      - run: npm test
```

ここでは `fail-fast: false` が重要です。新しいイメージ上の失敗を 1 回の実行で全て確認したいためです。`ubuntu-24.04` の枠をベースラインとして残しておくと、移行による退行と不安定なテストを切り分けられます。

Action のバージョンは現在使っているものに合わせてください。上記は例示です。コミット SHA で固定している場合は、そのまま維持してください。

## ステップ 3：暗黙の前提を点検する

ジョブが宣言的なセットアップではなく、イメージそのものに暗黙に依存している箇所を確認します。

- **セットアップなしで使っているプリインストールツール。** ワークフローがインストールしていない `hg` や `julia` などの CLI を呼んでいる場合、最も壊れやすい箇所です。明示的なインストール手順やセットアップ用 Action を追加してください。
- **システムライブラリのバージョン。** OpenSSL、libpq、画像系ライブラリにリンクするネイティブビルドは、新しいパッケージで挙動が変わることがあります。
- **言語ランタイムの既定値。** `actions/setup-python` ではなくシステムの `python3` に頼っていると、OS とともにバージョンが変わります。
- **Docker とコンテナ Action。** サービスコンテナや `docker build` が引き続き動くか、rootless や cgroup に関する前提も含めて確認します。
- **自作のインストールスクリプト。** `apt-get install <package>` は、新しいリリースでパッケージ名が変わったり削除されたりすると失敗します。
- **OS 名をキーにしたキャッシュ。** `${{ runner.os }}` は Ubuntu のリリースを区別しないため、24.04 でビルドした成果物が 26.04 に復元され得ます。キーにイメージのバージョンを含めてください。

```yaml
- uses: actions/cache@v5
  with:
    path: ~/.cache/build
    # runner.os は単に "Linux"。リリースを明示的に含める
    key: build-ubuntu-26.04-${{ hashFiles('**/lockfile') }}
```

## ステップ 4：方針を決めて固定する

現実的な選択肢は 2 つです。

1. **準備ができていなければ `ubuntu-24.04` に固定する。** GitHub の changelog でもオプトアウト手段として案内されています。時間を稼げますが、先送りにすぎません。古いイメージはいずれ廃止されるため、本格的な移行の予定を立ててください。
2. **マトリクスが通ったら `ubuntu-26.04` に明示的に移行する。** リリースを左右するジョブでは、`ubuntu-latest` より明示的なラベルを推奨します。自分で選んでいない日付に OS イメージが変わるデプロイパイプラインは、デバッグが困難です。

切り替え後の数回は、ジョブの所要時間と不安定なテストの発生率をベースラインと比較してください。新しいカーネルやツールチェーンはタイミングを変え、潜在していた競合状態を表面化させることがあります。

## 関連する変更も確認を

この秋のランナー関連の変更はこれだけではありません。Actions からの Node 20 の削除（ファーストパーティ Action は Node 24 対応）や、11 月 2 日の macOS 14 イメージの廃止にも対応済みか確認してください。公開リポジトリを管理している場合は、12 月 2 日から予定されている `pull_request_target` の既定ブロックも見直しておくとよいでしょう。

## webhani の推奨

`ubuntu-latest` は、プロトタイプや重要度の低いジョブでの利便性のために使うものと考えています。ビルドとリリースのパイプラインでは明示的な OS ラベルを固定し、新しい LTS が出たら 2 イメージのマトリクスで検証し、自分たちのスケジュールでアップグレードしてください。移行ごとに YAML を 1 行直すコストで、ランナーの更新が障害になる事態を避けられます。
