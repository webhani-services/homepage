GitHub Agentic Workflows が Public Preview に到達しました。2026年2月の Technical Preview から半年での昇格です。この機能は、Issue の Triage、PR Review、CI 失敗の原因調査、Documentation の更新といった Repository 運用タスクを、GitHub Actions 上で動く Coding Agent に自動化させる仕組みです。

## 何が新しいのか

最大の特徴は、複雑な YAML ではなく Markdown で自動化の意図を記述する点です。`.github/workflows/` に Markdown File を置くと、`gh aw` CLI がそれを標準の GitHub Actions Workflow に変換します。GitHub Copilot CLI などの Coding Agent を実行 Engine として使い、自然言語で書かれた指示を Agent が解釈して実行します。

以下は Issue Triage を行う Workflow の概念的な例です。

```markdown
---
on: issues.opened
permissions: read
---

# Issue Triage

When a new issue is opened:
1. Read the issue title and body
2. Check for related open issues or PRs
3. Suggest appropriate labels based on the repository's label conventions
4. Post a triage comment summarizing the issue and next steps

Do not close or modify existing issues.
```

この Workflow は追加設定なしで動作し、Issue が作成・再オープンされるたびに内容を分析し、関連 Issue のチェック、Label 付与、Triage Comment の投稿までを自動で行います。

## Security 設計が要点

Agent に Repository 内の操作を任せる以上、最大の懸念は「意図しない書き込み」です。GitHub Agentic Workflows はこれを 2 つの仕組みで抑えています。

- **デフォルトで Read-only 権限** — 明示的に許可しない限り、Agent は Issue や PR への書き込みができません
- **Safe Outputs という事前承認済み操作のみ許可** — Label 付与や Comment 投稿など、あらかじめ定義された安全な操作のみを Agent が実行可能

この設計により、「Agent が誤って本番 Branch に Push する」といった最悪のシナリオを構造的に防いでいます。

## 導入する際の実務的な進め方

webhani がこの種の Agentic CI/CD 機能を Client に提案する際は、以下の順序を推奨しています。

1. **まず Read-only な Workflow から始める** — Issue Triage のように書き込み範囲が限定されたものを最初に試す
2. **対象 Repository を限定する** — 全社の Repository に一括導入せず、影響範囲が把握しやすい 1〜2 個の Repository で運用実績を積む
3. **Agent の出力を Human が Review する期間を設ける** — Safe Outputs の範囲内であっても、初期は Comment や Label 付与の内容を人間が確認し、Prompt の調整を重ねる

## まとめ

GitHub Agentic Workflows は「CI/CD に AI Agent を組み込む」という大きな流れの中でも、Markdown による宣言的な記述と Safe Outputs による権限制御を両立させた点で実務的な完成度が高い機能です。ただし Public Preview 段階である以上、まずは Read-only かつ小規模な Repository での検証から始めるのが妥当です。
