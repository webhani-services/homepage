シークレットスキャナーが得意なのは、形式が決まったトークンの検出です。AWSのアクセスキー、GitHubのPersonal Access Token、Stripeのキーなどです。一方、形式のないシークレット、たとえば設定ファイル内のデータベースパスワードや独自APIの認証情報は苦手で、漏えいはそういうところで起きがちです。

2026年10月、GitHubはこの穴の一部を埋める動きを見せました。10月28日付のchangelogに、AI検出シークレットに対するPush Protectionがパブリックプレビューとして記載されています。同月前半に説明された、漏えいシークレット検出用の専用モデルを土台にした機能です。本稿では、公開されている内容、コストの考え方、チームのワークフローへの組み込み方を整理します。情報はGitHubのchangelogと報道にもとづくため、導入前にご自身のプランでの提供状況と料金を確認してください。

## 何が変わったか

Push Protectionは従来、GitHubのパートナーパターンやカスタムパターンに一致するシークレットを含む `git push` をブロックしてきました。今回の拡張では、AIモデルが検出したシークレットも対象になります。パターンでは表現できない汎用パスワードのようなものを拾えるようになります。

報じられている条件は次のとおりです。

- 対象リポジトリでPush ProtectionとAI検出シークレットスキャンがすでに有効であること。
- github.com上でGitHub Secret ProtectionまたはGitHub Advanced Securityを契約している組織が対象。
- パブリックプレビューで、Push ProtectionでのAI検出にはAIクレジットを消費し、オプトインした時点から課金される。push後のスキャンによるアラートは追加料金なしで含まれる。

最後の点が導入方法に影響します。パターンベースの保護と違い、push量に応じて変動コストが発生するため、初日から組織全体で有効化するのではなく、意図をもって段階的に進める必要があります。

## 今、重要性が増している理由

1年前より汎用シークレット検出の価値が上がっている背景は2つあります。

1つ目は、コーディングエージェントが設定ファイルを書くことです。エージェントは `.env.example`、docker-composeのサービス定義、テストフィクスチャを生成し、もっともらしいパスワードを入れることもあれば、見える範囲の環境から実物をコピーしてしまうこともあります。Universeで報じられたOctoverseの数字では、エージェントが開くプルリクエストは4割を超えています。機械が書くコードが増えるほど、誰も細かく見ないdiffに認証情報が紛れ込む機会も増えます。

2つ目は、見逃しのコストが高いことです。パターンスキャナーが汎用パスワードを見逃すと、実際には問題のあるリポジトリに「問題なし」の結果が出てしまいます。

## 多層で考える

単一の対策では足りません。前段が見逃したものを次の段が拾う、3層構成を提案します。

### 第1層：開発者のマシンでのpre-commitスキャン

シークレットがgit履歴に入る前に止めるのが最も安上がりです。オープンソースのスキャナーをローカルhookで使えば、オフラインで動き、クレジットも消費しません。

```yaml
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.24.2
    hooks:
      - id: gitleaks
```

`rev` は検証済みのリリースに固定してください。上記のバージョンは例であり、推奨ではありません。

### 第2層：サーバー側のPush Protection

GitHubの今回の機能はここに位置します。hookを通らなかったマシン、たとえばエージェントのサンドボックスやCIボットからのpushに対する最後の砦です。まずパターンベースのPush Protectionを広く有効化し、そのうえでAI検出オプションを、インフラや連携コードなど設定のリスクが高い数リポジトリで試し、アラートの質とクレジット消費の両方を観察します。

### 第3層：push後のアラートとローテーション

事後の検出にも価値はありますが、pushされたシークレットへの正しい対応は、侵害されたものとして扱うことだけです。履歴から消しても、漏れた事実は消えません。

REST APIで未対応のアラートを一覧し、ダッシュボードやオンコールのキューに流せます。

```bash
gh api repos/OWNER/REPO/secret-scanning/alerts \
  --jq '.[] | select(.state == "open") | {number, secret_type, created_at}'
```

あわせて、ローテーション手順書を用意しておきます。誰が回すのか、シークレットはどこにあるのか、目標は15分か2時間か、旧値が無効になったことをどう確認するのかを書きます。

## bypassの扱い

Push Protectionでは、開発者が理由（「誤検知」「テストで使用」など）を付けてブロックを回避できます。誰がそれをレビューするかを先に決めてください。最低限、bypassイベントをセキュリティチャンネルに流し、週次で確認します。「テストで使用」が多い場合は、テスト側を変えるサインです。`test-password-not-real` のように明らかに偽物とわかる値を使えば、人にもスキャナーにも区別がつきます。

## 導入チェックリスト

1. プランにSecret ProtectionまたはAdvanced Securityが含まれているか、AIクレジットの課金方式を理解する。
2. リポジトリテンプレートにローカルスキャナーのpre-commit hookを入れる。
3. 組織全体でパターンベースのPush Protectionを有効化する。
4. AI検出の保護を2〜3リポジトリで2週間試し、ブロック数、誤検知、消費クレジットを記録する。
5. 範囲を広げる前に、ローテーション手順書とbypassレビューの担当者を決める。
6. エージェントの設定を見直し、偽の値で作業させ、本番の認証情報を環境に渡さないようにする。

最後の項目が最も重要です。検出器はシークレットが漏れたときの被害を小さくしますが、より強い対策は、エージェントや開発者が編集するコードの手の届く範囲に、本番のシークレットをそもそも置かないことです。
