## 欠けていた拡張ポイントとしての Plugin

GitHub は今月、Agent Plugins 1.0 を VS Code、Copilot CLI、Copilot SDK、Copilot app 全体で一般提供しました。すべての Copilot プランで利用可能です。Plugin は Awesome Copilot マーケットプレイスに公開され、各サーフェスでデフォルト有効になっています。1.0 の Plugin 形式を対象としていない既存の Copilot 拡張機能も、移行なしで動作し続けます。

これだけを見ると「マーケットプレイスの追加」という細かなパッケージング変更に見えます。注目すべきはその上に何が積み上がっているかです — Model Roster は Claude Sonnet 4.6 / Opus 4.6、GPT-5.4、Gemini 3.1 Pro、Grok Code Fast 1 まで広がり、同じ期間に Gemini 3.7 Flash と Grok 4.6 の展開も始まりました。Copilot はもはや単一モデル・固定機能のプロダクトではなく、異なる Model を背負った異なる Agent が共通インターフェースを通じて接続する Runtime になりつつあります。

この違いは運用上重要です。Agent Plugins 1.0 向けに構築された Plugin は、そのセッションでたまたま選択された Model に縛られません。Tool、Context Provider、Instructions を一度定義すれば、背後の Model が Claude であれ GPT であれ Gemini であれ Grok であれ、一貫して呼び出されます。特定の Model の癖に合わせて Prompt Engineering を積み上げた挙句、Model が静かに切り替わって挙動が劣化した経験があるチームにとって、安定した Plugin Contract のほうがより持続的な投資です。

## 既存の Agentic Coding Stack のどこに収まるか

現在 AI Coding Agent を運用しているチームの多くは、その場しのぎの規約を積み重ねています — `CLAUDE.md` や `.cursorrules`、いくつかの MCP Server、独自の Slash Command、セッション開始前に Project Context を注入する Wrapper Script など。これらは機能しますが、Tool ごと Project ごとの個別実装であり、`.cursorrules` の内容は別の Editor を使うチームメイトには一切引き継がれません。

Agent Plugins 1.0 向けにパッケージされた Plugin は、より Portable な単位に近づきます — Tool 定義、Context 注入、Instructions を束ねて、リポジトリ間でのコピペではなくマーケットプレイス経由で配布します。実際にはこのような形になります。

```jsonc
// .github/copilot/plugin.json (構造例)
{
  "name": "webhani-nextjs-conventions",
  "version": "1.0.0",
  "description": "Next.js + TypeScript リポジトリの Project 規約",
  "tools": [
    {
      "name": "check_image_optimization",
      "description": "public/images 配下の新規画像が Project Policy 通りに圧縮されているか検証"
    }
  ],
  "contextProviders": [
    {
      "name": "component-naming",
      "description": "src/components 編集時に Area* Component 命名規約を提示"
    }
  ]
}
```

具体的な Schema は GitHub の実装次第で変わりますが、重要なのはその形です — 規約は Agent が丁寧に読むかどうか分からない Document ではなく、配布可能な Artifact になります。すべてを1つの Instructions File に詰め込んで、Model が正しいセクションに注意を払ってくれることを祈るより、明確な進歩です。

## より本質的な変化は Multi-Model Roster

Plugin 形式は有用ですが、Agentic Coding における Vendor Lock-in の考え方を変えるのは Model Roster の拡大です。半年前まで、AI Coding Tool を選ぶことは暗黙的に Model を選ぶことでした。今の Copilot Roster は4つの Lab の Frontier Model を含み、さらに Rolling で追加されています(Kimi K3 や MAI-Code-1.1-Flash も直近の Release Notes に登場しています)。

Engineering Lead にとって、これは評価の問い自体を変えます。もはや「どの Coding Assistant の Model が最も優れているか」ではありません — Model の品質差は月単位で縮小・変動し、どの Lab も全タスクタイプで持続的な優位を保てません。より本質的な問いは「Tooling を書き直さずに Model を切り替えられる Platform はどれか」です。GitHub 自身のエコシステムへの Lock-in 機構でない限り、Plugin Architecture がその問いへの答えになります。

## Client に推奨していること

すでに Claude Code や Cursor など単一 Vendor の Agentic Workflow に投資しているチームにとって、Agent Plugins 1.0 は乗り換えの理由にはなりません — 基盤となる Model の品質が依然として大部分の仕事をこなしており、切り替えコストも現実的なものです。しかし、チームの AI Coding 規約がどれだけ Portable かつ Versioned な Artifact として存在しているか、それとも1つの Tool でしか動かない Instructions File の山になっているかを監査する理由にはなります。

具体的に提案している2点です。

1. **共有規約を特定 Editor に縛られない形式へ抽出する。** `CLAUDE.md` などが Project 固有の事実を超えて「ここでの TypeScript の書き方」といった一般的な指針まで肥大化しているなら、その内容は最終的にどの Vendor の Plugin 形式が主流になるかに関わらず Plugin 候補です。
2. **Model 切り替えコストを明示的な指標として追跡する。** 次に Coding Agent を評価する際は、Model 変更にどれだけの Prompt/Tool 定義の作り直しが必要かを確認してください。「Portable な Plugin にすべて定義されているので不要」であれば、それは現時点で Benchmark 上位の Model が何であれ独立した優位性です。

Agentic Coding の landscape は、Tool アクセス用の Model Context Protocol と、規約パッケージング用の Plugin 形式という、少数の相互運用性標準へと収束しつつあります。持続的な社内 Tooling を構築するチームにとって、特定 Vendor の現時点の Model ラインナップではなく、こうした標準に賭けるほうがより防御力のある立ち位置です。
