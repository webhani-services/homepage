Go 1.27は8月にリリースされ、目玉はジェネリックメソッドでした(当ブログでも[以前取り上げました](/blog/go-1-27-generic-methods-2026))。ただし、より多くの本番コードに影響するのは地味な変更の方です。`encoding/json/v2`が、`GOEXPERIMENT=jsonv2`の裏にある実験ではなく通常のパッケージになり、パッケージドキュメントも新規のJSONコードにはv2を推奨しています。

計画上いちばん大事なのは、見落としやすい区別です。二次情報とパッケージドキュメントによると、Goのツールチェーンを更新しただけでは既存の`encoding/json`の挙動は変わらず、v1は従来のセマンティクスを保ちます。リスクが生じるのは、importを`encoding/json/v2`に変えたときです。コンパイルは通るのに挙動が変わる、というタイプの移行で、変更の後ではなく前にテストを用意しておく価値があります。

## 挙動が異なる箇所

v2の既定はより厳格です。ドキュメントで示されている違いのうち、確認しておきたい領域は次のとおりです。

- **重複したオブジェクトメンバー名。** `{"a":1,"a":2}`をv1は受け入れます(最後の値が優先)が、v2はエラーを返します。
- **不正なUTF-8。** v1は不正なシーケンスを黙って置換し、v2は既定で拒否します。
- **nilのスライスとマップ。** v1はnilスライスを`null`としてエンコードし、v2は設定しない限り空配列としてエンコードします。`null`と`[]`を区別するクライアントは違いに気づきます。
- **フィールド名の照合。** v1はJSONキーと構造体フィールドを大文字小文字を区別せずに照合し、v2は既定で区別します。`userId`タグのフィールドに`UserID`を送るクライアントは以前は動いていましたが、今後は黙って無視される可能性があります。
- **構造体タグ。** v1のタグオプションの一部は、v2では異なる、あるいは名前が変わった形になっています。

どれも特殊なケースではありません。実際のトラフィック、とくにサードパーティのクライアントや古いモバイルアプリは、寛容な挙動に依存している場合があります。

## テストを先に書く

一覧を読んで祈るのではなく、実際のペイロードで現在の挙動を記録し、同じコーパスをv2にも流します。

```go
package payload_test

import (
	jsonv1 "encoding/json"
	jsonv2 "encoding/json/v2"
	"reflect"
	"testing"
)

type Order struct {
	UserID string   `json:"userId"`
	Items  []string `json:"items"`
}

var corpus = []string{
	`{"userId":"u1","items":["a"]}`,
	`{"UserID":"u1","items":["a"]}`,        // 大文字小文字の不一致
	`{"userId":"u1","userId":"u2"}`,        // 重複キー
	`{"userId":"u1","items":null}`,         // nullのスライス
	"{\"userId\":\"\xff\"}",                // 不正なUTF-8
}

func TestV1V2Decode(t *testing.T) {
	for _, in := range corpus {
		var a, b Order
		errA := jsonv1.Unmarshal([]byte(in), &a)
		errB := jsonv2.Unmarshal([]byte(in), &b)
		if (errA == nil) != (errB == nil) || !reflect.DeepEqual(a, b) {
			t.Errorf("divergence for %q:\n v1=%+v err=%v\n v2=%+v err=%v", in, a, errA, b, errB)
		}
	}
}
```

コーパスは、可能であればマスキングした本番のリクエストログから作ってください。手書きの例では、すでに想定していたケースしか拾えません。出力される差分の一覧が、そのまま移行のバックログになります。

エンコード側では、レスポンス型のバイト出力を比較します。`null`が`[]`に変わるのは、Goのテストがすべて通ってもAPI利用者にとっては契約の変更だからです。

## 境界ごとに厳格さを選ぶ

すべての境界で同じ挙動にする必要はありません。

| 境界 | 推奨する方針 |
|---|---|
| 社内のサービス間通信 | v2の既定へ移行。厳格な失敗がバグを早期に表面化する |
| サードパーティ入力を受ける公開API | 差分を把握するまでv1の挙動を維持 |
| 自分たちで管理する設定ファイルやWebhook | v2の厳格さは多くの場合改善になる |
| 後で読み戻す保存済みJSON | デコーダーを切り替える前に古いレコードでテスト |

重複キーについては補足があります。2つのコンポーネントが同じドキュメントを読んで解釈が食い違う、いわゆるパーサー差異のバグの原因として知られています。ゲートウェイとバックエンドが同じリクエストを異なる解釈で処理すると、その隙を攻撃に使われる恐れがあります。重複の拒否は、正規のクライアントが重複を送っていないことを確認できれば、妥当な堅牢化です。

## 段階的なロールアウト

1. importは変えずに、ツールチェーンを1.27へ**更新**する。テストスイートを実行する。何も起きないはずです。
2. ログとフィクスチャから**コーパスを作成**し、上記の差分テストを実行する。
3. 差分ごとに**修正または許容**を決める。既定に頼らず、構造体タグやオプションを明示する。
4. 同じ差分テストをCIに置いたうえで、内部コードから**1パッケージずつ移行**する。
5. パッケージごとに本番の**デコードエラーを監視**する。400レスポンスの増加がシグナルです。

## まとめ

- ツールチェーンの更新とimportの変更は、別々の判断であり、リスクも別です。
- v2の厳格な既定は実際のバグを見つけますが、クライアントが依存する挙動も変えます。
- 移行ノートを読むより、実ペイロードでの差分テストが確実です。
- 重複キーの拒否はセキュリティ強化として扱いつつ、正規トラフィックに影響がないことを確認します。
- リポジトリ全体を1つのプルリクエストで置き換えず、境界ごとに移行します。

ここで述べた挙動はGoのパッケージドキュメントとサードパーティの移行解説に基づきます。お使いのバージョンでの正確な仕様は、Go 1.27のリリースノートで確認してください。
