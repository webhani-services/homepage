## Generics が残した空白

2022年に Go 1.18 が Generics を導入した際、具体的な型を軸に Generic な API を設計しようとした人なら誰もが気づいた制約がありました — Method は自身の Type Parameter を宣言できなかったのです。Package スコープで Generic な関数を書くことはできても、ある型に対する Method を別の型について Generic にしたい場合は、Free Function として書かざるを得ず、Method 構文の使い勝手を失っていました。

今月リリースされた Go 1.27 はこの空白を埋めます。Method は、Receiver 型自体が持つ Type Parameter とは独立に、自身の Type Parameter を宣言できるようになりました。これまでは、ある型に論理的に属する操作 — Container を map する、2つの Parameterized 型を変換する、異なる Element 型を持つ2つのインスタンスを結合する、といった操作 — は Package レベルの関数として書くしかありませんでした。言語がそれ以外の置き場所を提供していなかったからです。

```go
type Container[T any] struct {
    items []T
}

// Go 1.27: Method が自身の Type Parameter U を宣言。
// Container の T とは独立している
func (c Container[T]) MapTo[U any](f func(T) U) Container[U] {
    out := make([]U, len(c.items))
    for i, v := range c.items {
        out[i] = f(v)
    }
    return Container[U]{items: out}
}
```

1.27 以前は `MapContainer[T, U any](c Container[T], f func(T) U) Container[U]` のような独立した関数にするしかありませんでした。動作はしますが、Method Chaining が崩れ、操作が型自身の Namespace の外に置かれてしまいます。Collection 型や Result/Option Wrapper、Generic な Pipeline 抽象を書いてきた Library 作者にとって、これは単なる構文糖衣ではなく、意味のある使い勝手の改善です。

## それでも残る境界

Go の Generics は意図的に保守的な設計を保っています。Interface は依然として Type-Parameterized な Method を宣言できず、Generic Method で Interface を満たすこともできません。つまり「Generic な `Map` Method を持つ任意の型」のようなものを Interface 制約として表現することは、今もできません。Go チームはその扉を閉じたままにしています。おそらく Interface レベルでの Parametric Polymorphism がもたらす複雑性の爆発(Scala や Haskell のような言語が実際のコストを払って扱っている領域)を避けるためでしょう。

ほとんどの Backend・Web Service コードでは、この境界を直接意識することはないでしょう。より影響を受けるのは、Generic な Data Structure や関数型スタイルの Utility Package を構築する Library 作者で、これまでの制約が不格好な回避策を強いていた領域です。

## リリースのそれ以外の部分

Generic Methods が目玉ですが、Go 1.27 では本番 Service で Go を運用しているチームが追うべき変更が他にもいくつか入っています。

**新しい `encoding/json/v2` 実装** が標準ライブラリの一部として導入され、従来の `encoding/json` Package に長年寄せられていた Performance と正確性への不満 — 特に大きな Payload の Streaming や数値精度の扱いに関するもの — に対応します。

**サイズ特化型のメモリ Allocation** により、80 Byte 未満の Object の Allocation コストが最大30%削減されるとリリースノートに記載されています。JSON を多用する API や高スループットな Proxy など、Allocation の多い Service にとって、コード変更なしで得られる意味のある改善です。

**Goroutine Leak Profiling** が Runtime の Profiling Tool に組み込まれました。Channel が閉じられない、あるいは Context がキャンセルされないことで静かに蓄積していく Goroutine という、これまで発見が困難だったバグのクラスが、サードパーティの Leak Detector を必要とせず、標準の `pprof` 出力から見えるようになります。

**標準ライブラリの `uuid` Package** により、Go Service で最も頻繁に Vendor されてきた Utility の一つについて、サードパーティ依存が不要になります。

**実験的な `simd` Package** は、利用可能な場合にハードウェアの Vector 命令を使う、Portable かつ Vector サイズに依存しない SIMD 操作を提供します。これまで cgo か Vendor 固有のアセンブリを必要としていた、数値計算が多いワークロード(画像処理、Embedding、Data Pipeline)にとって意味があります。

**より柔軟になった Struct リテラル構文** により、Nested または Embedded された Struct のフィールドを直接初期化できるようになり、深くネストした設定用 Struct の Boilerplate が減ります。

## 実務的な結論

これらの変更は Go の根本的な性格を変えるものではありません — Go は依然として保守的で明示的な言語であり、機能追加はゆっくりで、一度リリースした設計判断を見直すことはめったにありません。Generic Methods はその原則を裏付ける例外です。2022年の Generics 導入時に特定されていた空白が、4年間の本番運用の経験を経てトレードオフが明確になった後、ようやく埋められました。

新しい Backend Service に Go を検討しているチームにとって、これらの変更単体で判断が変わることはないはずです — 言語の中核的な価値提案(高速な Compile、シンプルな Deploy、強力な標準ライブラリ、予測可能な Performance)は変わっていません。しかし既に本番で Go を運用しているチームにとって、`json/v2` Package と Goroutine Leak Profiling は既存の Service に対して試す価値があります。どちらも Architecture の変更を必要とせず、Go の Version 更新(`json/v2` については明示的な Opt-in)だけで、実際の運用課題に対応できます。
