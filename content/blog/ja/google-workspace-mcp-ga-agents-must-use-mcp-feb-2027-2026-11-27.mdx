2026年11月24日、Google は Workspace の Hosted MCP サーバーと公式の Workspace CLI を一般提供(GA)にしたと発表しました。ただ、製品そのものより重要なのは、それに付随するポリシーです。報道によると、Workspace のデータにアクセスする AI エージェントは、既存の REST API ではなく MCP サーバーか CLI を経由する必要があり、技術的な強制は2027年2月1日から始まります。

本記事は Google の Workspace Updates の投稿を伝える二次情報に基づいています。クォータや料金体系の数字は情報源によって異なるため、計画を固める前に必ず Google の公式ドキュメントで確認してください。ただし、方向性は十分に明確で、今から動けます。

## 発表内容(報道ベース)

- Gmail、Drive、Docs、Sheets、Slides、Calendar、Chat、Tasks 向けの Hosted MCP サーバーが GA。People API、Classroom、Universal Search などは Developer Preview のまま。
- 構造化 JSON を返し、スコープ付き OAuth でサインインする Workspace CLI も GA。
- 利用規約への追加条項で、エージェントはこれらを使うことが求められる。OAuth クライアントで認証するエージェントは、自身がエージェントであることを宣言する必要がある。
- 公開クォータ付きの無料枠があり、有料枠の課金は2027年4月開始と報じられている。
- Gmail サーバーは、少なくとも一部の分析では、送信・返信・転送が一般には使えないとされています。これは単一ソースの情報なので、クォータと機能のページで自分で確認するまでは未確認として扱ってください。

## 連携開発にとって何が変わるのか

これまで「エージェントから Gmail API を呼ぶ」ことは、単なる API 連携でした。Google は呼び出し元を2種類に分け始めています。

1. **決定論的なソフトウェア**(同期ジョブ、Webhook ハンドラ)。引き続き REST API を使う。
2. **エージェント**(LLM が呼び出しを決める)。MCP か CLI を使う必要がある。

曖昧なのは2番目です。夜間バッチが Drive API を呼ぶだけならソフトウェアですが、同じスクリプトがモデルに「どのファイルを読むか」を選ばせているなら、おそらくエージェントです。社内ツールにはこの中間が多くあります。共有 Doc を要約する Slack Bot や、メールボックスから返信を下書きするサポートツールなどです。

つまり「このコードの呼び出し先をモデルが決めているか」が、設計上の問いであると同時にコンプライアンス上の問いにもなります。まず棚卸しが必要です。

## 今週できる棚卸し

リポジトリ全体で Workspace API の利用箇所を検索し、分類します。

```bash
# 複数リポジトリで Google Workspace API の利用箇所を探す
rg -n "googleapis\.com/(gmail|drive|calendar|docs|sheets|slides)" --glob '!node_modules'
rg -n "from googleapiclient|google\.auth|@googleapis/" --glob '!node_modules'
```

見つかった連携ごとに、次を記録します。

| 確認項目 | 理由 |
| --- | --- |
| LLM が API 呼び出しやパラメータを決めているか | エージェント扱いになるかの判断材料 |
| どの OAuth スコープを持っているか | MCP/CLI はスコープ付きサインイン。広いスコープは説明が難しくなる |
| ユーザー委任の OAuth クライアントか、サービスアカウントか | エージェントの自己申告は OAuth クライアントが対象 |
| レート制限されたらどうなるか | MCP のクォータは REST と異なる |

表計算シート1枚で十分です。期限が来る前に、どの連携が影響範囲にあるかを把握することが目的です。

## Hosted MCP サーバーへの接続

MCP 対応クライアントの多くは、リモートサーバーの URL を指定すれば OAuth も処理してくれます。プロジェクト単位の設定は次のような形になります(URL はプレースホルダーです。実際は Google の設定ガイドのエンドポイントを使ってください)。

```json
{
  "mcpServers": {
    "workspace-drive": {
      "type": "http",
      "url": "https://example.invalid/workspace/drive/mcp"
    }
  }
}
```

早めに身につけたい習慣が2つあります。

- **最小のサーバーから始める。** 文書要約エージェントには Drive と Docs の読み取りだけを渡し、Gmail や Calendar は付けません。Hosted MCP は機能を足すのが簡単なので、足さない規律が重要です。
- **ツールの出力は信頼できない入力として扱う。** Doc やメール本文は攻撃者が操作できるテキストで、それがそのままモデルのコンテキストに入ります。読み取りツールと書き込み/送信ツールを同じエージェントに持たせる構成は、プロンプトインジェクションの典型的な標的です。エージェントを分けるか、書き込み経路に承認を挟んでください。

## webhani の推奨

**動いている連携を今すぐ書き換えない。** 処理が決定論的なら REST API が引き続き適切で、報じられているルールの対象はエージェントです。まず分類に時間を使います。

**エージェント型のワークロードから先に移行する。** モデルが Workspace のデータに対してツールを選ぶ処理は、期限があるため最初に MCP へ移します。無料枠のうちにプロトタイプを作り、レイテンシと失敗パターンを測っておきましょう。

**機能ギャップを把握する。** 依存している操作(たとえばメール送信)が Hosted サーバーにない場合、後日対応されるのか、パートナー限定なのかを確認します。1月になってから気付くのは避けたいところです。

**従量課金を見込む。** 有料枠が始まると、エージェントの通信量がコスト項目になります。ポーリングやループがあるなら、今のうちにキャッシュとリクエスト上限を入れてください。ターンごとに同じフォルダを読み直すエージェントは、従量課金下では高くつきます。

## より大きな流れ

エージェントのトラフィックを、専用の ID・クォータ・監査ログを持つ窓口に寄せる動きは Google だけではありません。SaaS ベンダーにとっては合理的です。エージェントはスクリプトとは挙動が違い、ベンダーはそれを見たいからです。開発側の教訓は、「API を呼ぶソフトウェア」と「ツールを呼ぶモデル」の境界を、コードにもドキュメントにも明確に残しておくことです。この境界は、設計だけでなくコンプライアンスの観点でも重要になっていきます。
