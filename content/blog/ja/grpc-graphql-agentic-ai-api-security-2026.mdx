これまでAPIの設計は「人間がブラウザやモバイルアプリから叩く」ことを前提に考えられてきました。しかし、AIエージェントが自律的にツールを呼び出し、複数のAPIを組み合わせてタスクを完遂する構成が一般化するにつれて、API設計の前提そのものを見直す必要が出てきています。Apolloが2026年8月に開催したセキュリティ関連のウェビナーでも「Agentic AI時代のGraphQL API Security」というテーマが取り上げられており、この論点は業界全体で意識され始めています。

本記事では、gRPCとGraphQLという2つの技術をAIエージェント時代の文脈で比較しつつ、認可設計で見落としがちなポイントを整理します。

## エージェントはAPIを「人間と違う叩き方」をする

人間のクライアントは、UIの制約の中でリクエストを発行します。一方でAIエージェントは、LLMが生成したツール呼び出しに基づいてAPIを叩くため、以下のような特徴があります。

- 短時間に大量の呼び出しが発生しやすい(タスク分解の結果として)
- 呼び出しパラメータが人間の入力より予測しにくい(プロンプトインジェクションの影響を受け得る)
- APIのスキーマそのものがツール定義としてLLMに渡されるため、型の明確さが実行の正確性に直結する

この特性を踏まえると、API層での設計判断は単なるパフォーマンスの話にとどまらず、セキュリティの話でもあります。

## gRPCが向いているケース

サービス間通信、特にAIエージェントが内部的に呼び出すツール群には、gRPCの厳密なスキーマ定義が向いています。

```protobuf
// tool.proto
syntax = "proto3";

service InventoryTool {
  rpc CheckStock (StockRequest) returns (StockResponse);
}

message StockRequest {
  string sku = 1;
  int32 warehouse_id = 2;
}

message StockResponse {
  int32 available_units = 1;
  bool backorder_allowed = 2;
}
```

Protocol Buffersで定義された型はLLMが誤った形式の引数を生成するリスクを構造的に減らします。また、gRPCはリクエスト/レスポンスの形が固定されているため、エージェントが想定外のフィールドを要求してデータを過剰に取得する余地が少ないという利点もあります。gRPC-jsの週間ダウンロード数は2026年初頭時点で410万件に達しており、マイクロサービス間通信での採用が着実に進んでいることがうかがえます。

## GraphQLが向いているケースと注意点

一方、人間とエージェントの両方が使うエッジ側のAPI、特に柔軟なクエリが必要な場面ではGraphQLの利点が引き続き有効です。ただし、エージェントが呼び出し元になる場合、フィールドレベルの認可を今まで以上に厳密に設計する必要があります。

```typescript
// フィールドレベルで認可を強制するリゾルバの例
const resolvers = {
  Customer: {
    ssn: (parent, _args, context) => {
      if (!context.caller.hasScope("pii:read")) {
        throw new Error("insufficient scope for field: ssn");
      }
      return parent.ssn;
    },
  },
};
```

エージェントが「タスク達成のために有用そうなフィールド」を広く要求してくる可能性がある以上、スキーマ全体を信頼する設計ではなく、フィールド単位でスコープを検証する設計が前提になります。GraphQLの柔軟性は人間のクライアントにとっては利点ですが、エージェントにとっては攻撃対象領域が広がることと表裏一体である点は意識しておくべきです。

## 使い分けの指針

- **内部のサービス間・エージェント間通信**: gRPC。型の厳密さと呼び出しの予測可能性を優先
- **人間とエージェントの両方が触れるエッジAPI**: GraphQL。ただしフィールドレベルの認可を必須とする
- **単純なCRUD中心で、エージェントの呼び出しパターンが限定的**: 従来通りRESTでも問題ないケースが多い

「新しい技術だから採用する」のではなく、呼び出し元がエージェントかどうかで要求されるセキュリティ設計が変わる、という観点から技術選定をすることをおすすめします。

## まとめ

- AIエージェントはAPIの呼び出しパターンが人間と異なり、設計上の前提を見直す必要がある
- gRPCは型の厳密さゆえに、エージェント向けの内部ツール呼び出しに適している
- GraphQLをエージェント向けエッジAPIに使う場合、フィールドレベルの認可設計が必須になる
- 技術選定はパフォーマンスだけでなく、エージェント特有のセキュリティ特性を踏まえて行う

AIエージェントをプロダクトに組み込む案件が増える中、API設計とセキュリティ設計を切り離さずに検討することが、これからのアーキテクチャレビューでは標準になっていくと考えています。
