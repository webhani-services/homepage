タイポスクワッティングは、人間の打ち間違いを狙う攻撃です。新しい変種は、モデルが「存在しない名前をそれらしく作ってしまう」ことを狙います。2026年7月、Tel Aviv University、Technion、Intuitの研究者が「HalluSquatting」を論文（arXiv、7月8日）として公開しました。LLMが繰り返し幻覚するリポジトリ名やスキル名を事前に調べ、その名前を攻撃者が先に登録しておき、エージェントが取得するのを待つ、という攻撃です。

エージェントに `git clone` や `npm install`、スキルのインストールを任せているチームには直接関係する話です。以下は論文を取り上げた二次情報にもとづく整理なので、数値を引用する際は原典を確認してください。

## 攻撃の流れ

1. ユーザーがエージェントに「ツールXの公式リポジトリをcloneしてプロジェクトに組み込んで」と依頼する。
2. モデルがそれらしいが誤った識別子を出力する。正しくは `acme/tool-x` なのに `acme-labs/tool-x` を出すようなケースです。
3. 攻撃者がその名前を先に登録していれば、エージェントは攻撃者管理のコンテンツを取得します。READMEのセットアップ手順やスキルファイルは、エージェントが信用して実行しやすいテキストです。

報告されている数値は、リポジトリのclone場面で最大85%、スキルのインストール場面で100%の確率で存在しない名前が生成され、clone場面でのエンドツーエンドの成功率はアプリケーション・モデル・ペイロードにより約20〜65%、というものです。複数の主要なエージェントで検証され、ペイロードは無害なプレースホルダーのみ、公開前にベンダーへ開示されたと伝えられています。

関連する事例もあります。Aikido Securityは、幻覚で生まれたnpmパッケージ名 `react-codeshift` が、AIが書いた手順書経由で数百規模のプロジェクトに広がっていたと報告しました。Palo Alto NetworksのUnit 42は、幻覚されたドメインに関する「phantom squatting」を取り上げています。共通点は、モデルが作った名前が、無人のエージェントにとっては本物の名前と区別がつかないという点です。

報道によれば、ベンダー側の見解の一つは「未使用の名前でリポジトリを作れるのはコードホスティングの通常動作で、問題はエージェントが取得内容を信用することにある」というものでした。つまり、対策の責任はエージェントを設定する側にあります。

## モデルの改善だけでは防げない理由

幻覚は減らせても、なくなりません。攻撃側のコストは低く、モデルを何度もサンプリングして繰り返し出る偽の名前を集め、登録するだけです。繰り返し出る名前こそ狙う価値があります。

したがって防御は、識別子がネットワークアクセスに変わる境界に置くべきです。そこはモデルの判断ではなく、決定的なコードで守る場所です。

## ガードレール1：取得の前に名前解決する

エージェントがcloneしようとするリポジトリは、必ず事前確認を通すようにします。存在するか、作成日はいつか、承認済みのオーナーかを確認する小さなスクリプトで足ります。

```bash
#!/usr/bin/env bash
# check-repo.sh owner/name  -> 問題なければ exit 0
set -euo pipefail

REPO="$1"
OWNER="${REPO%%/*}"
ALLOWED_OWNERS=("vercel" "facebook" "anthropics" "our-org")

if [[ ! " ${ALLOWED_OWNERS[*]} " =~ " ${OWNER} " ]]; then
  echo "blocked: owner '$OWNER' is not on the allowlist" >&2
  exit 1
fi

# GitHub REST API: GET /repos/{owner}/{repo}
created=$(gh api "repos/$REPO" --jq '.created_at' 2>/dev/null) || {
  echo "blocked: $REPO does not resolve" >&2
  exit 1
}
echo "ok: $REPO (created $created)"
```

オーナーのallowlistは粗い仕組みですが、「未知のアカウント配下のもっともらしい名前」という攻撃クラスをまとめて除外できます。未知のオーナーの場合は、作成日、スター数、プロジェクトの公式ドキュメントに載っている組織かどうか、といった確認結果を添えて人間の判断に回します。

## ガードレール2：install/cloneは手動承認のままにする

多くのエージェントツールでは、コマンドを事前承認できます。ここは選別が必要です。ファイル読み取りやテスト実行は許可して構いませんが、`git clone`、`npm install <新規パッケージ>`、`pip install`、スキルの追加は、未レビューのコードを取り込むので確認を挟みます。共有設定を管理している場合は、これらを既定で拒否し、信頼するレジストリだけを明示的に許可してください。

## ガードレール3：取得したリポジトリは信頼しない入力として扱う

cloneしたリポジトリには、エージェント向けの指示が含まれていることがあります。セットアップスクリプトの実行を促すREADMEや、コマンドが埋め込まれたスキルファイルなどです。見知らぬ人からのプルリクエストと同じ扱いにします。

- 初回の評価は、認証情報を渡さないサンドボックスや使い捨てコンテナで行う。
- クラウドキー、SSHエージェント、`.env` を、見慣れないコードを扱う環境に置かない。
- 信頼できないリポジトリを読んだセッションに、本番のシークレットを持たせない。

## ガードレール4：依存関係はpinし、ミラーを通す

エージェントが追加する依存関係には、レビューでのlockfile差分確認を必須にし、レジストリには社内ミラーやパッケージファイアウォールを使うのが望ましいです。コミットメッセージが「add helper」だけで、社内に実績のない依存関係が入ったプルリクエストは、特に注意して見てください。

## 今週やっておくこと

- エージェント設定を見直し、`clone`、`install`、スキル追加の事前承認を外す。
- 上のスクリプト（または同等のhook）を入れ、取得前に識別子を検証する。
- サードパーティのリポジトリの初回評価を、シークレットのないサンドボックスに移す。
- レビュールールとして、エージェントが追加した依存関係やスキルは、公式ドキュメントと照合して人間が出典を確認する。

ツールを疑えという話ではありません。モデルの自信ある出力は「名前についての提案」であり、名前は身元の証明ではない、と認めることが出発点です。その二つをつなぐ確認は、自分たちで管理するコードにしておくべきです。
