ハーバードの経済学者 Fiona Chen 氏と James Stratton 氏によるワーキングペーパー「Artificial Intelligence in the Firm: Bottlenecks in Software Production」が話題になっています。Jellyfish の開発活動データを使い、2021年1月から2026年3月までの718社・約72万6千人を分析したものです。ここでは InfoQ などの二次報道を通して読んでいるため、数値を引用する際は論文本体で手法を確認してください。

報じられている主な結果は次のとおりです。

- 企業がコーディング**エージェント**を導入した後、コード行数は約30%、コミット数は約20%、Pull Request 数は約23%増加しました。
- Issue の解決数は、コーディング**アシスタント**では増えず、エージェントでは約12%の増加と報告されています。別の要約では、完了した Jira の Issue や Epic に統計的に有意な変化はなかったとされています。
- PR の提出からマージまでの平均時間は約49%延び、変更要求が付く PR の割合はほぼ2倍になりました。
- 2026年3月時点で約80%の企業が AI コードレビューツールを使っていますが、レビューコメントのうち AI によるものは約23%にとどまります。

著者らの結論は、生成を増やすだけでなく、下流のレビュー能力への補完的な投資が成果の条件になる、というものです。

## 数字の読み方

二方向に注意が必要です。

一つ目に、Jira の Issue 数は出荷した価値の粗い代理指標です。Issue の大きさはまちまちで、エージェントによって小さなチケットが増えるなど構成が変わる可能性もあります。「完了 Issue が横ばい」は「価値がない」の証明ではありません。ただ、コードの出力量が成果の代わりにならないことは示しています。

二つ目に、これは母集団の平均です。レビューの習慣、テスト、PR を小さく保つ規約が整ったチームは、平均とは大きく異なるかもしれません。示されているのは典型的なパターンであって、避けられない結果ではありません。

データが裏付けているのは、パイプラインの一段を速くすると制約が次の段に移る、というよく知られた原則です。もともとコードを書く工程が最も遅くなかったのなら、そこを速くしても主にレビュー前の待ち行列が伸びるだけです。

## なぜレビューが制約になるのか

エージェントが作る変更には、行数以上にレビューを難しくする性質があります。

- **差分が大きく広い。** 1 ファイルで済む発想に対して、6 ファイルを平気で触ります。
- **もっともらしいが未検証。** コードが読みやすいため、粗い人間のコードよりミスを見落としやすくなります。
- **文脈を共有していない。** レビュアーは作者に理由を尋ねられず、PR 説明も思考ではなく生成物のことがあります。
- **量。** 1 人が複数のエージェントを監督すると、チームが読める量を超える PR が毎日出ます。

レビューは理解が形成される工程でもあります。省略してもコストは消えず、インシデント対応やオンボーディングに移るだけです。

## 具体的な対策

### 1. チューニングの前に計測する

エージェント導入の前後で、チームごとに次の数値を追います。

```bash
# 直近の PR について、作成からマージまでの中央値(時間)(GitHub CLI + jq)
gh pr list --state merged --limit 300 \
  --json createdAt,mergedAt \
  --jq '[.[] | ((.mergedAt | fromdateiso8601) - (.createdAt | fromdateiso8601)) / 3600]
        | sort | .[length/2 | floor]'
```

あわせて PR サイズ(変更行数)、PR あたりのレビュー往復回数、エージェントが作成・共同作成した PR の割合を記録します。完了した作業のスループットが横ばいのまま、PR のマージ時間とレビュー往復が増えているなら、研究と同じパターンです。

### 2. レビューへの入力を絞る

小さな PR を標準にし、チームの作法ではなくエージェントへの指示として強制します。

```markdown
## Pull Request ルール(CLAUDE.md / AGENTS.md)
- 1 PR 1 関心事。生成ファイルを除き変更は 300 行未満を目安にする。
- それ以上になる場合は分割し、依存順に PR を出す。
- PR 説明には、何を変えたか、なぜか、どう検証したか、何を変えていないかを書く。
- 無関係なリファクタリングを同じ PR に含めない。
```

### 3. 検証を機械側に寄せる

パイプラインで確認できることを、レビュアーが最初の防衛線として担うべきではありません。人に依頼する前に、型チェック、テスト、Linter、セキュリティスキャンの通過を必須にします。タスク定義の一部として、エージェントに変更に合わせたテストの追加・更新と実行を求めます。

### 4. AI レビューは承認ではなくトリアージに使う

AI レビューは機械的な問題の検出や差分の要約に向いています。23%という数字は、多くのチームで依然として人間がコメントの大半を担っていることを示唆します。現実的な分担は、AI が事前にスタイル、明らかなバグ、テスト不足を拾い、人間は設計、ドメインの正しさ、リスクに時間を使うというものです。

### 5. レビュー能力を意図的に増やす

エージェントで PR が倍増するなら、レビューの予算を増やすか、同時に流れるエージェント PR の数に上限を設ける必要があります。レビュアーあたりの未処理エージェント PR に WIP 制限をかけるのは、単純で効果的な方法です。

## webhani の見解

私たちは日常的にコーディングエージェントを使い、導入を勧めています。この論文から読み取るべきは「効かない」ではなく、導入計画がライセンスとオンボーディングは見積もってもレビュー工程を忘れがちで、実際にスループットを決めるのはそこだ、という点です。

チームへの導入を支援するときは、まず配信指標(PR のサイクルタイム、レビュー往復、流出した不具合)を計測し、リポジトリのエージェント指示に PR サイズと検証のルールを置き、そのあとでエージェントの利用を増やします。順序が重要です。生成を先に増やすと、レビューの滞留とツールへの悪い印象だけが残ります。

## まとめ

- 718社の報告データでは、エージェントでコード量は約20〜30%増えましたが、完了 Issue は大きく増えず、PR のマージ時間は延びました。
- レビュー能力を制約と捉え、導入前後で PR のサイクルタイムとレビュー往復を計測します。
- エージェント指示で PR サイズを制限し、チェックを CI に寄せ、AI レビューはトリアージに使い、同時進行のエージェント PR に上限を設けます。
