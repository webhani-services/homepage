HonoのJSXサーバーサイドレンダリングに、CVE-2026-56761(GitHubアドバイザリ GHSA-458j-xx4x-4375)として追跡されるHTMLインジェクションの問題がありました。NVDによれば、4.12.14より前のバージョンでは、不正な属性名を与えることで意図しないHTMLを挿入できます。アドバイザリの初公開は2026年4月、CVEの登録は6月なので、新しいニュースではありません。それでも今月のベンダーのセキュリティ情報に繰り返し登場しており、脆弱なバージョンのまま動いている環境が多いと考えて取り上げます。

情報源について補足します。アドバイザリ本文のページは開けず、検索結果の要約までしか確認できていません。以下の仕組みは、その要約で裏づけられる範囲で書いています。影響の有無を判断する前に、GitHubのアドバイザリ本文をご確認ください。

## 問題の内容

HonoはサーバーでJSXをレンダリングするとき、propsをHTMLの属性文字列に変換します。値はエスケープされます。アドバイザリが扱うのは属性の*名前*です。引用符や山括弧を含むキーが現在のタグを閉じ、新しいマークアップを始められます。深刻度の評価は情報源によって異なり、4.3〜5.3(Medium)で、挿入されたスクリプトの実行にはユーザー操作が必要とされています。

Snykは4.12.16未満を対象とする別のアドバイザリも掲載しており、JSX要素タグ経由のHTMLインジェクションと説明されています。詳細は確認できていませんが、実務上の結論は明確です。4.12.14だけでは不十分な可能性があるので、最低限の修正版ではなく最新のパッチリリースへ上げてください。

## 探すべきコードパターン

属性の*名前*は通常、ユーザーではなく開発者が書くため、この種の問題は見つけにくくなります。キーを制御できないオブジェクトをpropsにスプレッドすると到達可能になります。

```tsx
// 危険: extra のキーがリクエスト由来
app.get('/profile', (c) => {
  const extra = JSON.parse(c.req.query('attrs') ?? '{}')
  return c.html(<div class="card" {...extra}>Hello</div>)
})
```

この例では攻撃者が名前と値の両方を制御できます。データベースやユーザーが編集できる設定から読み込んだ任意の`attributes`オブジェクトを受け取る、ウィジェットやCMS風のコンポーネントも同様に危険です。

安全な形は、スプレッドの前に属性名を許可リストで絞ることです。

```tsx
const ALLOWED = new Set(['title', 'aria-label', 'data-id'])

function pick(input: Record<string, unknown>) {
  const out: Record<string, string> = {}
  for (const [key, value] of Object.entries(input)) {
    if (ALLOWED.has(key) && typeof value === 'string') out[key] = value
  }
  return out
}

app.get('/profile', (c) => {
  const extra = pick(JSON.parse(c.req.query('attrs') ?? '{}'))
  return c.html(<div class="card" {...extra}>Hello</div>)
})
```

許可リストはパッチ適用済みのバージョンでも有効で、設計としても優れています。ユーザー入力にマークアップの属性を決めさせるべきではありません。

## 影響範囲の確認

1. **インストール済みバージョンを、間接依存も含めて調べる。** フレームワークやテンプレートが内部でHonoを固定していることがあります。

   ```bash
   npm ls hono
   ```

   デプロイ対象すべてのlockfileと、過去にビルドしたコンテナイメージも確認します。

2. **JSXレンダリングを使っているか確認する。** HonoをJSON APIのルーターとしてのみ使っているなら、JSXをレンダリングしないため到達できません。`hono/jsx`のimportと`c.html(`の呼び出しを検索します。

3. **propsのスプレッドを検索する。** サーバーレンダリングされるコンポーネントで`{...`の後に変数が続く箇所を探し、リクエスト由来のキーが入り得るかをたどります。

4. **修正が反映される場所を確認する。** エッジやサーバーレスのバンドルはビルド成果物です。`package.json`を更新しても、再ビルドと再デプロイをするまで何も変わりません。

## アップグレードと検証

```bash
npm install hono@latest
npm ls hono
```

その後、悪意あるキーを使った回帰テストを追加します。将来のリファクタリングや依存の固定で問題が再発するのを防げます。

```tsx
import { test, expect } from 'vitest'
import { Hono } from 'hono'

test('入力由来の属性名がタグを抜け出せない', async () => {
  const app = new Hono()
  app.get('/', (c) => {
    const hostile = { 'x"><script>alert(1)</script>': '1' }
    return c.html(<div {...hostile}>ok</div>)
  })
  const body = await (await app.request('/')).text()
  expect(body).not.toContain('<script>')
})
```

脆弱なバージョンでは影響の確認に、修正版ではビルドに修正が効いていることの確認に使えます。

## 多層防御

インラインスクリプトを禁止するContent-Security-Policyは、挿入されたタグができることを制限します。サーバーレンダリングするアプリなら導入する価値があります。ただし、挿入されたマークアップによる改ざんやフィッシングは防げないため、アップグレードの代わりにはなりません。

## まとめ

Honoは4.12.14だけでなく現在のパッチリリースへ更新し、バンドルしているデプロイ対象をすべて再ビルドしてください。そのうえで、リクエスト由来のキーを含み得るpropsスプレッドを洗い出し、許可リストに置き換えます。アップグレードはこのCVEを直し、許可リストはこの種のミスそのものをなくします。
