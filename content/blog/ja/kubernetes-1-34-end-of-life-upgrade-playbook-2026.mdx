アップストリームのKubernetes 1.34は2026年10月27日にEOLを迎えます。ただし、マネージドサービスを使っている場合、この日付がそのまま期限になるわけではありません。Amazon EKSでは1.34の標準サポートの終了が12月2日とされ、その後は有料の延長サポートになります。GKEとAKSもそれぞれ独自の日付を公開しており、アップストリームとも、互いにも一致しません。各プロバイダーの公式ライフサイクルページで確認してください。二次情報のトラッカー同士でも一部の日付が食い違っています。

本当のリスクは日付そのものではなく、気づかないうちに起きる移行です。アップグレードしていないEKSクラスターは自動的に延長サポートに移り、延長サポートは標準サポートよりクラスターあたりの単価がかなり高く課金されます。1年放置したクラスターは、誰も選んでいない費用項目になります。

現在のアップグレード先は1.35と1.36です。コントロールプレーンは1マイナーずつしか上げられないため、1.34から1.36へは2回のアップグレードが必要です。最初から2回分を計画してください。

## Step 1: 忘れられたクラスターも含めてバージョンを棚卸しする

まず実際に何があるのかを確認します。AWSの場合です。

```bash
for region in ap-northeast-1 us-east-1; do
  for c in $(aws eks list-clusters --region "$region" --query 'clusters[]' --output text); do
    aws eks describe-cluster --region "$region" --name "$c" \
      --query '{name:cluster.name,version:cluster.version,policy:cluster.upgradePolicy.supportType}' \
      --output json
  done
done
```

`supportType` で標準サポートか延長サポートかが分かります。意外なものが見つかるのは、たいていステージングや「一時的な」クラスターです。

## Step 2: 壊れるAPI利用を見つける

マイナーリリースごとに、非推奨のAPIがいくつか削除されます。アップグレード前に、クラスターが実際に何を要求されているかを確認します。

```bash
# 稼働中のAPIサーバーに対して要求された非推奨API
kubectl get --raw /metrics | grep apiserver_requested_deprecated_apis

# リポジトリ/クラスター内のManifestとHelm releaseをスキャン
pluto detect-files -d ./k8s
pluto detect-helm -o wide
```

metricsからは実行時のクライアント(忘れていたコントローラーやCIジョブを含む)が分かり、`pluto` からはManifestの問題が分かります。両方実行してください。Manifestに問題がなくても、古いオペレーターが削除済みのエンドポイントを呼び続けていることがあります。

## Step 3: アドオンとバージョンスキューを確認する

アップグレードの失敗は、Kubernetes本体より周辺コンポーネントが原因であることが大半です。

- **Ingress/Gatewayコントローラー、CNI、CSIドライバー、Cluster AutoscalerやKarpenter**: 移行先のKubernetesバージョンに対応するバージョンがあるか確認します。各プロジェクトのドキュメントにある互換性表が正です。
- **Kubeletのスキュー**: kubeletはAPIサーバーより最大3マイナー古くても許容されますが、それを計画の前提にしないでください。ノードグループを早めに更新しておくと、次のアップグレードが簡単になります。
- **Admission webhook**: `failurePolicy: Fail` のwebhookがロールアウト中に使えなくなると、Pod作成がすべて止まることがあります。どれがあるかを把握しておきます。

## Step 4: アップグレードの順序

私たちが実際にうまくいった手順です。

1. 本番に近いワークロード構成の非本番クラスターを先に上げる。
2. コントロールプレーンをアップグレードする。EKSなら `aws eks update-cluster-version --name <cluster> --kubernetes-version 1.35`。完了を待つ。
3. マネージドアドオンを新しいコントロールプレーンに対応するバージョンへ上げる。
4. ノードグループをローリング更新する。重要なワークロードにPodDisruptionBudgetがあること、そしてdrainが固まるほど厳しくないことを確認する(レプリカ1つで `maxUnavailable: 0` は典型的な失敗例)。
5. スモークテストを実施し、1.36でも同じことを繰り返す。

1.35から1.36へは、続けて実施せず数日あけます。1回目のアップグレードが原因の問題と、2回目が原因の問題を切り分けるためです。

実際の障害はノードのdrainに潜んでいます。本番作業の前に次を確認してください。

```bash
kubectl get pdb -A
kubectl get deploy -A -o json | jq -r '.items[] | select(.spec.replicas==1) | "\(.metadata.namespace)/\(.metadata.name)"'
```

レプリカ1のDeploymentは、ノード更新中にダウンタイムが発生します。作業時間中だけ2に増やすか、停止を許容して周知するかを決めておきます。

## Step 5: 既定のまま延長サポートに入らない

標準サポートの期限までに間に合わないなら、それを自分で決めた判断にしてください。廃止予定のクラスターのつなぎとして延長サポートを使うのは妥当です。しかし、継続的に運用するクラスターの既定にするのは望ましくありません。各クラスターの標準サポート終了日をカレンダーやIaCのタグに記録し、60日前にアラートを設定します。

## webhaniの推奨

- Kubernetesのアップグレードは、EOL通知を受けて始めるプロジェクトではなく、四半期ごとの定常作業にする。
- クラスター定義をTerraformなどで管理し、バージョン更新をplan付きのレビュー対象の変更にする。
- 非推奨APIのスキャンをCIで自動化し、Manifestを書いた時点で削除済みAPIを検出する。
- コントロールプレーンとノードのバージョン差を小さく保つ。差が1マイナーなら簡単ですが、3マイナーになるとプロジェクトになります。

周期的に上げているチームは、1リリースあたり数時間で済みます。期限を待つチームは数週間かけ、それでもしばらく延長サポートに入るのが通例です。コスト差の大半は、技術ではなくプロセスから生まれます。
