分散学習ジョブや密結合なバッチワークロードには、Kubernetes のデフォルトスケジューラが長年うまく扱えなかった共通の失敗パターンがあります。「部分的なスケジューリング」です。あるジョブが8個の Pod を必要としているのに、クラスタが今すぐ配置できるのが5個だけだった場合、デフォルトのスケジューラはその5個をあっさり配置し、残りを Pending のまま放置します。単独では役に立たない Pod のために GPU の予約枠だけが消費されてしまうのです。Kubernetes 1.36 では、新しい PodGroup API を基盤とした Gang Scheduling によってこの問題に正面から取り組んでいます。

## 問題：オールオアナッシングなワークロード

分散 AI 学習が最も分かりやすい例です。8つの GPU ノードに分割された学習ジョブは、5ノードしか稼働していなければ実質的に何の役にも立ちません。ジョブは進行できないにもかかわらず、割り当て済みの5つの GPU は予約されたまま遊休状態になり、本来それらを使えたはずの他のワークロードからは利用できません。複数の学習ジョブが同居する共有クラスタでは、この無駄が急速に積み上がります。

Gang Scheduling の考え方はシンプルです。グループ単位でスケジューリングするか、まったくしないか。クラスタがグループ全体（または定められた最小数）を収容できる場合のみ Pod が配置され、そうでなければ一つも配置されません。

## 1つではなく2つの API

Kubernetes 1.36 では、これをライフサイクルの異なる2つのオブジェクトに分割しています。**Workload** は静的なスケジューリングポリシーのテンプレートであり、**PodGroup** は実際にスケジューリング時に Pod が参照するランタイムオブジェクトです。「ポリシー」と「ランタイムインスタンス」を分離するこの設計は、Deployment と ReplicaSet の関係にも見られる馴染みのあるパターンです。テンプレートが意図を記述し、ランタイムオブジェクトが実際の状態を追跡します。

## Job Controller との統合

多くのチームが実際に触れることになるのが、この Job Controller との統合部分です。`WorkloadWithJob` フィーチャーゲートを有効にすると、Job Controller は対象となる Job に対して Workload と対応する PodGroup を自動的に作成し、その Job が生成するすべての Pod に `.spec.schedulingGroup` を設定し、生成したオブジェクトの所有者となります。つまり、分散学習を典型例とする密結合な並列アプリケーションを表す Job は、追加のツールやサードパーティのスケジューラプラグインなしに Gang Scheduling されるようになります。

概念的には、学習用 Job はスケジューリンググループを参照する形で opt-in します。

```yaml
# 概念的なイメージです。正確なフィールド名は最新の Kubernetes ドキュメントで確認してください。
# このAPIは 1.36 / 1.37 にかけてまだ変化しています。
apiVersion: batch/v1
kind: Job
metadata:
  name: distributed-training
spec:
  parallelism: 8
  completions: 8
  template:
    spec:
      schedulingGroup:
        minCount: 8
      containers:
        - name: trainer
          image: your-training-image:latest
```

上記の YAML はコピー&ペーストできるマニフェストではなく、あくまで概念を示すスケッチとして扱ってください。これは現在も活発に進化しているアルファ/ベータ相当の API であり、KEP のリビジョン間でフィールド名がすでに変わっています。

## Preemption もグループ単位に

これまでの Preemption（強制退去）は、分散ワークロードの一部の Pod だけを退去させ、残りを稼働させたままにしてしまうことがありました。残った Pod は処理を進められないのにリソースだけは占有し続けるため、グループ全体を退去させるよりも状況が悪化するケースすらありました。Kubernetes 1.36 では、PodGroup を Preemption の判断単位としても扱うため、スケジューラはグループ全体を退去させるか、まったく退去させないかのどちらかになります。

## 実務への影響

マネージド Kubernetes（EKS、GKE、AKS など）上で AI/ML 学習や密結合なバッチパイプラインを運用しているチームにとって、これまでは正しい Gang Scheduling 挙動を得るためだけに Volcano や Kueue のようなサードパーティスケジューラが必要だった隙間が埋まることになります。これらのツールが不要になるわけではなく、より高度なキューイングやフェアシェアポリシーは依然としてそちらの強みですが、必要なのが正しいオールオアナッシングのスケジューリングだけだったチームにとっては、依存関係を一つ減らせることになります。

## webhani からの推奨

この機能領域はまだ変化が速い段階です。本番の AI ワークロードに導入する前に、次を確認することをお勧めします。

- 利用しているマネージド Kubernetes 提供元が、実際にどのフィーチャーゲートを有効化しているかを確認する。提供元によって upstream リリースへの追従に遅れがあります。
- まずは重要度の低いバッチジョブでパイロット導入し、ハッピーパスだけでなく実際のリソース競合状況下での Preemption 挙動を検証する。
- すでに Volcano や Kueue などのスケジューラを運用している場合は、ネイティブの PodGroup サポートが本当にスタックを簡素化するのか、それとも既存ツールのキューイング機能がまだネイティブ API ではカバーされない部分を担っているのかを見極める。

## まとめ

Kubernetes 1.36 のネイティブ Gang Scheduling は、AI/バッチワークロードにとって実際にコストのかかる問題 — 部分的なスケジューリングによる GPU 予約の無駄 — を解決します。既存のサードパーティスケジューラを初日から撤去する理由にはなりませんが、今まさに AI インフラのスタックを見直しているチームにとっては、正しい挙動を得るために追加で積み上げる必要のあるものを着実に減らしてくれる変化です。
