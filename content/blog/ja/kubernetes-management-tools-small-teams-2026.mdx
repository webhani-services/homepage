## Kubernetes が主流になったことと、あなたのチームに必要かは別問題

2026年時点で、Kubernetes は標準的な Engineering Toolkit の一部として定着しました。かつては大企業の Platform Team だけが扱う専門技術でしたが、今では Data Engineering Team が Batch Job の再現性のために Container 化し、ML Team も Training Pipeline を同じ流儀でパッケージングします。AWS EKS、Azure AKS、Google GKE といった Managed Kubernetes が主要な Cloud すべてで提供されているため、`etcd` や API Server の Upgrade を自前で手がけるチームはほとんど残っていません。

しかし、この事実は 15人規模で 2〜3個の Service を運用しているチームの計算式を変えません。Managed Kubernetes は Control Plane の運用負荷を取り除いてくれますが、RBAC 設計、Network Policy、Node Group のライフサイクル管理、Admission Controller の設定、そして Cluster Version をサポート期間内に保ち続ける規律までは肩代わりしてくれません。これらは一度きりの作業ではなく、継続的にコミットし続けなければならない実務です。

だからこそ、私たちがインフラの相談を受けるほぼすべての場面で最初に投げかける質問はこれです。「このチームは本当に Kubernetes を必要としているのか、それとも単一の Cloud Run Service や ECS Fargate Service、App Service Plan で、今後1〜2年の Scale と可用性要件を満たせるのか」。もし正直な答えが「Deployable な単位は1つで、Traffic は予測可能で、数十の Service を横断した Pod 単位のビンパッキングは必要ない」であれば、Managed Container Platform が運用上のメリットの9割を、はるかに小さい運用面積で提供してくれます。

## Kubernetes を選ぶべき局面

Kubernetes が本当に価値を発揮するのは、独立してデプロイされる Service が十分に多く、それら全体で一貫した Scheduling・Scaling・Networking の仕組みが必要になったときです。目安としては、Scaling Profile が異なる Service を6個以上運用しているか、あるいは Cloud 間の Workload Portability が仮説ではなく実際のビジネス要件になっている場合です。この条件に当てはまるなら、次に来る問いは「どのツールを使うか」であり、ここでチームは往々にして過剰投資しがちです。

## まず kubectl と K9s から始める。Dashboard からではない

Kubernetes に不慣れなチームがまずやりがちなのは、初日から Cluster の状態・Deployment・Log を一画面で見られる本格的な GUI を導入することです。この直感は多くの場合、時期尚早です。Cluster が1〜2個の小規模チームであれば、`kubectl` と `k9s` の組み合わせで日常の運用はほぼカバーできますし、どちらも Scriptable で軽量、導入コストも低く済みます。

具体例を見てみましょう。Pod が `CrashLoopBackOff` に陥っていて、原因を素早く特定したい場面です。

```bash
# Namespace 内の Pod を一覧し、問題の Pod を特定する
kubectl get pods -n checkout-service

# NAME                          READY   STATUS             RESTARTS   AGE
# checkout-api-7d8f9c6b4-x2k9p  0/1     CrashLoopBackOff   6          14m

# 直近の Exit 理由と OOM のシグナルを確認する
kubectl describe pod checkout-api-7d8f9c6b4-x2k9p -n checkout-service | grep -A5 "Last State"

# 現在の再起動ループではなく、直前にクラッシュした Container Instance の Log を読む
kubectl logs checkout-api-7d8f9c6b4-x2k9p -n checkout-service --previous --tail=100
```

K9s であれば同じ調査が数秒で終わります。`k9s` を起動し、`:pods checkout-service` で Namespace を絞り込み、クラッシュしている Pod を選択して `l` キーで Log を表示（`p` で直前の Container Instance に切り替え）、`d` キーで describe を確認する。これらすべてを Terminal から離れず、Pod 名を暗記する必要もなく行えます。これが raw `kubectl` に対する K9s の実質的な価値です。日常的に行う20個の操作について、Pod 名や Namespace Flag のコピペ作業を消し去ってくれる一方で、Browser Tab や認証フロー、各 Engineer の PC に常にパッチを当て続けなければならない別 Binary を増やすこともありません。

Lens のような重量級 GUI Tool を導入すべきなのは、Terminal ベースの Workflow が実際に時間を食い始めたときだけです。目安としては、3個以上の Cluster を運用しているとき、あるいは Infra を主業務としない Engineer が Platform Team に都度問い合わせることなく、Resource Graph や複数 Cluster の切り替えといった視覚的なコンテキストを自分で得る必要が出てきたときです。それ以下の規模では、GUI Dashboard は Licensing・Update・Access 付与の手間が増えるだけで、`k9s` がすでに解決している問題に対する追加投資になってしまいます。

## 本当にコストに見合うツール投資：Observability と Cost 配賦

ここがチームが過小評価しがちな部分です。Cluster が動き始めれば、Orchestration そのものが痛点になることはほとんどありません。痛点になるのは Autoscaling が予測不能な挙動をすること、そして「今月なぜ Cloud の請求額が3倍になったのか」を数時間の調査なしには誰も答えられないことです。専用の FinOps Tool が必要になる前に、ここへの手当てを済ませておくべきです。

Cluster が数個の Service を超えて成長する前に、初日から Instrument しておくべきことは2つあります。

**Resource Request/Limit の衛生管理。** すべての Container は、Tutorial からコピーした推測値ではなく、実測した使用量に基づいて Request と Limit を設定した状態で Deploy されるべきです。Request が未設定の Deployment では、Scheduler が合理的なビンパッキングを行えず、Horizontal Pod Autoscaler も何を基準に Scale すればよいか判断できません。

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: checkout-api
  namespace: checkout-service
spec:
  replicas: 3
  selector:
    matchLabels:
      app: checkout-api
  template:
    metadata:
      labels:
        app: checkout-api
        cost-center: payments
    spec:
      containers:
        - name: checkout-api
          image: registry.example.com/checkout-api:1.4.2
          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              cpu: "750m"
              memory: "512Mi"
          readinessProbe:
            httpGet:
              path: /healthz
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 10
```

`cost-center: payments` という Label に注目してください。これが早めに整えておくべき2つ目の要点です。Namespace と Team/Cost-Center による一貫した Labeling を統一的に適用しておけば、`kubectl top pods --all-namespaces` と Cloud の請求 Export を意味のある形で突き合わせられるようになります。私たちが顧客の Cluster で目にする Cost の予期しない増加の多くは、Label が付いていない、あるいは付け方が一貫していない Workload に起因しており、「どの Team の Service がこの支出を生んでいるか」を手作業の掘り起こしなしには答えられない状態になっています。

複数の Cluster を運用し、Namespace 単位の Cost に関する疑問が週次で発生するようになって初めて、専用 Tool（Kubecost、OpenCost、あるいは各 Cloud Native の Cost 配賦機能）を導入する意味が出てきます。それ以前は `kubectl top`、一貫した Label、そして Cloud の請求 Console の Tag ベース表示で十分です。

## まとめ

**今 Kubernetes を導入すべきかの簡易チェックリスト:**

- Scaling 特性が異なる、独立してデプロイ可能な Service を5〜6個以上持っているか。持っていなければ、単一の Managed Container Service で今後1年は十分にカバーできる可能性が高いです。
- Multi-Cloud の Portability は実際に近い将来必要なのか、それとも仮説にすぎないのか。仮説であれば、運用オーバーヘッドを正当化できません。
- RBAC・Network Policy・Cluster Upgrade のサイクルを責任持って担える人材がチームにいる、または採用予定があるか。誰も担わないなら、まだ導入すべきではありません。

**規模の成長に応じた推奨ツール進行:**

1. Cluster が1〜2個、小規模チーム: 日常運用は `kubectl` + `K9s` で十分。Dashboard は不要です。
2. Cluster が3個以上、または視覚的なコンテキストを必要とする非Infra Engineerがいる場合: CLI Workflow を置き換えるのではなく、その上に Lens などの GUI を重ねます。
3. Cluster数に関わらず初日から: すべての Deployment に Resource Request/Limit を設定し、Cost-Center・Team の Label を一貫させます。
4. 複数 Cluster を運用し、Cost 配賦に関する疑問が繰り返し発生する場合: Kubecost、OpenCost、あるいは Cloud Native の専用 Cost 可視化 Tool を導入します。

一貫しているのは、「複雑さを取り入れるのは、それが解決する問題がすでに実際の時間を食っているときだけ」という原則です。
