Kubernetes 1.36は2026年4月にリリースされました。そのリリースノートの中で、MLワークロードを運用するチームにもっと注目してほしい項目があります。OCI Image Volumeがstableになったことです。この機能を使うと、PodはOCIイメージ（またはアーティファクト）の中身を読み取り専用ボリュームとしてマウントできます。init containerも、コピー処理も、アプリケーションイメージへの同梱も要りません。

すべての人にとって新しい機能というわけではありません。alphaとbetaの期間が何リリースか続いていました。ただ、stableになると導入の判断材料が変わります。Feature Gateを気にする必要がなくなり、APIの形が互換性の約束になります。コンテナイメージに大きなペイロードを詰め込む回避策を取ってきたなら、検討する価値があります。

## 解決する問題

典型的な推論サービスには、ライフサイクルがまったく異なる2つの部分があります。

- **サーバー**：コードと依存関係。リリースのたびに変わります。
- **ペイロード**：モデルの重み、トークナイザ、埋め込み、地理データベース、静的アセットなど。独自のタイミングで変わり、サイズが大きい。

よくある回避策には、どれも難があります。

1. **ペイロードをアプリのイメージに同梱する**：コードを変えるたびに数GBのイメージを再ビルド・再pushすることになり、レジストリもノードも負担します。
2. **init containerでオブジェクトストレージからダウンロードする**：認証情報、リトライ処理、書き込み可能なボリュームが必要です。起動時間が毎回ネットワーク取得に左右されます。
3. **別経路で中身を入れたPersistentVolumeを使う**：動きますが、デプロイとは別のストレージライフサイクルを自分で抱えることになります。

Image Volumeは、ペイロードをバージョン管理されたレジストリ上の一級のアーティファクトとし、Pod specから参照できるようにします。

## 実際の書き方

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: classifier
spec:
  containers:
    - name: server
      image: registry.example.com/classifier-server:1.8.2
      volumeMounts:
        - name: model
          mountPath: /models
          readOnly: true
  volumes:
    - name: model
      image:
        reference: registry.example.com/models/classifier@sha256:4f1c...e9
        pullPolicy: IfNotPresent
```

kubeletはコンテナランタイム経由で参照先のアーティファクトをpullしてマウントします。サーバーからは`/models`が読み取り専用ディレクトリとして見えます。モデルの更新はPod specの変更になるため、通常のロールアウト、ロールバック、GitOpsのレビューにそのまま乗ります。

実務上の注意が2つあります。

- **本番ではダイジェストで固定する**：`:latest`はもちろん`:v3`のようなタグも動く可能性があります。稼働中のDeploymentの下でモデルが黙って入れ替わる事態は、後から再構築するのが困難なインシデントです。
- **マウントでは`subPath`が使える**：1つのアーティファクトに複数のファイルを入れ、コンテナが必要な1つだけをマウントできます。

## アーティファクトの作り方

OCI互換のレジストリならどれでも使えます。モデルのアーティファクトは、`FROM scratch`で作る最小のイメージで足ります。

```dockerfile
FROM scratch
COPY classifier-v3/ /
```

```bash
docker build -t registry.example.com/models/classifier:v3 .
docker push registry.example.com/models/classifier:v3
```

実行ファイルを含まないので、動かすものもベースイメージのCVEもありません。ただし、署名と、サプライチェーン上の通常のリスクに対するスキャンは必要です。アプリケーションイメージにすでにcosignやレジストリ側のポリシーを使っているなら、モデルのアーティファクトにも適用してください。イメージは厳重に固めているのに、モデルの重みは署名のないバケットから取得しているチームを見かけます。

## webhaniの案件に合う理由

Webアプリケーションに LLM コンポーネントを組み合わせるお客様案件では、この分離が責任の線引きをきれいにします。

- アプリチームは`server:1.8.2`を週に数回リリースする。
- データ・ML側は、新しい評価に合格したときに`classifier@sha256:...`を出す。
- 両者が出会う場所はPod specだけになる。「この問い合わせの時点でどのモデルが動いていたか」は、`git log`で答えられる質問になる。

ウォームなノードでのコールドスタートにも効きます。レイヤーはランタイムにキャッシュされるため、モデルのレイヤーを持つノードでは、Podの再作成や再起動でも再利用されます。init containerでのダウンロードは毎回やり直しです。

## 導入前に確認すべき制約

**ランタイムの対応**：kubeletはコンテナランタイムに処理を委ねるため、ランタイム側がImage Volumeを実装している必要があります。お使いのクラスタのリリースに対応するKubernetesドキュメントで、containerdまたはCRI-Oの最低バージョンを確認してください。マネージドKubernetesを使う場合は、ノードイメージが対応しているかも確認します。APIがstableでも、ノードが対応しているとは限りません。

**読み取り専用のみ**：ボリュームには書き込めません。モデルの隣に派生データをキャッシュするサービスは、そのために`emptyDir`をマウントしてください。フレームワークによっては、重みのそばにロックファイルやコンパイル済みキャッシュを書こうとして、思わぬ形で失敗します。早い段階で読み取り専用マウントで試してください。

**pullのコストは変わらない**：ノード上の最初のPodは、依然としてアーティファクト全体をダウンロードします。数十GBのモデルなら、DaemonSetでの事前pullや、ノードに近いレジストリミラーを検討してください。Image Volumeが減らすのは配管であって、帯域ではありません。

**共有の可変ストレージの代わりにはならない**：毎時更新されるベクトルインデックスのようにペイロードが絶えず変わるなら、PersistentVolumeや外部サービスのほうが適しています。

**メモリマップでの読み込み**：多くのフレームワークは重みをmmapします。ランタイムのsnapshotterや下位のファイルシステムによって、ローカルディスクと性能が異なる可能性があります。想定せず、自社のローダーで計測してください。

## 導入の進め方

1. ペイロードが500MBを超える、重要度の低いサービスを1つ選ぶ。
2. ペイロードを`FROM scratch`のアーティファクトにまとめ、ダイジェストつきでpushする。
3. ステージングのノードプールでランタイム対応を確認し、読み取り専用マウントでサーバーを動かす。
4. 導入前後でPodの起動時間とレジストリのegressを測る。
5. 本番に触れる前に、Admissionポリシーへ署名検証を追加する。
6. ダイジェストを更新する手順を文書化し、モデル更新をプルリクエスト経由にする。

Image Volumeは、モデルの学習や提供の方法を変えるものではありません。接着剤のようなコードを一種類減らし、モデルのバージョン管理をマニフェストの他の要素と同じレビュー経路に移します。すでにGitOpsでデプロイしているチームにとっては、小さな変更で効果が目に見えます。
