## YAMLは便利だが、事故が多い

Kubernetesマニフェストを書いたことがあるエンジニアなら、一度はYAML特有のトラブルに遭遇したことがあるはずです。インデントのずれでネスト構造が崩れる、`yes`や`no`が文字列ではなく真偽値として解釈される、バージョン番号の`1.20`が数値として解釈されて末尾のゼロが消える、といった問題です。

こうした「YAMLの気まぐれな型推論」は長年Kubernetesコミュニティの悩みの種でした。この状況を受けて登場したのが、より厳格な文法を持つYAML方言であるKYAMLです。この記事では、KYAMLが何を解決するのか、そして導入する際の実務的な考慮点を整理します。

## KYAMLが解決する具体的な問題

### 1. 曖昧な型変換の排除

標準的なYAMLパーサーは、クォートなしの値を文脈から型推論します。これが意図しない変換を引き起こすことがあります。

```yaml
# 標準YAMLでの事故例
metadata:
  labels:
    version: 1.20  # 数値として解釈され "1.2" になる可能性がある
    enabled: yes   # 真偽値trueとして解釈される
    country: NO    # ノルウェーの国コードのつもりが、falseと解釈される
```

KYAMLでは、こうした曖昧な変換を許容せず、文字列として扱ってほしい値には明示的なクォートを要求する方向に仕様が整理されています。

```yaml
# KYAMLでの記述例
metadata:
  labels:
    version: "1.20"
    enabled: "yes"
    country: "NO"
```

### 2. インデントの一貫性チェック

YAMLはインデントで構造を表現するため、タブとスペースの混在や、微妙なインデント幅の違いが構文エラーにならずに構造だけを壊してしまうことがあります。KYAMLでは、パース時により厳格なインデント検証を行い、曖昧な構造をエラーとして検出します。

### 3. 予測可能なマージ動作

複数のマニフェストやKustomizeのオーバーレイを重ね合わせる際、YAMLのマージ動作が直感と異なる結果を生むことがあります。KYAMLでは、マージ時の優先順位や配列の扱いをより明示的に定義することで、この種の予測不可能性を減らそうとしています。

## 実務での導入を検討する際の注意点

KYAMLは既存のYAMLと完全な互換性を持つわけではないため、導入にはいくつかの段階を踏む必要があります。

1. **既存マニフェストの検証**: 既存のYAMLファイルをKYAMLのバリデータに通し、暗黙の型変換に依存している箇所を洗い出します。多くの場合、`yes`/`no`のような真偽値のクォート漏れが最初に見つかります。

```bash
# 例: 既存マニフェストの互換性チェック(イメージ)
kyaml validate --strict ./manifests/*.yaml
```

2. **CI パイプラインへの組み込み**: 新規マニフェストについては、CI上でKYAML準拠のLintを必須化し、曖昧な記述がマージされることを防ぎます。
3. **段階的な移行**: 一度に全マニフェストを移行するのではなく、新規作成分から適用し、既存分は修正のタイミングで順次対応していくのが現実的です。

## Webhaniの見解

Kubernetesの運用でYAML起因の障害を経験したチームは少なくありません。特に、`enabled: no`のつもりで書いた値が文字列の"no"ではなく真偽値falseとして扱われ、意図と逆の設定が適用されてしまうようなケースは、レビューでも見逃されやすい典型例です。

KYAMLのような厳格な方言の採用は、即座に劇的な効果をもたらすものではありませんが、こうした「気づきにくい設定ミス」を仕組みで防ぐという点で、長期的な運用の安定性に寄与します。Webhaniでは、Kubernetes運用における構成管理の堅牢化を、こうした新しいツールの評価も含めて支援しています。

## まとめ

KYAMLは、KubernetesマニフェストにおけるYAMLの曖昧な型推論やインデント起因の事故を減らすことを目的とした、より厳格な方言です。既存資産との互換性を考慮しながら、CIでの検証を軸に段階的に導入することが現実的なアプローチです。構成ミスによる障害は再現性が低く原因究明に時間がかかりがちなため、こうした予防的な仕組みへの投資は十分に見合うものだと考えられます。
