Lambda関数を設計する際、これまでチームは早い段階である選択を迫られていました。ZIPアーカイブでパッケージングしてSnapStartのサブ秒コールドスタートを得るか、コンテナイメージでパッケージングして大きな依存関係を積める代わりにコールドスタートが数秒かかるのを受け入れるか、のどちらかです。2026年、AWSはこのギャップを埋め、SnapStartをコンテナイメージ形式のLambda関数にも対応させました（aws.amazon.com/about-aws/whats-new/2026/07/aws-lambda-snapstart-container/、2026年9月にはInfoQでも取り上げられています）。発表自体は地味に見えますが、多くのMLやデータ処理系のサーバーレスワークロードの設計を縛っていた制約がひとつ外れたことになります。

## なぜこのトレードオフが存在していたのか

SnapStartは、関数を一度初期化し、完全に起動し終えた実行環境（メモリ、ディスク状態、ロード済みのクラスやモジュール）のスナップショットを取得してキャッシュする仕組みです。次回以降のコールドスタート時には、初期化コードを最初から実行する代わりに、このスナップショットから再開します。特にJVM系のワークロードでは、クラスロードやJITウォームアップという最もコストのかかる処理がスナップショット取得前にすでに完了しているため、数秒かかっていたコールドスタートが200〜400ms程度まで短縮されます。

問題はパッケージング方式でした。SnapStartはもともとLambdaのマネージドZIPランタイム（Java、後にPythonと.NETが追加）のみに対応しており、ZIPアーカイブは展開後250MBが上限です。一方コンテナイメージは10GBまで対応しています。つまり、大きめのMLモデル、大きなネイティブライブラリ（OpenCV、CUDAランタイム、システムライブラリ込みのpandas/numpy/scipyスタックなど）を使う関数は、250MBを超えた時点で選択肢はコンテナ一択でした。SnapStartなし、コールドスタートはそのまま——単純な処理でも数秒かかることが多く、プロビジョニング済み同時実行を使う以外に回避策はありませんでした。

このトレードオフのせいで、設計段階で「小さく速いか、大きく遅いか」の二択を早期に決めざるを得ないケースが多く見られました。どちらが絶対的に間違いというわけではありませんが、ZIPサイズの制限を避けるためだけに、本来ひとつの論理的な関数を「軽量なホットパス用Lambda」と「別途ウォームアップする重いサービス」に分割する、といった過剰な設計をしているチームも少なくありませんでした。

## 何が変わったのか

コンテナイメージSnapStart対応により、ほとんどのケースでこの分割は不要になりました。2〜3GBのコンテナイメージにモデルと依存関係一式を詰め込んでも、コールドスタート時のスナップショット/再開の恩恵を受けられます。スナップショットはコンテナの初期化後の状態——初期化コードでメモリにロードした内容も含めて——キャプチャする点は、ZIPパッケージのJavaでこれまで動いていた仕組みと同じです。

ただし、ランタイムによって対応状況は異なります。Java 11+、Python 3.12+、.NET 8+のAWS提供ベースイメージは、ZIPベースのSnapStartと同様に基本的にそのまま動作します。それ以外——Node.js、Ruby、Go、完全にカスタムなランタイム——はDockerfileのラベルによる明示的なオプトインが必要で、場合によってはスナップショット対象と実行タイミングを制御するランタイムフックの実装も必要になります。

リージョン対応はほぼ完了していますが全てではありません。2026年9月時点の報道によると、Asia Pacific（New Zealand）とAsia Pacific（Taipei）を除く全ての商用AWSリージョンで利用可能です。これらのリージョンで運用している場合は、アーキテクチャを決める前に確認しておく価値があります。

## 具体例: Python製ML推論関数

ファインチューニング済みの文埋め込みモデルの推論を提供する関数を想定してみます。モデルの重みが数百MB、それに加えて`torch`、`transformers`とそのネイティブ依存関係が乗ります。これは簡単に250MBを超えるため、これまではコンテナでパッケージングするしかなく、スケールアウトのたびに4〜8秒のコールドスタートを受け入れるか、コールドスタートを完全に隠すためにプロビジョニング済み同時実行を24時間365日稼働させておくかの二択でした。

コンテナSnapStart対応後は以下のような流れになります。

- 同じコンテナイメージ（Python 3.12+ベース）をビルドする
- モデルのロードとライブラリのインポートはハンドラの外、初期化コードで一度だけ実行する
- AWSが最初の呼び出し後、その初期化済み環境のスナップショットを取得する
- 以降のコールドスタートはスナップショットから再開——モデルはすでにメモリ上、ライブラリもすでにインポート済み——で、JVM SnapStartユーザーがこれまで享受していたのと同程度のサブ秒レンジに収まる

実務上の効果としては、コールドスタートを隠すためだけにアイドル状態のプロビジョニング済み同時実行にコストを払い続ける必要がなくなり、ZIPアーカイブに収めるために依存関係を削る必要もなくなります。バーストするような推論トラフィック——Lambdaの従量課金モデルが本来最も活きるパターン——にとって、これは実質的なメリットです。

## Dockerfileパターン: Java/Python/.NET以外のランタイムでのオプトイン

「そのまま対応」のリストに入っていないランタイムでは、SnapStart対応を明示的に宣言する必要があります。カスタムランタイムやNode.jsベースのランタイムでの代表的なパターンは次のようになります（あくまで例示です。実際のフック契約はベースイメージのドキュメントで確認してください）。

```dockerfile
FROM public.ecr.aws/lambda/nodejs:20

# コンテナイメージでSnapStartを有効化するオプトイン
LABEL "aws.lambda.snapstart"="enabled"

# 依存関係はコールドスタート時ではなくビルド時にインストール
COPY package.json package-lock.json ./
RUN npm ci --omit=dev

COPY app/ ./app/

# 初期化時の副作用（コネクション、キャッシュ等）が
# スナップショットに暗黙的に焼き込まれないよう、
# beforeCheckpoint / afterRestoreフックを明示的に登録する
COPY snapstart-hooks.js ./
ENV AWS_LAMBDA_EXEC_WRAPPER=/opt/snapstart-wrapper

CMD ["app/handler.main"]
```

重要なのはラベルの正確な書き方（これはランタイムやベースイメージによって異なります）ではなく、考え方の部分です。イメージ内の何かが「スナップショット対象である」ことを明示的にマークし、ランタイムフックに対応しているものについてはチェックポイント/リストアのライフサイクルイベントに対するコールバックを登録する必要があります。これを省略すると、そもそもスナップショットが取得されないか、もっと悪いケースとして、コード側が想定していない暗黙の前提込みでスナップショットが取得されてしまいます。

## 落とし穴: 初期化コードの冪等性

ここがチームが見落としがちなポイントで、ZIPベースのSnapStartでも存在していた同じ落とし穴が、コンテナ対応によってより幅広いワークロードに関係してくることになります。スナップショット取得前に初期化コードが行うことは、そのスナップショットに焼き込まれ、再開のたびに再生されます。モデルをメモリにロードしたり、ライブラリをインポートしたりする分には問題ありません——これらは外部から見て決定的で副作用のない処理だからです。

問題になるのは次のようなケースです。

- **初期化時にシークレットや認証情報をキャッシュする。** 初期化中にデータベースのパスワードやAPIキーを取得し、それがスナップショットに含まれてしまうと、ローテーション後もすべての再開インスタンスが同じキャッシュ済みの値で動き続けてしまいます。シークレットの取得はスナップショット取得前ではなく再開後に行うか、`afterRestore`フックで更新するようにしてください。
- **初期化時に一意なIDやトークン、乱数シードを生成する。** スナップショット取得前に生成したUUIDやnonceは、そのスナップショットから再開するすべての環境で同一の値になってしまい、一意性という目的そのものが崩れます。この種の生成はハンドラ内、つまり再開後に移してください。
- **特定の時点を前提としたネットワーク接続を初期化時に開く。** スナップショット取得前に確立したTCP接続やTLSセッションは再開後には有効ではなく、通常はランタイムフックを使って再確立する必要があります。

概念としては目新しいものではなく、「スナップショットとは一時停止して再開されたプロセスである」というFirecrackerベースのSnapStartがこれまでずっと持っていたメンタルモデルそのものです。ただ、コンテナイメージによって、こうした初期化時の副作用を持ちやすいワークロード（MLパイプライン、初期化処理が重めのデータ処理関数）がより多く対象に入ってくる、という点が違います。

## webhaniとしての見解: いつ使うべきか、代替手段は何か

私たちがコンテナSnapStartを勧めるのは、「依存関係が250MBのZIPに収まらないほど大きい」ことと「呼び出し元にとってコールドスタートのレイテンシが実際に問題になる（インタラクティブなAPI、ユーザー向け推論、SLAがタイトなど）」ことの両方が当てはまる場合です。どちらか一方しか当てはまらない場合は、たいていもっと安価な選択肢があります。

- **依存関係は大きいがコールドスタートは気にならない**（バッチ処理、非同期処理など）: 通常のコンテナイメージのままでよく、SnapStartを導入する必要はありません。不要なスナップショット/再開の複雑さを持ち込まないことです。
- **コールドスタートは重要だが依存関係は小さい**: ZIPパッケージング＋SnapStart（Java/Python/.NET）の方がシンプルで、ライフサイクルフック付きのDockerfileよりデバッグすべき箇所が少なくて済みます。
- **持続的で予測可能な高トラフィック**: 実際にコールドスタートがほとんど発生しない状況では、プロビジョニング済み同時実行や常時稼働のFargateサービスの方がSnapStartよりコスト効率が良くなることがあります。SnapStartの価値はバースト性のある、スパイク的な、あるいは低頻度な呼び出しパターンにあり、常時ウォームな状態を維持するのが無駄になるケースで発揮されます。
- **非常に長時間実行される、またはステートフルなワークロード**: Lambdaの15分実行制限とSnapStartのリクエスト単位の再開モデルは、パッケージング方式にかかわらずそもそも向いていません。これはFargateやECSの領域です。

導入前には、初期化コードを上記の冪等性の観点で必ず監査してください。これはチームが省略しがちで、かつ後になって本番障害を引き起こしやすい部分です。手間は短時間で済みますが、SnapStartがきれいに効くか、それとも3ヶ月後に古い認証情報バグの原因になるかの分かれ目になります。
