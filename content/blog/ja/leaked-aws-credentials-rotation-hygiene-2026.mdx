## 数字が示すもの

Truffle Security は2026年8月、git commit 履歴・Hugging Face データセット・Docker Image・Package Registry・CI/CD ログといった公開ソースから収集された、10,616件の漏洩 AWS 認証情報ペアを再検証した Research を公開しました。対象は2022年8月から2026年8月にかけて蓄積されたものです。Report によると、検証対象の約88%が依然として認証に成功しました。有効だった企業関連 Key のうち、526件が AWS Root Access Key、242件が `AdministratorAccess` Policy を持つ IAM User に属していました。

このサンプルの背景にあるデータセットはさらに大規模で、431,875件の公開発見の中に64,024件のユニークな AWS Key ペア、そのうち10,000件以上が Root 認証情報でした。この Report で最も示唆的な統計は漏洩件数そのものではありません — 公開された認証情報の漏洩自体は目新しい話ではありません — 年齢分布です。漏洩した Key の中央値は5年前のもので、最も古いものは17.4年前に遡ります。Access Key の列挙が可能だった2,903件のサブセットのうち、新しい Replacement Key が発行されていたのはわずか13.7%でした。つまり、これらの認証情報の圧倒的多数は漏洩後に一度も rotate されておらず、多くの場合はそもそも一度も rotate されていなかった可能性が高いということです。

## なぜ漏洩が何年も有効なままなのか

ここでの技術的なメカニズムは高度なものではありません — プロセスの欠如です。公開 Repository に commit された Key、Docker Image のレイヤーに焼き込まれた Key、CI ログに出力された Key は、露出後ほぼ即座に scanner(防御側の Tool、攻撃側の Tooling いずれも)にインデックスされます。実際の被害範囲を決めるのは漏洩が起きるかどうか(数人以上の Engineer を抱える組織であれば漏洩は常に起きています)ではなく、露出後にその認証情報がどれだけ有効なままであり続けるかです。

漏洩した Key を何年も生かし続ける要因が3つ複合しています。

**露出時の自動 Revocation がない。** 顧客や研究者、攻撃者からの報告で初めて漏洩を発見する組織はすでに後手に回っています。GitHub のネイティブ Secret Scanning や Push Protection は commit 時点で一部の漏洩を捕捉しますが、Docker Image のレイヤーに焼き込まれた Key やアプリケーションログに出力された Key は Source レベルの Scanning を完全にすり抜けます。

**定期的な Rotation の基準がない。** Key が既知のインシデント対応としてのみ rotate されるのであれば、インシデント検出率が低いほど rotation の頻度もそれに従って低くなります。5年前に作成され一度も rotate されていない Root Key は珍しいことではなく、このデータセットでは中央値のケースです。

**Root Key と過剰な権限を持つ IAM User が実運用で使われている。** このサンプル規模で526件の有効な Root Key が見つかったことは、漏洩件数そのものより警戒すべき数字です。AWS は長年、プログラムによるアクセスに Root Access Key を使用しないよう推奨してきました。その存在が続いているということは、多くの組織がレガシー Tooling のために Root Key から移行できていないか、単発タスクのために一度作成して削除し忘れたことを示唆しています。

## CI/CD の実務にとって何が変わるか

AWS ワークロードを CI/CD 経由で運用しているチームにとって、実務上の教訓自体は目新しいものではありませんが、このデータは実際に実装させるための良い後押しになります。

**長期有効な Access Key ではなく、OIDC 経由の短期認証情報へ移行する。** GitHub Actions、GitLab CI、そしてほとんどの現代的な CI Platform は AWS との OpenID Connect Federation をサポートしており、Pipeline が静的な Key を Secret として保存することなく、1回の実行の間だけ IAM Role を assume できます。

```yaml
# GitHub Actions — OIDC ベースの AWS 認証、Access Key の保存不要
permissions:
  id-token: write
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/ci-deploy-role
          aws-region: ap-northeast-1
      # AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY という Secret 自体が存在しないため漏洩しようがない
```

**Root Access Key を完全に削除する。** AWS IAM では Root Access Key の無効化・削除がそもそも可能です。CI/CD を含む日常的な運用で Root Key が必要になることはあってはなりません。レガシーな Script が今も Root Key に依存している場合、それは移行タスクであって、Key を有効なまま残しておく理由にはなりません。

**Source Code 以外にも Secret Scanning を適用する。** 今回の漏洩の大部分は git 履歴だけでなく Docker Image・Package Registry・CI/CD ログから発生しているため、Scanning は commit だけでなく Build Artifact も対象にする必要があります。TruffleHog、Gitleaks、あるいは AWS 自身の IAM Access Analyzer などの Tool を Build Pipeline に組み込み、Image レイヤーやログ出力に認証情報のパターンが検出された時点で Build を失敗させることができます。

**インシデント検出とは独立した Rotation の SLA を設定する。** レガシーな理由で長期有効な Key を使わざるを得ない IAM User であっても、Key の最大有効期間(90日が一般的な基準)を強制し、誰かが Key の古さに気づくことに依存せず、自動 Rotation または失効を行うべきです。

## 5年前の Key は不運ではなく Policy の失敗である

この Research から得られる最も有用なフレームは「漏洩は起きる」ではありません — どの組織の脅威モデルもすでにそれを前提にしています。重要なのは、漏洩した認証情報が5年間 rotate されずに生き残っていること自体が、2つのものの欠如を示しているという点です。Source だけでなく Build Artifact 全体にわたる自動漏洩検出、そして誰かが手動で漏洩に気づくことに依存しない Rotation Policy です。

AWS Infrastructure について協業している Client 向けに現在推奨している監査は、範囲が狭く機械的です — 長期有効な Access Key を持つすべての IAM User と Role を列挙し、その中に Root Key が含まれていないことを確認し、最終 Rotation 日を90日 Policy と照合し、静的な Key が Secrets Manager や、さらに悪ければ Pipeline の環境変数に置かれている箇所を OIDC による Role Assumption に移行する。これらはどれも、ほとんどのチームがまだアクセスできていない新しい Tooling を必要としません。必要なのは、認証情報の Rotation をインシデント対応ではなく、定期的な運用タスクとして扱うことです。
