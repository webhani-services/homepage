## 小さなモデルと速いブラウザ

最近、webml-communityが公開したデモが話題になりました。Liquid AIの2億3,000万パラメータモデル「LFM2.5 230M」が、M4 Max上のブラウザタブ内だけで動作し、手書きのWebGPUカーネルによって約1,400 tokens/secを記録したというものです。バックエンド呼び出しもAPIキーも、ネットワークの往復も一切ありません。

ブラウザ内でのLLM推論自体は目新しい話ではありません。WebLLMのようなプロジェクトは以前からWebGPU経由で量子化モデルをクライアントサイドで動かしてきました。今回注目すべきは組み合わせです。小さいパラメータ数での効率を狙って設計されたアーキテクチャ（Liquid Foundation Models）に、多くの推論ライブラリが標準搭載する汎用バックエンドよりも意味のある差でスループットを引き出すカスタムカーネルを組み合わせている点です。結果として得られる速度は、単なる技術デモの域を超えて、実際にリアルタイムなUXを支えられるレベルに達しています。

## Web開発チームが注目すべき理由

ブラウザ内で推論を回すことは、特定の種類の機能についてコストとレイテンシの前提を変えます。

- **限界コストがゼロ**：モデルがクライアントにキャッシュされれば、リクエストごとの課金もレートリミットの計画も不要になります。
- **往復レイテンシがない**：オートコンプリートや簡易分類、ページ内サジェストのような短く対話的なタスクでは、モデルの精度そのものよりもネットワークのラウンドトリップを省けることの価値が大きいケースがあります。
- **データが端末から出ない**：下書きやフォーム入力、社内メモなど機微な情報を扱う機能では、サーバーに送らないこと自体がプライバシーやコンプライアンス上の大きな簡素化になります。
- **キャッシュ後はオフラインでも動く**：PWAやオフライン耐性のあるアプリで、限定的なAI機能を接続なしでも維持できます。

## 向いていない領域

2億3,000万パラメータのモデルは汎用アシスタントではありません。社内でそのように過大評価して説明しないことが重要です。テキスト分類、短めのオートコンプリート、キーワード抽出、簡単な言い換え、軽量な意図判定のような、範囲を絞ったタスクには向いています。一方で、長文脈でのマルチターン対話や、人間のレビューなしで出力品質を担保する必要がある用途、オープンエンドな推論をこなすフロンティアモデルの代替にはなりません。

考慮すべき制約も現実にあります。WebGPUの対応状況はブラウザによって差があり、古いブラウザや一部モバイル端末にはフォールバックが必要です。端末のメモリ容量もばらつきが大きく、初回ロード時のモデルダウンロードサイズは無視できないUXコストです。これは「一瞬で使える」ふりをするのではなく、キャッシュ設計とローディング状態の設計で解決すべき部分です。

## 最小構成の例

Hugging FaceのTransformers.jsは標準でWebGPUの実行プロバイダに対応しており、対応していない環境ではWebAssemblyにフォールバックできます。以下はFeature Detectionを組み込んだ最小構成です。

```js
import { pipeline } from "@huggingface/transformers";

async function createLocalAssistant() {
  const hasWebGPU = typeof navigator !== "undefined" && "gpu" in navigator;

  const generate = await pipeline("text-generation", "onnx-community/example-small-lm", {
    device: hasWebGPU ? "webgpu" : "wasm",
    dtype: "q4", // 量子化してダウンロードサイズとメモリ使用量を抑える
  });

  return async (prompt) => {
    const result = await generate(prompt, { max_new_tokens: 64 });
    return result[0].generated_text;
  };
}
```

利用するモデルは自社のタスクに合ったWebGPU対応の小型モデルに差し替えて構いません。重要なのはパターンです。対応状況を検出し、それに応じてバックエンドを切り替え、量子化を積極的に行ってダウンロードサイズとメモリ使用量をブラウザタブに収まる範囲に抑える、という設計です。

## webhaniの見解

コスト感度やデータプライバシーが制約条件になる、範囲を絞ったクライアントサイドAI機能のプロトタイピングには良い選択肢だと考えています。アプリ内検索の再ランキング、メッセージ送信前の軽量なコンテンツモデレーション、フォーム入力のサジェストなどが具体例です。ただし、プロダクトの中核となるAI機能をサーバーサイドモデルから移行する理由にはなりません。品質と一貫性の面では、依然として自社が制御できる環境で動く大きめのモデルに分があります。

WebGPU対応を前提にせず初日からサーバーサイドのフォールバックを用意すること、そして2億3,000万パラメータのモデルにできること・できないことをステークホルダーに正確に伝えることをお勧めします。デモの速度は確かに印象的ですが、速さは能力そのものではありません。適切な範囲のタスクに使えばコストとレイテンシの面で実質的な効果がありますが、プロダクトの主力AI機能の代替として使おうとすると期待外れに終わるでしょう。
