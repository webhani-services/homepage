Cloud の認証情報が漏れたとき、以前なら行き着く先はたいてい暗号資産のマイニングでした。その構図が変わりつつあります。Google Threat Intelligence Group (GTIG) と Mandiant が 11 月 2 日に公開したレポートによると、攻撃者は盗んだ Cloud ID を LLM へのアクセスに変えることを好むようになり、その周辺に転売市場ができあがっています。紹介されている事例の一つでは、1 人の攻撃者が 8 時間足らずで 50 万回以上のモデル呼び出しを行い、被害組織には約 100 万ドルのトークン費用が残りました。1 日で 10 万ドルを超えたケースも複数あるとのことです。

金額にも驚きますが、開発チームにとってより重要なのは構造の変化です。LLMjacking はもはや「キーが漏れた結果たまたま起きること」ではなく、分業化されたサプライチェーンになっています。

## 市場はどう分業されているか

レポートは二つの役割を区別しています。

- **侵入担当**: 認証情報を入手する役割です。主な入口は相変わらず、IAM アクセスキー、サービスアカウントのキーファイル、GitHub の Personal Access Token、有効なセッショントークンです。
- **「LLM Mixer」**: 集めた認証情報をオープンソースの API Gateway や独自のリレーの裏にプールし、利用量を計測して顧客にモデルアクセスを再販する役割です。リクエストは盗まれたキーのプールを経由するため、個々の呼び出しの出どころを追うのは困難です。

報道の中で、私たちが特に注目したのは次の 2 点です。

1. **一部の被害組織は LLM サービスを一度も有効化していなかった。** 攻撃者が盗んだ ID でモデルアクセスを自ら有効化していました。「うちは Bedrock も Vertex AI も使っていない」は防御にならず、むしろ死角になります。
2. **AI Gateway そのものが標的になっている。** セルフホストの LiteLLM Gateway の脆弱性により、通常の仮想キーが管理者権限に昇格されたとされる事例も報告されています。CVE の詳細がどう確定するにせよ、教訓は一般化できます。全社のプロバイダーキーを預かる Gateway は高価値な資産であり、ID プロバイダーと同じレベルのパッチ運用が必要です。

## 通常のキー漏洩と何が違うのか

Database のパスワードが漏れれば、データが危険にさらされます。モデルアクセス権を持つ Cloud ID が漏れると、危険にさらされるのは **予算** です。しかも、人が気づくより速いペースで進みます。LLM 推論は、インスタンスやクラスタのような目に見えるリソースを作らずに、1 日で数十万ドル規模の請求を発生させられる数少ない Cloud サービスです。1 日 1 回のコスト異常検知では間に合いません。

影響を受けるチームの範囲も広がります。AI 機能をまったく持たないチームでも、モデルを有効化・呼び出しできる Principal さえあれば攻撃は成立します。

## 推奨する対策

どれも新しいアイデアではありません。変わったのは優先度です。

### 1. 不要な場所ではモデル呼び出しを禁止する

AWS で最もシンプルなのは、推論を行う必要のない OU に Service Control Policy (SCP) を適用する方法です。Principal が `AdministratorAccess` を持っていても、盗まれた認証情報経由の利用を止められます。

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyBedrockOutsideAIWorkloads",
      "Effect": "Deny",
      "Action": [
        "bedrock:InvokeModel",
        "bedrock:InvokeModelWithResponseStream",
        "bedrock:PutFoundationModelEntitlement",
        "aws-marketplace:Subscribe"
      ],
      "Resource": "*"
    }
  ]
}
```

「legacy」「data-platform」「sandbox」のような OU に適用し、推論を許可するのは AI ワークロード専用のアカウント (または OU) だけにします。サードパーティモデルへのアクセスは Marketplace のサブスクリプションで制御されていることが多いため、`aws-marketplace:Subscribe` も入れています。SCP はスコープ内のすべての Principal に影響するので、まず非本番の OU で検証してください。

Google Cloud では、プロジェクト単位の IAM に頼るより、組織ポリシーで Vertex AI API を有効化できるプロジェクトを制限するのが同等の対策になります。

### 2. CI から長期キーをなくす

レポートでも、CI の Secret に置かれた GitHub PAT や静的な Cloud キーは主要な入手経路として挙がっています。パイプラインでまだ `AWS_ACCESS_KEY_ID` を使っているなら、OIDC フェデレーションに移行し、盗まれる長期キーそのものをなくしましょう。

```yaml
permissions:
  id-token: write
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/gha-deploy
          aws-region: ap-northeast-1
```

Role の信頼ポリシーは特定のリポジトリとブランチに絞り、Deploy に本当に必要でない限り Bedrock の権限は付けないでください。

### 3. 履歴も含めて Secret をスキャンする

何か月も前に漏れたキーでも、ローテーションしていなければ有効なままです。作業ツリーだけでなく Git 履歴全体をスキャンします。

```bash
gitleaks git . --redact --report-path gitleaks-report.json
```

検出されたキーはリポジトリから消すだけでなく、必ずローテーションしてください。コミット済みのキーを削除しても、すでに収集されたコピーには何の効果もありません。

### 4. コストアラートは「日」ではなく「時間」単位で

AI を使うアカウントごとに低めのしきい値で Budget アラートを設定し、実際に誰かが見ているチャンネルに通知します。プロバイダー側の制御も有効です。LLM Gateway でキーごとの利用上限やレート制限を設定しておけば、100 万ドルの事故を上限付きの事故に変えられます。LiteLLM などのプロキシを運用しているなら、キーごとの Budget を設定し、admin / master key はアプリケーション環境に一切置かないようにします。

### 5. AI Gateway を tier-0 インフラとして扱う

- SSO や Secret Manager と同じサイクルでパッチを当てる
- 管理 API をインターネットに公開しない
- キーの作成や権限変更をログに残し、アラートを設定する

## 今週確認しておきたいこと

1 時間しか取れないなら、次の 4 点だけでも確認してください。

- モデルアクセスが有効になっているアカウント / プロジェクトの一覧を出す。想定外のものがあれば、シャドー AI か攻撃者のどちらかです。
- モデルを呼び出せるすべてのアカウントに Budget アラートがあるか確認する。
- CI 設定に静的な Cloud キーや GitHub PAT が残っていないか検索する。
- セルフホストの LLM Gateway のバージョンを、セキュリティアドバイザリと照合する。

## まとめ

LLMjacking は単発のインシデントから、認証情報の窃取と転売が分業された「産業」へと変わりました。現実的な対応は地味なものです。使わない場所では推論を禁止し、長期の認証情報をなくし、間に合う速さでコストアラートを鳴らす。webhani では Cloud のセキュリティレビューで「この ID は本番データを読めるか」と並べて「この ID はモデルを呼び出せるか」を標準の確認項目にしています。どちらの答えも、意図して決めたものであるべきです。
