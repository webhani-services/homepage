## 2種類の利用者を同時に想定したDesign System

Metaは2026年6月28日、StyleXベースのReact 19向けDesign System「Astryx」をOpen Sourceとして公開しました。150以上のAccessibleなComponentと10種類のBuilt-in Themeを備えています。これだけであれば、堅実ではあるものの特筆すべきほどではないDesign Systemのリリースです — 同等のComponent Libraryを公開している企業は他にもいくつもあります。Astryxが注目に値するのは、そして今月InfoQが改めて取り上げたのは、これがHuman Engineerと、今や多くの企業でFrontend Codeの少なくない部分を書いているAI Coding Agent（Claude Code、Cursor、GitHub Copilotなど）という、明示的に2種類の利用者を想定して作られている点です。

## 「Agent対応」が具体的に指すもの

実質的な役割を果たしているFeatureは2つです。1つ目は、Componentの発見、Layout Templateの問い合わせ、設定の読み取りを行うための構造化されたAPIを提供するBuilt-in MCP Serverです。AgentがSource Codeをgrepしたり、RenderされたDocumentation Pageをスクレイピングして`<Card>`Componentの有効なPropsを推測したりする必要がなくなります。2つ目は、`astryx` CLIの`--dense`Flagで、Component Documentationから人間向けの説明文を削ぎ落とし、LLMのContext Windowに収まりやすいToken効率の良いPayloadを生成します。

これらを組み合わせることで、現場で実際に起きている失敗パターンに対処できます。「自社Design SystemでModalを追加して」と指示されたAgentが存在しないPropをHallucinationしたり、本当に必要な3行の情報を得るためだけにDocumentation Page全体を読み込んでContext Windowの大部分を消費したりする、というものです。

## 発想を最小限で示すと

このPattern自体を実現するのにAstryxが必須というわけではありません。Agent向けに構造化されたComponent Manifestの形はおおよそ次のようになります。

```json
{
  "component": "Modal",
  "props": {
    "open": { "type": "boolean", "required": true },
    "onClose": { "type": "() => void", "required": true },
    "size": { "type": "'sm' | 'md' | 'lg'", "default": "md" }
  },
  "slots": ["header", "body", "footer"],
  "a11y": "Traps focus, restores focus to trigger on close, closes on Escape"
}
```

これをMCP Tool呼び出し経由で問い合わせるAgentは、Codebase内の部分的に一致する他の例からProp名を推測するのではなく、一度で正しいCodeを生成するために必要な情報をそのまま得られます。これは、私たちがこれまで見てきたAgent生成UIのBugの多くが実際に発生している原因でもあります。

## Component Library選定への示唆

1. **「Agent対応」は単なる話題づくりではなく、実質的な評価基準になりつつあります**：Frontend PRの少なくない割合をAgentが下書きしているチームであれば、Agentが構造的に問い合わせられるDesign Systemの方が、Markdown DocumentationからPropを推測させるDesign Systemより、誤ったPropによるBugが少なくなります。
2. **簡易版は自社でも作れます**：内製のDesign Systemを運用しているなら、完全なMCP Serverを用意しなくても、ComponentのProps・Slot・Accessibility契約をJSON Manifestとして公開するだけで、Codebaseで作業するAgentにとってStorybookの説明文よりずっと信頼できる情報源になります。
3. **型安全性の代わりにはなりません**：TypeScriptのProp Typeはすでに、この情報の多くをAgent（そして人間）に無料で提供しています。Astryx的なManifestが最も価値を発揮するのは、型ではうまく表現できない部分 — Accessibilityの挙動、組み合わせのルール、型としては可能でも実際にはSupportされていないProp組み合わせ — です。

## Webhaniの見解

Astryxを「採用すべきDesign System」というより、「Design System向けToolingが向かっている方向を示すSignal」として捉えるのが適切だと考えます。人間向けの読みやすさより先に、機械向けの構造を優先したDocumentationです。すでにClaude Codeなどを使ってFrontendの一部を任せているチームであれば、Astryxの個々のComponentが自社Productに合うかを検討する前に、このDocumentation構造の優先順位自体を取り入れる価値があります。今この瞬間、Componentの数がわずかに多いDesign Systemより、Agentが正しく問い合わせられるDesign Systemの方が価値があります。
