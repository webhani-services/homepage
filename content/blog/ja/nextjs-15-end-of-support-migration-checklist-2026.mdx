Next.js 15 のリリースは 2024年10月21日でした。Next.js のサポートポリシーでは、メジャーバージョンはリリースから2年間 Maintenance LTS として扱われるため、15.x のサポート終了は 2026年10月21日、つまりあと約1週間です。この日以降、15.x へのセキュリティ修正は保証されなくなります。Vercel は深刻な場合に例外的にパッチを出す可能性があるとしていますが、本番運用の前提にすべきではありません。

この記事では、webhani がお客様のアプリケーションを 15.x から 16.x へ移行する際に使っているチェックリストを紹介します。App Router のプロジェクトを前提としています。日付などの情報はサポートポリシーと第三者の EOL トラッカーに基づくため、最終的には公式ドキュメントで確認してください。

## なぜ今回の期限が重要か

今年の Next.js はセキュリティリリースが続き、修正はサポート中のラインにのみ提供されました。15.x を使っているチームは「どれかの 15」ではなく、特定のパッチ済みマイナーに上げる必要がありました。サポートが終わると、次の脆弱性が公表されても 15.x にバックポートが出ない可能性があります。その場合、インシデント対応の最中にメジャーバージョンを急いで上げることになり、これは最も避けたい状況です。

自分たちのスケジュールで今のうちに上げるほうが、確実に安く済みます。

## Step 1: 実際に動いているバージョンを棚卸しする

コードに触る前に、どのバージョンがデプロイされているかを把握します。

```bash
# リポジトリ単位
npm ls next react react-dom --depth=0

# ディレクトリ配下の複数リポジトリをまとめて確認
for d in */; do
  [ -f "$d/package.json" ] && \
    echo "$d: $(node -p "require('./$d/package.json').dependencies?.next ?? 'n/a'")"
done
```

Preview 環境や長期間残っている staging ブランチも対象に含めてください。取り残されがちなのは社内ツールです。

## Step 2: まず最新の 15.x に上げる

16 に進む前に、15.x の最終パッチまで上げます。「16 が原因で壊れた」のか「古い 15 のマイナーだから壊れた」のかを切り分けるためです。

```bash
npm install next@15 react@19 react-dom@19
npm run build && npm test
```

ここでビルドが通れば、比較の基準となるクリーンなベースラインができます。

## Step 3: 公式の Codemod を実行する

Next.js には機械的な変更を適用する Codemod CLI があります。

```bash
npx @next/codemod@canary upgrade latest
```

差分は必ずレビューしてください。Codemod は API の名称変更には強いものの、データ取得まわりの前提が今も成り立つかまでは判断できません。

## Step 4: つまずきやすい3点を確認する

**バンドラー。** 16 では Turbopack がデフォルトです。`next.config` にカスタムの `webpack` 設定がある場合は、ビルド時に分かります。移行中は Webpack を明示的に使い続けることもできますが、機能追加や性能改善は Turbopack が先行するため、最終的には移行を計画してください。

```bash
# プラグインが対応していない場合の一時的な回避策
next build --webpack
```

**キャッシュ。** 15 から 16 にかけて、Cache Components と `use cache` が暗黙のキャッシュ挙動を置き換える方向で、キャッシュの意味合いが変わっています。`fetch` やルートハンドラーがたまたまキャッシュされていたデフォルト挙動に依存している場合は、アップグレード前に、鮮度が重要なページ(価格、在庫、ユーザーのダッシュボードなど)にテストを追加しておきましょう。

**削除された機能。** 16 では AMP のサポートが終了しています。レガシーなページで使っていれば、別途対応が必要です。

## Step 5: 切り替え前に回帰テストを用意する

少数の E2E チェックで、移行時の問題の大半は検知できます。私たちは通常、次をカバーします。

- ログインと、認証済みページの表示
- レンダリング方式ごと(静的・動的・ストリーミング)に1ページ
- Server Action 経由のフォーム送信
- 主要ルートのレスポンスヘッダー(cache-control、CSP)

```ts
// e2e/smoke.spec.ts (Playwright)
import { test, expect } from "@playwright/test";

test("pricing page is not served stale", async ({ page, request }) => {
  const res = await request.get("/pricing");
  expect(res.status()).toBe(200);
  expect(res.headers()["cache-control"]).not.toContain("immutable");
  await page.goto("/pricing");
  await expect(page.getByRole("heading", { name: /pricing/i })).toBeVisible();
});
```

15.x のベースラインと 16.x のブランチの両方で実行します。ヘッダーの差分は、キャッシュ挙動の変化を最初に示すサインになることが多いです。

## Step 6: 段階的にリリースする

プラットフォームが対応していれば、カナリアや割合指定のリリースを使います。Vercel なら Rolling Releases、セルフホストなら重み付けしたロードバランサーで同じことができます。100% に上げる前に、エラー率と p95 レイテンシを1日ほど観察してください。自信が持てるまでは、ロールバック用に 15.x のデプロイを残しておきます。

## webhani の推奨

- **現在 15.x の場合:** 今週中にアップグレードを計画してください。1週間の余裕は短いものの、多くのアプリでは対応可能です。
- **10月21日までに間に合わない場合:** 少なくとも最新の 15.x パッチに固定し、Next.js のセキュリティ勧告を購読し、緊急アップグレードを誰が判断するかを決めておきます。
- **多数のアプリを抱えている場合:** 最もリスクの低いアプリから先に上げ、その Codemod の差分とテストスイートをテンプレートとして再利用します。

アップグレード作業そのものが難しいことは多くありません。難しいのは、存在を忘れていたアプリを見つけることです。まず棚卸しから始めましょう。
