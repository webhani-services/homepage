Next.js 16.3 の性能改善（Turbopack のメモリ削減や永続 build キャッシュ）については、以前の記事で取り上げました。それとは別に、Next.js チームは「16.3 Preview」という build を並行して公開しており、こちらは build 速度ではなく「AI coding agent と一緒に開発すること」を前提にした devtools の刷新にフォーカスしています。webhani では Claude Code や類似の AI agent を日常的に開発フローへ組み込んでおり、この Preview build が実際に何を変えるのかを検証しました。

## なぜ今 "AI-native" な devtools なのか

ある調査では、開発者の 67% が JavaScript よりも TypeScript を多く書くようになっていると報告されています。型情報が充実したコードベースが標準になりつつある一方で、AI coding agent（Claude Code、Cursor、GitHub Copilot など）が pull request の下書きから debugging の補助まで担う場面が急速に増えています。つまり、フレームワーク側の devtools は「人間の開発者が読む」ことだけでなく「AI agent が正確に解釈して行動できる」ことも要求されるようになってきました。Next.js 16.3 Preview はこの前提に正面から応えようとしている build です。

## Bundled Documentation — なぜ「同梱」が重要なのか

これまで AI coding agent が Next.js の API について質問されると、多くの場合 web 検索や学習データに含まれる情報に頼っていました。しかし Next.js は年に数回大きな API 変更を行うフレームワークであり、web 上のドキュメントやブログ記事は簡単に version と乖離します。結果として agent が古い API（例えば app router 移行前の pages router の書き方）を提案し、開発者がそれを手動で修正するという非効率が頻発していました。

16.3 Preview では、framework 本体にドキュメントが bundle され、`node_modules` 経由でローカルに配置されます。AI agent がプロジェクトの `package.json` からインストール済みの Next.js version を特定し、そのバージョンに正確に対応したドキュメントをローカルで参照できるようになります。これは単なる利便性ではなく、hallucination を減らすための構造的な対策です。version が一致した一次情報がローカルにある状態と、web 検索で拾った「たぶん合っている」情報に頼る状態とでは、agent が生成するコードの信頼度が大きく変わります。

## Skills — AI Agent 向けの「実行可能なレシピ」

もう一つの目玉が Skills という仕組みです。これは Next.js プロジェクトに対して AI coding agent が呼び出せる、構造化された「手順書」だと考えると理解しやすいでしょう。例えば「新しい API route を追加する」「Server Component と Client Component を適切に分割する」「middleware で認証を挟む」といった典型的なタスクに対応する Skill が用意され、agent はそれを検索・実行することで、プロジェクト固有の慣習からずれないコードを生成できます。

webhani の実務では、チームごとに `AreaXxx` のような命名規則やファイル配置のパターンを持っています。Skills の仕組みが成熟すれば、こうした社内規約を Skill として定義し、AI agent に scaffolding を任せる際の一貫性を担保できる可能性があります。現時点では Preview 機能であり実装の詳細は流動的ですが、方向性としては「AI agent に対する社内ドキュメントの構造化」という発想に近いです。

## Browser 上での React State Introspection

従来、AI agent が pairing 相手として debugging を手伝う場合、開発者が console.log の出力や React DevTools のスクリーンショットを共有する必要がありました。16.3 Preview の browser introspection 機能は、動作中の React component の state を tooling から直接取得できるようにします。これにより、agent が「このコンポーネントは現在どういう state を持っているか」を実際の runtime から取得した上で、仮説ではなく事実に基づいた修正を提案できるようになります。

具体的には、開発者が「このボタンを押すと表示がおかしくなる」と伝えるだけで、agent 側が live な component tree の state を参照し、想定される state 遷移とのズレを特定するという workflow が現実的になります。これは「開発者が症状を説明し、agent が原因を推測する」という従来の非効率な往復を短縮する効果が期待できます。

## Actionable Error Messages — スタックトレースから「直し方」へ

これまでの Next.js の error message は、多くの場合スタックトレースと簡単な説明に留まっていました。AI agent はそこから原因を推測し、複数の修正候補を試すという non-deterministic な workflow になりがちでした。16.3 Preview では、error message がより具体的に「どのファイルのどの箇所を、どう直すべきか」を示す方向に改善されています。

擬似的な before/after で示すと次のようになります。

```text
# Before（従来の error message のイメージ）
Error: Cannot read properties of undefined (reading 'map')
    at ProductList (app/products/page.tsx:24:18)

# After（actionable error のイメージ）
Error: `products` is undefined in ProductList (app/products/page.tsx:24)
  → This component expects `products` to be passed as a prop or fetched
    via `getProducts()`, but no data source was provided.
  → Fix: add `const products = await getProducts()` before the return
    statement, or pass `products` from the parent Server Component.
```

前者では agent は state や data fetching の実装全体を読み直し、原因を推測してから修正案を提示する必要があります。後者ではエラー自体が修正方針を含んでいるため、agent は最短距離で修正パッチを提案できます。これは agent の推論コストを下げるだけでなく、誤った修正を提案するリスクも下げます。

## 想定されるプロジェクト構成

Preview 機能を試す場合、bundled documentation や Skills が実際にどこに配置されるかを意識しておくと理解が早まります。イメージとしては次のような構成です。

```text
my-nextjs-app/
├── node_modules/
│   └── next/
│       ├── dist/
│       └── docs/           # bundled documentation（version 固定）
│           └── skills/     # Skills の定義（構造化された手順）
├── app/
│   ├── layout.tsx
│   └── products/
│       └── page.tsx
├── package.json             # Next.js version の specify 元
└── next.config.mjs
```

AI agent は `package.json` から version を特定し、`node_modules/next/docs` 配下の該当バージョンのドキュメントと Skills を参照する、という流れが基本設計です。プロジェクト固有の Skill を追加する仕組みが今後どう提供されるかは Preview 段階のため未確定ですが、少なくとも「framework 側が version 一致を保証したドキュメントを提供する」という前提は明確です。

## Preview を今すぐ採用すべきか

結論から言うと、webhani としては本番プロジェクトへの即時導入は推奨しません。理由は次の通りです。

1. **Preview は GA ではない**。API や仕組みが今後変わる可能性が高く、破壊的変更のリスクがあります。
2. **Skills や browser introspection は AI agent 側の対応も必要**です。Claude Code や他のツールがこれらの仕組みをどこまで活用できるかは、agent 側の実装に依存します。framework が提供しても agent 側の対応が追いつかなければ効果は限定的です。
3. **既存の開発フローとの互換性検証が未実施**です。16.3 の性能改善（Turbopack、永続キャッシュ）は既に別途検証済みですが、Preview build の devtools 機能はまだ社内プロジェクトで試していません。

一方で、個人検証や社内の実験的プロジェクトで Preview build を触ってみる価値は十分にあります。特に Claude Code のような agent を日常的に使うチームであれば、bundled documentation と actionable error の組み合わせがどの程度 agent の精度を上げるかを早期に体感しておくことは、将来 stable 版が来た際のスムーズな移行につながります。

## まとめ

Next.js 16.3 Preview が扱っているのは、build 速度ではなく「AI agent と人間が同じコードベースをどう効率よく扱うか」という問題です。bundled documentation は agent の hallucination を構造的に減らし、Skills は scaffolding の一貫性を担保する可能性を持ち、browser introspection は debugging 時の情報共有コストを下げ、actionable error は修正までの往復を短縮します。いずれも単体の派手な機能ではなく、AI agent との協働を前提にした「摩擦の削減」という共通した狙いを持っています。

webhani としては、Preview build を prod へ急いで導入するのではなく、社内の実験的プロジェクトで検証を重ね、stable リリースのタイミングで本番導入を判断する方針です。AI agent と組む開発が既に日常になっているからこそ、この方向性の進化は継続的に追っていく価値があります。
