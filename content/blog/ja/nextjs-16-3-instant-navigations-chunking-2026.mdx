Next.js 16.3 では Instant Navigations と並んで、Turbopack のチャンキングを制御する実験的なオプション群が追加されました。目玉機能は Instant Navigations ですが、実際のアプリでナビゲーションが「本当に瞬時」に感じられるかどうかを左右するのは、その下にあるチャンキング制御の方です。デモ用の単純なルートではなく、実際のコンポーネントツリーを持つアプリでこそ効いてきます。

## これらのフラグが解決する問題

ルート単位のチャンキング — ルート境界ごとに JavaScript と CSS をまとめる方式 — は、複数の無関係なページで共有されるコンポーネントや、複数のコンポーネントが同時にレンダリングされて初めて意味を持つスタイルが存在すると、うまく機能しなくなります。本番環境でよく見られる症状は2つです。あるページに直接リロードした場合と、他のページからナビゲーションで遷移した場合とで、読み込まれる CSS が異なり見た目が崩れること。そして、ランタイムがページ単位でしかチャンクを認識していないため、何を取得すべきかについて賢い判断ができないことです。

Next.js 16.3 は、これらをより細かい粒度で解決します。

## コンポーネント単位のチャンキング

`generateComponentChunks` は、Turbopack をルート境界だけでなくコンポーネント単位でチャンク認識できるようにします。これにより、ランタイムはすでにキャッシュされている内容をもとに何を取得すべきか判断できるようになり、共有コンポーネントの小さな変更のためにルート全体分の JavaScript を再取得する、といった無駄がなくなります。

```js
// next.config.js
module.exports = {
  experimental: {
    generateComponentChunks: true,
  },
};
```

この恩恵が大きいのは、デザインシステムや、チャートやテーブルなどの共有コンポーネントが多用されるダッシュボードのように、共有 UI 層が大きいアプリです。ルート単位のチャンキングでは冗長なダウンロードが発生しがちだったケースです。

## グラフベースの CSS チャンキング

`cssChunking: "graph"` は、ルートツリーから推測するのではなく、実際にどのコンポーネントが一緒にレンダリングされるかに基づいてスタイルをグループ化します。これは「ナビゲーションで遷移した場合とリロードした場合で見た目が違う」というバグの直接的な対策であり、原因の多くは共有スタイルの重複や、ページ固有のスタイルとの読み込み順序が不定になることにあります。

```js
// next.config.js
module.exports = {
  experimental: {
    cssChunking: "graph",
  },
};
```

## staleTimes の調整

`staleTimes` は、クライアントがページのメモリ内コピーをどれだけの時間信頼して再取得しないかを制御します。プリフェッチ済みの静的ページ向けの `static`（デフォルト5分）と、それ以外の `dynamic`（デフォルト0、つまり常に再取得）です。Instant Navigations と組み合わせることで、頻繁には変わらないページについて、多少の古さと引き換えにネットワークラウンドトリップを大きく減らすことができます。

```js
// next.config.js
module.exports = {
  experimental: {
    staleTimes: {
      dynamic: 30,
      static: 300,
    },
  },
};
```

`dynamic` を30秒程度に設定するのは、頻繁ではないが定期的に更新されるコンテンツ — 社内ダッシュボードやカタログページなど — に対しては妥当な出発点です。

## 有効化を検討すべきタイミング

これらはまだ実験的なフラグであり、これは単なる建前ではありません。マイナーバージョン間で挙動が変わる可能性があります。私たちが有効化を検討するのは、次のような条件がそろったときです。

- アプリに、多くのルートで再利用される大規模な共有コンポーネント層やデザインシステムがある
- ナビゲーション時と リロード時での CSS の不整合を、推測ではなく実際に観測している
- ナビゲーションのパフォーマンスが、仮説ではなく Core Web Vitals やユーザーからの指摘といった形で実測されている問題である

## 移行時の注意点

3つのフラグを一度に有効化するのではなく、ステージング環境で1つずつ有効化してください。何か問題が起きた場合に、どの設定が原因かを特定できるようにするためです。有効化の前後で bundle analyzer の出力を確認することも重要です。コンポーネント単位のチャンキングは、冗長なダウンロードを減らす一方でチャンク総数自体は増える場合があり、これはアプリごとに確認すべきトレードオフです。

## webhani の見解

Next.js を用いたプロジェクトでは、実験的フラグはアプリ全体に一括展開するのではなく、まずトラフィックの多い1ルートで試すべきものと考えています。スタイルの不整合を実際に目にしているなら、`cssChunking: "graph"` を最優先で検討する価値があります。ユーザーに見える形の不具合を直接修正するものだからです。コンポーネントチャンキングと `staleTimes` の調整については、ナビゲーション時のペイロードサイズやデータの古さが実際にボトルネックになっているというデータが揃ってから採用するのが望ましく、推測だけで有効化するのは避けるべきです。
