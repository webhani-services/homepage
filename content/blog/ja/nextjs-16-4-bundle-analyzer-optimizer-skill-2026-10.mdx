バンドルサイズの悪化は、ひとつの大きな変更から起きることはまれです。共有ユーティリティにimportが1つ増えた、ダイアログのレジストリがすべてのダイアログを参照していた、といった小さな積み重ねで起こります。10月28日、Next.jsチームがこの問題に対する16.4のツールについて記事を公開しました。改良されたTurbopack Bundle Analyzerと、そのモジュールグラフを使うエージェント用Skill `next-bundle-optimizer` です。

ツールの詳細も読む価値がありますが、背景にある教訓のほうが実用的です。**lazy importがコードを遅延させるのは、他のどこからも静的にimportされていない場合だけ**です。

## 起きる問題

オンデマンドで読み込むつもりの重いエディタコンポーネントを考えます。

```tsx
// HeavyEditorLoader.tsx
'use client';
import { lazy } from 'react';

export const HeavyEditorLoader = lazy(() => import('./HeavyEditor'));
```

これで `HeavyEditor` が遅延されるのは、`HeavyEditorLoader` が唯一のimport元である場合だけです。同じバンドル内の別のモジュールが `import { HeavyEditor } from './HeavyEditor'` としていれば(型や同じファイルからexportされた定数を再利用するためなど)、バンドラは初期チャンクに含めざるを得ません。`lazy()` は動作し、警告も出ませんが、コードは最初から配信されます。

クライアント案件でよく見る原因は次のとおりです。

- コンポーネントのファイルからexportされた型や定数が、別の場所でimportされている。共有する型を別ファイルに移せば解消します。
- すべてを再exportするbarrelファイル(`index.ts`)のせいで、小さなヘルパーをimportしただけで隣の重いモジュールまで入ってくる。
- ダイアログ、アイコン、ルートとコンポーネントの対応表などの中央レジストリが、全エントリを静的に参照している。

個々のimportは妥当に見えるため、コードレビューでは見つかりません。

## 16.4でAnalyzerに加わったもの

アプリのディレクトリで `next analyze` を実行します。Next.jsの発表によると、Analyzerには次の機能が加わりました。

- **ルート概要。** 最も大きいクライアントルートを一覧し、グラフ全体ではなく重要なページから調査を始められます。
- **ルートごとのテーブル表示。** サイズで並べ替えて、大きな要因をすばやく見つけられます。
- **スナップショット。** 実行した分析が自動で保存され、2つを比較できます。最初に取り入れたい機能です。「先月のどこかでバンドルが大きくなった」という曖昧な感覚を、具体的な2点間の比較に変えられます。
- **クリティカルレンダーパスの強調表示。** 非同期の依存を除外し、初回レンダリングで同期的に読み込まれるものだけを表示できます。Next.jsの記事には注意書きがあり、実行時の状態によってはRSCのレンダリングで `next/dynamic` 由来のチャンクが初期ロードに含まれることがあるため、実際に動かして確認する必要があります。
- **`next analyze export`。** モジュールとチャンクのグラフデータを書き出し、独自のツールで照会できます。

AnalyzerはTurbopackのモジュールグラフに依存するため、Next.js 16からデフォルトのバンドラであるTurbopackが前提です。

## Optimizer Skill

次のコマンドで導入します。

```bash
npx skills add vercel/next.js --skill next-bundle-optimizer
```

その後、コーディングエージェントで `/next-bundle-optimizer` を実行します。デフォルトでは問題点と修正案を報告するだけで、`/next-bundle-optimizer fix` を実行すると変更を適用し、分析をやり直してスナップショットを比較します。

Next.jsチームによると、エージェントは相互に接続されたモジュールをグループ化し、importの連鎖をたどり、最小カットの考え方で大きなグループを遅延させられる少数のimport境界を探します。さらに、React Server Componentsに移せるロジック、大きな依存関係の重複バージョン、tree shakingが効いていない箇所も調べます。

報告されている成果はVercel自身のアプリのもので、v0とvercel.comで合計ほぼ2MB(圧縮後)のJavaScriptを削除または遅延させたとのことです。例として、ほぼ全ページで読み込まれていたコードエディタ(多くのページで約150KB削減)、重いダイアログを先読みしていたレジストリ(ページにより40〜650KB)、アシスタントに触れる前に読み込まれていた日付解析ライブラリ(平均で約55KB)が挙げられています。これは大規模で長く運用されているコードベースにおけるベンダー自身の数値なので、一般的な企業サイトでは絶対値の効果は小さいでしょう。ただし、間違いの種類は多くの中規模アプリで見られるものと同じです。

## 私たちの使い方

**変更前に必ず分析する。** 主要な3〜4ルートのベースラインのスナップショットを保存します。これがなければ、変更が効いたことを示せません。

**エージェントの出力は仮説のリストとして扱う。** import境界を動かすと挙動が変わることがあります。初回描画で準備できていたコンポーネントが、フォールバックを一瞬表示するようになるかもしれません。提案ごとに実際の使われ方と照らして確認し、ビルドだけでなく操作もテストします。

**1変更につき1 Pull Request。** Next.jsの記事では、変更ごとにPull Requestを作成し、preview deploymentで検証したと書かれています。この粒度が適切です。リグレッションが出たとき、原因の変更がわかります。

**CIにバジェットチェックを加える。** スナップショットは調査に便利ですが、それだけではリグレッションを防げません。ビルド出力に基づくルートごとのFirst Load JSの簡単なチェックがあれば、次に偶然入る静的importをマージ前に捉えられます。

```yaml
# .github/workflows/bundle-budget.yml (抜粋)
- run: npm run build
- run: node scripts/check-first-load-budget.mjs
```

スクリプトはビルド出力を読み、設定したバジェットを超えたルートで失敗します。数値の決め方は自由ですが、しきい値をリポジトリ内に置くことが重要です。

**根本原因は可能な限り手で直す。** 共有する型を別ファイルに切り出し、クライアントコードではbarrel経由のimportを直接importに置き換え、レジストリはエントリごとに遅延させます。小さな変更ですが、同じ問題の再発を防げます。

## まとめ

- `lazy()` や `next/dynamic` の呼び出しがあっても、遅延されている証拠にはなりません。モジュールグラフで確認してください。
- スナップショット比較により、バンドルの増加が曖昧な感覚ではなく計測できる出来事になります。今からベースラインを保存しましょう。
- Optimizer Skillは、誰も監査していないコードベースの最初の一巡には妥当ですが、提案ごとに挙動変化の人間によるレビューが必要です。
- 改善を維持するため、CIでFirst Loadのバジェットを強制します。

App Routerに移行してからプロファイリングしていないサイトなら、`next analyze` に1時間かければ何か見つかる可能性が高いです。
