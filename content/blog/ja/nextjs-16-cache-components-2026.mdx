## 暗黙のfetchキャッシュから明示的なモデルへ

Next.js 16は、Partial Pre-Rendering（PPR）と明示的な `use cache` ディレクティブを組み合わせた新しいキャッシュモデル「Cache Components」を搭載しました。これまでのフレームワークのデフォルト動作 — `fetch()` 呼び出しを自動的かつヒューリスティックにキャッシュする方式 — を置き換え、コンポーネントや関数単位でソースコード上に明示的にキャッシュを宣言するモデルへと移行します。

この一文だけでは、実務にどれほどの変化をもたらすか伝わりにくいかもしれません。従来のモデルでは、あるページが静的生成されるのか、キャッシュされるのか、完全に動的になるのかは、どのデータ取得APIをどの順序で呼んだかに依存していました。ドキュメントには丁寧なルール説明がありましたが、実際には多くのチームが予期しない再検証（revalidation）に遭遇し、後から原因を追ってそのルールを学ぶことになっていました。Cache Componentsはこの境界を明示的かつローカルなものにします。ある関数がキャッシュされるのは、そう宣言されているからであり、暗黙のルール群のリントが「そうすべき」と判断した結果ではありません。

## use cacheが実際にすること

このディレクティブは、ファイルの先頭・関数・コンポーネントのいずれにも付けられます。付けられた対象はキャッシュ可能な単位となり、Next.jsはその出力を入力値をキーとして保存・再利用できます。

```tsx
// app/lib/pricing.ts
async function getPricingTiers(region: string) {
  "use cache";

  const res = await fetch(`https://api.example.com/pricing?region=${region}`);
  return res.json();
}

export default getPricingTiers;
```

一方、意図的に動的なままにしておきたいServer Component — 例えばCookieを読んで表示内容を決めるようなもの — と比較してみます。

```tsx
// app/dashboard/account-banner.tsx
import { cookies } from "next/headers";

export default async function AccountBanner() {
  const store = await cookies();
  const plan = store.get("plan")?.value ?? "free";

  return <Banner plan={plan} />;
}
```

`AccountBanner` は `cookies()` を読むため、キャッシュ可能な境界の外に置かれます。Partial Pre-Renderingがあれば、これは問題になりません。ナビゲーションやフッター、マーケティング用のセクションといったページの残りの部分は、キャッシュされたシェルからそのまま配信され、`AccountBanner` だけが `Suspense` 境界の中でリクエストごとにレンダリングされます。1つのコンポーネントがライブデータを必要としたからといってルート全体が完全動的レンダリングに落ちるのではなく、ほとんど静的なHTMLの中に動的な「穴」が1つ空く、という形になります。

## マーケティング＋アプリ型サイトにとっての意味

Webhaniが手がけるサイトの多くは、「完全に静的なマーケティングサイト」と「完全に動的なWebアプリ」の中間に位置します。個人化された要素をいくつか持つ公開サイトや、ほとんどが静的な設定画面を持つアプリのシェルなどです。従来のfetchキャッシュモデルでは、レイアウト内の1つの動的なAPI呼び出しが、実際のデータ依存関係が必要とする以上にルートの多くを動的レンダリングへ押しやることがありました。Cache Componentsはこの影響範囲を狭めます。本当にリクエストごとに変わる部分だけがそのように振る舞えばよくなります。

具体的には次のような効果があります。

- **ユーザーごとに変わらないコンテンツのナビゲーションが高速化する**：`use cache` を付けた料金ページやブログ一覧、マーケティングセクションは、同じページ内のサインイン済みバナーが何を必要としていようと、キャッシュから配信されます。
- **コードレビューで指し示せるキャッシュ境界ができる**：「このルートはなぜ動的なのか」は、以前はfetchグラフ全体を推論する必要がありました。今では「`use cache` がなく、かつ動的なAPIを呼んでいるコンポーネント」を探せば答えが出ます。
- **チャンク分割の制御と組み合わせられる**：Next.js 16はコードの分割・共有方法を調整できる実験的なチャンク制御機能も搭載しています。キャッシュ境界と動的境界が明示的になったことで、ルート境界ではなく実際のレンダリング境界に合わせてチャンクのサイズを決められるようになります。

## 移行するチームに伝えたいこと

実際のNext.js 15のコードベースにこのモデルを当てはめて見えてきた実務上の注意点です。

1. **まず意図しない動的化を洗い出す**：`use cache` を追加する前に、必要もないのに `cookies()` や `headers()` を呼んでいたり、`searchParams` を読んでいたりするコンポーネントを探します。多くはコピペの名残であり、本当の要件ではありません。これを取り除くだけで、キャッシュに手を付ける前に動的な範囲を縮小できます。
2. **ページ単位ではなく関数単位でキャッシュする**：`getPricingTiers` のような共有データ取得関数に1つ `use cache` を付ければ、それをimportするすべてのページが恩恵を受けます。ルート全体にマークを付けようとするより、これの方が良いキャッシュの単位になりがちです。
3. **キャッシュキーを意識的に扱う**：キャッシュが明示的になった今こそ、キャッシュされた出力を何が変化させるのか — リージョン、ロケール、フィーチャーフラグなど — も同じくらい明示的に扱うべきです。キャッシュされる関数内で暗黙のコンテキストから読み取るのではなく、関数の引数として渡すようにします。

## Webhaniの見解

Cache Componentsは、仕組みを明示的にすることで最初にディレクティブを書く手間が少し増える代わりに、後のデバッグ時間を大きく取り戻せる典型例です。従来の自動fetchキャッシュは、うまく機能している間は便利でしたが、あるルートが予期せず完全動的になった（あるいは、そうすべきでないのにキャッシュされ続けた）瞬間、原因を追うにはNext.jsの内部ルールを再構築する必要がありました。明示的な `use cache` 境界があれば、答えは常に今見ているファイルの中にあります。

すでにNext.js 16を運用しているチームへの推奨は、この移行を機械的な置換作業としてではなく、監査の機会として捉えることです。価値は `use cache` をあちこちに振りかけることではなく、実際のデータ要件以上にルートの中へ動的レンダリングが漏れ出していた箇所を見つけるためにこの作業を使うことにあります。
