10月27日、Next.jsチームは2026年11月3日(火)に定期セキュリティリリースを行うと予告しました。告知によると、対象はMedium深刻度の脆弱性7件で、詳細なアドバイザリはリリースと同時に公開されます。事前に開示されるのはそれだけです。事前告知の目的は、詳細が公開される前にチームが準備する時間を与えることにあります。

本番でNext.jsを運用しているなら、フレームワークのパッチを出荷するまでにどのくらいかかるかを見直すよい機会です。9月以降のNext.jsブログを見ると、パッチリリースは頻繁です。

- **9月22日:** 上流の重大な問題に対する臨時アップデート(16.3.6と15.5.26)。
- **9月30日:** 9月の定期セキュリティリリース。
- **10月14日:** 上流依存関係のCritical 2件とHigh 1件の脆弱性に対する臨時アップデート。
- **11月3日:** 10月27日に告知された11月の定期リリース。

チームは7月に正式なセキュリティリリースプロセスへ移行し、各リリースの前に告知を出しています。計画は立てやすくなりましたが、パッチ対応がときどき起きる出来事ではなく、Next.jsアプリの運用に恒常的に含まれる作業になったとも言えます。

## 「準備ができている」状態とは

目標は、11月3日にパッチを当てる作業が、1日がかりの調査ではなく、通常のPull Requestで済むことです。それを左右する要素を挙げます。

### 1. 実際に動いているバージョンを把握する

`package.json` の記述ではなく、実際にインストールされているバージョンから始めます。

```bash
npm ls next react react-dom
```

複数のアプリを管理しているなら、すべてで実行して結果を1か所にまとめます。よくある失敗は、リリース当日になって、忘れられていた社内ツールが2マイナーバージョン遅れで、修正が入らないブランチに固定されていたと気づくことです。

どのリリースラインを使っているかも確認します。Next.js 15系はバックポート(9月の15.5.26)を受けてきましたが、サポート終了したラインは受けなくなります。思い込まず公式のサポートポリシーを確認し、緊急パッチが必要になる前に、現行ライン(ブログ上では現在16.4)への更新を計画してください。

### 2. アップグレードを1行の変更にする

パッチ更新はバージョン番号だけに触れるようにします。パッチ更新を許可する範囲指定を使い、再現性はlockfileに任せます。

```json
{
  "dependencies": {
    "next": "~16.4.0"
  }
}
```

`~` なら、次のパッチバージョンへの更新はlockfileの更新で済みます。RenovateやDependabotなどの自動化ツールでPull Requestを自動作成でき、セキュリティ更新を高優先にして、フレームワーク関連パッケージ(`next`、`eslint-config-next`、Reactパッケージ)をグループ化しておきます。

### 3. 火曜日に信頼できるテストを用意する

セキュリティパッチは素早くデプロイできて初めて価値があり、それはCIへの信頼にかかっています。最低限、次を用意します。

- 型エラーとlintエラーでビルドが失敗すること。
- 重要なページのスモークテスト: トップページ、ログイン、フォーム送信、動的ルート1つ。
- セキュリティ修正はリクエスト処理に触れることが多いため、middlewareとroute handlerが想定どおり応答するかの確認。

網羅的なカバレッジは不要です。パイプラインが成功すれば同日に出荷できる、という程度の確からしさがあれば十分です。

### 4. デプロイ経路とロールバックを把握する

パッチが本番に届く手順と、戻す手順をリポジトリに書いておきます。即時ロールバックができるプラットフォームならそう書き、コンテナ運用なら最後に正常だったイメージタグを記録します。これを調べる時期は、障害対応の最中ではありません。

セルフホスト構成では、Node.js側も確認してください。Node 20はEOLを過ぎ、セキュリティ修正が提供されません。サポート外のランタイムの上でNext.jsにパッチを当てても、問題の一部しか解決しません。移行手順はNode 20のランブックで取り上げています。

### 5. 担当者を決める

リリース当日にNext.jsのブログとセキュリティアドバイザリを見る担当者を1人、Pull Requestを承認できるレビュアーを1人決めておきます。リリース告知はスプリントの予定に関係なく届きます。担当者のいない火曜日のリリースは、木曜日のデプロイになりがちです。

## リリース当日とその後

アドバイザリが公開されたら次のように進めます。

1. **自分たちの構成に照らしてアドバイザリを読む。** Medium深刻度の問題は、特定のmiddlewareパターン、画像最適化の設定、Server Actionsなど、特定機能に依存することが多いです。影響の有無は調べつつ、「おそらく影響なし」を待つ理由にせず、更新はします。
2. **まずpreview環境を更新し**、スモークテストを実行してから昇格させます。
3. **推移的依存関係も確認する。** 10月14日のアップデートは上流の依存関係の脆弱性に対するものでした。修正は `next` 経由で届いても、問題は別の場所にあるかもしれません。更新後に `npm audit` を実行して、残っているものを確認します。
4. **対応を記録する。** 更新前後のバージョンと日付を、changelogやチケットに短く残します。顧客や監査人がいずれ尋ねる質問への答えになります。

## 触れておくべきトレードオフ

完全固定(`"next": "16.4.0"`)は最も予測しやすいビルドになりますが、パッチごとに手作業の編集が必要になり、経験上パッチが後回しになります。マイナーで浮動させる(`^16.4.0`)と修正は自動で入りますが、レビューしていない挙動の変更も入りえます。チルダ範囲はその折衷で、パッチリリースだけを許可し、いつ反映するかはlockfileとCIが決めます。

これは11月3日に限った話ではありません。次のアドバイザリは、こちらでは制御できないスケジュールで届きます。落ち着いて対応できるチームは、急ぎでないときにパイプラインを整えたチームです。アップグレード経路について第三者の目が必要でしたら、短い期間のご支援で対応でき、費用対効果も説明しやすい内容です。
