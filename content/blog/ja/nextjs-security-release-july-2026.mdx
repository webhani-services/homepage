## 1回のリリースに5種類の脆弱性

2026年7月20日前後、Next.jsが複数の脆弱性クラスをまとめて修正するセキュリティリリースを公開しました。内訳は、DoS（サービス拒否）、認可バイパス、XSS（クロスサイトスクリプティング）、SSRF（サーバーサイドリクエストフォージェリ）、そしてCacheポイズニングです。影響範囲はServer Components、App Router、Middleware、Proxyレイヤーにまたがっています。

このリリースで注目すべきなのは、個々のCVEそのものよりも「パターン」です。数年前まで「Next.jsのセキュリティバグ」といえば、特定のHelper関数のXSSやHeaderの設定ミスといった、比較的狭い範囲の話でした。しかし今のNext.jsは、リクエストごとにサーバー側でかなりの処理を実行します。Server Componentsはサーバー上でレンダリングされ、MiddlewareはFluid Compute的なPlatform上でNode.js相当のコードを実行でき、Proxyレイヤーがルーティングの判断の手前に立ちます。これらすべてが、単なるレンダリングパイプラインではなく、Attack Surfaceの一部になっているということです。

本番でNext.jsを運用しているチームであれば、たとえ該当バージョンをピンポイントで使っていなくても、このリリースには目を通す価値があります。以下、それぞれの脆弱性クラスが実務上何を意味するか、そして何をすべきかを整理します。

## なぜ1回のリリースに5種類ものバグが出るのか

それぞれの脆弱性クラスは、App Routerのサーバーサイド機能が悪用されうる特定の経路に対応しています。ラベルだけでなく仕組みを理解することが、自分たちのプロジェクトのリスクを判断する助けになります。

### DoS（サービス拒否）

Server ComponentsやMiddlewareは、リクエストごとにData FetchingやStreaming、Header解析、Cache Key計算といった実際の計算を行います。このレイヤーのDoSバグは、大量のトラフィックというより、細工されたリクエスト（巨大なHeader、極端なRoute Param、Redirectループなど）が1リクエストあたり不釣り合いなCPU・Memory消費を引き起こす、というケースが典型です。この違いは運用上重要で、WAFのRate Limiterだけでは検知できません。攻撃者に必要なのはトラフィック量ではなく、特定の形をしたリクエストを地道に繰り返すことだからです。

### 認可バイパス（Access Control Bypass）

このクラスがもっとも警戒すべきものです。多くのチームがMiddlewareに認可チェックを置いています。Session Cookieを確認し、未認証ユーザーを`/dashboard`から弾く、といった実装です。もしMiddlewareのMatching・Rewrite・ProxyのRequest処理とRoute解決の相互作用にバイパスが存在すると、攻撃者は「想定していたチェックを通らずに」保護されたServer Componentへ到達するURLの形を見つけられる可能性があります。これは理論上の話ではありません。「認可はMiddlewareにある」というのは、App Routerのコードベースで非常によく見るパターンであり、だからこそこのバグクラスの被害範囲は大きくなりがちです。

### XSS

Server Componentsはサーバー上でレンダリングされますが、最終的にはBrowserに渡るHTMLになります。このカテゴリのバグは典型的には、レンダリングパイプラインでEscapeされるべき入力がEscapeされなかった、というケースです。Query ParamがTitleタグにそのまま反映される、エラーメッセージがPageシェルにそのままレンダリングされる、といった具合です。挙動としては古典的なReflected XSSと同じで、それが新しいレンダリング経路から発生している点が違います。

### SSRF

MiddlewareやServer Componentsは、自社API・サードパーティサービス・内部Microserviceなどへの外向きリクエストを日常的に行います。この文脈でのSSRFは、攻撃者がサーバーがFetchするURLに影響を与えられる、つまり外部から到達できるはずのないInternal専用Endpoint（Metadataサービス、内部Admin画面など）に到達しうる、ということです。「ただのWebアプリ」を社内Infrastructureへのピボットポイントに変えてしまう、まさにこの種のバグです。

### Cacheポイズニング

Next.jsは複数のレイヤーでCacheを持ちます。Data Cache、Full Route Cache、Response Headerをキーにしたエッジ（CDN）Cacheなどです。Cacheポイズニングバグは、攻撃者が制御したリクエストによって、悪意ある、あるいは特定ユーザー固有のResponseがCacheに保存され、それが無関係な他のユーザーに配信されてしまう、という問題です。これは静かに広がるタイプの問題で、一度Poisoningされたエントリがキャッシュされてしまえば、それを消したり期限切れになるまで、能動的な攻撃トラフィックがなくても悪いコンテンツを配り続けます。

## Middlewareパターンの例 — Middlewareだけをゲートにしない

認可バイパスのバグから得られる構造的な教訓は、Middlewareは高速なRedirectを行うのには適した場所だが、認可判断の「唯一の場所」にしてはいけない、ということです。MiddlewareはUXの一部として扱い、実際のチェックはData Accessのレイヤーで改めて行います。

```ts
// middleware.ts — あくまで高速Redirectのみ。Security Boundaryではない
import { NextResponse, type NextRequest } from "next/server";

export function middleware(request: NextRequest) {
  const hasSession = request.cookies.has("session_token");

  if (!hasSession && request.nextUrl.pathname.startsWith("/dashboard")) {
    const loginUrl = new URL("/login", request.url);
    loginUrl.searchParams.set("from", request.nextUrl.pathname);
    return NextResponse.redirect(loginUrl);
  }

  return NextResponse.next();
}

export const config = {
  matcher: ["/dashboard/:path*"],
};
```

```ts
// app/dashboard/page.tsx — Data Layerで改めて確認する本当のゲート
import { redirect } from "next/navigation";
import { getSessionFromCookies } from "@/lib/auth";
import { getDashboardData } from "@/lib/data";

export default async function DashboardPage() {
  const session = await getSessionFromCookies();
  if (!session) redirect("/login");

  // どのRouting/Rewriteの経路を通ってこのComponentに到達したかに関わらず、
  // ここで改めて認可を検証する。
  const data = await getDashboardData(session.userId);
  return <DashboardView data={data} />;
}
```

このコード自体が万能というわけではありません。重要なのは原則です。Middleware・Proxy・Rewriteといったルーティング層のチェックだけを、認可のような重大な判断の唯一のEnforcement Pointにしてはいけません。将来Middleware Matchingを迂回できるバグが出ても、Data Layerが最後の砦になります。

同じDefense-in-Depthの発想はCacheにも当てはまります。ResponseがUser・認証状態・Localeによって変わるなら、Cache KeyはPathだけで構成せず、それらの次元を明示的に含めるべきです。`Cache-Control`もデフォルトに頼らず、意図的に設定します。

```ts
// app/api/profile/route.ts — 明示的で狭いCache挙動
export async function GET(request: Request) {
  const data = await getProfileData(request);

  return Response.json(data, {
    headers: {
      // Private / User固有のデータは共有Cacheの対象にしない
      "Cache-Control": "private, no-store",
    },
  });
}
```

## 実務チェックリスト

現在該当バージョンかどうかに関わらず、Next.jsを本番運用するチームに推奨する内容です。

1. **Major Versionだけでなく、セキュリティリリースを追う**。Next.jsのリリースノートとセキュリティAdvisoryを個別にWatchする。Patchリリースはメジャーバージョンの間に挟まって出るため、機能アナウンスだけ見ていると見落としがちです。
2. **意図的にPinし、更新する**。本番では`next`をLoose Semver Rangeではなく厳密なVersionでPinし、セキュリティPatchは通常の依存関係更新とは別の、迅速なUpdate Laneとして扱います。
3. **認可をMiddleware単体に依存させない**。Routing Layerだけでなく、Data Accessの時点で認証・認可を再確認します。MiddlewareはUXレベルのRedirect用、本当のゲートはDataのそばに置きます。
4. **Cache Keyの衛生状態を監査する**。User・Session・Locale・Feature Flagによって変わるResponseは、必ずそれらの次元をCache Keyに含めるか、`private`/`no-store`を指定します。Frameworkのデフォルトが自分たちのデータの機密性と一致しているとは限りません。
5. **サーバー側からの外向きRequestを制約する**。MiddlewareやServer ComponentsがUser入力に基づいて外部HTTPを叩くなら、User制御のURL・Hostnameをそのまま通さず、宛先をValidate・Allowlistします。
6. **CI/CDにFast-Patch Laneを用意する**。セキュリティリリースは通常のSprint単位の依存関係更新サイクルを待つべきではありません。Smoke TestとCanary Deployだけで、1日程度でFrameworkのセキュリティPatchを本番に出せる軽量な経路を用意します。
7. **Patchを適用するだけでなくTestする**。Frameworkのセキュリティ修正は、Matcherの挙動やRedirect処理、Cacheのデフォルトなど、Edge Caseの挙動を変えることがあります。本番昇格前に、Route・認証系のTest SuiteをPatch後のVersionで実行します。

## まとめ

このリリースで興味深いのは、個別のCVEそのものよりも、Next.jsのサーバーサイドの守備範囲が広がりすぎて、1回のPatchでDoS・認可・XSS・SSRF・Cacheポイズニングを同時にカバーしなければならなくなっている、という点です。それがApp Routerの機能性の代償です。Server Components・Middleware・Proxyはエッジで大きな力を与えてくれますが、同時に、DatabaseやAuth Libraryのセキュリティリリースノートと同じくらいの注意を、Frameworkのリリースノートにも払う必要がある、ということでもあります。

Frameworkのアップデート、特にセキュリティ関連のものは、本番Criticalな依存関係として扱い、上記のDefense-in-Depthの習慣を組み込んでおくことで、Framework側の1つのバグがアプリケーション全体のSingle Point of Failureにならないようにしましょう。
