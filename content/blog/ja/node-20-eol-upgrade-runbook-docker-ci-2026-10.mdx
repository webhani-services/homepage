Node.jsの10月のセキュリティリリースは、22.x、24.x、26.xの各ラインが対象でした。Node 20は含まれていません。プロジェクトのアドバイザリには、EOLのバージョンもこれらの問題の影響を受けるため、サポート対象のリリースへ更新するよう記載されています。また、Vercelは2026年10月1日付でNode.js 20を非推奨にしたと案内しています。Node 20がまだ残っているなら、移行する理由は独立して2つあります。修正が提供されないこと、そしてホスティング側が提供を終了することです。

この記事は機能紹介ではなくランブックです。Nodeのアップグレードで難しいのはコードそのものよりも、バージョンが固定されているすべての場所を見つけることです。

## ステップ1: Node 20がどこにあるかを棚卸しする

バージョン番号は `package.json` 以外にも数多くの場所に潜んでいます。次のコマンドで洗い出します。

```bash
# Dockerfileとcomposeファイル
grep -RInE "node:(20|lts)|NODE_VERSION" --include="Dockerfile*" --include="*.yml" --include="*.yaml" .

# バージョン管理ファイルとenginesフィールド
cat .nvmrc .node-version .tool-versions 2>/dev/null
grep -n '"engines"' -A3 package.json

# CIワークフロー
grep -RIn "node-version" .github/workflows/

# サーバーレス・ホスティング設定
grep -RInE "nodejs20|runtime" vercel.json vercel.ts serverless.yml template.yaml 2>/dev/null
```

特に注意したい落とし穴が2つあります。`node:lts` や `node:lts-alpine` のようなタグは時間とともに指す先が変わるため、ビルド時はNode 20だったイメージが、再ビルドすると別のバージョンになることがあります。また、LambdaなどのFunctionランタイム文字列(`nodejs20.x` など)は独立した固定であり、ロックファイルからは見つかりません。

## ステップ2: 移行先のラインを決める

アドバイザリに記載されたサポート対象の22、24、26から選びます。多くのアプリケーションチームにとって無難なのは、Active LTSに入っている最新のラインです。Node 26は、プロジェクトが採用した年1回メジャーリリースのモデルにより今月LTSに入る予定です(この変更については以前の記事で扱いました)。依存パッケージが保守的で急ぐ場合は、22や24のほうが飛び幅は小さくなります。どれを選んでも、1か所に書き、他はすべてそこから読むようにします。

信頼できる唯一の情報源(single source of truth)を置くと、将来のずれの大半がなくなります。

```bash
# .nvmrcはnvm、fnm、actions/setup-nodeが読み取る
echo "24" > .nvmrc
```

```yaml
# .github/workflows/ci.yml
- uses: actions/setup-node@v4
  with:
    node-version-file: ".nvmrc"
```

```dockerfile
# Dockerfile: メジャーを固定し、--pullで再ビルドしてパッチを取り込む
ARG NODE_VERSION=24
FROM node:${NODE_VERSION}-alpine AS base
```

バージョンをビルド引数にしておくと、Dockerfileを編集せずにCIで別のメジャーを試せます。

## ステップ3: 本番より先に壊れる箇所を見つける

ブランチでアップグレードし、ツールチェーンに問題点を教えてもらいます。

1. **ゼロから再インストールする。** `node_modules` を削除し、ネイティブモジュールを再ビルドします。コンパイル済みアドオンを含むパッケージが最も失敗しやすいため、利用中のバージョンが新しいNodeのABI向けバイナリを配布しているか確認します。
2. **テストスイート全体を2回実行する。** 旧Nodeと新Nodeでそれぞれ実行し、既存の失敗と新規の失敗を切り分けます。
3. **非推奨警告を読む。** `node --trace-deprecation` でアプリを起動し、表示されたものを今のうちに直します。将来のメジャーで警告がエラーに変わる前に対処できます。
4. **影響する組み込みの挙動変更を確認する。** fetchやURLの扱い、テストランナーの既定動作など、飛ばすメジャーごとのリリースノートを読みます。20から24への移行は、2つのメジャー分の変更をまたぎます。

```bash
# 新しいバイナリが必要なネイティブアドオンの簡易確認
npm ls --all 2>/dev/null | grep -iE "node-gyp|bindings|prebuild" | head
npm rebuild
```

## ステップ4: 戻せる形で展開する

ランタイムの変更も、他の本番変更と同様に扱います。

- ステージングへデプロイし、E2Eテストと代表的な負荷テストを実行します。メモリプロファイルと起動時間はどちらも変わることがあります。
- プラットフォームが対応していれば、まず一部のトラフィックにだけ展開し、エラー率とレイテンシを比較します。
- 以前のイメージタグを残しておき、ロールバックを再ビルドではなく再デプロイで済ませます。

## ステップ5: 再発を防ぐ

- `.nvmrc`、Dockerfile、`engines` が食い違ったらCIが失敗するチェックを追加します。
- ベースイメージと `setup-node` アクションの自動更新を有効にし、新しいパッチリリースがプルリクエストとして届くようにします。
- Nodeのリリーススケジュールをチームのカレンダーに入れます。各ラインの終了日は事前にわかっており、半年前のリマインダーがあれば、緊急対応を通常のチケットにできます。

## webhaniの推奨

まだNode 20を使っているなら、今週中に棚卸しを行ってください。短時間で終わり、作業の実際の規模がわかります。移行は「いつか」ではなく次のスプリントに組み込みます。パッチの当たらないランタイムは、ただ古いだけの状態では済まないからです。Node 20が対象外となった同じリリースサイクルで、プロジェクトはBrotliのメモリ安全性の不具合や、証明書の同一性に関する複数の問題を、サポート対象のラインで修正しました。それらの修正はNode 20には届きません。

多くのWebアプリケーションでは、アップグレード自体はレビューサイクルをまたいで1〜2日分の作業です。高くつくのは、インシデントの後に急かされて行う場合です。
