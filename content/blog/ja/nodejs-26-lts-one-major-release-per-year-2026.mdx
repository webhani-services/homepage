今月のNode.jsには注目点が2つあります。1つ目は、プロジェクトのリリーススケジュールによると、Node.js 26が2026年10月28日にActive LTSへ移行し、セキュリティパッチは2029年4月30日まで提供される予定であることです。2つ目は、[InfoQの報道](https://www.infoq.com/news/2026/06/nodejs-release-changes/)にあるとおり、Node 27から年2回だったメジャーリリースが年1回になることです。Node 26は旧ペースで出る最後のメジャーリリースになります。

LTSの日付はカレンダー上の予定にすぎません。計画の立て方を変えるべきなのは、スケジュール変更のほうです。

## 新スケジュールの概要

新しいモデルでは、メジャーバージョンが毎年4月に1つ出て、翌10月にLTSへ昇格します。これまでのように、LTSにならない奇数バージョンのCurrentリリースはなくなります。

実務上は次のようになります。

- アップグレードの判断が年2回から年1回になる。
- 4月に新メジャー、10月に本番利用できるLTSという予測しやすい流れになる。
- すべてのメジャーがLTSに到達する想定なので、隔番でスキップする必要がなくなる。

正確な日付とサポート期間は、ロードマップに書き込む前にnodejs.orgで確認してください。スケジュールはプロジェクトが発表するもので、調整される可能性があります。

## アプリケーション開発チームにとっての利点

年2回のペースでは、「本番では偶数バージョンだけを使う」という経験則が広まっていました。奇数バージョンは寿命が短く、LTSにならなかったからです。リリースノートの半分は頭の中で読み飛ばす、という運用にもなっていました。

年1回になれば、この経験則は不要です。10月にLTSになったバージョンを採用し、前のバージョンとはおよそ1年間重なるサポート期間を持つ、という単純な対応になります。

トレードオフは、1回のメジャーに含まれる変更が大きくなることです。1年分のV8更新、依存関係の更新、非推奨化が1つのリリースにまとまります。摩擦が起きやすいのは、ネイティブアドオンとビルドツールチェーンです。

## Node 26へのアップグレードチェックリスト

10月28日を待たず、今のうちにテストを始めてください。Node 26はすでに利用できるので、手元のテストスイートを今日から流せます。

1. **ランタイムを明示的に固定する。** `.nvmrc` や `engines` フィールドで、ローカル・CI・本番のバージョンを揃えます。
2. **CIマトリクスにNode 26を追加する。** 現行のLTSと並べ、最初は失敗してもブロックしない設定にします。
3. **ネイティブ依存関係を確認する。** インストール時にコンパイルされるもの(画像処理、データベースドライバ、暗号関連のバインディングなど)は、再ビルドしてテストします。
4. **非推奨APIの一覧を読む。** 自分のコードや依存パッケージが使うAPIを確認し、`--throw-deprecation` を付けてテストを実行すると、警告を失敗に変えられます。

```bash
node --throw-deprecation --test
```

5. **コンテナのベースイメージを更新する。** ブランチ上で更新し、イメージサイズと起動時間が悪化していないことを確認します。

現行LTSと次のLTSをテストする、GitHub Actionsの最小構成のマトリクスは次のとおりです。

```yaml
name: test
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        node: [24, 26]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
          cache: npm
      - run: npm ci
      - run: npm test
```

ここでは `fail-fast: false` が重要です。別のジョブが失敗してもNode 26の結果を確認できるので、非互換が早期に見つかり、後で積み上がることを防げます。

## フレームワークとホスティング環境

アプリケーションフレームワークやホスティング事業者は、LTSへの昇格後まもなく新バージョンに対応するのが普通ですが、同日とは限りません。バージョンを上げる前に、次の点を確認してください。

- 利用中のフレームワークのサポート対象バージョン表にNode 26が載っているか。
- ホスティング環境やサーバーレスのランタイムが対応しているか。デフォルトバージョンが決まっていて、明示的に選択する必要がある環境もあります。
- ロックファイルで解決されるパッケージの中に、`engines` の範囲がNode 26を除外しているものがないか。

私たちの経験では、問題の原因は自分のコードより、`engines` が厳格に指定された間接依存パッケージであることが多いです。

## webhaniの推奨

- 今すぐCIでNode 26を、失敗を許容するジョブとして動かす。
- 本番への移行は、Node 26がLTSに入った当日ではなく、その数週間後に計画する。エコシステムのパッケージが追いつくのを待ちます。
- 寿命が近いバージョンを使っている場合、Node 26への移行は中継ぎではなく置き換え先として扱う。
- 新しいペースをチームのカレンダーに入れる。4月は評価、10月は採用です。
- 移行中は1つ前のLTSとの併走期間を残し、ロールバックできるようにする。

年1回のモデルはアップグレードの日程を立てやすくしますが、変更は集中します。次のバージョンをCIで常にテストしておくという小さな習慣が、年1回のアップグレードを大規模プロジェクトにしないための鍵です。
