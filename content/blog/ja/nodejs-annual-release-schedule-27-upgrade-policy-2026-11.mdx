Node.js プロジェクトは、Node.js 27 から新しいリリーススケジュールに移り、メジャーリリースを年1回にすると発表しました。Node.js 26 は、年2回のメジャーリリースという従来の体制では最後のラインになります。プロジェクト自身がこのスケジュールを暫定的なもので変更の可能性があるとしているため、以下は契約ではなく現時点の計画として読んでください。

多くのチームには「最新の LTS に乗り、次の LTS が出たら上げる」という経験則があります。この考え方は今後も通用しますが、前提がいくつか変わります。ここでは、新しいスケジュールの内容と、自社の方針で見直すべき点をまとめます。

## 新スケジュールの内容

プロジェクトの発表によると、次のとおりです。

- **メジャーリリースは年1回**、4月に出て、10月に LTS へ昇格します。
- **バージョン番号は、最初の Current リリースの暦年に揃います。** Node.js 27.0.0 は 2027 年、28.0.0 は 2028 年というように続きます。
- **約6か月の Alpha フェーズ**（10月〜3月）が Current の前に入ります。Alpha 中も semver-major の変更は許され、Node.js 27 の Alpha チャンネルは 2026 年 10 月に開きます。
- **Current** は約6か月（4月〜10月）で、安定化のための期間です。
- **LTS** は30か月です。Node.js 27 の計画は、2027 年 10 月に LTS 開始、2030 年 4 月に EOL です。

実務的には、追いかけるラインが年2本から1本になり、「奇数バージョンは非 LTS」という区別がなくなり、番号を見れば初リリースの年が分かる、ということです。

## 変わらないこと

本番ワークロードを置くべき場所は、これまでどおり LTS です。リリースの翌年前半はそのラインは Current であり、本番向けではありません。LTS の期間は長いため、2つの LTS ラインが同時にサポートされる期間がしばしばあり、移行には十分な重なりが取れます。

すでに EOL に達したラインを使っているなら、この話はまだ関係ありません。まずそちらを解消してください。その場合の手順は、[Node 20 EOL のアップグレード Runbook](/blog/node-20-eol-upgrade-runbook-docker-ci-2026-10) にまとめています。

## 方針で見直すポイント

### 1. アップグレード周期を LTS の日付で定義する

「新しいバージョンが出たら上げる」ではなく、カレンダーに結びついたルールとして書き下します。たとえば「新しい LTS は LTS 入りした四半期に評価し、前の LTS がメンテナンス専用に入る前に移行を終える」といった形です。年1回のリリースなら、場当たり的な対応ではなく、予測できる年次のプロジェクトにできます。

### 2. バージョンの固定箇所を一つにする

ローカル、CI、本番の間でずれが生じる原因は、たいていバージョン文字列があちこちにあることです。真実の源を一つ決め、残りはそこから導出します。

```text
# .nvmrc
26
```

```json
{
  "engines": {
    "node": ">=26 <27"
  }
}
```

```dockerfile
ARG NODE_VERSION=26
FROM node:${NODE_VERSION}-slim AS base
```

```yaml
# .github/workflows/ci.yml (抜粋)
- uses: actions/setup-node@v4
  with:
    node-version-file: ".nvmrc"
```

`node-version-file` を使えば、バージョンの更新は1行の変更になり、CI もローカル開発も同じ値を参照します。固定するメジャーは、実際に運用しているラインに合わせてください。

### 3. 次のラインは早めに試す。ただしブロッキングにはしない

Alpha フェーズは、リリースが切られる前に下流のプロジェクトが問題を見つけられるように用意されています。コミットのたびにテストスイート全体を回す必要はありません。失敗を許容するスケジュール実行のジョブで、重要な不具合は十分に拾えます。

```yaml
name: node-next
on:
  schedule:
    - cron: "0 3 * * 1"   # 週1回
jobs:
  test-next:
    runs-on: ubuntu-latest
    continue-on-error: true
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: "27.0.0-alpha"   # プロジェクトが公開する識別子に合わせてください
      - run: npm ci
      - run: npm test
```

プレリリースビルドの正確なバージョン文字列は、プロジェクトの公開方法によります。上のプレースホルダーに頼る前に、ダウンロードページや `nvm ls-remote` で確認してください。失敗はブロッカーではなく、追跡すべき情報として扱います。

### 4. ネイティブアドオンとビルドツールを見直す

メジャーアップグレードのコストは、自社コードよりも、新しい ABI 向けのビルド済みバイナリが必要なネイティブモジュール、lockfile の変動、ベースイメージにかかることが多いです。年1回の周期なら、こうしたコストは年に一度まとめて処理できます。ネイティブコードをコンパイルする依存を洗い出し、新しいラインのバイナリが公開されているかを、日程を決める前に確認しておきましょう。

### 5. Docker とランタイムイメージを揃える

イメージタグには `latest` ではなくメジャーを固定し、ライン内のパッチを取り込めるよう定期的に再ビルドします。セキュリティ修正はポイントリリースで入ります。メジャーを間違えているよりも、メジャーは合っているがパッチが数か月遅れている状態のほうが実際にはよく見かけます。

## トレードオフ

年1回にするとチャーンは減りますが、変更は集中します。各メジャーは6か月ではなく1年分の semver-major 変更を抱えるため、個々のアップグレードはやや大きくなる可能性があります。Alpha フェーズはその対策ですが、自社の誰かが実際に試して初めて効果が出ます。

暦年に合わせたバージョン番号も、小さな読みやすさの改善です。「Node 28」と聞けば初リリースの時期がおおよそ分かるため、ランタイムの古さについての監査上の会話が少し楽になります。

## webhani の推奨

多くのクライアント案件では、次のようにします。

1. LTS のみを使い、新しい LTS を採用する期限の日付を明文化する。
2. バージョン固定（`.nvmrc` など）を一箇所にまとめ、CI と Docker をそこから駆動する。
3. 次のラインの Alpha ビルドが出たら、週次のノンブロッキングジョブを追加する。
4. リリースごとに反応するのではなく、新しいラインが LTS に入る時期に合わせて、年1回のアップグレード枠を確保する。

どれも Node.js 27 を待つ必要はありません。今すぐ始める価値があります。同じ構造が、現在のアップグレードのコストも下げてくれるからです。
