Node.jsプロジェクトは10月21日にセキュリティリリース(v26.12.1、v24.22.1、v22.23.4)を公開しました。修正されたCVEは10件で、4件が高深刻度です。全文に目を通す時間がなければ、一覧よりも「パターン」を押さえるほうが役に立ちます。今回の修正の多くはメモリ破壊ではなく、同じ文字列に対して2つのコードが異なる意味を与えてしまう問題だからです。

## 高深刻度の修正

公式アドバイザリによると、次のとおりです。

- **CVE-2026-111497**: Brotliデコーダーが、不正な入力に対して8バイトのバッファ外へ書き込みます。クラッシュ、メモリ内容の漏えい、コード実行につながる可能性があります。外部由来のBrotliデータ(第三者のHTTPレスポンスやアップロードファイル)を展開するサービスが対象です。
- **CVE-2026-105483**: `tls.checkServerIdentity()` が `１２７.0.0.1` のような全角数字のIP文字列をIPアドレスとして扱わず、DNS SANを持つ証明書で認証が通ってしまいます。26.xと24.xが対象です。
- **CVE-2026-106069**: `0127.0.0.1` のようなホストを、WHATWG URLは8進数、OSのリゾルバーは10進数として解釈します。その結果、別のIP向けの証明書が受け入れられる場合があります。
- **CVE-2026-105482**: `dns.resolve*()` と `dns.reverse()` がNULバイトで名前を切り詰めます。過去のCVEに対する修正が不完全だったものと説明されています。

中程度のCVE-2026-106072も同じ系統です。`0x7f.0.0.1`、`2130706433`、`127.1` といった非正規表記により、DNSのみのSANでIPエンドポイントを認証できてしまいます。

## なぜこの種のバグは繰り返し起きるのか

証明書検証には2つの入力があります。クライアントが意図した接続先の名前と、証明書に含まれる名前です。この検証が成り立つのは、クライアントが考える「接続先ホスト」とネットワークスタックが実際に使うホストが一致しているときだけです。URLパーサー、バリデーター、リゾルバーがそれぞれ独自のルールでIPv4の省略表記、8進リテラル、Unicode数字を扱うと、攻撃者は「ある検査は通るが、次の処理では別の意味になる」文字列を作る余地を得ます。

アプリケーション側の教訓は、正規化を一度だけ行い、その正規形で比較することです。生の文字列を検証してから、その生の文字列を別の処理に渡してはいけません。

```ts
import { isIP } from "node:net";

// 正規のIPまたは通常のDNS名以外は拒否する
function normalizeHost(input: string): string {
  const url = new URL(`https://${input}`);
  const host = url.hostname; // WHATWGの正規化を適用

  // 数値っぽいのに正規のドット区切りIPv4/IPv6でなければ拒否
  const looksNumeric = /^[0-9.xX:\[\]a-fA-F]+$/.test(host);
  if (looksNumeric && isIP(host.replace(/^\[|\]$/g, "")) === 0) {
    throw new Error(`Non-canonical IP-like host: ${input}`);
  }
  return host;
}
```

これはパッチの代わりではなく、防御的な書き方です。SSRF対策のallow-listやWebhook URLの検証など、Node本体の修正が届かない箇所で効きます。内部レンジのallow-listを持っている場合は、文字列ではなくパース済みの数値アドレスで比較してください。

## どこから対応するか

バージョン番号ではなく、露出度で優先順位を付けます。

1. **ユーザー指定のURLにアクセスするサービス**(Webhook、リンクプレビュー、URLからのインポート)。IP解釈の問題が最も影響します。
2. **外部のBrotliコンテンツを展開するサービス**。リバースプロキシやHTTPクライアントも確認してください。`Accept-Encoding` でBrotliは広く使われています。
3. **それ以外**のサポート対象ライン。通常の運用サイクルで構いませんが、数週間ではなく数日以内に更新します。

同じリリースには依存関係の更新も含まれています。c-ares、undici、OpenSSL(24.xと22.x)、SQLite(22.x)、そして侵害された中間CAに関するCA証明書の変更です。コンテナで独自のCAバンドルを固定している場合は、同じ削除が反映されているか確認してください。

補足が2点あります。Permission Modelの問題(CVE-2026-106071、CVE-2026-106073)は、`--allow-fs-read` や `--allow-fs-write` を使う場合のみ関係します。ワイルドカード指定が意図より短いパスにも一致していました。またCVE-2026-106074により、起動スナップショットや単一実行可能アプリケーション(SEA)で `randomUUID()` や `randomInt()` の出力が繰り返される可能性がありました。SEAやスナップショットを作っている場合は、古い成果物を再デプロイするのではなく、アップグレードして再ビルドしてください。

## 実際に動いているバージョンの確認

```bash
# コンテナまたはCIイメージ内
node --version

# 複数のDockerfileを横断して確認
grep -R "FROM node:" --include=Dockerfile* . | sort | uniq -c
```

`node:24` のようなタグは浮動しますが、キャッシュされたレイヤーは更新されません。v24.22.1を取り込むには `--pull` 付きの再ビルド(`docker compose build --pull`)が必要です。Dockerfileの記述ではなく、稼働中のコンテナ内で `node --version` を実行して確認してください。

## webhaniの推奨

- v22.23.4、v24.22.1、v26.12.1のいずれかへ更新して再デプロイします。ユーザー指定URLを扱うものを最優先にしてください。
- 自社のホスト検証にも、アドバイザリの入力例(`0127.0.0.1`、`0x7f.0.0.1`、`127.1`、全角数字)を使った回帰テストを追加します。これらがallow-listを通過するなら、同種のバグを自社コードが抱えています。
- EOLのラインには修正が提供されない点を再確認してください。Node.js側も、EOL版は影響を受けるためサポート対象リリースへ移行するよう推奨しています。移行計画については別記事で扱います。

今回の修正自体は特殊なものではありません。ただ、根本にある「コンポーネント間のパース不整合」は、アプリケーション開発でも頻繁に再現される問題です。パッチはNode側の該当箇所を塞ぎますが、自社のURL・ホスト検証も、このタイミングで見直す価値があります。
