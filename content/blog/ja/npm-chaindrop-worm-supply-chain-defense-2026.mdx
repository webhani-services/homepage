2026 年 8 月 4 日、セキュリティ研究機関（Elastic Security Labs、Microsoft Security、Wiz、Snyk、Datadog ほか）が新たな npm パッケージワームを報告しました。「CHAINDROP」と呼ばれるこの攻撃は、先月の TanStack Router 事件とは別の、より大規模な第二波です。

## 事件の規模

**keyv** というキー・バリューストレージライブラリのメンテナンスアカウントが侵害され、その後、同じメンテナンス権を持つ関連パッケージが次々と trojanize されました：

- `keyv`（月間 600M ダウンロード）
- `flat-cache`（月間 580M）
- `cacheable-request`（月間 137M）
- `cacheable`（月間 30M）
- `cache-manager`（月間 16M）
- その他複数の関連パッケージ

**合計では、434 パッケージ以上、1,381 のバージョンが確認された時点で侵害されており、月間ダウンロード数は 20 億を超えます。** これらは transitive dependency として npm エコシステム全体に深く浸透しているため、直接的に依存していないプロジェクトまで影響を受ける可能性があります。

## 技術的なメカニズム

攻撃は npm の `preinstall` ライフサイクルフックを悪用しています：

1. パッケージのインストール時、npm はビルドスクリプトやライフサイクルフック（`preinstall`、`postinstall` など）を自動実行
2. 悪意あるコードが、圧縮・難読化された loader として仕込まれる
3. loader は二次ペイロードをダウンロード・実行
4. 開発マシンや CI 環境に存在する認証情報を盗む：
   - npm publish トークン
   - AWS、GCP などのクラウド認証情報
   - CI/CD シークレット
   - IDE 統合トークン
5. **盗まれた npm publish 認証情報を使って、被害者が管理する他のパッケージをも自動的に侵害 → 「自己伝播型」**

これが「Shai-Hulud ワーム」と呼ばれる理由です。攻撃者の手を離れても、盗まれた認証情報を通じて自律的に広がります。

## 今すぐ取るべき対応

### 1. package-lock.json を監査する

まず、侵害されたパッケージが依存関係に入っていないか確認します。以下のスクリプトで検査できます：

```bash
#!/bin/bash
# 侵害されたパッケージバージョンを検査するスクリプト

COMPROMISED_PACKAGES=(
  "keyv"
  "flat-cache"
  "cacheable-request"
  "cacheable"
  "cache-manager"
)

echo "Checking package-lock.json for compromised packages..."

for pkg in "${COMPROMISED_PACKAGES[@]}"; do
  if grep -q "\"$pkg\":" package-lock.json; then
    echo "Found: $pkg"
    grep -A 2 "\"$pkg\":" package-lock.json | head -3
  fi
done

# より詳しい情報が必要な場合
echo -e "\nDetailed version info:"
npm list 2>/dev/null | grep -E "(keyv|flat-cache|cacheable-request|cacheable|cache-manager)"
```

実行例：
```bash
$ bash check-compromised.sh
Found: flat-cache
  "flat-cache": {
    "version": "1.3.4",

Found: cacheable-request
  "cacheable-request": {
    "version": "10.2.1",
```

侵害されたパッケージが見つかった場合は、**パッケージのアップデートが配信されるまで、プロジェクトのインストールを避けます。**

### 2. 開発マシンと CI 環境の認証情報をローテーションする

侵害されたバージョンをインストールしたことのあるすべての環境で、以下の認証情報をローテーションします：

```bash
# npm publish トークンのローテーション
npm logout
npm login  # 新しいトークンを取得

# ローカル .npmrc をクリア（必要に応じて）
rm ~/.npmrc

# CI 環境では GitHub Secret / GitLab Variables を更新
# AWS 認証情報、その他の API キーも確認
```

**重要**: CI/CD 環境で秘密情報が露出していないか、Cloud provider のアクティビティログを確認します（AWS CloudTrail、GCP Cloud Audit Logs など）。

### 3. preinstall/postinstall スクリプトをデフォルト無効化する

npm では、デフォルトでライフサイクルスクリプトを実行しないように設定できます：

```bash
# ローカル開発環境
npm config set ignore-scripts true

# または .npmrc ファイルで設定
cat >> ~/.npmrc <<EOF
ignore-scripts=true
EOF

# CI 環境での例（GitHub Actions）
- name: Install dependencies with scripts disabled
  run: npm install --ignore-scripts
  
# その後、信頼できるスクリプトだけを明示的に実行
- name: Run build script
  run: npm run build
```

**注意**: プロジェクトが build スクリプト（native modules をコンパイルするパッケージなど）に依存している場合は、信頼できるパッケージだけに限定します。

### 4. package-lock.json の整合性を CI で検証する

lockfile がコミット後に改ざんされていないか確認するステップを追加します：

```yaml
# GitHub Actions の例
- name: Verify package-lock.json integrity
  run: |
    npm ci --prefer-offline --no-audit
    if ! git diff --exit-code package-lock.json; then
      echo "package-lock.json was modified by npm ci"
      exit 1
    fi

# または npm の lockfile 検証コマンドを使う
- name: Verify lockfile
  run: npm audit --production
```

### 5. npm audit を CI に組み込む

毎回の PR/コミットで依存関係をスキャンします：

```yaml
# GitHub Actions
- name: Audit npm dependencies
  run: npm audit --audit-level=moderate
  # --audit-level: low|moderate|high|critical
  # デフォルト moderate 以上で失敗
```

```bash
# ローカル開発
npm audit

# 脆弱性が見つかった場合
npm audit fix          # 自動修正を試みる
npm audit fix --force  # 破壊的な変更を許可
```

### 6. Dependabot または Snyk による継続的監視

GitHub Dependabot を有効化して、依存関係の更新を自動追跡します：

```yaml
# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "daily"
    reviewers:
      - "security-team"
    allow:
      - dependency-type: "production"  # 本番環境のみ
```

## チェックリスト

このワーム対策の優先度付けチェックリスト：

- [ ] `npm list` または `package-lock.json` で keyv、flat-cache などが使用されていないか確認
- [ ] npm publish トークン、AWS/GCP 認証情報をローテーション
- [ ] CI 環境に `--ignore-scripts` フラグを追加
- [ ] lockfile 整合性チェックを CI に追加
- [ ] npm audit を CI パイプラインに組み込む
- [ ] チームに認証情報ローテーション完了を周知

## webhani の見解

この事件は npm エコシステムの「構造的な脆弱性」を浮き彫りにしました。わずかなメンテナンスアカウント侵害が、月間 20 億ダウンロード以上に及ぶパッケージ群を支配できるという現実です。

特に危険なのは `preinstall` スクリプトの無制限実行です。開発者が気づかないうちに、信頼できると思っているパッケージから任意コードが実行されます。この構造自体を変えるまでは、npm コミュニティ全体が常に「感染」のリスクに曝されています。

webhani では、Node.js プロジェクトの依存関係監査と、セキュアな CI/CD 構築をサポートしています。まずは `ignore-scripts` フラグの導入と lockfile 整合性確認から始めることをお勧めします。
