Trusted Publishingは、CIから長期有効なnpmトークンを排除するための仕組みです。シークレットを保存する代わりに、レジストリが特定のGitHubリポジトリとワークフローを信頼し、そのワークフローが公開するときに発行される短命のOIDC IDトークンを受け入れます。良いモデルであり、私たちも推奨しています。

Bloom Securityの調査に関する報道によると、この信頼関係がリポジトリの恒久的なIDではなくリポジトリの「名前」に紐づいていたとされ、報告から約4か月後の10月2日にGitHubが修正をリリースしました。本稿はそれらの報道に基づいており、当社で再現したわけではありません。細部は「報告された内容」として読んでください。

ここでの教訓は1つのレジストリに限りません。名前はラベルであって、IDではありません。

## 起こり得た問題

リポジトリ名は人の手に渡ることがあります。問題になるのは次の流れです。

1. メンテナがリポジトリの名前変更・移管・削除を行う。
2. 古い`owner/name`が空く。
3. 別の誰かがその名前を取得し、同名のリポジトリを作成する。
4. レジストリが依然として`owner/name`を信頼していると、新しいリポジトリのワークフローが信頼ルールに一致するOIDCトークンを取得し、そのパッケージとして公開できてしまう。

この流れにトークンの窃取やアカウントの侵害は不要です。信頼ルールが、再割り当て可能なものを指しているだけです。恒久的な数値のリポジトリIDに紐づければ、再作成されたリポジトリには新しいIDが付くため、これを防げます。

これは、dangling DNSレコードや放棄されたS3バケット名と同じ種類の問題です。再利用可能な名前に信頼を置く場合は、そのライフサイクルの管理が必要です。

## 修正後も重要な理由

npmに公開しているなら、レジストリ側の修正でこの特定のリスクは下がります。ただし周辺のリスクがなくなるわけではなく、同じ時期にはパイプラインを狙った別の活動も見られました。たとえばGitGuardianが報告したGhostAction系のアカウント侵害は、CIからレジストリのトークンを盗むことを狙っています。共通点は、公開経路が価値の高い標的だということです。

Trusted Publishingは状況を改善しますが、それは周辺の設定が適切に絞られている場合に限ります。

## 堅牢化チェックリスト

**1. 信頼ルールを狭く設定する。** Trusted Publisherには、正確なリポジトリとワークフローファイルを指定し、レジストリが対応していればEnvironment名も指定します。リポジトリ内の任意のワークフローを許可するルールは、必要以上に広いです。

**2. 公開を保護されたEnvironmentの背後に置く。**

```yaml
# .github/workflows/release.yml
name: release
on:
  push:
    tags: ["v*"]

permissions:
  contents: read

jobs:
  publish:
    runs-on: ubuntu-latest
    environment: npm-release       # リポジトリ設定で必須レビュアーを設定
    permissions:
      contents: read
      id-token: write              # OIDC IDトークンの発行に必要
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v5
        with:
          node-version: 24
          registry-url: https://registry.npmjs.org
      - run: npm ci --ignore-scripts
      - run: npm publish --provenance
```

`id-token: write`はワークフロー全体ではなく、公開ジョブにだけ付与します。`npm-release` Environmentには必須レビュアーを設定し、タグをpushしただけでは公開できないようにします。サードパーティのActionは、完全なコミットSHAで固定してください。

**3. リリースのトリガーとなるタグとブランチを保護する。** 書き込み権限があれば誰でも`v*`タグをpushできる状態では、Environmentのレビュアーが唯一の関門になります。タグ保護ルールやRulesetで、リリースタグを作成できる人を限定してください。

**4. 公開元のリポジトリを失効させない。** 削除ではなくアーカイブを選びます。名前変更や移管が必要な場合は、同じ変更の中でレジストリ側のTrusted Publisher設定も更新し、後で検証します。どのパッケージがどのリポジトリを信頼しているかの一覧も管理してください。

**5. 残っているトークンを削除する。** Trusted Publishingへ移行した後は、古い自動化用トークンを失効させ、レジストリのプランで可能なら、トークンによる公開を禁止する設定も検討します。忘れられたトークンが1つ残っていれば、効果は帳消しです。

**6. 利用側が受け取るものを検証する。** Provenance付きで公開し、自社のインストール環境で`npm audit signatures`を実行して、依存パッケージのProvenanceと署名を確認します。

```bash
npm audit signatures
```

Provenanceは、どのリポジトリのどのワークフローがパッケージをビルドしたかを示します。有用な証拠ですが、そのリポジトリの統制を信頼できる範囲でしか意味を持ちません。

## 今週やること

- 公開しているすべてのパッケージを一覧にし、現在の認証方式(トークンかTrusted Publishingか)を記録します。
- Trusted Publisherのルールごとに、リポジトリが同じオーナーのもとに存在し、ワークフローとEnvironmentが意図どおり絞られていることを確認します。
- 公開用リポジトリの名前変更・移管・削除に、組織内でレビュー手順が必要になっているか確認します。
- 古い自動化トークンを探して失効させます。

## まとめ

- Trusted Publishingは長期トークンより依然として良い選択肢であり、報告された欠陥はレジストリ側で修正済みです。
- IDは、名前ではなく、再割り当てできない数値IDなどに紐づけるべきです。
- この機能がどこまで守ってくれるかは、自社の設定次第です。ワークフローの範囲を絞り、Environmentとタグを保護し、トークンを残さないことが要点です。
- リポジトリのライフサイクルイベント(名前変更・移管・削除)は、セキュリティ上重要な変更として扱ってください。
