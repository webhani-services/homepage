Gartner のアナリスト Mark Petty 氏と Raymond Paquet 氏が「Open-Weight Models Will Run 90% of Enterprise Agentic Workflow Steps」というレポートを公開しました。11月3日の The Register の報道によると、主張の要点は次のとおりです。業務用エージェントのワークフローの大半のステップは定型的であり、オープンウェイトモデルは最も安いクローズドモデルと同等の品質で、その約 4 分の 1 の価格で処理できる。すべてのステップをフロンティアモデルに送る場合と比べると、コストはおよそ 20 分の 1 になる、というものです。

より参考になるのは但し書きのほうです。アナリスト自身、オープンモデルは出力が冗長になりやすくリトライも多いため、フロンティアモデルに対するタスク単位の実際の削減幅は 5〜6 倍程度だと認めています。Gartner の想定では、2030年までに業務用エージェントワークフローのステップの 90% がオープンウェイトモデルで動き、フロンティアモデルは研究開発や難しい推論に使われ続けるとしています。

私たちが注目しているのは数字そのものより、この予測が前提としている判断の単位です。**「このアプリにどのモデルを使うか」ではなく、「このステップにどのモデルを使うか」** です。

## アプリ単位ではなくステップ単位で考える理由

たとえば請求書を処理する業務エージェントは、性質の異なる作業をいくつも行います。

1. PDF から項目を抽出する
2. 取引先とコストセンターを分類する
3. 日付と通貨を正規化する
4. 発注書との差異が妥当かどうかを判断する
5. 担当者向けに説明文を書く

1〜3 は範囲が狭く、検証可能で、繰り返しの多い作業です。4 は判断が必要です。5 は文章力が活きますが、リスクは低めです。パイプライン全体をフロンティアモデルで動かせば、必要のないステップにも高い料金を払うことになります。逆に全部を小さなモデルで動かすと、4 で失敗します。

## 検証付きの 2 段構成ルーター

私たちが使っているパターンはシンプルです。ステップの種類でモデルを振り分け、出力をスキーマで検証し、失敗したら上位モデルにエスカレーションします。TypeScript で要点だけ書くと次のようになります。

```ts
import { z } from "zod";

type Tier = "open" | "frontier";

interface Step<T> {
  name: string;
  routine: boolean;
  schema: z.ZodType<T>;
  prompt: (input: unknown) => string;
}

const MODELS: Record<Tier, string> = {
  open: process.env.OPEN_MODEL_ID!,       // セルフホストまたはホスティングされたオープンウェイトモデル
  frontier: process.env.FRONTIER_MODEL_ID!,
};

async function runStep<T>(step: Step<T>, input: unknown): Promise<T> {
  const tier: Tier = step.routine ? "open" : "frontier";
  const first = await tryModel(step, input, tier);
  if (first.ok) return first.value;

  metrics.increment("agent.escalation", { step: step.name });
  const second = await tryModel(step, input, "frontier");
  if (second.ok) return second.value;

  throw new Error(`Step ${step.name} failed on both tiers`);
}

async function tryModel<T>(step: Step<T>, input: unknown, tier: Tier) {
  const raw = await callModel(MODELS[tier], step.prompt(input));
  const parsed = step.schema.safeParse(safeJson(raw.text));
  metrics.record("agent.tokens", raw.usage.totalTokens, { step: step.name, tier });
  return parsed.success
    ? { ok: true as const, value: parsed.data }
    : { ok: false as const };
}
```

本番で機能させるためのポイントは 3 つです。

- **スキーマが契約になる**：定型ステップには機械的にチェックできる出力が必要です。スキーマを書けないなら、そのステップはおそらく定型ではありません。
- **エスカレーションは失敗ではなくメトリクス**：ステップごとのエスカレーション率を記録します。30% もエスカレーションしているなら、そのステップにオープンモデルは合っておらず、「削減効果」はほぼ見かけだけです。
- **モデル ID は設定値にする**：環境変数やゲートウェイの設定に置いておけば、デプロイなしでモデルを差し替えられます。

## トークン単価ではなくタスク単価で比べる

冗長さとリトライに関する Gartner 自身の但し書きは、私たちが最もよく目にする誤りを指しています。料金表だけを比べることです。トークン単価が 4 分の 1 でも、トークン消費が 2 倍で 5 回に 1 回リトライするなら、4 倍安いことにはなりません。

私たちはワークフローごとに次の 3 つの数字を報告しています。

- **完了タスクあたりのコスト**（リトライとエスカレーションを含む）
- **ステップごとのエスカレーション率**
- **固定評価セットでの品質**（たとえば正解がわかっている実際の請求書 200 件）

3 つすべてが許容範囲に入ったときだけ、そのステップをオープンモデル側に移します。評価セットは、裏でモデルのバージョンが変わったときの防御策にもなります。

## データ管理という観点

アナリストはコストよりもコントロールとデータの所有を強調しています。定型処理をフロンティアの API に流すということは、ワークフローのデータの一部を自社の境界の外に出すことになる、という指摘です。日本のお客様の場合、これが決め手になることも少なくありません。自社の VPC や選んだリージョンでオープンウェイトモデルを動かせば、セキュリティ審査や顧客から「データはどこに行くのか」と聞かれたときに答えやすくなります。

ただし、セルフホストには GPU の確保、モデルの更新、オンコール対応といった別のコストがかかります。多くのチームにとっては、クラウドプロバイダーが提供するホスティング型のオープンウェイトモデルが現実的な落としどころです。

## webhani の見解

方向性には同意しますが、時間軸についてはもう少し慎重に見ています。フロンティアモデルは急速に進化し、価格も下がり続けているため、差は縮まっていきます。長く通用する教訓はアーキテクチャのほうです。各ステップに明確な契約を持たせ、その背後のモデルを差し替えられるようにエージェントを設計しておくこと。2028年に安いモデルがオープンウェイトかどうかに関係なく、この設計は役に立ちます。

## まとめ

- モデルの選択はアプリ単位ではなくステップ単位で行う
- 定型ステップにはスキーマを用意し、出力を検証する
- 失敗時はフロンティアモデルにエスカレーションし、その率を記録する
- リトライを含めた完了タスクあたりのコストで比較する
- 安いモデルに移す前に、固定の評価セットを用意する
