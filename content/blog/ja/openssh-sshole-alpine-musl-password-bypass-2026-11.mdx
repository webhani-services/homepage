11月5日、Alpine Linux と OpenSSH から sshd のパスワード認証バイパスに関する advisory が出ました。CVE-2026-123158 として採番され、「sshole」という通称で呼ばれています。CVSS 3.1 のベーススコアは 8.1（High）です。

この脆弱性で厄介なのは、**「パスワードを使っていないから安全」と考えていたアカウントほど影響を受ける**点です。鍵認証のみのユーザーや、パスワードがロックされたアカウントが対象になります。

## 何が起きているのか

公開情報を整理すると、条件は次のとおりです。

- **musl libc でビルドされ、PAM を使わない OpenSSH**。Alpine の標準 `openssh-server` パッケージがこれに該当します
- `PasswordAuthentication` が有効（OpenSSH のデフォルトは `yes`）
- 対象アカウントに「使用可能なパスワード」が設定されていない

この条件で、細工した長いパスワードを送ると、本来ログインできないはずのアカウントに入れてしまうとされています。Dropbear など OpenSSH 以外のサーバーは影響を受けないという分析も出ています。

修正版は OpenSSH 10.6p2 で、11月5日にリリースされました。Alpine は edge と 3.16 以降のすべての stable branch に修正パッケージを出しています。11月6日時点で公開された再現コードはあるものの、実環境での悪用は確認されておらず、CISA の KEV にも載っていません。ただし、再現コードが出ている以上、悪用されるまでの猶予は短いと考えてください。

## まず「どこに Alpine の sshd があるか」を洗い出す

glibc ベースの Debian/Ubuntu/RHEL は今回の条件に当てはまりません。webhani でお客様の環境を確認するときも、最初にやるのは対象の絞り込みです。Alpine の sshd は、意外な場所に残っていることがよくあります。

- 踏み台（bastion）として立てた小さな VM や Container
- CI で使う SFTP 受け口や Git ミラー
- 開発用の `docker compose` に入っている「SSH できる Container」
- ベンダー提供のアプライアンス（内部が Alpine の場合あり）

ホスト側で確認するときは、次のようなスクリプトで判定できます。

```bash
#!/bin/sh
# sshole の影響有無を判定する簡易チェック
set -eu

if [ -f /etc/alpine-release ]; then
  echo "distro: alpine $(cat /etc/alpine-release)"
fi

# libc の確認（musl かどうか）
if ldd "$(command -v sshd)" 2>/dev/null | grep -q musl; then
  echo "libc: musl"
fi

# 実際に有効な設定値を確認（Include されたファイルも含めて展開される）
sshd -T 2>/dev/null | grep -Ei '^(passwordauthentication|usepam) '

# OpenSSH のバージョン
sshd -V 2>&1 | head -1 || ssh -V 2>&1
```

`sshd_config` を grep するのではなく、`sshd -T` で**実効設定**を見るのがポイントです。`Include` で読み込まれる drop-in ファイルの値で上書きされていることがあるからです。

Container イメージの場合は、レジストリ上のイメージを走査します。

```bash
# Alpine ベースで openssh-server を含むイメージを探す
for img in $(docker images --format '{{.Repository}}:{{.Tag}}' | grep -v '<none>'); do
  if docker run --rm --entrypoint sh "$img" -c \
      'test -f /etc/alpine-release && apk info -e openssh-server' >/dev/null 2>&1; then
    echo "AFFECTED CANDIDATE: $img"
  fi
done
```

本番運用では Trivy や Grype などの SBOM ベースのスキャナで CVE ID を指定して検索するほうが確実です。データベースに CVE が反映されるまでラグがあるので、反映前は上のような直接チェックと併用します。

## 対応手順

### 1. パッケージ更新と sshd の再起動

```bash
apk update
apk upgrade openssh-server openssh
rc-service sshd restart   # OpenRC の場合
```

Alpine の advisory でも強調されていますが、**パッケージを更新しただけでは、稼働中の sshd は古いバイナリのまま**です。必ず再起動し、実際に動いているプロセスが新しいバイナリかを確認してください。

```bash
# 起動時刻がアップデート後になっているか
ps -o pid,lstart,args -C sshd 2>/dev/null || ps -ef | grep '[s]shd'
```

### 2. すぐに更新できない場合の緩和策

パスワード認証そのものを無効化すれば、今回の経路は塞がります。

```text
# /etc/ssh/sshd_config.d/00-disable-password.conf
PasswordAuthentication no
KbdInteractiveAuthentication no
```

ファイル名を `00-` で始めているのは、OpenSSH では**最初に現れた値が優先される**ためです。後ろのファイルで `no` を書いても、先に `yes` があれば効きません。設定後は `sshd -t` で構文を確認し、`sshd -T` で実効値が `no` になっているかを確認してから reload します。

### 3. Container イメージの再ビルド

Container の場合は「中で apk upgrade」ではなく、ベースイメージを更新して再ビルド・再デプロイします。

```dockerfile
FROM alpine:3.24
# ビルド時に最新パッチを取り込む
RUN apk add --no-cache --upgrade openssh-server
COPY sshd_config.d/ /etc/ssh/sshd_config.d/
```

`--upgrade` を付けておくと、キャッシュされた古いベースイメージを使っていても、パッケージは最新版に揃います。

## ログの確認

再現コードが出回っている以上、攻撃の痕跡がないかも見ておくべきです。sshole の特徴は「パスワードを持たないアカウントへの password 認証成功」なので、次のようなログは要注意です。

```bash
grep -E 'Accepted password for' /var/log/messages /var/log/auth.log 2>/dev/null
```

パスワードログインを一切運用していない環境で `Accepted password` が出ていたら、それ自体が異常です。該当があれば、そのホストは侵害を前提に扱い、鍵の入れ替えと再構築を検討してください。

## webhani の見解

今回の件で改めて確認したいのは、「鍵認証にしているから大丈夫」という前提が、**設定ではなく運用上の思い込み**になっていないかという点です。鍵しか使っていなくても、`PasswordAuthentication` がデフォルトの `yes` のまま残っている環境は珍しくありません。

私たちが推奨している方針は次のとおりです。

- SSH を受け付けるすべてのホストで `PasswordAuthentication no` を明示する（使っていない機能は閉じる）
- 設定の確認は `sshd -T` の出力を CI や構成管理で検証する
- 踏み台は可能なら SSM Session Manager や IAP など、SSH ポートを公開しない方式へ移行する
- Container に sshd を入れる構成は、本当に必要かを見直す

パッチを当てて終わりにせず、この機会に「SSH の入口がどこに何個あるか」を棚卸ししておくと、次に同種の問題が出たときの対応が大きく速くなります。
