## Passkeyはもはや実験的ではない

2026年の認証環境は、大きな転換点を迎えています。Passkey（FIDO2/WebAuthn ベースの認証器）がブラウザとOSレベルで95%以上のカバレッジに到達し、Microsoftが2025年5月に消費者向けアカウントでPasskeyをデフォルト認証にするなど、パイロットから本格運用への流れが加速しています。

同時にNIST SP 800-63-4（2025年7月公開）がPasskeyをAAL2（Authenticator Assurance Level 2）に分類し、EU NIS2指令がサービスの重要な認証にパスワード単独を推奨しないと明記しました。こうした規制とプラットフォームの動きが、これまで「セキュリティのベストプラクティス」に留まっていた技術を、組織レベルでの必須対応に変えつつあります。

本稿では、実装側の視点でPasskeyの導入考慮点と、OAuth3というより大きな業界議論の位置づけを整理します。

## Passkey（WebAuthn）の現在地

Passkey の強みは、シンプルさと安全性の両立にあります。業界データによると、Passkey による認証成功率は93%（パスワード認証は63%）、完了時間は約73%高速化されています。さらに、Passkey 環境への移行後の組織では、認証関連のヘルプデスク対応が81%削減されるケースが報告されています。

ブラウザと OS の対応状況はほぼ完全に近い状態です。Chrome 67+、Edge 18+、Safari 13+（iOS 14.5+）、および主要 Chromium フォーク、iOS 16+、Android 9+、Windows 10+ のすべてで WebAuthn API が利用可能です。この水準に達すると、「一部の環境で動かない」という理由は消えます。

### 実装の基本形

Developer 向けの実装は、W3C標準の `navigator.credentials` API が中心になります。フロントエンド側では以下のような流れになります。

```javascript
// 登録フロー（Passkey生成）
async function registerPasskey() {
  const credential = await navigator.credentials.create({
    publicKey: {
      challenge: new Uint8Array(32), // サーバーから取得したチャレンジ
      rp: { name: "example.com", id: "example.com" },
      user: {
        id: new Uint8Array(16),
        name: "user@example.com",
        displayName: "User"
      },
      pubKeyCredParams: [{ alg: -7, type: "public-key" }],
      attestation: "direct",
      timeout: 60000
    }
  });
  // credentialをサーバーに送信し、公開鍵を保存
}

// 認証フロー（Passkeyを使用したサインイン）
async function authenticateWithPasskey() {
  const assertion = await navigator.credentials.get({
    publicKey: {
      challenge: new Uint8Array(32), // サーバーから取得したチャレンジ
      timeout: 60000,
      userVerification: "preferred"
    }
  });
  // assertionをサーバーに送信し、署名を検証
}
```

サーバー側では、標準ライブラリ（Go の `github.com/go-webauthn/webauthn`、Node.js の `@simplewebauthn/server`、Python の `webauthn` など）が提供する検証ロジックを使います。秘密鍵はクライアント側に留まり、サーバーは公開鍵と登録済みの認証器のメタデータを保持するだけです。

## 既存システムとの共存

組織のほとんどは、一夜にしてパスワード認証を廃止することはできません。段階的な導入が現実的です。Webhaniが顧客プロジェクトで採用しているパターンは次の通りです。

### フェーズ1：Passkeyを選択肢として追加

既存のパスワード認証に加え、新規ユーザーや既存ユーザーが Passkey を登録できるオプションを提供します。このとき、セッション管理（JWT や OAuth 2.0）の仕組みは変えません。Passkey は単に新しい認証要素であり、認可フローには影響しません。

```text
ログイン画面
├─ メールアドレス入力
├─ Passkeyでサインイン（新規オプション）
├─ パスワード入力（既存）
└─ 多要素認証（既存ユーザー向け）
```

### フェーズ2：Passkeyをデフォルトに

ユーザーの Passkey 登録数が一定数に達したら、新規登録時のデフォルトを Passkey に切り替えます。既存ユーザーへは「フォールバック手段を残しながら」移行を促します。

### フェーズ3：パスワード廃止

ユーザーベースの90%以上が Passkey に移行した段階で、パスワード認証を廃止します。ただし、復旧用の仕組み（バックアップコード、管理者による検証）は必須です。

重要なのは、各フェーズでの品質確保です。Passkey は安全ですが、導入後に「ユーザーが別デバイスにサインインできない」といった運用課題が生じやすいです。組織内での十分なテストと、カスタマーサポートの拡張が先行します。

## 規制動向が導入を加速

NIST SP 800-63-4 は、2要素認証で求められる「Authenticator Assurance Level 2（AAL2）」の要件に、Passkey（特に端末に同期されたPasskey）を含めました。これは、政府機関や規制産業の顧客にとって、Passkey 導入が単なるセキュリティ向上ではなく、コンプライアンス要件になったことを意味します。

EU NIS2指令は、重要インフラやデジタルサービス提供事業者に対し、重要なサービスの認証にパスワード単独を推奨しないと明記しています。多くのヨーロッパ企業はこれに対応するため、2026年後半から2027年にかけて Passkey の導入・検証を加速させています。

これらの規制は、Webhani のような IT コンサルティング企業にとって、顧客への実装支援の契機になります。

## OAuth3：業界議論の現在地

一方で「OAuth3」という言葉が業界で浮上していますが、重要な注記が必要です。**OAuth 3.0 は、OAuth 2.0 に代わる正式な IETF 標準ではまだありません。**

現在進行中なのは、セキュリティ研究者やプロトコル設計者による非公式な議論です。これまでの OAuth 2.0 は次のような課題を抱えていました。

- 暗号化強度が古い（PKCE などで事後対応）
- リフレッシュトークンの管理が複雑
- 企業向けの認可フロー（スコープ管理など）がやや冗長

業界の議論は、これらを最初から設計に組み込んだ仕様を検討する段階です。ただし、標準化のプロセス（W3C や IETF への提案、複数の実装による検証、相互運用性テスト）はこれからです。

実装側の視点では、**2026年時点で OAuth 3.0 に移行する必要はありません。**OAuth 2.0 は依然として堅牢で、認可フローが十分に複雑でない場合はそのまま使用できます。ただし、業界の議論が具体化する 2027 年以降の動向は注視する価値があります。

## Webhani の視点：実装戦略の整理

1. **Passkey を主軸に**：ブラウザ対応が完全に近く、規制動向も後押しするため、Passkey の実装・テストはすべての新規プロジェクトで標準化を推奨します。段階的な導入計画を立てることが重要です。

2. **OAuth 2.0 は継続**：OAuth 3.0 は業界議論の段階です。現在の顧客システムに大規模な変更を迫る根拠にはなりません。ただし、新規設計時には「将来的な拡張可能性」を想定した設計を心がけます。

3. **規制対応を前提に**：NIST AAL2 や NIS2 対応が顧客要件に挙がりやすくなっています。Passkey の実装時には、これらの規制要件をチェックリスト化し、検証プロセスに組み込むことが顧客信頼につながります。

4. **段階的運用設計**：Passkey 導入はセキュリティと利便性の両立が課題です。組織内トレーニング、カスタマーサポート体制の拡張、フォールバック手段の確保を、実装と同時に計画します。

## まとめ

2026年の認証トレンドは、Passkey が「ベストプラクティス」から「運用標準」へ移行する転換点です。ブラウザ対応の完成度と規制動向が、この変化を加速させています。

OAuth3 は、ようやく業界の議論テーブルに上った次世代プロトコルです。標準化はまだ先ですが、長期戦略の情報として注視する価値はあります。

Webhani では、Passkey 実装の相談から段階的な導入計画、そして規制対応の検証まで、顧客の認証戦略をトータルで支援しています。
