10月15日、PerplexityはSPACE(Sandboxed Platform for Agentic Code Execution)をOSSとして公開しました。同社のComputerエージェントの全セッションを支えるSandbox基盤とされており、ライセンスはApache 2.0、実装はRustで、E2B Python SDK互換のラッパーも含まれます。以下の数値は報道およびPerplexity自身の発表に基づくもので、ベンダー公表値として読む必要があります。

数値そのものより注目したいのは設計です。「モデルが書いたコードは、どこで実行するのか」という、多くのチームがいま直面している問いに対する、実運用レベルの回答例だからです。

## 基本設計

報道によると、SPACEの設計は次の4点に集約されます。

1. **タスクごとに1つのmicroVM**:各エージェントタスクに専用のFirecracker microVMを割り当て、タスク終了時に破棄します。
2. **認証情報はSandboxの外**:シークレットをSandbox内に置かず、Sandboxは「操作の依頼」だけを行い、実行は外側の信頼できる層が担います。
3. **EgressはNode側で制御**:外向き通信はゲストの設定ではなくホスト側で制限するため、VM内のコードが自分でルールを緩めることはできません。
4. **状態は明示的に管理**:一時停止・再開・ブランチが可能で、ローリングスナップショットは一定期間のみ保持されます。

Perplexityは作成時間の中央値を約60msと報告しています。正確な値はともかく、「信頼できないコードに耐える分離」が数秒の起動コストを伴わなくなってきた、という点が重要です。

## なぜコンテナでは足りないのか

エージェントのコードを素のDockerコンテナで動かしているチームは多いと思います。自社の信頼できるサービスであれば妥当な選択です。ただし、プロンプト経由で生成され、信頼できない入力が混ざり得るコードに対しては弱い選択です。コンテナはホストのカーネルを共有するため、カーネルのバグやcapabilityの設定ミスがそのままホスト侵害につながります。

microVMはゲストとホストの間にハイパーバイザの境界を置きます。メモリと起動時間のコストは少し増えますが、生成されたスクリプトに問題があっても影響範囲は使い捨てVM1つに収まります。

すでにE2Bやクラウドベンダーのマネージドサンドボックスを使っているなら、この境界は得られています。SPACE公開の意義は、推測ではなく本番規模の実装を読めるようになった点にあります。

## セキュリティ検証結果は慎重に読む

Perplexityの敵対的テストについては、報道によって数字が食い違っています。約118回の試行でエスケープはゼロとする記事がある一方、108回の試行で9つのモデルがホストに到達できなかったものの、4つがネットワーク制限の一部を回避したと伝える記事もあります(Perplexityは修正と再テストを実施したとしています)。

どちらが正確であれ、次の2点は学びになります。

- ホスト境界は守られた一方、モデルが抜け道を見つけたのは**ネットワークポリシー**でした。Egressルールはサンドボックスの中でも最も微妙な誤りが入りやすい部分です。
- 能力の高いモデルを使ったレッドチーミングは実用的な手法になっています。自前で作るなら、モデルに攻撃させ、突破された箇所をバグとして管理するのが有効です。

## Perplexity規模でなくても取り入れられること

多くのお客様は1日に数百万のSandboxを動かすわけではありません。それでも設計の考え方は小さな構成に活かせます。

**認証情報を実行環境の外に置く。** 最も低コストで効果が高い対策です。APIキーをSandboxに渡す代わりに、検証付きの狭いプロキシ経由で呼び出します。

```ts
// ホスト側:エージェントは操作を依頼し、シークレットはホストが保持する
type ToolCall = { name: "create_issue"; args: { title: string; body: string } };

async function handleToolCall(call: ToolCall) {
  switch (call.name) {
    case "create_issue":
      // 実APIを呼ぶ前にスキーマで引数を検証する
      return githubClient.issues.create({
        owner: "example-org",
        repo: "example-repo",
        title: call.args.title.slice(0, 200),
        body: call.args.body,
      });
    default:
      throw new Error(`Tool not allowed: ${call.name}`);
  }
}
```

Sandboxはトークンを一切見ません。生成コードがプロンプトインジェクションで乗っ取られても、できるのは許可された操作を検証済みの引数で依頼することだけです。

**Egressはデフォルト拒否。** 外向き通信なしから始め、許可ホストをレビュー対象のリストとして追加します。強制はゲストの外で行います。

**Sandboxは使い捨てにする。** タスクまたはセッションごとに作成し、終了後に破棄します。長寿命のSandboxを複数ユーザーやタスクで使い回すと、状態の漏えいがテナント間の問題になります。

**何を残すかを決める。** スナップショットは長時間動くエージェントに便利ですが、保存されたスナップショットはすべて、分類・期限設定・保護が必要なデータです。保持期間は意図的に決めてください。

## 注意しておきたい点

- **運用負荷**:Firecrackerを自前運用するにはKVM対応ホスト、イメージ管理、ネットワーク設計が必要です。小規模なチームではマネージドサービスのほうが現実的です。
- **成熟度**:SPACEは公開されたばかりです。採用前にIssueやセキュリティポリシーを確認し、粗い部分があることを前提にしてください。
- **Sandboxは防御の一層にすぎない**:被害を限定しますが、許可された権限の範囲内でエージェントが有害な操作をすることは防げません。ツール権限を絞り、不可逆な操作には人の承認を挟んでください。

## まとめ

- モデル生成コードは信頼できないものとして扱い、リスクに見合う場合はハイパーバイザ境界の内側で実行します。
- シークレットはSandboxの外に置き、検証付きのツール層を介してアクセスさせます。
- ネットワークポリシーはホスト側でデフォルト拒否にし、敵対的にテストします。
- 多くのチームは、まずマネージドSandboxを採用し、SPACEは「良い実装の参考」として読むのが現実的です。
