PgBouncer 1.26.1が2026年10月14日にリリースされ、3件のCVEが修正されました。うち1件は認証バイパスであり、PostgreSQLの前段にPgBouncerを置いている環境では、通常のパッチリリースとは扱いが異なります。以下の内容はPostgreSQLプロジェクトの告知とDebianのセキュリティトラッカーに基づいています。まとめサイトではCVE番号の表記が揺れていたため、実際にはお使いのベンダーのアドバイザリーと突き合わせてください。

## 3つの脆弱性

**CVE-2026-107350:認証バイパス。** あるSCRAMユーザーのパスワードを知っているクライアントが、adminやバックエンドのスーパーユーザーを含む他のSCRAMユーザーとしてログインできます。接続先データベースが存在しない場合に、SCRAM認証中に届く2つ目のstartupメッセージの処理に問題があります。最優先で対応すべきものです。

**CVE-2026-107349:認証前のDoS。** startup optionsの中の空のオプション名で無限ループが発生します。`ignore_startup_parameters`が設定されていて`options`を含まない場合の、1.20.0から1.26.0が対象です。

**CVE-2026-107348:認証前のDoS。** パケットバッファの拡張時の整数オーバーフローにより無限ループが発生します。`max_packet_size`を既定値より大きくしている場合にのみ問題になります。

直前の1.26.0でも別の3件のCVEが修正されているため、1.26.0に留まるのも安全ではありません。

## 影響を受けるのは誰か

DoSの2件は設定に依存します。懸念が大きいのは認証バイパスで、前提条件が小さいためです。必要なのはプーラー上のSCRAMユーザー1人分の有効な認証情報だけです。テナントごとにDBロールがある構成や、複数のアプリケーションサービスが1つのPgBouncerを共有する構成では、「有効なユーザーが1人いる」という条件は簡単に満たされます。影響範囲は、攻撃者が到達できたアカウントの権限であり、プーラー経由で到達可能ならスーパーユーザーも含まれます。

まず実際に何が動いているかを確認します。

```bash
# 管理コンソールからバージョンを確認
psql -h pgbouncer.internal -p 6432 -U pgbouncer pgbouncer -c 'SHOW VERSION;'

# DoSに関わる設定を確認
psql -h pgbouncer.internal -p 6432 -U pgbouncer pgbouncer -c 'SHOW CONFIG;' \
  | grep -E 'ignore_startup_parameters|max_packet_size|auth_type'
```

コンテナイメージやディストリビューションのパッケージも確認してください。Debianでは1.26.1-1がunstableで修正済みとされ、それ以前のパッケージは脆弱なままです。パッケージマネージャーが追従していなければ、「定期的に更新している」つもりでも露出が残ります。

## 事前に把握しておきたい挙動変更

1.26.1では、`ignore_startup_parameters`と追跡対象パラメータの優先関係も変わり、前者が優先されるようになりました。1.26.0では`search_path`が追跡されていましたが、今回から`ignore_startup_parameters`に列挙すれば1.25と同じく無視されます。

```ini
; pgbouncer.ini
[pgbouncer]
ignore_startup_parameters = extra_float_digits,search_path
```

アプリケーションが接続オプションで`search_path`(たとえばテナントごとのスキーマ)を指定している場合は重要です。PgBouncerに追跡させるのか、無視させるのかを意図して決め、実際のクライアントライブラリの設定を使ってステージングで確認してください。セキュリティ対応のロールアウト中に違いに気づく、という事態は避けたいところです。

## パッチ以外の被害軽減策

修正はアップグレードですが、この種の不具合による被害を抑える手段もあります。

1. **PgBouncerを広く公開しない。** アプリケーションのサブネットからのみ到達可能にします。セキュリティグループやNetworkPolicyに反映し、「認証前」の不具合にインターネットから到達できないようにします。
2. **スーパーユーザーをプーラーに通さない。** `auth_query`と`auth_user`は慎重に扱い、スーパーユーザーロールがPgBouncer経由で認証できないようにします。管理作業はbastionからPostgreSQLに直接接続し、`pg_hba.conf`で制限します。
3. **信頼境界ごとにプーラーを分ける。** 全テナント・全サービスで1つのプーラーを共有すると、認証バグの影響が広がります。環境や機密度で分けるコストは小さいです。
4. **不審なログインを検知する。** 提示されたユーザーとアクセスされたデータベースを突き合わせます。アプリケーションが使わないロールでのログインは通知対象にする価値があります。
5. **`max_packet_size`を見直す。** 大きなペイロードのために引き上げている場合は、下げるか、パッチ適用までリスクを受容する判断が必要です。

## アップグレードの進め方

PgBouncerはオンライン再起動に対応していますが、コネクションのドレインには注意が必要です。

```bash
# 新しいプロセスを起動し、リスニングソケットを引き継ぐ
pgbouncer -R /etc/pgbouncer/pgbouncer.ini
```

Kubernetesでは、プーラーのポートに対するreadiness probe付きの通常のローリングアップデートで多くの場合は十分です。クライアントが接続エラー時に再試行することが前提です。まずステージングで`search_path`の挙動を確認し、その後、本番を少しずつ進めてください。

## まとめ

- 1.26.1(またはディストリビューションの修正済みパッケージ)へ更新してください。1.26.0では不十分です。
- SCRAMバイパスは有効なユーザー1人分で成立するため、共有プーラーは優先度を高くします。
- `ignore_startup_parameters`を確認し、ロールアウト前に`search_path`の扱いをテストします。
- プーラーへのネットワーク到達性を絞り、スーパーユーザーのアクセスを通さないようにします。
- CVEの参照は情報源によって揺れていたため、自社ベンダーのアドバイザリーで確認してください。
