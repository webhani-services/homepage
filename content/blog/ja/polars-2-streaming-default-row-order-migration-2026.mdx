Polars 2.0 では、`LazyFrame` のクエリを実行するエンジンが変わり、Streaming エンジンが既定になりました。Polars チームの告知では、全体として数倍の高速化が見込まれるとされています。また初期報道によれば、正式版は10月6日に公開され、out-of-core(ディスクへのスピル)にも初期対応したとのことです。公開日は第三者の記事1件でしか確認できていないため、計画に組み込む前に pola.rs で確認してください。

注目されるのは速度ですが、痛い目に遭いやすいのは別の点です。**Streaming エンジンは、一部の操作で行順序を保証しません。** 報道では join、group_by、unpivot が挙げられています。従来のインメモリエンジンの並びにたまたま依存していたコードは、同じ行を違う順序で返すようになる可能性があります。

## なぜ行順序が問題になるのか

多くのパイプラインは、順序に依存する「つもり」はありません。偶然依存しているだけです。

- グループ集計の先頭 N 行を出力し、後続の処理がそれを上位 N 件だと思い込んでいる。
- テストで `assert_frame_equal` をソートなしで使っている。
- join の結果を CSV に書き出し、差分ベースのチェックが毎回「変更あり」と判定する。
- ソートしていない結果に `.head()` を「サンプル」として使っている。

旧エンジンでは、これらがたまたま安定していました。新エンジンでは実行ごと、あるいはバージョンごとに変わりえます。エラーにはならず、値の位置だけがずれます。

## 順序を明示する

対処は安上がりで、コードも正直になります。順序が必要な箇所でソートします。

```python
import polars as pl

orders = pl.scan_parquet("orders/*.parquet")
customers = pl.scan_parquet("customers.parquet")

result = (
    orders
    .join(customers, on="customer_id", how="left")
    .group_by("region")
    .agg(pl.col("amount").sum().alias("revenue"))
    .sort("revenue", descending=True)   # 偶然ではなく明示する
    .collect()
)
```

join や group_by で入力順を保ちたい場合は `maintain_order` 引数があります(メソッドごとに受け付ける値が異なるため、2.0 の API リファレンスで確認してください)。

```python
grouped = orders.group_by("customer_id", maintain_order=True).agg(
    pl.col("amount").sum()
)
```

`maintain_order` は Streaming の高速化の一部を犠牲にします。順序が契約の一部である箇所に限って使い、それ以外は業務キーでソートするのが基本です。

## 移行中のオプトアウト

時間が必要な場合は、`collect` 時に旧来のインメモリエンジンを明示的に指定できます。最近の Polars ではおおよそ次の形です。

```python
df = lazy_query.collect(engine="in-memory")
```

エンジン指定の書き方はマイナーバージョンごとに変わっており、旧エンジンを既定に戻す engine affinity の設定に触れた記事もあります。現行の書き方は 2.0 のドキュメントで確認してください。これは目的地ではなく橋渡しです。実質的には、インメモリエンジンが段階的に退いていく方向だと考えるのが安全です。

## 移行チェックリスト

1. **ブランチで単独アップグレードする。** 2.0 だけを上げて、テストスイート全体を回します。
2. **順序に敏感なテストを探す。** `assert_frame_equal` を grep し、順序が仕様でない箇所には `check_row_order=False` を、仕様である箇所には明示的なソートを足します。
3. **新旧の出力を比較する。** 本番クエリをサンプルデータで両エンジンに流し、ソート後の結果を diff します。ソート後も差があれば、順序の問題ではなく本物のバグです。
4. **`head()`・`first()`・`unique()`・`limit` を点検する。** ソートされていないデータが「答え」として見えてしまう典型的な箇所です。
5. **自社のワークロードで再計測する。** 全体的な速度の主張が個別のパイプラインに当てはまることは稀です。効果が大きいのは、メモリを超えるデータに対するスキャン、フィルタ、集計です。
6. **スピル有効時のメモリを監視する。** out-of-core 対応は初期段階とされています。本番で頼る前に、RAM より大きいデータで試してください。

テストにそのまま入れられる簡単な同値チェックです。

```python
def assert_same_rows(a: pl.DataFrame, b: pl.DataFrame, key: list[str]) -> None:
    a_sorted = a.sort(key)
    b_sorted = b.sort(key)
    assert a_sorted.equals(b_sorted), "行順序以外にも差があります"
```

## 当社の見解

良いデフォルトだと考えています。多くのチームが実際に扱うデータ規模には Streaming 実行が向いており、速い経路を既定にするのは妥当な判断です。代償として、「エンジンは都合のよい順序で行を返してくれる」という隠れた前提があらわになりました。これはむしろ歓迎すべきことです。明示的にソートしているパイプラインは、理解しやすく、テストしやすく、エンジンが変わっても移植できます。

Polars でデータパイプラインを動かしている場合は、依存関係の単純な更新ではなく、出力 diff の工程を含む小さなプロジェクトとしてアップグレードを計画してください。移行のレビューが必要でしたら、webhani がお手伝いします。
