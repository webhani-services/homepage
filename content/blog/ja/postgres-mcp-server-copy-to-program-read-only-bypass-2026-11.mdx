AWS は、`awslabs` の Postgres MCP サーバーに関するセキュリティ情報 2026-104-AWS を公開しました。読み取り専用の強制を回避できる問題で、CVE-2026-87911 として追跡され、バージョン 1.1.7 で修正されています。情報によると、セルフマネージドの PostgreSQL に接続し、そのデータベースロールがスーパーユーザーまたは `pg_execute_server_program` 権限を持つ場合に、1.1.7 より前のバージョンが影響を受けます。同じ SQL 検証コンポーネントの関連する問題(CVE-2026-85787。禁止リストの不備により、読み取り専用の範囲を超えてデータを変更できた)も、同じリリースで修正されたと報じられています。スコアは情報源によって異なり(CVSS 3.1 で 9.6 とするものもあります)、確認時点では NVD のエントリも処理中でしたので、詳細は AWS のセキュリティ情報でご確認ください。

当面の対応はアップグレードです。この記事では、そもそもなぜこのバグが生まれたかを扱います。同じ設計が、皆さんの社内ツールにも使われている可能性が高いからです。

## 設計:権限システムの代わりをするパーサー

このサーバーには「読み取り専用モード」があり、LLM エージェントがデータベースを変更せずに調べられるようになっています。報告されている実装は、実行前に SQL 文字列を検証し、危険と判断した文を拒否するものです。欠陥は、検証が `COPY ... TO PROGRAM` を止めていなかったことです。この構文は、PostgreSQL にデータベースホスト上のシェルコマンドを実行させ、クエリ結果をそこへ流し込みます。読み取りに見える文が、OS コマンドを実行できてしまいます。

重要なのは、AWS が説明している攻撃経路です。攻撃者はデータベースに直接アクセスする必要がありません。認証済みの MCP ユーザーが処理するコンテンツ、たとえばモデルのコンテキストに入るドキュメント、チケット、Web ページ内のテキストが、エージェントにその文を発行させる誘導になりえます。つまり、データベースを出口とするプロンプトインジェクションです。

危険を大きくしていたのは次の二点です。

1. **強制がアプリケーションコードの中にあった。** 文字列レベルの許可・拒否チェックは、巨大で進化し続ける SQL 方言のあらゆる危険な構文を予見しなければなりません。禁止リストは常に不完全であり、それが二つ目の CVE そのものです。
2. **データベースロールがタスクに対して強すぎた。** `COPY ... TO PROGRAM` にはスーパーユーザーか `pg_execute_server_program` のメンバーシップが必要です。テーブルを読むだけのロールがそれを持つ理由はありません。

## 読み取り専用は、データのある場所で強制する

パーサーは便宜的な層にすぎません。境界は、セッションに何を許すかを決めることだけが仕事であるデータベース自身の権限モデルであるべきです。AWS が示した暫定回避策も同じ方向を向いています。必要なスキーマに `CONNECT`、`USAGE`、`SELECT` だけを付与し、ロール単位で読み取り専用トランザクションを強制する、というものです。スケッチは次のとおりです。

```sql
CREATE ROLE agent_ro LOGIN PASSWORD :'agent_password'
  NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT;

-- このロールが開くすべてのトランザクションを既定で読み取り専用にする
ALTER ROLE agent_ro SET default_transaction_read_only = on;
-- エージェントが生成しうる暴走クエリを制限する
ALTER ROLE agent_ro SET statement_timeout = '15s';
ALTER ROLE agent_ro SET idle_in_transaction_session_timeout = '30s';

GRANT CONNECT ON DATABASE app TO agent_ro;
GRANT USAGE ON SCHEMA reporting TO agent_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA reporting TO agent_ro;
ALTER DEFAULT PRIVILEGES IN SCHEMA reporting
  GRANT SELECT ON TABLES TO agent_ro;
```

注意点があります。`default_transaction_read_only` はセッション自身が `SET` で解除できるため、単体ではシートベルトであって壁ではありません。壁になるのは、書き込み権限と昇格したメンバーシップが存在しないことです。両方を組み合わせてください。`INSERT` / `UPDATE` / `DELETE` の権限がなければ、設定を切り替えられても書き込めません。

さらに良いのは、ベーステーブルではなく**ビューで構成した reporting スキーマ**を公開することです。ビューなら機密カラムを除外し、事前にジョインし、エージェントが見る必要のないテーブルを隠せます。接続先がレプリカであれば、ロールの設定ミスがあってもプライマリには届きません。

## 信じるのではなく検証する

境界を信用するのではなく、証明するテストを追加します。エージェントが使うのと同じロールで実行してください。

```sql
-- agent_ro では、これらはすべて失敗しなければならない
INSERT INTO reporting.some_table DEFAULT VALUES;
CREATE TABLE reporting.should_fail (id int);
COPY (SELECT 1) TO PROGRAM 'id';
SELECT pg_read_file('/etc/passwd');
```

どれかが成功したなら、攻撃者のプロンプトより先に問題を見つけたことになります。このスクリプトをステージングのコピーに対する CI に組み込んでおけば、将来の権限変更でロールが広がったときにビルドが落ちます。

危険なメンバーシップを現在誰が持っているかも一覧にしましょう。

```sql
SELECT r.rolname, m.rolname AS member_of
FROM pg_auth_members am
JOIN pg_roles r ON r.oid = am.member
JOIN pg_roles m ON m.oid = am.roleid
WHERE m.rolname IN ('pg_execute_server_program', 'pg_write_server_files',
                    'pg_read_server_files');
```

## LLM とデータベースを接続する際の webhani の推奨

1. **postgres-mcp-server を使っているなら 1.1.7 以降へ更新し**、接続しているロールを見直します。
2. **エージェントの用途ごとに、最小権限の専用ロールを作る。** アプリケーションや管理者の認証情報を使い回さないでください。
3. **ツール内のバリデーターは多層防御として扱い、強制の層にしない。** バリデーターを外すと安全でなくなる構成は、そもそも安全ではありません。
4. **取得したコンテンツはすべて攻撃者の影響を受けうると想定する。** チケット、メール、スクレイピングしたページなど、モデルが読むものは指示を運べます。モデルがときどきそれに従う前提で、ツールの権限を設計してください。
5. **エージェントが発行したすべての文を、ロールとセッションとともにログに残す。** `COPY ... PROGRAM` の試行のような異常が見えるようになります。
6. **探索的なエージェント利用には、リードレプリカやビューといった管理されたアクセス経路を優先する。**

このパターンは Postgres に限りません。シェル、クラウド API、データベースのような強力なシステムを、テキストフィルタとして実装された「安全モード」で包んでいる MCP サーバーは、フィルタに穴があったときに何が起きるかを見直すべきです。そのときの答えは「基盤の認証情報自体が、それを実行できない」であるべきです。LLM エージェントを社内データの前に置く際、権限モデルの独立したレビューが必要でしたら、webhani がお手伝いします。
