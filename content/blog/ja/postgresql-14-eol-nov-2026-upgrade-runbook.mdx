PostgreSQLはメジャーバージョンごとに5年間サポートします。PostgreSQL 14は2021年9月にリリースされ、プロジェクトのリリーススケジュールや、それを追っているサードパーティの移行ガイドによると、最後の定期マイナーリリースは2026年11月12日です。その日以降、セキュリティ修正は出ません。本番にまだ14が残っているなら、猶予は約2週間です。

一方、PostgreSQL 19は10月15日に最初のリリース候補が公開され、プロジェクトの告知ではGAは11月19日の予定です。移行先の選択は明快です。今すぐ移行を迫られている本番DBなら、成熟していてマイナーリリースも重ねた18にします。19は、最初の数回のポイントリリースが出てから改めて検討してください。

以下は、自社運用（セルフマネージド）のインスタンスで使っている手順です。RDSやCloud SQLなどのマネージドサービスには独自の延長サポート規定と料金があるため、事業者のカレンダーを確認してください。流れ自体は同じように使えます。

## 方式を選ぶ

現実的な選択肢は3つです。

| 方式 | ダウンタイム | 複雑さ | 向いているケース |
|---|---|---|---|
| `pg_upgrade --link` | 数分 | 低 | 多くの単一ノードDB |
| `pg_upgrade`（コピー） | データ量に比例 | 低 | 手つかずのロールバック用コピーが欲しいとき |
| 論理レプリケーション | 切替時に数秒 | 高 | 大規模DBで、ほぼ無停止が必要なとき |

メンテナンス時間を取れる数TB程度までのDBなら、`--link`が現実的な既定値です。データファイルをコピーせずハードリンクするため、所要時間はデータ量よりオブジェクト数に左右されます。代わりに、新クラスタを起動した時点で旧クラスタは安全には使えなくなります。事前にバックアップかファイルシステムのスナップショットを必ず取ってください。

## ステップ1：触る前に棚卸しする

```sql
-- 拡張機能とバージョン
SELECT extname, extversion FROM pg_extension ORDER BY 1;

-- データベースごとのロケール設定
SELECT datname, datcollate, datctype FROM pg_database;
```

すべての拡張機能について、新しいメジャーバージョン向けの互換バイナリパッケージが入っている必要があります。リハーサルが失敗する最も多い原因は、拡張機能パッケージの不足です。

## ステップ2：復元したバックアップでリハーサルする

初めての`pg_upgrade`を本番で実行してはいけません。昨夜のバックアップを検証用ホストに復元し、所要時間を計りながら全手順を通してください。

```bash
# 18のバイナリを14と並べてインストールしてから:
/usr/lib/postgresql/18/bin/initdb -D /var/lib/postgresql/18/main

pg_upgrade \
  -b /usr/lib/postgresql/14/bin \
  -B /usr/lib/postgresql/18/bin \
  -d /var/lib/postgresql/14/main \
  -D /var/lib/postgresql/18/main \
  --link --check
```

`--check`は何も変更せずに互換性テストをすべて実行します。出力は最後まで読み、指摘された点を直して再実行し、問題がなくなってから`--check`を外します。

## 落とし穴1：データチェックサム

PostgreSQL 18では、`initdb`で作る新規クラスタのデータチェックサムが既定で有効です。`pg_upgrade`は新旧クラスタの設定が一致していることを要求します。14のクラスタをチェックサムなしで作っている場合は、アップグレード用に18側を`--no-data-checksums`で初期化するか、別の作業時間に`pg_checksums`で有効化する計画を立てます。正確なオプション名は、お使いのマイナーバージョンの18リリースノートで確認してください。

## 落とし穴2：照合順序の変化はOSアップグレードに潜む

Postgresのアップグレードと同時にOSイメージも変わると、glibcの照合順序バージョンが新しくなることがあります。テキスト列のインデックスが微妙に不整合になる恐れがあります。アップグレード後に次を比較してください。

```sql
SELECT collname, collversion, pg_collation_actual_version(oid)
FROM pg_collation
WHERE collversion IS DISTINCT FROM pg_collation_actual_version(oid);
```

行が返れば、その照合順序に依存するインデックスは`REINDEX`が必要です。可能であれば、OSとPostgresのアップグレードは別の変更として切り分けてください。

## 落とし穴3：アップグレード後の統計情報

古いメジャーバージョンでは`pg_upgrade`の際にプランナ統計が破棄され、切替直後にクエリが遅くなる原因になっていました。18ではこれが改善され、オプティマイザ統計の大半が引き継がれますが、拡張統計など一部は対象外です。新クラスタを起動したら次を実行します。

```bash
vacuumdb --all --analyze-in-stages --missing-stats-only
```

このフラグは統計のないリレーションだけに処理を絞ります。お使いのクライアントが受け付けない場合は、通常の`--analyze-in-stages`が安全な代替です。

## ステップ3：切替チェックリスト

1. 作業時間を周知し、アプリケーションの書き込みを止める。
2. スナップショットまたはベースバックアップを取り、保存場所をチケットに記録する。
3. 14を正常停止する（`pg_ctl stop -m fast`）。
4. `--check`を付けずに`pg_upgrade --link`を実行する。
5. 18を起動し、上記の`vacuumdb`を実行してから、拡張機能を更新する（`ALTER EXTENSION ... UPDATE`）。
6. `psql`だけでなく、実際のアプリケーションでスモークテストを行う。
7. 書き込みを再開し、エラー率とp95レイテンシを1時間監視する。
8. 旧データディレクトリは削除を決めるまで触らない。新クラスタが書き込みを受けた後は、ロールバックは14の再起動ではなくバックアップからの復元になります。

## 見落としがちな点

- **コネクションプーラーとドライバー**：PgBouncerとドライバーのバージョンが18の認証の既定値に対応しているか確認してください。先日取り上げたPgBouncerのアドバイザリのパッチ水準も念頭に置いてください。
- **レプリカ**：プライマリを`--link`でアップグレードしても、スタンバイは更新されません。追随を期待せず、新プライマリから再構築するか、pg_upgradeのドキュメントにある`rsync`方式を使います。
- **監視ダッシュボード**：`pg_stat_*`の一部の列はバージョン間で変わっています。エクスポーターとダッシュボードが正しく表示されるか確認してください。
- **バックアップツール**：`pgBackRest`や`wal-g`の設定を新しいデータディレクトリに合わせて更新し、すぐにフルバックアップを取ってください。

## webhaniの推奨

11月12日は目標ではなく、動かせない期限として扱ってください。リハーサルは今週、本番作業は来週に設定し、少なくとも一度は実際に復元したことのあるロールバック用の成果物を持っておきます。今は18に着地し、19は新年に落ち着いて進める別プロジェクトとして計画するのがよいでしょう。
