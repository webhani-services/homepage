PostgreSQL 14 は本日、2026年11月12日に End of Life を迎えます。PostgreSQL プロジェクトの 5 年間のサポートポリシーにもとづき、今日が 14 系の最後の定期マイナーリリースの日です。これ以降、14 系にはバグ修正もセキュリティパッチも提供されません。来月公開される CVE は、14 では修正されないということです。

マネージドサービスを使っている場合、プロバイダーによっては有償の延長サポートなどで 14 をしばらく動かし続けられます。時間は稼げますが、コミュニティがもうメンテナンスしていないブランチの上にいるという状況は変わりません。各プロバイダーが公表しているスケジュールを確認したうえで計画を立ててください。

ここでは、私たちがお客様の環境でこの種のアップグレードを進める際の考え方を、14 から 18 へ 3 メジャーバージョンを飛び越えるケースを中心にまとめます。

## 移行先は 15 ではなく 18

15 へ上げるのが最小の変更ですが、15 自体が 2027年11月に EOL になります。1 年後にまた同じ作業をすることになります。

PostgreSQL 19 は今月下旬に GA の予定です。私たちは通常、新しいメジャーバージョンを最初の数回のマイナーリリースを待たずに本番投入することは避けています。そのため、多くのチームにとって現時点での現実的な移行先は **PostgreSQL 18** です。十分に成熟しており、2030年までサポートされ、`pg_upgrade` で 14 から直接上げられます。

## ステップ 1：14 クラスタの棚卸し

移行方法を決める前に事実を集めます。重要な情報はおおむね次のクエリで取れます。

```sql
-- バージョンと主要な設定
SELECT version();
SHOW data_checksums;
SHOW password_encryption;

-- 拡張機能とバージョン
SELECT extname, extversion FROM pg_extension ORDER BY extname;

-- まだ MD5 ハッシュを使っているロール
SELECT rolname FROM pg_authid WHERE rolpassword LIKE 'md5%';

-- データベースサイズ（ダウンタイム見積もりに使う）
SELECT datname, pg_size_pretty(pg_database_size(datname))
FROM pg_database ORDER BY pg_database_size(datname) DESC;
```

拡張機能はそれぞれ 18 向けのビルドがあるか確認します。PostGIS や pgvector、pg_partman はたいてい問題ありません。止まりやすいのは、小規模な拡張や社内製の拡張です。

## ステップ 2：14 から 18 までの変更点を把握する

3 メジャー分を飛ばすということは、3 回分の挙動変更をまとめて受けるということです。実際にトラブルになりやすいものを挙げます。

**`public` スキーマの権限（15 以降）**：新しく作るデータベースでは、`public` スキーマへの `CREATE` 権限が全ユーザーには付与されなくなりました。`pg_upgrade` は既存の権限を引き継ぎますが、アップグレード後に作られるデータベース（マイグレーションツールが作るテスト用 DB を含む）では挙動が変わります。アプリケーションのロールが `public` にテーブルを作るなら、明示的に GRANT してください。

**データチェックサムがデフォルト有効（18）**：18 の `initdb` は、明示的に無効にしない限りデータチェックサムを有効にします。`pg_upgrade` は新旧クラスタの設定が一致している必要があります。14 側が `data_checksums = off` なら、新クラスタは `--no-data-checksums` で初期化し、チェックサムを有効にするかどうかは別のメンテナンス枠で `pg_checksums` を使って判断します。

**MD5 パスワードの非推奨化（18）**：18 でも MD5 認証は動きますが、非推奨の警告が出るようになりました。アップグレードを機に、残っているロールを SCRAM-SHA-256 に移行しましょう。

```sql
SET password_encryption = 'scram-sha-256';
ALTER ROLE app_user PASSWORD 'new-secret-from-your-vault';
```

すべてのクライアントライブラリが対応していることを確認したら、`pg_hba.conf` も `scram-sha-256` に切り替えます。古いドライバーが障害になることが多いです。

**削除・変更された機能**：15、16、17、18 のリリースノートの「Migration」セクションを順に読んでください。地味な作業ですが、切り替えに失敗してからデバッグするより短時間で済みます。

## ステップ 3：アップグレード方法を選ぶ

| 方法 | ダウンタイム | 向いているケース |
| --- | --- | --- |
| `pg_upgrade --link` | 数分 | セルフマネージド、同一ホスト、短時間の停止が許容できる |
| 論理レプリケーション | 切り替え時に数秒 | 大規模 DB、厳しい SLA、ホスト移行も同時に行う |
| マネージドの Blue/Green | 短時間（サービス依存） | RDS、Aurora、Cloud SQL、Azure |
| `pg_dump` / `pg_restore` | 大規模 DB では数時間 | 小規模 DB、整理も兼ねたい場合 |

セルフマネージドの場合は、必ずチェックモードから実行します。

```bash
/usr/lib/postgresql/18/bin/pg_upgrade \
  --old-datadir=/var/lib/postgresql/14/main \
  --new-datadir=/var/lib/postgresql/18/main \
  --old-bindir=/usr/lib/postgresql/14/bin \
  --new-bindir=/usr/lib/postgresql/18/bin \
  --link --check
```

`--link` はファイルをコピーせずハードリンクを使うため高速ですが、新クラスタを一度起動すると旧クラスタは起動できなくなります。本番実行の前に、リストア確認済みのバックアップを取っておいてください。

## ステップ 4：アップグレード後

PostgreSQL 18 の `pg_upgrade` はプランナー統計の大部分を引き継ぐため、以前のバージョンで問題になっていたアップグレード直後の性能低下はかなり緩和されています。ただし、拡張統計など一部は再作成が必要です。全体を ANALYZE する代わりに、不足している分だけを対象にできます。

```bash
vacuumdb --all --analyze-in-stages --missing-stats-only
```

そのうえで、主要なクエリの実行計画をアップグレード前に取得したベースラインと比較します。私たちは `pg_stat_statements` からコストの高い上位 10 件を抜き出し、前後で `EXPLAIN` を比べるようにしています。

## webhani の見解

EOL の日付は事前にわかっているのに、スキャナーや監査で指摘されて初めて気づくチームを私たちはよく見かけます。必要なのは特別な対応ではなく、すべてのデータベースのサポート期限を、証明書の更新と同じカレンダーに入れておくことです。PostgreSQL はポリシーが固定されているので簡単です。メジャーバージョンのサポートは 5 年間で、最終リリースは 11 月です。

今日の時点で 14 のままでも緊急事態ではありません。ただ、パッチが当たらないリスクを受け入れている状態になりました。今四半期中にアップグレードを計画しましょう。

## まとめ

- PostgreSQL 14 には本日の最終リリース以降、修正が提供されない
- 来年また同じ作業をしないよう、15 ではなく 18 を移行先にする
- 方法を決める前に、拡張機能・チェックサム・MD5 ロールを棚卸しする
- `pg_upgrade --check` を実行し、新クラスタのチェックサム設定を旧クラスタに合わせる
- 切り替え後は `vacuumdb --missing-stats-only` を実行し、実行計画を比較する
