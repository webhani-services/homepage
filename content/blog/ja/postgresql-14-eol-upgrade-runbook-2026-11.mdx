PostgreSQLのバージョニングポリシーのページによると、PostgreSQL 14の最終リリースは **2026年11月12日** です。これ以降、14系へのバグ修正やセキュリティ修正はコミュニティから提供されません。現在のマイナーバージョンは14.24で、初回リリースは2021年9月なので、予定どおり5年間のサポートが終わる形です。

14がまだどこかで動いていても、11月13日にすぐ問題が起きるわけではありません。ただし、今後見つかるCVEはすべて「パッチを当てられないもの」になります。本記事では、webhaniがこの種のアップグレードで使っているランブックを紹介します。

## ステップ1: 14.xのインスタンスをすべて洗い出す

本番のデータベースだけが対象とは限りません。コンテナ、CI、ローカルの開発環境も確認します。

```bash
# コンテナイメージとcomposeファイル
grep -RnE "postgres(ql)?:14|postgres:14" --include="*.yml" --include="*.yaml" --include="Dockerfile*" .

# CIのサービスコンテナ
grep -RnE "image:\s*postgres" .github/workflows/ 2>/dev/null

# Terraform / IaC
grep -RnE "engine_version\s*=\s*\"14" --include="*.tf" .
```

稼働中のサーバーでは、READMEに書かれたバージョンではなく実際のバージョンを確認します。

```sql
SELECT version();
SHOW server_version_num;  -- 14xxxx なら 14.x
```

Amazon RDSやAuroraなどのマネージドサービスは、コミュニティのEOL後も有償の延長サポートを提供しているのが一般的です。時間は稼げますが、それはコストであって計画ではありません。利用中のサービスの期限と料金を確認し、それを締め切りとして扱ってください。

## ステップ2: 移行先のバージョンを決める

現在サポートされているのは15から18です。拡張機能やマネージドサービスの制約がなければ、**18**(現在18.6、2030年11月までサポート)へ直接上げることを推奨します。14から15に上げても、サポート期間は1年しか延びません。

PostgreSQL 19はリリース候補(RC)の段階です。本番のアップグレード先を19.0にするのは避け、いくつかマイナーリリースが出て安定するのを待つのが無難です。

14から18へ上げる場合に特に押さえておきたい点です。

- **18ではinitdbでデータチェックサムがデフォルトで有効** です。`pg_upgrade` は新旧クラスタの設定が一致している必要があります。14のクラスタがチェックサムなしで作られている場合は、新クラスタを `--no-data-checksums` で初期化するか、事前に旧クラスタで `pg_checksums` を使って(停止状態で)有効にします。
- **MD5パスワード認証は非推奨** となり、警告が出ます。この機会にSCRAM-SHA-256へ移行しましょう。
- **`pg_upgrade` がプランナー統計を引き継ぐ** ようになりました(拡張統計は除く)。アップグレード直後にクエリが遅くなる期間が短くなります。

15、16、17、18のリリースノートにはそれぞれ「非互換」のセクションがあります。4つのメジャーバージョンを飛ばすなら、4つとも読む必要があります。

## ステップ3: 何より先に拡張機能を確認する

アップグレードが失敗する原因の多くは拡張機能です。

```sql
SELECT extname, extversion FROM pg_extension ORDER BY extname;
```

それぞれについて、移行先バージョン向けのビルドがあるか確認します。PostGIS、pgvector、TimescaleDB、`pg_partman` などは、`pg_upgrade` の前に新クラスタ側へ対応パッケージをインストールしておく必要があります。

## ステップ4a: pg_upgradeでインプレース移行

セルフマネージドのサーバーの多くは `pg_upgrade` が最もシンプルです。必ず先にチェックモードで実行します。

```bash
# 設定を合わせて新クラスタを初期化
/usr/lib/postgresql/18/bin/initdb -D /var/lib/postgresql/18/main \
  --no-data-checksums --encoding=UTF8 --locale=C.UTF-8

# ドライラン: 何も変更せずに非互換を報告する
/usr/lib/postgresql/18/bin/pg_upgrade \
  --old-bindir=/usr/lib/postgresql/14/bin \
  --new-bindir=/usr/lib/postgresql/18/bin \
  --old-datadir=/var/lib/postgresql/14/main \
  --new-datadir=/var/lib/postgresql/18/main \
  --check
```

`--check` で問題がなければ、バックアップを取って旧サーバーを停止し、`--check` を外して同じコマンドを実行します。`--link` を付けるとコピーではなくハードリンクを使うため、大きなデータベースでも高速に終わります。ただし新クラスタを一度起動すると、旧クラスタは安全に起動できなくなります。使う前に、リストアを検証済みのバックアップを用意してください。

アップグレード後は次を実行します。

```bash
# 引き継がれなかった統計情報を補完する
vacuumdb --all --analyze-in-stages --missing-stats-only
```

## ステップ4b: ロジカルレプリケーションでほぼ無停止の移行

停止時間を秒単位に抑えたい場合は、新バージョンをロジカルレプリケーションのサブスクライバーとして構築し、追いついた時点でアプリケーションの接続先を切り替えます。

```sql
-- 14.x(パブリッシャー)側
CREATE PUBLICATION upgrade_pub FOR ALL TABLES;

-- 18.x(サブスクライバー)側。先に pg_dump --schema-only でスキーマを作成しておく
CREATE SUBSCRIPTION upgrade_sub
  CONNECTION 'host=old-db dbname=app user=replicator'
  PUBLICATION upgrade_pub;
```

制約も把握しておきます。ロジカルレプリケーションはシーケンスとDDLを複製しません。切り替え前に書き込みを止め、`setval` でシーケンスの値を合わせ、移行期間中はスキーマ変更を凍結します。主キーのないテーブルでUPDATEやDELETEを複製するには、`REPLICA IDENTITY` の設定が必要です。

## ステップ5: コンテナとCI

composeファイルの `postgres:14` を `postgres:18` に書き換えても、データはアップグレードされません。新しいメジャーバージョンは古いデータディレクトリでは起動しません。ローカル開発環境なら、ボリュームを作り直してシードし直すのが一番簡単です。また、公式Dockerイメージは18からデフォルトのデータディレクトリ構成が変わっているため、既存のボリュームのマウントパスを使い回す前にイメージのドキュメントを確認してください。

CIのサービスコンテナも同時に更新し、本番と同じバージョンでテストが走るようにします。

## まとめ

- PostgreSQL 14の最後のコミュニティ修正は2026年11月12日です。
- Docker、CI、IaCも含めて、14.xのインスタンスをすべて洗い出します。
- 特段の制約がなければ18を移行先にし、飛ばすメジャーバージョンの非互換をすべて確認します。
- 拡張機能を最初に確認し、`pg_upgrade --check` を実行し、検証済みのバックアップを用意します。
- 停止時間を最小にしたいならロジカルレプリケーションを使い、シーケンスの同期を忘れないようにします。
- マネージドサービスの延長サポートは、解決策ではなく有償の猶予期間として扱います。

webhaniでは、セルフマネージドのPostgreSQLとAWS RDS/Auroraの両方でデータベースのアップグレードを支援しています。本番切り替えの前に、本番相当のデータで予行演習を行うところまで含めて対応します。
