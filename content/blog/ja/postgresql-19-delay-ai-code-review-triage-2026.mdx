PostgreSQL 19 は10月15日に RC1 が公開されましたが、GA は11月19日に延期され、RC2 は11月12日の予定です。The Register の報道を元にした二次情報によると、コミッターの Peter Eisentraut 氏は「LLM を使ったレビューで、修正が追いつかない速さで欠陥が見つかった」と説明し、SQL/PGQ を含む8〜10件ほどの主要機能がリリースブランチから revert されたとのことです。元の pgsql-hackers のスレッドは確認できていないため、件数や発言は「報じられている内容」として読んでください。

正確な数字がどうであれ、この件は良い教材になります。欠陥を「見つける」コストが急に下がった一方で、「判断して直す」コストは下がっていない、という状況で何が起きるかを示しているからです。

## アップグレード計画への影響

今四半期に PostgreSQL 19 の導入を予定していた場合、実務上の影響は小さいはずです。

- **RC を本番の primary に使わないでください。** RC はテスト用です。
- **それでも RC1 での検証は続けてください。** revert された機能はブランチから外れますが、デフォルト値の変更や削除された挙動はアップグレードで問題になりやすい箇所です。スキーマと遅いクエリを RC1 に流しておけば、11月19日より前に問題を見つけられます。
- **19.0 の直後に 19.1 が出る前提で計画してください。** 新しいメジャーバージョンは最初のマイナーリリースを待ってから重要システムに入れる、というのが当社の習慣です。終盤に変更が多かったリリースなら、なおさらです。

使い捨ての RC1 インスタンスで行う最小限のスモークテストの例です。

```bash
# 直近の論理ダンプを使い捨ての RC1 コンテナに復元
docker run --rm -d --name pg19rc -e POSTGRES_PASSWORD=test -p 5433:5432 postgres:19rc1
pg_restore --no-owner -h localhost -p 5433 -U postgres -d postgres latest.dump

# 遅い上位10クエリの実行計画を比較
psql -h localhost -p 5433 -U postgres -f slow_queries_explain.sql > explain_pg19.txt
diff explain_pg18.txt explain_pg19.txt
```

RC 用のイメージタグはレジストリによって異なるため、実際に公開されているタグを確認してから使ってください。

## 本題:指摘は安く、判断は高い

多くのチームが何らかの形で AI レビューを導入し始めています。今回の延期は、クライアント案件でも見てきた失敗パターンの公開事例です。AI レビューアは「もっともらしい指摘」を大量に出します。そして各指摘について、人間が次の3点に答える必要があります。

1. 本物か(再現できる、またはコードから証明できるか)
2. 重要か(到達可能か、ユーザーに見えるか、セキュリティ上の意味があるか)
3. 今、安全に直せるか

指摘の増えるペースが、この3点に答えるペースを超えると、チームは止まるか、レビューアを無視し始めます。どちらも、レビューアがいない状態より悪い結果です。

### 破綻しにくいトリアージ構成

既存のコードベースに AI レビューを入れるとき、当社が勧めている構成です。

**再現手順か根拠の提示を必須にする。** ファイル、行範囲、具体的な失敗入力を示せない指摘は自動的に破棄します。次のようなプロンプトで出力を実用的に保てます。

```text
各指摘について、file、行範囲、severity(crash / data loss /
incorrect result / style)、それを引き起こす最小の入力または呼び出し手順を出力してください。
手順を構築できない場合は "unverified" とラベルし、1行にとどめてください。
```

**マージを止める基準を重大度で分ける。** マージをブロックするのは、再現手順のある「crash」「data loss」「incorrect result」だけにします。それ以外は PR ごとではなく、週次で見直すバックログに回します。

**仕掛かり数に上限を設ける。** あるモジュールに未対応の AI 指摘が5件あれば、そのモジュールへの新規スキャンは件数が減るまで止めます。形式的に見えますが、誰も読まなくなる無限のキューを防げます。

**量ではなく精度を測る。** 人間が「本物」と認めた指摘の割合を追います。半分を切るようなら、スキャン範囲を広げる前にプロンプトや対象を絞ってください。件数は見かけの指標にすぎません。

**指摘ごとに担当者を置く。** 担当のない指摘は、誰にも閉じられません。作成時に割り当てます。

### 早めに revert する

既知の問題を抱えたまま出荷せず、機能を外すという Postgres チームの判断も参考になります。確信の持てない変更は、ブランチが開いている間なら安く戻せますが、リリース後は高くつきます。アプリケーションチームなら、デフォルト OFF の feature flag が同じ役割を果たします。終盤に疑義が出ても、その機能だけを外して残りを出荷できます。

## 当社の推奨

データベース利用者へ:PostgreSQL 19 の検証は続けつつ、本番の切り替え時期は 19.1 以降に置いてください。余った数週間で、リリースノートの非互換項目のチェックを進められます。

AI レビューを導入するエンジニアリングリードへ:スキャン範囲を広げる前に、トリアージの仕組みへ投資してください。希少なのはレビューアの注意力であり、再現手順・担当者・明確な重大度を備えた指摘だけにそれを使う設計が要になります。
