IBMのサポート向けアドバイザリが、PostgreSQLの複数の不具合を取り上げています。その中に、`timeofday()`関数でサーバーメモリが開示される問題があり、CVSSは8.8とされています。修正版として挙げられているのは18.4、17.10、16.14、15.18、14.23です。私たちが確認したページには公開日が表示されておらず、リリース日も特定できませんでした。そのため、ここに書いた数値に基づいて動く前に、PostgreSQLのセキュリティページと公式リリースノートで詳細を確認してください。

この記事は脆弱性そのものの詳細解説ではありません。多くのチームが苦手とする、PostgreSQLのマイナーリリースをどれくらい急いで適用するか、そして驚きなく適用するにはどうするか、という実務の話です。

## マイナーリリースが「簡単なアップグレード」である理由

PostgreSQLのバージョニングでは、変更の種類が分けられています。マイナーリリース(例: 17.9から17.10)にはバグ修正とセキュリティ修正のみが含まれ、ディスク上のフォーマットは変わりません。そのため、ダンプとリストアなしでバイナリを元に戻せます。メジャーリリース(17から18)は変更が大きく、計画的なアップグレード手順が必要です。これはプロジェクトのバージョニングポリシーに記載されています。

だからこそ、マイナーリリースを溜めないようお客様にお伝えしています。何回分もスキップすると、最終的なジャンプのレビュー範囲が大きくなり、既知のセキュリティ修正も未適用のままになります。

## メモリ開示の緊急度を判断する

CVSSの数値だけでは、自分たちが影響を受けるかどうかはわかりません。組み込み関数の情報漏えいバグでは、次の3点を考えます。

1. **誰が呼び出せるか**: マルチテナントのアプリ、レポート用ユーザー、SQLを実行できるAIエージェントなど、信頼できない、または半分しか信頼できないロールが任意のSQLを実行できるなら、リスクは現実的です。アプリケーションの固定クエリしかデータベースに届かないなら、リスクは低くなります。
2. **何が漏れうるか**: サーバーメモリには、他のセッションのデータ、クエリ文、場合によっては認証情報が含まれます。悪用が難しくても、機微な情報になりうるものとして扱います。
3. **信頼できない相手がデータベースに到達できるか**: ネットワークへの露出、共有された認証情報、広すぎる`GRANT`はいずれもリスクを高めます。

3点目は、別の記事でも触れたテーマにつながります。ツールやエージェントに与えるデータベースアクセスです。LLM駆動のツールにSQLを実行させるなら、早めにパッチを当て、権限を絞った読み取り専用ロールを使ってください。

## 稼働中のバージョンを確認する

まず、すべてのインスタンスで正確なバージョンを確認します。ステージングと本番が一致しているとは思い込まないでください。

```sql
SELECT version();
SHOW server_version;
```

次に、自分のメジャーバージョンの修正版と比較します。RDS、Cloud SQL、Azure Databaseなどのマネージドサービスを使っている場合は、プロバイダー自身の告知を確認してください。マネージドサービスは独自のスケジュールで修正を適用し、メンテナンスウィンドウ中にマイナーバージョンアップを自分でトリガーまたはスケジュールする必要がある場合もあります。

環境をまたいだ簡単な棚卸しスクリプトがあると時間を節約できます。

```bash
for host in db-prod-1 db-prod-2 db-staging; do
  echo -n "$host: "
  psql -h "$host" -U monitor -Atc "SHOW server_version;"
done
```

## マイナーアップグレードの進め方

自己管理のサーバーでは、保守的な順序が有効です。

1. 自分のメジャーバージョンのリリースノートを読みます。特に「migration to version X」のセクションです。マイナーリリースでも、特定の種類のインデックスの再作成など、アップグレード後の手順が必要になることがあります。
2. ステージングのインスタンスをアップグレードし、テストスイートと現実的なクエリ負荷を流します。
3. 先にレプリカをアップグレードし、昇格またはフェイルオーバーしてから、元のプライマリをアップグレードします。ダウンタイムはフェイルオーバーの時間だけで済みます。
4. 1日ほどエラーログとレプリケーション遅延を監視します。ロールバック用に、以前のパッケージバージョンを残しておきます。

コンテナ構成では、フローティングタグではなく、マイナーバージョンまで固定したイメージタグを使うと、アップグレードがプルリクエスト上の意図的な変更になります。

```yaml
services:
  db:
    image: postgres:17.10   # pin the minor; bump deliberately
```

`postgres:17`のようなフローティングタグは便利ですが、再起動するだけで気づかないうちにバージョンが変わる可能性があります。固定すれば、変更をレビューでき、元にも戻せます。

## まだ14を使っている場合

修正版の一覧に14が入っているので、まだ修正が提供されていることがわかります。PostgreSQL 14はサポート期間の終盤か終了間際にあり、アップグレード計画については当ブログの別記事でも扱っています。14を使っているなら、今回のパッチはつなぎと考え、マイナーリリースが今後も続くと期待せず、メジャーアップグレードを計画してください。

## まとめ

- 私たちが見たページには日付がなかったため、アドバイザリの詳細と修正バージョンはPostgreSQLの公式情報で確認する。
- マイナーアップグレードはリスクが低く、バイナリ単位で元に戻せる。特にセキュリティ修正は早めに適用する。
- 緊急度は、CVSSの数値だけでなく、インスタンスに対して誰がSQLを実行できるかで判断する。
- コンテナイメージのタグはマイナーバージョンまで固定し、プライマリより先にレプリカをアップグレードする。
- これを機に、特に自動化やAIツールに付与しているロールなど、データベースのロールを見直す。
