Python 3.15 は、追加のリリース候補を挟んだため予定日より1週間ほど遅れ、10月9日にリリースされました。lazy imports や新しい `frozendict` については多く語られています。この記事では、過大に受け取られがちな残り3つの目玉、JIT コンパイラ、新しい安定 ABI の `abi3t`、そして Free-Threading を扱います。

以下の数値や互換性の情報は、二次情報で引用された CPython の Release Notes と業界メディアに基づいています。ベンチマークの数値は情報源によって食い違うため、高速化の数字は自社で計測するための仮説として扱ってください。

## JIT:効果は控えめで、まだ実験的

3.15 の JIT コンパイラには、引き続き experimental のラベルが付いています。報告されている改善幅は、一桁台から十数%程度です。ある報告では x86-64 Linux でインタープリタ比の平均 8〜9%、別の報告では幾何平均で約 7〜8%、Apple silicon では 12〜13% とされています。これはベンチマーク全体の平均で、個々のワークロードは速くなることも、変わらないことも、遅くなることもあります。

一般的な Web バックエンドでは、この幅よりも「時間がどこで使われているか」のほうが重要です。リクエストハンドラの大半が DB、キャッシュ、外部 HTTP 呼び出しの待ち時間なら、インタープリタ内の CPU 律速ではないため、ループが速くなっても p95 レイテンシはほとんど動きません。JIT が効きやすいのは、パース、Python で書いたシリアライズ、テンプレート描画、データ変換といった、純粋な Python のタイトなループです。

注意点が2つあります。

- 2026年7月のニュースレターは、スレッドが起動すると JIT が自動的に無効になると報告していました。これが事実なら、スレッドを使うサーバーや Free-Threaded ビルドとの相性は良くありません。最終リリースで変わったという確認は取れなかったため、どちらとも決めつけず、自社の構成で確認してください。
- 実験的機能には安定性の約束がありません。本番で有効にするなら、1つのスイッチで無効に戻せるようにしておくべきです。

評価するには JIT 対応でビルドされたインタープリタが必要で、有効化は通常、環境変数で制御します。正確なビルドフラグと変数名は 3.15 のドキュメントで確認してください。比較用のハーネスは単純です。

```python
# bench_endpoint.py: CPU 律速のハンドラを2つの構成で同じように実行する
import time
import statistics

def handler(payload: dict) -> dict:
    # 実処理の代役。シリアライズや変換の実コードに置き換えてください
    return {k: str(v).upper() for k, v in payload.items()}

payload = {f"key{i}": i for i in range(200)}

def run(n: int = 20_000) -> float:
    start = time.perf_counter()
    for _ in range(n):
        handler(payload)
    return time.perf_counter() - start

samples = [run() for _ in range(7)]
print(f"median {statistics.median(samples):.3f}s  min {min(samples):.3f}s")
```

同じマシンで、JIT を有効にした場合と無効の場合の2回実行します。このようなマイクロベンチマークが示すのは上限です。そのうえで、実トラフィックを再生してアプリケーション全体で再計測してください。意味があるのはその数字です。

## abi3t:地味だがパッケージングへの影響が最も大きい変更

Free-Threaded ビルドの Python は、既存の安定 ABI(`abi3`)の Wheel を使えませんでした。そのため、ネイティブ拡張の作者は Free-Threaded インタープリタ向けに、Python バージョンごとに別の Wheel を配布する必要がありました。3.15 では Free-Threaded ビルド向けの安定 ABI である `abi3t` が追加され、1つの Wheel で複数バージョンに対応できるようになります。

ただし、報じられた Release Notes によると、ビルドツールがまだ追いついていません。setuptools、meson-python、scikit-build-core、Maturin は未対応と記載されていました。これはメンテナではなく利用者側にも実害があります。自社コードが純粋な Python でも、ネイティブ拡張を持つ依存(DB ドライバ、暗号ライブラリ、数値計算パッケージなど)に、3.15 向けの Free-Threaded Wheel がまだないかもしれません。その場合、`pip` はソースからビルドするか、失敗します。

Free-Threaded 化を計画する前に、棚卸ししておきましょう。

```bash
# 対象のインタープリタで新しい環境を作り、実際に何が解決できるかを見る
python3.15t -m venv .venv-ft
. .venv-ft/bin/activate
pip install --only-binary=:all: -r requirements.txt
```

`--only-binary=:all:` を付けると、ソースビルドが必要なパッケージは明示的に失敗します。その失敗が、実際の阻害要因の一覧です。インタープリタ名の `t` サフィックスは Free-Threaded ビルドの一般的な表記ですが、お使いのインストーラーが提供する名前は確認してください。

## Free-Threading:サポートされたが、デフォルトで勧めるものではない

Free-Threading は 3.14 で experimental ではなくなり、3.15 では公式の macOS インストーラーで既定で有効になったと報じられています。これは成熟度のシグナルであって、サーバーを切り替えるべきというシグナルではありません。

Web サービスにとっての変化は、スレッド内の CPU 負荷の高い処理が1プロセスで複数コアを使えるようになる点です。これにより、ワーカープロセス数と、プロセス間で重複するメモリを減らせる可能性があります。変わらないのは、すでに Gunicorn や Uvicorn の背後で複数ワーカープロセスを動かしているなら、コアはすでに使えているという点です。効果が大きいのは、プロセス間で安価に共有できない大きなメモリ上の状態を持つサービスです。

リスクは想像どおりです。GIL が隠していたスレッドセーフティのバグが顕在化し、スレッドセーフでない拡張モジュールが誤動作することがあります。Free-Threaded ビルドのシングルスレッド性能は、通常のビルドより多少低い傾向があったため、計測してください。

## 当社の推奨

1. **3.15 へのアップグレードは通常の理由で行う**:lazy imports、UTF-8 の既定エンコーディング、新しい型、サポート対象バージョンであること。通常の(GIL あり)ビルドで行います。
2. **JIT は実験として扱い**、CPU 律速のパスに限ってベンチマークします。平均値を根拠に全環境で有効にしないでください。
3. **`--only-binary` の棚卸しを今のうちに実施する**:依存ツリーが Free-Threading にどこまで対応しているかが分かります。10分で済み、来年の判断材料になります。
4. **Free-Threaded の本番投入は見送る**:1プロセスでマルチコアを使いたい具体的な課題と、並行性のバグを見つけられるテストカバレッジがある場合を除きます。

新しい Python のリリースは、地味な採用が報われます。サポート対象のバージョンに移り、既定の設定を保ち、実験の予算は計測でボトルネックと分かった場所に使うことです。
