Python 3.15.0 は2026年10月9日にリリースされ、続けて 3.15.1、3.15.2 のメンテナンスリリースも出ています。リリースノートは長いですが、アプリケーション開発チームにとって重要なのは、明示的な lazy import、組み込みの `frozendict`、組み込みの `sentinel`、そしてテキストエンコーディングの UTF-8 デフォルト化の4点です。このうち、手を入れていない既存コードの挙動を変えうるのは最後の1つだけです。以下の構文例は公式の "What's New" に基づいています。細かい仕様に依存する場合は、必ず原文で確認してください。

## 明示的な lazy import（PEP 810）

CLI、サーバーレスのハンドラー、テストランナーでは、起動時に重いモジュールを十数個 import しておきながら、実際に使うのは2つだけ、ということがよくあります。3.15 では `lazy` というソフトキーワードが追加され、名前が最初に使われるまでロードを遅らせられます。

```python
lazy import json
lazy from pathlib import Path

print("starting")            # どちらのモジュールもまだ完全には import されていない
data = json.loads('{"a": 1}')  # ここで json が import される
```

知っておくべき制約は次のとおりです。

- `lazy` はモジュールスコープでのみ使えます。関数内、クラス本体、`try`/`except`/`finally` ブロック内では `SyntaxError` になります。
- `lazy from x import *` と `lazy from __future__ import ...` も `SyntaxError` です。
- グローバルな切り替えとして `-X lazy_imports` または `PYTHON_LAZY_IMPORTS` があり、`all` か `normal`（既定）を指定できます。

実務上は `try`/`except` の制約が効いてきます。オプション依存を `try: import x except ImportError` で包む定番のパターンは lazy にできません。また、import の失敗が表面化するタイミングも変わります。lazy import では、モジュールの欠落や循環 import が起動時ではなく初回使用時に発覚します。起動時にすぐ分かっていた失敗が、あまり通らないコードパスでの実行時エラーに変わる可能性があります。

**使いどころ:** サブコマンドの多い CLI のエントリポイント、コールドスタートが問題になる Lambda 型のハンドラー、大規模なテストスイート。**避けたい場所:** プラグイン登録、パッチ適用、ログ設定など import 時の副作用を持つモジュール。遅延させると実行順序が変わるためです。

導入前後で必ず計測してください。`python -X importtime -c "import yourapp"` でモジュール別のコストが分かります。たいてい、2〜3個のモジュールが大半を占めています。

## frozendict（PEP 814）と sentinel（PEP 661）

`frozendict` は不変でハッシュ可能なマッピングです。`dict` ではなく `object` を直接継承しています。

```python
config = frozendict(region="ap-northeast-1", retries=3)
config["retries"] = 5   # TypeError: 要素の代入は不可
```

すべてのキーと値がハッシュ可能なときにハッシュ可能で、等価性の比較では挿入順序は無視されます。用途としては、変更されてはならないデフォルトオプション、現状は dict をソート済みタプルに変換して作っているキャッシュキー、モジュールレベルの定数などが考えられます。

`dict` を継承していないため、`isinstance(x, dict)` は `False` になります。`dict` で型判定しているコード（シリアライザやバリデーター）に `frozendict` を渡す前に、確認が必要です。

組み込みの `sentinel` は、読みやすい repr を持つ一意なマーカーオブジェクトを提供します。ドキュメントによると、コピーしても同一性が保たれ、型式で `|` と組み合わせて使えます。ログで repr が読みにくく、型付けも扱いづらかった `_MISSING = object()` という自前パターンの置き換えになります。

## UTF-8 がデフォルトに（PEP 686）

`encoding` を指定せずに `open("notes.txt")` を呼ぶと、3.15 ではロケールに関係なく UTF-8 が使われます。以前はロケールで決まっていたため、レガシーなコードページ（日本語なら cp932、韓国語なら cp949）の Windows と Linux コンテナで挙動が食い違っていました。

多くのチームにとっては不具合の解消になります。リスクがあるのは逆のケースです。古い社内システムが出力する cp932 の CSV を、ロケール既定に頼って読んでいたスクリプトは、3.15 では `UnicodeDecodeError` になるか、さらに悪いことにエラーなく誤ってデコードされます。レガシーなソフトウェアとファイルをやり取りする日本・韓国のシステムでは、ここが監査ポイントです。

```bash
# encoding 未指定の open() を洗い出す
grep -rnE "open\([^)]*\)" --include='*.py' src | grep -v "encoding="
```

退避策として `PYTHONUTF8=0` または `-X utf8=0` がありますが、長期的な解決策としては勧めません。レガシー入力が実在する箇所には `encoding="cp932"` を、それ以外には `encoding="utf-8"` を明示し、インタプリタのモードに挙動が左右されないようにします。

## そのほかの変更点

ドキュメントの非推奨・削除リストから、気づいた点を挙げます。

- `profile` モジュールは非推奨で、3.17 で削除予定です。代わりに `cProfile` を使います。
- モジュール属性 `__cached__` は削除されました。`__spec__.cached` を使ってください。
- `re.match()` と `Pattern.match()` は soft-deprecated となり、`re.prefixmatch()` と `Pattern.prefixmatch()` が推奨されます。
- 実験的な JIT は大幅に改善されたと説明されています。二次情報では x86-64 Linux で約7〜8%の向上とされていますが、プラットフォームやワークロードに依存し、JIT は依然として実験的です。ベンチマークなしに本番で有効化することは勧めません。

## アップグレード計画

1. **CI で 3.15 のテストを走らせる。** 現行バージョンの隣にマトリクスとして追加し、いきなり置き換えない。
2. **`open()`、`read_text()`、`subprocess` のテキストモード呼び出し**で、暗黙のエンコーディングに依存している箇所を洗い出す。
3. **依存パッケージが 3.15 向けの wheel を出しているか確認する。** C 拡張を含むパッケージは対応が最も遅くなりがちです。
4. **lazy import は1つの CLI かハンドラーで試す。** `-X importtime` で計測しながら導入します。
5. **本番サービスは数回のパッチリリースを待つ。** 3.15.2 がすでに出ているのは良い兆候ですが、私たちは通常、2〜3回目のパッチと自社テストの安定を確認してからサービスを移行します。

Python 3.15 は大きな破壊を伴うリリースではありません。言語の追加機能はオプトインです。頼まなくても適用されるのは UTF-8 デフォルト化だけで、アップグレード前に意識的に grep をかける価値があります。
