Python 3.15がリリースされました。python.orgによると、正式版の公開日は2026年10月9日です。リリースの紹介記事はPEPを網羅的に並べがちですが、ここではWebバックエンド、CLI、データ処理ツールで影響が大きそうな変更と、既存環境を壊し得る変更を1つに絞って取り上げます。

内容は公式の「What's new in Python 3.15」に沿っています。新しい機能はエッジケースの文書化が進行中のため、構文や挙動は利用前に公式ドキュメントで確認してください。

## lazy import(PEP 810)

大きなPythonアプリケーションで最も多い不満は起動の遅さです。重い依存ツリーをimportするCLIは、実行したコマンドがそれを使わない場合でも、毎回そのコストを払います。

これまでの回避策は、関数内でのimportや自作のlazy loaderでした。Python 3.15では`lazy`キーワードが追加され、言語側で扱えるようになります。

```python
# cli.py
lazy import pandas as pd
lazy from sqlalchemy import create_engine

def report(path: str) -> None:
    # pandasは初回利用時にここで実際にimportされる
    df = pd.read_csv(path)
    print(df.describe())

def version() -> None:
    # このコマンドはpandasもsqlalchemyも読み込まない
    print("1.4.2")
```

ドキュメントには制約も記載されています。lazy importはモジュールスコープでのみ許可され、関数内、クラス本体、`try`ブロックの中では使えません。

使いどころは次のとおりです。

- **サブコマンドの多いCLIや開発ツール**:起動時間が体感に直結します。
- **サーバーレス関数**:コールドスタートの時間が課金と体験に影響します。
- **大きなモノリス**:ほとんどのリクエストが使わないオプション連携のimportを抱えている場合。

注意したいのは、importエラーや副作用が発生する「タイミング」が変わる点です。依存パッケージの欠落は従来なら起動時に失敗しましたが、`lazy`では初回利用時、つまり本番で利用頻度の低いパスで初めて失敗する可能性があります。採用する場合は、lazyにしたモジュールをすべて通すテストか、CIで明示的に解決する起動チェックを追加してください。

## frozendictとsentinel

小さな2つの組み込みが、以前からの欠落を埋めます。

**`frozendict`**はイミュータブルでハッシュ可能なmappingです。これまでは`types.MappingProxyType`(読み取り専用ビューでハッシュ不可)や自作ラッパーが使われていました。設定オブジェクト、キャッシュキー、防御的コピーなしでスレッド間共有したいデータに向いています。

**`sentinel`**(PEP 661)は、一意のマーカーオブジェクトを作る標準的な方法です。従来の`_MISSING = object()`でも動きますが、`repr`が読みにくく、コピーやpickleで同一性が崩れます。専用のsentinel型でこれが解消されます。

```python
MISSING = sentinel("MISSING")

def get_setting(name: str, default=MISSING):
    value = _store.get(name, MISSING)
    if value is MISSING:
        if default is MISSING:
            raise KeyError(name)
        return default
    return value
```

`None`が正当な値であるAPIで、「指定されていない」と「Noneを明示した」を区別したい場面で特に役立ちます。ライブラリで採用する前に、コンストラクタの正確なシグネチャを公式ドキュメントで確認してください。

## comprehension内のアンパック(PEP 798)

新しい構文では、comprehensionの中でアンパックができます。よくあるネストしたループを書かずに済みます。

```python
batches = [[1, 2], [3], [4, 5]]
flat = [*batch for batch in batches]   # [1, 2, 3, 4, 5]

configs = [{"a": 1}, {"b": 2}]
merged = {**cfg for cfg in configs}    # {"a": 1, "b": 2}
```

可読性の改善であり、性能向上の機能ではありません。動いているコードをわざわざ書き換える必要はありませんが、新規コードは読みやすくなります。

## エンコーディングのデフォルトがUTF-8に(PEP 686)

計画しておくべき変更はこれです。Python 3.15では、`open()`などの既定エンコーディングがプラットフォームのロケール依存ではなく、UTF-8になります。

多くのLinuxやmacOSのサービスでは、もともとロケールがUTF-8なので変化はありません。リスクがあるのは次の2か所です。

- **WindowsやレガシーなロケールのEnvironment**:誰も気づかないままUTF-8以外の既定エンコーディングで読んでいたファイルが、デコード結果が変わったり`UnicodeDecodeError`になったりする可能性があります。
- **古いツールが地域別エンコーディングで書き出したデータ**:Shift_JISやEUC-KRなどのファイルを、`encoding=`なしで開いている場合。

日本語や韓国語のデータパイプラインでは特に関係します。対策は既定値に頼らないことです。

```python
# UTF-8以外のファイルは明示する
with open("legacy_export.csv", encoding="shift_jis", newline="") as f:
    rows = list(csv.reader(f))
```

現実的な点検方法は、`encoding=`のない`open(`呼び出しを検索し、警告を有効にしてPython 3.15でテストを走らせることです。この変更による失敗は多くの場合はっきり表面化するため、発見はしやすいです。

## パフォーマンスとプロファイリング

JITの改善も含まれています。数値は情報源によって異なり、プラットフォームに応じて幾何平均で約7〜12%の改善と報告されています。JITは引き続き実験的で、デフォルトでは無効です。自社のワークロードで計測してから有効化し、見出しの数値でキャパシティ計画を立てるのは避けてください。

組み込みの統計的サンプリングプロファイラ(ドキュメントによると新しい`profiling`パッケージ)は、実行中のプロセスにアタッチできます。計装を入れて再デプロイせずに本番の遅延を調べられる点は便利ですが、オーバーヘッドと必要な権限は事前にドキュメントで確認してください。

## アップグレードの進め方

1. 切り替える前に数週間、CIで現行バージョンと並行して3.15のテストを実行します。
2. `open()`やsubprocessのテキスト処理に、暗黙のエンコーディング依存がないか点検します。
3. 主要な依存パッケージが3.15用のwheelを公開するまで待ちます。ネイティブ拡張を持つパッケージが律速になりがちです。
4. `lazy import`はまずCLIのエントリポイントで採用します。効果を測りやすいためです。
5. `frozendict`と`sentinel`は、新規コードでの任意の整理として扱います。

## まとめ

Python 3.15は、破壊的すぎず有用なリリースです。lazy importは明確なトレードオフのもとで起動時間の改善が見込め、`frozendict`と`sentinel`は手作りのパターンを置き換えます。UTF-8のデフォルト化だけは、特に日本語・韓国語のデータファイルを扱うチームで、明示的な点検が必要です。
