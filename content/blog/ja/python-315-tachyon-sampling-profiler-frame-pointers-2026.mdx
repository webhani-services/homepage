Python 3.15の話題は、明示的なlazy importと新しい`frozendict`に集まりがちです。ただ、本番でPythonのサービスを動かすチームにとっては、あまり語られない次の2点のほうが重要かもしれません。組み込みのサンプリングプロファイラを含む`profiling`パッケージの再編成と、インタプリタのビルドでフレームポインタが既定で有効になることです。どちらも「いまこのプロセスはどこで時間を使っているのか」を、より少ない手間で知るための変更です。以下の内容は、公式の「What's New in Python 3.15」ドラフトと関連するPEP（799、831）に基づきます。ドキュメントはまだドラフトの扱いなので、依存する前に正式なリリースノートで確認してください。

## 何が変わるのか

**PEP 799：`profiling`パッケージ。** Pythonのプロファイリングツールが、1つの名前空間にまとめられます。

- `profiling.tracing`：呼び出しごとに記録する決定論的なトレーサ。`cProfile`から移されたものです。
- `profiling.sampling`：新しい統計的サンプリングプロファイラで、名前はTachyonです。

`cProfile`は後方互換のためのエイリアスとして残ります。古い`profile`モジュールは非推奨で、Python 3.17で削除される予定です。

**PEP 831：フレームポインタを既定で有効化。** ネイティブのスタックフレームを確実にたどれるようにインタプリタがビルドされます。`perf`やeBPFベースのプロファイラといったシステムレベルのツールが対象です。これらはこれまで、Pythonプロセスで読みやすいスタックを得るのに苦労してきました。

## サンプリングが重要な理由

`cProfile`のような決定論的プロファイラは、すべての関数呼び出しを計測します。呼び出し回数は正確に分かりますが、オーバーヘッドが測定結果を歪めます。何百万回も呼ばれる小さな関数が実際より悪く見え、稼働中のサービスに使うことも普通はありません。

サンプリングプロファイラは、プロセスのスタックを定期的に覗いて、いまどこにいるかを記録します。コストは小さくほぼ一定なので、本番に近い環境でも代表性のある結果が得られます。ドラフトのドキュメントでは、Tachyonは非常に高いサンプリングレートに対応すると説明されています。実際には、詳細さとオーバーヘッドのバランスでレートを選ぶことになります。見出しの数字を信用せず、自分のワークロードでオーバーヘッドを測ってください。

実務上の変化は、稼働中のプロセスにアタッチできる点です。遅いリクエストを追うために計測コードを入れて再デプロイする代わりに、すでに問題を抱えているプロセスにサンプラを向けられます。

## 試すためのワークロード

デモ用に、意図的に無駄を入れた小さな関数を用意しました。うっかり二乗オーダーになっている箇所があり、サンプラならはっきり見えるはずです。

```python
# report.py
import json


def build_index(rows):
    index = []
    for row in rows:
        # 挿入のたびに線形探索: 全体でO(n^2)
        if row["id"] not in [r["id"] for r in index]:
            index.append(row)
    return index


def render(rows):
    return json.dumps(build_index(rows))


if __name__ == "__main__":
    data = [{"id": i % 5000, "v": i} for i in range(20000)]
    for _ in range(5):
        render(data)
```

3.15をインストールしたら、`python3.15 -m profiling.sampling --help`で正確な呼び出し方を確認してください。コマンドラインの仕様は正式リリース前に変わる可能性があります。サンプルの大半を`build_index`が占め、その中のリスト内包表記が目立つはずです。修正は、見たIDを集合で持つことです。

```python
def build_index(rows):
    seen = set()
    index = []
    for row in rows:
        if row["id"] not in seen:
            seen.add(row["id"])
            index.append(row)
    return index
```

修正後にもう一度プロファイルして比較します。サンプラは、一度きりの診断よりも、修正前後の比較に向いたツールです。

## フレームポインタとシステムプロファイラ

フレームポインタがあれば、`perf`はネイティブのスタックを低コストでたどれます。Linuxでの一般的な手順は次のとおりです。

```bash
perf record -F 99 -g -p <pid> -- sleep 30
perf report --stdio | head -50
```

インタプリタ、C拡張、カーネルにまたがる時間配分を1つのビューで確認できます。Python専用のプロファイラにはできないことです。遅さの原因がデータベースドライバや数値計算の拡張といったネイティブライブラリの内部にある場合に、特に役立ちます。

フレームポインタにはレジスタを1つ占有する小さなコストがあります。Pythonプロジェクトは、可観測性のためにこのトレードオフを受け入れました。大きな差ではなく、わずかな性能差を想定し、レイテンシに敏感なら計測してください。また、Pythonコードのフレームに関数名を表示するには、インタプリタを理解するツールが引き続き必要です。フレームグラフが完全に読めると考える前に、使っているプロファイラがPython 3.15に対応しているかを確認してください。

## webhaniの推奨

1. **これだけを理由に移行しないでください。** Python 3.15は新しく、新しいマイナーバージョン向けのライブラリのwheelは遅れて提供されます。まずはCIのマトリクスに追加して試すのが現実的です。
2. **`profile`を直接importしていないか洗い出してください。** 社内ツールが使っていれば、3.17より前に`cProfile`か`profiling.tracing`へ切り替えます。
3. **再現できるプロファイリングの手順書を作ってください。** オンコールの担当者が本番コンテナにサンプラをアタッチする方法、必要な権限（ptrace関連のcapabilityが必要になることが多い）、出力の保存先を事前に決めておきます。
4. **トレーサはテスト用に残してください。** 呼び出し回数が重要なマイクロベンチマークや回帰テストでは、決定論的なプロファイリングにも出番があります。
5. **数値はその環境のものとして扱ってください。** サンプリングレート、オーバーヘッド、フレームポインタの影響は、ワークロードによって変わります。前後で測定してください。

## まとめ

Python 3.15のプロファイリング関連の変更は、稼働中のシステムでホットスポットを見つけるコストを下げます。サンプラはPythonレベルの視点を、フレームポインタはシステムレベルの視点を改善します。どちらも、適切なログやメトリクスの代わりにはなりません。それでも、性能インシデントで「アタッチして見てみる」を現実的な最初の一手にしてくれます。Pythonのバックエンドを運用していて、プロファイリングやオブザーバビリティを運用に組み込みたい場合は、webhaniにご相談ください。
