Goサービスの前段にRedisを置くとき、多くのチームは「Redis自体のCPU処理が速いから遅延も小さい」と考えがちです。それ自体は間違っていませんが、負荷のかかった実際のリクエストパスを見ると、ボトルネックはそこではないことがほとんどです。p99のグラフに現れる本当のコストは、アプリケーションプロセスとRedisサーバー間のラウンドトリップです。1リクエストで何個のキーに触れるかに比例して、このコストは積み上がっていきます。

2026年9月にリリースされたgo-redis 9.22.0は、このラウンドトリップの問題に正面から取り組む2つの実験的機能を追加しました。RESP3の`CLIENT TRACKING`を使ったクライアントサイドキャッシュと、自動パイプライニングです。すぐに採用するかどうかは別として、キャッシュという概念がクライアント層でどう変わりつつあるかを理解しておく価値はあります。

## コストの正体はRedisの処理時間ではなくラウンドトリップ

典型的なGo Webサービスが、あるリクエストでユーザーのセッション、3つのフィーチャーフラグ、共有Configの1項目を必要とするケースを考えます。素朴な実装では、Redisへの`GET`が5回発生します。同一AZ内のよくチューニングされたネットワークで1回のラウンドトリップが0.3msだとしても、Redisが何も処理していない段階ですでに1.5msのネットワークタックスが発生しています。負荷がかかりコネクションプールの競合やGCの一時停止が絡んでくると、この数字は改善されるどころか悪化していきます。しかもこれは全リクエスト、全レプリカ、毎分積み重なっていきます。

Redis自体はシングルスレッドで、単純なキー参照であれば数十マイクロ秒というレベルで非常に高速に処理します。「Redisの処理は50マイクロ秒で終わる」のに「ラウンドトリップには300マイクロ秒以上かかる」というミスマッチこそが、クライアントサイドキャッシュが存在する理由です。読み取りのラウンドトリップそのものを回避できれば、支配的なコストを消せます。

## RESP3 CLIENT TRACKINGが変えること

クライアント側でRedisへの負荷を減らす従来の方法は、TTL付きのローカルキャッシュ（`sync.Map`やLRUキャッシュ)をアプリケーションプロセス内に持つことでした。これは機能しますが、居心地の悪いトレードオフがあります。TTLを長くしすぎると書き込み後に古いデータを返してしまい、短くしすぎるとラウンドトリップがほとんど減りません。

`CLIENT TRACKING`はRESP3プロトコルの一部で、この推測作業そのものをなくします。クライアントがトラッキングを有効にすると、Redisはそのクライアントがどのキーを読み取ったかを記憶します。別のクライアント（あるいは同一クライアント）がそのキーを更新すると、Redisは同じコネクション経由で無効化メッセージをプッシュし、「あなたがキャッシュしたこの値はもう有効ではない」と通知します。クライアントはTTL失効を待たず、即座にローカルキャッシュからエントリを削除できます。

これは本質的な発想の転換です。クライアントが鮮度を「推測」するのではなく、サーバーが鮮度が失われたタイミングを「教えてくれる」のです。Goプロセス内のキャッシュは、Redisのキースペースの一部をベストエフォートで近似するものではなく、正しさを保証されたミラーになります。

## イメージをつかむためのコード例

以下は考え方の輪郭を示すための例示的なGoコードであり、go-redisのAPIをそのまま書き写したものではありません。実験的機能であり、APIの表面はまだ変わる可能性があるため、実際の実装時はgo-redis 9.22.0の公式ドキュメントで正確なメソッド名やオプションを確認してください。

Before（読み取りのたびにラウンドトリップが発生）:

```go
func GetFeatureFlag(ctx context.Context, rdb *redis.Client, key string) (string, error) {
    // 過去1時間フラグが変わっていなくても、毎回ネットワークを叩く
    return rdb.Get(ctx, key).Result()
}
```

After（クライアントサイドキャッシュを有効にした場合のイメージ）:

```go
// 例示: go-redis 9.22.0はRESP3のCLIENT TRACKINGを利用した
// オプトインのクライアントサイドキャッシュを提供する見込みです。
// 実際のAPI表面は異なる可能性があるため、あくまで相互作用パターンの
// スケッチとして扱ってください。
type TrackedCache struct {
    rdb   *redis.Client
    local *sync.Map // key -> キャッシュ値。サーバーからのプッシュで無効化される
}

func (c *TrackedCache) GetFeatureFlag(ctx context.Context, key string) (string, error) {
    if v, ok := c.local.Load(key); ok {
        return v.(string), nil // ラウンドトリップなし
    }

    val, err := c.rdb.Get(ctx, key).Result()
    if err != nil {
        return "", err
    }

    // この読み取り自体がRedis側でトラッキング対象として登録される。
    // バックグラウンドのgoroutineがこのコネクション上の無効化プッシュを
    // 消費し、Redisがキー変更を通知したらc.local.Delete(key)を呼ぶ。
    c.local.Store(key, val)
    return val, nil
}
```

重要なのは厳密なメソッドシグネチャではなく、このパターンです。完全にプロセス内で完結するローカル読み取りパスと、TTLに頼らずローカル状態の正しさを維持する別チャネル（無効化プッシュ）が分離されている点です。

自動パイプライニングは関連していますが別の問題を扱います。キャッシュなしでも、短い時間window内に複数の独立したRedisコマンド（たとえば複数のgoroutineがそれぞれ`GET`を発行するケース）が発生した場合、go-redisはそれらを1回のネットワークラウンドトリップに透過的にまとめることができます。`Pipeline`を手動で組み立てる必要はありません。これはデータの鮮度に関するセマンティクスを一切変えないネットワーク層の最適化なので、クライアントサイドキャッシュよりもリスクの低い機能です。

## 正しさに関わる注意点

クライアントサイドキャッシュはタダではありません。リスクのほとんどは以下の注意点に集約されます。

- **サーバー側のトラッキングテーブルにはメモリ上限がある。** Redisは、どのクライアントがどのキーをトラッキングしているかを記憶しておく必要があり、これはRedis側のメモリを消費します。多数のクライアントコネクションにまたがって非常にカーディナリティの高いキー集合をトラッキングすると、クライアント側のラウンドトリップ削減以上に、Redis本体に実質的なメモリ圧力をかけることになります。
- **切断・再接続時はローカルキャッシュを必ずフラッシュする。** 無効化プッシュを運ぶコネクションが切断されると、クライアントはその間に無効化通知を取りこぼしていないという保証を失います。安全な振る舞いは、再接続時にローカルキャッシュを全消去し、ゼロから再構築することだけです。クライアントサイドキャッシュの実装は、この処理を正しく行う必要があります。再接続後に古いエントリを黙って保持してしまうのは、些細な非効率ではなく本物の正しさのバグです。
- **ホットで読み取り頻度が高く、書き込みが少ないキーに効く。** フィーチャーフラグ、Config値、書き込み1回に対して何度も読まれるセッション参照はまさに狙い目です。削減できるラウンドトリップが受け取る無効化プッシュを大きく上回ります。
- **書き込みが多いキーには効かない。** 読み取りと同じ頻度で書き込まれるキーでは、書き込みのたびにトラッキング中の全クライアントへ無効化プッシュが送られます。結果として、無効化チャネルで支払うネットワークコストが読み取りで節約した分とほぼ相殺、あるいはそれを上回ります。カウンターやレート制限のバケット、頻繁に更新されるキューにとって、クライアントサイドキャッシュはほぼ純粋なオーバーヘッドです。

## webhaniの導入に関する推奨

既存のキャッシュ層を置き換えるものではなく、あくまで追加の選択肢として位置づけるべきだと考えています。現実的な導入手順は次の通りです。

1. まず、明確に読み取り中心で書き込みが少ないキーから始めます。フィーチャーフラグや静的なConfigが最初の対象として扱いやすく、セッション参照は次のステップとして妥当です。
2. 導入前後で無効化の発生頻度を計測します。トラッキングを有効にしたキーが読み取りとほぼ同じ頻度で無効化されているなら、そのキーでは機能していないということなので対象から外します。
3. 既存のキャッシュ層（CDN、明示的なTTL付きのアプリケーション内キャッシュ、リードレプリカ）はそのまま維持します。`CLIENT TRACKING`によるクライアントサイドキャッシュは、特定のアクセスパターンに効く狭く精密なツールであり、既存のキャッシュアーキテクチャ全体を置き換えるものではありません。
4. go-redis 9.22.0ではこの2機能とも実験的機能扱いなので、本番投入時はFeature Flagで制御し、対象キーを増やしていく前にRedis側のメモリ挙動、特にトラッキングテーブルのサイズを注意深く監視することを推奨します。

「クライアントがTTLで推測するのではなく、サーバーがキャッシュの誤りを教えてくれる」という発想自体は堅実です。その価値は、対象キーの選び方にすべてかかっています。
