## 「ほぼ同じ質問」への課金をなくす

LLMを組み込んだチャットボットやカスタマーサポートアプリを運用していると、ユーザーからの質問には「文字列としては違うが意味的にはほぼ同じ」ものが大量に含まれることに気づきます。「返品方法を教えて」と「商品を返品したいのですが」は、通常のキー・バリューキャッシュでは別物として扱われますが、意味的には同じ質問です。

Redisが提供するLangCacheは、この「意味的な重複」を検出してLLM呼び出し自体を省略するマネージド型のセマンティックキャッシュサービスです。埋め込みベクトルによる類似度検索を使い、過去に回答済みの質問と意味的に近い質問が来た場合はキャッシュ済みの回答をそのまま返し、一致しない場合のみ実際にLLMを呼び出します（参考: [Redis公式ドキュメント: Redis LangCache](https://redis.io/docs/latest/develop/ai/context-engine/langcache/)）。

## 仕組み：完全一致ではなく意味的一致

通常のキャッシュ（Redisの文字列キーなど）は完全一致でしかヒットしません。セマンティックキャッシュは、質問文を埋め込みベクトルに変換し、ベクトル空間上での類似度がしきい値を超えた場合にキャッシュヒットとみなします。

```text
質問A: "返品方法を教えてください"
質問B: "商品を返品したいのですが、どうすればいいですか"

→ 文字列としては不一致
→ 埋め込みベクトルの類似度は高い
→ セマンティックキャッシュではヒット扱い
```

LangCacheはこの埋め込み生成とベクトル検索をマネージドサービスとして提供し、REST API経由で利用できます。自前でベクトルDBとキャッシュ層を組み合わせて構築する手間を省ける点が、導入のハードルを下げています（参考: [Redis公式ブログ: What is semantic caching?](https://redis.io/blog/what-is-semantic-caching/)）。

## 実装イメージ

Redisが公開しているRedisVLライブラリを使ったセマンティックキャッシュの基本パターンを、公式ドキュメントで案内されている考え方に沿って示します。

```python
from redisvl.extensions.llmcache import SemanticCache

cache = SemanticCache(
    name="support_cache",
    redis_url="redis://localhost:6379",
    distance_threshold=0.15,  # 類似度のしきい値
)

def answer_question(question: str) -> str:
    cached = cache.check(prompt=question)
    if cached:
        return cached[0]["response"]

    response = call_llm(question)  # 実際のLLM呼び出し
    cache.store(prompt=question, response=response)
    return response
```

`distance_threshold` の値が小さいほど「厳密に似ている」質問だけをヒットとみなし、大きいほど幅広くヒットします。この値のチューニングが、セマンティックキャッシュ運用の要になります（参考: [Redis LangCache Docs](https://redis.io/docs/latest/develop/ai/redisvl/0.6.0/user_guide/llmcache/)）。

## しきい値チューニングの落とし穴

セマンティックキャッシュの最大のリスクは「誤ってヒットしてしまう」ことです。しきい値を緩く設定しすぎると、微妙にニュアンスの異なる質問（例：「返品したい」と「返品期限を過ぎたが返品できるか」）が同じキャッシュ回答を返してしまい、ユーザーに誤った情報を提示するリスクがあります。

運用上は次のような段階的アプローチを推奨します。

1. **保守的なしきい値から始める**：まずは厳しめの `distance_threshold` で運用し、キャッシュヒット率とユーザーからの苦情の両方をモニタリングします。
2. **カテゴリごとにしきい値を分ける**：FAQのような定型的な質問は緩めのしきい値でも安全ですが、価格や契約条件に関わる質問は厳しめに設定するなど、質問の性質に応じて調整します。
3. **キャッシュのTTLを設ける**：価格改定やポリシー変更があった際に古い回答がキャッシュされ続けないよう、有効期限を設定します。

## コストと遅延への効果

セマンティックキャッシュがヒットした場合、LLM呼び出し自体が発生しないため、トークン課金とレイテンシの両方をゼロにできます。FAQ的な質問が多いカスタマーサポート用途では、キャッシュヒット率が高くなりやすく、削減効果も大きくなります。

一方で、埋め込み生成とベクトル検索自体にもコストと遅延が発生するため、「LLM呼び出しより埋め込み検索の方が明らかに軽い」ことが前提になります。この前提が崩れるほど質問のバリエーションが多い、あるいはリアルタイム性が極めて重要なユースケースでは、恩恵が薄れる点に注意が必要です。

## webhaniの見立て

webhaniが顧客のAIチャットボットやサポート自動化を設計する際、セマンティックキャッシュは「万能の高速化装置」ではなく「質問の分布に偏りがあるワークロード向けの最適化」と位置づけています。導入前に次を確認することを推奨します。

- 過去の問い合わせログを分析し、実際にどれだけ「意味的に重複した質問」が存在するか定量化する
- 誤ヒットが許容できない領域（法務・医療・金銭に関わる回答など）ではキャッシュを使わない、または人間のレビューを挟む
- キャッシュヒット率とユーザー満足度の両方をダッシュボードで継続的に観測する

## まとめ

Redis LangCacheのようなセマンティックキャッシュは、LLMアプリケーションのコストとレイテンシを構造的に下げる手段として実用段階に入っています。ただし効果はワークロードの質問分布に大きく依存し、しきい値のチューニングを誤ると誤情報のリスクを抱え込みます。webhaniでは、こうしたキャッシュ戦略の設計と検証を含めたAIアプリケーション構築を支援していきます。
