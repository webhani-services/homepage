DeepSeek が、より自律的なコーディングエージェントのオープンソースのプロトタイプを公開しました。位置づけは Claude Code への対抗です。ただし本人たちの説明では、成熟した製品ではなくアーキテクチャの探求であり、私たちもベンチマークは取っていません。報道では構造上のアイデアが一つ紹介されており、システムが Router 層と複数の Worker セッションに分かれているというものです。

ここでは製品のレビューはしません。この分離自体が有用なパターンで、エンジニアにとって馴染みのある仕組みに対応づけられるからです。何であるか、どんなときに効くか、何がうまくいかなくなりやすいかを整理します。

## パターンの概要

エージェントの1つのセッションは、作業するうちにコンテキストをためていきます。読んだファイル、実行したコマンド、行き止まりの探索などです。このコンテキストは強みであると同時に限界でもあります。長いセッションは遅くなり、コストも増え、古い詳細でウィンドウが埋まると品質が落ちやすくなります。

Router/Worker の分離は、2つの役割を切り分けます。

- **Router:** 全体のゴールと短い計画を持ちます。次に何をするかを決め、範囲を区切ったタスクを Worker に渡し、簡潔な結果を受け取ります。コードにはほとんど直接触れません。
- **Worker:** 範囲の明確な1つのタスクと、必要なファイル、受け入れ基準を与えられた新しいセッションです。読み書きを行い、要約と差分を返し、そのコンテキストは破棄されます。

ジョブキューを使ったことがあれば見覚えがあるはずです。Router はコーディネーター、Worker はステートレスなコンシューマー、要約は両者の間のメッセージ契約にあたります。

## 利点

- **重要な場所でコンテキストを小さく保てる。** Router は、Worker が読んだすべてのファイルではなく要約だけを見ます。Worker はリポジトリの自分の担当部分だけを見ます。
- **並列化できる。** 無関係な3つのモジュールのテスト更新のような独立したタスクを、別々の Worker で同時に走らせられます。
- **失敗が局所化される。** 誤った道に入った Worker は、メインのセッションを汚さずに破棄して再試行できます。
- **レビューしやすい。** 各 Worker が、目的の明確な独立した変更を出力します。

## 最小限のスケッチ

以下の TypeScript は、制御フローを示すために書いたオリジナルの例であり、特定ベンダーの実装ではありません。`runWorker` は、お使いの環境でエージェントセッションを起動する処理の代わりです。

```ts
type Task = {
  id: string;
  goal: string;
  files: string[];          // この Worker が触ってよい範囲
  acceptance: string[];     // 「完了」を定義するチェック
};

type WorkerResult = {
  taskId: string;
  status: "ok" | "failed";
  summary: string;          // Router 向けの短い要約
  changedFiles: string[];
};

// 代替: 1つのタスクに絞った新しいエージェントセッションを起動する
declare function runWorker(task: Task): Promise<WorkerResult>;

async function runPlan(tasks: Task[], maxParallel = 3): Promise<WorkerResult[]> {
  const results: WorkerResult[] = [];
  const queue = [...tasks];

  async function lane() {
    for (let task = queue.shift(); task; task = queue.shift()) {
      let result = await runWorker(task);
      if (result.status === "failed") {
        // 失敗の要約を追加コンテキストとして、再試行は1回だけ。
        result = await runWorker({
          ...task,
          goal: `${task.goal}\n\nPrevious attempt failed: ${result.summary}`,
        });
      }
      results.push(result);
    }
  }

  await Promise.all(Array.from({ length: maxParallel }, lane));
  return results;
}
```

コードそのものより重要な点が2つあります。1つ目は `files` フィールドで、Worker は変更してよいファイルを宣言する、あるいは与えられるべきです。2つ目は `acceptance` です。客観的なチェックがない Worker は、自分では成功したと思っているので成功と報告します。

## 想定しておくべき失敗モード

**編集の衝突。** 2つの Worker が同じファイルを変更すると衝突します。並列に走らせる前に、ファイルの所有でタスクを分割し、分割が不明確なら直列実行に戻します。git で並列ブランチを扱うときと同じ問題で、対処も同じです。

**要約での情報欠落。** Router は Worker の報告に基づいて判断します。Worker が注意点を省くと、Router には取り戻せません。自由記述だけにせず、置いた前提や未実施のテストといった項目を明示した構造化された要約を求めてください。

**Router のドリフト。** 再計画を繰り返す Router はループしかねません。再計画の回数と Worker の総起動回数に上限を設け、その上限に達したことは人に知らせます。

**コストの倍増。** 並列の Worker はそれぞれ自分のコンテキスト分のコストを払います。このパターンはセッション単体の肥大を抑えますが、タスクの切り分けが悪いと総コストは増えます。セッション単位ではなく、完了したタスクあたりのトークン数を測ってください。

**自信満々の誤り。** 自律性が高いほど、人が誤った前提に早く気づく機会は減ります。エージェントがコードを大量に出す場合は[レビュー容量が本当のボトルネック](/blog/ai-agents-more-code-same-output-review-bottleneck-2026-10)だと以前の記事で書きましたが、Worker を扇状に広げるとこの点はさらに鋭くなります。

## 他のエージェントにも通用するガードレール

これらは特定のモデルやベンダーには依存しません。複数セッションの構成で私たちが勧める統制は次のとおりです。

1. **Worker ごとの最小権限。** 各 Worker に作業コピーまたはブランチを与え、認証情報はタスクの範囲に絞ります。
2. **決定的なゲート。** テスト、型チェック、リンターはエージェントの外で実行し、結果を受け入れるかどうかを決めます。
3. **フェイルクローズなフック。** ポリシーチェックを実行できない場合、許可ではなく拒否にします。詳しくは[フェイルクローズなフック](/blog/claude-code-hooks-fail-closed-guardrails-2026-10)の記事を参照してください。
4. **人のチェックポイントは、各ステップではなくマージ時に。** 統合された結果をレビューし、各 Worker の要約と差分は補助情報として参照できるようにします。
5. **監査証跡。** どの Worker がどのタスク記述からどの変更を作ったかを記録します。

## 今すぐ採用すべきか

すでにサブエージェントやフォークに対応したエージェントを使っているなら、必要な部品は揃っており、段階的に試せます。メインのセッションに、テスト生成や機械的な移行のような範囲の明確なタスクを委譲させ、アーキテクチャの判断はメインのセッションに残します。

登場したばかりのプロトタイプを本番ツールとして扱うのは慎重にしてください。新しいプロジェクトはアイデアの検証にはなっても、重要なリポジトリで無人運転できる状態とは限りません。私たちのお勧めは、使い捨てのリポジトリでアーキテクチャを評価し、現在の単一セッションのワークフローとコストやレビュー負荷を比べたうえで、特定の製品をツールチェーンに加えるかどうかを決めることです。
