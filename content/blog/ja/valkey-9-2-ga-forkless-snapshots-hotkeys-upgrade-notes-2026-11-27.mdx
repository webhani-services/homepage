Valkey 9.2 は2026年11月19日に GA となりました。RC を追っていた方には、目玉機能はおなじみのはずです。新しいのは、本番アップグレードを現実的に計画できるリリースになったという点です。この記事では、運用に影響する変更点と、展開前に私たちならどうテストするかをまとめます。

以下の内容は Valkey のリリース発表と二次情報に基づいています。第三者の比較記事にある性能値(たとえば Sorted Set の大幅なメモリ削減)は、こちらで検証したものではありません。必ず自分たちのデータで計測してください。

## 運用に効く変更点

**Forkless snapshot(オプトイン)。** RDB スナップショットとレプリカの full sync を、fork した子プロセスではなくバックグラウンドスレッドで実行できます。なぜ重要かというと、`fork()` は copy-on-write のメモリに依存しており、データセットが大きく書き込みが多いインスタンスでは、スナップショット中にメモリ使用量が急増しうるからです。このスパイクを吸収するためだけに RAM を多めに確保しているチームは少なくありません。有効化は `forkless-infrastructure-enabled` で、設定ファイルに書いて起動時に指定する必要があります。キーあたり4バイトの追加コストがかかると報告されています。`prefer-forkless` ポリシーでは、必要に応じて fork にフォールバックします。

**サーバー側の Hot Key 検出。** `hotkeys-top-k` を設定すると、`HOTKEYS GET` と `HOTKEYS RESET` で、どのキーにアクセスが集中しているかをサーバーに問い合わせられます。これまでは、本番では高コストで危険な `MONITOR` によるサンプリングや、クライアント側の計装が必要でした。

**B+ tree の Sorted Set。** Sorted Set が B+ tree 表現になり、メモリオーバーヘッドが下がります。`ZADD` ベースのリーダーボード、レートリミッター、遅延ジョブキューが特に恩恵を受けます。

**レプリケーション圧縮と ACL ロール。** レプリケーションの通信を圧縮でき(LZ4 または Zstandard と報じられています)、転送量課金のあるアベイラビリティゾーン間で効果があります。ACL ロールにより、権限管理の繰り返し作業も減ります。

## Forkless snapshot に最も注目する理由

メモリの余裕は、インメモリストアを運用する際の見えにくいコストです。fork 時の copy-on-write の最悪ケースに備えて、大きな空きメモリを残しておくのが一般的な経験則でした。書き込みパターンによっては forkless snapshot がうまく機能し、容量ぎりぎりまで使える、あるいは少なくともスナップショットの瞬間を気にしなくて済むようになる可能性があります。

オプトインなのには理由があります。バックグラウンドスレッドによるスナップショットは、fork 方式とレイテンシの特性が異なります。また、キーあたり4バイトは大きなキー空間では無視できません。10億キーなら約4GBです。無条件に得をすると決めつけず、テストしてください。

## アップグレードのテスト計画

リリース当日に本番を上げないでください。現実的な手順は次のとおりです。

1. **削除・変更された挙動をリリースノートで確認する。** 明示的に設定しているオプションは特に注意します。
2. **ステージングのプライマリのレプリカとして新バージョンを起動**し、同期させます。レプリケーション遅延とメモリが妥当か確認します。
3. **代表的なトラフィックを再生する。** コマンドパターンを取得し、平均ではなくレイテンシのパーセンタイルで比較します。
4. **書き込み負荷下でスナップショットを試す。** forkless あり・なしで、スナップショット中のピーク RSS と p99 レイテンシを記録します。
5. **フェイルオーバーを試す。** 新しいレプリカを昇格させ、クライアントが再接続できることを確認します。

スナップショット中のメモリ挙動を手早く比較する方法です。

```bash
# バックグラウンド保存を開始し、書き込みを続けながらメモリを観察する
valkey-cli BGSAVE
while true; do
  valkey-cli INFO memory | rg 'used_memory_rss_human|used_memory_peak_human'
  valkey-cli INFO persistence | rg 'rdb_bgsave_in_progress'
  sleep 1
done
```

同じ書き込み負荷のもとで、デフォルトの fork 経路と forkless 有効の2回実行します。ピーク RSS の差が、知りたい数字です。

Hot key 検出は、最初の確認なら手軽です。

```bash
# 起動時に設定ファイルで有効化: hotkeys-top-k 10
valkey-cli HOTKEYS GET
valkey-cli HOTKEYS RESET
```

コマンドの引数はビルドによって二次情報と異なる場合があるため、正確な構文は公式ドキュメントで確認してください。

## クライアントとマネージドサービスの注意点

- **クライアントライブラリ。** Valkey は Redis エコシステムとプロトコル互換なので、ほとんどのクライアントはそのまま動きます。新しいコマンドに依存するクライアント側機能だけテストしてください。
- **マネージドサービス。** クラウドのマネージド Valkey を使っている場合、アップグレード経路や forkless snapshot などの新機能の提供時期は事業者次第です。計画前にサポートバージョンを確認してください。
- **セキュリティパッチ。** ここ数か月、Valkey のセキュリティアドバイザリが複数出ています。パッチレベルが遅れているなら、新機能とは別の理由として更新を進めるべきです。

## webhani の推奨

Valkey をキャッシュやセッションストアとして使う一般的な Web アプリケーションなら、9.2 は急ぎではありません。通常のパッチ運用に合わせて更新し、実際に抱えている問題を解決する機能だけを有効にしてください。

次のいずれかに当てはまるなら、優先してテストする価値があります。

- fork のために確保しているメモリの余裕を取り戻したい。
- 原因不明のレイテンシスパイクがあり、hot key を疑っている。
- Sorted Set を多用していて、メモリが主なコストになっている。
- ゾーンやリージョン間でレプリケーションしており、転送コストが気になる。

いずれも、新機能が具体的で測定可能な課題に対応しており、それが採用の正しい理由です。まず測定し、設定は1インスタンスずつ切り替えてください。
