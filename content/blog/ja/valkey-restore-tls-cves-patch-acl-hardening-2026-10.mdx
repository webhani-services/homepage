夏の終わり頃から、LinuxディストリビューションがValkeyのセキュリティアップデートを配布しています。Red Hatのアドバイザリ（RHSA-2026:64807）はRHEL 9/10をValkey 8.0.10にリベースし、9月にはUbuntuのUSN-8771-1が続きました。このうち2件は、単にパッチを当てるだけでなく仕組みを理解しておく価値があります。どちらも、皆さんが管理できる設定で影響を狭められるからです。以下はNVDのエントリとディストリビューションのアドバイザリに基づきます。なお、まとめサイトの間でアドバイザリ番号が一致しない箇所があったため、お使いのベンダーの情報で確認してください。

## 2つの問題

**CVE-2026-63639：RESTOREにおける不正なストリームペイロード。** 細工したRDBストリームのペイロードを`RESTORE`で送ると、メモリ破壊が起き、最悪の場合はリモートコード実行につながります。攻撃者が`RESTORE`を実行できることが前提です。NVDでの公開は2026-08-18です。

**CVE-2026-56684：TLSの保留データにおけるuse-after-free。** TLSの保留データの扱いが不適切で、サーバーがクラッシュしたり、コード実行につながる可能性があります。悪用には、`CLIENT KILL`を実行できる認証済みクライアントが必要です。

どちらも7.2.14、8.0.10、8.1.9、9.0.5、9.1.1で修正されています。Ubuntuの通知には、クラスターのスロット移行に起因するサービス拒否（CVE-2026-85522）も含まれています。

いずれも、特定のコマンド権限を持つ認証済みクライアントが必要です。ここが重要な点で、認証なしでインターネットから突かれる種類のバグではありません。パッチ適用の緊急度と、適用までの間にどう露出を減らすかが変わってきます。

## ステップ1：実行中のバージョンを確認する

```bash
valkey-cli INFO server | grep -E "valkey_version|redis_version"
```

ステージング、CIのサービスコンテナ、バージョンを自分で制御できないマネージドインスタンスも含め、すべての環境を確認します。マネージドサービスの場合は、思い込まずに、提供元のステータスページで修正済みエンジンバージョンを確認してください。

上の修正済みリストと比較します。8.0系なら8.0.10、8.1系なら8.1.9が必要です。緊急パッチの最中にブランチを跨ぐことは避けてください。

## ステップ2：ACLで危険なコマンドを制限する

多くの環境では、デフォルトユーザーがすべてのコマンドを実行できます。アプリケーションコードが`RESTORE`や`CLIENT KILL`を必要とすることはほとんどありません。最小権限のユーザーを作ります。

```text
# valkey.conf または ACLファイル
user default off
user app on >REPLACE_WITH_STRONG_SECRET ~app:* &* +@read +@write +@connection -@dangerous -@admin
user ops on >REPLACE_WITH_OTHER_SECRET ~* &* +@all
```

`-@dangerous`は`KEYS`、`FLUSHALL`、`DEBUG`などを除外します。頼る前に、お使いのサーバーバージョンが各カテゴリに何を含めているか確認してください。

```bash
valkey-cli ACL CAT dangerous
valkey-cli ACL DRYRUN app RESTORE app:key 0 payload
valkey-cli ACL DRYRUN app CLIENT KILL ID 1
```

`ACL DRYRUN`は、`app`が両方とも権限を持たないと報告するはずです。アプリケーションの正当な機能が`RESTORE`を使う場合（移行やキャッシュのウォームアップ用ツールには使うものがあります）は、そのツール専用のユーザーにだけ権限を付与します。

## ステップ3：ネットワークへの露出を減らす

- プライベートなインターフェースにのみバインドし、アプリケーションホストだけが到達できるネットワークセグメントにValkeyを置きます。
- VPCの内側も含め、あらゆる場所で認証を必須にします。認証なしで到達できるインスタンスは、攻撃者がすでに完全な制御を持っているため、これらのCVEが問題になる以前の状態です。
- TLSは必要な場所でのみ有効にし、有効にしている場所では速やかにパッチを当てます。CVE-2026-56684はTLSの処理に関わるためです。
- デバッグのためにロードバランサーやポートフォワード経由でポートを公開し、そのまま放置しないでください。

## ステップ4：ロールバック計画を持ってパッチを当てる

レプリケーション構成では、レプリカを先に更新し、フェイルオーバーしてから、元のプライマリを更新します。前後でレプリケーションの状態を確認します。

```bash
valkey-cli INFO replication
```

キャッシュ専用の用途では再起動のコストは小さいですが、コールドスタート後のウォームアップでデータベースにかかる負荷は大きくなり得ます。再起動はずらして行い、データベースのCPUを監視してください。

## ステップ5：不正利用を監視する

想定外のユーザーによる`RESTORE`や`CLIENT KILL`をログに記録し、アラートを出します。ACLログが役立ちます。

```bash
valkey-cli ACL LOG 20
```

アプリケーションユーザーからの拒否が繰り返し出ている場合は、バグか探索行為のどちらかです。

## Redisから移行中の場合

Redisを使っている場合も同じハードニングが当てはまります。Red Hatのアドバイザリには、RedisのRESTOREの問題（CVE-2026-66373）も載っています。今年前半のRedis固有のアドバイザリについては、以前の記事「[Redisハードニングのチェックリスト](/blog/redis-rce-cve-2026-hardening)」をご覧ください。

## まとめ

現在のブランチ内で修正済みのポイントリリースにパッチを当て、アプリケーションユーザーから`RESTORE`と`CLIENT KILL`を外し、信頼できないネットワークから切り離し、ACLログを監視してください。ACLの変更はコストが小さく、次のコマンドレベルの脆弱性に対するリスクも下げます。マネージドインスタンスを含むキャッシュ基盤の監査が必要でしたら、webhaniのクラウドコンサルティングの一環としてお手伝いします。
