LLM を使った機能を運用していると、必ずこんな作業が発生します。新しいモデルが出た、あるいは既存モデルのコストが合わなくなった。そのたびに複数のリポジトリでモデル名の文字列を書き換え、レビューを通し、再デプロイする。Vercel の AI Gateway が提供する Virtual Models は、この文字列をコードの外に出すための仕組みです。

本記事では、機能の概要、プロジェクトでの組み込み方、事前に想定しておくべき失敗パターンをまとめます。内容は Vercel の changelog とドキュメントに基づいています。提供プランや制限は発表内で明示されていなかったため、導入前に最新情報を確認してください。

## Virtual Model とは

Virtual Model は AI Gateway に保存する設定です。スラッグ、背後のモデル、リクエストに適用する設定を持ちます。アプリケーションはスラッグをモデル ID として呼び出し（Vercel の例では `vmc/coding-agent` のような形式）、ゲートウェイが実際のモデルに解決します。背後のモデルをダッシュボードや CLI で変更すれば、再デプロイなしで全ての呼び出し元に反映されます。

Vercel によると、言語モデルだけでなく画像・動画・音声・Embedding・リアルタイムなどのモデル種別に対応し、AI SDK と OpenAI / Anthropic 互換 API のどちらからも利用できます。言語モデルを指す Virtual Model は、ゲートウェイがコーディングエージェント向けに返すモデルカタログにも掲載されます。

## AI SDK からの利用

アプリケーション側に特別な書き方は不要です。モデルは単なる文字列です。

```ts
import { generateText } from 'ai';

export async function summarizeTicket(body: string) {
  const { text } = await generateText({
    // AI Gateway で作成した Virtual Model のスラッグ（プロバイダのモデル ID ではない）
    // 正確な形式はゲートウェイ側の設定に従う
    model: process.env.SUMMARY_MODEL ?? 'vmc/ticket-summary',
    prompt: `次のサポートチケットを 3 点で要約してください:\n\n${body}`,
  });
  return text;
}
```

スラッグを環境変数にしておくと、ステージングと本番で別の Virtual Model を指せます。候補モデルを本番に近いトラフィックで試してから昇格させる、という運用がしやすくなります。

## 効果が出る場面

**モデル選定の変更箇所が 1 つになる。** チケット要約、コードレビューコメント、分類など、複数のサービスが同じ機能を呼ぶ場合、機能ごとに Virtual Model を 1 つ用意すれば切り替えは 1 か所で済みます。インフラ設定における DRY の適用です。

**プロバイダ側の変更に素早く追従できる。** 廃止や価格改定はプロバイダの都合で来ます。後継モデルへの移行がリリースではなく設定変更になります。

**責任分界を作りやすい。** アプリ側は「何をさせるか」を決め、コストと品質の担当者が「どのモデルで動かすか」を決める。モデル ID がコードにあると、この分離は徹底しにくくなります。

## 注意すべき点

間接層は、変更が見えにくくなることでもあります。広く導入する前に、次の点を検討しておくことをお勧めします。

1. **挙動が静かに変わる。** 背後のモデルを替えると、出力の文体、長さ、拒否の傾向、ツール呼び出しの安定性が変わります。JSON やツール引数をパースしている箇所は、デプロイ履歴と紐づかないまま壊れる可能性があります。
2. **監査証跡が弱くなる。** コード変更には Pull Request が残りますが、ダッシュボード操作は残らないことがあります。誰が編集できるか、変更をどこに記録するかを決めておく必要があります。
3. **評価のずれ。** 回帰テストがプロバイダのモデル ID を直書きしていると、本番で動いているものを検証していないことになります。評価は本番と同じスラッグで実行するか、解決後のモデルを記録してください。
4. **ゲートウェイへの依存。** スラッグの解決にゲートウェイが必要になります。すでにゲートウェイ経由なら状況は変わりませんが、障害分析には明記しておくべきです。
5. **コストの急変。** より大きなモデルへの切り替えが、全ての呼び出し元に一度に効きます。予算アラートとセットで運用してください。

## 導入の進め方

1. **リスクの低い機能から始める。** 顧客向けエージェントではなく、社内の要約処理などが適しています。
2. **スラッグはモデル名ではなく機能名にする。** `ticket-summary` はモデルを替えても使えますが、`gpt-fast` は使えません。
3. **変更の前後で評価セットを同じスラッグに対して実行する。** 結果は変更記録と一緒に残します。
4. **ステージングと本番でスラッグを分ける。** 評価が通ったら設定をコピーして昇格します。
5. **編集権限を絞り、変更理由を短く記録する。**
6. **構造化出力のパースは防御的にする。** zod などのスキーマで検証し、失敗の増加をロールバックの合図にします。

```ts
import { z } from 'zod';

const Summary = z.object({ bullets: z.array(z.string()).length(3) });

export function parseSummary(raw: string) {
  const result = Summary.safeParse(JSON.parse(raw));
  if (!result.success) {
    // ここでメトリクスを送出。スラッグ変更後の急増がロールバックの契機になる
    throw new Error('Summary output failed schema validation');
  }
  return result.data;
}
```

## webhani の見解

複数の LLM 機能を運用するチームにとって、Virtual Models は妥当な標準選択肢です。モデル選定が「リリース作業」から「運用上の判断」に変わるためです。一方、1 チームが 1 機能だけを持つ場合は、コード内の定数のほうが単純でレビューもしやすいでしょう。

リスクは技術ではなくプロセスにあります。デプロイ不要でモデルを替えられるということは、意図して仕組みを作らない限りレビューも不要になるということです。Virtual Model の変更は本番設定の変更として扱い、評価済みで、担当者が明確で、元に戻せる状態にしてください。そうすれば、日々の摩擦を確実に減らせます。
