今月のAI関連の週次まとめによると、CursorとGoogleがそれぞれコーディングエージェントに双方向の音声機能を追加し、7月から音声に対応しているとされるOpenAIのCodexに続いたとのことです。ただし情報源が少なく、細部は記事によって食い違っています。詳細は未確認として扱い、各ベンダーのリリースノートで確認してください。それでも、エージェントに話しかけて音声で返答を受け取る機能が、デモではなく標準機能になりつつあることは確かです。

私たちが注目しているのは「コードを口述できるか」ではありません。それは何年も前からできました。問題は、入力経路が音声になったとき、チームがエージェントを監督するやり方がどう変わるかです。

## 何が変わるのか

プロンプトをタイプするときは、意図を圧縮して書くことになります。話す場合は逆で、背景や制約、理由まで口に出して説明しがちです。これはまさにエージェントに不足しがちな情報です。経験上、質の低いプロンプトの多くは理由のない三行の指示です。音声は、冗長に説明するコストを下げることでこの問題を緩和する可能性があります。

双方向の音声は、非同期での監督もしやすくします。長いタスクの途中で「マイグレーションを修正しました。2ファイルでテストが失敗しています。続けますか?」と声で報告されれば、別のウィンドウで作業したり、席を離れたりできます。エディタ内のバックグラウンドエージェントで起きた変化と同じく、人間の役割は「運転」から「レビュー」へ移っていきます。

## 変わらないこと

音声は精密さに向いていません。ファイルパス、フラグ名、SQL、正規表現は、音声認識を通すと崩れやすくなります。厳密な内容にはテキストの画面が必要です。ツールが「何を聞き取ったか」を文字で表示するかどうかは重要です。識別子の聞き間違いは、気づかれないまま失敗につながります。

レビューも変わりません。音声で出した指示でも、生成されるdiffはタイプした場合と同じで、同じようにレビューが必要です。むしろ流暢な会話は、エージェントを実力以上に信頼できるように感じさせます。承認ゲートを維持すべき理由です。

## 評価チェックリスト

クライアント向けに音声対応エージェントを評価するとき、次の点を確認します。

1. **文字起こしの可視性**: エージェントが動く前に、理解した内容を確認・修正できるか。
2. **承認の境界**: 音声の「はい、進めてください」は、クリックと同じ操作を承認してしまうのか。ファイル削除、force push、マイグレーション実行のような破壊的操作を、曖昧な音声で承認できてはいけません。
3. **データの扱い**: 音声はどこへ送られるのか。端末内で処理されるのか、サーバーへ送られるのか。保持されるのか。契約中のエンタープライズプランで対象になるのか。周囲の会話を拾う可能性があるため、NDA下の案件では特に重要です。
4. **割り込み**: 声でエージェントの動作を途中で止められるか。確実に止められないツールは、長いタスクでは危険です。
5. **利用環境**: オープンオフィスや共有の通話環境、騒がしい場所では使いにくくなります。自宅での集中レビューには合っても、共有スペースでは難しいかもしれません。
6. **アクセシビリティ**: 腱鞘炎や運動機能に制約のある開発者にとって、音声は大きな利点です。それだけでも対応する価値があります。

## リスクを抑えた試し方

チーム全体へ一度に展開することはおすすめしません。小さく試す方が良いデータが得られます。

- 2〜3人の開発者と、テスト作成や小さなリファクタリングなど範囲の明確なタスクを1種類選ぶ。
- 既存の承認ポリシーは変えない。会話的なインターフェースだからと権限を緩めない。
- 数週間、タイプ入力のセッションとプロンプトの質、修正の往復回数を比較する。
- 参加者に、役立った場面とタイプに戻した場面を聞く。戻したタイミングに最も多くの示唆があります。

音声セッションとタイプのセッションでルールを揃えるには、ルールをテキストで明文化しておくと便利です。エージェントがプロジェクト単位の指示ファイルに対応しているなら、入力方法に関係なく適用できます。

```md
## Agent rules (apply to all sessions, typed or spoken)

- Never run destructive commands (rm -rf, git push --force, DROP) without
  showing the exact command and waiting for explicit written confirmation.
- Restate the file paths you intend to change before editing.
- If an instruction contains an identifier you are not sure you heard
  correctly, ask for it to be spelled or typed.
```

音声で特に重要なのは最後のルールです。識別子の確認を求めるのは低コストで、最も多い音声認識の誤りを防げます。

## webhaniの見解

コーディングエージェントの音声操作は、小規模かつ構造化した試行に値します。主な利点は、より豊富なコンテキストが得られやすいことと、長時間タスクをハンズフリーで監督できることです。精密さが必要な場面でテキストの代わりにはなりませんし、誰が何を承認するかも変えるべきではありません。入力方法が違ってもガードレールは同一にし、クライアントのコードで有効にする前にデータの扱いを確認し、印象ではなく結果で測ってください。

多くのエージェント機能と同じく、確認すべきは「修正の往復とレビューの負担が減ったか」です。減らなければ、物珍しさはすぐに消えます。
