現在のブラウザ上で動くAIエージェントの多くは、忍耐強いテスターが手動でテストするのと似た方法で動いています。スクリーンショットを撮り、「カートに追加」ボタンらしき要素を推測し、クリックし、待って、また撮る。この繰り返しです。動作はしますが、遅く、デザイン変更に弱く、モデルが毎ステップごとにピクセルやDOMツリーを解釈し直すため、トークンの消費量も大きくなります。

2026年2月10日に、GoogleとMicrosoftのエンジニアがW3C Web Machine Learning Community Groupの枠組みで最初に発表したWebMCPは、これとは別のアプローチを取ります。エージェントがページの機能を推測するのではなく、ページ側が直接伝える仕組みです。`navigator.modelContext`（および対になる`document.modelContext`）というJavaScript APIを通じて、サイトは呼び出し可能なツールの一覧——名前、説明、パラメータのスキーマ——を登録します。ブラウザ内で動くエージェントは、`addToCart`や`applyFilter`のようなツールを他の関数呼び出しと同じ感覚で直接呼び、構造化された結果を受け取れます。

現時点ではChrome 146 Canaryで実験的に提供され、Chrome 149ではPublic Origin Trialに移行しています。この記事の執筆時点ではまだDraft Community Group Report（2026年4月23日公開）の段階であり、確定した標準ではありません。各ブラウザでの安定版展開は2026年第4四半期あたりが目安とされています。以下の内容はすべて、まだ動きうる初期段階の仕様であるという前提で読んでください。

## なぜ重要なのか: 「エージェントが速くクリックできる」以上の話

実務上のドライバーはコストと信頼性です。スクリーンショットやDOMスクレイピングに基づくエージェント操作は、ステップごとにページ構造と意図を再推定する必要があり、トークンコストが高く、レイアウトが変わるたびに壊れやすくなります。初期の報告では、同等のタスクにおいてスクリーンショットベースの操作と比較して約89%のトークン削減があったという数字も出ています——これはあくまで初期ベンチマークに基づく参考値として扱うべきで、確約された仕様上の数字ではありません。ただ方向性としては、「型付き引数で関数を呼ぶ方が、レンダリングされたページを解析して同じ意図を推測するより安い」という直感と一致します。

正確さの観点でも意味があります。`checkout({ paymentMethodId, shippingAddressId })`をスキーマ付きのツールとして公開しているページであれば、エージェントがその週たまたまデプロイされているDOM構造に依存して、正しい見た目の状態で正しい順序でボタンをクリックする必要があるページに比べて、誤操作のリスクは明らかに低くなります。

## AnthropicのMCPとの関係

名前が似ているため混同しがちですが、この2つのプロトコルは異なる場所で異なる問題を解決しています。AnthropicのModel Context Protocol（MCP）はバックエンド間のプロトコルです。LLMホストアプリケーションと外部のツールサーバーを、多くの場合ローカルプロセスやネットワーク接続経由で接続し、データベースクエリやファイル検索など、ブラウザの外側に存在するツールをモデルが呼び出せるようにします。

一方WebMCPは完全にクライアントサイドで、ユーザーがすでに認証済みのブラウザセッション内で動きます。別途サーバーを立てる必要も、別の認証情報を管理する必要もありません。Webページ自体がツールサーバーになり、ユーザーがすでにログインしているのと同じセッションの中で動作します。これは認証が絡む機能にとって重要な違いです。WebMCPのツールは、ページ上のボタンクリックと同様に、ユーザーのセッションと権限をそのまま引き継ぎます。概念的には、この2つは競合するというより補完関係にあります。MCPはモデルをインフラやデータソースに接続するためのもの、WebMCPはモデルを特定のWebアプリケーション自身のUIレベルの操作に接続するためのものです。

## Next.jsアプリでのパターンをスケッチする

以下のコードはあくまで例示です。APIの表面はまだDraftの段階であり、メソッド名、オプション、登録のライフサイクルなどの詳細は正式版までに変わる可能性が高いです。そのままコピーして本番投入するコードとしてではなく、考え方の輪郭として読んでください。

React/Next.jsアプリでの妥当なパターンは、他のブラウザAPIを副作用として組み込むのと同様に、マウント時にツールを登録し、アンマウント時にクリーンアップする小さなフックです。

```tsx
// あくまで例示: APIの表面はW3CのDraftであり今後変わる可能性があります。
function useModelContextTool(tool: {
  name: string;
  description: string;
  inputSchema: Record<string, unknown>; // JSON Schemaに近い形
  execute: (input: unknown) => Promise<unknown>;
}) {
  useEffect(() => {
    if (!("modelContext" in navigator)) return; // Feature Detection

    const unregister = navigator.modelContext.registerTool(tool);
    return () => unregister();
  }, [tool]);
}
```

チェックアウト画面のコンポーネントでは、内部の生の状態をそのまま公開するのではなく、範囲を絞った操作を登録するイメージです。

```tsx
// あくまで例示。
function CheckoutSummary({ cartId }: { cartId: string }) {
  useModelContextTool({
    name: "applyDiscountCode",
    description: "現在のカートに割引コードを適用し、更新後の合計金額を返します。",
    inputSchema: {
      type: "object",
      properties: { code: { type: "string" } },
      required: ["code"],
    },
    execute: async (input) => {
      const { code } = input as { code: string };
      // 通常のフォーム送信が使うのと同じServer側のバリデーション経路を再利用する
      return applyDiscountCodeAction(cartId, code);
    },
  });

  return /* 既存のUIをそのまま返す */ null;
}
```

ここで重要なのは`execute`の最後の行です。ツールのハンドラーは、通常のUIがすでに使っているのと同じServer ActionやAPI Routeを呼び出しています。WebMCPは既存の、すでに検証済みのビジネスロジックへの新しい入り口であるべきで、独自ルールを持つ別のコードパスであってはいけません。

## 実務上の注意点

- **これはまだDraftであり、確定した標準ではありません。** メソッド名、登録のライフサイクル、スキーマの形式さえも、一般提供までに変わる可能性があります。今の段階で組み込むものは、Feature Detectionを前提にし、いつでも取り外せる状態にしておくべきです。
- **登録したツールはそれぞれ新しい認可の境界になります。** 状態を変更するツールであれば、対応するUI操作とまったく同じServer側のチェック——認証、所有権の確認、Rate Limiting——が必要です。認証済みセッションからエージェントがツールを呼び出しているからといって、ボタンをクリックするユーザーより本質的に信頼できるわけではなく、バリデーションを迂回させてはいけません。
- **ツールの説明文は、人間ではなくモデルに向けたAPI契約として機能します。** 曖昧な説明は、ドキュメント不足のREST Endpointが誤用されるのと同様に、エージェントが誤ったツールを呼んだり不正な入力を渡したりする原因になります。公開APIのドキュメントを書くのと同じ注意深さで説明文を書くべきです。
- **ブラウザ対応は現時点でChromeのみ、しかも実験的機能です。** クロスブラウザでの保証はまだなく、他のエンジンが異なる形・異なるタイミングでAPIを実装する可能性もあります。
- **可観測性の整備が追いついていません。** エージェントによるツール呼び出しは、クリックイベントと同じAnalyticsのファネルには現れません。早期に導入するチームは、後から気づくのではなく、最初からツール呼び出しを別軸でログ・監視する計画を立てておくべきです。

WordPress Playgroundチームによる初期の実験——ネストされたiframeからWebMCPツールを公開し、Proxy経由で埋め込み先のサイトに呼び出しを転送する——は、この技術がどこへ向かうのかを示す興味深い兆候です。トップレベルのページだけでなく、埋め込みウィジェットやサードパーティコンポーネントも同様にツールを公開するようになれば、iframeをまたいでツール呼び出しを転送する際の信頼境界という新たな論点も出てきます。

## webhaniとしての推奨

現時点で本番アプリケーションをWebMCP前提に作り直すことは推奨しません。まだ1つのブラウザのOrigin Trial上で動くDraft Community Group Reportの段階です。ただし、自社サイトにエージェントが関わりやすいユースケースがあるなら、今のうちにプロトタイプとして試す価値はあります。ECのチェックアウトフロー、CRUD操作が明確なSaaSダッシュボード、検索中心のUIなどが最初の候補として扱いやすいでしょう。

試すのであれば、状態を変更しない検索・フィルタリング・データ参照系のツールから始め、状態を変更する操作を公開するのは後回しにすることを勧めます。`navigator.modelContext`はFeature Detectionし、存在しない場合は黙って何もしないようにしてください。現時点ではほとんどのユーザーがまだこのAPIを持っていません。そして、それぞれのツールの`execute`ハンドラーは、既存のAPIがすでに強制している認可・バリデーションのロジックを必ず経由させ、WebMCPのツールがUI側では当然視されているチェックを迂回する抜け道にならないようにすべきです。私たちも2026年第4四半期の安定化に向けた仕様の進捗を追い続け、APIの表面が固まった段階で具体的な実装ガイドを改めて整理する予定です。
