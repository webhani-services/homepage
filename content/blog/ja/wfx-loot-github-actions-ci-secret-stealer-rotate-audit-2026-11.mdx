2026年11月10日ごろから、乗っ取られた数千の GitHub アカウントを使って、認証情報を盗むスクリプトが多数のリポジトリに送り込まれています。セキュリティベンダーは「wfx」または「wfx-loot」と呼んでいます。数字はソースごとに異なり、Aikido は約4,837アカウントが約6万1千のリポジトリに調査用の Pull Request を出し、ペイロードが実際に動作したのは2,000弱と報告しています。いずれも概数として扱ってください。

エンジニアリングチームにとって重要なのは規模ではありません。Endor Labs などの分析によれば、このキャンペーンは GitHub Actions の脆弱性を突いているのではなく、盗んだアカウント認証情報やトークンを使い、そのアカウントがもともと持つ権限を利用しています。ワークフローファイルが配送手段であり、CI のシークレットが標的です。

## スティーラーの動き(公開分析に基づく)

1. 乗っ取ったアカウントが、到達できるリポジトリに調査用の Pull Request を出し、ワークフローを注入できるだけの書き込み権限があるかを確認します。
2. 権限がある場合、GitHub Actions 内でシェルスクリプトを実行します。ここにはリポジトリシークレット、クラウド認証情報、パッケージレジストリのトークン、AI プロバイダーの API キーが集まりがちです。
3. スクリプトは見つけた情報を外部へ送信し、痕跡となるワークフローの実行履歴を削除するとされています。
4. その後、Azure アプリケーションへのフェデレーション認証情報の登録や、AWS ロールの信頼ポリシーの改変により、クラウド側に永続化します。

4 が、「シークレットをローテーションすればよい」では不十分な理由です。トークンを更新しても、攻撃者のプリンシパルがロールを引き受けられる信頼ポリシーはそのまま残ります。

## まず確認すること

クラウドにアクセスする CI を持つリポジトリがあれば、次の順で確認してください。

**1. 身に覚えのないワークフローがないか。** 直近の履歴で、見慣れないコミットが追加・変更したワークフローを探します。デフォルトブランチ以外も対象です。

```bash
# 直近30日のワークフロー変更(作者付き)
git log --since="30 days ago" --all \
  --format='%h %an %ad %s' --date=short \
  -- .github/workflows/

# キャンペーンの識別子らしき文字列
git grep -n -i "wfx" $(git rev-list --all --since="30 days ago") -- .github 2>/dev/null | head
```

**2. キーだけでなくクラウド側の信頼関係を監査する。** AWS では、知らないプリンシパルや設定した覚えのない OIDC subject を許可しているロールを洗い出します。CloudTrail の `UpdateAssumeRolePolicy` イベントが出発点になります。

```bash
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=EventName,AttributeValue=UpdateAssumeRolePolicy \
  --start-time "$(date -u -d '30 days ago' +%FT%TZ)" \
  --query 'Events[].{time:EventTime,user:Username,res:Resources[0].ResourceName}'
```

macOS のシェルでは `date` 部分を `date -u -v-30d +%FT%TZ` に置き換えてください。

Azure では、アプリ登録のフェデレーション ID 資格情報を確認します。報告には `wfx-ci-` というプレフィックスの項目が挙がっていますが、名前に頼らず、説明できないものはすべて確認対象にしてください。

**3. 正しい順序でローテーションする。** 先に見覚えのない信頼設定やフェデレーション資格情報を削除し、その後にシークレットを更新します。逆にすると、バックドア経由で新しい認証情報を発行される隙が残ります。

**4. 人側も確認する。** 書き込み権限を持つユーザーの棚卸し、古い Personal Access Token や OAuth アプリ許可の失効、組織での二要素認証の強制を確認します。報告では、アカウントはクレデンシャルスタッフィング、フィッシング、インフォスティーラーのログなどで乗っ取られたとされ、GitHub 自体の侵害ではありません。

## 被害範囲を狭めるハードニング

新しい話ではありませんが、今回のキャンペーンは「本当に適用していたか」の試金石になります。

**長期クラウドキーではなく OIDC フェデレーションを使い、subject を絞る。** リポジトリ内のどのワークフローでも許可する信頼ポリシーは、静的キーより少しましな程度です。環境で固定します。

```json
{
  "Condition": {
    "StringEquals": {
      "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
      "token.actions.githubusercontent.com:sub": "repo:your-org/your-repo:environment:production"
    }
  }
}
```

レビュー承認必須の `production` Environment と組み合わせれば、フィーチャーブランチ上の不正なワークフローは本番の認証情報を取得できません。

**デフォルト権限を最小にする。**

```yaml
permissions:
  contents: read
```

**ワークフローを変更できる人を限定する。** `.github/workflows/` に CODEOWNERS を設定し、少人数のレビューを必須にします。Branch protection や Ruleset は管理者にも適用します。

**サードパーティ Action は完全なコミット SHA で固定し**、信頼できない Pull Request イベントで動くジョブにはシークレットを渡さないでください。

**クラウド側でアラートを張る。** 信頼ポリシーの更新や新規フェデレーション資格情報の作成は頻度が低く、アラートのコストが小さい割に検知精度が高いイベントです。

## webhani の見解

支援先のチームに共通する学びが二つあります。

一つ目は、CI は「外部から触れられるトリガーを持つ認証情報の保管庫」だということです。アプリケーションコードは丁寧にレビューしても、ワークフローは軽く扱われがちです。しかしワークフローは、最も強い権限のシークレットにアクセスできる任意コードです。

二つ目は、CI 侵害のインシデント対応には、トークンのローテーションだけでなくクラウドの ID 監査を含める必要があることです。手順書が「シークレットをローテーション」で終わっているなら、信頼ポリシー、フェデレーション資格情報、暴露期間中に作られた新規プリンシパルの確認を追加してください。

AI プロバイダーの API キーも標的に含まれています。パイプラインやコーディングエージェントが保持している場合は、クラウドキーと同じスコープ設定とローテーションの規律を適用しましょう。

## まとめ

- 悪用されているのは GitHub Actions の脆弱性ではなく盗まれた認証情報です。アカウント衛生とトークンのスコープが最初の防御線です。
- ワークフロー履歴とクラウドの信頼関係を監査し、バックドアを削除してからシークレットをローテーションします。
- OIDC の subject を環境に絞り、ワークフロー変更のレビューを必須にし、信頼ポリシーの変更を監視します。

詳細は更新が続いており、数値もベンダーで異なります。自社の確認を終える前に、Aikido、Endor Labs、GitHub の最新アドバイザリーを確認してください。
