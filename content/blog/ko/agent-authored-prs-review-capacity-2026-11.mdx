이번 주 GitHub Octoverse 2026 관련 보도에서, 9월 기준으로 AI Agent가 연 Pull Request가 전체의 40%를 넘었고 3월의 약 17%에서 크게 늘었다고 전해졌습니다. 저희는 보고서 원문이 아니라 2차 자료를 참고했으므로 수치는 참고용으로 받아들여 주시기 바랍니다. 다만 방향성은 고객사 Repository에서 보는 상황과 일치합니다. Diff를 만드는 비용은 급격히 떨어졌지만, Diff를 읽는 비용은 그대로입니다.

이 비대칭이 개발 팀에 중요한 이유는 분명합니다. 사람이 PR 하나를 여는 동안 Agent가 열 개를 열 수 있다면, 제약이 되는 자원은 승인하는 사람의 주의력입니다. 아무 대책이 없으면 Review 대기열이 계속 늘거나, 형식적인 승인이 늘어나는 두 가지 중 하나로 흘러갑니다.

## Throughput만 보면 안 되는 이유

Coding Agent를 도입한 팀은 PR 수와 Merge까지 걸리는 시간을 지표로 삼기 쉽습니다. 두 수치 모두 좋아 보이지만 다음 문제가 가려집니다.

- 대기열이 길어질수록 Review는 얕아집니다. 훑어보게 됩니다.
- Agent의 PR은 하나씩 보면 대체로 "문제없어 보입니다". 그 결과 전체가 Architecture에 맞는지는 아무도 묻지 않게 됩니다.
- 직접 작성한 사람이 없으니, 새벽 2시에 장애가 났을 때 "내 Code"라는 책임감이 생기지 않습니다.

더 유용한 지표는 Review 대기 시간, 실질적인 Comment가 달린 PR의 비율, 30일 이내 Revert 비율입니다. 대기 시간과 Revert 비율이 함께 오른다면 속도를 품질로 지불하고 있다는 신호입니다.

## 확장 가능한 운영 규칙

Agent가 연 PR을 사람의 PR과 똑같이 취급하지 말고, 명시적인 규칙을 가진 별도 범주로 다루시기를 권합니다. 최소한의 예시입니다.

1. **모든 Agent PR에는 사람 Owner를 둡니다.** 작업을 지시한 사람이 작성자로서 책임을 지고 첫 번째 Reviewer가 됩니다. 다른 사람의 승인도 여전히 필요합니다.
2. **크기 상한을 둡니다.** 기준 줄 수를 넘는 PR은 Review 전에 분할합니다. 1,500줄짜리 Diff는 누가 썼든 Review할 수 없습니다.
3. **의도를 적게 합니다.** 지시한 작업, 확인한 것, 확인하지 못한 것을 PR 설명에 쓰게 하고 Template으로 강제합니다.
4. **자동 검사를 먼저 통과시킵니다.** Test, Type Check, Lint가 통과한 뒤에 사람에게 Review를 요청합니다. 깨진 Build를 가장 먼저 발견하는 역할은 사람이 아닙니다.
5. **WIP 제한을 둡니다.** 한 사람이 가질 수 있는 열린 Agent PR 수에 상한을 둡니다. 대기열이 줄어야 다음 작업이 생기므로 가장 효과가 큰 통제 수단입니다.

## Agent PR 자동 Labeling

보이지 않는 것은 관리할 수 없습니다. 작성자 유형별로 Label을 붙이고 너무 큰 Diff를 걸러내는 작은 Workflow가 데이터와 Guardrail 역할을 함께 합니다. 아래 예시는 공식 `pull_request` Event와 `actions/github-script`를 통한 REST API만 사용합니다.

```yaml
name: pr-triage
on:
  pull_request:
    types: [opened, synchronize, reopened]

permissions:
  pull-requests: write
  contents: read

jobs:
  triage:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/github-script@v7
        with:
          script: |
            const pr = context.payload.pull_request;
            const labels = [];

            // Agent의 인증 방식에 맞게 수정하십시오
            const agentLogins = ["copilot-swe-agent[bot]", "my-org-agent[bot]"];
            if (agentLogins.includes(pr.user.login)) labels.push("agent-authored");

            const changed = pr.additions + pr.deletions;
            if (changed > 600) labels.push("needs-split");

            if (labels.length > 0) {
              await github.rest.issues.addLabels({
                ...context.repo,
                issue_number: pr.number,
                labels,
              });
            }

            if (changed > 600) {
              core.setFailed(
                `Diff is ${changed} lines. Split it before requesting review.`
              );
            }
```

이 검사를 Branch protection의 필수 항목으로 지정합니다. 일부러 실패하게 만든 이유는, Agent에게 분할을 요청하는 편이 너무 큰 PR을 사람이 Review하는 것보다 저렴하기 때문입니다.

## 의도를 강제하는 PR Template

```markdown
## Task
Agent에게 무엇을 지시했는가. Issue 링크.

## Verified
- [ ] Test를 추가하거나 수정했다
- [ ] Local / Preview에서 동작을 확인했다
- [ ] 지시 범위 밖의 변경이 없는지 확인했다

## Not verified
확인하지 못한 것과 그 이유.

## Human owner
@username
```

가장 중요한 항목은 "Not verified"입니다. 암묵적인 위험을 Reviewer가 반응할 수 있는 문장으로 바꿔 줍니다.

## AI Review는 Filter이지 판정자가 아닙니다

Copilot code review 같은 Tool은 Style, 명백한 Bug, 부족한 Test 같은 1차 검토에 적합합니다. 사람이 보기 전에 Noise를 줄이는 용도로 쓰고, 승인자로 삼지는 마십시오. Code를 작성한 Agent와 Review하는 Tool은 비슷한 학습 자료에 기반한 언어 모델이므로 사각지대를 공유하기 쉽습니다. 같은 계열 Tool의 두 번째 의견은 보기보다 독립적이지 않습니다.

역할 분담의 기준입니다.

- **자동:** Formatting, Lint, Type 오류, 의존성·Secret 스캔, Test 결과.
- **AI 보조:** Diff 요약, 위험한 영역 지적, 부족한 Test Case 제안.
- **사람:** 이 변경이 여기에 있어야 하는가, Module 경계를 지키는가, 실패했을 때의 영향을 감당할 수 있는가.

## CODEOWNERS는 여전히 유효합니다

Agent가 여러 영역을 건드린다면 `CODEOWNERS`로 해당 영역을 잘 아는 사람에게 Review를 보내는 구조가 중요합니다. 인증, 결제, 인프라 정의, Migration처럼 실수의 대가가 큰 경로일수록 규칙은 느슨하게가 아니라 엄격하게 가져가야 합니다. Test가 통과한 Agent PR이라도 이런 경로에서는 Code Owner의 승인을 필수로 두십시오.

## webhani의 권장 사항

- 이번 주 안에 `agent-authored` Label을 도입하고, 한 달 동안은 Review 대기 시간만 관찰합니다.
- Owner별 WIP 제한을 둡니다. 열린 Agent PR 3개에서 시작해 운영하며 조정합니다.
- "Not verified"를 필수 항목으로 만듭니다.
- Merge 시간과 함께 30일 Revert 비율을 추적합니다.
- 인증, Data, 인프라를 건드리는 변경은 최종 승인을 반드시 사람이 합니다.

Agent 기반 개발은 거부할 대상이 아니며, 수치를 보면 이미 일상이 되어 가고 있습니다. 성과를 내는 팀은 Review 용량을 한정된 자원으로 보고 그에 맞춰 프로세스를 설계한 팀입니다. 제약을 장애를 통해 알게 되기 전에 먼저 대비하시기 바랍니다.
