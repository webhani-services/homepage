## 벤치마크 경쟁은 사실상 무의미해졌습니다

현재 기준 벤치마크인 Terminal-Bench 2.1에서 GPT-5.6 Sol이 약 89.5%, Claude Opus 5가 89.1%를 기록하고 있습니다. Meta도 이번 달 자체 Terminal-native Coding Agent인 Muse Code를 출시하면서 Claude Code, Cursor와 함께 선택지가 하나 더 늘었습니다. 최상위 Model 간 점수 차이가 1% 미만으로 좁혀진 상황에서, 그 숫자는 더 이상 구매 결정을 좌우할 만한 신호가 아닙니다.

"어떤 AI Coding Tool을 도입해야 하나요"라는 질문을 이제 클라이언트로부터 거의 매주 받습니다. 솔직히 말하면 벤치마크는 가장 먼저 물어야 할 질문이 아닙니다. 실제 조직 안에서 성패를 가르는 요소는 Terminal-Bench가 전혀 측정하지 않는 부분입니다 — Tool이 팀의 Permission 체계를 얼마나 세밀하게 다루는지, Task마다 다시 채워 넣어야 하는 Context가 얼마나 되는지, 그리고 결과물이 기존 Review Process를 형식적인 절차로 전락시키지 않고 실제로 통과하는지 여부입니다.

## 도입 성공을 좌우하는 4가지 기준

### 1. Capability 자체보다 Permission의 세밀함

Agent가 `git push --force`나 DB Migration 적용을 자율적으로 수행할 수 있다는 것 자체는 장점이 아니라, 팀이 그에 맞는 Guardrail을 마련하지 못했다면 오히려 Risk 요인입니다. 확인해야 할 질문은 "무엇을 할 수 있는가"가 아니라 "Repository별, Branch별로 승인 없이 실행 가능한 Command를 얼마나 세밀하게 제어할 수 있는가"입니다. 전체 승인/전체 차단이라는 단일 Toggle만 제공하는 Tool은 팀을 두 가지 극단으로 몰아넣습니다. 단순 작업을 처리하기 위해 Prod Deploy 권한까지 내주는 과도한 권한 부여, 혹은 아예 제대로 활용하지 못하는 과소 활용입니다.

### 2. Context Window 크기보다 Task당 Context Cost

Context Window의 크기는 흔히 주요 마케팅 포인트로 강조되지만, 실무에서 중요한 수치는 "Task를 시작할 때마다 프로젝트 Convention을 다시 설명하는 데 Window를 얼마나 소모하는가"입니다. Coding Standard와 Architecture 결정이 Engineer 머릿속에만 있고 문서화되어 있지 않다면, Window 크기와 무관하게 매 Session마다 재학습 비용을 지불하게 됩니다. 최신 상태로 관리되는 `CLAUDE.md` 같은 Instruction File 하나가, Window Token 10만 개를 더 늘리는 것보다 실질적인 Throughput에 훨씬 효과적입니다.

```markdown
<!-- Tool을 평가하기 전에 준비해 둘 가치가 있는 CLAUDE.md 예시 -->

## Conventions
- API Route는 Handler 경계를 넘어 throw하지 않고 `{ data, error }`를 반환합니다
- 새 DB Migration은 같은 PR 안에 Rollback Script를 포함합니다
- `docs/dependency-policy.md`를 확인하지 않고 새 npm Dependency를 추가하지 않습니다
```

### 3. Review 부담이 늘어나는가, 줄어드는가

코드 생성 속도가 빨라져도 Reviewer가 PR 하나에 쓰는 시간이 늘어난다면 의미가 없습니다. AI 지원을 받은 PR과 사람이 직접 작성한 PR의 Review 시간, 수정 요청 건수를 몇 주간 추적해 본 뒤 판단하기를 권합니다. 그럴듯해 보이지만 미묘하게 틀린 코드를 생성하는 Tool은 부담을 "작성"에서 "검토"로 옮길 뿐입니다. 낯선 코드의 정확성을 검증하는 작업은 직접 작성하는 것보다 느리고 실수도 잦습니다 — 이것이 자동 채점 방식인 벤치마크가 절대 포착하지 못하는 실패 유형입니다.

### 4. 실패의 가독성

Agent가 실수했을 때, Engineer가 1분 안에 원인을 파악할 수 있는지, 아니면 긴 Tool Call Transcript를 뒤져야 하는지도 중요합니다. 자신의 판단 근거와 실행한 Command를 함께 제시하는 Agent는, 완성된 Diff만 내놓는 Agent보다 디버깅 비용이 훨씬 낮습니다. 업계 전체가 Autocomplete에서 이른바 "Agent Engineering" 단계로 넘어가면서 Agent가 감독 없이 처리하는 작업이 늘어날수록, 이 가독성의 중요도는 더 커집니다.

## 최소한의 평가 체크리스트

Benchmark Suite를 돌리는 대신, 각 후보 Tool에 회사 Backlog에서 가져온 동일한 Ticket — 파일 2~3개를 건드리는 중간 난이도의 Bug Fix가 이상적입니다 — 을 주고 다음을 채점하는 방식을 권합니다.

- Mergeable PR이 나오기까지의 시간(평소 Review Cycle 포함)
- Agent가 지시 없이 만든 Scope 밖 변경의 개수
- Ticket이 모호할 때 확인을 요청했는지, 아니면 임의로 추측해서 진행했는지
- Task에 필요한 것 이상의 Access를 부여하지 않고도 Permission Model을 운용할 수 있었는지

Tool 하나당 반나절이면 충분하고, Leaderboard 순위보다 훨씬 많은 것을 알려줍니다. Frontier Model 간 벤치마크 격차는 이제 오차 범위 안으로 좁혀졌지만, Tool과 팀 프로세스의 적합도 격차는 여전히 뚜렷하게 남아 있습니다.
