Temporal의 2026년 개발자 조사에는 흥미로운 수치가 담겨 있습니다. AI coding agent를 "매일 이상 사용한다"고 응답한 엔지니어의 비율이 47.3%에서 80.8%로 1년 사이 70.8% 증가했습니다. 미국과 영국을 대상으로 한 544명의 조사 결과입니다.

하지만 같은 보고서에는 또 다른 흐름이 있습니다. "에이전트를 더 자주 사용하지 않는 이유"를 묻는 질문에 35.7%의 응답자가 "태스크의 State를 추적할 수 없다"고 답했습니다. 그 다음으로 Agent 동작의 Debugging 어려움(구문적으로는 정상이지만 의미상 틀린 출력 감지), 그리고 예측 불가능한 실행 비용이 주요 과제로 지목되었습니다.

즉, 도입 급증과 신뢰성은 정반대 방향으로 움직이고 있습니다. State 관리, 관찰성, Cost 제어를 해결한 팀은 앞으로 나아가고 있고, 기존 프로세스에 Agent를 단순히 추가한 팀은 벽에 부딪혔습니다.

## State 추적: 왜 실패는 항상 중간에 발생하는가

Multi-step Agent 태스크가 2번째 스텝까지 성공하다가 3번째 스텝에서 예기치 않은 상황을 만납니다. Agent를 다시 시작하면 될까요? 하지만 7번째 스텝에서 실패했다면 어떨까요? 15번째 스텝이라면 말입니다.

보편적인 접근은 "처음부터 다시 시작"입니다. 이는 외부 API 호출 비용을 다시 지불하고, 실시스템에 대한 중복 작업의 위험을 감수한다는 뜻입니다.

webhani가 권장하는 방식은 각 스텝 완료 후 State를 파일 또는 간단한 로그에 저장하는 Checkpoint 방식입니다. 재개할 때는 완료된 스텝을 건너뛰고 실패한 지점부터 시작합니다.

```typescript
// 각 Agent 스텝 완료 후 상태를 저장
interface TaskCheckpoint {
  stepId: string;
  status: "pending" | "in_progress" | "completed" | "failed";
  result?: unknown;
  timestamp: number;
  agentContext?: Record<string, unknown>;
}

async function executeTaskWithCheckpoint(
  taskId: string,
  steps: Array<{ id: string; action: () => Promise<unknown> }>
) {
  const checkpointFile = `./checkpoints/${taskId}.json`;
  let checkpoint = loadCheckpoint(checkpointFile) || { taskId, steps: [] };

  for (const step of steps) {
    const existing = checkpoint.steps.find((s) => s.stepId === step.id);
    if (existing?.status === "completed") {
      console.log(`Step ${step.id} 이미 완료됨, 건너뜁니다.`);
      continue;
    }

    try {
      checkpoint.steps.push({
        stepId: step.id,
        status: "in_progress",
        timestamp: Date.now(),
      });
      saveCheckpoint(checkpointFile, checkpoint);

      const result = await step.action();

      checkpoint.steps = checkpoint.steps.map((s) =>
        s.stepId === step.id
          ? {
              ...s,
              status: "completed",
              result,
              timestamp: Date.now(),
            }
          : s
      );
      saveCheckpoint(checkpointFile, checkpoint);
    } catch (err) {
      checkpoint.steps = checkpoint.steps.map((s) =>
        s.stepId === step.id ? { ...s, status: "failed" } : s
      );
      saveCheckpoint(checkpointFile, checkpoint);
      throw err;
    }
  }

  return checkpoint;
}
```

완료된 스텝은 재개 시 자동으로 건너뛰어집니다. 실패한 스텝만 재시도됩니다. 스텝 레벨에서 멱등성을 확보할 수 있기 때문에, 실시스템에 대한 작업도 안전하게 관리됩니다.

## Agent 동작 디버깅: 표준 로깅이 작동하지 않는 이유

Agent 실패는 일반적인 애플리케이션 오류와 질이 다릅니다. Output은 유효한 JSON이고, HTTP 상태는 200이며, Tool 호출은 성공했습니다. 하지만 Agent가 의미상 잘못된 판단을 내렸고, 태스크가 완료될 때까지 알 수 없습니다.

각 스텝에서 Agent의 추론을 기록하고, 예상 결과와 실제 결과를 즉시 비교하여 감지합니다.

```typescript
// Agent의 모든 판단을 구조화된 로그로 기록
interface AgentDecisionLog {
  taskId: string;
  stepNumber: number;
  decision: string;
  reasoning: string;
  toolSelected: string;
  toolArguments: Record<string, unknown>;
  toolResult: unknown;
  expectedOutcome: string;
  actualOutcome: string;
  match: boolean;
  timestamp: number;
}

async function logAgentDecision(
  taskId: string,
  stepNumber: number,
  decision: string,
  reasoning: string,
  tool: { name: string; args: Record<string, unknown> },
  result: unknown,
  expectedOutcome: string
) {
  const actual = String(result);
  // 간단한 부분 문자열 검사; 프로덕션에서는 의미론적 유사성 또는 LLM 기반 판정 사용
  const match = actual
    .toLowerCase()
    .includes(expectedOutcome.substring(0, 20).toLowerCase());

  const log: AgentDecisionLog = {
    taskId,
    stepNumber,
    decision,
    reasoning,
    toolSelected: tool.name,
    toolArguments: tool.args,
    toolResult: result,
    expectedOutcome,
    actualOutcome: actual,
    match,
    timestamp: Date.now(),
  };

  // Agent가 삭제할 수 없는 Append-only 로그
  fs.appendFileSync(
    `./agent-logs/${taskId}.jsonl`,
    JSON.stringify(log) + "\n"
  );

  // 불일치 시 즉시 알림
  if (!match) {
    await notifySlack(
      `⚠️ Task ${taskId} step ${stepNumber} 판단 불일치: ` +
      `예상 "${expectedOutcome}" 하지만 "${actual}" 수신`
    );
  }
}
```

모든 Agent 판단이 그 추론과 함께 로그됩니다. 불일치는 태스크 완료 시가 아닌 즉시 표면화됩니다. 전체 의사결정 체인이 Agent 메모리 외부에 보존되므로 사후 분석도 가능합니다.

## Cost 제어: 기하급수적인 청구를 막기

Tool Loop를 실행하는 Agent는 단일 LLM 호출보다 10배의 토큰을 소비할 수 있습니다. Retry Loop이 예상보다 오래 실행됩니다. 한 번의 "무해해 보이는" 판단이 수십 개의 배경 API 호출을 유발합니다. 월말 송장을 보면 $1,000이 아니라 $10,000입니다.

우리의 접근: Agent 실행 전에 예산을 설정하고, 초과하면 중단합니다.

```typescript
// Agent 지출에 대한 하드 예산 가드
interface CostBudget {
  taskId: string;
  maxSpendUSD: number;
  currentSpendUSD: number;
  tokensUsed: { input: number; output: number };
}

const COST_PER_INPUT_TOKEN = 0.000003;   // Claude Haiku 가격 예시
const COST_PER_OUTPUT_TOKEN = 0.000015;

async function executeAgentWithCostGuard(
  taskId: string,
  maxBudgetUSD: number,
  agentFn: () => Promise<unknown>
) {
  const budget: CostBudget = {
    taskId,
    maxSpendUSD: maxBudgetUSD,
    currentSpendUSD: 0,
    tokensUsed: { input: 0, output: 0 },
  };

  const trackSpend = async (usage: { input_tokens: number; output_tokens: number }) => {
    budget.tokensUsed.input += usage.input_tokens;
    budget.tokensUsed.output += usage.output_tokens;

    const spend =
      budget.tokensUsed.input * COST_PER_INPUT_TOKEN +
      budget.tokensUsed.output * COST_PER_OUTPUT_TOKEN;

    budget.currentSpendUSD = spend;

    if (spend > budget.maxSpendUSD) {
      throw new Error(
        `비용 초과: $${spend.toFixed(4)} > $${maxBudgetUSD}`
      );
    }
  };

  try {
    // Agent 호출 전에 Cost 추적을 LLM SDK에 연결
    const result = await agentFn();
    return result;
  } catch (err) {
    console.error(`Task ${taskId} 중단됨:`, err.message);
    await recordCostExceeded(budget);
    throw err;
  }
}

async function recordCostExceeded(budget: CostBudget) {
  fs.appendFileSync(
    "./cost-overruns.log",
    `${new Date().toISOString()} - ${budget.taskId}: ` +
    `$${budget.currentSpendUSD.toFixed(4)} (한도: $${budget.maxSpendUSD})\n`
  );
}
```

Agent 지출을 지속적으로 추적합니다. 예산 초과? Agent가 즉시 중지됩니다. 더 이상 놀라움은 없습니다.

## 왜 격차가 점점 벌어지는가

Temporal 데이터는 전환을 시사합니다. Agent가 "실험"에서 "Infrastructure"로 움직이고 있다는 뜻입니다. Agent를 테스트할 때는 State 관리가 선택사항처럼 느껴집니다. Debugging은 사후 분석 때까지 기다릴 수 있습니다. Cost 초과는 한 두 번 일어납니다.

하지만 CI Pipeline에서 Agent가 실행되거나, 여러 팀이 공유하거나, 프로덕션 시스템을 다룰 때, 이 간격들은 운영 준비의 격차가 됩니다.

신뢰성 격차는 모델 품질 문제가 아닙니다. Agent가 믿을 수 있기 위해 필요한 Operational Layer를 구축했는지에 관한 것입니다.

State Checkpoint, 구조화된 의사결정 로깅, Cost 예산은 구현이 간단하지만 실제로는 변혁적입니다. "Agent를 써봤다"와 "Agent는 이제 우리의 Infrastructure다" 사이의 차이입니다.

도입률이 80% 이상인 지금, 질문은 "Agent를 사용할 것인가"가 아닙니다. "Agent를 안전하게 운영할 준비가 되었는가"입니다.
