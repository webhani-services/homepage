## 무인으로 작성되는 Code의 비중이 늘고 있습니다

Sonar의 2026 State of Code Developer Survey에 따르면, 응답자가 Commit한 Code 중 AI가 생성했거나 AI의 도움을 받은 Code의 비중이 42%에 달했고, Team들은 2027년까지 이 비율이 65%까지 오를 것으로 예상하고 있습니다. 이 수치는 많은 Engineering Team이 이미 체감하고 있는 변화를 보여줍니다. Agent는 더 이상 한 줄을 Autocomplete해주는 존재가 아니라, 함수를 작성하고, 이를 지원하기 위해 의존 Package를 설치하고, Test Suite를 실행하고, 반복 개선하는 존재입니다. 그것도 대부분 사람이 중간 과정을 하나하나 읽지 않은 상태로 말입니다.

바로 이 변화가 Cloud-native Infrastructure Provider들을 단순한 Container가 아니라 VM 수준의 격리로 Agent 실행을 감싸는 방향으로 밀어붙이고 있습니다. CI Job과 Build Pipeline에는 10년간 충분했던 경계가 왜 Agent에게는 갑자기 부족해졌는지 구체적으로 짚어볼 가치가 있습니다.

## Container는 알려진, 정적인 Workload를 전제로 합니다

표준적인 Container의 보안 Model은 상황을 잘 파악하고 능동적으로 적응해 나가는 Process를 막도록 설계된 것이 아닙니다. Container 격리(Namespace, cgroups, 공유 Kernel)는 Cost와 밀도 면에서 뛰어나며, 작성자가 예상한 대로 동작하는 Workload를 담아두는 데는 적합합니다. 하지만 문서를 읽고, 설정 오류를 알아채고, 예상 범위 밖의 무언가를 설치해보기로 "결정"할 수 있는 Process에 대한 견고한 경계로 설계된 적은 없습니다.

이것은 자율적인 코딩 Agent가 본질적으로 하는 일을 정확히 묘사합니다. 명시적으로 지시받지 않은 Command를 실행하고, 사전 승인되지 않은 Package를 설치하고, 자신이 놓인 환경을 파악하기 위해 File을 읽습니다 — 그리고 이는 정확히 그 Agent를 쓸모 있게 만드는 행동이기도 합니다. 망가진 Build에서 스스로 벗어날 수 있게 해주는 적응력과, "Container 경계를 신뢰한다"는 전제를 예전보다 약하게 만드는 요인은 같은 성질에서 나옵니다.

## VM 수준 격리가 실제로 더해주는 것

지금 진행되고 있는 변화는 특정 Agent에 대한 불신 때문이 아니라, Workload가 스스로 할 수 있게 된 범위에 격리 경계를 맞추는 문제입니다. VM 수준의 경계(실제 Hypervisor 기반 Sandbox, 또는 Firecracker 같은 microVM 방식)는 다음을 제공합니다.

- **Workload마다 독립된 Kernel**: Container 격리가 애초에 완전히 막도록 의도되지 않았던 공유 Kernel 경유 탈출 경로를 차단합니다.
- **Workload의 행동에 의존하지 않는 Resource·Network 경계**: Container의 cgroups 제한은 Kernel에 의해 강제되긴 하지만 어느 정도 협조적인 성격을 갖는 반면, VM 경계는 Workload가 얌전히 행동할 것을 전제하지 않고도 유지됩니다.
- **Sandbox 안에서 멈추는 영향 범위**: 이는 Agent의 행동(Package 설치, Shell Command, File 쓰기)이 동적이고, CI Job의 단계처럼 사전에 선언되는 것이 아니라 사후에야 전체가 파악된다는 점에서 특히 중요합니다.

## 실제 구성은 이런 모습입니다

Agent 기반 Code 생성이나 Build 단계를 운영 중인 Client에게 현재 권장할 만한 Pattern입니다.

```yaml
# Agent 실행 단계에 대한 개념적인 Sandbox Policy
sandbox:
  isolation: microvm       # Hypervisor 기반, 공유 Kernel 아님
  network:
    egress: allowlist      # Package Registry만 허용, 임의의 외부 통신 불가
  filesystem:
    scope: ephemeral        # Task 종료 후 Workspace 폐기
  resource_limits:
    cpu: "2"
    memory: "4Gi"
    timeout: "15m"
  audit:
    log_commands: true
    log_network: true
```

위 YAML은 특정 제품의 사양이 아니라 예시입니다. 중요한 것은 Policy의 형태입니다. 엄격한 Egress Allowlist, 임시 Filesystem, 명확한 Resource 상한, Command·Network에 대한 전체 Logging — 이것들은 사고가 발생한 뒤에 추가하는 것이 아니라 처음부터 필요한 것으로 전제해야 합니다. CNCF가 추진 중인 Certified Kubernetes AI Conformance Program도 같은 방향을 가리킵니다. AI/ML Workload, 그리고 앞으로 늘어날 Agent형 Workload를 Cluster Infrastructure 안에서 어떻게 운영해야 하는지 표준화하여, 각 Team이 그때그때 임시방편으로 자신만의 경계를 만드는 상황에서 벗어나려는 것입니다.

## 실제 Team에게 의미하는 것

대부분의 Engineering 조직에게 실무적인 질문은 Agent에게 Package 설치나 Shell Command 실행을 허용할지 여부가 아닙니다 — 그 능력 자체가 Agent의 가치 대부분을 차지하기 때문입니다. 질문은 그런 행동이 어디에서 일어나도록 허용할 것인지, 그리고 실수나 진짜 악의적인 Package가 거기서부터 얼마나 멀리까지 퍼질 수 있는지입니다.

구체적인 권장 사항 몇 가지입니다.

1. **Production 인증 정보를 보유한 Infrastructure 안에서는 절대 Agent 기반 Build를 실행하지 않습니다**: Agent의 Sandbox와 Deploy Pipeline의 Secret이 같은 경계를 공유한다면, 그 Sandbox는 이미 무력화된 것입니다.
2. **Task 수준이 아니라 Command와 Network 수준에서 Log를 남깁니다**: "Agent가 Build를 실행했다"는 사후에 아무 도움이 되지 않습니다. "Agent가 `pip install X`를 실행한 뒤 Y로 3번의 외부 통신을 했다"는 도움이 됩니다.
3. **Package 설치를 일상적인 작업이 아니라 Agent가 하는 행동 중 가장 위험도가 높은 행위로 취급합니다**: Agent가 검토되지 않은 의존성을 설치해 들여오는 Supply Chain 문제는 사람이 들여온 경우와 기능적으로 동일하며, 같은 Review Gate가 필요합니다.

## Webhani의 시각

Container 격리는 행동이 대체로 사전에 알려진 Workload를 위해 만들어졌습니다. Agent형 Workload는 설계상 그 전제를 깨뜨립니다. Agent의 가치는 정확히, 방금 발견한 것을 바탕으로 다음에 무엇을 실행할지 스스로 판단할 수 있다는 데 있기 때문입니다. 결정론적인 CI Job을 위해 만들어진 것과 같은 격리 Model로 Agent를 감싸는 Infrastructure는, 그런 종류의 적응력에 맞서도록 애초에 설계되지 않은 경계를 신뢰하고 있는 셈입니다.

Agent를 위한 VM 수준 Sandboxing으로의 현재 움직임은 선택적인 강화 조치가 아니라, Agent가 스스로 의존성을 설치하거나 명시적으로 Script화되지 않은 Command를 실행하는 모든 환경의 기본 구성으로 다뤄야 한다고 봅니다. Agent 기반 코딩의 편의성은 실재합니다. 동시에 그것이 격리 경계가 막아내야 할 대상 자체를 바꿔놓았다는 것도 사실입니다.
