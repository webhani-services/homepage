이번 주 700개 이상의 회사를 대상으로 AI Coding Agent 도입 전후를 비교한 조사가 화제가 되고 있습니다. 저희가 확인할 수 있었던 것은 2차 보도뿐이며(원문 논문은 환경상 접근하지 못했습니다), 수치는 참고용으로 봐 주십시오. 보도에 따르면 Commit은 약 20%, PR은 약 23% 늘었지만 Jira의 Issue/Epic 해결률은 거의 달라지지 않았습니다. 다른 보고서는 일부 도입 기업에서 PR Merge 시간이 약 절반 가까이 늘었다고 주장합니다. 데이터는 2026년 3월까지로 알려져 있습니다.

모든 숫자를 보증할 수는 없습니다. 다만 경향 자체는 저희가 고객 Project에서 보는 모습과 일치합니다. Agent 덕분에 "작성"하는 비용은 내려가지만, 그 비용은 다른 곳으로 옮겨 갑니다.

## 비용은 어디로 옮겨 가는가

변경 사항은 누군가 이해하고, 검증하고, Merge해야 비로소 "전달"된 것입니다. Agent는 유입되는 변경의 양을 늘리지만, 승인할 수 있는 사람의 수는 늘리지 않습니다. 그 결과 다음과 같은 일이 생깁니다.

1. **Review 대기열이 길어집니다.** Reviewer 한 명당 PR이 늘고, PR 하나의 크기도 직접 작성한 경우보다 큰 경우가 많습니다.
2. **부하가 걸리면 Review 품질이 떨어집니다.** 훑어보기만 하거나 "Test가 통과했으니" 하고 승인하게 됩니다.
3. **재작업이 늘어납니다.** 그럴듯해 보이지만 요구사항을 잘못 이해한 코드가 수정 PR로 돌아옵니다. PR 수는 늘지만 Issue는 닫히지 않습니다.

Commit이나 PR 수로 성과를 재면 이 세 가지가 모두 "진척"으로 보입니다. Issue 해결 건수로 재면 아무것도 진행되지 않은 것으로 보입니다.

## 측정 대상을 바꿉니다

Process를 바꾸기 전에 추적하는 지표부터 바꿉니다. Repository별로 Git Host에서 다음 네 가지를 가져오시기를 권합니다.

- PR의 Open부터 Merge까지 시간(중앙값과 90 Percentile)
- PR 크기(변경 줄 수, 변경 File 수)
- Review 대기 시간(Open부터 첫 Review까지)
- 재수정 비율(이전 PR의 수정을 위해 올라온 PR의 비율)

GitHub CLI를 사용하면 간단한 Script로 Baseline을 얻을 수 있습니다.

```bash
gh pr list --state merged --limit 200 \
  --json number,createdAt,mergedAt,additions,deletions \
  | jq -r '.[] |
      [.number,
       ((.mergedAt|fromdateiso8601) - (.createdAt|fromdateiso8601))/3600,
       (.additions + .deletions)] | @csv'
```

Agent 도입 전과 후를 비교해서 Merge까지 걸리는 시간의 중앙값과 PR 크기가 모두 늘었다면, 위에서 설명한 패턴에 해당합니다.

## 효과가 있는 조정

**PR 크기에 상한을 둡니다(Agent에게도).** `CLAUDE.md`나 `AGENTS.md` 같은 지침에 PR 하나에 관심사 하나, 변경은 수백 줄 이내를 목표로, 넘으면 분할한다고 적습니다. Review 용량을 늘리는 방법 중 가장 비용이 적게 듭니다.

**Review 보조 자료를 Agent가 작성하게 합니다.** 의도, 중요한 File, 위험한 부분을 명시한 PR 설명을 만들게 합니다. 어디를 봐야 하는지 알면 Reviewer가 변경을 다시 파악하는 시간이 줄어듭니다.

**기계적인 검사는 사람의 Review에서 제외합니다.** Type 검사, Lint, Formatting, 의존성 Policy, Secret Scan은 CI의 몫입니다. 사람의 주의력은 설계, 요구사항 부합 여부, 보안상 중요한 경로에 씁니다.

```yaml
# .github/workflows/pr-checks.yml (발췌)
jobs:
  checks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run lint
      - run: npx tsc --noEmit
      - run: npm test -- --coverage
```

**착수 전에 Issue와 연결합니다.** 재작업은 Review에서 잡는 것보다 예방하는 편이 쌉니다. 인수 조건이 있는 Issue를 필수로 하고, 그 본문을 Agent의 Task로 전달합니다. 모호한 지시에서는 그럴듯하지만 어긋난 변경이 나옵니다.

**Review 시간을 명시적으로 확보합니다.** Agent를 도입한다면 회의처럼 Review 시간도 Calendar에 잡아 둡니다. 그렇지 않으면 가장 먼저 밀리는 일이 됩니다.

## 권하지 않는 방법

두 번째 Agent에게 첫 번째 Agent의 PR을 승인하게 하는 것은 null check 누락 같은 문제를 잡는 데 도움이 될 수 있지만, 요구사항을 이해하는 사람을 대체하지는 못합니다. 저희는 자동 Review를 사람이 볼 목록을 줄여 주는 Filter로 취급하고, 승인자로 두지 않습니다.

또한 "엔지니어 1인당 PR 30% 증가" 같은 목표도 설정하지 않습니다. 조사에서 시사하는, 출하 가치로 이어지지 않는 행동을 그대로 보상하게 되기 때문입니다.

## 정리

Coding Agent 도입은 생성 용량에 대한 투자입니다. 다음에 부딪히는 제약은 대부분 Review와 통합 용량입니다. Commit 수 대신 Merge 시간과 해결률을 측정하고, PR을 작게 유지하고, 기계적 검사는 CI로 옮기고, Reviewer의 시간을 의도적으로 확보하십시오. Baseline 측정이나 Repository용 Agent 지침 조정이 필요하시면 저희가 고객과 정기적으로 진행하는 작업이므로 편하게 문의해 주십시오.
