## 쓰고는 있지만, 믿지는 않는다

Sonar가 발표한 2026년 State of Code Developer Survey에 따르면, 개발자가 Commit하는 코드의 42%가 AI 생성 혹은 AI 지원 코드입니다. 반면 AI 코딩 도구의 결과물을 신뢰한다고 답한 개발자는 29%에 그쳤습니다. 수치만 보면 모순처럼 보이지만, 현장 감각으로는 오히려 자연스럽습니다. "안 쓸 수는 없지만, 그대로 믿고 넘어갈 수도 없다"는 것이 실제 상황에 가깝습니다.

이번 글에서는 이 "사용률과 신뢰도의 격차"가 왜 발생하는지, 그리고 webhani가 고객사의 AI 도입을 지원하며 실제로 구성하는 Code Review 체계를 구체적으로 소개합니다.

## 격차가 생기는 이유

원인은 단순히 AI의 정확도 문제가 아닙니다. 오히려 운영 방식에서 오는 3가지 요인이 더 큽니다.

1. **생성 속도와 Review 속도의 비대칭**: AI는 코드를 즉시 생성하지만, 사람이 그 내용을 이해하고 타당성을 판단하는 속도는 그대로입니다. 생성량이 늘어날수록 Review가 병목이 됩니다.
2. **"동작한다"와 "옳다"의 혼동**: AI가 생성한 코드는 기존 테스트를 대부분 통과하기 때문에 문제없어 보입니다. 하지만 요구사항 오해나 Edge Case 누락은 테스트 통과 여부와 무관하게 남아있을 수 있습니다.
3. **책임 소재의 모호함**: AI가 작성한 코드에 장애가 발생했을 때, "왜 이런 구현을 택했는가"를 설명할 수 있는 사람이 아무도 없는 상황이 종종 벌어집니다.

## 실무적인 Review 체계 설계

webhani는 AI 지원 코드에 대한 Review를 기존 PR Review의 연장선으로 두지 않고, 전용 Checkpoint를 추가할 것을 권장합니다.

### 1. 생성 코드에는 Context를 함께 남긴다

PR Description에 AI에게 준 지시 내용과 AI가 채택하지 않은 대안을 남기는 Rule을 정합니다.

```text
## AI 지원 PR의 경우 Description에 아래 항목을 포함

- 사용한 Tool/Model (예: Claude Code, GitHub Copilot)
- Prompt의 핵심 요지
- 생성된 구현 중 사람이 직접 수정한 부분
- Reviewer가 특별히 확인해야 할 우려 사항 (있다면)
```

이렇게 하면 Reviewer는 "무엇이 자동 생성되었고 무엇이 사람의 판단으로 수정되었는지"를 구분해서 확인할 수 있습니다.

### 2. Edge Case와 Error Handling을 우선적으로 확인한다

AI는 전형적인 Happy Path 구현에는 강하지만, 업무에 특화된 예외 처리나 경계 조건은 놓치기 쉽습니다. Review 우선순위를 명확히 하기 위해 아래와 같은 Checklist를 사용합니다.

```text
□ 빈 배열, null, undefined 입력이 고려되어 있는가
□ 외부 API의 Timeout과 Error Response가 처리되어 있는가
□ 권한 체크가 구현에서 누락되지 않았는가
□ Business Logic이 요구사항과 1:1로 대응하는가 (과부족이 없는가)
```

### 3. "왜 이 구현인가"를 설명할 수 있는 상태를 유지한다

코드를 제출한 사람(AI를 사용한 본인)이 구현 의도를 스스로의 말로 설명할 수 있는 것을 Merge 조건으로 둡니다. AI가 생성한 코드를 그대로 붙여넣기만 한 상태로는, 장애 대응 시 아무도 원인을 추적할 수 없는 위험이 있습니다.

## 신뢰도를 감으로 판단하지 않는다

webhani는 Review 체계의 효과를 감이 아니라 수치로 추적할 것을 권장합니다. 구체적으로는 다음 지표를 지속적으로 기록합니다.

- AI 지원 PR에서 Review 이후 발생한 수정 Commit 수 (많을수록 생성 품질에 문제가 있을 가능성)
- AI 지원 코드로 인한 운영 장애 건수와 비-AI 코드와의 비교
- AI 지원 코드와 그렇지 않은 코드 간의 평균 Review 소요 시간 차이

이 지표들을 3~6개월 단위로 추적하면, "어떤 유형의 작업이라면 AI에게 맡겨도 되는가"에 대한 팀 내부의 근거 있는 기준이 쌓이게 됩니다.

## 마무리

AI 생성 코드의 사용률은 늘고 있지만 신뢰도가 따라가지 못하는 것은, AI 성능 자체의 문제라기보다 Review 체계가 AI 시대에 맞게 최적화되지 않았기 때문인 경우가 많습니다. 생성 속도에 맞는 Review 체계를 갖추고, Edge Case와 책임 소재를 명시적인 Checkpoint로 만들면 이 격차는 실질적으로 줄일 수 있습니다. webhani는 이러한 Review 체계 설계부터 도입 지원까지, 고객사의 AI 코딩 활용을 함께합니다.
