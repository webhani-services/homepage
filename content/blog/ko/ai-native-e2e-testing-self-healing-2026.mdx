## Testing Pyramid이 틀렸던 게 아니라, 비용 모델이었을 뿐입니다

Unit Test는 많이, Integration Test는 적당히, E2E Test는 아주 적게 두는 전통적인 Testing Pyramid는 사실 "어떤 Test가 가장 중요한가"에 대한 이야기가 아니었습니다. "비용"에 대한 이야기였습니다. Unit Test는 작성 비용이 낮고 밀리초 단위로 실행됩니다. E2E Test는 Real Browser가 필요해 느리고, 누군가 CSS Class 이름을 바꾸거나 Button 위치를 몇 px 옮기기만 해도 쉽게 깨집니다. 그래서 "검증은 최대한 저렴한 Layer로 내리고, E2E는 가장 중요한 Flow에만 쓰는 희소 자원으로 다뤄라"가 정설이었습니다.

이 원칙 자체는 지금도 유효합니다. 바뀐 건 "비싸다"는 말에 붙어 있던 숫자입니다. 2026년 들어 Client Project에서도 Testing Diamond라고 불리는 형태——여전히 소수의 진짜 Unit Test, 훨씬 넓어진 Integration Test 층, 그리고 Pyramid 정설보다 상당히 두꺼워진 E2E 층——로 옮겨가는 팀이 늘고 있습니다. 계기는 Testing 이론이 바뀐 게 아니라, 비용 방정식의 양쪽에서 동시에 일어난 두 가지 변화입니다.

첫째, AI Coding Agent가 새 Page, 새 Form Step, 새 Checkout Variant 같은 User-facing Flow를 사람이 Playwright Script를 작성하는 속도보다 빠르게 구현·배포하고 있습니다. E2E Suite의 성장 속도가 사람이 Typing하는 속도에 묶여 있으면, Product가 변하는 속도를 영원히 따라잡지 못합니다. 둘째, Tooling 자체의 유지 비용이 낮아졌습니다. 실행 속도 향상, 더 강력한 병렬화, 그리고 DOM의 사소한 변화로는 쉽게 깨지지 않는 Test Framework 덕분에 큰 E2E Suite를 Green 상태로 유지하는 비용이 줄었습니다. E2E의 두 가지 큰 비용——작성 비용과 유지 비용——이 동시에 낮아진 이상, "얇게 유지하라"를 무조건적인 규칙으로 취급할 이유가 없어졌습니다.

## Self-healing이 실제로 주는 것

용어가 느슨하게 쓰이는 경우가 많아서 정확히 짚고 넘어가겠습니다. 2026년 시점에 팀들이 실무적으로 채택하는 의미에서의 Self-healing E2E Tooling은, Page에 생긴 작고 비본질적인 변화——`div`가 한 겹 더 감싸져서 Selector가 어긋난 경우, CSS Refactor로 Class 이름이 바뀐 경우, DOM Tree 상 위치는 조금 옮겨졌지만 Role이나 화면에 보이는 Text로는 여전히 찾을 수 있는 경우——를 견디는 Test Infrastructure를 가리키는 게 일반적입니다. 부서지기 쉬운 CSS Path보다 Accessible Role과 화면 Text를 우선하는 Locator 전략과 결합하면, "실제로는 아무것도 안 깨졌는데 Test만 낡아서 실패하는" 종류의 오탐——E2E Suite 유지를 번거롭게 만들어온 주범——을 상당히 줄일 수 있습니다.

AI-assisted E2E 생성은 관련은 있지만 별개의 기능입니다. "재방문한 Customer가 Login하고, Cart에 상품을 담고, 저장된 Card로 Checkout을 완료한다"처럼 User Flow를 평문으로 설명하면 Test 초안을 받아볼 수 있습니다. 손으로 작성하기 번거로운 Flow에 새 Coverage를 빠르게 시작할 때 실제로 유용합니다.

여기서부터는 Client에게도 솔직하게 말하는 부분인데, 이런 것들이 "무엇을 Assert해야 하는가"에 대한 Engineering 판단을 대체하지는 않습니다. Self-healing Locator 전략은 `div` Refactor가 일어나도 Test가 살아남는다는 것을 보장할 뿐, 그 Test가 올바른 것을 검증하고 있는지는 아무것도 말해주지 않습니다. AI가 생성한 Test가 Login Flow를 정확히 Click으로 따라가고서도 "Page가 Crash하지 않았다"만 Assert하는 경우는 충분히 있을 수 있습니다. 실제로 검증해야 하는 건 "Login Redirect를 거쳐도 Cart 내용이 유지되는가", "잠긴 Account에 특정 Error Message가 뜨는가" 같은 Business Requirement입니다. 생성된 Test는 신뢰하고 쓰기 전에 사람이 Assertion을 확인하고 다듬는 과정을 반드시 거쳐야 합니다. AI-assisted 생성은 "빠른 초안"이지 "완성본"이 아니라는 태도로 다루는 게 맞습니다.

## 커지는 E2E Suite를 Page가 아니라 Flow 중심으로 구조화하기

"E2E가 이제 저렴해졌다"를 활용하려다 흔히 빠지는 실수는 Page 단위 Coverage를 기본값으로 삼는 것입니다——Route마다 Test를 하나씩 두고 Page가 정상 렌더링되는지만 확인하는 방식입니다. 낮아진 비용이 실제로 사주는 건 그게 아닙니다. Suite를 관리 불가능하게 만들지 않으면서 더 많은 핵심 User Journey를 End-to-End로 Cover할 수 있게 된 것이 핵심입니다. 정리의 단위는 여전히 Page가 아니라 Flow여야 합니다.

Next.js Client Project에서 실제로 쓰는 구조를, 표준 Playwright API만으로 예시로 들어보겠습니다.

```typescript
import { test, expect } from "@playwright/test";

test.describe("returning customer checkout", () => {
  test("logs in, keeps cart contents, and completes payment with a saved card", async ({ page }) => {
    await page.goto("/login");
    await page.getByLabel("Email").fill("returning-customer@example.com");
    await page.getByLabel("Password").fill("test-password");
    await page.getByRole("button", { name: "Log in" }).click();

    // 이 Flow에서 실제로 중요한 Assertion: Redirect를 거쳐도 상태가 유지되는가
    await expect(page.getByTestId("cart-count")).toHaveText("2");

    await page.getByRole("link", { name: "Checkout" }).click();
    await page.getByRole("radio", { name: /saved card ending in/i }).check();
    await page.getByRole("button", { name: "Place order" }).click();

    await expect(page.getByRole("heading", { name: "Order confirmed" })).toBeVisible();
  });
});
```

중간의 Assertion——Login Redirect를 거쳐도 Cart Count가 유지되는지——이 이 Flow에서의 진짜 Business Risk이지, "Button Click이 됐는가"가 아닙니다. 이 부분은 사람이 의도적으로 넣지 않으면 AI 생성 초안에서 빠지기 쉬운 종류의 Assertion입니다.

Test는 Route가 아니라 Journey(`onboarding`, `checkout`, `account-recovery`, `subscription-changes` 등) 단위로 묶고, "운영 환경에서 절대 깨지면 안 되는 Journey"와 "Cover되면 좋은 Journey"를 짧고 명시적인 목록으로 관리합니다. 이 목록은 Engineering만의 결정이 아니라 Product와 함께 논의할 사안이며, Business가 실제로 감내할 수 있는 Risk 수준이 여기에 반영됩니다.

## webhani가 권장하는 Test 투자 배분

전형적인 Next.js/React Client Project 기준으로, 2026년 시점에 저희가 권장하는 균형은 다음과 같습니다.

- **순수 Logic, 가격 계산 Rule, Data 변환, 독립된 Component 동작은 빠른 Unit Test로 그대로 유지합니다.** 이 Layer는 작고 빠른 상태를 유지해야 하며, Diamond 형태가 "여기를 늘려라"라고 말하는 건 아닙니다. 여전히 가장 저렴하고 빠른 Feedback입니다.
- **"이 Component가 이 API Route와 올바르게 연동되는가"에 대한 검증 대부분은 Integration Test로 옮깁니다.** Diamond 형태에서 실제로 가장 두꺼워지는 Layer가 바로 여기입니다. Full Browser의 Overhead 없이 Component와 Route 간 연동을 검증할 수 있습니다.
- **핵심적이고 경계를 넘나드는 User Journey에 집중해 E2E Coverage를 넓힙니다.** Auth Redirect, 결제 Provider, 여러 Step으로 이뤄진 Form, Navigation을 거쳐도 유지돼야 하는 상태 등이 대상입니다. E2E 비용이 낮아진 걸 실제로 활용해야 할 곳이 여기이며, 작성이 저렴해졌다고 해서 얕고 넓은 Page 렌더링 확인에 그 예산을 쓰는 건 좋은 활용이 아닙니다.
- **AI-assisted 생성은 새 E2E Case의 초안 작성에 활용하되, Merge 전에 반드시 사람의 Review Pass를 거치게 합니다.** "Error가 안 났다"가 아니라 "Assertion이 실제 Business Requirement와 일치하는가"를 구체적으로 확인합니다. AI가 생성한 Code를 다루는 것과 같은 태도로, 유능한 초안이지 완성품이 아니라고 봅니다.
- **Suite가 커져도 Flaky Test 발생률을 명시적으로 Track합니다.** Self-healing Locator가 있어도 이는 일부 오탐을 줄여줄 뿐, Flakiness 전체를 Tooling이 해결해준다고 전제해서는 안 됩니다.

Diamond 형태는 Pyramid의 논리를 부정하는 게 아니라, 몇 년 전과는 확연히 달라진 비용 구조에 같은 논리를 다시 적용한 결과입니다. 이 변화에서 가장 큰 이득을 보는 팀은 Test를 가장 많이 작성하는 팀이 아닙니다. 어떤 User Journey가 지금의 낮아진 E2E Coverage 비용을 쓸 가치가 있는지 의도적으로 선별하고, 그럼에도 CI에서 신뢰하기 전에 반드시 사람의 눈으로 Assertion을 확인하는 팀입니다.
