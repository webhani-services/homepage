## 예산에 잘 안 잡히는 병목

Autoscaling 지연을 예측할 때 대부분 Scheduler의 판단이나 Readiness Probe, JIT Warm-up 시간을 먼저 떠올립니다. 하지만 실제로는 Model Weight나 대용량 ML Dependency를 포함한 Container Image의 경우, Image Pull과 Unpack 과정만으로 전체 시작 시간의 75% 이상을 차지하는 경우가 드물지 않습니다. 5~10GB급 추론용 Image를 Cold Node에서 실행하면, Container Process가 뜨기까지 몇 분이 걸리기도 합니다.

AWS의 Seekable OCI(SOCI) Snapshotter는 Lazy Loading을 통해 이 문제의 일부를 이미 해결해 왔습니다. Image 전체를 다 받기 전에, 실제로 사용하는 Layer만 먼저 Pull해서 Container를 시작할 수 있는 구조입니다. 이번에 새로 나온 Parallel Pull Mode는 그 다음 단계의 병목을 겨냥합니다. 게다가 이번에는 Unpacking 처리 자체를 containerd 본체에 Upstream으로 Contribute했기 때문에, 그 혜택이 EKS에만 국한되지 않습니다.

## Parallel Pull Mode가 실제로 바꾸는 것

SOCI는 Image의 Layer 내용을 Index화해서, Layer 전체를 받지 않아도 어떤 파일이 어느 Chunk에 있는지 Snapshotter가 파악할 수 있게 하는 방식입니다. Parallel Pull Mode는 이 Index를 기반으로 두 가지를 병렬화합니다.

1. **Chunk 병렬 다운로드** — 하나의 Connection으로 Layer를 순차적으로 Pull하는 대신, 여러 Chunk를 별도 Connection으로 동시에 다운로드합니다.
2. **병렬 Unpacking** — 기존에는 다운로드 이후 순차적으로 진행하던 압축 해제와 파일시스템 쓰기 작업을, 나머지 다운로드와 병행해서 처리합니다.

Unpacking 부분은 containerd Core 기능으로 Upstream에 Merge되었기 때문에 AWS 전용 패치가 아닙니다. 해당 기능이 정식 버전에 포함되면 SOCI를 쓰는 EKS 사용자뿐 아니라 containerd 기반 Runtime 전반이 혜택을 받습니다.

이를 종합하면, AWS는 Model File을 포함한 대용량 Container에서 시작 시간을 약 60% 줄였다고 밝혔습니다. Image 크기가 클수록 효과가 커지는 구조라, 정확히 그런 워크로드에 유효합니다.

## EKS에서 활성화하기

SOCI는 Cluster 단위가 아니라 Node Group 단위로 활성화할 수 있습니다. 이는 실무적으로 유용한 포인트로, 대용량 Image를 실제로 실행하는 Node Group(추론용, Batch ML용 등)만 골라서 Pilot 도입하고 나머지에는 영향을 주지 않고 검증할 수 있습니다.

```hcl
# 예시: EKS Managed Node Group에서 SOCI Snapshotter 활성화 (Terraform)
resource "aws_eks_node_group" "inference" {
  cluster_name    = aws_eks_cluster.this.name
  node_group_name = "inference-gpu"
  node_role_arn   = aws_iam_role.node.arn
  subnet_ids      = var.subnet_ids

  launch_template {
    id      = aws_launch_template.soci_enabled.id
    version = "$Latest"
  }
}

# Launch Template의 Bootstrap User Data에서 Flag 지정:
# --local-disk-max-images 50 --soci-snapshotter-enabled true
```

Bootstrap Flag의 정확한 이름은 EKS 최적화 AMI Release에 따라 달라질 수 있으므로, 위 예시는 변경의 "형태"로만 참고하고 실제 배포 전에는 최신 EKS AMI 문서를 반드시 확인해야 합니다.

## 효과가 큰 경우, 크지 않은 경우

다음과 같은 워크로드에서는 확실한 효과를 기대할 수 있습니다.

- **트래픽 스파이크가 큰 추론 워크로드**：Pod 수를 0에 가까운 상태에서 Scale Up하는 구성에서, Pull 대기 시간을 피하기 위해서만 항상 Warm 상태를 유지하는 비용을 줄이고 싶은 경우.
- **CI/CD 환경**：Job마다 짧게 사는 Pod를 띄우는 구조에서는 Pull 속도 향상이 곧바로 Pipeline 시간 단축으로 이어집니다.
- **크지만 변경이 잦지 않은 Base Image**（CUDA, PyTorch, Model Weight를 포함한 Image 등）：같은 Registry에서 반복해서 Pull될수록 Index화 비용이 상쇄됩니다.

반대로 자주 바뀌는 작은 Application Image（100MB 안팎의 Node.js Service Image 등）에서는 Pull 시간 자체가 병목이 아니기 때문에, Chunk 병렬 다운로드로 늘어나는 CPU·Network 부하만큼의 이득을 보기는 어렵습니다.

## 도입 전에 확인할 것

- **Registry 호환성**：Lazy Loading과 Parallel Pull의 혜택을 받으려면 `soci` CLI나 Build Pipeline을 통해 SOCI Index가 포함된 Image를 만들거나 변환해야 합니다. Index가 없는 일반 OCI Image는 그냥 평범한 Pull로 처리됩니다.
- **Pull 중 Network·CPU 여유**：Chunk 병렬 다운로드와 병렬 Unpacking은 Pull 구간에서 Node가 동시에 사용하는 대역폭과 CPU를 늘립니다. Network가 빠듯한 Node Type에서는 이 부분이 이득을 일부 상쇄할 수 있습니다.
- **자사 Image로 직접 Benchmark**：약 60%라는 수치는 AWS가 대용량 AI/ML Image로 측정한 값입니다. 범용 Web App Image에서는 같은 비율이 나오지 않을 수 있으므로, 실제 워크로드로 전후를 측정해 보는 것을 권장합니다.

## webhani의 견해

EKS에서 GPU·추론 워크로드를 운영하는 고객이라면, 이는 투입 대비 실질적인 이득이 큰 변경입니다. Pull 대기 시간을 감추기 위해서만 여분의 Pod를 Warm하게 유지할 필요가 없어지므로, Autoscaling 여유분의 비용을 직접 줄일 수 있습니다. 먼저 하나의 Node Group에서 실제 Image로 Pod Ready 시간을 측정하고, 수치가 확인되면 나머지 추론용 Node로 확대 적용하는 방식을 권장합니다.

장기적으로는 Unpacking 처리가 containerd 본체에 들어갔다는 사실 자체가 더 흥미로운 Signal입니다. 앞으로 몇 번의 Release Cycle을 거치며, Parallel Pull과 유사한 동작은 AWS만의 기능이 아니라 Container Platform 전반의 기본 기대치가 될 가능성이 높습니다. EKS를 쓰지 않더라도 동향을 지켜볼 가치가 있습니다.
