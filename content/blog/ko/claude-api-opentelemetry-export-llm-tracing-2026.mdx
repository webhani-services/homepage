10월 14일 Claude Platform 릴리스 노트에 Messages API 요청과 Managed Agents 세션을 추적하는 OpenTelemetry Export(beta)가 추가되었습니다. Python, TypeScript, C#, Go, Java, PHP, Ruby SDK가 Span을 내보낸다고 합니다. 릴리스 노트는 짧기 때문에, 이 글에서는 "기존 Trace 안에 LLM 호출을 어떻게 둘 것인가", "Span에 무엇을 기록할 것인가"라는 실무 쪽 질문을 다룹니다.

활성화 방법은 beta라서 바뀔 수 있으니 공식 문서를 확인하시기 바랍니다. 아래 설계 원칙은 활성화 방식과 관계없이 적용됩니다.

## LLM 호출에 별도 Span이 필요한 이유

LLM 호출은 요청 전체에서 가장 느리고 비용이 큰 구간이 되기 쉽습니다. Span이 없으면 느린 Endpoint는 "API Handler가 9초 걸렸다"로만 보입니다. Span이 있으면 8.2초가 모델 호출 한 번에 쓰였고, 한 번 재시도되었으며, 지난주보다 Prompt가 커졌다는 사실까지 확인할 수 있습니다.

LLM Span이 일반 HTTP Client Span과 다른 점은 세 가지입니다.

- **Latency 편차가 수십 배에 이릅니다.** 출력 길이와 Thinking Effort에 따라 달라지므로, 고정 임계값 Alert는 계속 울리거나 한 번도 울리지 않습니다.
- **비용은 요청 수가 아니라 Token 수로 결정됩니다.** 입력, 출력, Cache 읽기의 단가가 서로 다릅니다.
- **재시도와 Streaming이 동작을 가립니다.** 40초 동안 Streaming한 호출과 빠르게 실패 후 재시도한 호출이 단순한 Duration 지표에서는 비슷해 보입니다.

## 기존 Trace에 연결하기

SDK Export를 쓰든 직접 Span을 작성하든 구조는 같습니다. LLM 호출을 요청 Span의 Child로 두어, 사용자 요청과 비즈니스 로직과 모델 호출이 하나의 Trace ID로 이어지게 합니다.

아래는 안정된 OpenTelemetry API만으로 작성한 예시입니다. SDK Export를 아직 쓸 수 없는 환경이나 Attribute를 직접 제어하고 싶을 때 유용합니다.

```ts
import Anthropic from "@anthropic-ai/sdk";
import { trace, SpanStatusCode } from "@opentelemetry/api";

const tracer = trace.getTracer("llm-client");
const client = new Anthropic();

export async function tracedMessage(
  params: Anthropic.MessageCreateParamsNonStreaming,
  feature: string,
) {
  return tracer.startActiveSpan(`llm.messages ${params.model}`, async (span) => {
    span.setAttributes({
      "gen_ai.system": "anthropic",
      "gen_ai.request.model": params.model,
      "gen_ai.request.max_tokens": params.max_tokens,
      "app.feature": feature,
    });
    try {
      const res = await client.messages.create(params);
      span.setAttributes({
        "gen_ai.response.id": res.id,
        "gen_ai.usage.input_tokens": res.usage.input_tokens,
        "gen_ai.usage.output_tokens": res.usage.output_tokens,
        "app.cache_read_tokens": res.usage.cache_read_input_tokens ?? 0,
        "gen_ai.response.finish_reasons": [res.stop_reason ?? "unknown"],
      });
      return res;
    } catch (err) {
      span.recordException(err as Error);
      span.setStatus({ code: SpanStatusCode.ERROR });
      throw err;
    } finally {
      span.end();
    }
  });
}
```

`gen_ai.*` Attribute 이름은 OpenTelemetry GenAI Semantic Conventions에서 가져온 것이며 아직 experimental 상태입니다. 지금 사용하면 이후 벤더가 내보내는 Attribute와 Dashboard를 맞추기 쉽지만, 이름이 바뀔 수 있습니다. `app.*`은 자체 Attribute이며, 실무에서는 이쪽의 가치가 더 큰 경우가 많습니다.

## 기록할 것과 기록하지 않을 것

**기록할 것**

- 모델 이름과 `max_tokens`: 배포로 모델이 의도치 않게 바뀐 경우를 알아챌 수 있습니다.
- Cache 읽기를 포함한 Token 수: Cache 읽기의 급감은 Prompt 앞부분이 바뀌어 비용이 오르기 직전이라는 가장 빠른 신호입니다.
- `feature` 또는 `tenant` Attribute: "Assistant에 하루 X달러가 든다"는 대응하기 어렵지만, "요약 기능이 X달러이고 그중 60%가 한 Tenant"라면 조치할 수 있습니다.
- Stop reason: `max_tokens`로 중단되는 비율이 늘면 잘린 답변이 사용자에게 가고 있다는 뜻입니다.

**기본값으로 기록하지 않을 것**

- Prompt와 응답 본문: Telemetry 백엔드에 개인정보가 들어가는 가장 큰 경로이며 저장 비용도 늘립니다. 디버깅에 필요하다면 Sampling하고, Masking하고, 별도 Store에서 짧은 보존 기간을 적용하십시오.

## Trace뿐 아니라 Metric도

Trace는 "이 요청에 무슨 일이 있었는가"에 답합니다. Alert에는 같은 데이터에서 Metric을 만들어 사용합니다. 최소한의 예시입니다.

| Metric | 목적 |
| --- | --- |
| 모델·feature별 Token 사용량 | 비용 귀속 |
| Cache 읽기 비율(읽기/입력 합계) | Prompt 앞부분 퇴행 감지 |
| 모델별 p95 Duration | 모델마다 Latency 기준이 다름 |
| 상태 유형별 Error 비율(429, 5xx, overloaded) | 자사 버그와 용량 이슈 구분 |
| `max_tokens` 중단 비율 | 출력 품질 Guard |

Prometheus 계열 백엔드에서는 Label Cardinality를 관리해야 합니다. `feature`와 `model`은 Label로 괜찮지만, 요청 ID나 사용자 ID는 Metric이 아니라 Span에 둡니다.

## Agent 세션은 다릅니다

다단계 Agent에서는 요청 하나가 여러 번의 모델 호출과 Tool 호출로 펼쳐집니다. 볼 단위는 세션입니다. 부모 Span 하나를 두고 각 Turn과 Tool 호출을 Child로 둡니다. 이 부분에서 Native Export가 가장 도움이 됩니다. Loop를 수작업으로 재구성하는 일은 번거롭고 틀리기 쉽기 때문입니다. Trace를 검토할 때는 개별 호출의 Latency보다 Turn 수를 먼저 보십시오. 5 Turn이면 될 일이 14 Turn 걸린다면 거의 항상 Prompt나 Tool 설명의 문제입니다.

## webhani의 권장 사항

1. 먼저 Staging 환경에서 SDK Export를 켜고, 직접 만든 Span과 비교한 뒤에 직접 만든 쪽을 제거합니다.
2. `app.feature`, `app.tenant`, Cache 읽기 Token의 세 가지 Custom Attribute를 서비스 전반에서 통일합니다.
3. Prompt 본문은 기본적으로 Span에 넣지 않습니다.
4. Latency와 Error뿐 아니라 Cache 읽기 비율과 `max_tokens` 중단 비율에도 Alert를 설정합니다.
5. beta라는 점을 가볍게 보지 않습니다. SDK 버전을 고정하고 위와 같은 얇은 Wrapper를 두어, Attribute 이름이 바뀌어도 수정이 한 파일에서 끝나도록 합니다.

LLM 호출은 이제 대부분의 Backend에서 핵심 의존성입니다. Database나 결제 호출과 같은 수준으로 Tracing을 갖추는 일은 작은 작업이지만, 청구 금액이나 Latency 그래프가 예상 밖으로 나왔을 때 그 수고가 확실히 보상받습니다.
