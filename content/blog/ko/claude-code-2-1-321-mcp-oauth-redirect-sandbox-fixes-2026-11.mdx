Claude Code 2.1.321에 대한 이야기는 대부분 모델 변경에 모입니다. Fable 5.2가 기본 Fable 모델이 되었고 1M context window를 지원합니다. 비용 산정에 중요한 내용이며, 모델 마이그레이션은 별도 글에서 다루었습니다. 이 글에서는 상대적으로 덜 주목받은 부분, 즉 권한과 보안 수정을 살펴봅니다.

먼저 전제를 밝힙니다. 아래 보안 관련 내용은 릴리스를 요약한 일본어 해설 글(labmemo.com) 한 건에 근거하며, 공식 changelog의 문구가 아닙니다. 공식 changelog에서 확인되는 것은 모델 변경입니다. 수정 내용의 정확한 표현은 공식 changelog에서 확인해 주십시오.

## 수정된 것으로 알려진 내용

해당 요약에서 눈에 띄는 항목은 두 가지입니다.

1. **MCP 서버의 OAuth Redirect 문제**. 특정 조건에서 사용자가 승인한 Host가 아닌 다른 Host로 refresh token 등의 비밀 정보가 전송될 수 있었다.
2. **read-only Bash 명령이 권한 확인 없이 Sandbox 밖에서 실행될 수 있었던 문제**.

2차 자료만으로는 발생 조건을 확인할 수 없으므로 추측하지 않겠습니다. 대신 두 수정이 건드리는 경계는 에이전트와 MCP를 쓰는 모든 팀에 공통이므로, 문제의 유형 관점에서 정리합니다.

## OAuth Redirect 문제가 중요한 이유

OAuth로 인증하는 MCP 서버는 개발자의 PC에 refresh token을 보관합니다. refresh token은 유효 기간이 길고, Scope도 한 작업에 필요한 범위보다 넓은 경우가 많습니다. Redirect 오류로 잘못된 Host에 전달되면 피해가 현재 Session에 그치지 않고, 폐기하기 전까지 계속 유효합니다.

이는 고전적인 OAuth open redirect와 같은 실패 유형입니다. 다만 이번에는 README의 URL을 붙여 넣어 설치하는 도구 안에서 발생합니다. 신뢰 판단은 설치 시점에 한 번 이루어지고, 이후에는 사람 없이 계속 동작합니다.

따라서 물어야 할 것은 "이 취약점의 영향을 받았는가"보다 "우리 노트북에 자격 증명을 가진 MCP 서버가 몇 개이고, 누가 승인했는가"입니다.

## read-only Bash 문제가 중요한 이유

에이전트의 권한 시스템은 분류에 의존합니다. 읽기 전용이면 실행하고, 쓰기이면 확인을 요청하는 방식입니다. 이 분류에 구멍이 있으면 편의 기능이 곧 우회 경로가 됩니다. 이번에 보고된 내용은 read-only로 분류된 명령이 확인 없이 Sandbox 밖에서 실행될 수 있었다는 점입니다.

여기서 얻는 교훈은 일반적입니다. "read-only"를 그 자체로 보안 경계로 취급하지 마십시오. 경계는 Sandbox이고, 분류기는 그 위에 얹힌 사용성 계층입니다.

## 오늘 바로 할 수 있는 점검

먼저 목록을 만듭니다. Project 단위 MCP 서버는 `.mcp.json`에, 사용자 단위 서버는 Claude Code 설정에 있습니다. Project 파일을 훑는 예시입니다.

```bash
# ~/work 아래 모든 Repository에 선언된 MCP 서버를 나열
find ~/work -name ".mcp.json" -not -path "*/node_modules/*" -print0 \
  | xargs -0 -I{} sh -c 'echo "== {}"; jq -r ".mcpServers | to_entries[] | \"\(.key)\t\(.value.url // .value.command)\"" "{}"'
```

서버마다 유지 보수 주체, OAuth 사용 여부, 요청하는 Scope, 토큰 저장 위치의 네 가지를 기록합니다. 한 줄로 답할 수 없는 항목은 검토 대상에 올립니다.

결과에 따라 다음과 같이 대응합니다.

- **먼저 업데이트합니다**. 팀 전체를 2.1.321 이상으로 올립니다. Homebrew를 쓰면 stable 채널과 cask 반영이 약 일주일 늦을 수 있다는 정보가 있으므로, `claude --version`으로 실제 버전을 확인하십시오.
- **중요도가 높은 서버는 재승인합니다**. 소스 호스팅, 클라우드 콘솔, 티켓 시스템에 연결된 MCP 서버는 Provider 쪽에서 기존 권한을 취소하고, 업데이트 후 다시 승인합니다. 잘못된 곳으로 전달되었을 수 있는 refresh token이 무효화됩니다.
- **Scope를 줄입니다**. 재승인은 더 적은 Scope를 요청할 가장 손쉬운 기회입니다. 에이전트 용도의 대부분은 read-only Scope로 충분합니다.
- **Sandbox를 켜 둡니다**. 빌드를 통과시키려고 끈 사람이 있다면 이유를 확인하고, 경로나 권한 문제의 근본 원인을 고치십시오.

## 함께 검토할 운영 정책

업데이트로 막히는 것은 이번 구멍뿐입니다. 다음 구멍에 대비해 아래 항목을 권장합니다.

| 대책 | 이유 |
| --- | --- |
| Repository별로 MCP 서버를 allowlist로 관리하고 PR에서 검토 | `.mcp.json` 변경이 Diff로 드러남 |
| 직접 호스팅하거나 계약된 Vendor의 서버를 우선 사용 | OAuth Flow에 책임지는 주체가 존재 |
| Provider가 지원하면 수명이 짧은 자격 증명 사용 | 유출되어도 자동으로 만료 |
| 에이전트용 ID와 사람 ID를 분리 | 폐기해도 사람이 잠기지 않음 |

특정 Vendor에 국한된 이야기가 아닙니다. CI 서비스 계정에 이미 적용하고 있는 최소 권한 원칙을 새로운 종류의 Client에도 적용하는 것뿐입니다.
