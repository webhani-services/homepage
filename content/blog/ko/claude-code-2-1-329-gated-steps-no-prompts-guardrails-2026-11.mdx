공식 Release Note를 미러링하는 서드파티 Changelog 계정에 따르면, Claude Code 2.1.329에서 "위험 작업 확인(risky-action confirmations)"이 제거되어 기존에 확인 단계가 있던 작업이 자동으로 실행된다고 합니다. 같은 Release에서 예약 Task, `/loop` wakeup, fork를 보여 주는 `/tasks` View도 추가되었다고 알려져 있습니다. 확인한 것은 2차 자료뿐이므로, 세부 내용은 공식 Changelog에서 다시 확인하시기 바랍니다.

세부 내용이 어떻든 방향은 분명합니다. 대화형 확인은 약한 통제 수단으로 취급되고, 안전을 지키는 부담이 Configuration 쪽으로 옮겨 가고 있습니다. 우리 팀의 Guardrail이 settings에 있는지, 아니면 담당자의 반사 신경에만 의존하는지 점검하기 좋은 시점입니다.

## 확인 Prompt가 약한 통제인 이유

확인 Dialog가 효과를 내려면 읽는 사람이 내용을 이해하고 주의를 기울여야 합니다. 하루에 40번 확인을 요구받으면 41번째는 읽지 않고 승인하게 됩니다. 악의가 아니라 익숙함이 원인입니다.

무인 실행에서는 Prompt가 아무 도움이 되지 않습니다. 예약 Task, `/loop`, CI Job에는 클릭할 사람이 없습니다. 파괴적인 명령을 막는 역할을 Prompt에 맡긴 Pipeline은 이미 무방비 상태입니다.

따라서 Prompt 제거 자체가 곧바로 퇴보는 아닙니다. 경계를 강제하는 다른 장치가 없을 때만 문제가 됩니다.

## 경계를 둘 곳: Settings

Claude Code는 settings 파일에서 권한 Rule을 읽습니다. 이 Rule은 결정적입니다. 허용된 명령은 실행되고, 거부된 명령은 사람의 판단 없이 거부됩니다. 되돌릴 수 없는 작업에 필요한 성질입니다.

프로젝트의 `.claude/settings.json`은 아래와 같은 형태에서 시작하면 무난합니다.

```json
{
  "permissions": {
    "allow": [
      "Bash(npm run test:*)",
      "Bash(npm run lint)",
      "Bash(git diff:*)",
      "Bash(git status)"
    ],
    "deny": [
      "Bash(git push --force:*)",
      "Bash(rm -rf:*)",
      "Bash(curl:*)",
      "Read(./.env)",
      "Read(./.env.*)"
    ]
  }
}
```

두 가지 습관이 효과를 좌우합니다. 첫째, allow 목록은 좁게 시작하고 실제 필요에 따라 넓힙니다. 둘째, `deny`를 가장 중요하게 다룹니다. 모델이 어떻게 판단하든 절대 일어나서는 안 되는 작업의 목록이기 때문입니다.

Rule의 정확한 문법은 Version에 따라 달라질 수 있으므로, 사용 중인 Version의 문서로 확인하시기 바랍니다.

## Pattern으로 표현할 수 없는 검사는 Hook으로

"이 Migration은 운영 Table을 건드린다" 같은 판단은 Pattern Rule로 표현할 수 없습니다. 이때는 `PreToolUse` hook으로 실행 직전의 호출을 검사하고, 0이 아닌 종료 코드로 차단합니다. 최소한의 예시입니다.

```bash
#!/usr/bin/env bash
# .claude/hooks/block-prod-db.sh
# stdin으로 tool call JSON을 읽고, 운영 대상이면 거부합니다.
input="$(cat)"
if echo "$input" | grep -qE 'prod(uction)?[-_.]?(db|database|cluster)'; then
  echo "Blocked: command references a production database" >&2
  exit 2
fi
```

이 정규식이 완전하지 않다는 점은 알고 있습니다. 중요한 것은 아무도 지켜보지 않는 Session을 포함해 매번 검사가 실행된다는 사실입니다.

## 적용 Checklist

이 변경이 포함된 Version으로 올릴 때의 순서입니다.

1. 2.1.329의 공식 Release Note를 읽고 어떤 작업의 확인이 사라졌는지 정확히 파악합니다.
2. force push, 재귀 삭제, secrets 파일, 외부 네트워크 도구에 대한 명시적 `deny` Rule을 `.claude/settings.json`에 Commit합니다.
3. CI나 예약 실행에서 차단해야 할 항목은 settings 또는 hook으로 옮깁니다. 이 경로들은 원래 사람이 없던 경로입니다.
4. 먼저 임시 Branch에서 새 Version을 실행해, 확인 없이 무엇이 실행되는지 관찰합니다.
5. Tool 호출을 Log로 남깁니다. 이미 Claude Code Telemetry를 내보내고 있다면, 거부된 호출에 Alert를 설정해 성공뿐 아니라 시도도 볼 수 있게 합니다.

## webhani의 관점

이번 변경을 "Claude Code가 덜 안전해졌다"로 읽을 필요는 없다고 봅니다. 안전을 Dialog에 맡기는 일을 그만두라는 신호로 읽는 편이 맞습니다. 제한을 Version 관리되는 settings에 적어 둔 팀은 거의 영향을 받지 않습니다. 개발자의 눈에 의존해 온 팀은 이번 Upgrade를 계기로 제한을 문서화해야 합니다.

간단한 점검 방법이 있습니다. 모든 개발자를 Script로 바꾼다고 가정해도, 현재 설정이 `main`으로의 force push를 막을 수 있습니까? 답이 "누군가 클릭하느냐"에 달려 있다면, Upgrade 전에 먼저 고쳐 두시기 바랍니다.
