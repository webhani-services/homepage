Claude Code 2.1.331(11월 23일)과 2.1.332(11월 25일)의 changelog에는 지나치기 쉽지만, 팀이 Agent 설정을 배포하고 신뢰하는 방식에 영향을 주는 항목이 있습니다. 실무에서 중요한 것은 세 가지입니다. MCP를 통해 제공되는 Skill, Skill 안의 Shell Command를 거부할 수 있는 새 Hook, 그리고 Plugin Marketplace 업데이트에 관한 날짜가 명시된 변경입니다.

아래 내용은 공식 changelog를 기준으로 합니다. Release Notes가 간결하기 때문에, 기재된 범위를 넘어 설명하는 부분에는 그 사실을 명시했습니다.

## 변경 사항

**MCP Server의 Skill(beta).** 2.1.332부터 MCP Server가 Skill을 노출할 수 있으며, `/` 메뉴에 `server:skill` 형태로 표시됩니다. 지금까지 Skill은 Repository, 사용자 홈 Directory, 또는 Plugin 안에 있는 파일 묶음이었습니다. MCP Server에서 제공하면 각 Repository에 복사하지 않고 중앙에서 버전 관리와 업데이트를 할 수 있습니다.

**`PreSkillShellCommand` Hook.** Skill은 로드될 때 실행되는 인라인 Shell Command를 포함할 수 있습니다. 새 Hook 이벤트는 이 Command가 실행되기 전에 발생하며, 실행을 거부할 수 있습니다. 이 단계에 정책을 끼워 넣을 수 있는 첫 번째 지점입니다.

**Marketplace 자동 업데이트.** 2.1.331에는 "향후 릴리스에서, 2026년 11월 30일 이후" 관리형 설정 `extraKnownMarketplaces`에 있는 Plugin Marketplace가 기본값으로 자동 업데이트된다고 적혀 있습니다. 해당 항목에 `"autoUpdate": false`를 지정하면 적용에서 제외할 수 있습니다.

특정 환경에서 영향을 줄 수 있는 작은 변경도 있습니다.

- Computer Use가 활성화된 Mac에서 `computer-use`가 예약된 Skill 이름이 되었습니다. 같은 이름의 Skill이나 Command는 더 이상 로드되지 않습니다.
- Desktop Code 탭의 기본 OpenTelemetry `service.name`이 `claude-code-desktop`으로 바뀌었습니다. `claude-code`로 필터링한 Dashboard나 Alert는 수정하거나 `OTEL_SERVICE_NAME`을 설정하지 않으면 조용히 매칭되지 않게 됩니다.
- 2.1.331에서 `PermissionDenied` Hook의 `retry: true`는 "사용자가 그 호출을 요청한 경우에만 재시도"를 의미하게 되었습니다.

## Marketplace 변경에 주의해야 하는 이유

Plugin Marketplace는 개발자의 Agent Session 안에서 실행되는 코드와 지시문(Skill, Hook, Slash Command, 때로는 MCP Server 정의)의 공급원입니다. 기본값이 자동 업데이트라는 것은 이것이 지속적인 Delivery 경로가 된다는 뜻입니다. Marketplace가 자사 소유이고 리뷰를 거쳤다면 편리합니다. 하지만 Plugin 최신 버전이 무엇을 하는지 아무도 확인하지 않은 상태라면 Supply Chain 노출 지점이 됩니다.

Hook은 개발자의 권한으로 실행되고, Skill의 인라인 Shell Command는 악의적이거나 부주의한 업데이트로 바뀔 수 있는 대표적인 위치입니다. 이런 유형의 위험에는 버전 고정과 리뷰가 일반적인 대응이며, Opt-out 플래그가 Claude Code가 제공하는 수단입니다.

아래는 changelog의 내용이 아니라 당사의 판단에 따른 권장 사항입니다.

1. 현재 `extraKnownMarketplaces` 항목을 전수 조사합니다.
2. 항목마다 소스를 직접 관리하고 리뷰하는지 판단합니다. 그렇다면 자동 업데이트를 유지해 수작업을 줄여도 대체로 괜찮습니다.
3. 서드파티 Marketplace는 11월 30일 전에 `"autoUpdate": false`를 설정하고, Diff를 읽은 뒤 정해진 주기로 업데이트합니다.

보수적인 구성의 관리형 설정 예시입니다. Marketplace 이름과 Repository는 Placeholder이며, 항목의 정확한 형식은 사용 중인 버전의 설정 Reference에서 확인하시기 바랍니다.

```json
{
  "extraKnownMarketplaces": {
    "internal-tools": {
      "source": { "source": "github", "repo": "your-org/claude-plugins" },
      "autoUpdate": true
    },
    "community-tools": {
      "source": { "source": "github", "repo": "some-vendor/claude-plugins" },
      "autoUpdate": false
    }
  }
}
```

## Skill Shell Hook 활용

Hook은 설정 파일에서 정의하며, `PreSkillShellCommand`도 다른 실행 전 이벤트와 마찬가지로 Command가 표준 입력으로 정보를 받고 종료 상태로 거부를 알리는 방식일 것으로 보입니다. 이 이벤트의 Payload 필드는 확인하지 못했으므로, 운영용 로직을 작성하기 전에 Hook Reference를 읽으시기 바랍니다. 보수적인 정책의 형태는 단순합니다.

```bash
#!/usr/bin/env bash
# 예시입니다. 입력 파싱은 공식 문서의 Payload에 맞게 조정하세요.
set -euo pipefail

payload="$(cat)"

# 내려받은 내용을 그대로 Shell에 넘기는 Command를 거부
if echo "$payload" | grep -Eq 'curl[^|]*\|[[:space:]]*(ba)?sh|wget[^|]*\|[[:space:]]*(ba)?sh'; then
  echo "Blocked: skill tried to pipe a download into a shell" >&2
  exit 2
fi

exit 0
```

이런 Deny-list는 경계가 아니라 보조 수단입니다. 더 견고한 방침은 신뢰하는 Marketplace의 Skill만 허용하고, Hook으로는 실행된 Skill을 기록해 변화를 감지하는 것입니다. Hook 스크립트 자체가 오류를 낼 때 어떻게 동작해야 하는지도 Fail-closed 관점에서 미리 정해 두십시오.

## MCP 제공 Skill의 Trade-off

중앙에서 제공하는 Skill은 실제 문제를 해결합니다. Repository가 30개인 팀에서 "마이그레이션 체크리스트 실행" Skill을 각 Repository에 복사하면 내용이 반드시 어긋납니다. MCP Server에서 제공하면 오류 수정은 한 곳에서 끝납니다.

대신 Skill이 MCP Server와 같은 신뢰 특성을 갖게 됩니다. Server가 침해되거나 잘못 설정되면 그 Skill을 로드하는 모든 Session이 영향을 받고, Repository에 Commit이 없어도 Session 사이에 내용이 바뀔 수 있습니다. Skill을 제공하는 MCP Server는 런타임에 의존하는 Package Registry와 같은 수준으로 다루는 것이 타당합니다.

- 직접 호스팅하거나, 이미 검증한 업체를 사용합니다.
- 인증을 적용하고, 자격 증명은 Commit되는 설정 파일에 두지 않습니다.
- 어떤 Session에서 어떤 Skill이 로드되었는지 기록합니다(Repository의 git 이력으로는 나중에 추적할 수 없기 때문입니다).

beta 기능이므로 Skill Library 전체를 옮기기보다 위험이 낮은 Skill 하나로 먼저 시험해 보시기를 권합니다.

## 이번 주에 할 일

- 관리 대상 Marketplace마다 11월 30일 전에 `autoUpdate` 값을 결정합니다.
- 기존 Skill과 Command 중 `computer-use`라는 이름이 있는지 검색합니다.
- Desktop Code 탭을 쓰는 개발자가 있다면 `service.name = claude-code`로 걸어 둔 OpenTelemetry 필터를 수정합니다.
- `PreSkillShellCommand`는 먼저 로그만 남기는 모드로 시험하고, 실제로 실행되는 Skill을 확인한 뒤 차단을 시작합니다.

각 변경은 단독으로는 크지 않습니다. 그러나 함께 보면 방향이 보입니다. Agent 설정은 배포되고 업데이트되는 Dependency가 되어 가고 있으며, 다른 Dependency와 마찬가지로 리뷰와 버전 고정 습관이 필요합니다.
