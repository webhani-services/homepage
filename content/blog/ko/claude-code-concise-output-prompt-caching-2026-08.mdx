## 무음의 비용 증가: 조용히 누적되는 캐싱 버그

2026년 8월 19일, Claude Code는 버전 2.1.237을 릴리스했습니다. 중요한 수정 항목은 다시 사용되어야 할 컨텍스트가 각 API 호출마다 다시 전송되는 프롬프트 캐싱 버그입니다. 기술적으로는 단순하지만 운영상의 영향은 무시할 수 없습니다. 이 버그는 명백한 실패 없이 수주 동안의 Agent 세션에 걸쳐 조용히 복합화됩니다.

구체적으로 생각해봅시다. 당신의 팀이 CI/CD 파이프라인에서 Claude Code를 지속적인 개발 보조도구로 실행 중입니다. 대규모 프로젝트 컨텍스트(시스템 프롬프트, 도구 정의, 참조 파일)가 있습니다. 캐싱 없는 기본 설정에서는 각 Agent 턴마다 이 컨텍스트를 전송합니다:

- 시스템 프롬프트 + 지시사항: 8 KB
- 도구 정의(Bash, 파일 읽기, grep, 편집): 15 KB
- 컨텍스트에 고정된 참조 파일(프로젝트 구조, 명명 규칙, 아키텍처 문서): 25 KB
- 현재 턴의 실제 대화 이력: 5 KB
- 합계: 53 KB/턴

일반적인 다단계 Agent 작업(예: 5~6개의 Agent 턴에 걸쳐 8~12개의 도구 호출을 포함하는 코드 리뷰)의 경우, 작업당 약 300 KB의 중복 컨텍스트 전송 및 동일한 시스템 프롬프트와 도구 정의 재처리 비용이 발생합니다. 1개월간의 CI 실행(약 50회의 코드 리뷰 실행)에서 프로젝트당 월간 약 15 MB의 불필요한 전송이 발생합니다.

프롬프트 캐싱이 제대로 작동하면, 첫 번째 턴은 안정된 컨텍스트 48 KB를 전송하고 API가 이를 캐싱합니다(일반 토큰 가격의 약 25% 가격으로 청구됨). 후속 턴은 그 캐시를 재사용하여 작은 대화 이력 델타만 지불합니다. 절감 효과는 복합화됩니다: 캐싱 사용 시 15 MB는 약 2 MB의 전송 토큰으로 변하고, 계산 비용도 비례적으로 감소합니다.

캐싱 버그는 팀이 캐싱의 이점을 모르면서 전체 비캐싱 가격을 지불하고 있었음을 의미합니다. 5개의 프로젝트에서 정기적으로 Agent 지원 코드 리뷰를 실행하는 팀의 경우, 월간 비용 차이는 실질적입니다: 프로젝트 규모와 Agent 빈도에 따라 $200~$800 범위입니다. 빠른 반복의 경우 더 중요합니다: Agent 작업이 예상보다 오래 걸린다면, 손상된 캐시가 2분 작업을 4분 작업으로 조용히 변환할 수 있습니다. API가 캐싱해야 할 컨텍스트를 재처리하고 있기 때문입니다.

## 수정이 지속 가능한 Agent 워크플로우에 미치는 중요성

직접적인 교훈은 프롬프트 캐싱이 무료 최적화가 아니라, agentic 워크플로우를 규모에서 경제적으로 실행 가능하게 하는 기본 가정이라는 것입니다. Claude Code를 장시간 실행하는 개발 보조도구로 사용하거나 CI/CD에 Agent 호출을 임베드하여 실행 중인 경우, 캐싱 정확성은 직접적으로 다음에 영향을 미칩니다:

**비용 예측 가능성.** Agent 지원 코드 리뷰에 $500/월을 예산화하는 팀은 캐싱의 완전한 이점을 얻고 있는지 알아야 합니다. 버그가 있었다면, 실제 비용은 더 높고, 확장은 고통스럽고 비선형인 곡선이 될 것입니다.

**지연 시간 일관성.** 시스템 프롬프트, 도구 정의, 참조 컨텍스트에 의존하는 Agent 작업은 API가 안정된 �ンテンツ 재처리를 건너뛰기 때문에 캐시 히트의 이점을 얻습니다. 캐싱이 조용히 손상되면, 사용자는 더 느린 완료를 보고 모델 속도 저하 또는 네트워크 지연이 아닌 구성 문제로 인한 것으로 생각할 수 있습니다.

**컨텍스트 윈도우 경제성.** Agentic 워크플로우에서는 Agent 동작을 안내하기 위해 시스템 컨텍스트에 참조 자료(아키텍처 가이드, 명명 규칙, 보안 정책)를 자주 고정합니다. 캐싱을 사용하면, 첫 히트 후 캐싱되므로 이 참조 자료가 더 많아도 무리 없습니다. 올바른 캐싱 없으면, 동일 자료는 반복 비용이 높고, 팀은 이를 제거하기 시작하여 Agent 출력 품질이 감소합니다.

v2.1.237 수정은 이러한 가정을 복원합니다. 그러나 더 깊은 교훈은 캐시 정확성이 손상될 때까지 보이지 않으므로, 설정에서 명시적으로 검증할 가치가 있다는 것입니다.

## 간결 출력 스타일: 신호와 노이즈 분리

동일한 릴리스에서 "Concise"라는 새로운 출력 스타일 옵션이 도입되었습니다. 이는 다른 문제점을 해결합니다: 장황한 Agent 출력입니다.

기본적으로 Claude Code의 Agent 모드는 코드 변경과 함께 완전한 설명 텍스트를 반환합니다. 이는 대화형 세션에서 추론을 이해하려 할 때 유용합니다. 그러나 터미널 중심 워크플로우(파이프라인에서 Agent를 무인 모드로 실행, Agent 로그를 대량으로 검토, 감사 목적으로 트랜스크립트 저장)에서는 그 장황함이 실제 작업 산출물(코드 변경, 도구 호출, 내린 결정)을 모호하게 하는 노이즈를 만듭니다.

Concise 모드는 설명적 내러티브를 제거합니다. 작업 출력 없이는 제거하지 않습니다. 일반적인 장황한 Agent 턴은 다음과 같습니다:

```
실패한 테스트를 분석하고 수정을 구현하겠습니다. 먼저 오류 메시지를 검토하여 무엇이 일어나고 있는지 이해하고, 관련 코드 섹션을 보고, 근본 원인을 해결하면서 부작용을 초래하지 않는 대상 수정을 작성하겠습니다.

[... 8개 파일 읽기, 2개 grep ...]

문제는 이벤트 리스너 정리의 경쟁 조건입니다. 현재 코드는 컴포넌트를 제거하기 전에 구독을 취소하지 않으므로, 언마운트 후 낡은 콜백이 실행됩니다. useEffect 반환에 정리 단계를 추가하겠습니다.

[... 편집 ...]

수정은 최소한이고 정확합니다. 정리 함수에 2줄만 추가됩니다. 이렇게 하면 리스너가 컴포넌트 언마운트 전에 제거됩니다.
```

Concise 모드에서는 동일한 턴이 다음처럼 됩니다:

```
오류 검사 → 정리에서 경쟁 조건 감지 → 수정 적용(useEffect 반환 핸들러).
```

CI 로그에서 20단계 Agent 작업을 스캔하여 패턴이나 디버깅을 찾는 경우, 차이는 뚜렷합니다. Verbose 모드는 40~50 KB의 텍스트를 생성합니다; Concise 모드는 2~3 KB의 신호를 생성합니다. 코드 변경 자체는 동일합니다. 오직 내러티브만 바뀝니다.

이는 여러 시나리오에서 유용합니다:

- **CI 로그:** 파이프라인의 Agent 실행은 실제 diff를 묻지 않는 더 깔끔하고 스캔 가능한 트랜스크립트를 생성합니다.
- **감사 추적:** 준수 또는 학습 목적으로 Agent 세션을 장기 저장할 때 노이즈 감소의 이점을 얻습니다.
- **병렬 Agent 조정:** 여러 Agent가 관련 작업에서 작업 중이고 텍스트를 읽지 않고 높은 수준의 결정을 추적해야 하는 경우, Concise 출력은 컨텍스트 전환을 줄입니다.
- **모델 비용:** 프롭스 토큰이 적을수록 동일한 작업 산출물에 대한 API 비용이 낮습니다.

트레이드오프는 Agent가 결정을 내린 이유를 이해하는 데 도움이 될 수 있는 추론 설명을 잃는 것입니다. 팀은 Verbose 설명을 필요로 하는 Agent 작업(대화형 문제 해결, 디버깅, 아키텍처 결정) 대 Concise 출력으로 충분한 작업(일상적 리팩터, 테스트 추가, 코드 생성)을 신중하게 결정해야 합니다.

## Webhani의 권장사항: 캐시 친화적 워크플로우 구조

캐싱 수정과 간결 출력을 모두 잘 작동시키려면, Agent 컨텍스트 설정 방식에 작은 구조적 투자를 권장합니다.

먼저 안정된 컨텍스트(시스템 프롬프트, 도구 정의, 참조 자료)를 턴 고유 콘텐츠(대화 이력, 현재 PR diff)에서 분리합니다. 이렇게 하면 캐싱 경계가 명시됩니다:

```yaml
# claude-code 설정(.claude/CLAUDE.md)
## 프로젝트 설정
name: webhani-project
version: 1

## 안정된 컨텍스트(첫 턴 후 캐싱)
system_context: |
  당신은 Webhani Inc.의 AI 코딩 보조도구입니다.
  우리 코드베이스는 Next.js 16, React 19, TypeScript, Tailwind CSS를 사용합니다.
  
  ### 명명 규칙
  - 컴포넌트: PascalCase, Area 프리픽스(AreaHero, AreaServices)
  - 훅: camelCase, use 프리픽스(useScrollReveal)
  - 파일: 비컴포넌트는 kebab-case

  ### Commit 스타일
  - 형식: "feat: description" 또는 "fix: description"
  - 공저자: "Co-Authored-By: Claude Code <noreply@anthropic.com>"

reference_files:
  - src/lib/constants.ts      # i18n 로케일 및 글로벌 상수
  - docs/architecture.md       # 시스템 설계 개요
  - .github/CODEOWNERS        # 리뷰 라우팅 소유권 규칙

## 출력 설정
output_style: "concise"  # 대화형 세션은 "verbose" 사용
log_level: "info"        # CI에서 디버그 출력 억제
```

이 구조는 다음을 보장합니다:
- 시스템 컨텍스트 블록이 10 KB 미만으로 유지되고 첫 API 호출 후 캐싱됩니다.
- 참조 파일(상수, 아키텍처 문서)이 고정되고 캐싱되며, 턴마다 재전송되지 않습니다.
- 출력 스타일이 환경에 맞춰 조정됩니다(CI는 Concise, 대화형 개발은 Verbose).

다음으로, 캐싱이 제대로 작동하는지 확인합니다. Agent 초기화에 작은 검사를 추가합니다:

```typescript
// 프롬프트 캐싱 활성 여부 확인
const client = new Anthropic({
  apiKey: process.env.ANTHROPIC_API_KEY,
});

const response = await client.messages.create({
  model: "claude-opus-5",
  max_tokens: 100,
  system: [
    {
      type: "text",
      text: "당신은 유용한 보조도구입니다.",
      cache_control: { type: "ephemeral" }  // 명시적 캐시 제어
    }
  ],
  messages: [
    { role: "user", content: "안녕하세요" }
  ]
});

// 캐시 성능 사용량 확인
console.log("캐시 생성 토큰:", response.usage.cache_creation_input_tokens);
console.log("캐시 읽기 토큰:", response.usage.cache_read_input_tokens);
console.log("일반 입력 토큰:", response.usage.input_tokens);
```

후속 호출에서 `cache_read_input_tokens`가 0이면 캐싱이 제대로 작동하지 않습니다. 이는 v2.1.237 버그를 발견했을 카나리입니다.

셋째, 작업마다 Concise 또는 Verbose가 적절한지 결정합니다. 결정 매트릭스:

| 작업 | 모드 | 이유 |
|------|------|------|
| 대화형 디버깅 | Verbose | 결정 이해를 위한 완전한 추론 필요 |
| 일상적 코드 생성 | Concise | 신호 대 노이즈; 산출물이 코드 |
| 보안 리뷰 | Verbose | 위협 분석 이해 필요 |
| CI 자동 리팩터 | Concise | 노이즈 감소; 사람이 나중에 diff 검토 |
| 아키텍처 변경 | Verbose | 결정 근거 이해 필요 |

## 핵심 요점

- **캐싱 버그는 복합화할 때까지 보이지 않습니다.** CI 또는 지속적 보조도구로 Agent 지원 워크플로우를 실행 중이라면, 프롬프트 캐싱이 작동하는지 감사합니다. 토큰 사용량 필드를 사용하여 캐시 히트가 발생하는지 확인합니다.
- **안정된 컨텍스트는 명시적이고 대화 이력에서 분리되어야 합니다.** CLAUDE.md 또는 시스템 프롬프트를 구조화하여 시스템 지시사항, 도구 정의, 참조 자료가 캐싱을 위해 명확히 표시되도록 합니다. 이렇게 하면 턴이 작아지고 비용 예측 가능성이 실현됩니다.
- **간결 출력이 보편적으로 좋은 것은 아닙니다. 이는 옵션입니다.** CI 로그, 감사 추적, 일상적 코드 생성에 Concise 모드를 사용합니다. 추론을 보려는 대화형 문제 해결, 아키텍처 결정, 디버깅에 Verbose 모드를 사용합니다.
- **캐시 정확성은 측정할 수 있는 비용 제어 레버입니다.** 캐싱이 작동하는지에 대한 가시성이 없으면, 생각하는 것보다 더 많이 지불하고 있습니다. Agent 설정에 캐시 히트율을 로깅하는 검사를 추가하고 드롭 시 알림을 설정합니다.
