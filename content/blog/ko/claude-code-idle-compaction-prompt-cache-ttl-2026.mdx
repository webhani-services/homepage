2026년 10월 14일자 Claude Code changelog에는 idle compaction이라는 변경 사항이 있습니다. 터미널에서 200K Token을 넘는 대화가 약 54분간 방치되면, 1시간짜리 Prompt Cache가 만료되기 전에 대화를 자동으로 compact한다는 내용입니다.

작은 변경처럼 보이지만, 장시간 Agent Session을 운영하는 팀이라면 이해해 둘 만한 사실을 보여줍니다. Session 비용은 일정하게 늘어나지 않고, 자리를 비운 뒤 보내는 첫 메시지에서 급증하는 경우가 많다는 점입니다.

## 문제의 구조

LLM Agent는 요청할 때마다 대화 전체를 다시 전송합니다. Prompt Caching은 요청 앞부분에서 동일한 구간을 재사용해, 해당 구간의 비용과 지연을 줄여 줍니다. Anthropic API에서 Cache 읽기는 일반 입력 Token보다 훨씬 낮은 요금으로 처리됩니다(정확한 단가는 공식 가격 페이지를 확인하시기 바랍니다).

다만 Cache에는 만료 시간이 있습니다. 1시간짜리 Cache는 1시간 동안 사용되지 않으면 사라집니다. 흐름은 이렇습니다.

1. 대화가 200K Token까지 커집니다. 거의 매 Turn마다 Cache가 적중하므로 저렴합니다.
2. 1시간 넘게 자리를 비웁니다. Cache가 만료됩니다.
3. 돌아와서 메시지를 한 번 보냅니다. 200K Token 전체가 Cache 없이 처리됩니다.

즉 휴식 뒤의 첫 메시지만 유독 비쌉니다. idle compaction은 만료 전에 대화를 요약해 크기를 줄여 두어, 이 한 번의 비용을 낮추려는 장치로 이해하고 있습니다.

## 대략적인 계산

설명을 위한 가정으로, 일반 입력 비용을 100만 Token당 X, Cache 읽기를 그 10분의 1이라고 하겠습니다.

- 200K Token, Cache 적중: 0.2 × 0.1X = 0.02X
- 200K Token, Cache 미스: 0.2 × X = 0.2X

메시지 한 번에 약 10배 차이가 납니다. 점심, 회의, 리뷰로 하루에도 여러 번 자리를 비운다면 누적 금액이 작지 않습니다. Cache 쓰기는 별도 요금이 있으므로 실제 추정에는 이 부분도 포함해야 합니다.

## 직접 만든 Agent에서의 대응

Agent를 직접 구현한다면 같은 구조의 문제가 발생합니다. Messages API에서는 `cache_control`로 Cache 경계를 지정합니다.

```python
import anthropic

client = anthropic.Anthropic()

response = client.messages.create(
    model="claude-sonnet-5-5",
    max_tokens=1024,
    system=[
        {
            "type": "text",
            "text": LONG_SYSTEM_PROMPT,
            "cache_control": {"type": "ephemeral"},
        }
    ],
    messages=history,
)

usage = response.usage
print(usage.cache_read_input_tokens, usage.cache_creation_input_tokens)
```

`usage`의 Cache 읽기·생성 Token 수를 기록해 두면, 어느 Turn에서 Cache가 적중하지 않았는지 나중에 확인할 수 있습니다. TTL 옵션과 요금은 바뀔 수 있으므로 구현 시점의 최신 문서를 참고하시기 바랍니다.

## 운영 측면의 대책

**Session을 의도적으로 나눕니다.** 작업이 자연스럽게 끊기는 지점에서 새 Session을 시작하는 것이 가장 단순한 방법입니다. 이전 맥락이 필요하다면 몇 줄의 메모만 넘기면 충분하며, 비대해진 기록을 그대로 이어갈 필요는 거의 없습니다.

**자리를 비우기 전에 compact합니다.** 오래 자리를 비우기 전에 수동으로 compact를 실행하면 돌아왔을 때의 첫 메시지가 가벼워집니다. idle compaction이 자동으로 해 주는 일을 미리 직접 하는 셈입니다.

**요약으로 정보가 손실된다는 점을 기억합니다.** 정확한 에러 메시지 문구나 Diff의 세부 내용은 요약 과정에서 사라질 수 있습니다. 작업 도중이라면 compact 후 관련 파일을 다시 읽게 하는 편이 안전합니다.

**측정합니다.** 팀 단위로 사용한다면 Session별 입력 Token과 Cache 적중률을 집계해 두세요. 비용이 한쪽으로 쏠리는 지점을 빠르게 찾을 수 있습니다. 데이터 수집 방법은 Claude Code의 OpenTelemetry Tracing을 다룬 글도 참고하시기 바랍니다.

## 정리

- Prompt Cache에는 TTL이 있으며, 1시간짜리 Cache는 1시간 동안 사용하지 않으면 만료됩니다.
- 만료 후 첫 요청은 대화 전체를 Cache 없이 처리하므로 비용이 커집니다.
- idle compaction은 이 비용 급증을 막기 위한 자동 안전장치입니다.
- 자체 Agent에서는 `usage`의 Cache 관련 필드를 기록하고, Session 분리와 사전 compact를 운영에 포함하면 안정적입니다.

LLM 비용은 Token 단가보다 사용 방식에 따라 크게 달라집니다. Agent 워크플로와 팀의 사용 규칙을 설계하고 계시다면 webhani가 도움을 드릴 수 있습니다.
