Anthropic이 이번 주 Claude Code Desktop에 iOS Simulator 지원을 Public Beta로 추가했습니다. Mac에서 iPhone App을 Build, 실행, Test, Debug하는 과정을 Agent Workflow에서 벗어나지 않고 처리할 수 있게 되었습니다. 기능 설명만 보면 소소해 보이지만, 실제로는 꽤 큰 공백을 메우는 변화입니다. 지난 1년간 성숙해진 Agentic Coding Tool 대부분은 Web과 Backend 중심의 검증 Loop——Code를 고치고, Server를 띄우고, Endpoint를 호출하고, Log를 읽는——를 전제로 만들어졌습니다. Mobile 개발은 Loop의 형태 자체가 다르기 때문에, 지금까지 Agent가 스스로 돌리기 어려운 영역이었습니다.

## Mobile Loop이 자동화하기 어려웠던 이유

Web 중심 Coding Agent는 비교적 저렴하게 자기 작업을 검증할 수 있습니다. Dev Server를 띄우고 HTTP Request를 보내서 Response를 확인하거나 Browser Screenshot을 찍으면 됩니다. Native Mobile 개발은 그렇게 간단히 압축되지 않습니다. SwiftUI Layout 수정을 검증하려면 App을 Build하고 Simulator를 Boot한 뒤 실행해서 Console 출력을 읽거나 실제 화면을 봐야 합니다. 지금까지는 Developer가 Terminal에서 Xcode로 직접 전환해야 했던 작업입니다.

Claude Code Desktop에 Simulator 지원이 내장되면서, 이 Loop을 Agent가 스스로 돌릴 수 있게 되었습니다.

```bash
# Agent가 내부적으로 자동화하는 작업의 실체
xcrun simctl boot "iPhone 17"
xcodebuild -scheme MyApp -destination "platform=iOS Simulator,name=iPhone 17" build
xcrun simctl launch booted com.example.myapp
xcrun simctl io booted screenshot after-fix.png
```

"작은 화면에서 Submit Button이 Keyboard 뒤에 가려진다"는 식의 Bug Report가 있으면, Agent가 수정하고 Rebuild한 뒤 Simulator를 띄워 Screenshot을 찍고 기대한 Layout과 비교하는 과정을 스스로 완결할 수 있습니다. Web 개발에서 이미 표준이 된 "완료라고 말하기 전에 검증한다"는 원칙이 Native App에도 확장된 셈입니다.

## 실제 Loop이 동작하는 예시

Layout에 문제가 있는 SwiftUI View를 예로 보겠습니다.

```swift
struct CheckoutView: View {
    var body: some View {
        VStack {
            Spacer()
            TextField("Card number", text: $cardNumber)
            Button("Submit") { submit() }
        }
        .padding()
        // 빠진 부분: .ignoresSafeArea(.keyboard, edges: .bottom)
        // 또는 ScrollView로 감싸기 — Spacer가 Content를
        // Keyboard 아래로 밀어넣고 있음
    }
}
```

예전에는 이런 Bug를 잡으려면 Developer가 실제로 App을 실행해서 Keyboard를 띄우고 겹치는 부분을 눈으로 확인해야 했습니다. 이제는 Bug 설명만 전달하면 Agent가 Layout을 고치고 Rebuild해서 Keyboard가 표시된 상태의 Simulator를 Screenshot까지 찍어 확인합니다.

## 아직 Beta인 부분, 감독이 필요한 부분

Team에 도입하기 전에 몇 가지는 신중하게 짚고 넘어가야 합니다.

- **Local에 완전한 Xcode 환경이 필요합니다.** 가벼운 통합이 아니라, Developer가 평소 쓰는 것과 동일한 Toolchain을 Agent가 그대로 조작하는 것이므로 Build 시간이나 Simulator 부팅 시간은 그대로입니다.
- **Simulator는 실제 기기가 아닙니다.** Camera 접근, Push 알림 전달, 성능 특성이 실기기와 다릅니다. Simulator 검증은 빠른 1차 확인일 뿐, Release 전 실기기 Test를 대체하지는 못합니다.
- **파괴적인 Simulator 조작에는 확인 절차를 둬야 합니다.** Simulator 상태 초기화, Derived Data 삭제, App Container 제거 같은 작업은 다른 Agentic Coding Workflow에서 `rm -rf`를 Gate하는 것과 같은 이유로, Agent가 무인으로 실행하기보다 명시적 승인을 거치도록 하는 편이 안전합니다.

## webhani의 권장 사항

- **먼저 검증 Loop에만 Scope를 한정하세요.** Simulator에서 눈으로 확인 가능한 Bug 수정이나 UI 조정부터 시작하고, Code Signing·Provisioning·Release Build는 당분간 Agent에게 맡기지 않는 편이 좋습니다.
- **Simulator Screenshot은 '증거'이지 '정확성의 증명'이 아니라는 점을 기억하세요.** Layout이 의도대로 그려졌다는 확인은 되지만, 실기기 Test나 Accessibility 점검을 대체하지는 못합니다.
- **기존 CI를 대체하지 말고 병행하세요.** Simulator Loop은 개발 중 빠른 Iteration에는 유용하지만, Release Gate 판단은 실기기·Cloud Simulator Test Matrix에 맡겨야 합니다.

## 정리

이번 기능 추가 자체보다 그것이 보여주는 방향성이 더 중요합니다. Agentic Web 개발에서 자리 잡은 "완료라고 말하기 전에 자기 작업을 검증한다"는 Loop이, 지금까지 수동 전환이 필요했던 영역으로 조금씩 확장되고 있습니다. Native iOS App을 개발하는 Team이라면 우선 범위를 좁힌 UI Bug 수정부터 시도해보고, Release Build에 가까운 작업은 신중하게 지켜본 뒤 맡기는 것을 권합니다.
