Claude Code 2.1.301(2026년 10월 16일경 확인)에서는 Vim 괄호 이동, VS Code의 수식 렌더링 같은 변경과 함께 OpenTelemetry Tracing이 확장되었습니다. 팀에서 AI Coding Agent를 쓰기 시작하면 누가 얼마나 쓰는지, 시간과 비용이 어디에서 나가는지 금세 보이지 않게 됩니다. Telemetry는 이를 다시 파악하기 위한 기반입니다.

이 글에서는 Claude Code의 Telemetry를 자사 Observability 환경으로 보내는 방법과 최소 구성을 소개합니다. 항목 이름과 Span 구조는 버전에 따라 달라지므로 세부 사항은 공식 문서에서 확인하시기 바랍니다.

## Agent에 Observability가 필요한 이유

일반적인 Web Service와 달리 Agent는 실행할 때마다 동작이 달라집니다. 같은 요청이라도 읽는 파일, 호출하는 Tool, 사용하는 Token 양이 다릅니다. 데이터가 없으면 다음 질문에 감으로 답하게 됩니다.

- 작업 하나에 평균 몇 Token을 쓰는가
- Tool 호출 실패는 얼마나 되고, 승인 대기로 멈춰 있는 시간은 얼마나 되는가
- 특정 프로젝트나 팀에 비용이 몰려 있지는 않은가

Metrics는 전체 추세를, Trace는 한 번의 실행 내역을 보는 데 적합합니다. 둘이 함께 있으면 "지난주부터 Token 사용량이 늘었다"는 추세 파악과 "이 실행은 왜 느렸는가"라는 원인 조사를 같은 환경에서 할 수 있습니다.

## 최소 구성

Telemetry는 환경 변수로 활성화합니다. 아래 예시는 공개 문서의 형식을 따른 것이지만, Tracing 관련 설정은 버전에 따라 다를 수 있으므로 사용 중인 버전의 문서를 확인하시기 바랍니다.

```bash
export CLAUDE_CODE_ENABLE_TELEMETRY=1
export OTEL_METRICS_EXPORTER=otlp
export OTEL_EXPORTER_OTLP_PROTOCOL=grpc
export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317
```

수신 측 OpenTelemetry Collector는 받아서 Label을 붙이고 전달하기만 하는 구성으로 시작하는 것이 무난합니다.

```yaml
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317

processors:
  batch: {}
  attributes/team:
    actions:
      - key: team
        value: web-platform
        action: upsert

exporters:
  otlphttp:
    endpoint: https://observability.example.com

service:
  pipelines:
    metrics:
      receivers: [otlp]
      processors: [attributes/team, batch]
      exporters: [otlphttp]
    traces:
      receivers: [otlp]
      processors: [attributes/team, batch]
      exporters: [otlphttp]
```

`attributes/team`으로 Team 이름을 붙이는 것은 이후 집계 기준으로 쓰기 위해서입니다. 개인 단위의 상세 추적이 필요한지는 아래 내용을 고려해 결정하시기 바랍니다.

## 설계 시 유의할 점

**목적과 Privacy를 분명히 합니다.** Telemetry에 Prompt 내용이나 개인을 식별할 수 있는 정보가 포함되면 직원 감시로 받아들여질 수 있습니다. 어떤 목적으로 어떤 항목을 수집하고 누가 볼 수 있는지 사전에 정하고 팀에 공유하세요. Token 수나 Tool 호출 횟수 같은 집계 값부터 시작하는 것이 부담이 적습니다.

**Cardinality를 관리합니다.** Metrics 속성에 Session ID나 파일 경로를 붙이면 Cardinality가 폭발해 Backend 비용이 급증합니다. Metrics에는 Team, Model, Tool 이름 정도만 두고, 세부 정보는 Trace에 맡기는 것이 기본입니다.

**Trace는 Sampling합니다.** 모든 Trace를 저장할 필요는 없습니다. 일부만 Sampling하되 실패하거나 비용이 큰 실행은 남기도록 Collector에서 설정하면 비용과 조사 가능성의 균형을 맞출 수 있습니다.

**볼 지표를 먼저 좁힙니다.** 처음에는 다음 항목이 유용합니다.

- Session당 입력 Token과 Cache 사용 현황(비용 추세)
- Tool 호출 실패율
- 승인 대기 등 사람의 조작 때문에 멈춰 있는 시간

Cache 관련 내용은 idle compaction과 Prompt Cache TTL을 다룬 글과도 연결됩니다.

## 정리

- Agent는 실행마다 동작이 달라지므로 Metrics와 Trace를 통한 관측이 효과적입니다.
- Claude Code의 Telemetry는 환경 변수로 활성화하고, OpenTelemetry Collector를 거쳐 기존 환경에 모을 수 있습니다.
- Cardinality, Sampling, Privacy 세 가지는 처음에 설계해 두어야 나중에 곤란하지 않습니다.
- 항목 이름은 계속 바뀌므로 Dashboard를 만들기 전에 사용 버전의 문서로 확인하시기 바랍니다.

AI Agent 도입 후 효과와 비용을 설명할 수 있는 상태를 만드는 것은 지속 사용 여부의 판단과 직결됩니다. Observability 환경 설계와 AI 사용 Governance 정비는 webhani에서도 지원하고 있습니다.
