팀에서 Claude Code를 사용한다면, Workflow의 토대가 되는 도구는 거의 매일 바뀌고 있습니다. Release 추적 사이트 havoptic은 10월 9일 기준 최신 Version을 v2.1.296으로 표시하고, 직전 30일 동안 25회 Release가 있었다고 집계합니다. 이 수치는 Anthropic 공식 Changelog가 아니라 서드파티 집계이므로 대략적인 값으로 받아들이십시오. 다만 Release 빈도가 높다는 사실 자체는 분명하며, 많은 팀이 아직 답하지 못한 질문이 생깁니다. 새 Version으로 언제, 누구의 판단으로 전원이 옮겨 갈 것인가 하는 질문입니다.

## 10월 초에 무엇이 바뀌었나

10월 Build를 정리한 Tracker에 따르면 변경은 Bug 수정에 그치지 않습니다. 보고된 항목은 다음과 같습니다(의존하기 전에 공식 Changelog에서 확인하십시오).

- 기본 Model 변경. v2.1.293에서 Haiku 계열 Model이 기본값이 되었다고 보고되었습니다.
- Marketplace에서 Plugin을 직접 설치할 수 있게 됨(v2.1.292).
- Subagent가 들이는 노력 수준을 제어할 수 있게 되었고, 이어서 사용할 Model도 선택할 수 있게 됨.
- 실패한 Hook의 처리 방식 변경. 실패 시 차단하는 옵션이 추가됨(v2.1.295).
- Plugin이 도구 동작의 더 깊은 부분을 수정할 수 있게 됨(v2.1.287).

모두 팀이 의존하고 있을 수 있는 영역을 건드립니다. 비용, 출력 품질, 보안 수준, 그리고 직접 만든 Guardrail입니다. 기본 Model이 바뀌면 청구액도, 눈에 띄는 실수의 종류도 달라집니다. 실패 시 차단하도록 바뀐 Hook은 이전에는 그냥 통과하던 Pipeline을 멈출 수 있습니다.

## 현장에서 자주 보는 실패 패턴

도입을 지원하다 보면 같은 네 가지 문제를 반복해서 만납니다.

1. **눈치채지 못하는 동작 Drift.** 누군가 업데이트해서 기본 Model이 바뀌고, 그 사람의 결과가 팀의 다른 구성원과 비교할 수 없게 됩니다.
2. **특정 Version 동작에 의존한 Guardrail.** 어떤 Exit Code 동작을 전제로 작성한 Hook이 업데이트 후 조용히 틀린 것이 됩니다.
3. **검토되지 않는 Plugin.** Marketplace 설치는 코드 실행에 대한 결정입니다. npm Dependency와 같은 수준의 검토가 필요합니다.
4. **예상치 못한 비용.** Model과 Subagent 기본값이 작업 하나에 소모되는 Token 양을 좌우합니다.

## 가벼운 운영 방침

거창한 위원회는 필요 없습니다. 아래 네 가지로 위험의 대부분을 다룰 수 있습니다.

**1. Project 설정에서 Model을 명시적으로 고정합니다.** 기본값을 상속하지 마십시오. Repository에 Commit한 공유 `.claude/settings.json`이 있으면 선택을 Review할 수 있습니다.

```json
{
  "model": "claude-sonnet-5-5",
  "permissions": {
    "deny": ["Bash(rm -rf:*)", "Read(./.env)"]
  }
}
```

Key 이름과 Model ID는 최신 설정 문서에서 확인하십시오. 과거에 바뀐 적이 있습니다. 핵심은 결정하는 주체가 각자의 노트북이 아니라 Repository라는 점입니다.

**2. 업데이트 주기를 정합니다.** 한 가지 방법은 담당자(순번제도 가능)가 주 1회 업데이트하고, Release Note를 읽고, Repository의 Hook에 대해 짧은 Smoke Test를 돌린 뒤 새 Baseline을 공지하는 것입니다. 나머지 구성원은 다음 공지까지 그 Baseline에 머뭅니다. 규제가 엄격한 환경이라면 자동 업데이트에 맡기지 말고 Bootstrap Script에서 설치 Version을 고정하십시오.

**3. 업데이트할 때마다 Guardrail Smoke Test를 수행합니다.** 동작하는 모습을 본 적 없는 Hook은 신뢰할 수 없습니다. 보호용 Hook마다 알려진 위험 입력을 주고 호출이 차단되는지 검증하는 작은 Script를 준비하십시오.

```bash
#!/usr/bin/env bash
# scripts/check-claude-guardrails.sh
set -euo pipefail

echo '{"tool_name":"Bash","tool_input":{"command":"rm -rf /tmp/x"}}' \
  | .claude/hooks/block-destructive.sh && {
    echo "FAIL: destructive command was not blocked"; exit 1; }
echo "OK: destructive command blocked"
```

Local뿐 아니라 CI에서도 실행하십시오. Hook을 "실패 시 차단"하도록 설계하는 방법은 이전 글에서 다루었습니다.

**4. Plugin은 Dependency로 취급합니다.** 사용할 Marketplace를 허용 목록으로 관리하고, 설치 전에 Plugin의 Hook과 Command를 읽고, 승인된 목록을 Repository에 기록합니다. Hook을 등록하는 Plugin은 도구를 호출할 때마다 사용자 권한으로 실행됩니다.

## 비용과 품질은 추측하지 말고 측정합니다

기본 Model이나 Subagent 설정이 바뀌었을 때는 변경 전후를 간단히 비교하면 충분합니다. 대표 작업 세 가지(Bug 수정, Refactoring, Test 작성)를 이전 설정과 새 설정으로 실행하고, 소요 시간, Token 사용량, Test 통과 여부를 비교합니다. 작고 빠른 Model은 탐색과 검색을 맡는 Subagent에는 적합한 경우가 많지만, 설계나 보안과 관련된 수정에는 맞지 않는 경우가 많습니다. 이 조합은 상속하지 말고 의도적으로 정할 가치가 있습니다.

## webhani의 권장 사항

- Model과 권한 규칙을 고정한 Project 수준 설정 파일을 Commit합니다.
- 주간 "Baseline 담당자"를 정하고 Baseline Version을 팀 문서에 게시합니다.
- Guardrail Smoke Test를 CI에 추가합니다.
- Plugin은 서드파티 코드로 Review하고 승인 목록을 Version 관리합니다.
- Release Note에 "default"라는 표현이 있으면 비용과 동작에 영향이 있다고 가정하고 검증합니다.

Release 주기가 빠른 것은 여러 면에서 좋은 일입니다. Bug가 빠르게 수정됩니다. 그 대가로 팀의 개발 도구가 "움직이는 Dependency"가 됩니다. Application의 Dependency에 적용하는 것과 같은 Version 고정과 Review를 도구에도 적용하면, 적은 노력으로 예상 밖의 일 대부분을 막을 수 있습니다.
