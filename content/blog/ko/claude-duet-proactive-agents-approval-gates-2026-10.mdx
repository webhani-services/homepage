10월 21일 Anthropic은 단독 Agent 앱인 Claude Duet의 Research Preview를 시작했습니다. 미국 대기자 명단에 등록한 Pro와 Max 구독자가 대상입니다. 보도에 따르면 Duet는 연결된 계정을 몇 시간마다 확인하고, 프롬프트를 기다리지 않고 작업을 진행하며, 전송·결제·서명·삭제 전에는 반드시 승인을 요청합니다. 또한 비밀번호나 로그인 Token을 직접 보지 않는다고 설명합니다.

저희는 아직 Duet를 직접 사용해 보지 못했고 제품 세부 사항은 2차 보도에 근거하므로, 사양은 잠정적인 것으로 보시기 바랍니다. 주목할 부분은 설계의 형태입니다. 먼저 움직이는 Agent는 안전성 문제의 성격을 바꿉니다. 매 Turn을 사람이 지켜보지 않으므로, 핵심 통제 지점이 "출력을 검토한다"에서 "부수 효과(Side Effect)를 관문에서 막는다"로 이동합니다. 고객사를 위해 Agent를 만든다면 같은 구조가 필요합니다. 아래에 구현 예시를 정리합니다.

## 선제형 Agent는 무엇이 다른가

Chat 형태의 Assistant는 수동적입니다. 사용자가 메시지를 보내고, 답을 읽고, 다음 행동을 결정합니다. 모든 행동이 구조적으로 사람을 거칩니다.

선제형 Agent는 이것이 반대가 됩니다. 스케줄이나 Event로 깨어나 받은 편지함과 캘린더를 읽고, 스스로 "이 일을 해야 한다"고 판단합니다. 여기서 세 가지 문제가 생깁니다.

- **신뢰할 수 없는 입력이 무인 상태로 들어옵니다**: 새벽 3시에 Agent가 읽는 메일에 Agent를 겨냥한 지시가 섞여 있을 수 있습니다. 아무도 알아채지 못합니다.
- **실수가 아무도 보지 않는 사이 누적됩니다**: 오전 9시의 잘못된 동작이 정오의 잘못된 계획으로 이어집니다.
- **승인 피로가 가장 큰 위험이 됩니다**: 모든 것을 물어보는 Agent라면 사람은 내용을 읽지 않고 "승인"만 누르게 됩니다.

보도된 Duet의 방식은 대화가 아니라 Action을 분류합니다. 읽기는 자유롭고, 영향이 큰 소수의 동작만 사람의 승인이 필요합니다.

## 위험 등급별 Action Policy

가장 단순하고 유효한 구현은 Agent가 호출할 수 있는 모든 Tool을 등급에 매핑하는 Policy 표를 만들고, 모델 바깥에서 강제하는 것입니다.

```ts
type Tier = "auto" | "approve" | "deny";

interface ToolPolicy {
  tier: Tier;
  // 호출 시점에 평가하는 선택적 Guard (예: 지출 한도)
  guard?: (args: Record<string, unknown>) => boolean;
}

const policy: Record<string, ToolPolicy> = {
  "calendar.read":   { tier: "auto" },
  "mail.search":     { tier: "auto" },
  "mail.draft":      { tier: "auto" },
  "mail.send":       { tier: "approve" },
  "payments.charge": { tier: "approve", guard: (a) => Number(a.amount) <= 50_000 },
  "docs.sign":       { tier: "approve" },
  "files.delete":    { tier: "approve" },
  "shell.exec":      { tier: "deny" },
};
```

중요한 점은 이 Policy가 System Prompt가 아니라 Runtime에 있다는 것입니다. Prompt는 설득당할 수 있지만 조회 표는 설득당하지 않습니다. 알 수 없는 Tool은 기본적으로 `deny`입니다.

## Approval Queue

호출이 `approve` 등급에 해당하면 Agent는 멈춰 서지 않고 요청을 보류한 뒤 다른 작업으로 넘어가야 합니다.

```ts
interface PendingAction {
  id: string;            // 멱등성 키 (재시도해도 동일한 값)
  tool: string;
  args: Record<string, unknown>;
  reason: string;        // Agent가 밝힌 사유
  sourceRefs: string[];  // 계기가 된 메시지 ID, 문서 URL
  createdAt: string;
  expiresAt: string;
}

async function dispatch(call: ToolCall, ctx: AgentContext) {
  const rule = policy[call.tool];
  if (!rule || rule.tier === "deny") throw new PolicyError(call.tool);
  if (rule.guard && !rule.guard(call.args)) throw new PolicyError(call.tool);

  if (rule.tier === "auto") return execute(call);

  const pending: PendingAction = {
    id: ctx.idempotencyKey(call),
    tool: call.tool,
    args: call.args,
    reason: call.reason,
    sourceRefs: ctx.currentSources(),
    createdAt: new Date().toISOString(),
    expiresAt: addHours(new Date(), 24).toISOString(),
  };
  await approvalQueue.put(pending);
  return { status: "awaiting_approval", id: pending.id };
}
```

세부 사항 세 가지가 중요합니다.

**멱등성 키**: Timeout 후 재시도하는 Agent가 같은 메일을 두 번 보내면 안 됩니다. 키는 시도가 아니라 의도에서 도출합니다.

**출처 참조**: 승인자에게는 Agent가 "왜" 행동하려는지, 어떤 메시지가 계기였는지를 보여줘야 합니다. 주입된 지시에 대한 가장 좋은 방어책입니다. "모르는 발신자의 메일을 계기로 새 주소로 청구서를 보낸다"는 요청이라면 모델이 놓친 것을 사람이 잡을 수 있습니다.

**만료**: 오래된 승인은 위험합니다. 밤사이 상황이 바뀌었다면 어제 상태를 기준으로 한 승인이 오늘 실행되어서는 안 됩니다.

## 자격 증명은 공유하지 말고 범위를 좁힙니다

Anthropic은 Duet가 비밀번호나 로그인 Token을 직접 보지 않는다고 밝혔습니다. 같은 성질을 목표로 할 수 있습니다. 모델에는 비밀 정보를 보여주지 않고, Tool 실행 쪽이 범위가 좁은 단기 자격 증명을 보유하는 구성입니다. 메일 Agent라면 읽기와 초안 작성이 가능한 Token, 그리고 전송 Scope는 승인 경로에서만 사용하는 Token으로 나눕니다. "초안"과 "전송"을 자격 증명 단계에서 분리하면, Prompt가 탈취되어도 관문을 우회할 수 없습니다.

## 승인 피로 줄이기

모든 동작에 클릭이 필요하면 관문은 장식이 됩니다. 도움이 되는 방법은 다음과 같습니다.

- **의도 단위로 묶기**: 답장 3건을 따로 묻지 말고 "전송 예정 답장 3건"을 Diff와 함께 보여줍니다.
- **변경점 보여주기**: 캘린더 변경이라면 기존 시각과 새 시각을 나란히 표시합니다.
- **검토 후 상시 Rule 허용**: "이 사내 메일링 리스트로 가는 답장은 항상 승인"은 사람이 선택한 뒤라면 합리적입니다. 철회할 수 있고 기록이 남아야 합니다.
- **거부율 측정**: 승인자의 거부율이 1% 미만이라면 Agent가 매우 우수하거나 아무도 읽지 않는다는 뜻입니다. 표본을 추출해 감사하십시오.

## 사후 분석을 위한 Log

제안된 Action, 승인, 거부, 실행을 모두 계기가 된 출처와 함께 Append-only Log로 남깁니다. 선제형 시스템에서 문제가 생기면 질문은 항상 "무엇을 보았고, 왜 그것을 지시라고 판단했는가"입니다. Log가 없으면 답할 수 없습니다.

## webhani의 권장 사항

일정에 따라 동작하는 Agent를 요청받으면 다음 순서로 진행합니다.

1. 처음 2주는 읽기 전용으로 운영하며 "실행했을 동작"을 검토합니다.
2. 등급 표를 코드에 두고 알 수 없는 Tool은 거부를 기본값으로 합니다.
3. 승인 요청에 출처 참조를 담고 만료 시간을 둡니다.
4. 비밀 정보를 모델 Context에 넣지 않고 자격 증명은 Action 단위로 제한합니다.
5. 승인율과 거부율을 Health Metric으로 추적합니다.

Duet는 Research Preview이며 Anthropic 스스로도 한계가 있다고 설명합니다. 그럼에도 "읽기는 자유롭게, 부수 효과는 관문을 통과시킨다"는 패턴은 Vendor와 무관하게 유효합니다. 첫 무인 실행 전에 적용하십시오. 첫 사고가 난 뒤에는 늦습니다.
