2026년 11월 6일 Anthropic 릴리스 노트에서 Claude Enterprise의 Project Tags가 Beta로 발표되었습니다(대상 조직 한정). 관리자는 회사에서 이미 쓰고 있는 코드 — 부서 Charge Code, WBS, 고객 사건 번호 등 — 를 Claude Project에 붙이고, Tag별로 사용 금액을 확인할 수 있습니다. 하루 전에는 Security Center, inference hooks, 중앙 관리 기능 등 Enterprise용 보안·관리 기능도 공개되었고, 이 중 일부도 Beta입니다.

AI를 활용한 작업을 고객에게 청구하거나 프로젝트별로 원가를 관리하는 조직에게 이 기능은 오래된 빈틈을 메워 줍니다. 지금까지 "A사 프로젝트에서 Claude 사용료가 얼마나 들었나"라는 질문에는 Spreadsheet와 추정으로 답할 수밖에 없었습니다. Project Tags가 있으면 최소한 공식 수치를 출발점으로 삼을 수 있습니다.

기능 자체는 복잡하지 않습니다. 쓸모가 있느냐는 도입 전에 준비하는 Tag 설계에 달려 있습니다.

## 할 수 있는 것과 없는 것

Anthropic의 consumption guide와 릴리스 노트에서 확인되는 내용은 다음과 같습니다.

- Tag는 **Project**에 붙입니다. 사용 금액은 Project에 귀속되고 Tag 단위로 집계됩니다.
- 금액은 **Organization settings > Usage > Spend by project**에서 확인합니다.
- Admin API로 Tag 목록 조회, Tag 허용 값 추가, Project Tag 설정이 가능합니다(Beta).
- 모든 Claude 제품이 대상은 아니며, 표시 금액이 **청구서와 정확히 일치하지 않을 수 있습니다**.
- Project 밖에서 발생한 사용량은 별도로 묶입니다. 제3자 분석에 따르면 Project가 설정되지 않은 Claude Code Session도 여기에 포함됩니다.
- **Tag 이름과 값은 조직 내 모든 구성원에게 보입니다.**

마지막 항목은 보기보다 중요합니다. 고객 사건 번호나 프로젝트 코드명 자체가 기밀이라면, 그대로 Tag에 넣는 순간 조직 전체에 공개됩니다.

## Tag가 아니라 필요한 Report에서 출발하기

Tag를 정의하기 전에 실제로 필요한 Report를 먼저 적어 보십시오. 저희 컨설팅 경험상 질문은 거의 세 가지로 나뉩니다.

1. **청구** — 고객 프로젝트별로 AI 사용료를 얼마나 전가하거나 원가로 잡아야 하는가
2. **예산 관리** — 어떤 사내 팀의 사용량이 늘고 있고, 계획 범위 안인가
3. **투자 파악** — R&D·사내 Tool 지출과 Delivery 지출의 비중은 어떤가

질문 하나가 Tag Key 하나에 대응합니다. "혹시 몰라서" 추가하는 Tag는 만들지 마십시오. 축이 하나 늘 때마다 입력의 불일치도 하나 늘어납니다.

세 질문을 모두 다루는 최소 구성 예시입니다.

```yaml
# claude-project-tags.yaml — 기준 정의. 변경은 PR로 리뷰
tags:
  cost-center:
    description: "사용 금액을 부담하는 회계상 Cost Center"
    values: ["CC-1100-eng", "CC-1200-consulting", "CC-1300-education"]
  engagement:
    description: "청구 시스템의 불투명한 프로젝트 ID (고객명 사용 금지)"
    pattern: "^ENG-[0-9]{5}$"
  purpose:
    description: "지출 목적"
    values: ["delivery", "presales", "internal-tooling", "research"]
```

의도적으로 정한 점은 두 가지입니다.

- `engagement`에는 고객명이 아니라 **불투명한 ID**를 씁니다. ID와 고객의 매핑은 이미 접근 제어가 되어 있는 청구 시스템 쪽에 둡니다. 이것으로 "조직 전체에 보인다"는 문제를 피할 수 있습니다.
- 정의는 Repository에서 관리하고, Tag 변경도 다른 Configuration처럼 리뷰를 거칩니다.

## 적용 전에 Validation하기

관리 화면에서 설정하든 Admin API로 설정하든, 간단한 Validation 단계 하나로 실수 대부분을 막을 수 있습니다. 위 정의를 읽어 Project에 붙일 Tag를 검사하는 TypeScript 예시입니다.

```ts
// validate-tags.ts
import { readFileSync } from "node:fs";
import { parse } from "yaml";

type TagRule = { values?: string[]; pattern?: string };
type Scheme = { tags: Record<string, TagRule> };

const scheme: Scheme = parse(readFileSync("claude-project-tags.yaml", "utf8"));

export function validateProjectTags(tags: Record<string, string>): string[] {
  const errors: string[] = [];

  for (const key of Object.keys(scheme.tags)) {
    if (!(key in tags)) errors.push(`missing required tag: ${key}`);
  }

  for (const [key, value] of Object.entries(tags)) {
    const rule = scheme.tags[key];
    if (!rule) {
      errors.push(`unknown tag key: ${key}`);
      continue;
    }
    if (rule.values && !rule.values.includes(value)) {
      errors.push(`${key}="${value}" is not an allowed value`);
    }
    if (rule.pattern && !new RegExp(rule.pattern).test(value)) {
      errors.push(`${key}="${value}" does not match ${rule.pattern}`);
    }
  }
  return errors;
}

// 예시
console.log(
  validateProjectTags({
    "cost-center": "CC-1200-consulting",
    engagement: "Acme Corp", // 검출됨: ID 대신 고객명
    purpose: "delivery",
  }),
);
```

Admin API로 Tag 지정을 자동화한다면, API를 호출하는 같은 Job 안에서 이 검사를 먼저 실행합니다. Project Tags 관련 Endpoint는 Beta라 바뀔 수 있으므로, 정확한 이름과 Scope는 최신 Admin API Reference에서 확인하십시오.

## "Project 밖" 사용량 줄이기

Tag 없는 사용 금액이 가장 많이 생길 곳은 Claude Code로 예상됩니다. 개발자는 Project에 연결하지 않고 Session을 시작하는 경우가 많고, 그 금액은 미할당 영역으로 들어갑니다.

실무적인 대응은 세 가지입니다.

1. **가시화** — 미할당 비율을 매월 Report합니다. 전체의 15~20% 정도를 넘는다면 청구에 쓸 수 있는 정확도가 아닙니다.
2. **기본값 바로잡기** — 팀의 Claude Code 온보딩과 Repository Template에 Project 설정을 포함해, 새 작업이 처음부터 올바른 Project에 연결되도록 합니다.
3. **과도하게 만들지 않기** — 사내 Tool 용도라면 `purpose: internal-tooling`을 붙인 포괄 Project 하나면 충분합니다. 정확도가 필요한 것은 청구 대상 작업이지, 모든 작업이 아닙니다.

## 금액은 "청구액"이 아니라 "배분 근거"로 다루기

Anthropic은 Tag별 금액이 청구서와 다를 수 있다고 명시합니다. Tag 데이터는 청구액을 대체하는 것이 아니라, 청구 총액을 **배분**하는 비율로 쓰는 것이 안전합니다.

```text
배분액(tag) = 청구 총액 × (tag 사용 금액 / 미할당 포함 전체 사용 금액)
```

이렇게 하면 회계 수치는 실제 지불액과 맞추면서도 프로젝트별 비용을 설명할 수 있습니다.

## 새 보안 기능과의 관계

11월 5일 업데이트(Security Center, inference hooks, 중앙 관리)와 Project Tags는 같은 방향을 가리킵니다. Claude Enterprise가 생산성뿐 아니라 감사(Audit) 질문에도 답해야 하는 조직에 맞춰 다듬어지고 있다는 것입니다. Security Center는 아직 공개 정보가 제한적이라 지금 그것을 전제로 설계하는 것은 권하지 않습니다. 반면 Project Tags는 지금 바로 쓸 수 있고 효과도 분명합니다.

## webhani의 권장 사항

- Tag Key는 필요한 Report에서 역산하고 세 개 이하로 유지
- Tag는 조직 전체에 보이므로 고객명 대신 불투명한 ID 사용
- 정의는 Version 관리하고 적용 전에 Validation
- 특히 Claude Code에서 나오는 미할당 비율 추적
- Tag 데이터는 단독 청구 근거가 아니라 청구 총액 배분에 사용

이 작은 준비는 고객이나 재무팀이 "이 프로젝트의 AI 부분에 실제로 얼마가 들었나"라고 처음 묻는 순간 충분히 보답합니다.
