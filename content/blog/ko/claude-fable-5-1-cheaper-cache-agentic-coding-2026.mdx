## Fable 5.1과 Mythos 5.1이 나왔습니다

2026년 9월 1일, Anthropic이 Claude Fable 5.1과 Claude Mythos 5.1을 발표했습니다. 두 Model은 동일한 기반 위에서 만들어졌으며, Fable 5.1은 Production 환경을 위한 표준 안전장치를 갖춘 일반 공개 버전이고, Mythos 5.1은 Cybersecurity·Life Science 분야의 승인된 조직에 한해 제약을 완화한 형태로 제공됩니다 ([Anthropic 공식 발표](https://www.anthropic.com/claude-fable-and-mythos-5-1)).

이번 발표에서 실무적으로 눈여겨봐야 할 부분은 새로운 기능 자체보다 "Cache Read 요금 75% 인하"와 "Agentic Coding Benchmark 향상"입니다. 이 글에서는 이 두 가지를 중심으로 webhani의 관점에서 실무 영향을 정리합니다.

## Cache Read란 무엇이고, 왜 75% 인하가 중요한가

Claude를 비롯한 많은 LLM API에는 "Prompt Caching"이라는 구조가 있습니다. 긴 System Prompt나 반복적으로 참조하는 Context(Codebase 일부, 문서, 이전 대화 이력 등)를 Server에 캐싱해 두고, 이후 요청에서 캐시 적중분을 더 저렴한 단가로 읽어오는 방식입니다.

이번 발표에 따르면 Cache Read 단가는 100만 Token당 $1에서 $0.25로 75% 인하되었습니다. 이를 통해 일반적인 작업에서는 약 25%, 복잡한 Agentic Workflow에서는 최대 45%의 비용 절감이 가능하다고 합니다 ([VentureBeat](https://venturebeat.com/technology/anthropics-claude-fable-5-1-and-mythos-5-1-arrive-with-a-75-cost-reduction-for-fable-cache-reads), [gHacks](https://www.ghacks.net/2026/09/03/anthropic-releases-claude-fable-5-1-and-cuts-cached-token-pricing-by-75/)).

Claude Code 같은 Agentic Coding Tool은 하나의 작업 안에서 같은 Codebase와 System Prompt를 수십 번씩 반복 참조합니다. Tool 실행 결과를 Context에 계속 쌓아가며 수십 회의 API 호출을 반복하는 구조상 Cache Hit율이 높아지기 쉽고, 따라서 Cache Read 단가 인하의 혜택을 가장 크게 받는 Use Case입니다.

## Prompt Caching의 기본 패턴

Anthropic이 공식 문서화한 Prompt Caching 사용법을 TypeScript로 보여드립니다. 변하지 않는 긴 Context(Coding 규칙이나 Codebase 설명 등)에 `cache_control`을 지정하면 이후 요청에서 재사용됩니다.

```typescript
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

const CODEBASE_CONTEXT = `
# 프로젝트 Coding 규칙
- Component 이름은 Area Prefix를 사용합니다
- 번역 Key는 useTranslations Hook으로 접근합니다
...(긴 참조 문서)
`;

async function askAboutCode(question: string) {
  const response = await client.messages.create({
    model: "claude-fable-5-1",
    max_tokens: 1024,
    system: [
      {
        type: "text",
        text: CODEBASE_CONTEXT,
        cache_control: { type: "ephemeral" },
      },
    ],
    messages: [{ role: "user", content: question }],
  });
  return response;
}
```

`cache_control`을 지정한 부분은 내용이 동일하면 이후 요청에서 Cache로부터 읽힙니다. Agentic Workflow에서는 "고정된 부분"과 "매번 바뀌는 부분"을 명확히 구분하는 것이 비용 최적화의 첫걸음입니다.

## 간단한 비용 계산

하루 1,000회 API 호출이 있고, 그중 평균 8,000 Token 분량이 Cache에 적중하는 Workflow를 가정해 보겠습니다.

- 인하 전: 8,000 × 1,000 × $1 / 1,000,000 = 하루 $8
- 인하 후: 8,000 × 1,000 × $0.25 / 1,000,000 = 하루 $2

단순 계산으로 Cache Read 비용이 4분의 1이 됩니다. 실제 Workflow에서는 Cache되지 않은 Token도 과금 대상이므로 절감률이 이만큼 단순하지는 않지만, Cache Hit율이 높은 Workflow일수록 혜택이 커진다는 점은 분명합니다.

## Benchmark가 보여주는 Agentic Coding의 진화

Anthropic이 공개한 Benchmark에 따르면 Fable 5.1은 Terminal-Bench-Science에서 52.6%를 기록해 Fable 5의 24.7%보다 두 배 이상 향상되었습니다. 또한 CursorBench 3.2의 Agentic Coding 평가에서는 73.4%를 기록했으며, 복잡한 작업에서 자체 검증(생성한 Code나 실행 결과를 스스로 확인하고 수정하는 것) 능력이 강점이라고 설명합니다 ([MarkTechPost](https://www.marktechpost.com/2026/09/01/anthropic-releases-claude-fable-5-1-and-claude-mythos-5-1-52-6-on-terminal-bench-science-and-75-cheaper-cache-reads/)).

Benchmark 수치 자체를 맹신하기보다 "자체 검증 능력 향상"이라는 방향성에 주목해야 합니다. Agent가 자신의 출력을 의심하고 Test를 실행하며 실패 시 수정하는 Loop를 돌릴 수 있는지는, 실무에서 Agent에게 맡길 수 있는 작업 범위를 결정짓습니다.

## webhani의 실무 관점

고객 Project에서 AI Coding Agent를 운영하는 입장에서 몇 가지 실무 Point를 짚어보겠습니다.

1. **처음부터 Cache 구조를 설계합니다.** System Prompt나 Codebase 설명을 "변하지 않는 부분"으로 분리하고 `cache_control`을 부여하는 설계를, Agent 구축 초기 단계부터 반영해야 합니다.
2. **Benchmark보다 자사 Workload 검증을 우선합니다.** 공개 Benchmark는 참고 지표일 뿐입니다. 실제 Codebase와 작업으로 A/B Test를 진행해 비용과 품질의 균형을 확인하는 것을 권장합니다.
3. **Model 전환 시 호환성 확인을 잊지 않습니다.** Model을 교체하면 출력 Format이나 Tool 호출 동작에 미묘한 차이가 생길 수 있습니다. Production 투입 전 기존 Agent Flow로 회귀 Test를 진행해야 합니다.

## 마무리

Claude Fable 5.1의 Cache Read 인하는 단순한 가격 조정이 아니라, Agentic Coding이라는 Use Case 자체를 겨냥한 최적화로 봐야 합니다. 동시에 Benchmark 향상은 Agent에게 맡길 수 있는 작업 범위가 꾸준히 넓어지고 있음을 보여줍니다. webhani는 이러한 Model 진화를 고려한 비용 설계와 Agent 운영 지원을 계속해 나가겠습니다.
