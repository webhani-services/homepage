## 일주일 사이에 나온 두 가지 발표

2026년 8월 15일, Anthropic은 조용히 가격 페이지를 업데이트했습니다. 9월 1일로 예정되어 있던 $3/$15 per MTok 인상을 진행하지 않는다는 내용입니다. Flagship Tier의 $2/$10 per MTok는 한시적 프로모션이 아니라 표준 가격으로 유지됩니다.

그로부터 2주 뒤인 9월 1일, Anthropic은 Agentic 및 Tool-use 작업에 특화된 GA Flagship Model인 Claude Fable 5.1과, 보안·생명과학 분야 검증된 조직에 한해 제공되는 제한적 Access Model인 Claude Mythos 5.1을 출시했습니다. Fable 5.1은 이전 버전 대비 Cache Read(캐시 읽기) 가격이 상당히 낮아진 것이 특징입니다.

각각을 따로 보면 흔한 벤더 소식으로 보일 수 있습니다. 하지만 두 발표를 함께 놓고 보면, 장시간 지속되는 Agent Session을 운영하는 팀 — 지금 시점에서 webhani 고객 대부분이 여기에 해당합니다 — 의 비용 구조가 실제로 바뀝니다.

## 헤드라인 가격보다 Cache Read 가격이 중요한 이유

Agentic Coding Tool은 매 Turn마다 System Prompt, Tool 정의, File 내용, 대화 이력 같은 큰 Context를 반복해서 전송합니다. Prompt Caching이 없다면 이 Context에 대해 매 호출마다 전체 Input Token 가격을 지불해야 합니다. Caching이 적용되면 첫 호출만 전체 가격을 지불하고, 이후 Cache Window 내의 호출은 할인된 Cache Read 가격만 지불합니다.

그래서 "MTok당 표시 가격"이 예전만큼 많은 정보를 주지 못합니다. List 가격이 더 높더라도 Cache Read가 더 저렴한 Model이, Context를 자주 재사용하는 Agentic Workload에서는 실질적으로 더 저렴할 수 있습니다. 이는 거의 모든 Claude Code Session, CI에 통합된 Agent, 장시간 실행되는 Background Job에 해당하는 이야기입니다.

실제 Workload에 대한 비용을 단순화하면 다음과 같은 식이 됩니다.

```text
session_cost = (첫 호출의 Input Token 수 * input_price)
             + (Cache Read 횟수 * cache_read_price)
             + (Output Token 수 * output_price)
```

예를 들어 20-Turn Agent 실행에서 Context의 90%(System Prompt, Tool Schema, File Tree 등)가 안정적이고, 나머지 10%만 Turn마다 바뀐다고 가정해 봅시다. 이 경우 input_price 항목보다 cache_read_price 항목이 전체 비용을 훨씬 크게 좌우합니다. Fable 5.1의 Cache Read 가격 인하가 실제로 움직이는 것은 바로 이 숫자입니다.

## 구체적인 비교

대표적인 사례로, 20-Turn Session에서 Turn당 안정적인 Context 약 8,000 Token(Cache Read), 신규 Input 약 800 Token(전체 가격), Output 약 600 Token을 가정해 보겠습니다.

```text
Turn당 재사용되는 안정 Context: 8,000 Token(Cache Read)
Turn당 신규 Input:             800 Token(전체 가격)
Turn당 Output:                 600 Token
Turn 수:                       20
```

Cache Read 가격이 낮아지기 전에도, 20-Turn Session 전체 비용 중 Caching된 Context 부분이 40~50%를 차지하는 경우가 드물지 않습니다. "할인된 항목"임에도 불구하고 20번 읽히기 때문입니다. Cache Read 가격의 작은 하락도 매 Turn, 매 Session, 매일 실행되는 Agent에 걸쳐 누적됩니다. 월별 청구액을 실제로 움직이는 것은 이 Lever이지, Input/Output의 헤드라인 가격이 아닙니다.

## 고객들에게 전하고 있는 내용

1. **List 가격만으로 Model을 비교하지 마세요.** Agentic Workflow에서는 전체 Token 소비 중 Cache Read가 차지하는 비율을 확인하세요(Vendor에 문의하거나 자체 사용 Log를 확인하면 됩니다). 30%를 넘는다면, 비용을 좌우하는 주요 Lever는 마케팅 표의 숫자가 아니라 Cache Read 가격입니다.

2. **$2/$10의 영구화는 "인하"가 아니라 "불확실성의 제거"입니다.** 9월 인상을 예상해 예산을 잡아둔 팀은 그 여유분을 다른 곳에 돌릴 수 있습니다. 다만 "인상이 없었다"를 "저렴해졌다"로 혼동하지는 마세요. 연간 비용 예측 측면에서는 유용한 확실성 확보입니다.

3. **Model을 교체할 때마다 비용 모델을 다시 계산하세요.** Fable 5.0에서 Fable 5.1로의 이전(또는 다른 Version 간 이전 어떤 경우든)은 위 식의 cache_read 계수를 바꿉니다. 같은 Prompt 구조를 유지하면서 "비용은 List 가격에 비례해 변할 것"이라고 가정하는 팀을 종종 보는데, Caching이 개입되는 순간 그렇게 되지 않습니다.

4. **Model 선택뿐 아니라 Cache Hit을 극대화하는 설계를 하세요.** System 지시사항, Tool 정의, File Context처럼 정적인 내용을 앞쪽에, 최신 사용자 Turn처럼 변동하는 내용을 뒤쪽에 배치하면 Caching 지원 Model이 실제로 재사용할 수 있는 양이 극대화됩니다. 이는 어떤 Model을 쓰는지와는 독립적인 Prompt 설계 판단이며, 대부분의 사람들이 생각하는 것보다 효과가 큽니다.

## 결론

이번 사안의 핵심은 "가격이 오르지 않았다"가 아니라, Agentic AI의 실질적인 비용 단위가 "호출당 Input 가격"에서 "Cache Read 경제성"으로 옮겨갔다는 점입니다. 그리고 대부분의 비용 Dashboard는 아직 이 내역을 명확하게 보여주는 구조로 만들어져 있지 않습니다. 운영 환경에서 Agent를 돌리고 있고, Cache Read 지출과 신규 Input 지출을 나눠서 모니터링하고 있지 않다면, 다음 Model 이전 전에 메워둘 가치가 있는 공백입니다.
