Anthropic이 11월 9일 Claude Fable 5.2를 공개했습니다. 보안·생명과학 분야의 검증된 조직에만 제공되는 Claude Mythos 5.2도 함께 발표되었습니다. API의 model ID는 `claude-fable-5-2`입니다. ID 교체는 금방 끝나지만, Production에서 돌아가는 Agent나 Batch 작업을 전환할 때는 품질보다 먼저 비용과 Latency의 전제가 바뀌는지 확인해야 합니다.

## 무엇이 바뀌었나

공식 Migration Guide와 보도 내용을 기준으로 운영에 영향을 주는 부분만 추리면 다음과 같습니다.

- **요금**: SD Times가 Anthropic 발표를 인용해 보도한 바에 따르면 100만 token당 입력 $8 / 출력 $40으로, Fable 5.1보다 낮아졌습니다.
- **속도**: Anthropic은 출력 생성 속도가 Fable 5.1 대비 최대 30% 빨라졌다고 밝혔습니다.
- **Context**: 기본 1M token context window, Request당 최대 128k 출력 token.
- **Effort**: 다섯 단계를 모두 지원합니다. API 기본값은 5.1과 같은 `high`이지만, Claude 앱과 Claude Code의 기본값은 medium으로 바뀌었습니다.
- **Thinking**: Adaptive thinking이 항상 켜져 있습니다.
- **Fast mode**: Messages API에서 사용할 수 있습니다. 한 개발자 가이드는 `speed: "fast"`로 지정하고 요금은 $16 / $80이라고 설명하지만, 2차 정보이므로 공식 요금 페이지에서 확인하시기 바랍니다.
- **제공 채널**: Claude 유료 플랜, API, Amazon Bedrock, Google Cloud, Microsoft Azure.

Migration Guide는 "대체로 그대로 교체 가능"하다고 설명합니다. 문제는 effort 기본값입니다.

## 함정: 위치마다 다른 기본값

Claude Code에서 Fable 5.2를 써 본 엔지니어는 medium effort로 동작하는 모델을 경험한 것입니다. 같은 Prompt를 API로 보내면 high로 동작합니다. 체감도, token 사용량도 일치하지 않습니다.

다른 모델에서 넘어오는 경우에는 차이가 더 커집니다. Opus 5.5의 기본값은 medium이므로, model ID만 Fable 5.2로 바꾸면 모든 Request의 effort가 한 단계 올라갑니다. Effort가 올라가면 출력 token이 늘고, 그만큼 Latency와 비용도 늘어납니다. 단가가 내려갔다고 청구액이 반드시 줄지는 않습니다.

저희의 권장 사항은 **기본값에 맡기지 말고 Workload별로 effort를 명시하는 것**입니다.

```ts
// llm-profiles.ts — Workload별 model과 effort를 한곳에서 관리
type Effort = "low" | "medium" | "high";

interface LlmProfile {
  model: string;
  effort: Effort;
  maxTokens: number;
}

export const profiles = {
  // 사용자가 기다리는 Chat 응답: Latency 우선
  chat: { model: "claude-fable-5-2", effort: "medium", maxTokens: 4_000 },
  // 야간 Code Review Batch: 품질 우선
  review: { model: "claude-fable-5-2", effort: "high", maxTokens: 16_000 },
  // 분류·추출: 작은 모델로 충분
  classify: { model: "claude-haiku-5-5", effort: "low", maxTokens: 512 },
} satisfies Record<string, LlmProfile>;
```

Effort를 Request에 전달하는 정확한 필드 이름은 사용 중인 SDK 버전에서 확인하시기 바랍니다. 핵심은 model과 effort를 같은 곳에 두어, 하나를 바꿀 때 다른 하나도 의식적으로 결정하게 만드는 구조입니다.

## Fast mode는 어디에 쓸까

Fast mode는 출력이 빨라지는 대신 단가가 올라갑니다. 위의 2차 정보가 맞다면 약 2배입니다. 모든 Traffic에 켜면 비용 항목이 그대로 두 배가 되므로, 저희는 다음과 같이 나눠 씁니다.

- **사용**: 사용자가 화면 앞에서 기다리는 대화형 UI, 개발자를 Block하는 짧은 CI 작업
- **미사용**: 야간 Batch, 비동기 문서 생성, Webhook으로 실행되는 Agent

판단 기준은 "단축된 몇 초를 실제로 기다리는 사람이 있는가"입니다. 기다리는 사람이 없다면 Fast mode의 효과는 청구서에만 나타납니다.

## 전환 전 점검 목록

Production Traffic을 옮기기 전에 다음을 확인합니다.

1. **Eval 재실행**: 실제 입력 50~100건 정도로 기존 모델과 Fable 5.2의 품질, 출력 token 수, 소요 시간을 비교합니다.
2. **Request 단위 Usage Logging**: token 데이터 없이는 전환으로 비용이 줄었는지 판단할 수 없습니다.

```ts
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

export async function runWithUsageLog(profileName: string, prompt: string) {
  const started = Date.now();
  const res = await client.messages.create({
    model: "claude-fable-5-2",
    max_tokens: 4_000,
    messages: [{ role: "user", content: prompt }],
  });
  console.info(JSON.stringify({
    profile: profileName,
    model: res.model,
    inputTokens: res.usage.input_tokens,
    outputTokens: res.usage.output_tokens,
    ms: Date.now() - started,
  }));
  return res;
}
```

3. **데이터 보존 조건 확인**: 일부 보도에 따르면 Claude Platform에서 Fable 5.2를 사용하려면 zero retention 승인을 받은 경우를 제외하고 30일 데이터 보존이 필요합니다. 고객 데이터를 다루는 프로젝트라면 공식 문서와 계약 조건을 함께 확인하시기 바랍니다.
4. **Fallback 유지**: model ID를 환경 변수나 Feature Flag 뒤에 두고, 전환 직후 며칠간 Error율과 Timeout을 모니터링합니다.
5. **Claude Code 사용 방식 통일**: medium이 기본값이 되면서 어려운 문제에서 답변이 얕아졌다고 느끼는 경우가 있을 수 있습니다. Architecture 판단이나 까다로운 Debug처럼 effort를 명시적으로 올릴 상황을 팀 내에서 합의해 두면 혼란이 줄어듭니다.

## webhani의 관점

이번 업데이트는 성능 도약보다는 "비슷한 품질을 더 싸고 빠르게"에 가깝다고 봅니다. 유용한 변화지만, 단가 인하가 곧 비용 절감은 아닙니다. Effort 기본값과 Fast mode 사용 방식에 따라 청구액은 오르기도, 내리기도 합니다.

한 줄짜리 Migration일수록 측정 없이 배포되기 쉽습니다. 먼저 Usage를 기록하고, Workload별 effort를 고정하고, Eval로 비교한 다음 전환하십시오. 이 순서를 지키면 새 모델의 효과를 숫자로 확인하면서 도입할 수 있습니다.
