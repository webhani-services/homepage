## 2주 사이에 Flagship Model이 네 개나 나왔습니다

2026년 7월 초, 주요 AI Lab들이 잇따라 새 Model을 출시했습니다. 7월 8일 xAI가 Grok 4.5를 공개했습니다. Cursor로 학습된 저렴한 Coding Model이라는 Positioning으로, 가격은 100만 Token당 $2/$6입니다. 바로 다음 날 OpenAI는 GPT-5.6 계열(내부 코드명 Sol, Terra, Luna)을 General Availability로 전환하고 ChatGPT의 Default Model로 설정했습니다. Input 100만 Token당 $1-$5, Context Window는 1M Token입니다. Meta도 같은 날 첫 유료 Model인 Muse Spark 1.1을 $1.25/$4.25로 출시했습니다. 그리고 7월 24일, Anthropic이 Claude Opus 5를 발표했습니다. Artificial Analysis의 Intelligence Index에서 Score 61, Agentic Index에서 Score 55.3으로 두 지표 모두 1위를 차지했고, 가격은 $5/$25로 Claude Fable 5의 절반입니다.

이번 주 고객들과의 대화는 거의 다 같은 질문으로 시작합니다. "그래서 우리는 어떤 Model로 갈아타야 하나요?" 솔직히 말하면 Leaderboard 숫자는 이 결정에서 가장 덜 중요한 부분입니다. 저희가 실제로 어떻게 접근하고 있는지 정리해봅니다.

## Leaderboard 순위는 우리 팀의 Workflow에 대해서는 약한 Signal입니다

Intelligence Index와 Agentic Index는 광범위한 Task 분포에 대한 평균적인 성능을 측정합니다. 유용한 정보이긴 하지만, 이는 우리 팀의 Task 분포가 아닙니다. Django Monolith를 유지보수하는 팀, 복잡한 React State 관리를 다루는 팀, Terraform Module을 작성하는 팀은 Coding Agent에게 작업을 맡길 때 사실상 전혀 다른 문제를 풀고 있는 셈입니다. Agentic Index에서 1위를 한 Model이라 해도, 우리 팀의 CI 설정, Lint 규칙, PR 작성 관습까지는 알지 못합니다.

Grok 4.5의 "Cursor로 학습됨"이라는 Positioning이 좋은 예시입니다. 이는 특정 Coding Workflow에 맞춰 조정되었다는 의미입니다. 우리 Workflow가 그것과 비슷하면 강점이 되지만, 그렇지 않다면 무의미한 특징입니다.

실무적인 해결책은 단순하지만 효과적입니다. 우리 팀 자체의 History로 작은 내부 Eval Set을 만드는 것입니다. 시작점은 다음과 같습니다.

1. 실제로 Merge된 PR 10-30개를 선정합니다. Bug Fix, 기능 추가, Refactoring을 골고루 섞습니다.
2. 각 PR의 원본 Issue 설명을 Prompt Input으로 보존합니다.
3. 구체적인 기준으로 Output을 평가합니다. 생성된 Diff가 기존 Test Suite를 통과하는지, Style 관습에 맞는지, 사람이 Review했다면 몇 개의 Comment를 남겼을지.

이 Eval Set에 대해 후보 Model(Opus 5, GPT-5.6, Grok 4.5)을 동일한 Prompt와 동일한 Tool 정의로 실행하고, Pass Rate와 예상 Review 부담을 비교합니다. 이 결과가 Intelligence Index 순위보다 우리 팀에게 훨씬 강력한 Signal입니다.

## Opus 5의 가격 인하가 실제로 여는 것

Opus 5가 Fable 5의 절반 가격이 된 것은 단순한 비용 절감 이야기가 아닙니다. Agentic Coding Setup에서 무엇이 가능한지를 바꿉니다. 무거운 Agentic Workflow는 많은 Tool Call을 발생시키고, Task당 여러 Agent를 병렬로 실행하는 경우가 많습니다. Token당 비용이 절반이 되면, 같은 예산으로 대략 두 배의 병렬 Agent 작업이 가능해집니다.

구체적으로 보면, 이전에는 PR당 범용 Review Agent 하나만 감당할 수 있던 팀이 이제 같은 지출로 여러 개의 전문화된 Agent를 병렬로 돌릴 수 있습니다.

- Agent A: Logic의 정확성과 Edge Case 확인
- Agent B: Security 관점(Injection, 권한 처리) 확인
- Agent C: 기존 Codebase와의 Style·Naming 일관성 확인
- Agent D: Test Coverage Gap 확인

각 Agent가 PR Diff에 대해 동시에 실행되고, 결과는 하나의 Summary Comment로 병합됩니다. 이전에는 대부분의 팀에게 이 구성이 비용 효율적이지 않았습니다 — 범용 Reviewer Agent 하나가 실질적인 한계였습니다. 단, 이것이 공짜는 아닙니다. 병렬 Agent가 늘어날수록 Noise(중복되거나 우선순위 낮은 지적)도 늘어나므로, 결과를 취합하는 Aggregation Step 설계에 실제 노력을 들여야 합니다.

## 더 중요한 교훈: 품질은 "특정 Model을 쓰고 있다"는 것만으로 고정되는 속성이 아닙니다

이번 뉴스에서 실무적으로 가장 유용한 부분은 Opus 5의 Benchmark Score가 아니라, Anthropic 스스로 공개한 사후 조사 결과라고 생각합니다. 2026년 3월부터 4월 사이, Anthropic은 Version이 바뀌지 않은 채 이루어진 세 가지 독립적인 변경이 Claude의 출력 품질을 조용히 저하시켰다는 것을 확인했습니다. Claude Code의 Default Reasoning Effort Level 인하, Cache 최적화 관련 Bug, 그리고 System Prompt 개정입니다. 세 가지 모두 조사 후 되돌려졌습니다.

어떤 Provider의 Production Agent를 운영하든 시사점은 같습니다. 우리 Code를 한 줄도 바꾸지 않고 Version String도 그대로인데, Model의 동작이 Drift할 수 있다는 것입니다. Default 설정은 안정적인 계약이 아닙니다.

구체적인 대응책은 세 가지입니다.

**Default에 의존하지 말고 Reasoning Effort를 명시적으로 고정합니다.**

```python
# 취약한 방식: Provider의 현재 Default에 의존
response = client.messages.create(
    model="claude-opus-5",
    messages=[...],
)

# 나은 방식: 명시적으로 지정하여 조용한 Default 변경의 영향을 받지 않음
response = client.messages.create(
    model="claude-opus-5",
    reasoning_effort="high",
    messages=[...],
)
```

**작은 Regression Eval Suite를 만들고, Model을 바꿀 때뿐 아니라 정기적으로 재실행합니다.** 앞서 언급한 내부 Eval Set은 다른 목적으로도 유용합니다 — Model 교체 여부와 무관하게, 기존 Production Agent의 Drift를 잡아내는 용도입니다.

```yaml
# .github/workflows/agent-regression.yml
name: Agent Regression Check
on:
  schedule:
    - cron: "0 3 * * 1" # 매주 월요일
  workflow_dispatch:

jobs:
  eval:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run internal eval set against production agent config
        run: npm run eval:agent -- --suite=internal-30 --threshold=0.85
      - name: Alert on regression
        if: failure()
        run: npm run notify:slack -- "Agent regression detected"
```

**설명되지 않는 동작 변화가 있다면 먼저 Provider 측 변경을 의심합니다.** Prompt나 Config를 건드리지 않았는데 Verbosity, Tool Call 횟수, Error Handling의 꼼꼼함이 달라졌다면, 우리 Code보다 Provider의 Default 변경을 먼저 의심해야 합니다.

## 정리

- Intelligence Index나 Agentic Index 순위만으로 Model을 고르지 마세요. 실제 PR과 Issue 10-30개로 자체 Eval Set을 만들고 Pass Rate와 Review 부담을 직접 측정하세요.
- Opus 5의 가격 인하는 PR당 전문화된 병렬 Review/Verification Agent를 감당 가능하게 만듭니다. 다만 Agent가 늘어날수록 Aggregation Step 설계가 중요해집니다.
- Model 품질은 한번 채택했다고 영구히 고정되는 속성이 아닙니다. Reasoning Effort Default, Caching, System Prompt에 대한 Provider 측의 조용한 변경이 Version 변화 없이 Production 동작을 저하시킬 수 있습니다.
- Reasoning Effort를 비롯한 조정 가능한 Default는 API Call에서 명시적으로 Pin하고, Provider의 현재 Default에 의존하지 마세요.
- 작은 Regression Eval Suite를 Production Agent Config에 대해 정기적으로 재실행하세요 — Model 교체 여부와 무관하게, Drift를 조기에 잡기 위함입니다.
- Opus 5, GPT-5.6, Grok 4.5의 채택 여부를 판단할 때는 Vendor Benchmark Score보다 우리 팀 자체 Eval 결과에 더 무게를 두세요.
