## 성능은 올라가고 가격은 내려간 흔치 않은 릴리스

2026년 7월 24일, Anthropic이 Claude Opus 5를 출시했습니다. 며칠 만에 Artificial Analysis의 Intelligence Index(점수 61)에서 1위에 올랐고, 저희 업무와 더 직접 관련된 Agentic Index(55.3)에서도 1위를 차지했습니다. 다만 실제 의사결정에 영향을 주는 건 오히려 가격입니다. Input Token 100만 개당 $5, Output Token 100만 개당 $25로, Anthropic의 또 다른 Flagship급 Model인 Claude Fable 5의 대략 절반 가격입니다.

이런 조합은 흔치 않습니다. 보통 새로운 Frontier Model은 성능이 오르는 대신 가격은 그대로거나 오히려 비싸지기 마련입니다. 이번에는 성능이 오르면서 가격은 내려갔습니다. 여기에 함께 기억해둘 만한 사실이 하나 있습니다. Fable 5 자체가 2026년 6월 미국의 수출 통제 조치로 약 3주간 서비스가 중단되었고, 7월 1일에야 재배포되었다는 점입니다. 그 기간 동안 Fable 5 하나에만 의존해 업무를 돌렸던 팀이라면, 단일 Vendor·단일 Model 의존이 이론이 아니라 실제 운영 Risk라는 걸 이미 체감했을 것입니다.

이 글에서는 저희가 고객들로부터 자주 받는 질문 — "지금 당장 Agent를 Opus 5로 옮겨야 하나, 그리고 그걸 어떻게 판단해야 하나" — 에 답합니다.

## "Agentic Index" 1위가 실무에서 의미하는 것

일반적인 Intelligence Benchmark는 단일 Turn에서의 추론 품질에 가까운 것을 측정합니다. 어려운 문제를 주고 답을 채점하는 방식입니다. 이는 코딩 능력과 어느 정도 상관관계가 있지만, 실제로 Agentic Coding Workflow를 무너뜨리는 원인과는 다소 거리가 있습니다.

Agentic Index가 측정하는 건 저희가 실제로 신경 쓰는 부분에 더 가깝습니다. 여러 Step으로 이루어진 작업을 얼마나 계획적으로 처리하는지, Tool을 정확하게 호출하는지, Tool 호출 실패나 Test 실패에서 제대로 회복하는지, 긴 Session 동안 계획이 흐트러지지 않고 일관성을 유지하는지가 관건입니다. 실무에서 엔지니어의 시간을 갉아먹는 실패는 "문법을 몰랐다"가 아니라 대개 이런 것들입니다.

- Agent가 잘못된 인자로 Tool을 호출하고도 스스로 고치지 못하는 경우
- 실제로 Test를 돌리지 않았는데 작업 완료라고 보고하는 경우
- Tool 호출을 30번쯤 거친 뒤 Session 초반의 제약을 잊어버리는 경우
- 실패한 접근 방식을 다른 방식으로 바꾸지 않고 그대로 반복하는 경우

Agentic Index에서 1위인 Model이라면 원칙적으로 이런 실패 유형에 더 강할 것입니다. 이는 CI에 통합된 Coding Agent 입장에서, 수학 Benchmark에서의 0.5점 개선보다 훨씬 의미 있는 차이입니다.

## 진짜 물어야 할 질문은 "업그레이드해야 하나"가 아닙니다

Opus 5가 Fable 5보다 성능도 좋고 가격도 싸다고 하면, "그럼 다 옮기자"는 반응이 나오기 쉽습니다. 여기서 한 번 멈춰야 합니다. 문제는 Opus 5가 좋은 Model인지가 아닙니다 — Artificial Analysis의 수치가 이미 그걸 뒷받침합니다. 진짜 문제는 여러분이 실제로 돌리고 있는 각각의 Workload에 맞는 Model인지입니다. "Flagship"이 "모든 작업의 정답"을 의미하지는 않습니다. Agentic Coding 작업의 상당수 — Lint 수정, Changelog 생성, 단순 Refactor 등 — 는 애초에 Flagship급 추론이 필요 없고, 가격이 싸졌다는 이유만으로 그쪽으로 몰아넣는 건 더 작은 Model로도 충분한 작업에 불필요한 비용을 쓰는 것일 수 있습니다.

아래는 Agent Config에서 Model 선택 Logic을 어떻게 구조화하는지, 의도적으로 일반화된 형태로 보여주는 예시입니다. "가장 최근에 나온 Model이라서"가 아니라, 판단 기준을 명시적이고 Test 가능하게 만드는 게 목적입니다.

```typescript
type ModelId = "claude-opus-5" | "claude-fable-5" | "claude-haiku-5";

interface ModelPricing {
  inputPer1M: number;  // USD / 100만 Input Token
  outputPer1M: number; // USD / 100만 Output Token
}

// 예시용 수치입니다. 실제 Price는 반드시 Provider의 최신 정보로 확인하세요.
const PRICING: Record<ModelId, ModelPricing> = {
  "claude-opus-5":  { inputPer1M: 5,    outputPer1M: 25 },
  "claude-fable-5": { inputPer1M: 10,   outputPer1M: 50 },
  "claude-haiku-5": { inputPer1M: 0.8,  outputPer1M: 4 },
};

function estimateCost(model: ModelId, inputTokens: number, outputTokens: number): number {
  const p = PRICING[model];
  return (inputTokens / 1_000_000) * p.inputPer1M + (outputTokens / 1_000_000) * p.outputPer1M;
}

interface TaskProfile {
  requiresMultiStepToolUse: boolean;
  estimatedToolCalls: number;
  riskIfWrong: "low" | "medium" | "high"; // 예: 인증·결제 관련 코드라면 high
}

function pickModel(task: TaskProfile): ModelId {
  // 영향 범위가 크거나 Tool Chain이 길면, 최고의 Agentic 성능에 투자합니다.
  if (task.riskIfWrong === "high" || task.estimatedToolCalls > 8) {
    return "claude-opus-5";
  }
  // 중간 정도 복잡도: opus-5와 중위 Model을 단정하지 말고 A/B Test로 비교할 가치가 있습니다.
  if (task.requiresMultiStepToolUse) {
    return "claude-opus-5";
  }
  // 낮은 Risk·낮은 복잡도: 대개 작은 Model로 충분합니다.
  return "claude-haiku-5";
}
```

이 코드에서 중요한 건 구체적인 숫자가 아닙니다(본문의 모든 가격은 작성 시점의 Snapshot이며, 읽으실 때쯤이면 이미 낡은 정보일 수 있습니다). 중요한 건 패턴입니다. 판단 기준은 "어떤 Model이 최근에 나왔나"가 아니라 작업의 Risk와 Tool 호출 깊이여야 합니다.

## 고객이 마이그레이션을 고민할 때 저희가 안내하는 방식

기존 Flagship에서 새 Model로 옮길지 고객이 물어올 때, Webhani는 발표가 아무리 화려해도 매번 같은 네 단계로 정리합니다.

**1. 무엇이든 Production에 반영하기 전에 자체 Eval을 먼저 돌립니다.** 공개 Benchmark가 보여주는 건 Artificial Analysis의 Task에 대한 성능이지, 여러분의 Codebase나 Test Suite, 사내 API에 대한 성능이 아닙니다. 자사 Backlog에서 대표적인 Ticket 20~50개 정도를 고정 Set으로 만들고, 기존 Model과 신규 Model을 실제 사용 중인 Agent 환경 위에서 같이 돌려보세요. "그럴듯한 코드가 나왔는가"가 아니라 Pass율, 완료까지 걸린 Tool 호출 횟수, 사람이 Review하는 데 걸린 시간을 비교해야 합니다.

**2. Token 가격이 아니라 작업 전체의 Cost를 계산합니다.** Token 단가가 싸더라도, 같은 결과에 도달하는 데 더 많은 Tool 호출이나 Retry가 필요하다면 작업 전체 Cost는 오히려 비쌀 수 있습니다. 단가만 볼 게 아니라 호출 횟수를 곱해서 견적을 내야 합니다.

**3. Rollout을 단계적으로 진행합니다.** 출시 당일에 Traffic을 100% 전환하지 마세요. 중요도가 낮은 작업 일부를 새 Model로 Routing하고, 1~2주 정도 실패율과 Cost를 관찰한 뒤 확대합니다. 이렇게 하면 Benchmark에는 드러나지 않는 출시 초기의 불안정성으로부터도 보호받을 수 있습니다.

**4. Architecture에 단일 Model 의존을 박아 넣지 않습니다.** 여기서 떠올려야 할 구체적인 사례가 바로 Fable 5의 6월 수출 통제로 인한 3주 중단입니다. 어떤 Model을 고르든, Model ID만 바꾸면 되도록 Agent Config를 충분히 추상화해두어야 합니다. 위 코드의 `ModelId`가 이 판단을 한곳에 모아두기 위해 존재하는 이유입니다.

## 정리

- Opus 5가 Agentic Index에서 1위라는 사실은 특히 Tool을 사용하는 Coding Agent에게 의미가 있습니다. 실무 Cost를 좌우하는 실패 유형을 잡아내는 지표로서, 일반 Intelligence Score보다 실제에 더 가깝습니다.
- 기존 Flagship보다 싸고 성능도 좋다는 사실만으로는 전면 마이그레이션의 이유가 되지 않습니다. Model Tier는 출시일이 아니라 작업의 Risk에 맞춰 골라야 합니다.
- Model 선택은 Data 기반의, 교체 가능한 Config로 구성하세요. 위 코드 예시는 완성형이 아니라 출발점 Pattern입니다.
- Production Workload를 전환하기 전에 반드시 자사 작업으로 Eval하세요. 공개 Benchmark 1위는 "확인해봐야 할 신호"이지 "마이그레이션 지시"가 아닙니다.
- 단일 Flagship 의존은 운영상의 Risk로 다뤄야 합니다. Fable 5의 올해 6월 중단은 가정이 아니라 실제로 일어난 사례입니다.
