## 작은 토글이지만 설계상 의미는 큽니다

Anthropic은 이번 주 Claude의 Voice Mode를 업데이트하여 Opus·Sonnet·Haiku 중 어떤 Model이 대화를 처리할지 선택할 수 있게 했습니다. 이전에는 모든 Voice Session이 하나의 고정 Model을 거쳤지만, 이제는 Text Chat에서 마지막으로 사용한 Model이 기본값이 되고, 그중에서도 가장 빠른 Variant가 기본으로 선택됩니다.

겉으로 보면 설정 메뉴의 변경처럼 보입니다. 하지만 실무적으로는 Voice Product를 만드는 사람이라면 명시적으로 판단해야 할 Trade-off를 드러냅니다. Voice Interface는 Text Chat보다 Latency 여유가 훨씬 적지만, 사용자는 복잡한 요청에 대해서는 여전히 제대로 된 추론 능력을 기대합니다. 예전에는 이 Trade-off가 Provider 쪽에서 고정되어 있었지만, 이제는 Session 단위, Product 단위로 결정할 수 있는 문제가 되었습니다.

## Voice에서 계산이 달라지는 이유

Text Chat은 몇 초 정도의 "생각 중" 상태를 용인합니다. Voice는 그렇지 않습니다. 1~2초를 넘는 Turn-taking 지연은 그 자체로 뭔가 고장 난 것처럼 느껴집니다. 사람이 음성 대화에서 기대하는 리듬은 타이핑한 메시지에서 기대하는 리듬보다 훨씬 빠르기 때문입니다. 그래서 Voice Assistant는 역사적으로, 얕은 추론이라는 비용을 감수하고서라도 가장 작고 빠른 Model을 기본값으로 삼아 왔습니다.

문제는 Voice의 많은 Use Case가 실제로는 얕지 않다는 점입니다. "오늘 날씨 어때"는 빠르고 저렴한 Model로 충분하지만, "이 미해결 청구서 분쟁을 어떻게 재구성할지 같이 정리해줘"는 다릅니다. 둘 다 같은 Model에 통과시키면, 간단한 요청에는 Capacity를 낭비하고 어려운 요청에는 사용자를 답답하게 만들게 됩니다.

Anthropic의 이번 업데이트처럼 Session마다 Model을 다르게 가져갈 수 있고, 이미 사용하던 Model의 가장 빠른 Variant가 기본값이 되는 구조는, Text 기반 Agent가 이미 실천하고 있는 "작업 복잡도에 Model 능력을 맞추는" 설계를 Voice Interface로 확장하는 한 걸음이라 할 수 있습니다.

## 설계 패턴으로 적용하기

이 아이디어는 Claude 자체의 Voice Mode에 국한되지 않습니다. Anthropic API 위에 Voice Product를 구축한다면, 동일한 계층화 패턴을 직접 구현할 수 있습니다. 먼저 들어온 요청을 저렴하게 분류한 뒤, 복잡도에 맞는 Model Tier로 Routing합니다.

```ts
type ModelTier = "haiku" | "sonnet" | "opus";

const MODEL_IDS: Record<ModelTier, string> = {
  haiku: "claude-haiku-4-5",
  sonnet: "claude-sonnet-5",
  opus: "claude-opus-5",
};

// 실제 응답 생성(Latency에 민감한 부분) 전에
// 저렴하고 빠른 분류 Pass로 Tier를 정합니다
async function pickTier(utterance: string): Promise<ModelTier> {
  const wordCount = utterance.trim().split(/\s+/).length;
  const looksMultiStep = /\b(then|after that|compare|why)\b/i.test(utterance);

  if (wordCount < 8 && !looksMultiStep) return "haiku";
  if (looksMultiStep || wordCount > 25) return "opus";
  return "sonnet";
}

async function respondToVoiceTurn(utterance: string) {
  const tier = await pickTier(utterance);
  return anthropic.messages.create({
    model: MODEL_IDS[tier],
    max_tokens: 512,
    messages: [{ role: "user", content: utterance }],
  });
}
```

일부러 단순하게 만든 예시입니다. 실제 운영용 Router라면 현재 발화뿐 아니라 대화 History도 반영하고, 빠른 Tier의 응답이 얼버무리거나 불완전해 보이면 상위 Tier로 Fallback하는 식으로 설계할 것입니다. 여기서 전하고 싶은 것은 그 형태 자체입니다. Tier 판단은 저렴하고 빠르게 하고, Latency 예산은 실제로 효과가 있는 곳에만 씁니다.

## 주의해서 볼 지점

Voice Product에 Model 전환을 도입할 때 놓치기 쉬운 부분이 몇 가지 있습니다.

- **Persona의 흔들림**: Model Tier가 다르면 표현 방식도 달라집니다. Product에 고유한 Persona가 있다면 System Prompt와 Tone 지시를 Tier에 무관하게 유지하고, 개발 시 사용하는 한 Tier뿐 아니라 세 Tier 모두에서 Persona가 유지되는지 Test해야 합니다.
- **대화 중간의 Tier 전환**: 같은 Session 안에서 Turn마다 Tier를 바꾸면 응답 Style의 변화가 눈에 띌 수 있습니다. Session 단위로 Tier를 고정할지, 전환을 허용할지 미리 정해두는 편이 좋습니다.
- **진짜 제약은 여전히 Latency**: 어려운 질문을 위해 선택한 상위 Model도 결국 Latency 예산 안에 들어와야 합니다. 각 Tier의 실제 Round-trip Time을 자사의 Network와 TTS Pipeline에서 직접 측정하세요. Tier 간 홍보용 속도 차이가 그대로 Product의 체감 Latency로 이어지지는 않습니다.

## 정리

Voice Mode에서의 Model 선택은 작은 기능이지만 그 안에 담긴 메시지는 더 큽니다. Voice AI가 Text 기반 Agent가 이미 사용하던 Routing 패턴을 따라잡고 있다는 것입니다. Claude API 위에 Voice Product를 만들고 있다면, 실무적으로 취할 다음 조치는 "어떤 Model을 쓸지"를 하나의 전역 설정으로 다루는 것을 멈추고, 실제 작업 복잡도와 직접 측정한 Latency 예산에 맞춘 Turn 단위 Routing 판단으로 다루는 것입니다. Webhani는 Text 기반 Agent 설계에서 사용해 온 이 계층화 원칙을 Voice Interface 설계에도 그대로 적용하고 있습니다.
