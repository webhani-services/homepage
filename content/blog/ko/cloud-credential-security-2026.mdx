## 취약점 없는 대규모 유출

2026년 8월 17~18일경, "TheHatman"이라는 이름의 위협 행위자가 여러 Fortune 500 기업의 Microsoft Azure/Entra ID 테넌트에서 탈취했다고 주장하는 직원 데이터베이스를 판매하기 시작했습니다. McDonald's 관련 약 170만 건을 포함해 Vodafone, Gap Inc, HCL Technologies, InterContinental Hotels Group, Kyndryl, Tata Consultancy Services, Hexaware Technologies, Wyndham Hotels 등 대상 기업이 다양했고, 전체 규모는 360만 건을 넘었습니다. 유출된 데이터에는 이름, 사번, 전화번호, 우편 주소, 회사 이메일, 직급, 관리자 배정 정보, 그룹 멤버십은 물론 서비스 계정과 Global Administrator 목록까지 포함되어 있었습니다.

이번 사건에서 가장 주목해야 할 부분은 유출 건수가 아닙니다. 보안 연구자들이 조사한 결과, Azure나 Entra ID 자체에 제로데이나 플랫폼 취약점은 발견되지 않았습니다. 데이터는 2026년 7월 31일경부터 수집된 것으로 보이는데, 그 방식은 특별할 것이 없었습니다. 탈취된 정상 자격 증명과 그 계정이 원래 가지고 있던 정당한 접근 권한을 그대로 악용한 것뿐이었습니다.

이는 최근 클라우드 침해 사고에서 공통으로 나타나는 패턴입니다. Infrastructure 자체는 견고했지만, 그 주변을 둘러싼 Identity 계층이 뚫렸다는 구도입니다.

## 왜 Identity가 진짜 공격 표면인가

Azure 같은 클라우드 Platform은 테넌트 격리, 저장 데이터 암호화, 기반 Infra 패치에 막대한 엔지니어링 자원을 투입합니다. 그 덕에 Platform 자체에 대한 침해는 실제로 드뭅니다. 공격 표면이 좁고 감시도 철저하기 때문입니다. 반면 자격 증명은 상황이 다릅니다. 모든 직원, 모든 서비스 계정, 모든 CI Pipeline이 하나씩 키를 쥐고 있고, 그 키가 탈취되면 경보음 하나 없이 정문을 그대로 통과하게 됩니다.

디렉터리 동기화용 계정, 오래된 스크립트에 남아 있는 API Token, 피싱으로 넘어간 관리자 세션 — 어느 것이든 공격자에게 정상 운영자와 동일한 시야를 열어줍니다. 디렉터리 데이터 자체가 민감해서가 아니라, 그것이 하나의 "지도" 역할을 한다는 점이 문제입니다. 어떤 계정이 높은 권한을 가졌는지, 누가 누구를 관리하는지, 어떤 서비스 계정이 무엇에 접근하는지가 한눈에 드러납니다. 이 지도가 있으면 자격 증명 하나가 유출되는 순간 수평 이동(lateral movement)을 위한 실행 계획으로 바뀝니다.

여기서 얻어야 할 교훈은 "Azure가 안전하지 않다"가 아니라, Identity와 자격 증명 위생 관리가 이제는 Platform 자체보다 보안을 더 많이 좌우하는 요소가 되었는데도, 대부분의 조직이 네트워크·Infra 통제에 투자하는 만큼 이쪽에는 투자하지 않는다는 사실입니다.

## 실무 예시: Global Administrator 점검

가장 먼저 손대야 할 것은 침해됐을 때 피해가 가장 큰 계정입니다. Entra ID의 Global Administrator 권한은 소수로 제한하고, 누가 보유하고 있는지 항상 파악하며, 정기적으로 검토해야 합니다. 사고가 터진 뒤에야 존재를 알게 되는 상황은 피해야 합니다. Microsoft Graph PowerShell SDK로 점검하는 예시입니다.

```powershell
# 읽기 전용 감사에 필요한 최소 Scope로 연결
Connect-MgGraph -Scopes "RoleManagement.Read.Directory","User.Read.All"

# Global Administrator 역할 정의 조회
$role = Get-MgDirectoryRole -Filter "displayName eq 'Global Administrator'"

# 현재 멤버 목록 조회
Get-MgDirectoryRoleMember -DirectoryRoleId $role.Id | ForEach-Object {
    $user = Get-MgUser -UserId $_.Id -Property DisplayName,UserPrincipalName,AccountEnabled
    [PSCustomObject]@{
        Name    = $user.DisplayName
        UPN     = $user.UserPrincipalName
        Enabled = $user.AccountEnabled
    }
} | Format-Table -AutoSize
```

이 작업은 최소 분기 1회 실행하고, 낯선 이름이 목록에 있다면 "그럴 수도 있지"라고 넘기지 말고 곧바로 Incident로 다루세요. 함께 Graph API에 높은 권한을 가진 서비스 계정과 App Registration도 점검해야 합니다. 이들은 대개 MFA가 걸려 있지 않고, 사람 계정만큼 주시받지 않기 때문에 공격자에게는 매력적인 표적입니다.

## 이번 사고를 늦출 수 있었던 실질적 통제

아래 항목들은 특별한 Tool 없이도, Entra ID P1/P2 라이선스나 다른 Identity Provider의 동급 플랜에서 그대로 사용할 수 있습니다.

- **피싱에 강한 MFA.** Push 기반 MFA나 SMS 인증 코드는 프롬프트 폭탄(prompt bombing)이나 SIM 스와핑으로 우회될 수 있습니다. Global Administrator, 서비스 계정 소유자, Production 쓰기 권한을 가진 계정 등 특권 계정부터 FIDO2 보안 키나 Passkey로 전환하세요. Entra ID는 Authentication Methods 정책에서 기본 지원합니다.

- **Conditional Access를 기본 차단(default-deny) 방식으로.** MFA만 요구할 게 아니라 Device 준수 상태, 접속 위치, Sign-in Risk 기준으로 접근 범위를 제한합니다. 관리자 역할용 최소 정책 예시입니다.

  ```text
  Policy: "관리자 역할에는 Compliant Device + 피싱에 강한 MFA 요구"
  Assignments:
    Users: Directory roles → Global Administrator, Privileged Role Administrator
    Cloud apps: All cloud apps
  Conditions:
    Sign-in risk: Medium 이상 → 차단
  Access controls:
    Grant: Compliant Device 요구
           AND Authentication strength = 피싱에 강한 MFA 요구
  Session:
    Sign-in frequency: 4시간
  ```

- **Session Token 수명 단축.** 오래 지속되는 Refresh Token이야말로 자격 증명 하나가 몇 시간이 아니라 몇 주 동안 "쓸모 있게" 만드는 원인입니다. 특권 세션의 Sign-in Frequency를 줄이고, Continuous Access Evaluation을 활성화해서 권한을 회수하면 다음 Token 갱신을 기다리지 않고 즉시 반영되도록 하세요.

- **비정상 로그인 및 Impossible Travel 탐지.** Entra ID Protection은 낯선 위치, 익명화된 IP, 물리적으로 불가능한 이동 패턴에서의 로그인을 자동으로 표시합니다. 다만 이는 Risk 기반 Conditional Access 정책이 로그만 남기는 게 아니라 실제 조치를 취하도록 설정되어 있을 때만 유효합니다.

- **정기적인 최소 권한(Least Privilege) IAM 검토.** 역할 할당은 시간이 지나며 계속 쌓이고 좀처럼 회수되지 않습니다. 분기별 Access Review(Entra ID에 기본 기능으로 제공)를 실행하면, 퇴사한 계약직 직원이 여전히 구독(Subscription)에 Contributor 권한을 가지고 있는 경우를 발견할 수 있습니다.

- **CI Pipeline의 Secret Scanning.** "자격 증명 도난"의 상당수는 피싱된 로그인이 아니라 Repository에 커밋된 Token에서 시작됩니다. Secret Scanning(GitHub Advanced Security, GitLab Secret Detection, 또는 Pipeline에 넣는 Gitleaks 등)을 활성화하고, 발견된 Secret은 커밋만 지우지 말고 이미 노출된 것으로 간주해 즉시 Rotation하세요.

- **서비스 계정의 실질적인 Rotation 주기 확립.** 서비스 계정의 자격 증명은 그것이 만들어진 Project보다 오래 살아남는 경우가 많습니다. 목록을 만들고, Owner를 지정하고, "누군가 기억날 때"가 아니라 고정 주기(기준으로 90일)로 Rotation하세요.

## webhani가 클라이언트 프로젝트에서 확인하는 체크리스트

클라이언트의 클라우드 환경을 온보딩할 때 대략 다음 순서로 점검합니다.

1. Global Administrator 및 특권 역할 목록을 뽑아 인사 기록과 대조 확인
2. 서비스 계정과 App Registration을 목록화하고 각각 Owner 지정
3. 특권 계정부터 피싱에 강한 MFA를 먼저 적용한 뒤 범위 확대
4. Sign-in Risk와 Device 준수 상태 기반 Conditional Access 정책 활성화
5. 특권 역할의 Session·Refresh Token 수명 단축
6. CI Pipeline에 Secret Scanning이 없다면 도입
7. 정기적인 Access Review 일정 수립(특권 역할은 최소 분기 1회)

이 중 어느 것도 화려한 작업이 아니고, 보안 벤더의 영업이 필요한 것도 아닙니다. Dependency 업데이트와 같은 성격의 작업입니다. 눈에 띄지 않고 뒤로 미루기 쉽지만, 침해 위험을 낮추는 데 투자 대비 효과가 가장 큰 작업입니다.

## 요약

2026년 8월 중순 공개된 Fortune 500 기업 디렉터리 유출 사건은 Azure에 구멍이 있어서 벌어진 게 아닙니다. 사람과 기계, 양쪽의 자격 증명이 탈취되어 설계된 대로 — 즉 디렉터리 데이터를 읽는 데 — 사용된 결과입니다. 바로 이 지점이 불편한 사실입니다. 이런 유형의 공격을 막는 통제 수단은 새롭지도 비밀스럽지도 않습니다. Conditional Access, 피싱에 강한 MFA, 특권 계정 점검, Pipeline 내 Secret 관리입니다. 이런 캠페인에서 실제 피해를 입는 조직은 대체로 Identity 관련 통제를 "있으면 좋은 것" 정도로만 취급해온 곳들입니다.
