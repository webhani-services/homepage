11월 1일, DeepSeek의 Harness 팀이 coding agent인 Super-agent를 공개했습니다. Bloomberg 등은 Claude Code의 경쟁 제품으로 보도했지만, Repository(`deepseek-ai/dsh-superagent-prototype`)를 직접 보면 성격이 다릅니다. 제품이 아니라 **MIT License의 연구 Prototype**이며, Repository는 10월 31일에 생성되었고 공개 시점의 commit은 1개뿐이었습니다.

그래도 눈여겨볼 이유는 있습니다. 지금까지의 coding agent는 사람이 요청해야 움직였습니다. Super-agent는 개발자 대화를 지켜보다가 고칠 부분을 스스로 찾아내고, 요청받기 전에 수정안을 제시하는 방향을 지향합니다. 이 proactive한 성격 때문에 권한 설계의 전제가 바뀝니다.

## 공개 정보로 확인할 수 있는 내용

Repository와 주요 보도를 대조해 보면 현재 확인 가능한 내용은 다음과 같습니다.

- **범위**: GitHub Repository 하나를 담당하는 proactive agent이며, DeepSeek Harness(DSH)용 bundle로 배포됩니다
- **동작 방식**: 허가된 사용자가 요청하면 work item을 만들고, 전용 agent session과 작업 Directory에서 처리한 뒤 원래 대화에 결과를 회신합니다. 여러 요청은 병렬 worker session으로 분산됩니다
- **설치 요건**: 전용 DSH profile, agent 전용 GitHub 계정, Model Provider 설정, Node.js 22.19 이상, pnpm, git, tmux, Python, GitHub CLI
- **주의 사항**: Dataconomy에 따르면 DeepSeek 스스로 "OS 사용자의 전체 권한으로 동작하므로 사용 전에 격리하라"고 명시했습니다. DSH 자체도 developer preview 단계이며, 호환성을 깨는 변경이 예고되어 있습니다
- **성능**: DeepSeek의 Simulation Test에서 작업 완료 시간 중앙값은 12.4분, 95 percentile은 15.7분으로 보도되었습니다. 실제 환경의 수치가 아니라는 점에 유의해야 합니다

정리하면, session마다 작업 Directory는 나뉘지만 **OS 수준의 Sandbox는 사용자가 직접 준비해야 합니다**. 이 부분을 놓치면 "잠깐 시험해 보려고" 설치한 도구가 개발 장비의 SSH key와 Cloud 자격 증명에 접근할 수 있게 됩니다.

## Proactive Agent에서 달라지는 위험

요청형 agent에서는 사람이 요청하는 순간이 곧 확인 지점이었습니다. Proactive agent에서는 이 지점이 사라집니다.

1. **입력의 신뢰 경계가 넓어집니다.** 채팅 메시지, Issue 본문, CI log 등 agent가 수정의 단서로 읽는 텍스트는 모두 Prompt Injection 경로가 됩니다
2. **실행 시점을 사람이 정하지 못합니다.** 늦은 밤의 대화가 아무도 지켜보지 않는 작업을 시작시킬 수 있습니다
3. **병렬 worker가 피해를 키웁니다.** 동시에 도는 session이 많을수록 잘못된 판단 하나가 퍼지는 범위도 넓어집니다

따라서 Prompt나 설정 파일에 적는 주의 문구가 아니라, **권한·Network·계정 계층에서 제한하는 것**이 기본입니다.

## 평가 환경의 최소 구성

사내에서 평가할 때는 다음 세 겹으로 감싸는 것을 권장합니다.

### 1. 일회용 Container에서 실행

Host의 home Directory를 mount하지 않고, root가 아닌 사용자로 실행합니다.

```dockerfile
# Dockerfile.agent-sandbox
FROM node:22-bookworm-slim

RUN apt-get update && apt-get install -y --no-install-recommends \
      git tmux python3 ca-certificates curl gh \
    && rm -rf /var/lib/apt/lists/* \
    && corepack enable

RUN useradd --create-home --shell /bin/bash agent
USER agent
WORKDIR /home/agent/work
```

```bash
docker build -f Dockerfile.agent-sandbox -t agent-sandbox .

docker run --rm -it \
  --name superagent-eval \
  --network agent-egress \
  --memory 4g --cpus 2 \
  --cap-drop ALL --security-opt no-new-privileges \
  -e GH_TOKEN="$(cat ./secrets/agent-gh-token)" \
  -e MODEL_API_KEY="$(cat ./secrets/model-key)" \
  agent-sandbox bash
```

`agent-egress` Network에는 GitHub와 Model Provider endpoint만 허용하는 egress proxy를 둡니다. 통신할 수 있는 곳이 그 두 곳뿐이면 정보를 외부로 빼돌릴 경로도 대부분 막힙니다.

### 2. Agent 전용 GitHub 계정과 범위를 좁힌 Token

요건에 있는 "agent 전용 계정"은 평가 단계에서 특히 철저히 지켜야 합니다.

- fine-grained personal access token을 대상 Repository 하나로 한정합니다
- 권한은 Contents와 Pull requests의 read/write, Issues의 read 정도로 제한합니다
- 평가가 끝나면 Token을 폐기하고 계정도 정지합니다

### 3. 기본 Branch로의 직접 push 금지

Agent가 무엇을 하든 결과물은 사람이 Review한 Pull Request를 통해서만 `main`에 들어가도록 합니다.

```bash
gh api -X POST repos/your-org/sandbox-repo/rulesets \
  --input - <<'JSON'
{
  "name": "protect-main-from-agents",
  "target": "branch",
  "enforcement": "active",
  "conditions": { "ref_name": { "include": ["~DEFAULT_BRANCH"], "exclude": [] } },
  "rules": [
    { "type": "pull_request", "parameters": {
        "required_approving_review_count": 1,
        "dismiss_stale_reviews_on_push": true,
        "require_code_owner_review": false,
        "require_last_push_approval": true,
        "required_review_thread_resolution": false } },
    { "type": "non_fast_forward" },
    { "type": "deletion" }
  ]
}
JSON
```

`require_last_push_approval`을 켜 두면 승인 후 agent가 추가로 push하더라도 다시 Review를 받기 전에는 merge할 수 없습니다.

## 평가할 때 볼 항목

Demo의 완성도보다 우리 팀 Workflow에 얹을 수 있는지를 확인합니다.

| 항목 | 확인 방법 |
| --- | --- |
| 착수 판단 | 어떤 대화가 계기가 되어 work item이 만들어졌는지 log로 추적할 수 있는가 |
| 오탐률 | 수정할 필요가 없는 부분에 PR을 연 비율 |
| Diff 단위 | PR 하나가 하나의 논점에 머무르는가 |
| 중단 용이성 | 실행 중인 worker를 안전하게 멈출 수 있는가 |
| 비용 | Model 호출 총량이 worker 수에 비례해 늘어나는가 |

Proactive agent에서는 오탐의 비용이 커집니다. 불필요한 PR이 하루에 몇 건씩 쌓이면 Reviewer의 집중력이 떨어지고, 정말 중요한 변경을 놓치기 쉬워집니다.

## webhani의 견해

Super-agent는 agent가 "호출해서 쓰는 도구"에서 "팀에 상주하는 구성원"으로 옮겨 가는 흐름을 보여 주는 시제품입니다. 방향은 흥미롭지만, 지금 단계에서 Production Repository에 넣을 대상은 아닙니다.

시험해 본다면 다음 순서를 권장합니다.

1. 민감 정보가 없는 Sandbox Repository와 전용 계정을 준비합니다
2. Container, egress 제한, Branch 보호의 세 겹으로 감쌉니다
3. 2주 정도 운영하면서 오탐률과 Review 부담을 수치로 기록합니다

지금 Prototype을 만져 보는 가장 큰 의미는, proactive agent가 실용 단계에 들어섰을 때 서두르지 않도록 "사람이 요청하지 않은 실행"을 어떻게 통제할지 미리 정해 두는 데 있다고 봅니다.
