## 아무도 신경 쓰지 않았던 발신 트래픽

Amazon EKS의 Control Plane은 대부분의 운영자가 평소 의식하지 못하는 발신 통신을 항상 만들어냅니다. Admission Webhook Callback, 인증을 위한 OIDC Provider 조회, 그리고 Aggregated API Server로의 요청입니다. 지금까지 이 트래픽은 AWS가 관리하는 경로로 나갔고, 그 자체로는 문제가 없었습니다 — 다만 이 호출들 중 하나의 목적지가 자신이 통제하는 Private한 네트워크 경계 안쪽에 있는 경우는 예외였습니다.

이는 결코 드문 상황이 아닙니다. Admission Webhook Server나 자체 OIDC Provider, 혹은 Aggregated API 확장이 VPC 내부에서만 이름을 해석할 수 있는 경우 — 내부 서비스와만 통신하거나, Private Endpoint 뒤에 있거나, 해당 트래픽을 Public Internet에 노출하지 않으려고 의도적으로 그렇게 설계된 경우 — EKS Control Plane은 단순히 거기에 도달할 수 없었습니다. 많은 팀이 IP Allowlist나 mTLS로 보호한 Public Endpoint를 두는 방식으로 이를 우회해왔지만, 기술적으로는 동작하더라도 규제 산업이나 보안에 민감한 조직이 원하는 "Private Cluster"라는 설계 철학과는 어긋나는 타협이었습니다.

## Customer-Routed Egress가 바꾸는 것

Amazon EKS는 이제 Control Plane의 발신 트래픽을 자신의 VPC를 통해 Routing하는 기능을 지원합니다. 활성화하면 Kubernetes API Server의 발신 통신은 VPC 내에 배치된 ENI(Elastic Network Interface)를 거치고, 그다음부터는 Route Table, Security Group, VPC Endpoint, PrivateLink 연결을 직접 통제할 수 있습니다.

활성화는 설정 하나만 바꾸면 됩니다.

```bash
# Customer-Routed Control Plane Egress를 활성화한 신규 Cluster
aws eks create-cluster \
  --name production-private-cluster \
  --kubernetes-version 1.36 \
  --resources-vpc-config subnetIds=subnet-0abc123,subnet-0def456 \
  --access-config controlPlaneEgressMode=CUSTOMER_ROUTED
```

```bash
# 기존 Cluster에 활성화
aws eks update-cluster-config \
  --name existing-cluster \
  --access-config controlPlaneEgressMode=CUSTOMER_ROUTED
```

이렇게 하면 VPC 내부에서만 이름을 해석할 수 있는 Private OIDC Provider나 Webhook Server에 도달할 수 있게 됩니다. Public Endpoint도, IP Allowlist 우회책도 필요 없이 원래 원했던 "Private Cluster" 설계를 그대로 구현할 수 있습니다.

## 구체적인 사례: Private한 Admission Control

내부 서비스 Metadata를 기반으로 Sidecar 설정을 주입하는 Mutating Admission Webhook을 운영한다고 가정해봅니다. 이 Metadata는 절대 외부 네트워크로 나가서는 안 됩니다.

```yaml
# webhook-config.yaml — CUSTOMER_ROUTED 활성화 후에는 VPC를 통해서만 도달 가능
apiVersion: admissionregistration.k8s.io/v1
kind: MutatingWebhookConfiguration
metadata:
  name: sidecar-injector
webhooks:
  - name: inject.internal.example.com
    clientConfig:
      url: "https://webhook.internal.example.com:8443/mutate"
    rules:
      - apiGroups: [""]
        apiVersions: ["v1"]
        operations: ["CREATE"]
        resources: ["pods"]
    admissionReviewVersions: ["v1"]
    sideEffects: None
```

이 기능이 나오기 전에는 `webhook.internal.example.com`이 AWS 관리 Egress 경로에서 도달 가능해야 했고, 이는 대부분 Public으로 노출한 뒤 엄격한 Access Control을 거는 것을 의미했거나, 애초에 Private Hostname을 쓸 수 없다는 뜻이었습니다. Customer-Routed Egress를 사용하면 Control Plane에서 이 URL로의 호출이 자신의 ENI를 거치므로, Private Hosted Zone을 기준으로 이름을 해석하고 경로 전체가 VPC 내부에서 완결됩니다.

## 어떤 조직이 활성화해야 하는가

이는 기본값으로 켜둘 기능이 아니고, 그래서도 안 됩니다. 특히 다음과 같은 경우에 가치를 발휘합니다.

- **규제 산업**에서 특정 Workload에 대해 Control Plane 트래픽이 AWS 관리 경로를 거치는 것 자체를 금지하는 Data Perimeter 요건이 있는 경우
- **Private한 Identity Provider** — Internet에 노출할 의도가 없는 내부 OIDC Issuer를 운영하는 경우
- **확장 API Server나 Webhook**이 본래는 Private해도 되지만, Control Plane 도달성을 만족시키기 위해서만 Public으로 열려 있던 경우

반대로 Webhook, OIDC Provider, Aggregated API 중 어느 것도 Private하지 않다면, 이 기능은 상응하는 이점 없이 관리 대상(감시해야 할 ENI, 관리해야 할 경로)만 늘리는 셈이 됩니다.

## 활성화 전에 확인할 것

**Route Table의 완결성**: ENI의 트래픽은 VPC의 Route Table을 따라갑니다. Private Hosted Zone이나 PrivateLink Endpoint로 가는 경로가 빠져 있으면, 지금까지 잘 동작하던 Control Plane 호출이 조용히 실패합니다.

**Security Group의 범위**: ENI에는 Control Plane이 실제로 만들어내는 발신 통신을 허용하는 Security Group 규칙이 필요합니다. 일단 동작하게 만들려고 지나치게 넓은 Egress 규칙을 기본값으로 두지 말고, Webhook과 OIDC Provider가 실제로 사용하는 Port와 CIDR로 범위를 좁히세요.

**Hot Path의 Latency**: Admission Webhook은 Pod 생성 경로의 Critical Path에 있습니다. 이 호출을 추가 VPC 인프라를 거치게 하면 Network Hop이 하나 늘어나므로, Cluster 전체에 적용하기 전에 Webhook 응답 시간을 측정해보세요.

## webhani의 견해

이 기능은 내부 Admission Control이나 Identity 기반을 갖춘, 진짜 의미의 Private EKS Cluster를 구축하려는 팀에게 그동안 은근히 골치 아팠던 구멍을 메워줍니다. 모든 팀이 처음부터 필요로 하는 기능은 아니지만, Control Plane 도달성을 만족시키기 위해서만 Public Endpoint와 Allowlist라는 타협을 강요받아온 금융·의료 등 규제 산업의 Client에게는 그 타협 자체를 완전히 없애줍니다. 먼저 Staging 환경의 Webhook으로 검증해볼 것을 권합니다 — Route 설정이 빠졌을 때 나타나는 장애 형태가 "새 Pod를 Admit하지 못하는 것"이기 때문에, Production에서 처음 발견하고 싶지는 않을 종류의 실패입니다.
