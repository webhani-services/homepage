## 되돌릴 수 없던 Upgrade

EKS Cluster를 1년 넘게 운영해본 팀이라면 이 감각을 알 것입니다. 지금 쓰고 있는 Kubernetes Minor Version의 지원 종료(EOL)가 다가오고 있고, Upgrade는 이미 두 번 미뤘고, 이제는 준비가 됐든 안 됐든 이번 Quarter 안에 해야 하는 상황입니다.

지금까지는 Cluster의 Control Plane Version을 한 번 올리고 나면, 공식적으로 지원되는 되돌리기 방법이 없었습니다. 2주 뒤에 뭔가 깨져도 — Deprecate된 API에 의존하던 Workload, 어느 순간 Reconcile을 멈춘 Operator, 정상 Object를 거부하기 시작한 Webhook — 남은 선택지는 앞으로 나가는 것뿐이었습니다. 문제를 우회하는 Patch를 붙이거나, 이전 Version으로 Cluster를 새로 만들어 전부 다시 옮기거나 둘 중 하나였습니다.

Amazon EKS가 이번에 Cluster 재구축 없이 Kubernetes Version을 7일 이내에 Rollback할 수 있는 기능을 지원하기 시작했습니다. 많은 팀이 Infrastructure Calendar에서 가장 긴장되는 작업으로 꼽아온 이 Operation의 Risk 구조가 실질적으로 바뀌는 셈입니다. 다만 정확히 무엇이 안전해지고, 무엇이 여전히 그대로인지는 구분해서 짚어볼 가치가 있습니다.

## Upgrade가 애초에 High Risk였던 이유

Kubernetes Upgrade에서는 성격이 다른 세 가지 Failure Mode가 겹쳐서 발생합니다. 그리고 Rollback 기능이 깔끔하게 해결하는 것은 이 중 하나뿐입니다.

**Control Plane의 API Deprecation·삭제.** 모든 Minor Version은 이전 Release에서 Deprecate 처리됐던 API를 삭제할 수 있습니다. `PodSecurityPolicy`가 유명한 예지만, Version마다 고유한 목록이 있고 batch/v1beta1 CronJob이나 오래된 Ingress API Group 등도 대상이 될 수 있습니다. Helm Chart나 사내 Controller, 서드파티 Operator가 삭제된 API Group을 호출하고 있었다면 Graceful하게 실패하지 않고, 해당 Code Path가 실제로 실행되는 시점에서야 문제가 드러나는 경우가 많습니다.

**CRD와 Webhook 호환성.** Custom Resource Definition과 여기 연결된 Validating/Mutating Webhook은 Cluster 본체와 별도로 Version 관리됩니다. Upgrade로 인해 API Server가 Custom Resource를 Serialize·변환하는 방식이 바뀔 수 있고, 이전 API Server의 동작을 전제로 작성된 Admission Webhook이 이전까지 통과시키던 Object를 거부하기 시작하거나 — 반대로 거부해야 할 Object를 통과시켜버릴 수도 있습니다. 이 Failure 유형은 Staging 환경에서 가장 잡아내기 어렵습니다. 실제 사용 중인 CRD Version, Webhook 설정, Object 형태의 정확한 조합에 따라 동작이 달라지기 때문입니다.

**Data Plane Drift.** Node 쪽 Component(kubelet, Container Runtime, CNI, CSI Driver)는 Control Plane과 약간 다른 주기로 Upgrade되며, kubelet의 특정 동작(Eviction Threshold, cgroup Driver, Device Plugin API)을 전제로 한 Workload는 자기 Manifest가 전혀 바뀌지 않았는데도 동작이 달라질 수 있습니다.

이 세 가지를 합쳐보면, "강제될 때까지 미룬다"가 많은 팀에게 합리적인 전략이 됐던 이유가 보입니다. 실행하지 않은 Upgrade는 아무것도 망가뜨리지 않지만, 실행한 Upgrade는 일방통행 문이었기 때문입니다.

## 7일 Rollback Window가 실제로 바꾸는 것

Rollback Window는 위의 세 Failure Mode 자체를 없애지 않습니다. 바뀌는 것은 그것을 발견했을 때의 비용입니다.

이전에는 Upgrade 3일 뒤에 Control Plane 비호환을 발견하면, "어떻게 하면 알려진 정상 상태로 돌아갈까"에서 시작하는 Incident Response가 됐고, 솔직한 답은 대개 "재구축하고 이전한다"였으며 이는 며칠 단위의 시간이 걸렸습니다.

지금은 같은 발견이 Rollback을 촉발하고, 같은 Cluster Identity와 (호환 가능한 범위에서) 같은 Node Group을 사용하며, 재구축 같은 State 이전 Risk 없이 수분에서 한 시간 정도면 끝납니다.

이 비용 감소는 Upgrade 주기에 대한 Incentive 구조를 구체적으로 바꿉니다. 예전에는 "연간 Risk 발생 건수를 줄이기" 위해 Minor Version을 건너뛰고 두 Version을 한 번에 Upgrade하던 팀도 있었습니다. 지금은 그럴 이유가 줄어듭니다. 실효성 있는 Rollback 안전망이 있는 상태에서 Minor Version을 하나씩, 더 자주 Upgrade하는 쪽이 안전망 없이 두 Version을 한 번에 Upgrade하는 쪽보다 총 Risk가 낮습니다. 또한 Cluster가 지원 대상보다 2~3 Minor Version 뒤처진 채 방치되어 Deprecation Gap이 쌓이고, EOL 압박 아래서 그걸 한 번에 다 해소해야 하는 — 팀이 예상치 못한 문제를 흡수할 여유가 가장 적은 시점에 벌어지는 — 패턴도 줄어듭니다.

Production에서 Inference Workload를 돌리는 Cluster에게는 이 변화가 예전보다 더 중요합니다. CNCF의 2025 Annual Cloud Native Survey에 따르면 Production에서 Kubernetes를 쓰는 사용자 다수가 이미 그 위에서 GenAI Workload를 돌리고 있습니다. Mutating Webhook이 Pod Spec을 거부하기 시작해 Model-serving Deployment가 CrashLoopBackOff에 빠지는 상황은, 동일한 일이 Stateless Web Service에서 벌어지는 것과는 의미가 다릅니다. 대개는 그 Inference Path에 의존하는 Product 기능의 장애를 뜻하고, Dashboard보다 사용자가 먼저 알아차리는 경우가 많습니다.

## Rollback이 해결하지 못하는 것

이 부분은 고객에게도 분명히 짚어줘야 합니다. "이제 Rollback Button이 생겼다"는 사실이, Upgrade를 실제보다 Low Risk로 착각하게 만들 수 있기 때문입니다.

Version Rollback은 어디까지나 Control Plane Version을 되돌리는 것입니다. 다음은 되돌아가지 않습니다.

- **새 Format으로 기록된 Data.** 어떤 Component가 새 Control Plane만 이해할 수 있는 Schema나 API Version으로 etcd 기반 CR, 설정, Cache 등을 저장하기 시작했다면, Control Plane을 되돌려도 그 Data가 소급해서 변환되지는 않습니다. Rollback 이후에도 그 Data를 읽는 쪽은 여전히 걸릴 수 있습니다.
- **이미 적용된 CRD 변경.** Upgrade와 함께 Operator Update에 Bundle된 새 CRD Schema를 적용했다면, 이는 Control Plane Version과 별개인 Cluster State 변경입니다. Control Plane을 Rollback해도 CRD는 되돌아가지 않습니다.
- **이미 전파된 Node 레벨 변경.** 같은 변경 Window에서 Node Group의 AMI나 kubelet Version, CNI/CSI Driver Version을 올렸고 Workload가 이미 새 동작에 적응했거나 그로 인해 깨졌다면, Control Plane Rollback은 그 Layer를 건드리지 않습니다.
- **외부로 나간 부수 효과.** 오작동하던 기간 동안 Controller가 외부 System에 한 일(Cloud Resource 생성, DNS Record 기록, IAM Policy 부여 등)은 그대로 남습니다.

정리하면, Rollback은 Control Plane 호환성이라는 특정 Failure Class에 대한 안전망이지, Upgrade 전체에 대한 범용 Undo Button이 아닙니다.

## 실무 Runbook

다음은 Reversible Rollback이 전제가 된 지금의 현실에 맞춰, Webhani가 고객의 EKS 운영에 권장하는 일련의 흐름입니다. 예전의 "한 번뿐이니 최대한 신중히"라는 전제와는 다릅니다.

**1. Upgrade 전 Compatibility Scan.** 뭔가를 건드리기 전에, 실제로 삭제·Deprecate된 API를 호출하고 있는 대상을 먼저 찾습니다. 표준 `kubectl`만으로도 아래와 같은 Script로 1차 점검이 가능합니다.

```bash
#!/usr/bin/env bash
# pre-upgrade-api-check.sh
# 예시용 점검: 대상 Kubernetes Version에서 API 삭제의 영향을 받을 수 있는
# Custom Resource와 Workload를 나열한다.

TARGET_VERSION="1.31"

echo "== 현재 설치된 CRD =="
kubectl get crds -o custom-columns=NAME:.metadata.name,VERSION:.spec.versions[*].name

echo "== Upgrade 중 Traffic에 관여하는 Admission Webhook =="
kubectl get validatingwebhookconfigurations,mutatingwebhookconfigurations \
  -o custom-columns=NAME:.metadata.name,FAILURE_POLICY:.webhooks[*].failurePolicy

echo "== Deprecate된 API Group을 참조하는 Workload(수동 확인 필요) =="
kubectl get all --all-namespaces -o json \
  | jq -r '.items[] | select(.apiVersion | test("v1beta1|extensions/")) | "\(.metadata.namespace)/\(.kind)/\(.metadata.name): \(.apiVersion)"'

echo "위 결과를 대상 Version ${TARGET_VERSION}의 AWS EKS Deprecation Notes와 대조한 뒤 진행하세요."
```

이걸로 전부 걸러지지는 않습니다. 명백한 Case를 먼저 걸러내는 Filter일 뿐이고, 나머지는 Staging Cluster와 AWS Release Notes로 확인합니다.

**2. Staging Cluster에서 Production 수준의 CRD와 Webhook을 그대로 두고 Upgrade를 시험합니다.** Production 수준의 Workload 개수만으로는 부족합니다.

**3. Upgrade 전에 '알려진 정상 상태'를 Snapshot으로 남깁니다.** 현재 CRD Version, Webhook 설정, Node Group AMI Version을 기록해두면, Rollback 판단을 감이 아니라 명확한 Before/After Diff를 근거로 내릴 수 있습니다.

**4. Control Plane을 Upgrade한 뒤 잠시 멈춥니다.** Node Group Upgrade를 바로 연쇄시키지 않습니다. Control Plane에 의존하는 동작(Admission, API 응답, Controller Reconcile)을 정해둔 Observation Window 동안 지켜본 뒤 Data Plane Component에 손을 댑니다.

**5. Rollback을 실행할 Trigger 조건을 사전에 정의해둡니다.** Incident가 벌어진 도중에 정하는 게 아닙니다. 예를 들어 "Admission Rejection이 원인으로 보이는 CrashLoopBackOff가 하나라도 발생", "Controller Reconcile Error Rate가 Baseline을 15분 이상 초과", "Customer 대상 Latency가 X% 이상 악화" 같은 기준입니다.

**6. CRD와 Node 레벨 변경은 독립적이고 Rollback 불가능한 Step으로 취급합니다.** Control Plane Observation Window 이후로 순서를 나누고, 같은 변경에 묶지 않습니다.

## 정리

7일 Rollback Window는 Upgrade에 따르는 Risk를 실질적으로 낮춰주며, 많은 팀에게 "몰아서 미루기"에서 "작게 자주"로 방향을 바꿀 이유를 줍니다. 다만 이는 Control Plane Version의 Incompatibility라는 특정 Failure Class에 대한 안전망일 뿐, Upgrade 전 Compatibility Check나 Staged Rollout, CRD·Node 레벨 변경의 신중한 Sequencing을 대체하지 않습니다. Runbook은 Rollback이 실제로 커버하는 범위를 기준으로 짜야 하고, Data Migration과 CRD Schema 변경은 지금도 여전히 일방통행 문이라는 전제를 유지해야 합니다.
