Google은 11월 12일 Gemini 4 Hydrogen을 발표했고, Gemini 앱과 Search, 개발자 대상으로 순차 제공하고 있습니다. 보도에서는 일상 용도의 고속 Model로 소개되며, 일부 기사는 Google의 종합 지표에서 상위 Model인 Gemini 4 Argon을 앞선다고 전합니다. 다만 2차 자료마다 Model 이름과 날짜가 엇갈리므로, 정확한 라인업과 가격은 Google 공식 발표에서 확인하시기 바랍니다.

이 글은 기능 소개가 아닙니다. Benchmark 수치가 어떻든, Production에서 LLM 기능을 운영하는 팀의 실무적 질문은 같습니다. **"호출량이 많고 Latency에 민감한 요청을 품질 저하 없이 새 Model로 옮길 수 있는가."** 이 질문에 확실히 답할 수 있는 것은 자사 Traffic으로 만든 Regression Harness뿐입니다.

## 공개 Benchmark로는 답이 나오지 않는 이유

Fast-tier Model은 분류, 추출, 짧은 입력 요약, Routing, 자동완성처럼 호출 빈도가 가장 높은 기능을 맡는 경우가 많습니다. 이런 용도는 Downstream 코드가 출력 형식에 의존하기 때문에, 작은 동작 변화도 크게 영향을 줍니다.

Model 교체 후 자주 나타나는 문제는 다음과 같습니다.

- 항상 유효하던 JSON에 끝부분 주석이나 불필요한 Key가 섞입니다.
- 분류 Label의 분포가 몇 퍼센트 포인트 이동해 비즈니스 지표가 달라집니다.
- 응답 길이가 바뀌어 Token 비용과 UI Layout에 영향을 줍니다.
- 중앙값은 빨라졌지만 고부하 시 Tail Latency가 나빠집니다.

이런 문제는 공개 Benchmark에는 나타나지 않지만, 실제 요청을 재생하는 Harness에서는 확실히 드러납니다.

## Step 1: Production에서 Replay Set 만들기

실제 요청을 Sampling하고 개인정보를 제거한 뒤, 입력과 **현재 Model의 출력**을 저장합니다. 수천 건까지는 필요 없으며, 기능마다 수백 건을 잘 고르면 대부분의 Regression을 잡을 수 있습니다.

Sample은 의도를 가지고 선택합니다.

- 일반 경로를 대표하는 무작위 Case
- 사용자가 출력을 수정하거나 거부한 Case (어려운 Case입니다)
- 빈 입력, 매우 긴 입력, 한국어·일본어·영어가 섞인 입력 같은 Edge Case

```ts
// eval/cases.ts
export type EvalCase = {
  id: string;
  feature: "ticket-triage" | "summary" | "extract-invoice";
  input: string;
  baseline: string; // 현재 Production Model의 출력
  tags: string[];
};
```

## Step 2: Model을 좁은 Interface 뒤에 두기

Model ID가 코드베이스 곳곳에 흩어져 있으면 Model 간 비교에 비용이 많이 듭니다. 작은 Interface 하나를 두고, 구현은 Configuration으로 선택하도록 합니다.

```ts
// llm/client.ts
export interface Completion {
  text: string;
  inputTokens: number;
  outputTokens: number;
  latencyMs: number;
}

export interface LlmClient {
  complete(args: {
    system: string;
    user: string;
    maxOutputTokens: number;
  }): Promise<Completion>;
}

export function createClient(modelId: string): LlmClient {
  // 여기서 Provider SDK 또는 Gateway에 연결합니다.
  // Model ID는 Configuration에서 받으며, 기능 코드에 직접 쓰지 않습니다.
  throw new Error(`not implemented for ${modelId}`);
}
```

AI 제품에서 가장 자주 바뀌는 부분에 Dependency Inversion 원칙을 적용하는 것입니다. 이미 Gateway를 사용 중이라면 생각은 같습니다. Model 이름은 코드가 아니라 데이터로 다룹니다.

## Step 3: 감이 아니라 검사로 Scoring하기

먼저 저렴하고 결정적인 검사를 작성하고, 그것으로 부족한 부분에만 LLM Judge를 추가합니다.

```ts
// eval/score.ts
import { z } from "zod";

const Triage = z.object({
  category: z.enum(["billing", "bug", "feature", "other"]),
  priority: z.number().int().min(1).max(4),
});

export function scoreTriage(output: string, baseline: string) {
  let parsed: z.infer<typeof Triage>;
  try {
    parsed = Triage.parse(JSON.parse(output));
  } catch {
    return { valid: false, sameCategory: false };
  }
  const base = Triage.parse(JSON.parse(baseline));
  return {
    valid: true,
    sameCategory: parsed.category === base.category,
  };
}
```

실행할 때마다 기록해 둘 지표입니다.

| 지표 | 중요한 이유 |
| --- | --- |
| Schema 유효율 | 떨어지면 Downstream 코드가 즉시 깨집니다 |
| Baseline과의 일치율 | 정확도가 아니라 Drift를 측정합니다. 불일치는 직접 확인합니다 |
| p50 / p95 Latency | 사용자가 체감하는 것은 Tail 쪽입니다 |
| 호출당 출력 Token 수 | 비용에 직결됩니다 |
| 거부·빈 출력 비율 | 버전마다 안전성 Tuning이 다릅니다 |

Baseline과의 일치율은 정확도가 아닙니다. 새 Model이 다른 답을 낼 때, 새 Model이 틀렸을 수도 있고 이전 Model의 오류를 바로잡았을 수도 있습니다. 불일치 Sample을 읽어 보는 10분이 이 과정에서 가장 가치 있는 시간입니다.

## Step 4: Flag 뒤에서 Shadow 운영 후 배포하기

Harness 결과가 깨끗해도 실제 Traffic에서만 나타나는 영향은 잡지 못합니다. 위험이 낮은 순서는 다음과 같습니다.

1. **Shadow**: 같은 요청을 두 Model에 보내고, 사용자에게는 이전 Model의 결과만 반환하며 둘 다 Log로 남깁니다.
2. **Canary**: 일부 Traffic만 새 Model로 처리합니다. 사용자나 Tenant의 안정적인 Hash로 분배해 사용자별 동작을 일관되게 유지합니다.
3. **Ramp**: Schema 유효율, Latency, 해당 기능이 영향을 주는 비즈니스 지표를 보면서 단계적으로 늘립니다.
4. **Rollback 유지**: 일주일 치 정상 데이터가 쌓일 때까지 이전 Model ID를 Configuration에 남겨 둡니다.

```ts
function pickModel(userId: string, rolloutPercent: number) {
  const bucket = hash(userId) % 100;
  return bucket < rolloutPercent ? "candidate" : "stable";
}
```

## webhani의 의견

빠른 Model은 분명 유용합니다. Latency가 줄면 체감 품질이 올라가고, Token 단가가 내려가면 이전에는 성립하지 않던 기능이 가능해지기도 합니다. 하지만 Model ID도 다른 Dependency와 같은 Dependency이며, Dependency를 올릴 때는 Test가 필요합니다.

고객사에는 다음 방식을 권장합니다.

- Model ID는 Configuration에 두고 하나의 Interface 뒤에 숨깁니다.
- 기능별로 Replay Set을 유지하고, "사소한" 업데이트를 포함한 모든 Model 변경에서 실행합니다.
- 구조화된 출력의 유효율은 Hard Gate로, 일치율·Latency·비용은 검토 대상으로 다룹니다.
- Harness 결과가 좋아도 Shadow와 Canary 단계를 생략하지 않습니다.

Harness 구축에는 하루 정도가 걸립니다. 평균적으로는 더 좋지만 자사의 가장 중요한 경로에서는 나빠지는 Model을 벤더가 내놓았을 때, 단 한 번으로 본전을 뽑습니다.
