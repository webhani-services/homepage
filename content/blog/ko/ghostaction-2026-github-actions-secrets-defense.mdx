GhostAction은 2025년 9월에 처음 보고되었습니다. GitGuardian은 수백 개의 Repository에 악성 Workflow가 Push되어 Repository Secret이 공격자의 Server로 전송되었다고 밝혔습니다. 보안 연구자들에 따르면 2026년 8월 말부터 9월까지 두 번째 물결이 있었습니다. GitGuardian은 이 기간에 공개 Repository 772개와 Secret 2,577건이 표적이 되었다고 집계했고, 다른 분석 글에서는 새 변종이 Anthropic, OpenAI, OpenRouter 같은 AI Provider의 API Key도 찾는다고 설명합니다. 수치는 출처마다 다르므로 참고용으로만 보시기 바랍니다.

숫자보다 중요한 것은 공격 방식입니다. 단순하고, 앞으로도 재사용될 것입니다. 이 글에서는 동작 방식과 Repository에서 무엇을 바꿔야 하는지 설명합니다.

## 공격은 이렇게 진행됩니다

GitHub Actions 자체의 취약점을 이용하는 것이 아닙니다. 공격자는 Maintainer의 자격 증명을 확보한 뒤 세 가지를 수행합니다.

1. 기존 Workflow 파일이 참조하는 Secret 이름을 나열합니다.
2. 그럴듯한 이름의 새 Workflow를 Push합니다. 2025년 캠페인에서는 "Add GitHub Actions Security workflow" 같은 제목이 사용되었습니다.
3. Workflow가 Push를 Trigger로 실행되어 각 Secret을 이름으로 읽고 외부 Endpoint로 전송합니다.

간과하기 쉬운 부분은 1번입니다. Workflow 파일에는 어떤 Secret이 존재하는지가 그대로 적혀 있습니다. 쓰기 권한만 있으면 값을 보지 않고도 이름을 나열할 수 있습니다. 악성 Workflow는 그 이름을 참조하기만 하면 되고, 값은 GitHub이 실행 시점에 주입해 줍니다.

근본 원인은 탈취된 자격 증명으로 얻은 쓰기 권한입니다. 유출된 Personal Access Token, 침해된 개발자 PC, 디스크의 Token을 읽어 간 악성 Package 등이 진입로가 됩니다. Workflow는 데이터를 빼내는 통로일 뿐입니다.

## 방어 1: Workflow 변경을 검토 대상으로 만들기

쓰기 권한이 있는 계정이 Secret을 쓸 수 있는 Branch에 Workflow를 바로 Push할 수 있다면, Token 하나만 탈취되어도 끝입니다. 이 경로를 막아야 합니다.

- 기본 Branch를 보호하고, 관리자도 포함해 Pull Request 리뷰를 필수로 합니다.
- Workflow Directory에 `CODEOWNERS` 규칙을 추가해 특정 팀의 승인이 필요하도록 합니다.

```text
# .github/CODEOWNERS
/.github/workflows/  @your-org/platform-security
```

참고로 Feature Branch에 Push된 Workflow는 `push` Event에서 해당 Branch의 파일 버전으로 실행됩니다. 다음 방어 수단이 중요한 이유입니다.

## 방어 2: 모든 Branch에 Secret을 주지 않기

Repository 수준 Secret은 Repository 안의 모든 Workflow에서 읽을 수 있습니다. Environment Secret은 접근을 제한할 수 있습니다.

- 운영 자격 증명을 GitHub Environment로 옮깁니다.
- 해당 Environment를 보호된 Branch나 Tag로 제한합니다.
- 해당 Environment로의 Deploy에 Reviewer 승인을 필수로 합니다.

그러면 임의의 Branch에 있는 Workflow는 운영 Secret을 읽을 수 없습니다. 시도하는 순간 승인 단계에서 멈추고, 사람의 눈에 띕니다.

## 방어 3: 장기 Secret을 OIDC로 대체하기

가장 효과적인 방법은 훔칠 가치가 있는 Secret 자체를 줄이는 것입니다. 클라우드 접근에는 OpenID Connect를 사용해, Job이 실행 시점에 수명이 짧은 Token을 자격 증명으로 교환하도록 합니다.

```yaml
permissions:
  id-token: write
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/gha-deploy
          aws-region: ap-northeast-1
```

IAM Role의 Trust Policy는 Repository, Environment, Branch로 범위를 좁히십시오. 다른 Branch나 Fork에서 탈취한 Workflow는 이 Role을 Assume할 수 없습니다. Trust Policy의 세부 사항은 [GitHub Actions OIDC와 AWS](/blog/github-actions-oidc-aws-keyless-2026) 글에서 다루었습니다.

OIDC를 지원하지 않는 외부 API, 현재로서는 대부분의 LLM Provider가 여기에 해당하는데, 이 경우에는 정적 Key를 보유하게 됩니다. 이런 Key를 위험도가 가장 높은 Secret으로 취급하십시오. 프로젝트마다 별도의 Key를 발급하고, Provider 쪽에서 사용 한도를 설정하며, Repository 전체가 아니라 Environment 범위 Secret에 보관합니다.

## 방어 4: Token 권한은 최소에서 시작하기

조직 수준에서 기본 `GITHUB_TOKEN` 권한을 읽기 전용으로 설정하고, 쓰기가 필요한 Job에만 개별적으로 부여합니다.

```yaml
permissions:
  contents: read
```

악성 Workflow가 다른 Secret을 전송하는 것까지 막지는 못하지만, 내장 Token이 유출되었을 때 할 수 있는 일을 제한합니다.

## 방어 5: 외부 송신을 제한하고 감시하기

이 캠페인들의 유출은 단일 주소로 보내는 평문 HTTP였다고 보도되었습니다. Runner의 외부 송신을 제한하면 이것은 차단된 Request와 Alert로 바뀝니다. Self-hosted Runner를 Egress 허용 목록 안쪽에 두면 구현하기 쉽고, GitHub 호스팅 Runner에서도 외부 연결을 기록하는 모니터링 Agent를 사용할 수 있습니다. 자세한 내용은 [GitHub Actions Egress 방화벽](/blog/github-actions-egress-firewall-2026) 글을 참고하십시오.

또한 Push Protection이 포함된 Secret Scanning을 활성화하고, Pull Request를 거치지 않고 생성된 Workflow 파일이 조직 Audit Log에 나타나는지 확인하십시오.

## 악성 Workflow를 발견했다면

Secret을 교체하는 것은 필요하지만 그것만으로는 충분하지 않습니다. GitGuardian은 침해된 GitHub 자격 증명 자체도 폐기하라고 조언합니다. 그렇지 않으면 공격자가 새 Secret에 같은 수법을 반복할 수 있기 때문입니다.

1. 침해된 계정의 Personal Access Token, SSH Key, OAuth App 권한을 폐기하고 Session을 종료합니다.
2. 악성 Workflow를 삭제하고, 모든 Branch에 같은 파일이 남아 있지 않은지 확인합니다.
3. Workflow가 참조한 모든 Secret을 교체합니다. 클라우드와 Package Registry 자격 증명이 최우선입니다.
4. Push부터 정리까지의 기간에 대한 Audit Log와 Provider 쪽 사용 내역을 검토합니다.
5. 관련 Repository의 git 이력을 검색합니다. 일부 변종은 Actions Secret뿐 아니라 이력에 있는 자격 증명까지 훑는다고 보도되었습니다.

## 체크리스트

- 리뷰가 필수인 기본 Branch 보호
- `.github/workflows/`에 대한 `CODEOWNERS`
- Branch 제한과 승인이 걸린 Environment의 운영 Secret
- Repository, Environment, Branch로 범위를 좁힌 클라우드용 OIDC
- 기본값이 읽기 전용인 `GITHUB_TOKEN`
- 사용 한도가 설정된 프로젝트별 LLM API Key
- Push Protection이 켜진 Secret Scanning
- Runner Egress 모니터링

새로운 조언은 하나도 없습니다. 바로 그 점이 핵심입니다. 이런 캠페인은 기본 대책이 일부만 적용된 Repository에서 성공합니다. 위에서부터 순서대로 정비하면, Token 하나를 훔친 공격자가 얻는 가치 대부분을 없앨 수 있습니다.
