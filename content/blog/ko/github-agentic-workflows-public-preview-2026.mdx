GitHub Agentic Workflows가 Public Preview에 도달했습니다. 2026년 2월 Technical Preview로 시작한 지 약 반년 만입니다. 이 기능은 Issue Triage, PR Review, CI 실패 원인 조사, Documentation 업데이트 같은 Repository 운영 작업을 GitHub Actions 위에서 동작하는 Coding Agent에게 맡기는 방식입니다.

## 무엇이 새로운가

가장 눈에 띄는 특징은 복잡한 YAML 대신 Markdown으로 자동화 의도를 작성한다는 점입니다. `.github/workflows/`에 Markdown File을 두면 `gh aw` CLI가 이를 표준 GitHub Actions Workflow로 변환합니다. GitHub Copilot CLI 같은 Coding Agent가 자연어로 작성된 지시를 해석하고 실행하는 구조입니다.

다음은 Issue Triage를 수행하는 Workflow의 개념적인 예시입니다.

```markdown
---
on: issues.opened
permissions: read
---

# Issue Triage

When a new issue is opened:
1. Read the issue title and body
2. Check for related open issues or PRs
3. Suggest appropriate labels based on the repository's label conventions
4. Post a triage comment summarizing the issue and next steps

Do not close or modify existing issues.
```

이 Workflow는 추가 설정 없이 동작하며, Issue가 생성되거나 재오픈될 때마다 내용을 분석하고 관련 Issue를 확인한 뒤 Label을 제안하고 Triage Comment를 자동으로 남깁니다.

## Security 설계가 핵심

Agent에게 Repository 내 작업을 맡기는 이상 가장 큰 우려는 "의도치 않은 쓰기 작업"입니다. GitHub Agentic Workflows는 이를 두 가지 방식으로 통제합니다.

- **기본값이 Read-only 권한** — 명시적으로 허용하지 않는 한 Agent는 Issue나 PR에 쓰기 작업을 할 수 없습니다
- **Safe Outputs라는 사전 승인된 작업만 허용** — Label 부여, Comment 작성처럼 미리 정의된 안전한 작업만 Agent가 실행할 수 있습니다

이 구조 덕분에 "Agent가 실수로 운영 Branch에 Push한다"와 같은 최악의 시나리오를 구조적으로 방지합니다.

## 도입 시 실무적인 접근 순서

webhani가 Client에게 이런 종류의 Agentic CI/CD 기능을 제안할 때는 다음 순서를 권장합니다.

1. **Read-only Workflow부터 시작** — Issue Triage처럼 쓰기 범위가 제한된 것부터 시도합니다
2. **적용 Repository를 한정** — 전사 Repository에 일괄 도입하지 않고, 영향 범위를 파악하기 쉬운 1~2개 Repository에서 먼저 운영 경험을 쌓습니다
3. **초기에는 사람이 Agent 출력을 확인하는 기간을 둠** — Safe Outputs 범위 내라 하더라도, 초반에는 Comment와 Label 내용을 사람이 직접 확인하며 Prompt를 조정합니다

## 정리

GitHub Agentic Workflows는 "CI/CD에 AI Agent를 결합한다"는 큰 흐름 속에서도, Markdown 기반의 선언적 작성 방식과 Safe Outputs를 통한 권한 통제를 동시에 갖췄다는 점에서 실무적으로 완성도가 높은 기능입니다. 다만 아직 Public Preview 단계인 만큼, Read-only이면서 소규모인 Repository에서의 검증부터 시작하는 것이 타당합니다.
