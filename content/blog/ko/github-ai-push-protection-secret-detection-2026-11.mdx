Secret Scanner가 잘하는 일은 형식이 정해진 Token을 알아보는 것입니다. AWS Access Key, GitHub Personal Access Token, Stripe Key 같은 것들입니다. 반면 설정 파일 속 Database Password나 자체 제작 API 인증 정보처럼 형식이 없는 Secret에는 약하고, 유출은 대개 그런 곳에서 일어납니다.

2026년 10월 GitHub는 이 빈틈의 일부를 메우는 움직임을 보였습니다. 10월 28일자 changelog에 AI가 탐지한 Secret에 대한 Push Protection이 Public Preview로 올라왔습니다. 같은 달 앞서 소개된, 유출 Secret 탐지 전용 Model을 기반으로 한 기능입니다. 이 글에서는 공개된 내용과 비용 구조, 팀의 Workflow에 넣는 방법을 정리합니다. 정보는 GitHub changelog와 보도를 바탕으로 하므로, 도입 전에 사용 중인 Plan에서의 제공 여부와 요금을 확인하시기 바랍니다.

## 무엇이 바뀌었나

Push Protection은 그동안 GitHub의 Partner Pattern이나 Custom Pattern과 일치하는 Secret이 포함된 `git push`를 차단해 왔습니다. 이번 확장으로 AI Model이 찾아낸 Secret도 대상이 됩니다. Pattern으로 표현하기 어려운 일반 Password 같은 것을 잡아낼 수 있게 됩니다.

보도된 조건은 다음과 같습니다.

- 대상 Repository에서 Push Protection과 AI 탐지 Secret Scanning이 이미 활성화되어 있어야 합니다.
- github.com에서 GitHub Secret Protection 또는 GitHub Advanced Security를 사용하는 Organization이 대상입니다.
- Public Preview이며, Push Protection에서의 AI 탐지는 AI Credit을 소비하고 Opt-in한 시점부터 과금됩니다. Push 이후 Scan Alert는 추가 비용 없이 포함됩니다.

마지막 항목이 도입 방식에 영향을 줍니다. Pattern 기반 보호와 달리 Push 양에 따라 변동 비용이 발생하므로, 첫날부터 Organization 전체에 켜기보다 의도를 가지고 단계적으로 진행해야 합니다.

## 지금 더 중요해진 이유

1년 전보다 일반 Secret 탐지의 가치가 커진 배경은 두 가지입니다.

첫째, Coding Agent가 설정 파일을 작성합니다. Agent는 `.env.example`, docker-compose Service 정의, Test Fixture를 만들면서 그럴듯한 Password를 채우기도 하고, 볼 수 있는 환경에서 실제 값을 복사해 오기도 합니다. Universe에서 보도된 Octoverse 수치에 따르면 Agent가 여는 Pull Request는 40%를 넘습니다. 기계가 작성하는 Code가 늘수록, 아무도 꼼꼼히 보지 않는 diff에 인증 정보가 섞일 가능성도 커집니다.

둘째, 놓쳤을 때의 비용이 큽니다. Pattern Scanner가 일반 Password를 놓치면, 실제로는 문제가 있는 Repository에 "이상 없음"이라는 결과가 나옵니다.

## 계층적으로 접근합니다

단일 통제로는 충분하지 않습니다. 앞 단계가 놓친 것을 다음 단계가 잡는 3계층 구성을 제안합니다.

### 1계층: 개발자 PC의 pre-commit 스캔

Secret이 git 이력에 들어가기 전에 막는 것이 가장 저렴합니다. 오픈소스 Scanner를 Local Hook으로 쓰면 오프라인에서 동작하고 Credit도 소비하지 않습니다.

```yaml
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.24.2
    hooks:
      - id: gitleaks
```

`rev`는 검증한 Release로 고정하십시오. 위 버전은 예시일 뿐 권장 값이 아닙니다.

### 2계층: Server 측 Push Protection

이번 GitHub 기능이 놓이는 위치입니다. Hook을 거치지 않은 환경, 예를 들어 Agent Sandbox나 CI Bot에서 들어오는 Push를 막는 마지막 방어선입니다. 먼저 Pattern 기반 Push Protection을 넓게 활성화하고, 이후 AI 탐지 옵션을 인프라나 연동 Code처럼 설정 위험이 큰 몇 개 Repository에서 시험하며 Alert 품질과 Credit 소비를 함께 관찰합니다.

### 3계층: Push 이후 Alert와 Rotation

사후 탐지도 가치가 있지만, Push된 Secret에 대한 올바른 대응은 유출된 것으로 간주하는 것뿐입니다. 이력에서 지워도 이미 유출된 사실은 사라지지 않습니다.

REST API로 처리되지 않은 Alert를 조회해 Dashboard나 On-call Queue에 연결할 수 있습니다.

```bash
gh api repos/OWNER/REPO/secret-scanning/alerts \
  --jq '.[] | select(.state == "open") | {number, secret_type, created_at}'
```

여기에 Rotation Runbook을 함께 준비합니다. 누가 교체하는지, Secret이 어디에 있는지, 목표 시간이 15분인지 2시간인지, 이전 값이 무효화되었음을 어떻게 확인하는지를 적어 둡니다.

## Bypass 처리

Push Protection에서는 개발자가 사유("오탐", "Test에서 사용" 등)를 남기고 차단을 우회할 수 있습니다. 누가 이를 검토할지 미리 정하십시오. 최소한 Bypass 이벤트를 보안 Channel로 보내고 주 단위로 확인합니다. "Test에서 사용"이 많다면 Test 쪽을 바꿔야 한다는 신호입니다. `test-password-not-real`처럼 누가 봐도 가짜인 값을 쓰면 사람과 Scanner 모두 구분할 수 있습니다.

## 도입 Checklist

1. Plan에 Secret Protection 또는 Advanced Security가 포함되어 있는지, AI Credit 과금 방식을 이해합니다.
2. Repository Template에 Local Scanner의 pre-commit Hook을 넣습니다.
3. Organization 전체에 Pattern 기반 Push Protection을 활성화합니다.
4. AI 탐지 보호를 2~3개 Repository에서 2주간 시험하고, 차단 수, 오탐, 소비 Credit을 기록합니다.
5. 범위를 넓히기 전에 Rotation Runbook과 Bypass 검토 담당자를 정합니다.
6. Agent 설정을 점검해 가짜 값으로 작업하게 하고, 운영 인증 정보를 환경에 전달하지 않도록 합니다.

마지막 항목이 가장 중요합니다. 탐지기는 Secret이 유출되었을 때의 피해를 줄여 줄 뿐이고, 더 강력한 통제는 Agent와 개발자가 편집하는 Code 가까이에 운영 Secret을 애초에 두지 않는 것입니다.
