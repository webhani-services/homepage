## 비어 있던 확장 지점, Plugin

GitHub는 이번 달 Agent Plugins 1.0을 VS Code, Copilot CLI, Copilot SDK, Copilot app 전반에 걸쳐 모든 Copilot Plan에서 일반 제공했습니다. Plugin은 Awesome Copilot 마켓플레이스에 등록되며, 각 표면에서 기본적으로 활성화되어 제공됩니다. 1.0 Plugin 형식을 대상으로 하지 않는 기존 Copilot 확장 기능도 별도 마이그레이션 없이 계속 동작합니다.

이것만 보면 "마켓플레이스 추가" 정도의 사소한 패키징 변화로 보일 수 있습니다. 주목할 부분은 그 위에 무엇이 쌓이고 있는가입니다 — Model Roster는 Claude Sonnet 4.6·Opus 4.6, GPT-5.4, Gemini 3.1 Pro, Grok Code Fast 1까지 확장되었고, 같은 기간 Gemini 3.7 Flash와 Grok 4.6의 롤아웃도 시작되었습니다. Copilot은 더 이상 단일 Model에 고정된 제품이 아니라, 서로 다른 Model을 등에 업은 서로 다른 Agent가 공통 인터페이스를 통해 연결되는 Runtime이 되어가고 있습니다.

이 차이는 운영 관점에서 중요합니다. Agent Plugins 1.0을 대상으로 만들어진 Plugin은 특정 세션에서 우연히 선택된 Model에 종속되지 않습니다. Tool, Context Provider, Instructions를 한 번 정의해두면, 배후 Model이 Claude든 GPT든 Gemini든 Grok이든 일관되게 호출됩니다. 특정 Model의 특성에 맞춰 Prompt Engineering을 쌓아뒀다가 Model이 조용히 바뀌면서 동작이 나빠진 경험이 있는 팀이라면, 안정적인 Plugin Contract가 더 지속 가능한 투자입니다.

## 기존 Agentic Coding Stack에서의 위치

현재 AI Coding Agent를 운영하는 대부분의 팀은 임시방편의 관례를 쌓아가고 있습니다 — `CLAUDE.md`나 `.cursorrules`, 몇 개의 MCP Server, 커스텀 Slash Command, 세션 시작 전에 Project Context를 주입하는 Wrapper Script 등입니다. 이런 것들은 작동은 하지만 Tool마다 Project마다 개별적으로 존재하며, `.cursorrules`의 내용은 다른 Editor를 쓰는 팀원에게는 전혀 전달되지 않습니다.

Agent Plugins 1.0을 위해 패키징된 Plugin은 좀 더 Portable한 단위에 가깝습니다 — Tool 정의, Context 주입, Instructions를 하나로 묶어 리포지토리 간 복붙이 아니라 마켓플레이스를 통해 배포합니다. 실제로는 다음과 같은 형태가 됩니다.

```jsonc
// .github/copilot/plugin.json (구조 예시)
{
  "name": "webhani-nextjs-conventions",
  "version": "1.0.0",
  "description": "Next.js + TypeScript Repository의 Project 컨벤션",
  "tools": [
    {
      "name": "check_image_optimization",
      "description": "public/images 하위 신규 이미지가 Project Policy대로 압축되었는지 검증"
    }
  ],
  "contextProviders": [
    {
      "name": "component-naming",
      "description": "src/components 편집 시 Area* Component 명명 규칙을 제시"
    }
  ]
}
```

구체적인 Schema는 GitHub의 실제 구현에 따라 달라지겠지만, 중요한 것은 이 형태 자체입니다 — 규약이 Agent가 꼼꼼히 읽어줄지 알 수 없는 Document가 아니라 배포 가능한 Artifact가 됩니다. 모든 것을 하나의 Instructions File에 욱여넣고 Model이 올바른 섹션에 주의를 기울여주기를 바라는 것보다 확실한 개선입니다.

## 더 본질적인 변화는 Multi-Model Roster

Plugin 형식도 유용하지만, Agentic Coding에서 Vendor Lock-in을 바라보는 방식을 바꾸는 것은 Model Roster의 확장입니다. 반년 전만 해도 AI Coding Tool을 선택하는 것은 암묵적으로 Model을 선택하는 것이었습니다. 지금 Copilot의 Roster는 4개 Lab의 Frontier Model을 포함하며, 계속 Rolling 방식으로 추가되고 있습니다(Kimi K3와 MAI-Code-1.1-Flash도 최근 Release Notes에 등장했습니다).

Engineering Lead 입장에서 이는 평가 질문 자체를 바꿉니다. 더 이상 "어느 Coding Assistant의 Model이 가장 뛰어난가"가 아닙니다 — Model 품질 격차는 월 단위로 좁혀지고 뒤바뀌며, 어떤 Lab도 모든 Task 유형에서 지속적인 우위를 유지하지 못합니다. 더 본질적인 질문은 "Tooling을 다시 짜지 않고도 Model을 바꿀 수 있는 Platform은 어디인가"입니다. GitHub 자체 생태계로의 Lock-in 장치가 아니라면, Plugin Architecture가 이 질문에 대한 답이 됩니다.

## Client에게 권하는 것

이미 Claude Code나 Cursor 등 단일 Vendor의 Agentic Workflow에 투자한 팀에게 Agent Plugins 1.0이 갈아탈 이유가 되지는 않습니다 — 근본적인 Model 품질이 여전히 대부분의 일을 해내고 있고, 전환 비용도 현실적으로 존재합니다. 하지만 팀의 AI Coding 관례가 얼마나 Portable하고 Versioned된 Artifact로 존재하는지, 아니면 하나의 Tool에서만 동작하는 Instructions File 더미로 남아 있는지를 점검할 이유는 됩니다.

구체적으로 제안하는 것은 두 가지입니다.

1. **공유 관례를 특정 Editor에 종속되지 않는 형식으로 추출하세요.** `CLAUDE.md` 등이 Project 고유의 사실을 넘어 "여기서 TypeScript를 작성하는 방식" 같은 일반적인 지침으로 비대해졌다면, 그 내용은 어느 Vendor의 Plugin 형식이 결국 표준이 되든 Plugin 후보입니다.
2. **Model 전환 비용을 명시적인 지표로 추적하세요.** 다음에 Coding Agent를 평가할 때, Model을 바꾸는 데 Prompt/Tool 정의를 얼마나 다시 작업해야 하는지 확인하세요. "Portable한 Plugin에 모두 정의되어 있어서 필요 없다"는 답이 나온다면, 그것은 현재 Benchmark 1위 Model이 무엇이든 상관없는 독립적인 강점입니다.

Agentic Coding landscape는 Tool 접근을 위한 Model Context Protocol과, 이제는 관례 패키징을 위한 Plugin 형식이라는 소수의 상호운용성 표준으로 수렴하고 있습니다. 지속 가능한 사내 Tooling을 구축하는 팀이라면, 특정 Vendor의 현재 Model 라인업이 아니라 이런 표준에 베팅하는 편이 더 방어력 있는 선택입니다.
