AI Coding Tool에서 "어떤 Model을 쓸지" 결정하는 일은 대개 Dropdown 하나로 끝납니다. 정형화된 작업에는 저렴하고 빠른 Model을, 막힐 때는 비싸고 강력한 Model을 쓰는 식입니다. GitHub의 Project HydraFusion은 Copilot CLI에서 Research Preview 단계로 제공되는 기능인데, 이 전제 자체를 다른 질문으로 바꿉니다. Session 단위로 Model을 고르는 대신, Task마다 *실행 Pattern*을 고르고 한 번의 Turn 안에서 여러 Model을 함께 사용합니다.

## 핵심 아이디어: Model 하나가 아니라 세 가지 Pattern

HydraFusion은 Copilot CLI의 `/experimental` 설정에서 다른 Model과 똑같이 선택할 수 있습니다. 다만 내부적으로는 Task마다 다음 세 Pattern 중 무엇을 실행할지 판단합니다.

- **Single** — 선택된 Model 하나가 Task를 직접 해결합니다. Orchestration Overhead가 없으며, 추론 깊이나 Tool 사용 복잡도 같은 Capability Signal이 단일 Model만으로 충분하다고 판단될 때 사용됩니다
- **Cascade** — 저렴하고 효율적인 Model이 먼저 초안을 작성합니다. 이후 Quality Gate가 이 초안을 채택할지, 더 강력한 Model로 Escalation할지 결정합니다. 대부분의 단순한 Refactoring이나 정형 작업은 이 저렴한 단계에서 해결됩니다
- **Critique** — 한 Model이 초안을 작성하면, *다른 Model Family*에 속한 두 번째 Model이 읽기 전용 Critic으로 검토하고, 원래 Model이 이 Critique를 반영해 한 번 수정합니다

아키텍처적으로 흥미로운 부분은 Critique Pattern입니다. 같은 Family의 더 큰 Model이 아니라 굳이 다른 Family의 Model을 Critic으로 쓰는 것은, 단일 Model의 Blind Spot에 대한 의도적인 대비책입니다. 같은 학습 계통의 Model끼리는 실패 Pattern도 비슷하게 공유하는 경향이 있지만, 진짜 다른 Model이라면 첫 번째 Model이 자신 있게 틀린 부분을 잡아낼 가능성이 더 높아집니다.

## 실제 사용 모습

```bash
# 고정 Model 대신 HydraFusion을 선택합니다
copilot config set model hydrafusion --experimental

# 정형적인 Task는 Single이나 저렴한 Cascade 초안으로 해결될 가능성이 높습니다
copilot "이 Module 전체에서 변수명을 바꾸고 JSDoc도 업데이트해줘"

# 요구사항이 모호한 Task는 Critique를 Trigger하기 쉽습니다
copilot "기존 Route를 깨지 않으면서 JWT와 Session Cookie를 모두 지원하도록 이 인증 Middleware를 Refactoring해줘"
```

어떤 Pattern이 실행될지는 직접 고르지 않습니다. HydraFusion의 Routing Model이 Prompt에서 Capability Signal(추론 깊이 추정, Code 생성 복잡도, Debugging인지 작성인지, Tool 사용 필요 여부 등)을 읽어, 성능·비용·지연 시간의 균형을 최적화하는 Workflow를 선택합니다.

## 주목할 만한 수치

GitHub 내부 CheckpointBench 기준으로, HydraFusion은 최상위 Frontier Model 단독 성능과 비교해 0.1%p 차이까지 근접하면서도 비용은 약 65% 낮습니다. 이 정도 격차라면, 대부분의 일상적인 Coding 작업에서 단순한 Task를 저렴한 Model로 Routing하고 필요할 때만 Escalation하는 데서 오는 비용 절감이, 가끔 Model 두 개를 쓰는 데서 오는 지연 시간 비용을 상쇄하고도 남습니다.

다만 이 수치가 보여주지 않는 Trade-off도 있습니다. Cascade와 Critique 모두 같은 최상위 Model에 대한 Single 호출보다 지연 시간이 늘어납니다. Escalation되는 Task에서는 초안 작성 후 검토라는 왕복 비용을 추가로 치르기 때문입니다. Inline Completion처럼 지연 시간에 민감한 대화형 사용에서는 이 Overhead가 실질적인 비용이지만, 지연 시간보다 비용 대비 출력 품질이 중요한 자율 Background Task에서는 거의 무시할 수 있는 수준입니다.

## 수동 Model 전환과의 차이

대부분의 Engineer는 이미 이와 비슷한 일을 수동으로 하고 있습니다. 빠른 Model로 시작했다가 명백히 막히면 강력한 Model로 바꾸는 방식입니다. HydraFusion의 가치는 이 Escalation 판단이 나쁜 답을 실제로 본 *뒤*가 아니라 Task Signal을 근거로 *사전에* 이루어진다는 점입니다. 나쁜 답을 보고 나서 한 번의 왕복을 낭비하는 일이 없어집니다. Critique Pattern은 한 걸음 더 나아갑니다. 대부분의 Engineer는 이미 해결된 Task를 일부러 다른 Model Family로 다시 검증하는 습관이 없지만, 사실 그것이야말로 Review에 도달하기 전에 미묘한 버그를 잡아내는 종류의 Check입니다.

## webhani의 의견

아직 Research Preview 단계이며, 주의해서 지켜봐야 할 실패 유형은 Critique를 Trigger할 만큼 모호하지만 실제로는 Critique가 필요할 만큼 복잡하지는 않은 Task에서 발생하는 Routing Overhead입니다. 단일 유능한 Model이 이미 정답을 맞혔을 Task에 대해 두 번째 Model의 의견을 위한 비용을 추가로 지불하게 되는 경우입니다. 지연 시간에 민감한 Workflow의 기본값으로 추천하기 전에, Routing 판단에 대한 Telemetry를 먼저 확인해보고 싶습니다.

반면 자동 Refactoring, 의존성 Upgrade, Script화된 Migration처럼 1초 미만의 대화형 응답이 필요 없고 Model 선택에 신경 쓰지 않고도 정확한 답을 얻는 것이 중요한 Batch·CI 기반 Coding Task라면 지금 시도해볼 가치가 있습니다. 항상 최상위 Model을 쓰는 것에 근접한 품질을 그 일부 비용으로 얻을 수 있다는 비용 구조는, 즉각적인 대화형 응답이 필요 없는 모든 용도에 합리적인 기본값이 될 수 있습니다.
