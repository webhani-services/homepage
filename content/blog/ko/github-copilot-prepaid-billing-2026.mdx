GitHub는 2026년 4월 22일, Usage-based Billing 전환 준비의 일환으로 Copilot Business 및 Copilot Enterprise의 Self-serve 신규 신청을 일시 중단했습니다. 2026년 9월 1일, Credit Card 또는 PayPal로 결제하는 고객을 대상으로 신청이 재개되었습니다. 다만 예산 관리 관점에서 진짜 중요한 것은 재개 자체가 아니라 그에 딸려온 규칙 변경입니다. 이제 모든 신규 Seat 할당은 User의 Access 부여 전에 선결제(Upfront)를 요구하며, 2026년 10월 1일부터는 기존 Card/PayPal 고객도 동일한 선결제·Cycle 단위 Billing Model로 전환됩니다.

여러 개의 Copilot Seat를 관리하는 조직이라면, 이는 단순한 가격표 각주가 아니라 조달 프로세스와 사내 승인 프로세스의 변경입니다. webhani는 Client에게 실제로 무엇을 해야 하는지 정리해서 안내하고 있습니다.

## 구조적으로 무엇이 바뀌는가

기존 Model에서는 Admin이 신규 입사자나 Contractor에게 즉시 Seat를 할당할 수 있었고, Billing은 Cycle 말에 사용량을 반영했습니다. 새 Model에서는 Seat 할당과 결제가 결합됩니다. 결제가 완료되어야만 Seat가 활성화됩니다. 표준 Onboarding Checklist의 일부로 Copilot Access를 Provisioning하는 Team이라면, 기존에 없던 Dependency가 생깁니다. Seat를 할당하는 Onboarding Automation은 이제 즉시 활성화를 전제할 수 없고, 실패하거나 지연될 수 있는 결제 Step을 반영해야 합니다.

```text
기존 Flow:
  Admin이 Seat 할당 → User는 즉시 Access 획득 →
  Billing Cycle 말에 사용량이 Invoice에 반영

새 Flow (2026년 10월 1일부터):
  Admin이 Seat 할당 → 결제가 Upfront로 청구 →
  결제 완료 → User에게 Access 부여
```

GitHub API를 통해 Copilot Seat를 Provisioning하는 Script나 Terraform 관리 Process가 있다면, 다음 채용 Batch 전에 Sandbox Org에서 한 번 Test해보는 것이 좋습니다. 결제가 조용히 실패하는 경우, 이제는 나중에 정리하면 되는 Billing 불일치가 아니라 Developer의 작업을 막는 문제가 됩니다.

## 예산 측면의 영향: Seat가 Prepaid Commitment로 바뀐다

선결제·Cycle 단위 Billing은 예산 안에서 Copilot이 보이는 방식을 바꿉니다. Cycle 중간의 실제 Seat 사용량에 따라 늘었다 줄었다 하는 변동비성 월간 항목이 아니라, 각 Cycle 시작 시점에 Seat 수를 Commit하는 방식이 됩니다. Cycle 도중 퇴사자의 Seat를 Deprovisioning해도 해당 Cycle의 청구액은 환불되지 않습니다. 이는 대부분의 Prepaid Seat형 SaaS와 동일한 방식입니다(Slack, Zoom 등 유사한 Per-seat SaaS Tool들은 이미 이런 방식으로 Billing하고 있으므로, 이를 처리할 운영 역량은 이미 Finance Team에 갖춰져 있을 가능성이 높고, 보통 부족한 것은 Finance의 능력이 아니라 IT와 Finance 간의 Communication입니다).

Client에게는 Copilot Seat 수를 다른 Prepaid Seat형 SaaS와 동일하게 취급하도록 권장합니다. 즉, 누군가 Invoice 불일치를 알아차린 뒤 대응하는 것이 아니라 매달 정기적으로 재직 중인 Headcount와 대조하는 것입니다.

```yaml
# 예시: 월간 Seat 대조 Checklist
copilot_seat_audit:
  frequency: monthly
  steps:
    - compare_active_seats_to: hris_active_employee_list
    - flag: seats_assigned_to_terminated_accounts
    - flag: seats_unused_in_last_30_days  # 회수 후보
    - action: deprovision_before_next_billing_cycle_start
```

마지막 줄이 가장 중요합니다. 청구가 선결제·Cycle 단위이기 때문에, 실제로 비용을 절감하는 것은 Cycle 도중이 아니라 Cycle 시작 전 Deprovisioning입니다. 30일 Cycle의 15일째에 Seat를 삭제해도 해당 Cycle의 전체 금액은 이미 청구된 상태입니다.

## 중단 기간 동안 기다리고 있었다면

4월부터의 Self-serve 신청 중단 때문에 Copilot Business/Enterprise 도입을 미뤄왔던 조직이라면, 9월 1일 재개로 그 장애물은 사라집니다. 다만 Seat가 더 이상 저마찰로 수시 조정 가능한 자원이 아니게 된 만큼, 대규모로 Onboarding하기 전에 Seat 할당 Model을 먼저 정해두기를 권장합니다. 구체적으로는 다음을 미리 결정합니다.

- 어떤 Role이 상시 Copilot Access를 갖고, 어떤 Role이 Project 단위로 Provisioning되는지
- 월간 대조 작업을 누가 담당하는지(보통 Engineering Manager가 아니라 HRIS Feed를 받는 IT 부서)
- 재직 기간과 무관하게 동일한 Prepaid Cost가 발생하는 만큼, Contractor나 임시 Seat에 정규직 Seat보다 더 짧은 내부 Review Cycle을 둘 것인지

## 정리

- 2026년 10월 1일부터 GitHub Copilot Business/Enterprise Seat는 Cycle 단위로 선결제됩니다. Cycle 도중 Deprovisioning해도 해당 Cycle 비용은 환불되지 않으므로, Seat 정리 시점이 비용에 직접 영향을 미칩니다.
- Seat Provisioning이 자동화되어 있다면, 실제 Onboarding에 사용하기 전에 결제→Access 부여라는 Dependency를 Sandbox에서 Test해보세요. 결제 실패는 이제 미래의 Invoice 문제가 아니라 Developer의 작업을 막는 문제입니다.
- 재직 중인 Headcount List에 대한 월간 Seat 대조를 지금 마련해두세요. 이는 대부분의 Team이 다른 Prepaid Seat형 SaaS Tool에서 이미 사용 중인 것과 같은 운영 Pattern입니다.
