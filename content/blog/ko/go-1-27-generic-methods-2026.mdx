## Generics가 남겨둔 공백

2022년 Go 1.18이 Generics를 도입했을 때, 구체적인 타입을 중심으로 Generic API를 설계해본 사람이라면 누구나 알아챈 제약이 있었습니다 — Method는 스스로 Type Parameter를 선언할 수 없었습니다. Package 범위에서는 Generic 함수를 작성할 수 있었지만, 어떤 타입의 Method를 다른 타입에 대해 Generic하게 만들고 싶다면 Free Function으로 작성할 수밖에 없었고, Method 문법의 편의성을 잃어야 했습니다.

이번 달 출시된 Go 1.27은 이 공백을 메웁니다. Method는 이제 Receiver 타입 자체가 가진 Type Parameter와는 독립적으로, 자신만의 Type Parameter를 선언할 수 있습니다. 이전에는 어떤 타입에 논리적으로 속하는 연산 — Container를 map하거나, 서로 다른 두 Parameterized 타입 사이를 변환하거나, Element 타입이 다른 두 인스턴스를 결합하는 등 — 은 Package 수준 함수로 작성할 수밖에 없었습니다. 언어가 그 외에는 둘 곳을 제공하지 않았기 때문입니다.

```go
type Container[T any] struct {
    items []T
}

// Go 1.27: Method가 자신만의 Type Parameter U를 선언.
// Container의 T와는 독립적
func (c Container[T]) MapTo[U any](f func(T) U) Container[U] {
    out := make([]U, len(c.items))
    for i, v := range c.items {
        out[i] = f(v)
    }
    return Container[U]{items: out}
}
```

1.27 이전에는 `MapContainer[T, U any](c Container[T], f func(T) U) Container[U]`처럼 독립적인 함수로 작성할 수밖에 없었습니다. 동작은 하지만 Method Chaining이 깨지고, 연산이 타입 자체의 Namespace 밖에 놓이게 됩니다. Collection 타입이나 Result/Option Wrapper, 함수형 스타일의 Generic Pipeline 추상화를 작성해온 Library 저자에게 이는 단순한 문법 설탕이 아니라 의미 있는 사용성 개선입니다.

## 여전히 남아 있는 경계

Go의 Generics는 의도적으로 보수적인 설계를 유지하고 있습니다. Interface는 여전히 Type-Parameterized Method를 선언할 수 없고, Generic Method로 Interface를 만족시킬 수도 없습니다. 즉 "Generic한 `Map` Method를 가진 임의의 타입" 같은 것을 Interface 제약으로 표현하는 것은 여전히 불가능합니다. Go 팀은 그 문을 계속 닫아두고 있는데, 아마도 Interface 수준에서의 Parametric Polymorphism이 가져오는 복잡성 폭발(Scala나 Haskell 같은 언어가 실제 비용을 치르며 다루고 있는 영역)을 피하기 위해서일 것입니다.

대부분의 Backend·Web Service 코드에서는 이 경계를 직접 체감할 일이 많지 않을 것입니다. 더 큰 영향을 받는 쪽은 Generic Data Structure나 함수형 스타일의 Utility Package를 만드는 Library 저자들로, 기존 제약이 어색한 우회책을 강요했던 영역입니다.

## 이번 릴리스의 나머지 부분

Generic Methods가 핵심이지만, Go 1.27에는 실제 서비스에서 Go를 운영하는 팀이 눈여겨볼 만한 다른 변경 사항도 여러 개 담겼습니다.

**새로운 `encoding/json/v2` 구현**이 표준 라이브러리의 일부로 도입되어, 기존 `encoding/json` Package에 오랫동안 제기되어온 Performance 및 정확성 관련 불만 — 특히 대용량 Payload의 Streaming과 숫자 정밀도 처리 — 을 다룹니다.

**크기 특화 메모리 Allocation**으로 80 Byte 미만 Object의 Allocation 비용이 최대 30% 줄어든다고 Release Notes에 명시되어 있습니다. JSON을 많이 다루는 API나 고처리량 Proxy처럼 Allocation이 많은 Service라면 코드 변경 없이도 얻는 의미 있는 개선입니다.

**Goroutine Leak Profiling**이 Runtime의 Profiling Tool에 내장되었습니다. Channel이 닫히지 않거나 Context가 취소되지 않아 조용히 쌓이는 Goroutine이라는, 발견하기 까다로웠던 유형의 버그를 서드파티 Leak Detector 없이도 표준 `pprof` 출력으로 확인할 수 있게 되었습니다.

**표준 라이브러리 `uuid` Package**로, Go Service에서 가장 흔하게 Vendor되어온 Utility 중 하나에 대한 서드파티 의존성이 사라집니다.

**실험적인 `simd` Package**는 가능한 경우 하드웨어 Vector 명령어를 사용하는, Portable하고 Vector 크기에 구애받지 않는 SIMD 연산을 제공합니다. 기존에는 cgo나 Vendor 전용 어셈블리가 필요했던 수치 연산 중심 Workload(이미지 처리, Embedding, Data Pipeline)에 유용합니다.

**더 유연해진 Struct 리터럴 문법**으로 Nested되거나 Embedded된 Struct의 필드를 직접 초기화할 수 있게 되어, 깊게 중첩된 설정용 Struct의 Boilerplate가 줄어듭니다.

## 실무적 결론

이번 변경들이 Go의 근본적인 성격을 바꾸지는 않습니다 — Go는 여전히 보수적이고 명시적인 언어로, 기능을 천천히 추가하며 한 번 내놓은 설계 판단을 다시 뒤집는 일이 거의 없습니다. Generic Methods는 그 원칙을 증명하는 예외입니다 — 2022년 Generics 출시 당시 확인된 공백이, 4년간의 실제 운영 경험을 통해 Trade-off가 명확해진 뒤에야 메워졌습니다.

새 Backend Service에 Go를 검토하는 팀이라면 이번 변경 사항만으로 판단이 바뀌어서는 안 됩니다 — 언어의 핵심 가치 제안(빠른 Compile, 단순한 Deploy, 강력한 표준 라이브러리, 예측 가능한 Performance)은 그대로입니다. 하지만 이미 Go를 프로덕션에서 운영 중인 팀이라면 `json/v2` Package와 Goroutine Leak Profiling은 기존 Service에 적용해볼 가치가 있습니다. 둘 다 Architecture 변경 없이, Go Version을 올리는 것(그리고 `json/v2`의 경우 명시적 Opt-in)만으로 실제 운영상의 문제를 다룰 수 있습니다.
