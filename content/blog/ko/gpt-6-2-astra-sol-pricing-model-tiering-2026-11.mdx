OpenAI는 2026년 11월 17일 GPT-6.2 Astra와 GPT-6.2 Sol을 공개했습니다. 엔지니어에게 중요한 부분은 Benchmark보다 가격 구조입니다. 어떤 요청을 어떤 Model에 맡길지에 대한 설계 판단이 달라지기 때문입니다.

먼저 정보 출처에 대해 말씀드립니다. 아래 수치는 언론 보도와 Aggregator 사이트에서 가져온 것이며, OpenAI 공식 가격 페이지(영어판)는 직접 확인하지 못했습니다. Benchmark 주장도 OpenAI 자체 발표입니다. 예산을 바꾸기 전에 반드시 공식 페이지에서 수치를 확인하시기 바랍니다.

## 보도된 내용

- `gpt-6.2-astra`: 장시간 전문 업무용 상위 Model입니다. 입력 약 $8 / 출력 약 $40(100만 Token 기준)이며, GPT-6 Astra보다 약 20% 저렴하다고 보도되었습니다.
- `gpt-6.2-sol`: 일상 업무용 저가 Model입니다. 입력 약 $2 / 출력 약 $10으로 GPT-6.1 Sol과 동일합니다.
- Cache 입력은 Astra 약 $0.40, Sol 약 $0.10이고, Batch 처리는 표준 가격의 절반으로 알려져 있습니다.
- 입력이 약 27만 2천 Token을 넘는 Prompt에는 할증이 붙는다는 보도가 있습니다(입력·Cache 2배, 출력 1.5배).
- Context Window는 약 105만 Token이며 Responses와 Chat Completions API 모두에서 사용할 수 있습니다.

한 보고서는 Sol이 Coding Benchmark에서 Astra와 거의 같은 점수를 약 5분의 1 비용으로 낸다고 전합니다. 다만 이는 자사 Workload로 검증해야 할 가설이지, 사실로 받아들일 내용은 아닙니다.

## 할인율보다 가격 차이가 중요한 이유

같은 계열 Model 사이에 4배 가격 차이가 있으면 "항상 최상위 Model 사용"은 비싼 기본값이 되고, "항상 저가 Model 사용"은 품질 리스크가 됩니다. 물어야 할 질문은 "요청 유형별로 정답 1건을 얻는 데 드는 비용이 얼마인가"입니다.

```text
Task당 비용 = (입력 Token × 입력 단가 + 출력 Token × 출력 단가) / 합격률
```

어떤 Task에서 Sol의 합격률이 90%, Astra가 96%라면 Astra 가격이 약 1.07배 이내여야 이득입니다. 4배 가격에서는 이득이 아닙니다. 반대로 Sol 합격률이 60%까지 떨어지는 어려운 Task에서는 재시도 비용까지 포함하면 결론이 뒤집힙니다. 이는 Task 유형별로 측정해야만 알 수 있습니다.

## 긴 Prompt Guard를 둔 간단한 Router

놓치기 쉬운 부분이 할증 기준선입니다. Agent Loop가 Tool 출력을 계속 덧붙이면 아무도 모르는 사이에 27만 2천 Token을 넘길 수 있습니다. Router에서 이 경계를 명시적으로 다루는 편이 좋습니다.

```typescript
import OpenAI from "openai";

const client = new OpenAI();

type Tier = "sol" | "astra";

const LONG_PROMPT_THRESHOLD = 272_000;

// 대략적인 추정: 영어 기준 약 4자 = 1 Token.
// 기준선에 가까울 때는 실제 Tokenizer로 교체하세요.
function estimateTokens(text: string): number {
  return Math.ceil(text.length / 4);
}

function pickTier(task: { kind: string; input: string }): Tier {
  // Task 유형은 예시입니다. 자사 Eval 결과로 정하세요.
  const hardKinds = new Set(["multi-file-refactor", "incident-analysis"]);
  return hardKinds.has(task.kind) ? "astra" : "sol";
}

export async function run(task: { kind: string; input: string }) {
  const tokens = estimateTokens(task.input);
  if (tokens > LONG_PROMPT_THRESHOLD * 0.9) {
    // 할증 요금을 모르고 내지 않도록, 먼저 요약하거나 분할합니다.
    throw new Error(
      `Prompt ~${tokens} tokens is near the long-prompt threshold; compact it first`,
    );
  }

  const tier = pickTier(task);
  const response = await client.responses.create({
    model: tier === "astra" ? "gpt-6.2-astra" : "gpt-6.2-sol",
    input: task.input,
  });

  console.info(JSON.stringify({ tier, kind: task.kind, usage: response.usage }));
  return response.output_text;
}
```

`throw`는 의도적입니다. Batch나 Background 작업에서는 청구서에서 할증을 발견하는 것보다 빨리 실패하고 Context를 압축하는 편이 안전합니다. 대화형 용도에서는 자동 요약 후 계속 진행할 수도 있지만, 그 판단은 우연이 아니라 코드에 드러나야 합니다.

## 도입 순서

1. **Eval을 먼저 만듭니다**: 로그에서 Task 유형별로 실제 요청 50~100건을 뽑고, 신뢰할 수 있는 합격/불합격 판정을 붙입니다. 이것이 없으면 Tiering은 추측에 불과합니다.
2. **같은 Dataset으로 두 Tier를 실행합니다**: 합격률, 입출력 Token, Latency를 기록하고 호출당 비용이 아니라 "정답 1건당 비용"을 계산합니다.
3. **기본은 Sol, 근거가 있을 때만 Astra로 올립니다**: 합격률 차이가 4배 가격을 정당화하는 Task만 Astra로 보냅니다. 저렴한 검증 Step에서 실패한 건만 Astra로 재투입하는 방식이 전부 Astra로 보내는 것보다 대체로 쌉니다.
4. **Cache와 Batch를 활용합니다**: 고정된 System Prompt는 Cache 입력 단가의 혜택을 받습니다. 즉시 응답이 필요 없는 야간 요약·분류 등은 Batch 후보입니다.
5. **모든 호출에 tier를 기록합니다**: 관찰할 수 없는 Router는 조정할 수 없습니다. 위의 `console.info`가 최소한입니다.

## 주의할 점

OpenAI는 두 Model이 자사 "Critical" 사이버 보안 기준에 해당한다고 설명하며, 위험도가 높은 보안 관련 요청에는 더 엄격한 안전 장치가 적용된다고 보도되었습니다. 취약점 Triage 같은 보안 용도에서는 이전보다 거부나 제약이 늘 수 있으므로 해당 경로를 별도로 Test하시기 바랍니다.

또한 직전 Point Release 이후 7주 만에 이번 Release가 나왔다는 보도가 있습니다. Model 이름을 여러 곳에 Hard Code했다면 한 곳으로 모아 두는 것이 다음 전환에 유리합니다.

## 정리

Astra 가격 인하도 반갑지만, 더 오래 영향을 미칠 변화는 Astra와 Sol의 가격 차이입니다. Task 유형별로 "정답당 비용"을 측정하고, 근거에 따라 Routing하며, 긴 Prompt 할증에 Guard를 두는 세 가지를 권장합니다. 공식 가격 페이지에서 수치를 확인한 뒤 적용하시기 바랍니다.
