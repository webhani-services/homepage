OpenAI가 2026년 9월 3일 GPT-6 Astra를 출시했습니다. GPT-5 계열의 Point Release가 아니라 정식으로 Major Version을 올린 릴리스입니다. Texas Datacenter에서 10만 개 이상의 GPU를 사용한, OpenAI 역사상 최대 규모의 Training Run이었다고 합니다. 성능 향상은 Computer Use와 Software Engineering 영역에 집중되어 있습니다.

webhani 같은 Consulting Team 입장에서 새 Frontier Model 출시는 "전부 갈아탈 이유"가 되지 않습니다. 오히려 Agent Stack의 Routing Logic을 다시 점검할 계기로 삼아야 합니다. Astra는 비싼 Model이고, 비싼 Model은 적합한 작업에만 붙여야 본전을 뽑습니다.

## 실제로 달라진 것

OpenAI Model Card와 초기 Benchmark 결과를 정리하면 다음과 같습니다.

| 항목 | GPT-6 Astra | 비고 |
|------|-------------|------|
| Context Window | 1M Token | 최근 Gemini와 같은 급 |
| API 가격 (Standard) | Input $10 / Output $50 (100만 Token당) | GPT-5.6 Sol 대비 2.5배 |
| Fast Mode | 속도 2배, 가격 2배 | Request 단위 Opt-in |
| Batch / Flex | Standard의 50% | 비대화형 Workload용 |
| 배포 순서 | Enterprise(Daybreak) 우선 → API/AWS/ChatGPT 각 Plan | 며칠 단위 단계적 배포 |

Coding Agent 입장에서 가장 중요한 변화는 Codex에서 Astra가 Context Window를 넘나들며 Note를 유지할 수 있다는 점입니다. 기존처럼 오래된 State를 반복적으로 Summarize하고 버리는 대신, 이전 Context Window도 검색 가능한 상태로 남습니다. 이는 Benchmark 상의 수치가 아니라 실질적인 Architecture 변화이며, 긴 Refactor나 Multi-file Migration에서 자주 발생하는 "몇 File 전에 한 작업을 Agent가 잊어버리는" 문제를 직접 해결합니다.

출시를 지연시킨 원인이었던 Offensive Cyber Capability는 동시에 가장 접근이 제한된 기능이기도 합니다. 이 Tier에 접근하려면 OpenAI의 Daybreak Program을 통한 Enterprise Vetting이 필요합니다. 자사에 해당 용도가 없다면 볼 일이 없겠지만, Client가 물어보기 전에 존재 자체는 알아두는 편이 좋습니다.

## Multi-Model을 유지해야 하는 이유

Claude Opus의 새 Release가 나올 때마다 반복해온 이야기지만, 이번에도 동일하게 적용됩니다. 단일 Frontier Model만을 Coding Backend로 쓰는 것은 단순화가 아니라 비용과 신뢰성 Risk입니다.

사내에서 테스트 중인 현실적인 분배 예시입니다.

```typescript
// route.ts — Agentic Coding Pipeline를 위한 간단한 Model Router
type TaskProfile = {
  fileCount: number;
  requiresLongHorizon: boolean; // 여러 Session에 걸친 대규모 Refactor/Migration
  isInteractive: boolean;
};

function pickModel(task: TaskProfile): string {
  if (task.requiresLongHorizon && task.fileCount > 20) {
    // Astra의 Cross-window Memory가 효과를 발휘하는 경우
    return "gpt-6-astra";
  }

  if (!task.isInteractive) {
    // Batch 가격으로 처리 가능한 Background Job: Code Review Comment 생성, 문서 생성 등
    return "gpt-6-astra-batch";
  }

  // 일상적인 작은 Diff, Interactive Pair Programming
  return "claude-fable-5-1";
}
```

이는 개념적인 예시가 아니라 실제 운영 중인 `AI Gateway`나 Custom Router가 하는 일에 가깝습니다. Project 단위로 Provider를 고정하는 것이 아니라 Task의 형태에 따라 Model을 선택합니다. 가장 흔한 실수는 특정 Provider의 SDK를 Application Code에 직접 박아넣는 것인데, 이렇게 하면 Routing 변경이 Config 변경이 아니라 반나절짜리 Rewrite가 되어 버립니다.

## Astra 가격이 아깝지 않은 경우

- **대규모이면서 오래 걸리는 Migration.** 여러 Session에 걸친 Framework 업그레이드나 Monorepo 전체 Refactor는 영구적인 Context의 혜택을 받습니다. "계획을 다시 설명하는" Prompt가 줄어들수록 낭비되는 Token도 그만큼 줄어듭니다.
- **Computer Use 중심 Agent.** Browser나 GUI를 Agent가 직접 조작하는 Task(QA 자동화, RPA성 Workflow)에서는 보고된 성능 향상이 바로 그 영역에 집중되어 있습니다.
- **Batch 가격의 Background 작업.** 야간 Code Review 일괄 처리, Changelog 생성, Documentation 보완 작업은 기다리는 사람이 없으므로 절반 가격의 Batch/Flex로 충분합니다.

## 아까운 경우

- **일상적인 Interactive Coding.** 이전 세대 대비 2.5배 가격으로 모든 작은 Diff를 Astra에 통과시키는 것은 측정 가능한 품질 향상 없이 Budget만 소모합니다.
- **Fast Mode를 켠 Latency 민감 용도.** Fast Mode는 이미 비싼 Standard 가격을 다시 2배로 만듭니다. 활성화하기 전에 Latency 요구사항을 먼저 명확히 해야 합니다.

## 정리

1. GPT-6 Astra는 장시간·다중 Session·Computer Use 중심 작업을 위한 Specialist Model로 취급하고, Default Coding Model의 전면 교체 대상으로 보지 않는다.
2. 사람이 Response를 기다리지 않는 작업에는 Batch/Flex 가격을 사용한다. 같은 Model을 절반 가격에 쓸 수 있다.
3. Model 선택은 Application Code에 직접 박아넣지 말고 Router나 Gateway 계층 뒤에 숨긴다. 다음 Release, 그다음 Release에서도 같은 판단을 다시 내려야 한다.
4. Client의 Workload가 Security 민감 자동화와 맞닿아 있다면, Restricted Access Tier에 해당하는지 먼저 확인한 뒤 일정을 약속한다.

Frontier Model이 출시될 때마다 던져야 할 질문은 "갈아타야 하는가"가 아니라 "우리 Workload의 어느 부분이 저렴해지거나 나아졌고, 어느 부분은 변하지 않았는가"입니다.
