지금까지 API 설계는 "사람이 브라우저나 모바일 앱에서 호출한다"는 전제를 바탕으로 이루어져 왔습니다. 하지만 AI 에이전트가 스스로 tool을 호출하고 여러 API를 조합해 작업을 완수하는 구조가 일반화되면서, API 설계의 전제 자체를 다시 검토할 필요가 생겼습니다. Apollo가 2026년 8월에 진행한 보안 관련 웨비나에서도 "Agentic AI 시대의 GraphQL API Security"라는 주제가 다뤄질 만큼, 이 논점은 업계 전반에서 주목받기 시작했습니다.

이번 글에서는 gRPC와 GraphQL을 AI 에이전트 시대라는 맥락에서 비교하고, 인가 설계에서 놓치기 쉬운 부분을 정리합니다.

## 에이전트는 API를 사람과 다르게 호출한다

사람 클라이언트는 UI의 제약 안에서 요청을 발생시킵니다. 반면 AI 에이전트는 LLM이 생성한 tool call을 기반으로 API를 호출하기 때문에 다음과 같은 특성을 갖습니다.

- 작업 분해의 결과로 짧은 시간에 대량의 호출이 발생하기 쉽다
- 호출 파라미터가 사람의 입력보다 예측하기 어렵고, prompt injection의 영향을 받을 수 있다
- API 스키마 자체가 tool 정의로서 LLM에 전달되기 때문에, 타입의 명확성이 실행 정확도에 직결된다

이런 특성을 고려하면, API 계층에서의 설계 판단은 단순한 성능 문제를 넘어 보안 문제이기도 합니다.

## gRPC가 적합한 경우

서비스 간 통신, 특히 AI 에이전트가 내부적으로 호출하는 tool 군에는 gRPC의 엄격한 스키마 정의가 적합합니다.

```protobuf
// tool.proto
syntax = "proto3";

service InventoryTool {
  rpc CheckStock (StockRequest) returns (StockResponse);
}

message StockRequest {
  string sku = 1;
  int32 warehouse_id = 2;
}

message StockResponse {
  int32 available_units = 1;
  bool backorder_allowed = 2;
}
```

Protocol Buffers로 정의된 타입은 LLM이 잘못된 형식의 인자를 생성할 위험을 구조적으로 줄여줍니다. 또한 gRPC는 요청/응답 형태가 고정되어 있어, 에이전트가 예상치 못한 필드를 요구하며 데이터를 과도하게 가져갈 여지가 적다는 장점도 있습니다. gRPC-js의 주간 다운로드 수는 2026년 초 기준 410만 건에 달하며, 마이크로서비스 간 통신에서의 채택이 꾸준히 늘고 있음을 보여줍니다.

## GraphQL이 적합한 경우와 주의점

한편 사람과 에이전트가 함께 사용하는 엣지 단 API, 특히 유연한 쿼리가 필요한 상황에서는 GraphQL의 장점이 여전히 유효합니다. 다만 에이전트가 호출자가 되는 경우, 필드 단위 인가를 기존보다 훨씬 엄격하게 설계해야 합니다.

```typescript
// 필드 단위로 인가를 강제하는 리졸버 예시
const resolvers = {
  Customer: {
    ssn: (parent, _args, context) => {
      if (!context.caller.hasScope("pii:read")) {
        throw new Error("insufficient scope for field: ssn");
      }
      return parent.ssn;
    },
  },
};
```

에이전트는 "작업 달성에 유용해 보이는 필드"를 폭넓게 요구할 가능성이 있기 때문에, 스키마 전체를 신뢰하는 설계가 아니라 필드 단위로 스코프를 검증하는 설계가 전제가 되어야 합니다. GraphQL의 유연함은 사람 클라이언트에게는 장점이지만, 에이전트 입장에서는 공격 표면이 넓어진다는 것과 동전의 양면이라는 점을 인식하고 있어야 합니다.

## 사용 구분 기준

- **내부 서비스 간·에이전트 간 통신**: gRPC. 타입의 엄격함과 호출의 예측 가능성을 우선한다
- **사람과 에이전트가 함께 사용하는 엣지 API**: GraphQL. 단, 필드 단위 인가를 필수로 한다
- **단순 CRUD 위주로 에이전트 호출 패턴이 제한적인 경우**: 기존처럼 REST로도 충분한 경우가 많다

"새로운 기술이니까 채택한다"가 아니라, 호출자가 에이전트인지 여부에 따라 요구되는 보안 설계가 달라진다는 관점에서 기술을 선정하는 것을 권장합니다.

## 정리

- AI 에이전트는 사람과 다른 호출 패턴을 가지므로 설계 전제를 다시 검토할 필요가 있다
- gRPC는 타입의 엄격함 덕분에 에이전트용 내부 tool 호출에 적합하다
- GraphQL을 에이전트용 엣지 API에 사용할 경우 필드 단위 인가 설계가 필수가 된다
- 기술 선정은 성능뿐 아니라 에이전트 특유의 보안 특성까지 고려해서 이루어져야 한다

AI 에이전트를 프로덕트에 내장하는 프로젝트가 늘어나면서, API 설계와 보안 설계를 분리하지 않고 함께 검토하는 것이 앞으로의 아키텍처 리뷰에서 표준이 될 것이라고 봅니다.
