Typosquatting은 사람이 이름을 잘못 입력하는 실수를 노립니다. 새로운 변종은 모델이 존재하지 않는 이름을 그럴듯하게 만들어내는 점을 노립니다. 2026년 7월 Tel Aviv University, Technion, Intuit 연구진이 "HalluSquatting"을 논문(arXiv, 7월 8일)으로 공개했습니다. LLM이 반복해서 환각하는 Repository 및 Skill 이름을 미리 측정하고, 그 이름을 공격자가 먼저 등록해 둔 뒤 Agent가 가져가기를 기다리는 방식입니다.

Agent에게 `git clone`, `npm install`, Skill 설치를 맡기고 있다면 직접 관련된 이야기입니다. 아래 내용은 논문을 다룬 2차 보도를 바탕으로 정리했으므로, 수치를 인용하실 때는 원문을 확인하시기 바랍니다.

## 공격 흐름

1. 사용자가 Agent에게 "도구 X의 공식 Repository를 clone해서 프로젝트에 연결해 줘"라고 요청합니다.
2. 모델이 그럴듯하지만 틀린 식별자를 출력합니다. 정답이 `acme/tool-x`인데 `acme-labs/tool-x`를 내놓는 식입니다.
3. 공격자가 그 이름을 미리 등록해 두었다면, Agent는 공격자가 관리하는 콘텐츠를 가져옵니다. README의 설치 안내나 Skill 파일은 Agent가 신뢰하고 실행하기 쉬운 텍스트입니다.

보도된 수치는 Repository clone 시나리오에서 최대 85%, Skill 설치 시나리오에서 100%의 확률로 존재하지 않는 이름이 생성되었고, clone 시나리오의 end-to-end 성공률은 애플리케이션, 모델, Payload에 따라 약 20~65%였다는 내용입니다. 여러 주요 Agent에서 검증되었고 Payload는 무해한 Placeholder만 사용했으며, 공개 전에 Vendor에 먼저 알렸다고 합니다.

관련 사례도 있습니다. Aikido Security는 환각으로 생겨난 npm Package 이름 `react-codeshift`가 AI가 작성한 안내문을 통해 수백 개 규모의 프로젝트에 퍼졌다고 보고했습니다. Palo Alto Networks Unit 42는 환각된 Domain을 다루는 "phantom squatting"을 설명했습니다. 공통점은 모델이 지어낸 이름이 무인으로 동작하는 Agent에게는 진짜 이름과 구별되지 않는다는 점입니다.

보도에 따르면 Vendor 측 입장 중 하나는 "사용되지 않는 이름으로 Repository를 만드는 것은 Code Hosting의 정상 동작이며, 문제는 Agent가 가져온 내용을 신뢰하는 데 있다"는 것이었습니다. 결국 대응의 책임은 Agent를 설정하는 쪽에 있습니다.

## 모델 개선만으로 막기 어려운 이유

환각은 줄일 수 있어도 사라지지 않습니다. 공격자의 비용은 낮습니다. 모델을 여러 번 샘플링해 반복적으로 나오는 가짜 이름을 모으고 등록하면 됩니다. 반복해서 나오는 이름이 바로 노릴 가치가 있는 이름입니다.

따라서 방어는 식별자가 네트워크 요청으로 바뀌는 경계에 있어야 합니다. 이 지점은 모델의 판단이 아니라 결정적인 Code로 지켜야 합니다.

## Guardrail 1: 가져오기 전에 이름을 검증합니다

Agent가 clone하려는 모든 Repository는 사전 조회를 통과하도록 합니다. 존재 여부, 생성일, 승인된 Owner인지 확인하는 작은 Script로 충분합니다.

```bash
#!/usr/bin/env bash
# check-repo.sh owner/name  -> 문제가 없을 때만 exit 0
set -euo pipefail

REPO="$1"
OWNER="${REPO%%/*}"
ALLOWED_OWNERS=("vercel" "facebook" "anthropics" "our-org")

if [[ ! " ${ALLOWED_OWNERS[*]} " =~ " ${OWNER} " ]]; then
  echo "blocked: owner '$OWNER' is not on the allowlist" >&2
  exit 1
fi

# GitHub REST API: GET /repos/{owner}/{repo}
created=$(gh api "repos/$REPO" --jq '.created_at' 2>/dev/null) || {
  echo "blocked: $REPO does not resolve" >&2
  exit 1
}
echo "ok: $REPO (created $created)"
```

Owner Allowlist는 거친 방식이지만, "알 수 없는 계정 아래의 그럴듯한 이름"이라는 공격 유형 전체를 제거합니다. 알 수 없는 Owner라면 생성일, Star 수, 프로젝트 공식 문서에 나온 조직과 일치하는지 같은 조회 결과를 첨부해 사람에게 판단을 넘깁니다.

## Guardrail 2: install과 clone은 수동 승인으로 유지합니다

대부분의 Agent 도구는 Command를 사전 승인할 수 있습니다. 여기서는 선별이 필요합니다. 파일 읽기와 Test 실행은 허용해도 좋지만, `git clone`, `npm install <새 패키지>`, `pip install`, Skill 추가는 검토하지 않은 Code를 들여오므로 확인 절차를 두어야 합니다. 공유 설정을 관리하신다면 기본값을 거부로 두고, 신뢰하는 Registry만 명시적으로 허용하십시오.

## Guardrail 3: 가져온 Repository는 신뢰할 수 없는 입력으로 취급합니다

clone한 Repository에는 Agent를 겨냥한 지시가 들어 있을 수 있습니다. Setup Script 실행을 유도하는 README나 Command가 포함된 Skill 파일이 그 예입니다. 낯선 사람이 보낸 Pull Request와 같은 수준으로 다루십시오.

- 처음 평가할 때는 인증 정보가 없는 Sandbox나 일회용 Container에서 실행합니다.
- Cloud Key, SSH Agent, `.env` 파일을 낯선 Code를 다루는 환경에 두지 않습니다.
- 신뢰할 수 없는 Repository를 읽은 Session이 운영 환경의 Secret을 함께 갖지 않도록 합니다.

## Guardrail 4: 의존성은 고정하고 Mirror를 거치게 합니다

Agent가 추가하는 의존성은 Review에서 lockfile 변경을 반드시 확인하고, Registry는 사내 Mirror나 Package Firewall을 거치는 편이 좋습니다. Commit 메시지가 "add helper" 정도인데 조직 내 이력이 없는 의존성이 들어온 Pull Request는 특히 주의해서 보시기 바랍니다.

## 이번 주에 해 둘 일

- Agent 설정을 점검해 `clone`, `install`, Skill 추가의 사전 승인을 제거합니다.
- 위 Script(또는 동등한 Hook)를 넣어 가져오기 전에 식별자를 검증합니다.
- 서드파티 Repository의 첫 평가를 Secret이 없는 Sandbox로 옮깁니다.
- Review 규칙으로, Agent가 추가한 의존성이나 Skill은 공식 문서와 대조해 사람이 출처를 확인하도록 합니다.

도구를 불신하자는 이야기가 아닙니다. 모델의 자신 있는 출력은 이름에 대한 제안일 뿐이고, 이름이 곧 신원은 아니라는 점을 받아들이는 것이 출발점입니다. 둘을 이어 주는 확인 절차는 우리가 통제하는 Code여야 합니다.
