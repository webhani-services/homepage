Container Image에서는 내용물이 위험하고 Metadata는 부가 정보라고 생각하기 쉽습니다. 최근 두 Advisory는 이 전제에 의문을 던집니다. 두 경우 모두 Tool이 이미지의 `LABEL` 값을 읽어 어떤 동작을 수행했고, 그 값을 작성한 사람은 이미지 제작자였습니다.

아래 내용은 취약점 Aggregator와 Advisory Feed에 근거합니다. 이런 출처는 공개일이나 영향 Version 범위가 완전하게 나와 있지 않을 수 있습니다. 단서로만 활용하시고, 조치하기 전에 upstream Advisory와 NVD에서 확인하십시오.

## 두 Advisory

**containerd CRI plugin, CVE-2026-53488**. 한 Feed에 따르면 CRI plugin이 이미지 설정의 `LABEL` 값을 검증 없이 Container에 전달하는 문제이며, Host에서 root 권한 명령 실행으로 이어질 수 있다고 합니다. 심각도는 critical로 분류되고, 수정 Version은 1.7.33, 2.0.10, 2.1.9, 2.2.5, 2.3.2로 기재되어 있습니다. 날짜는 2026년 6월로 되어 있어 새로운 이야기는 아니지만, 오랫동안 아무도 손대지 않은 Node에 남기 쉬운 유형의 문제입니다.

**Podman auto-update, CVE-2026-121885**. stack.watch에 따르면 2026년 11월 10일에 공개되었으며, 신뢰할 수 없는 이미지 Label로 Podman의 auto-update 기능이 임의의 systemd unit을 재시작하게 만들 수 있는 문제입니다. 같은 출처는 네트워크를 통해 악용 가능하며 사용자 조작이 필요하다고 설명합니다.

제품도 영향도 다르지만 근본 원인은 같습니다. 이미지 작성자가 제어할 수 있는 Metadata를, 권한을 가진 Component가 운영자의 설정인 것처럼 해석했습니다.

## 왜 반복될까요

Label은 Tool이 이미지에 의미를 부여하기 위한 장치입니다. `org.opencontainers.image.*` 계열 Key는 설명용입니다. 그러나 많은 Tool은 Label을 지시로도 읽습니다. 어떤 unit을 재시작할지, 어떤 Port를 노출할지, 어떤 Volume을 Mount할지, 어떤 healthcheck를 실행할지 같은 것들입니다. 권한을 가진 Process가 Label에 따라 동작하는 순간, 그 Label은 이미지를 빌드한 사람이 보내는 입력 경로가 됩니다.

이미지가 자사 Registry와 자사 CI에서 나왔다면 그 경로는 자사의 것입니다. 공개 Registry, 서드파티 Base Image, "친절한" Vendor 이미지에서 왔다면 그렇지 않습니다.

## 실행 중인 환경 확인

Kubernetes Node의 containerd는 먼저 Version을 확인합니다. Managed Service는 자체 일정으로 Patch를 적용하므로, Node가 보고하는 값을 확인하십시오.

```bash
# Node별 Container Runtime Version
kubectl get nodes -o custom-columns=NAME:.metadata.name,RUNTIME:.status.nodeInfo.containerRuntimeVersion

# SSH로 접속 가능한 Node에서
containerd --version
```

결과를 사용 중인 Release Line에 해당하는 수정 Version과 비교합니다. 수정은 minor 계열별로 제공됩니다. 2.1.x Node에 필요한 것은 2.1.9 이상이며, "1.7.33보다 새로우면 된다"는 뜻이 아닙니다.

Podman은 auto-update를 실제로 사용하는지부터 확인합니다.

```bash
podman --version
systemctl list-timers | grep -i podman-auto-update
podman auto-update --dry-run
```

timer가 활성화되어 있지 않고 `io.containers.autoupdate` Label을 가진 Container도 없다면 노출 범위는 훨씬 작아집니다. 결론을 내리기 전에 Advisory에서 수정 Version을 확인하십시오.

## 실행 전에 Label 살펴보기

이미지 전체를 pull하지 않아도 Label은 가볍게 읽을 수 있습니다. `skopeo`는 config만 가져옵니다.

```bash
skopeo inspect docker://registry.example.com/team/app:1.4.2 \
  | jq '.Labels'
```

이미 로컬에 있는 이미지라면 다음과 같습니다.

```bash
docker image inspect registry.example.com/team/app:1.4.2 \
  --format '{{json .Config.Labels}}' | jq
```

표시용이 아니라 Tool이 해석할 만한 Label에 주의하십시오. auto-update, systemd, hook, mount, capability와 관련된 Key는 특히 직접 빌드하지 않은 이미지라면 한 번 더 살펴볼 가치가 있습니다.

## 일회성이 아니라 Policy로

CI에 작은 검사를 넣어 두면 예상치 못한 Label이 Review 없이 운영 환경에 도달하는 것을 막을 수 있습니다. 아래 Script는 허용 목록에 없는 prefix의 Label이 있으면 Build를 실패시킵니다.

```bash
#!/usr/bin/env bash
set -euo pipefail

image="$1"
allowed='^(org\.opencontainers\.image\.|com\.example\.)'

unexpected=$(skopeo inspect "docker://${image}" \
  | jq -r '.Labels // {} | keys[]' \
  | grep -Ev "$allowed" || true)

if [ -n "$unexpected" ]; then
  echo "Unexpected labels on ${image}:" >&2
  echo "$unexpected" >&2
  exit 1
fi
```

자체 Key를 추가하는 Base Image 때문에 허용 목록은 조정이 필요합니다. 이 번거로움은 유익합니다. 새 Label이 무엇을 하는지 출시 전에 누군가 확인하게 되기 때문입니다.

## webhani의 권장 사항

1. **Runtime에 Patch를 적용합니다**. 모든 Cluster의 containerd Version을 점검하고 각 minor 계열을 수정 Release로 맞춥니다. Managed Service가 이미 적용했을 것이라 가정하지 말고 보고되는 Version을 확인하십시오.
2. **auto-update 사용을 점검합니다**. Podman auto-update를 켜 두었다면 정말 필요한지 판단하고, 직접 빌드한 이미지로 제한합니다.
3. **digest로 고정하고 신뢰할 수 있는 출처를 사용합니다**. 서드파티 Base Image는 자사 Registry에 Mirroring하여 pull 사이에 Label이 바뀌면 알아챌 수 있게 합니다.
4. **Label도 Code처럼 Review합니다**. 이미지 CI에 Label 검사를 추가하고, Base Image를 올릴 때 Label Diff를 확인합니다.
5. **최소 권한으로 실행합니다**. Rootless Runtime과 Node 접근 제한은 잘못 처리된 Label이 닿는 범위를 줄여 줍니다.

## 정리

- 이미지가 공격자의 것이라면 Metadata도 공격자가 제어합니다.
- 2026년에 서로 다른 두 Tool이 부여해서는 안 될 권한으로 Label에 따라 동작했습니다.
- containerd는 minor 계열별로 Version을 확인하고, Podman은 auto-update 활성화 여부를 확인합니다.
- 이미지 Review에 Label 검사를 추가하고 예외 목록은 짧게 유지합니다.
