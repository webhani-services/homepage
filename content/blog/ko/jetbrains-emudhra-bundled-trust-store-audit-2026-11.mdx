10월 말, JetBrains가 보안 advisory를 발표했습니다. eMudhra 중간 인증서 8개의 개인 키가 유출되었다는 내용입니다. 이 키를 가진 사람은 신뢰된 Root로 이어지는 TLS 인증서를 임의 도메인에 대해 발급할 수 있고, 이는 Server를 사칭하는 데 필요한 조건 그 자체입니다. JetBrains는 IDE, ReSharper, .NET 도구, Toolbox App, Gateway의 수정 버전과 함께 background Service(`jetbrainsd` 0.9.9728 이상) 수정판을 배포했습니다. 발표 시점에 JetBrains 사용자를 대상으로 한 악용은 확인되지 않았다고 밝혔습니다.

사고 자체보다 주목할 부분은 advisory의 한 문장입니다. **OS를 업데이트해도 이 문제는 해결되지 않는다.** JetBrains 도구는 함께 배포되는 JetBrains Runtime 위에서 동작하고, 이 Runtime이 신뢰할 인증서 목록을 따로 가지고 있기 때문입니다.

IDE가 그렇다면, 여러분의 Stack에도 같은 구조를 가진 것이 여럿 있을 가능성이 높습니다.

## 무엇을 신뢰할지는 실제로 누가 정할까요

많은 개발자는 "시스템"이 신뢰할 인증 기관을 정한다고 생각합니다. 실제로는 Runtime마다 다릅니다.

| Runtime | 기본 신뢰 출처 | OS 패치로 갱신되는가 |
| --- | --- | --- |
| JetBrains IDE (JBR) | 번들된 `cacerts` | 아니요 |
| Java / JVM Application | JDK의 `cacerts` | 배포판 JDK가 시스템 store에 연결된 경우만 |
| Node.js | binary에 내장된 Mozilla CA 목록 | 아니요 (`--use-system-ca` 사용 시 제외) |
| Python `requests` | `certifi` Package | 아니요 (`pip`로 갱신) |
| Go (Linux) | 시스템 store (`/etc/ssl/certs`) | 예 |
| Container Image | Image 내부의 `ca-certificates` | 재빌드할 때만 |
| Electron 앱 | Chromium의 Root store | 앱 릴리스와 함께 갱신 |

CA 사고가 터지면 "아니요"라고 적힌 행 하나하나가 각기 다른 담당자가 처리해야 하는 별도 작업이 됩니다.

## 레이어별 점검 방법

공개 Trust Store에 들어 있는 eMudhra의 Root 인증서는 **emSign**이라는 브랜드명을 쓰므로, 두 이름으로 모두 검색합니다.

### JVM과 JetBrains Runtime

```bash
# PATH에 있는 JDK
keytool -list -cacerts -storepass changeit 2>/dev/null | grep -iE 'emudhra|emsign'

# IDE에 번들된 JetBrains Runtime (macOS 예시)
JBR="/Applications/IntelliJ IDEA.app/Contents/jbr/Contents/Home"
"$JBR/bin/keytool" -list -keystore "$JBR/lib/security/cacerts" \
  -storepass changeit | grep -iE 'emudhra|emsign'
```

Root 목록에 결과가 나온다고 바로 위험하다는 뜻은 아닙니다. 유출된 것은 중간 인증서이고, JetBrains의 수정은 해당 chain을 신뢰하지 않도록 바꾸는 방식입니다. 이 점검으로 얻는 것은 머신에 JVM이 몇 개 있고 각각 별도의 Trust Store를 쓰고 있다는 목록이며, 대개 예상보다 많이 나옵니다.

### Node.js

Node는 Mozilla Root 목록을 binary 안에 내장합니다. 내용은 직접 확인할 수 있습니다.

```javascript
// list-roots.mjs
import { rootCertificates } from "node:tls";
import { X509Certificate } from "node:crypto";

const matches = rootCertificates
  .map((pem) => new X509Certificate(pem))
  .filter((c) => /emudhra|emsign/i.test(c.subject));

for (const c of matches) {
  console.log(c.subject.replace(/\n/g, ", "), "| expires", c.validTo);
}
console.log(`${matches.length} matching roots in Node ${process.version}`);
```

내장 목록은 Node를 업그레이드할 때만 바뀝니다. 즉 CA 불신 결정이 Service에 반영되는 시점은 OS를 패치할 때가 아니라 새 Node 버전을 Deploy할 때입니다. 조직의 신뢰 정책을 따라야 하는 Server라면, 최근 Node가 지원하는 `--use-system-ca`(또는 `NODE_USE_SYSTEM_CA=1`)를 쓰면 OS 쪽 변경 한 번으로 전체에 적용됩니다.

### Python

```bash
python -c "import certifi; print(certifi.where())" \
  | xargs grep -iE '^# (Issuer|Subject):.*(emudhra|emsign)'
```

`certifi`는 Package를 올릴 때 갱신되므로, 사실상 lockfile이 Trust Store를 결정합니다. 신뢰를 중앙에서 관리하고 싶다면 `truststore` Package(또는 시스템 bundle을 가리키는 `SSL_CERT_FILE`)로 Python이 OS store를 쓰게 할 수 있습니다.

### Container Image

```dockerfile
FROM node:24-bookworm-slim
# 빌드 시점의 최신 CA bundle 반영
RUN apt-get update \
 && apt-get install -y --no-install-recommends ca-certificates \
 && update-ca-certificates \
 && rm -rf /var/lib/apt/lists/*
ENV NODE_USE_SYSTEM_CA=1
```

석 달 전에 빌드한 Image에는 석 달 전의 Trust Store가 들어 있습니다. 해결 방법은 재빌드뿐입니다. Application 코드가 바뀌지 않았더라도 Image를 정기적으로 재빌드해야 하는 이유가 여기에도 있습니다.

## 이번 주에 할 일

JetBrains 사용자라면 다음을 진행합니다.

1. IDE, Toolbox App, Gateway, ReSharper를 advisory에 명시된 수정 버전으로 업데이트합니다
2. background daemon이 0.9.9728 이상인지 확인합니다
3. 구버전 IDE에는 수정이 제공되지 않습니다. 구버전에 고정되어 있다면 지금 업그레이드 계획을 세웁니다
4. JetBrains에 따르면 드물게, 제거된 Root로 이어지는 인증서를 쓰는 Server와의 연결이 실패할 수 있습니다. 업데이트 후 사내 Service에 접속이 안 된다면 예전 Root를 다시 추가할 것이 아니라 해당 Server의 인증서를 재발급하는 것이 올바른 대응입니다

Stack 전체에 대해서는 목록을 한 번 만들어 두십시오. TLS를 받거나 여는 모든 Runtime에 대해 Trust Store의 출처와 갱신 담당자를 정리합니다. webhani가 고객 환경에서 이 작업을 해 보면, 잊힌 JVM 몇 개, 몇 년 된 Base Image 몇 개, 그리고 "임시로" 인증서 검증을 꺼 둔 Service가 최소 하나는 나오는 것이 보통입니다.

## webhani의 시각

인증 기관 사고는 드물지만, 일어났을 때의 대응 속도는 사전 준비로 거의 결정됩니다. 이번 eMudhra 건은 비교적 온건한 편입니다. Vendor 대응이 빨랐고 악용 보고도 없습니다. 비용 없이 해 볼 수 있는 리허설로 받아들이는 것이 좋다고 봅니다.

webhani의 권장 사항은 다음과 같습니다.

- Server에서는 OS Trust Store를 따르는 Runtime 설정(`--use-system-ca`, `truststore`, 배포판 JDK)을 우선해, 한 번의 변경이 전체에 적용되게 합니다
- Container Image는 코드 변경 때만이 아니라 정기적으로 재빌드합니다
- Trust Store의 출처를 SBOM이나 Service catalog에 기록합니다
- `NODE_TLS_REJECT_UNAUTHORIZED=0`, `verify=False` 같은 설정은 CI의 grep 규칙으로 금지합니다

개발 도구 업데이트는 몇 분이면 끝납니다. 50개 Service가 각각 무엇을 신뢰하는지 알고 있는 것이 다음 사고에서 효과를 발휘합니다.
