Upstream Kubernetes 1.34는 2026년 10월 27일에 EOL을 맞습니다. 하지만 Managed Service를 사용 중이라면 이 날짜가 곧바로 기한은 아닙니다. Amazon EKS는 1.34의 Standard Support 종료일을 12월 2일로 안내하며, 그 이후에는 유료 Extended Support가 적용됩니다. GKE와 AKS도 각자 다른 날짜를 공개하고 있어 Upstream과도, 서로 간에도 일치하지 않습니다. 각 Provider의 공식 Lifecycle 페이지에서 확인하시기 바랍니다. 2차 정보를 제공하는 Tracker들끼리도 일부 날짜가 엇갈립니다.

진짜 위험은 날짜 자체가 아니라 조용히 일어나는 전환입니다. 업그레이드하지 않은 EKS Cluster는 자동으로 Extended Support로 넘어가고, Extended Support는 Standard Support보다 Cluster당 단가가 훨씬 높게 청구됩니다. 1년간 방치된 Cluster는 아무도 선택하지 않은 비용 항목이 됩니다.

현재 업그레이드 대상은 1.35와 1.36입니다. Control Plane은 Minor 버전을 하나씩만 올릴 수 있으므로 1.34에서 1.36으로 가려면 업그레이드가 두 번 필요합니다. 처음부터 두 번을 계획하십시오.

## Step 1: 잊힌 Cluster까지 포함해 버전 파악

먼저 실제로 무엇이 있는지 확인합니다. AWS 기준입니다.

```bash
for region in ap-northeast-1 us-east-1; do
  for c in $(aws eks list-clusters --region "$region" --query 'clusters[]' --output text); do
    aws eks describe-cluster --region "$region" --name "$c" \
      --query '{name:cluster.name,version:cluster.version,policy:cluster.upgradePolicy.supportType}' \
      --output json
  done
done
```

`supportType`으로 Standard인지 Extended인지 알 수 있습니다. 뜻밖의 Cluster는 대개 Staging이나 "임시" Cluster에서 나옵니다.

## Step 2: 깨질 API 사용 찾기

Minor Release마다 일부 Deprecated API가 제거됩니다. 업그레이드 전에 Cluster가 실제로 무엇을 요청받고 있는지 확인합니다.

```bash
# 가동 중인 API Server에 요청된 Deprecated API
kubectl get --raw /metrics | grep apiserver_requested_deprecated_apis

# Repository/Cluster 내 Manifest와 Helm Release 스캔
pluto detect-files -d ./k8s
pluto detect-helm -o wide
```

Metric은 런타임 Client(잊고 있던 Controller나 CI Job 포함)를, `pluto`는 Manifest를 보여줍니다. 둘 다 실행하십시오. Manifest가 문제없어도 오래된 Operator가 제거된 Endpoint를 계속 호출하고 있을 수 있습니다.

## Step 3: Add-on과 Version Skew 확인

업그레이드 실패의 대부분은 Kubernetes 자체가 아니라 주변 Component에서 나옵니다.

- **Ingress/Gateway Controller, CNI, CSI Driver, Cluster Autoscaler 또는 Karpenter**: 목표 Kubernetes 버전을 지원하는 버전이 있는지 확인합니다. 각 프로젝트 문서의 호환성 표가 기준입니다.
- **Kubelet Skew**: kubelet은 API Server보다 최대 3개 Minor 버전 뒤처져도 허용되지만, 이를 계획의 전제로 삼지 마십시오. Node Group을 빨리 올려 두면 다음 업그레이드가 쉬워집니다.
- **Admission Webhook**: `failurePolicy: Fail`인 Webhook이 Rollout 중 사용 불가 상태가 되면 Pod 생성이 전부 막힐 수 있습니다. 어떤 Webhook이 있는지 파악해 두십시오.

## Step 4: 업그레이드 순서

저희가 실제로 효과를 본 순서입니다.

1. 운영과 비슷한 Workload 구성의 비운영 Cluster를 먼저 올립니다.
2. Control Plane을 업그레이드합니다. EKS라면 `aws eks update-cluster-version --name <cluster> --kubernetes-version 1.35`. 완료될 때까지 기다립니다.
3. Managed Add-on을 새 Control Plane과 호환되는 버전으로 올립니다.
4. Node Group을 Rolling 업데이트합니다. 핵심 Workload에 PodDisruptionBudget이 있는지, 그리고 drain이 멈출 만큼 빡빡하지 않은지 확인합니다(Replica 1개에 `maxUnavailable: 0`이 대표적인 실패 사례입니다).
5. Smoke Test를 수행하고 1.36에서도 같은 과정을 반복합니다.

1.35에서 1.36으로는 연달아 진행하지 말고 며칠 간격을 둡니다. 첫 번째 업그레이드가 원인인 문제와 두 번째가 원인인 문제를 분리하기 위해서입니다.

실제 장애는 Node drain에 숨어 있습니다. 운영 작업 전에 다음을 확인하십시오.

```bash
kubectl get pdb -A
kubectl get deploy -A -o json | jq -r '.items[] | select(.spec.replicas==1) | "\(.metadata.namespace)/\(.metadata.name)"'
```

Replica가 1개인 Deployment는 Node 교체 중에 다운타임이 발생합니다. 작업 시간 동안만 2개로 늘리거나, 중단을 감수하고 공지하는 쪽 중에서 정해 두십시오.

## Step 5: 기본값으로 Extended Support에 들어가지 않기

Standard Support 기한까지 끝내지 못한다면, 그것을 흘러가는 대로 두지 말고 의식적인 결정으로 만드십시오. 폐기 예정인 Cluster를 위한 임시 방편으로는 Extended Support가 합리적일 수 있습니다. 하지만 계속 운영하는 Cluster의 기본값으로는 좋지 않습니다. 각 Cluster의 Standard Support 종료일을 캘린더나 IaC의 Tag에 기록하고, 60일 전에 Alert를 설정하십시오.

## webhani의 권장 사항

- Kubernetes 업그레이드를 EOL 공지를 받고 시작하는 프로젝트가 아니라 분기별 정기 작업으로 만듭니다.
- Cluster 정의를 Terraform 등으로 관리하여, 버전 변경이 plan이 붙은 리뷰 대상 변경이 되도록 합니다.
- Deprecated API 스캔을 CI에서 자동화해, Manifest를 작성하는 시점에 제거된 API를 잡아냅니다.
- Control Plane과 Node의 버전 차이를 작게 유지합니다. 차이가 Minor 1개면 쉽지만 3개가 되면 프로젝트가 됩니다.

주기적으로 올리는 팀은 Release당 몇 시간이면 끝납니다. 기한을 기다리는 팀은 몇 주를 쓰고도 한동안 Extended Support에 머무는 경우가 많습니다. 비용 차이의 대부분은 기술이 아니라 프로세스에서 나옵니다.
