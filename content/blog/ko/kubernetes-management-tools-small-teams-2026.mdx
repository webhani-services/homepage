## Kubernetes가 주류가 된 것과, 우리 팀에 필요한 것은 별개의 문제

2026년 현재 Kubernetes는 표준 Engineering Toolkit의 일부로 자리 잡았습니다. 한때는 대기업 Platform Team만 다루던 전문 기술이었지만, 이제는 Data Engineering Team이 Batch Job의 재현성을 위해 Container화하고, ML Team도 Training Pipeline을 같은 방식으로 패키징합니다. AWS EKS, Azure AKS, Google GKE 같은 Managed Kubernetes가 주요 Cloud 전반에서 제공되면서, `etcd`나 API Server의 Upgrade를 직접 다루는 팀은 거의 남아있지 않습니다.

하지만 이 사실이 15명 규모로 2~3개 Service를 운영하는 팀의 계산을 바꾸지는 않습니다. Managed Kubernetes는 Control Plane 운영 부담을 없애주지만, RBAC 설계, Network Policy, Node Group의 Lifecycle 관리, Admission Controller 설정, 그리고 Cluster Version을 지원 기간 내로 유지하는 규율까지 대신해주지는 않습니다. 이것들은 한 번으로 끝나는 작업이 아니라 계속 감당해야 하는 실무입니다.

그래서 저희가 인프라 상담을 할 때 거의 항상 먼저 던지는 질문은 이것입니다. "이 팀은 정말 Kubernetes가 필요한가, 아니면 단일 Cloud Run Service나 ECS Fargate Service, App Service Plan으로 앞으로 1~2년의 Scale과 신뢰성 요구사항을 충족할 수 있는가." 만약 솔직한 답이 "Deployable 단위는 하나뿐이고, Traffic은 예측 가능하며, 수십 개 Service에 걸친 Pod 단위 Bin Packing은 필요 없다"라면, Managed Container Platform이 운영상 이점의 90%를 훨씬 작은 운영 표면적으로 제공해줍니다.

## Kubernetes를 선택해야 하는 상황

Kubernetes가 진가를 발휘하는 시점은 독립적으로 Deploy되는 Service가 충분히 많아서, 이들 전반에 걸쳐 일관된 Scheduling·Scaling·Networking 체계가 필요해질 때입니다. 대략적인 기준으로는 Scaling Profile이 서로 다른 Service를 6개 이상 운영하고 있거나, Cloud 간 Workload Portability가 가설이 아니라 실제 비즈니스 요구사항인 경우입니다. 이 조건에 해당한다면 다음 질문은 "어떤 도구를 쓸 것인가"이고, 여기서 팀들은 종종 과도하게 투자하는 경향이 있습니다.

## Dashboard가 아니라 kubectl과 K9s부터 시작한다

Kubernetes에 익숙하지 않은 팀이 흔히 보이는 첫 반응은 첫날부터 Cluster 상태, Deployment, Log를 한 화면에서 보여주는 본격적인 GUI를 도입하는 것입니다. 이 직감은 대부분 시기상조입니다. Cluster가 1~2개인 소규모 팀이라면 `kubectl`과 `k9s` 조합만으로 일상 운영의 거의 전부를 커버할 수 있고, 둘 다 Scriptable하고 가벼우며 온보딩 부담도 낮습니다.

구체적인 예를 살펴보겠습니다. Pod가 `CrashLoopBackOff` 상태에 빠졌고, 원인을 빠르게 파악해야 하는 상황입니다.

```bash
# Namespace 내 Pod 목록을 확인하고 문제의 Pod를 특정합니다
kubectl get pods -n checkout-service

# NAME                          READY   STATUS             RESTARTS   AGE
# checkout-api-7d8f9c6b4-x2k9p  0/1     CrashLoopBackOff   6          14m

# 최근 Exit 이유와 OOM Signal을 확인합니다
kubectl describe pod checkout-api-7d8f9c6b4-x2k9p -n checkout-service | grep -A5 "Last State"

# 현재의 재시작 Loop가 아니라, 직전에 Crash한 Container Instance의 Log를 읽습니다
kubectl logs checkout-api-7d8f9c6b4-x2k9p -n checkout-service --previous --tail=100
```

K9s를 사용하면 같은 조사가 몇 초 만에 끝납니다. `k9s`를 실행하고 `:pods checkout-service`로 Namespace를 필터링한 뒤, Crash 중인 Pod를 선택해 `l` 키로 Log를 보고(`p`로 직전 Container Instance 전환), `d` 키로 describe를 확인합니다. 이 모든 과정을 Terminal을 벗어나지 않고, Pod 이름을 외울 필요도 없이 할 수 있습니다. 이것이 raw `kubectl` 대비 K9s의 실질적인 가치입니다. 매일 반복하는 20가지 작업에서 Pod 이름과 Namespace Flag를 복사-붙여넣기하는 수고를 없애주면서도, Browser Tab이나 인증 Flow, 각 Engineer의 노트북에서 계속 Patch해야 하는 별도 Binary를 늘리지 않습니다.

Lens 같은 무거운 GUI Tool을 도입할 시점은 Terminal 기반 Workflow가 실제로 시간을 잡아먹기 시작할 때뿐입니다. 대략적인 기준은 Cluster를 3개 이상 운영하거나, Infra가 본업이 아닌 Engineer가 Platform Team에 매번 물어보지 않고도 Resource Graph나 여러 Cluster 전환 같은 시각적 Context를 스스로 얻어야 할 때입니다. 그 이하 규모에서는 GUI Dashboard가 Licensing·Update·Access 부여의 부담만 늘어날 뿐, 이미 `k9s`가 해결하고 있는 문제에 대한 추가 투자가 됩니다.

## 실제로 비용을 들일 가치가 있는 도구: Observability와 Cost 배분

여기가 팀들이 과소평가하는 부분입니다. Cluster가 돌아가기 시작하면 Orchestration 자체는 좀처럼 통증 지점이 되지 않습니다. 통증 지점이 되는 것은 Autoscaling이 예측 불가능하게 동작하는 것, 그리고 "이번 달 Cloud 청구액이 왜 3배가 됐는지"를 몇 시간짜리 조사 없이는 아무도 답하지 못하는 상황입니다. 전용 FinOps Tool이 필요해지기 전에 이 부분을 미리 손봐야 합니다.

Cluster가 몇 개의 Service를 넘어 커지기 전, 첫날부터 계측해야 할 것은 두 가지입니다.

**Resource Request/Limit 위생 관리.** 모든 Container는 Tutorial에서 복사한 추측치가 아니라 실제 측정된 사용량을 기반으로 Request와 Limit이 설정된 상태로 Deploy되어야 합니다. Request가 설정되지 않은 Deployment는 Scheduler가 합리적인 Bin Packing을 할 수 없고, Horizontal Pod Autoscaler도 무엇을 기준으로 Scale해야 할지 판단할 근거가 없습니다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: checkout-api
  namespace: checkout-service
spec:
  replicas: 3
  selector:
    matchLabels:
      app: checkout-api
  template:
    metadata:
      labels:
        app: checkout-api
        cost-center: payments
    spec:
      containers:
        - name: checkout-api
          image: registry.example.com/checkout-api:1.4.2
          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              cpu: "750m"
              memory: "512Mi"
          readinessProbe:
            httpGet:
              path: /healthz
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 10
```

`cost-center: payments`라는 Label에 주목하세요. 이것이 일찍부터 챙겨야 할 두 번째 요소입니다. Namespace와 Team/Cost-Center 기준의 일관된 Labeling을 통일적으로 적용해두면, `kubectl top pods --all-namespaces`와 Cloud의 청구 Export를 의미 있게 대조할 수 있습니다. 고객사 Cluster에서 저희가 확인하는 예상치 못한 Cost 급증의 상당수는 Label이 붙지 않았거나 일관되지 않게 붙은 Workload 때문이며, "어느 Team의 Service가 이 지출을 만들고 있는지"를 수작업 조사 없이는 답할 수 없는 상태입니다.

여러 Cluster를 운영하면서 Namespace 단위 Cost에 대한 질문이 매주 나올 정도가 되었을 때 비로소 전용 Tool(Kubecost, OpenCost, 혹은 각 Cloud Native의 Cost 배분 기능)을 도입할 의미가 생깁니다. 그 전까지는 `kubectl top`, 일관된 Label, Cloud 청구 Console의 Tag 기반 View만으로 충분합니다.

## 정리

**지금 Kubernetes를 도입해야 하는지 확인하는 간단한 Checklist:**

- Scaling 특성이 서로 다른, 독립적으로 Deploy 가능한 Service를 5~6개 이상 가지고 있습니까? 그렇지 않다면 단일 Managed Container Service로 앞으로 1년은 충분히 커버할 가능성이 높습니다.
- Multi-Cloud Portability가 가까운 미래에 실제로 필요한 것입니까, 아니면 가설에 불과합니까? 가설이라면 운영 부담을 정당화할 수 없습니다.
- RBAC·Network Policy·Cluster Upgrade 주기를 책임지고 담당할 사람이 팀에 있거나 채용 계획이 있습니까? 아무도 담당하지 않는다면 아직 도입할 때가 아닙니다.

**규모가 커짐에 따른 권장 도구 진행:**

1. Cluster 1~2개, 소규모 팀: 일상 운영은 `kubectl` + `K9s`로 충분합니다. Dashboard는 필요 없습니다.
2. Cluster 3개 이상, 또는 시각적 Context가 필요한 비Infra Engineer가 있는 경우: CLI Workflow를 대체하는 것이 아니라 그 위에 Lens 같은 GUI를 얹습니다.
3. Cluster 수와 무관하게 첫날부터: 모든 Deployment에 Resource Request/Limit을 설정하고, Cost-Center·Team Label을 일관되게 유지합니다.
4. 여러 Cluster를 운영하며 Cost 배분에 대한 질문이 반복적으로 나오는 경우: Kubecost, OpenCost, 혹은 Cloud Native의 전용 Cost 가시화 Tool을 도입합니다.

전체를 관통하는 원칙은 하나입니다. "복잡성을 들이는 것은 그것이 해결하는 문제가 이미 실제 시간을 잡아먹고 있을 때뿐이다."
