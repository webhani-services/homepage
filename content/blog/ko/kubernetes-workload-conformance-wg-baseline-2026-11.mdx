10월 27일 Kubernetes 프로젝트는 새로운 Workload Conformance Working Group의 출범을 발표했습니다. 목표는 Cluster가 아니라 Workload가 실행 시 어떻게 동작해야 하는지에 대한 공통 표준을 만드는 것입니다. 발표에 따르면 산출물은 세 가지입니다. Kubernetes 마이너 버전별 workload behavior Spec, 각 요구 사항을 실행 중인 Workload에 대해 검증하는 방법, 그리고 이 검증을 구현하는 upstream Tool입니다. Application 로직은 명시적으로 범위에서 제외됩니다. Spec은 SIG Architecture의 subproject가 관리하고, SIG Apps가 Application 관점을 보탤 예정입니다.

저희가 확인한 자료는 발표문뿐입니다. Draft Spec은 아직 공개되지 않았으므로 최종 내용에 대한 이야기는 모두 추측입니다. 그럼에도 이 발표는 실용적인 가치가 있습니다. Kubernetes 메인테이너가 표준화할 가치가 있다고 보는 질문이 무엇인지 알려 주기 때문이며, 대부분의 팀은 그 질문에 대한 자신들의 답을 아직 문서로 남기지 않았습니다.

## 기존 Program과의 관계

Conformance와 관련된 노력은 이미 두 가지가 있고, 새 Group은 그 옆에 위치합니다.

- **Certified Kubernetes**는 Cluster를 검증합니다. API가 Spec대로 동작하는지를 봅니다.
- **Kubernetes AI Conformance**(CNCF, 2025년 11월 시작)는 Cluster가 AI/ML Workload를 안정적으로 실행할 수 있는지를 검증합니다.
- **Workload Conformance**는 계약의 반대편, 즉 Cluster가 흔히 하는 동작(재스케줄링, Drain, Scaling)에 Workload가 올바르게 대응하는지를 검증하는 위치가 됩니다.

발표문은 공통 Workload Spec이 다른 두 Program의 공통 Baseline 역할을 한다고 설명합니다. 저희 같은 컨설팅 회사에는 "이 Service가 Kubernetes에서 올바르게 동작하는가"에 대해 Code Review의 의견이 아니라 검증 가능한 답을 줄 수 있는 미래를 뜻합니다.

## Workload 계약이 다룰 만한 내용

Spec이 없으므로 운영 환경에서 실제로 무엇이 깨지는지에 대한 경험에 의존할 수밖에 없습니다. 아래는 저희가 프로젝트마다 점검하는 항목이며, 어떤 Workload 표준이든 다루게 될 가능성이 높다고 봅니다.

1. **Graceful termination.** Process가 `SIGTERM`을 처리하고, 새 작업 수신을 멈추고, 처리 중인 Request를 마무리한 뒤, `terminationGracePeriodSeconds`가 끝나기 전에 종료합니다.
2. **Health 신호.** Readiness는 트래픽을 받을 수 있는지를 나타내고, Liveness는 복구할 수 없는 상태만 감지합니다. 시작이 느리다면 Liveness 지연을 늘리지 않고 Startup probe를 사용합니다.
3. **Resource 선언.** Request와 Limit을 설정해 Scheduler와 Autoscaler가 합리적인 판단을 하게 합니다.
4. **중단 내성.** 가용성이 필요한 곳에서는 Replica를 둘 이상으로 하고, `PodDisruptionBudget`으로 Node Drain 때 Service가 내려가지 않게 합니다.
5. **최소 권한.** 비 root 사용자, 권한 상승 금지, Application이 허용하는 한 Read-only root filesystem.
6. **Stateless 또는 선언된 State.** 로컬 디스크는 임시 저장소로 취급하고, 영속 Data는 선언된 Volume에 둡니다.

## Baseline Manifest

안정적이고 문서화된 Field만 사용했습니다. 표준이 아니라 출발점입니다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 3
  selector:
    matchLabels: { app: api }
  template:
    metadata:
      labels: { app: api }
    spec:
      terminationGracePeriodSeconds: 30
      securityContext:
        runAsNonRoot: true
        seccompProfile: { type: RuntimeDefault }
      containers:
        - name: api
          image: registry.example.com/api@sha256:REPLACE_WITH_DIGEST
          ports:
            - containerPort: 8080
          resources:
            requests: { cpu: 250m, memory: 256Mi }
            limits: { memory: 512Mi }
          startupProbe:
            httpGet: { path: /healthz, port: 8080 }
            failureThreshold: 30
            periodSeconds: 2
          readinessProbe:
            httpGet: { path: /ready, port: 8080 }
            periodSeconds: 5
          livenessProbe:
            httpGet: { path: /healthz, port: 8080 }
            periodSeconds: 10
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities: { drop: ["ALL"] }
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api
spec:
  minAvailable: 2
  selector:
    matchLabels: { app: api }
```

CPU Limit을 일부러 생략했다는 점에 유의하십시오. CPU Limit은 원인을 찾기 어려운 Throttling을 일으키므로 Memory Limit이 더 안전한 장치라고 판단합니다. 이는 판단이 갈리는 부분이며 Workload에 따라 다를 수 있습니다.

## 종료 경로 Test

Graceful termination은 Deploy나 Drain 때에만 실패가 드러나기 때문에 가장 자주 생략되는 항목입니다. 간단한 점검 방법은 Container를 띄우고 `SIGTERM`을 보낸 뒤 종료 시간과 Exit code를 검증하는 것입니다.

```bash
#!/usr/bin/env bash
set -euo pipefail

IMAGE="$1"
CID=$(docker run -d "$IMAGE")
trap 'docker rm -f "$CID" >/dev/null 2>&1 || true' EXIT

sleep 3
start=$(date +%s)
docker kill --signal=SIGTERM "$CID" >/dev/null
code=$(docker wait "$CID")
elapsed=$(( $(date +%s) - start ))

echo "exit code: $code, shutdown took ${elapsed}s"
[ "$elapsed" -le 25 ] || { echo "shutdown too slow"; exit 1; }
[ "$code" -eq 0 ] || { echo "non-zero exit on SIGTERM"; exit 1; }
```

배포 직전의 Image를 대상으로 CI에서 실행하십시오. `SIGTERM`을 무시하는 Service는 유예 시간이 지나면 강제 종료되어 처리 중이던 작업을 잃게 됩니다.

## CI에서의 Manifest 검증

선언적인 부분은 Test용 Cluster에 대한 Server-side dry run으로 Schema 오류를 잡고, Policy Tool로 Baseline을 검증할 수 있습니다. Kyverno나 OPA Gatekeeper를 쓰고 있다면 위 항목을 각각 Policy로 표현하고 먼저 Audit 모드로 운영하십시오. 누구도 막지 않으면서 기존 Workload 중 몇 개가 위반하는지 보여 주므로, 도입 논의가 구체적이 됩니다.

```bash
kubectl apply --dry-run=server -f k8s/
```

## webhani의 권장 사항

- Spec을 기다릴 필요는 없습니다. 위의 동작들은 그 자체로 가치가 있고, 합리적인 표준과 상충할 가능성은 낮다고 봅니다.
- Baseline을 짧은 Checklist로 정리해 CI에서 강제하십시오. Wiki에만 있는 Checklist는 표준이 아닙니다.
- 종료 경로 Test와 PodDisruptionBudget부터 시작하십시오. 이 두 가지가 Deploy 시점 장애의 대부분을 막아 줍니다.
- Platform 인프라를 운영한다면 Working Group의 동향을 따라가십시오. 격주 수요일 15:00 UTC에 열리며 Slack의 `#wg-workload-conformance` 채널에서 연락할 수 있습니다.
- 최종 Spec에 대한 주장은 저희 것을 포함해 Draft가 공개되기 전까지는 잠정적인 것으로 취급하십시오.

핵심은 개념의 전환입니다. 오랫동안 "Kubernetes에서 동작한다"는 "누군가 어떻게든 띄웠다"는 뜻이었습니다. Workload 표준은 초기 단계라 하더라도 업계를 검증 가능한 방향으로 이끕니다. Spec보다 먼저 준비하는 데 드는 비용은 Manifest 몇 군데의 수정과 CI Job 하나면 충분합니다.
