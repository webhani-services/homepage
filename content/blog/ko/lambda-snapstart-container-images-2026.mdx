Lambda 함수를 설계할 때 팀들은 초기에 거의 되돌리기 힘든 선택을 해야 했습니다. ZIP Archive로 패키징해서 SnapStart의 Sub-second 콜드 스타트를 확보하거나, 컨테이너 이미지로 패키징해서 무거운 의존성을 담는 대신 콜드 스타트가 몇 초씩 걸리는 걸 감수하거나, 둘 중 하나였습니다. 2026년 AWS는 이 간극을 메꿨습니다. SnapStart를 컨테이너 이미지로 패키징된 Lambda 함수까지 확장한 것입니다(aws.amazon.com/about-aws/whats-new/2026/07/aws-lambda-snapstart-container/, 2026년 9월 InfoQ에서도 추가로 다뤘습니다). 발표 자체는 담백해 보이지만, ML이나 데이터 처리 위주의 Serverless Workload 설계를 오랫동안 제약해온 조건 하나가 사라졌다는 점에서 의미가 있습니다.

## 이 Tradeoff가 왜 존재했나

SnapStart는 함수를 한 번 초기화한 뒤, 완전히 부팅이 끝난 실행 환경(메모리, 디스크 상태, 로드된 클래스/모듈)의 Snapshot을 찍어 캐싱하는 방식으로 동작합니다. 이후 콜드 스타트가 발생하면 초기화 코드를 처음부터 실행하는 대신 이 Snapshot에서 바로 재개(Resume)합니다. 특히 JVM 기반 Workload에서 효과가 컸는데, 클래스 로딩과 JIT Warmup이라는 가장 비싼 작업이 Snapshot을 찍기 전에 이미 끝나 있기 때문에, 몇 초 걸리던 콜드 스타트가 200~400ms 수준으로 줄어들었습니다.

문제는 패키징 방식이었습니다. SnapStart는 원래 Lambda의 Managed ZIP Runtime(Java가 먼저, 이후 Python과 .NET이 추가)에만 적용됐고, ZIP Archive는 압축 해제 기준 250MB가 상한선입니다. 반면 컨테이너 이미지는 10GB까지 지원합니다. 즉 큰 ML 모델이나 무거운 Native Library(OpenCV, CUDA Runtime, System Library까지 포함한 pandas/numpy/scipy 스택 등)를 쓰는 함수는 250MB를 넘는 순간 선택지가 컨테이너 하나뿐이었습니다. SnapStart는 못 쓰고, 콜드 스타트는 그대로——웬만한 처리에도 몇 초가 걸렸고, Provisioned Concurrency를 쓰는 것 외에는 우회할 방법이 없었습니다.

이 Tradeoff 때문에 설계 초기 단계에서 "작고 빠르게 갈지, 크고 느리게 갈지"를 미리 정해야 하는 경우가 많았습니다. 어느 쪽도 절대적으로 틀린 선택은 아니었지만, 상당수 팀이 ZIP 용량 제한을 피하려고 논리적으로는 하나였어야 할 함수를 "가벼운 Hot Path용 Lambda"와 "따로 Warm-up해야 하는 무거운 Service"로 쪼개는 과설계를 하곤 했습니다.

## 무엇이 달라졌나

컨테이너 이미지 SnapStart 지원으로 대부분의 경우 이런 분리가 더 이상 필요 없어졌습니다. 2~3GB짜리 컨테이너 이미지에 모델과 의존성 전체를 담아도 콜드 스타트 시 Snapshot/Resume의 이점을 그대로 받을 수 있습니다. Snapshot은 컨테이너의 초기화 완료 상태——초기화 코드가 메모리에 로드한 내용까지 포함해서——를 그대로 캡처한다는 점에서, 기존 ZIP 패키징 Java에서 동작하던 방식과 동일합니다.

다만 Runtime별로 지원 방식은 다릅니다. Java 11+, Python 3.12+, .NET 8+의 AWS 제공 Base Image는 기존 ZIP 기반 SnapStart와 거의 동일하게 별다른 작업 없이 동작합니다. 그 외——Node.js, Ruby, Go, 완전한 Custom Runtime——는 Dockerfile Label을 통한 명시적 Opt-in이 필요하고, 경우에 따라 Snapshot 대상과 시점을 제어하는 Runtime Hook 구현까지 필요합니다.

Region 지원은 거의 다 됐지만 전부는 아닙니다. 2026년 9월 기준 보도에 따르면 Asia Pacific(New Zealand)와 Asia Pacific(Taipei)를 제외한 모든 상용 AWS Region에서 사용 가능합니다. 이 두 Region에서 운영 중이라면 아키텍처를 확정하기 전에 확인해볼 가치가 있습니다.

## 구체적인 예시: Python ML Inference 함수

Fine-tuning된 문장 임베딩 모델의 Inference를 서빙하는 함수를 생각해보겠습니다. 모델 가중치만 수백 MB에, `torch`, `transformers`와 그 Native 의존성까지 더해집니다. 이 정도면 250MB를 가볍게 넘기 때문에, 지금까지는 컨테이너로 패키징하는 수밖에 없었고, Scale-out될 때마다 4~8초 콜드 스타트를 감수하거나 콜드 스타트를 아예 숨기려고 Provisioned Concurrency를 24시간 돌려야 했습니다.

컨테이너 SnapStart를 적용하면 흐름은 다음과 같습니다.

- 동일한 컨테이너 이미지(Python 3.12+ Base)를 빌드합니다.
- 모델 로딩과 Library Import는 Handler 밖, 초기화 코드에서 한 번만 실행합니다.
- 첫 호출 이후 AWS가 이 초기화된 환경의 Snapshot을 찍습니다.
- 이후 콜드 스타트는 Snapshot에서 Resume——모델은 이미 메모리에, Library는 이미 Import된 상태——되면서, JVM SnapStart 사용자들이 누려온 것과 비슷한 Sub-second 범위에 도달합니다.

실무적으로는 콜드 스타트를 감추려고 Idle 상태의 Provisioned Concurrency에 계속 비용을 지불할 필요가 없어지고, ZIP Archive에 맞추려고 의존성을 억지로 줄일 필요도 없어집니다. Burst성 Inference 트래픽——Lambda의 종량제 모델이 원래 가장 유리한 패턴——에는 실질적인 이득입니다.

## Dockerfile 패턴: Java/Python/.NET 외 Runtime에서 Opt-in하기

"별다른 작업 없이 되는" 목록에 없는 Runtime은 SnapStart 지원을 명시적으로 선언해야 합니다. Custom Runtime이나 Node.js 기반 Runtime에서 흔히 쓰이는 패턴은 다음과 같습니다(예시이며, 실제 Hook Contract는 사용 중인 Base Image의 문서를 확인해야 합니다).

```dockerfile
FROM public.ecr.aws/lambda/nodejs:20

# 컨테이너 이미지에서 SnapStart를 활성화하는 Opt-in
LABEL "aws.lambda.snapstart"="enabled"

# 의존성은 콜드 스타트 시점이 아니라 Build 시점에 설치
COPY package.json package-lock.json ./
RUN npm ci --omit=dev

COPY app/ ./app/

# 초기화 시점의 Side Effect(Connection, Cache 등)가
# Snapshot에 암묵적으로 박히지 않도록
# beforeCheckpoint / afterRestore Hook을 명시적으로 등록
COPY snapstart-hooks.js ./
ENV AWS_LAMBDA_EXEC_WRAPPER=/opt/snapstart-wrapper

CMD ["app/handler.main"]
```

중요한 건 정확한 Label 문법(이건 Runtime과 Base Image마다 다릅니다)이 아니라 개념입니다. 이미지 안의 어딘가가 "이건 Snapshot 대상이다"라고 명시적으로 표시해야 하고, Runtime Hook을 지원하는 경우라면 Checkpoint/Restore Lifecycle Event에 대한 Callback도 등록해야 합니다. 이걸 생략하면 아예 Snapshot이 찍히지 않거나, 더 나쁘게는 코드가 준비되지 않은 암묵적 전제를 깔고 Snapshot이 찍혀 버립니다.

## 함정: 초기화 코드의 멱등성(Idempotency)

이 부분은 팀들이 자주 놓치는 지점이고, ZIP 기반 SnapStart에도 이미 있던 함정이 컨테이너 지원으로 더 넓은 Workload에 적용되는 것뿐입니다. Snapshot을 찍기 전에 초기화 코드가 하는 일은 그대로 Snapshot에 박혀서 Resume될 때마다 재생됩니다. 모델을 메모리에 로드하거나 Library를 Import하는 정도는 문제없습니다——둘 다 외부 입장에서 결정적(Deterministic)이고 Side Effect가 없는 작업이기 때문입니다.

문제가 되는 경우는 다음과 같습니다.

- **초기화 시점에 Secret이나 인증 정보를 캐싱하는 경우.** 초기화 중에 Database Password나 API Key를 가져와서 그게 Snapshot에 포함되면, Rotation 이후에도 모든 Resume된 Instance가 동일한 캐싱된 값으로 계속 동작하게 됩니다. Secret은 Snapshot 이전이 아니라 Resume 이후에 가져오거나, `afterRestore` Hook에서 갱신해야 합니다.
- **초기화 시점에 고유한 ID, Token, Random Seed를 생성하는 경우.** Snapshot을 찍기 전에 생성한 UUID나 Nonce는 그 Snapshot에서 Resume되는 모든 환경에서 동일한 값이 되어 버려, 고유성이라는 목적 자체가 무너집니다. 이런 생성은 Handler 안, 즉 Resume 이후로 옮겨야 합니다.
- **특정 시점을 전제로 한 Network Connection을 초기화 시점에 여는 경우.** Snapshot 이전에 맺은 TCP Connection이나 TLS Session은 Resume 이후에는 유효하지 않으며, 보통 Runtime Hook을 통해 다시 맺어야 합니다.

개념 자체는 새로울 게 없습니다. "Snapshot은 일시정지됐다가 재개되는 Process다"라는, Firecracker 기반 SnapStart가 원래부터 가지고 있던 Mental Model 그대로입니다. 다만 컨테이너 이미지가 등장하면서 이런 초기화 시점 Side Effect를 가지기 쉬운 Workload(ML Pipeline, 초기화가 무거운 데이터 처리 함수 등)가 더 많이 대상에 들어온다는 점이 다릅니다.

## webhani의 판단: 언제 쓰고, 언제 다른 걸 쓸까

저희는 "의존성이 250MB ZIP에 안 들어갈 만큼 크다"는 조건과 "호출하는 쪽 입장에서 콜드 스타트 지연이 실제로 문제가 된다(Interactive API, 사용자 대상 Inference, SLA가 빡빡한 경우 등)"는 조건이 동시에 맞을 때 컨테이너 SnapStart를 권합니다. 둘 중 하나만 해당한다면 보통 더 저렴한 대안이 있습니다.

- **의존성은 크지만 콜드 스타트는 상관없는 경우**(Batch Job, 비동기 처리 등): 그냥 기존 컨테이너 이미지로 가면 됩니다. SnapStart 도입은 불필요합니다. 필요 없는 Snapshot/Resume 복잡도를 들일 이유가 없습니다.
- **콜드 스타트는 중요한데 의존성은 작은 경우**: ZIP 패키징 + SnapStart(Java/Python/.NET) 조합이 더 단순하고, Lifecycle Hook이 들어간 Dockerfile보다 디버깅할 게 적습니다.
- **지속적이고 예측 가능한 High Traffic**: 콜드 스타트가 실질적으로 거의 발생하지 않는 상황이라면 Provisioned Concurrency나 상시 가동되는 Fargate Service가 SnapStart보다 비용 효율적일 수 있습니다. SnapStart의 가치는 Burst성, Spike성, 저빈도 호출 패턴——즉 24시간 Warm 상태를 유지하는 게 낭비인 경우——에서 나옵니다.
- **매우 오래 실행되거나 Stateful한 Workload**: Lambda의 15분 실행 제한과 SnapStart의 요청 단위 Resume 모델은 패키징 방식과 무관하게 애초에 맞지 않습니다. 이런 경우는 Fargate나 ECS 영역입니다.

도입하기 전에는 반드시 초기화 코드를 위 멱등성 관점에서 감사(Audit)해야 합니다. 이건 팀들이 흔히 건너뛰는 단계이면서, 나중에 Production 장애로 이어지기 가장 쉬운 부분입니다. 검토 자체는 짧게 끝나지만, SnapStart가 깔끔하게 이득이 되느냐 아니면 3개월 뒤 오래된 인증 정보 Bug의 원인이 되느냐를 가르는 지점입니다.
