## 숫자가 말해주는 것

Truffle Security는 2026년 8월, git commit 이력·Hugging Face 데이터셋·Docker Image·Package Registry·CI/CD 로그 등 공개 소스에서 수집된 10,616건의 유출 AWS 자격증명 쌍을 재검증한 Research를 발표했습니다. 대상은 2022년 8월부터 2026년 8월까지 축적된 것들입니다. Report에 따르면 검증 대상의 약 88%가 여전히 인증에 성공했습니다. 활성 상태였던 기업 관련 Key 중 526건은 AWS Root Access Key였고, 242건은 `AdministratorAccess` Policy를 가진 IAM User에 속해 있었습니다.

이 샘플 뒤에 있는 전체 데이터셋은 더 방대해서, 431,875건의 공개 발견물 중 64,024개의 고유한 AWS Key 쌍이 있었고 그중 10,000건 이상이 Root 자격증명이었습니다. 이 Report에서 가장 시사하는 바가 큰 통계는 유출 건수 자체가 아닙니다 — 공개된 자격증명 유출 자체는 새로운 이야기가 아닙니다 — 바로 연령 분포입니다. 유출된 Key의 중앙값은 5년 전 것이었고, 가장 오래된 것은 17.4년 전으로 거슬러 올라갑니다. Access Key 열거가 가능했던 2,903건의 하위 집합 중, 새로운 Replacement Key가 발급된 경우는 13.7%에 불과했습니다. 즉, 이 자격증명들의 압도적 다수는 유출 이후 한 번도 rotate되지 않았고, 많은 경우 애초에 한 번도 rotate된 적이 없었을 가능성이 높습니다.

## 왜 유출이 몇 년씩 유효한 채로 남는가

여기서의 기술적 메커니즘은 정교하지 않습니다 — 프로세스의 부재입니다. 공개 Repository에 commit된 Key, Docker Image 레이어에 박혀 있는 Key, CI 로그에 출력된 Key는 노출 직후 거의 즉시 scanner(방어 측 Tool이든 공격 측 Tooling이든)에 의해 색인됩니다. 실제 피해 범위를 결정하는 것은 유출이 일어나느냐(Engineer가 몇 명만 넘어가도 모든 조직에서 유출은 끊임없이 일어납니다)가 아니라, 노출 이후 그 자격증명이 얼마나 오래 유효한 상태로 남아 있느냐입니다.

유출된 Key를 몇 년씩 살려두는 데는 세 가지 요인이 복합적으로 작용합니다.

**노출 시 자동 Revocation이 없습니다.** 고객이나 연구자, 공격자의 신고로 뒤늦게 유출을 발견하는 조직은 이미 뒤처진 상태입니다. GitHub의 Native Secret Scanning과 Push Protection은 commit 시점의 일부 유출을 잡아내지만, Docker Image 레이어에 박힌 Key나 Application 로그에 출력된 Key는 Source 수준 Scanning을 완전히 우회합니다.

**정기적인 Rotation 기준이 없습니다.** Key가 알려진 인시던트에 대한 대응으로만 rotate된다면, 인시던트 탐지율이 낮을수록 rotation 빈도도 그에 따라 낮아집니다. 5년 전 생성되어 한 번도 rotate되지 않은 Root Key는 드문 사례가 아니라, 이 데이터셋의 중앙값 사례입니다.

**Root Key와 과도한 권한의 IAM User가 실제 운영에서 사용되고 있습니다.** 이 정도 규모의 샘플에서 526건의 활성 Root Key가 발견된 것은 유출 건수 자체보다 더 경계해야 할 수치입니다. AWS는 수년간 프로그래밍 방식 접근에 Root Access Key를 사용하지 말 것을 권고해 왔습니다. 이런 Key가 여전히 존재한다는 것은, 많은 조직이 Legacy Tooling 때문에 Root Key에서 벗어나지 못했거나, 일회성 작업을 위해 한 번 만들어두고 삭제를 잊었음을 시사합니다.

## CI/CD 실무에서 달라져야 할 것

AWS Workload를 CI/CD로 운영하는 팀에게 실무적인 교훈 자체는 새롭지 않지만, 이 데이터는 실제로 그것을 구현하게 만드는 좋은 계기가 됩니다.

**장기 유효한 Access Key 대신 OIDC 기반의 단기 자격증명으로 전환하세요.** GitHub Actions, GitLab CI를 비롯한 대부분의 현대적인 CI Platform은 AWS와의 OpenID Connect Federation을 지원하여, Pipeline이 정적인 Key를 Secret으로 저장하지 않고도 단일 실행 동안만 IAM Role을 assume할 수 있습니다.

```yaml
# GitHub Actions — OIDC 기반 AWS 인증, 저장된 Access Key 없음
permissions:
  id-token: write
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/ci-deploy-role
          aws-region: ap-northeast-1
      # AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY Secret 자체가 존재하지 않으므로 유출될 것이 없음
```

**Root Access Key를 완전히 삭제하세요.** AWS IAM은 Root Access Key를 아예 비활성화하거나 삭제할 수 있게 해줍니다. CI/CD를 포함한 일상적인 운영에서 Root Key가 필요한 경우는 없어야 합니다. Legacy Script가 여전히 Root Key에 의존한다면, 그것은 마이그레이션 대상 Task이지 Key를 활성 상태로 유지할 이유가 아닙니다.

**Source Code뿐 아니라 그 이상에도 Secret Scanning을 적용하세요.** 이번 유출의 상당 부분이 git 이력뿐 아니라 Docker Image, Package Registry, CI/CD 로그에서 발생했기 때문에, Scanning은 commit만이 아니라 Build Artifact까지 포괄해야 합니다. TruffleHog, Gitleaks, 또는 AWS 자체의 IAM Access Analyzer 같은 Tool을 Build Pipeline에 연동해, Image 레이어나 로그 출력에서 자격증명 패턴이 감지되면 Build를 실패시킬 수 있습니다.

**인시던트 탐지와 무관한 Rotation SLA를 설정하세요.** Legacy 사유로 장기 유효 Key를 써야 하는 IAM User라도, Key의 최대 유효 기간(보통 90일을 기준으로 삼습니다)을 강제하고, 누군가 Key가 오래됐다는 것을 알아차리는 데 의존하지 않는 자동 Rotation 또는 만료 처리가 있어야 합니다.

## 5년 된 Key는 불운이 아니라 Policy의 실패입니다

이 Research에서 얻을 수 있는 가장 유용한 관점은 "유출은 일어난다"가 아닙니다 — 어떤 조직의 위협 모델이든 이미 그것을 전제로 하고 있습니다. 중요한 것은, 유출된 자격증명이 5년간 rotate되지 않은 채 살아남았다는 사실 자체가 두 가지의 부재를 보여준다는 점입니다. Source뿐 아니라 Build Artifact 전반에 걸친 자동 노출 탐지, 그리고 누군가 수동으로 유출을 알아차리는 데 의존하지 않는 Rotation Policy입니다.

AWS Infrastructure로 협업 중인 Client에게 현재 권장하는 감사는 범위가 좁고 기계적입니다 — 장기 유효한 Access Key를 가진 모든 IAM User와 Role을 나열하고, 그중 Root Key가 없는지 확인하고, 마지막 Rotation 날짜를 90일 Policy와 대조하고, Secrets Manager나 더 나쁘게는 Pipeline 환경 변수에 놓인 정적 Key를 OIDC 기반 Role Assumption으로 전환하는 것입니다. 이 중 어느 것도 대부분의 팀이 아직 접근하지 못하는 새로운 Tooling을 필요로 하지 않습니다. 필요한 것은 자격증명 Rotation을 인시던트 대응이 아니라 정기적인 운영 Task로 취급하는 것뿐입니다.
