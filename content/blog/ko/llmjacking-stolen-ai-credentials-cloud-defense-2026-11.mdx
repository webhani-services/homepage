예전에는 Cloud 자격 증명이 유출되면 대개 암호화폐 채굴로 이어졌습니다. 이 공식이 바뀌고 있습니다. Google Threat Intelligence Group(GTIG)과 Mandiant가 11월 2일 공개한 보고서에 따르면, 공격자들은 탈취한 Cloud Identity를 호스팅된 LLM에 대한 Access로 바꾸는 쪽을 선호하게 되었고, 그 주변에 재판매 시장까지 형성되었습니다. 보고서에 소개된 한 사례에서는 공격자 한 명이 8시간이 채 안 되는 동안 50만 회 이상 Model을 호출했고, 피해 조직에는 100만 달러에 가까운 Token 비용이 남았습니다. 하루에 10만 달러를 넘긴 사례도 여럿 있었다고 합니다.

금액도 놀랍지만, 개발 조직 입장에서 더 중요한 것은 구조의 변화입니다. LLMjacking은 더 이상 "Key가 유출되어 우연히 생기는 일"이 아니라, 역할이 분업화된 공급망이 되었습니다.

## 시장은 어떻게 분업되어 있나

보고서는 두 가지 역할을 구분합니다.

- **침투 담당**: 자격 증명을 확보합니다. 주요 진입점은 익숙한 것들입니다. IAM Access Key, Service Account Key 파일, GitHub Personal Access Token, 유효한 Session Token 등입니다.
- **"LLM Mixer"**: 수집한 자격 증명을 오픈소스 API Gateway와 자체 Relay 뒤에 Pool로 묶고, 사용량을 계량해 자기 고객에게 Model Access를 재판매합니다. 요청이 탈취된 Key Pool을 거쳐 라우팅되기 때문에 개별 호출의 출처를 추적하기 어렵습니다.

보도 내용 중 저희가 특히 주목한 점은 두 가지입니다.

1. **일부 피해 조직은 LLM Service를 한 번도 활성화한 적이 없었습니다.** 공격자가 탈취한 Identity로 Model Access를 직접 활성화했습니다. "우리는 Bedrock도 Vertex AI도 안 쓴다"는 방어가 아니라 사각지대입니다.
2. **AI Gateway 자체가 공격 대상이 되고 있습니다.** Self-hosted LiteLLM Gateway의 취약점으로 일반 Virtual Key가 Admin 권한으로 상승된 사례도 보고되었습니다. CVE 세부 내용이 어떻게 확정되든 교훈은 같습니다. 회사 전체의 Provider Key를 보관하는 Gateway는 고가치 자산이며, Identity Provider와 같은 수준의 Patch 관리가 필요합니다.

## 일반적인 Key 유출과 무엇이 다른가

Database 비밀번호가 유출되면 데이터가 노출됩니다. Model Access 권한을 가진 Cloud Identity가 유출되면 노출되는 것은 **예산**이고, 사람이 알아차리기 전에 빠르게 소진됩니다. LLM Inference는 Instance나 Cluster처럼 눈에 보이는 리소스를 만들지 않고도 하루 만에 수십만 달러를 청구하게 만들 수 있는 몇 안 되는 Cloud Service입니다. 하루 한 번 도는 비용 이상 탐지로는 늦습니다.

관심을 가져야 할 팀의 범위도 넓어집니다. AI 기능이 전혀 없는 팀이라도, Model을 활성화하고 호출할 수 있는 Principal이 하나만 있으면 공격이 성립합니다.

## 권장하는 통제 방안

새로운 아이디어는 아닙니다. 달라진 것은 우선순위입니다.

### 1. 필요 없는 곳에서는 Model 호출을 차단합니다

AWS에서 가장 깔끔한 방법은 Inference를 할 이유가 없는 OU에 Service Control Policy(SCP)를 적용하는 것입니다. Principal이 `AdministratorAccess`를 갖고 있더라도 탈취된 자격 증명 경로를 막을 수 있습니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyBedrockOutsideAIWorkloads",
      "Effect": "Deny",
      "Action": [
        "bedrock:InvokeModel",
        "bedrock:InvokeModelWithResponseStream",
        "bedrock:PutFoundationModelEntitlement",
        "aws-marketplace:Subscribe"
      ],
      "Resource": "*"
    }
  ]
}
```

"legacy", "data-platform", "sandbox" 같은 OU에 적용하고, Inference는 AI Workload 전용 Account(또는 OU)에서만 허용합니다. Third-party Model Access는 Marketplace 구독으로 제어되는 경우가 많아 `aws-marketplace:Subscribe`도 포함했습니다. SCP는 범위 내 모든 Principal에 영향을 주므로 반드시 비운영 OU에서 먼저 Test하십시오.

Google Cloud에서는 Project 단위 IAM에 의존하기보다, Organization Policy로 Vertex AI API를 활성화할 수 있는 Project를 제한하는 것이 같은 효과를 냅니다.

### 2. CI에서 장기 Key를 없앱니다

보고서에서도 CI Secret에 저장된 GitHub PAT와 정적 Cloud Key가 주요 탈취 경로로 꼽힙니다. Pipeline에서 아직 `AWS_ACCESS_KEY_ID`를 사용한다면 OIDC Federation으로 전환해 훔쳐갈 장기 자격 증명 자체를 없애야 합니다.

```yaml
permissions:
  id-token: write
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/gha-deploy
          aws-region: ap-northeast-1
```

Role의 Trust Policy는 특정 Repository와 Branch로 한정하고, Deploy에 꼭 필요하지 않다면 Bedrock 권한은 부여하지 않습니다.

### 3. History까지 포함해 Secret을 Scan합니다

몇 달 전에 유출된 Key도 Rotation하지 않았다면 여전히 유효합니다. Working Tree뿐 아니라 Git History 전체를 Scan합니다.

```bash
gitleaks git . --redact --report-path gitleaks-report.json
```

탐지된 Key는 Repository에서 지우는 데 그치지 말고 반드시 Rotation해야 합니다. Commit된 Key를 삭제해도 이미 수집된 사본에는 아무 영향이 없습니다.

### 4. 비용 Alert는 "일"이 아니라 "시간" 단위로

AI를 사용하는 Account마다 낮은 임계값으로 Budget Alert를 설정하고, 실제로 누군가 확인하는 Channel로 보내십시오. Provider 측 통제도 효과적입니다. LLM Gateway에서 Key별 사용 한도와 Rate Limit을 걸어두면 100만 달러짜리 사고를 상한이 있는 사고로 바꿀 수 있습니다. LiteLLM 같은 Proxy를 운영한다면 Key별 Budget을 설정하고, Admin/Master Key는 Application 환경에 절대 두지 마십시오.

### 5. AI Gateway를 Tier-0 Infrastructure로 취급합니다

- SSO나 Secret Manager와 같은 주기로 Patch합니다.
- Admin API를 Internet에 노출하지 않습니다.
- Key 생성과 권한 변경을 Logging하고 Alert를 설정합니다.

## 이번 주에 확인할 것

한 시간밖에 없다면 다음 네 가지만이라도 확인하십시오.

- Model Access가 활성화된 Account/Project 목록을 뽑습니다. 예상하지 못한 항목이 있다면 Shadow AI이거나 공격자입니다.
- Model을 호출할 수 있는 모든 Account에 Budget Alert가 있는지 확인합니다.
- CI 설정에 정적 Cloud Key나 GitHub PAT가 남아 있는지 검색합니다.
- Self-hosted LLM Gateway의 Version을 Security Advisory와 대조합니다.

## 정리

LLMjacking은 단발성 사고에서 자격 증명 탈취와 재판매가 분업화된 "산업"으로 바뀌었습니다. 현실적인 대응은 화려하지 않습니다. 쓰지 않는 곳에서는 Inference를 차단하고, 장기 자격 증명을 없애고, 의미 있는 속도로 비용 Alert가 울리게 하는 것입니다. webhani는 Cloud 보안 Review에서 "이 Identity가 운영 데이터를 읽을 수 있는가"와 함께 "이 Identity가 Model을 호출할 수 있는가"를 표준 확인 항목으로 다루고 있습니다. 두 답 모두 의도적으로 결정된 것이어야 합니다.
