## 오래 유지되는 Connection에서, 어디로 라우팅되어도 되는 Request로

Model Context Protocol은 등장한 이후 LLM Agent를 외부 Tool과 Data에 연결하는 Default 방식으로 자리 잡았고, Claude의 Connector Directory에만 이미 950개가 넘는 Server가 등록되어 있습니다. 2026-07-28 개정판은 초기 설계 이후 Protocol 구조에서 가장 큰 변화입니다. 기존 MCP Server가 의존하던 `initialize` Handshake와 `Mcp-Session-Id` Header를 없애고, 어떤 Request든 어떤 Server Instance에 도착해도 되는 Stateless Request/Response Model로 대체했습니다.

MCP Server를 구현하거나 운영해 본 적이 있다면 이 문장은 한 번 곱씹어볼 가치가 있습니다. Stateful한 Protocol은 첫 Message를 처리한 Server Instance가 다섯 번째 Message도 처리한다고 전제합니다. Stateless는 그 반대입니다. 전제도 없고 Sticky Session도 없으며, 직접 어딘가에 영속화하지 않는 한 Call마다 공유되는 In-Memory State는 없습니다. 이건 의도된 Trade-off입니다. Session Affinity가 걸린 Load Balancer 뒤에 오래 실행되는 Process 집합을 고정된 개수로 유지할 필요 없이, 다른 Stateless HTTP API와 마찬가지로 Serverless나 Edge Infrastructure 위에서 확장할 수 있게 해줍니다.

## 실제로 깨지는 부분

가장 먼저 영향을 받는 것은 `initialize` 이후 Process 안의 Map에 Auth Context를 Caching하거나, 여러 Request에 걸쳐 부분적으로 완성된 Tool Call State를 들고 있는 식으로 조용히 In-Memory Session State에 의존하던 Server입니다. 그런 State는 Stateless Core 아래에서는 살아남지 못합니다. 그 "Session"의 다음 Request가 기억이 없는 다른 Instance로 향할 수도 있기 때문입니다.

해결 자체는 특별하지 않지만, 실질적인 Migration이 필요합니다.

```ts
// Before: Server 로컬 Session State에 의존 (Stateless Core에서 깨짐)
const sessions = new Map<string, { authContext: AuthContext }>();

server.onRequest((req) => {
  const session = sessions.get(req.sessionId); // 더 이상 Session ID가 없음
  return handleToolCall(req, session.authContext);
});

// After: Auth Context를 Request마다 Token에서 해석, 공유 Memory 불필요
server.onRequest(async (req) => {
  const authContext = await resolveAuthContext(req.headers.authorization);
  return handleToolCall(req, authContext);
});
```

실무 원칙은 이렇습니다. Request N+1에 올바르게 응답하기 위해 필요한 정보가, Request N을 처리한 Process에만 존재해서는 안 됩니다. Request를 가로지르는 State — 여러 Step의 Workflow나 오래 걸리는 Job — 가 정말 필요하다면, 스펙이 제시하는 답은 임시방편 In-Memory Map이 아니라 새로 생긴 Tasks 확장입니다.

## Auth가 본격적으로 진지해졌다

두 번째 큰 변화는 Authorization입니다. 기존 MCP Auth는 개인이 자신의 API Key를 연결하는 정도에는 충분했지만, Enterprise가 실제로 Identity를 관리하는 방식과는 잘 맞지 않았습니다. 2026-07-28 스펙은 MCP의 Authorization Flow를 실제 운영 중인 OAuth 2.0/OIDC 배포에 맞췄습니다. 실무적으로는 MCP Server가 별도의 Custom Bridge 없이 Okta나 Entra ID 등 표준을 따르는 어떤 Identity Provider 뒤에도 놓일 수 있다는 뜻입니다.

저희가 내부에서 관리하는 Server 기준으로는, 대체로 독자적인 API Key 검사를 실제 Token 검증 Step으로 바꾸는 작업이 됩니다.

```ts
async function resolveAuthContext(authHeader?: string): Promise<AuthContext> {
  if (!authHeader?.startsWith("Bearer ")) {
    throw new McpAuthError("missing_token");
  }
  const token = authHeader.slice("Bearer ".length);
  const claims = await verifyJwt(token, { issuer: OIDC_ISSUER, audience: MCP_AUDIENCE });
  return { userId: claims.sub, scopes: claims.scope?.split(" ") ?? [] };
}
```

단일 User가 아니라 Team을 위해 내부 System 앞단에 MCP Server를 두려고 했다면, 이건 순수하게 이득입니다. 직접 구현할 필요 없이 표준 Token 만료, 표준 Scope 검사, 표준 Revocation을 그대로 얻을 수 있습니다.

## Apps와 Tasks — Core를 건드리지 않고 기능을 추가하기

누군가 새 기능을 원할 때마다 Base Protocol을 계속 키우는 대신, 이번 스펙은 Version이 관리되는 확장 Framework를 도입했습니다. 먼저 알아둘 것은 MCP Apps입니다. Server가 Client에게 Text나 JSON만 돌려주는 대신 Form, Picker, 작은 Dashboard 같은 Interactive UI를 넘겨주는 방식을 표준화합니다. MCP Tasks는 오래 걸리는 비동기 작업을 표준화합니다. Tool Call이 Job을 시작시키고, Client가 완료를 Polling하거나 구독할 수 있게 해서, Connection을 계속 열어두거나 Block할 필요가 없어집니다.

둘 다 같은 이유로 중요합니다. 그동안 각 Team이 독자적으로, 대개는 Custom Webhook이나 Side Channel Polling Loop, 혹은 MCP의 Tool Call Response 위에 억지로 얹은 자체 UI Protocol로 임시 해결하던 것에, 문서화된 정식 방법을 제공해 줍니다.

## 기존 Server를 위한 Migration Checklist

이미 MCP Server를 운영 중이라면, 2026-07-28 스펙은 "나중에 하지 뭐"가 아니라 명시적인 점검 대상으로 다뤄야 합니다.

1. **Session State를 Grep 합니다.** Session ID를 Key로 삼거나 여러 Request에 걸쳐 Module Level 변수에 저장해 둔 부분을 찾아 Database, Cache, 혹은 Token Claim으로 옮깁니다.
2. **임시방편 Auth를 OIDC로 교체합니다.** 현재 고정 API Key를 검증하고 있다면, 실제 Identity Provider를 대상으로 한 Token 기반 Auth로의 전환을 계획합니다. Security Team이 가장 먼저 물어볼 변경 사항이기도 합니다.
3. **오래 걸리는 Tool Call을 재검토합니다.** 몇 초 이상 Block하던 Tool Call은 긴 HTTP Connection 대신 Tasks 확장의 후보로 둡니다.
4. **실제 Stateless 상태에서 재테스트합니다.** Session Affinity를 끈 Load Balancer 뒤에서, 혹은 서로 다른 두 Instance에 걸쳐 돌려본 뒤에야 Production에서 신뢰합니다. 스스로도 몰랐던 State를 드러내는 가장 빠른 방법입니다.

## 정리

- Stateless Core는 단순한 Version Up이 아니라 실질적인 Architecture 변화입니다. Production Server를 Upgrade하기 전에 숨어 있는 Session State를 점검하세요.
- OAuth 2.0/OIDC 지원은 Enterprise Team이 우선적으로 챙겨야 할 변화입니다. 내부 MCP Server를 단일 User 이상 규모에서 안전하게 운영할 수 있게 해줍니다.
- Apps와 Tasks는 Interactive UI와 비동기 Job을 위한 표준 수단입니다. 직접 우회 방법을 만들기 전에 먼저 확인하세요.
- Session Affinity를 끈 상태에서 명시적으로 Stateless 여부를 테스트하세요. 간단한 수동 확인을 통과했다고 해서 스펙을 준수한다고 단정하지 마세요.
