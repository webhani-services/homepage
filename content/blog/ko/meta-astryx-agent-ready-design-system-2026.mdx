## 두 종류의 사용자를 동시에 겨냥한 Design System

Meta는 2026년 6월 28일, StyleX 기반의 React 19 Design System인 Astryx를 Open Source로 공개했습니다. 150개 이상의 Accessible한 Component와 10가지 내장 Theme을 제공합니다. 이것만 보면 견고하지만 특별할 것 없는 Design System Release입니다 — 비슷한 수준의 Component Library를 공개한 회사는 이미 여럿 있습니다. Astryx가 눈여겨볼 만한 이유는, 그리고 이번 달 InfoQ가 다시 다룬 이유는, 이 Design System이 인간 Engineer와 오늘날 많은 회사에서 Frontend Code의 적지 않은 부분을 작성하고 있는 AI Coding Agent(Claude Code, Cursor, GitHub Copilot 등)라는 두 종류의 사용자를 명시적으로 겨냥해 만들어졌기 때문입니다.

## 'Agent 대응'이 구체적으로 가리키는 것

실질적인 역할을 하는 Feature는 두 가지입니다. 첫째는 Component 탐색, Layout Template 조회, 설정 읽기를 위한 구조화된 API를 제공하는 내장 MCP Server입니다. Agent가 Source Code를 grep하거나 Render된 Documentation Page를 긁어서 `<Card>` Component의 유효한 Prop을 추측할 필요가 없어집니다. 둘째는 `astryx` CLI의 `--dense` Flag로, Component Documentation에서 사람을 위한 설명 문구를 걷어내고 LLM의 Context Window에 딱 맞게 들어가는 Token 효율적인 Payload를 만들어 줍니다.

이 둘을 합치면 실제 현장에서 흔히 발생하는 실패 Pattern을 해결합니다. "우리 Design System으로 Modal을 추가해줘"라는 지시를 받은 Agent가 존재하지 않는 Prop을 Hallucination하거나, 정작 필요한 세 줄짜리 정보를 얻기 위해 Documentation Page 전체를 읽느라 Context Window의 상당 부분을 소모하는 문제입니다.

## 최소한의 예시로 보는 아이디어

이 Pattern 자체를 구현하는 데 Astryx가 꼭 필요한 것은 아닙니다. Agent를 위한 구조화된 Component Manifest는 대략 다음과 같은 형태입니다.

```json
{
  "component": "Modal",
  "props": {
    "open": { "type": "boolean", "required": true },
    "onClose": { "type": "() => void", "required": true },
    "size": { "type": "'sm' | 'md' | 'lg'", "default": "md" }
  },
  "slots": ["header", "body", "footer"],
  "a11y": "Traps focus, restores focus to trigger on close, closes on Escape"
}
```

MCP Tool 호출을 통해 이를 조회하는 Agent는 Codebase 안의 부분적으로 비슷한 다른 예제에서 Prop 이름을 추측하는 대신, 한 번에 올바른 Code를 생성하는 데 필요한 정보를 그대로 얻습니다. 이는 저희가 그동안 봐온 Agent 생성 UI Bug의 상당수가 실제로 발생하는 지점이기도 합니다.

## Component Library를 선택하는 Team에게 주는 의미

1. **'Agent 대응'은 단순한 화젯거리가 아니라 실질적인 평가 기준이 되고 있습니다**: Frontend PR의 적지 않은 비중을 Agent가 초안 작성하는 Team이라면, Agent가 구조적으로 조회할 수 있는 Design System이 Markdown Documentation에서 Prop을 추측하게 만드는 Design System보다 잘못된 Prop으로 인한 Bug가 줄어듭니다.
2. **간단한 버전은 직접 만들 수 있습니다**: 내부 Design System을 운영하고 있다면, 완전한 MCP Server 없이도 Component의 Props·Slot·Accessibility 계약을 JSON Manifest로 공개하는 것만으로, Codebase에서 작업하는 Agent에게 Storybook 설명 문구보다 훨씬 신뢰할 수 있는 정보 원천이 됩니다.
3. **Type 안전성을 대체하지는 않습니다**: TypeScript의 Prop Type은 이미 이 정보의 상당 부분을 Agent(그리고 사람)에게 무료로 제공합니다. Astryx 방식의 Manifest가 가장 가치 있는 지점은 Type으로 잘 표현되지 않는 부분 — Accessibility 동작, 조합 규칙, Type상으로는 가능하지만 실제로는 지원되지 않는 Prop 조합 — 입니다.

## Webhani의 시각

Astryx를 "도입해야 할 Design System"이라기보다 "Design System Tooling이 향하고 있는 방향을 보여주는 Signal"로 보는 편이 적절하다고 생각합니다. 사람이 읽기 쉬운 것보다 기계가 소비하기 쉬운 구조를 먼저 챙긴 Documentation이라는 뜻입니다. 이미 Claude Code 등으로 Frontend 작업의 일부를 맡기고 있는 Team이라면, Astryx의 개별 Component가 자사 Product에 맞는지 따지기 전에 이 Documentation 구조의 우선순위 자체를 먼저 받아들일 가치가 있습니다. 지금 이 시점에는 Component 개수가 조금 더 많은 Design System보다, Agent가 정확히 조회할 수 있는 Design System이 더 가치 있습니다.
