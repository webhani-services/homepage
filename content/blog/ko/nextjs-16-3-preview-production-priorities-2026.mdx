## Changelog은 마이그레이션 계획이 아닙니다

2026년 7월, Next.js 16.3이 Preview로 공개되었습니다. Changelog는 꽤 깁니다. Turbopack의 Persistent Build Cache, Rust 기반 React Compiler 지원, 더 똑똑한 Prefetch와 Streaming을 통한 "Instant Navigations", 그리고 Claude Code 같은 AI Coding Agent가 Next.js Codebase에서 더 잘 작동하도록 만드는 일련의 개선이 포함되어 있습니다. 7월 21일 즈음에는 Next.js 최초의 전용 Security Release도 나왔습니다.

하지만 이 목록만으로는 월요일 아침에 무엇부터 해야 할지 알 수 없습니다. 저희도 최근 자체 Homepage(바로 이 Site, Next.js 16 + React 19로 구축됨)를 대상으로 Upgrade 검토를 진행했는데, 실제로 도움이 된 질문들은 Changelog보다 훨씬 좁았습니다. Cache가 CI에서 구체적으로 무엇을 절약하는지, Compiler가 어딘가 동작을 바꾸는지, "Instant"한 Navigation이 정말 공짜인지, 그리고 이 모든 것이 AI 기반 구현 작업에 들이는 시간을 실제로 줄여주는지. 아래는 저희가 검토 과정에서 실제로 조치할 가치가 있다고 판단한 부분입니다.

## Persistent Build Cache — 무엇을 절약하고, 무엇은 절약하지 않는가

Turbopack의 In-Memory Cache는 하나의 Dev Session이나 하나의 CI Job 안에서는 항상 빨랐습니다. 다만 새로 Checkout한 직후, 새 Container, 처음부터 실행하는 `npm ci`에는 이 이점이 미치지 않았습니다. 16.3의 Persistent Cache는 Disk에 기록되고 재시작을 넘어서도 유지됩니다. 이것이 바꾸는 것은 구체적으로 두 가지입니다. 로컬 Dev Server 재시작(Branch 전환, `main` Pull, Crash 후 재시작)과 CI의 Cold Build입니다.

CI 쪽은 의도적으로 연결해 둘 가치가 있습니다. 현재 Pipeline이 매번 처음부터 Build한다면, `.next/cache`를 Build 사이에 복원하는 것이 지렛대가 됩니다.

```yaml
# .github/workflows/build.yml
- name: Restore Turbopack cache
  uses: actions/cache@v4
  with:
    path: .next/cache
    key: nextjs-${{ runner.os }}-${{ hashFiles('package-lock.json') }}-${{ github.sha }}
    restore-keys: |
      nextjs-${{ runner.os }}-${{ hashFiles('package-lock.json') }}-
      nextjs-${{ runner.os }}-

- name: Build
  run: npm run build
```

정말로 신경 써야 할 부분은 이 Cache가 무엇에 의해 Invalidate되는가입니다. `package-lock.json`만 Key로 삼으면 `next.config.mjs`, `tsconfig.json`, Build 시점 환경 변수 같은 Config 변경을 놓칩니다. Invalidate되어야 할 시점에 오래된 Cache가 재사용되면, 눈치채지 못한 채 낡거나 미묘하게 잘못된 Build 결과물이 나올 수 있습니다. `restore-keys`를 통한 Fallback은 Warm Start를 빠르게 하기 위한 편의로만 여기고, 정확성을 보장하는 장치로는 생각하지 마세요. Code 변경 내용과 Build 결과물이 일치하지 않는다면, 가장 먼저 의심할 것은 Cache Clear입니다.

## Turbopack의 Rust 경로에서 동작하는 React Compiler — 속도는 실제, 하지만 동작 확인이 먼저

React Compiler는 Component와 Hook을 자동으로 Memoization합니다. 정적 분석을 기반으로 Compile 시점에 `useMemo`, `useCallback`, `React.memo`에 해당하는 처리를 삽입해 주기 때문에, 불필요한 재 Render를 막기 위해 Dependency Array를 손으로 조정하는 작업에서 벗어날 수 있습니다. 이 부분 자체는 16.3에서 새로 생긴 것이 아닙니다. 새로운 것은 Turbopack이 JS 기반 Babel Plugin을 호출하는 대신, Compiler 자체를 Rust Pipeline 위에서 실행할 수 있게 되었다는 점입니다. 여기가 실제 Build 속도 향상이 발생하는 지점입니다. File마다 발생하는 Process 경계와 Serialization Overhead가 줄어들기 때문입니다.

신규 Project라면 Default로 켜두는 것이 합리적인 선택입니다.

```js
// next.config.mjs
/** @type {import('next').NextConfig} */
const nextConfig = {
  experimental: {
    reactCompiler: true,
  },
};

export default nextConfig;
```

반대로 규모가 큰 기존 Codebase에서는 하나의 PR로 Repo 전체에 한 번에 켜지 마세요. Compiler의 Memoization은 대상 Component가 Rules of React를 얼마나 따르고 있는지에 따라 안전성이 달라집니다. Props를 직접 Mutate하는 Code, Object의 동일성이 매번 바뀌는 것을 암묵적인 Invalidation Signal로 활용하는 Code, 특정 방식으로 항상 재 Render된다고 가정하는 Effect는 자동 Memoization 이후 동작이 달라질 수 있습니다. 실무에서 권장하는 방식은 Flag를 켠 다음, Merge 전에 기존의 Visual Regression이나 Interaction Test Suite를 돌리는 것입니다. 나중이 아니라 먼저입니다. 애초에 그런 Test Suite가 없다면, 그것이야말로 진짜 걸림돌이지 Compiler Flag가 문제가 아닙니다.

## Instant Navigations — 전제하지 말고 측정하세요

16.3의 Prefetch와 Streaming 개선은 더 적극적으로 Fetch하고, 완전한 Response가 준비되기 전부터 Streaming을 시작함으로써 Client Side Route 전환을 더 빠르게 느끼도록 만듭니다. 대부분의 경우 체감 성능 향상은 실제입니다. 전통적인 Core Web Vitals 3대 지표보다는 Navigation의 체감이나 INP에 더 가까운 영역이지만, "즉시처럼 느껴지는가"라는 관점에서는 같은 범주의 관심사입니다. 다만 공짜는 아닙니다. 더 많은 Route를 더 적극적으로 Prefetch한다는 것은, 사용자가 실제로는 방문하지 않을 Page에 대해서도 Server나 Edge Cache로의 Request가 늘어난다는 뜻입니다. Outbound Link가 많은 Site — 목록 Page에서 수십 개의 Blog 글로 Link가 걸린 Marketing Site가 꽤 구체적인 예입니다 — 에서는 제한 없는 Prefetch가 Origin Request 수와 대역폭의 의미 있는 증가로 이어질 수 있습니다.

구체적인 조치는 "Instant Navigations"를 당연한 이득으로 받아들이지 않는 것입니다. 더 적극적인 Prefetch를 켜기 전후로 Real User Monitoring을 통해 실제 Navigation Latency를 측정하고, 동시에 Server Request 양도 함께 확인하세요. Outbound Link가 50개를 넘는 Page라면, Framework의 Default가 모든 Page 형태에 맞다고 믿기보다, 우선순위가 낮은 Link에는 `prefetch={false}`를 지정하거나 Viewport 기반 Prefetch로만 제한하는 등 명시적으로 Prefetch의 범위를 좁히는 것을 고려하세요.

## AI Agent를 겨냥한 개선 — 조용히 가장 많은 시간을 아껴주는 부분

이 부분은 많은 팀이 그냥 지나치기 쉬운 Section이지만, 저희가 실제로 일하는 방식을 생각하면 가장 관련성이 높은 부분이라고 봅니다. 저희 구현 작업 중 Claude Code 같은 AI Coding Agent를 통해, 바로 이 Codebase에 대해 이루어지는 비중은 계속 늘어나고 있습니다. Agent의 수정 Loop에서 가장 큰 비용은 대개 Reasoning 능력의 문제가 아니라, Guess-and-Check를 반복하게 만드는 모호한 Error 출력입니다. 16.3의 Actionable한 Error Message와 함께 제공되는 Markdown 기반 Docs는 바로 이 간극을 좁히는 것을 목표로 합니다.

현실적인 구체 사례를 들어보겠습니다. `next/image`를 `fill`과 함께 사용하면서 `sizes` Prop을 지정하지 않은 Component는, 이전에는 일반적인 Console Warning만 보여주었고, Agent(또는 주니어 Engineer)는 근본 원인을 고치는 대신 너비와 높이를 임의로 지정한 값으로 대충 넘어가는 경우가 많았습니다. 정확한 Prop 이름, 정확한 File과 Line, 관련 Docs 위치까지 알려주는 Actionable한 Error라면 수정은 세 번의 시행착오가 아니라 한 번으로 끝납니다. Agent가 Error를 읽고 정확한 수정을 한 번에 적용한 뒤 다음으로 넘어가는 것과, 그럴듯한 수정을 여러 번 시도하며 매번 다시 Build해서 Warning이 사라지는지 확인하는 것은 누적되는 비용이 전혀 다릅니다. AI 기반 구현이 1년 동안 만들어내는 모호한 Error의 총량에 이를 곱해보면, Framework 차원에서 Agent가 읽기 쉬운 Error에 투자하는 것은 단순한 홍보 요소가 아니라 실질적인 생산성 항목이 됩니다.

## Security Release — 선택 사항으로 취급하지 마세요

7월 21일의 Security Release는 이 목록에서 가장 화려하지 않은 항목이면서, 판단의 여지가 가장 적은 항목이기도 합니다. Framework의 Security Patch는 "여유 있을 때 가져오면 좋은 것"이 아니라 정해진 일정의 Task입니다. 아직 이에 대한 명확한 주기를 정해두지 않았다면(저희는 주 단위로 Dependency Update Check를 돌리고, CI 통과를 조건으로 자동 PR을 Merge합니다) 지금 정하세요. Patch Release가 존재하는데 한 달간 Merge되지 않고 방치되는 것은 스스로 만든 취약점 창구이며, "기능 개발 Deadline 때문에 바빴다"는 Incident 이후에는 통하지 않는 변명입니다.

## 정리

- 먼저 Security Release를 위해 Upgrade하세요. 16.3의 다른 변경 사항과는 별도의, 독립된 PR로 처리합니다.
- Persistent Build Cache는 지금 바로 CI에 연결하세요. Risk는 낮고, 위 GitHub Actions 예시는 거의 그대로 적용할 수 있습니다. 다만 Cache Key가 Config나 환경 변수 변경을 포괄하지 못한다면 낡은 Build의 증상이 나타나는지 주의하세요.
- React Compiler는 신규 Project에서는 Default로 켜세요. 기존의 대규모 Codebase에서는 Repo 전체에 Merge하기 전에 Rendering Regression Test를 거치는 방식으로 단계적으로 시범 적용하세요.
- "Instant Navigations"를 무조건적인 이득으로 전제하지 마세요. 특히 Link가 많은 Page에서는 활성화 전후로 실제 Navigation Latency와 Server Request 양을 측정하세요.
- AI Coding Agent를 통한 구현 작업이 의미 있는 비중을 차지하는 팀이라면, Actionable한 Error와 함께 제공되는 Docs 개선은 일찍 도입할 가치가 있습니다. 수정 Loop마다 조용히 누적되는 효과이기 때문입니다.
