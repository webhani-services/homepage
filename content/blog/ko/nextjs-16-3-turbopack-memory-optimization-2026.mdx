2026년 8월 초, Next.js 16.3이 릴리스되었습니다. 눈에 띄는 새 기능보다는 Turbopack의 내부 안정성 개선에 초점을 맞춘 버전입니다. 핵심은 이것입니다: 장시간 Dev Server 실행 시 Turbopack의 메모리 사용량이 최대 90%까지 감소합니다. 이건 마케팅 수치가 아닙니다. Monorepo에서 여러 개발 서버를 동시에 돌리거나, 야간 CI 빌드를 실행하는 팀이라면 체감할 수 있는 개선입니다.

이 글에서는 무엇이 달라졌는지, 왜 중요한지, 그리고 업그레이드 시 확인할 사항을 정리합니다.

## Turbopack이 마주친 메모리 문제

Turbopack은 원래 Webpack보다 훨씬 가볍습니다. 그런데 Dev Server에는 숨은 비용이 있었습니다. 시간이 지나면서 파일을 편집할 때마다 Compiler가 Module Metadata, 타입 정보, AST를 메모리에 쌓아두는데, Garbage Collector는 이들이 안전하게 삭제될 수 있다는 걸 모릅니다. 8시간 후에는 메모리 사용량이 25~40GB로 불어나서, Dev Server가 Crash 나거나 강제 재시작되는 일이 발생합니다.

Monorepo 상황은 더 심합니다. 5개 Package의 Dev Server를 동시에 실행 중이면 (에디터 각 Pane마다 하나씩), 각 서버가 독립적으로 메모리를 누수합니다. 하루가 지나면 Dev Process만 200GB 이상의 RAM을 차지합니다.

## Memory Eviction — 선택적 망각

Next.js 16.3은 Memory Eviction이라는 Background Garbage Collection 메커니즘을 도입했습니다. 핵심은 간단합니다: Compiler가 지금까지 만져본 모든 Module의 중간 단계를 기억할 필요는 없다는 것입니다. 효율적으로 Rebuild할 수 있는 만큼만 기억하면 됩니다.

Dev Server가 메모리 압박을 감지하면 (보통 Process당 2~3GB 기준), 다음을 수행합니다:

1. 지난 30분간 접근되지 않은 Compiler Segment를 식별합니다.
2. 필수 Metadata (어떤 Module이 존재하는지, 그들의 공개 API)를 Disk에 직렬화합니다.
3. 나머지 내부 상태를 폐기합니다.
4. 다음 File Change가 해당 Module을 건드릴 때, Metadata를 읽고 필요한 것만 다시 구성합니다.

결과: 세션 길이와 무관하게 메모리가 특정 수준에서 안정화됩니다. 실제 사례에서는 Dev Server당 5~8GB로 보고되고 있습니다 (Session 길이가 12시간을 넘어도).

```bash
# 장시간 세션에서 메모리 모니터링
npm run dev &
DEV_PID=$!

# 4시간 후에 메모리 확인
ps aux | grep -E "node|dev" | grep -v grep
```

## 영속 Build Cache

Memory Eviction과 함께, 새로운 Persistent Cache가 도입됩니다: `.next/turbopack`. Dev Server가 종료되어도 이 Cache는 Disk에 남아있습니다. 재시작하거나 CI 환경에서 Turbopack은 Cache를 읽고 변경되지 않은 Module의 재컴파일을 건너뜁니다.

```typescript
// next.config.ts — 사용자 정의 Cache 위치 (선택)
import type { NextConfig } from "next";

const config: NextConfig = {
  experimental: {
    turbo: {
      cacheDir: process.env.TURBOPACK_CACHE_DIR || ".next/turbopack",
    },
  },
};

export default config;
```

CI에서는 다음과 같은 변화를 가져옵니다:

| 상황 | 이전 | 이후 |
|---|---|---|
| Cold Build (신규 Checkout) | 90~120초 | 90~120초 (Cache 없음) |
| Warm Build (Code 변경 없음) | 90~120초 | 20~30초 (Cache Hit) |
| Incremental (5개 File 변경) | 45~60초 | 10~15초 (Delta Rebuild) |

Monorepo CI Pipeline에서 하루에 수백 번 Build를 실행한다면, 누적된 시간 절감 (그리고 Metered CI를 사용한다면 비용 절감)이 상당합니다.

## Rust 기반 React Compiler 통합

React Compiler (React 19와 함께)는 명시적인 `memo()` 나 `useMemo()` 없이도 Component 재렌더링을 자동 최적화합니다. 다만 Compiler의 분석 단계—어떤 변수가 정말 독립적인지 판단하는 부분—이 JavaScript 기반의 병목이었습니다.

Next.js 16.3은 그 분석을 Rust로 옮겼습니다. 결과: Compiler 자체의 컴파일 시간 오버헤드가 60~70% 감소합니다. 500개 이상의 Component를 가진 프로젝트라면 눈에 띕니다 (Build 시간이 2~4초 단축).

```typescript
// React Compiler가 자동으로 Props/Dependencies 변경이 없으면
// 재렌더링을 스킵합니다. 명시적인 memo()가 필요 없습니다.

function ProductCard({ product, onAdd }) {
  return (
    <div className="card">
      <img src={product.image} alt={product.name} />
      <h3>{product.name}</h3>
      <p>${product.price}</p>
      <button onClick={() => onAdd(product.id)}>Add</button>
    </div>
  );
}

// Compiler가 추론: onAdd는 Parent에서 온 Callback.
// product나 onAdd가 변할 때만 재렌더링.
// <Memo> Wrapper가 필요 없습니다.
```

## `import.meta.glob` 지원

작지만 유용한 추가 사항: `import.meta.glob`이 Next.js App Router에서 이제 동작합니다. Vite 사용자에게는 낡은 기능이지만, Next.js에서는 처음 공식 지원합니다. Build 시간에 Pattern에 맞는 여러 File을 Import합니다.

```typescript
// app/blog/route.ts
const postModules = import.meta.glob("../../content/blog/*.mdx", {
  eager: true,
});

export async function GET() {
  const posts = Object.entries(postModules).map(([path, module]: any) => {
    const slug = path.split("/").pop()?.replace(".mdx", "");
    return {
      slug,
      title: module.frontmatter?.title,
      date: module.frontmatter?.date,
    };
  });

  return Response.json(posts);
}
```

이를 통해 File 기반 Content System (Blog, Docs, Changelog)에서 Custom Build Script가 필요 없어집니다. Monorepo에서 많은 Package가 Content를 Export한다면 Build Pipeline을 단순화할 수 있습니다.

## Monorepo와 CI에 미치는 현실적 영향

### 로컬 개발

5개 이상의 Dev Server를 Monorepo에서 메모리 압박 없이 실행하면, Edit-to-Refresh Cycle이 빨라지고 "Node Process Out of Memory" Crash가 줄어듭니다. 팀은 흐름의 연속성 향상을 보고합니다—Dev Server 재시작으로 인한 Context Switching이 적어집니다.

### CI Build 시간과 비용

Persistent Cache는 CI의 Force Multiplier입니다. GitHub Actions Workflow를 예로 들면 (PR당 2회 Build—Push 시 1회, Rerun 시 1회):

- 첫 번째 Run: Main Branch Cache 사용 → 2분
- 두 번째 Run: 첫 번째 `.next/turbopack` 재사용 → 30초

주당 50개 PR이 있고, PR당 평균 1.5회 Rerun이 있으며, Build당 비용이 $0.008/분이라면:

- 이전: 50 × 1.5 × 2분 × $0.008 = $1.20/주
- 이후: 50 × 1 × 2분 + 50 × 0.5 × 0.5분 × $0.008 = $0.20/주

Build 양이 늘수록 절감액이 커집니다.

### Docker 환경

`docker compose`를 로컬 개발에 사용한다면, Persistent Cache가 Container 재시작을 견뎌야 합니다. Named Volume을 사용하세요:

```yaml
services:
  app:
    image: node:20
    volumes:
      - .:/app
      - turbopack_cache:/app/.next/turbopack
    working_dir: /app
    command: npm run dev

volumes:
  turbopack_cache:
```

## CI에서의 Cache 전략

GitHub Actions에서 Run 간에 Cache를 유지합니다:

```yaml
- name: Restore Turbopack cache
  uses: actions/cache@v4
  with:
    path: .next/turbopack
    key: turbopack-${{ hashFiles('**/package-lock.json') }}
    restore-keys: |
      turbopack-

- name: Build
  run: npm run build
```

`package-lock.json` 또는 `pnpm-lock.yaml`의 Hash를 Cache Key로 사용합니다. Dependency가 바뀌면 Cache는 자동 무효화됩니다.

## 검증과 문제 해결

### 로컬에서 Cache 정확성 테스트

1. 같은 Code에서 `npm run build`를 두 번 실행합니다. 두 번째는 60~80% 빨라야 합니다.
2. 파일 하나를 수정하고 Rebuild합니다. 영향받은 Module만 재컴파일되어야 합니다.

### 필요 시 Cache 초기화

```bash
rm -rf .next/turbopack
npm run dev
```

`next.config.ts` 또는 `tsconfig.json`이 바뀌면 Cache는 자동 무효화되지만, 수동으로도 가능합니다.

### Cache 크기 모니터링

CI에서 `.next/turbopack`은 Project 크기에 따라 보통 100~500MB로 자랍니다. 1GB를 넘으면 주간 Reset을 고려하세요:

```yaml
- name: Clear old cache (weekly)
  if: github.event_name == 'schedule'
  run: rm -rf .next/turbopack
```

## 정리

Next.js 16.3은 실제 마찰 지점을 해결합니다: Dev 환경 안정성과 CI 효율성. Memory Eviction은 장시간 세션을 안정적으로 유지합니다. Persistent Cache는 반복적인 Build 시간을 단축합니다. Rust Compiler 가속이 이를 뒷받침합니다. Monorepo를 운영하는 팀이라면 업그레이드는 직관적이며 효과는 측정 가능합니다.

필요한 작업: CI Pipeline에서 Cache 동작을 테스트하고, Docker를 사용한다면 Volume 설정을 구성한 후 첫 주간 안정성을 모니터링하면 됩니다. 그 이후로는 이점이 누적됩니다.
