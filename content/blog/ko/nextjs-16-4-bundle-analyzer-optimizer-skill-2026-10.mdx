Bundle 크기 악화는 하나의 극적인 변경에서 비롯되는 경우가 드뭅니다. 공유 Utility 파일에 import가 하나 늘었거나, Dialog Registry가 모든 Dialog를 참조하고 있는 것과 같은 작은 변화가 쌓여서 생깁니다. 10월 28일 Next.js 팀은 이 문제를 위해 16.4에 추가된 Tooling에 관한 글을 공개했습니다. 개선된 Turbopack Bundle Analyzer, 그리고 Analyzer의 Module Graph를 활용하는 Agent용 Skill인 `next-bundle-optimizer`입니다.

Tool의 세부 내용도 읽을 가치가 있지만, 그 밑에 깔린 교훈이 더 실용적입니다. **lazy import가 코드를 지연시키는 경우는 다른 어디에서도 정적으로 import하지 않을 때뿐입니다.**

## 발생하는 문제

필요할 때만 로드할 생각인 무거운 Editor Component를 예로 들어 보겠습니다.

```tsx
// HeavyEditorLoader.tsx
'use client';
import { lazy } from 'react';

export const HeavyEditorLoader = lazy(() => import('./HeavyEditor'));
```

`HeavyEditor`가 지연되는 것은 `HeavyEditorLoader`가 유일한 import 지점일 때뿐입니다. 같은 Bundle 안의 다른 Module이 `import { HeavyEditor } from './HeavyEditor'`를 하고 있다면(타입이나 같은 파일에서 export한 상수를 재사용하려는 경우 등) Bundler는 초기 Chunk에 포함할 수밖에 없습니다. `lazy()`는 정상 동작하고 경고도 없지만 코드는 처음부터 전송됩니다.

고객사 프로젝트에서 자주 보는 원인은 다음과 같습니다.

- Component 파일에서 export한 타입이나 상수를 다른 곳에서 import하는 경우. 공유 타입을 별도 파일로 옮기면 해결됩니다.
- 모든 것을 재export하는 Barrel 파일(`index.ts`) 때문에 작은 Helper 하나를 import했을 뿐인데 옆의 무거운 Module까지 딸려 오는 경우.
- Dialog, Icon, Route와 Component의 매핑 표 같은 중앙 Registry가 모든 항목을 정적으로 참조하는 경우.

개별 import는 모두 합리적으로 보이기 때문에 Code Review에서는 발견되지 않습니다.

## 16.4에서 Analyzer에 추가된 기능

앱 Directory에서 `next analyze`를 실행합니다. Next.js 발표에 따르면 Analyzer에 다음 기능이 추가되었습니다.

- **Route 요약.** 가장 큰 Client Route를 나열하여, 전체 Graph가 아니라 중요한 페이지부터 조사를 시작할 수 있습니다.
- **Route별 Table 보기.** 크기순으로 정렬하여 큰 요인을 빠르게 찾습니다.
- **Snapshot.** 실행한 분석이 자동 저장되고 두 개를 비교할 수 있습니다. 가장 먼저 도입하고 싶은 기능입니다. "지난달 어느 시점부터 Bundle이 커졌다"는 막연한 느낌을 구체적인 두 시점 간의 비교로 바꿀 수 있습니다.
- **Critical Render Path 강조.** 비동기 Dependency를 제외하고 초기 렌더링에서 동기적으로 로드되는 것만 볼 수 있습니다. Next.js 글에는 주의 사항이 있습니다. Runtime 상태에 따라 RSC 렌더링에서 `next/dynamic`이 만든 Chunk가 초기 로드에 포함될 수 있으므로 실제 동작으로 확인해야 합니다.
- **`next analyze export`.** Module과 Chunk의 Graph 데이터를 내보내서 자체 Tool로 조회할 수 있습니다.

Analyzer는 Turbopack의 Module Graph에 의존하므로 Next.js 16부터 기본 Bundler인 Turbopack이 필요합니다.

## Optimizer Skill

다음 명령으로 설치합니다.

```bash
npx skills add vercel/next.js --skill next-bundle-optimizer
```

그런 다음 Coding Agent에서 `/next-bundle-optimizer`를 실행합니다. 기본값은 문제점과 수정안을 보고만 하며, `/next-bundle-optimizer fix`를 실행하면 변경을 적용하고 분석을 다시 실행하여 Snapshot을 비교합니다.

Next.js 팀에 따르면 Agent는 서로 연결된 Module을 묶고 import 연쇄를 추적하며, Minimum Cut 방식으로 큰 Group을 지연시킬 수 있는 소수의 import 경계를 찾습니다. 또한 React Server Components로 옮길 수 있는 로직, 큰 Dependency의 중복 버전, Tree Shaking이 적용되지 않은 지점도 살핍니다.

보고된 성과는 Vercel 자체 앱에서 얻은 것으로, v0와 vercel.com에서 압축 기준 약 2MB에 가까운 JavaScript를 제거하거나 지연시켰다고 합니다. 예로는 거의 모든 페이지에서 로드되던 Code Editor(대부분의 페이지에서 약 150KB 절감), 무거운 Dialog를 미리 로드하던 Registry(페이지에 따라 40~650KB), Assistant를 사용하기 전에 로드되던 날짜 파싱 Library(평균 약 55KB)가 있습니다. 이는 크고 오래된 Codebase에서 나온 Vendor 자신의 수치이므로 일반적인 기업 사이트에서는 절대적인 효과가 더 작을 것입니다. 다만 실수의 유형은 많은 중간 규모 앱에서 나타나는 것과 같습니다.

## webhani의 활용 방식

**변경 전에 먼저 분석합니다.** 주요 3~4개 Route의 Baseline Snapshot을 저장합니다. 이것이 없으면 변경이 효과가 있었음을 보여 줄 수 없습니다.

**Agent의 출력은 가설 목록으로 취급합니다.** import 경계를 옮기면 동작이 달라질 수 있습니다. 첫 렌더링에서 준비되어 있던 Component가 Fallback을 잠깐 보여 줄 수도 있습니다. 제안마다 실제 사용 방식과 대조하여 검토하고, Build뿐 아니라 사용자 상호작용도 테스트합니다.

**변경 하나당 Pull Request 하나.** Next.js 글에서는 변경마다 Pull Request를 만들고 Preview Deployment에서 검증했다고 설명합니다. 이 정도 단위가 적절합니다. Regression이 생겼을 때 어느 변경이 원인인지 알 수 있습니다.

**CI에 Budget 검사를 추가합니다.** Snapshot은 조사에는 유용하지만 그것만으로 Regression을 막지는 못합니다. Build 출력에 기반한 Route별 First Load JS의 간단한 검사가 있으면 다음에 우연히 들어오는 정적 import를 Merge 전에 잡을 수 있습니다.

```yaml
# .github/workflows/bundle-budget.yml (발췌)
- run: npm run build
- run: node scripts/check-first-load-budget.mjs
```

Script는 Build 출력을 읽고 설정한 Budget을 초과한 Route에서 실패합니다. 수치를 정하는 방법은 자유이지만, 임계값이 Repository 안에 있어야 한다는 점이 중요합니다.

**근본 원인은 가능한 한 직접 수정합니다.** 공유 타입을 별도 파일로 분리하고, Client Code에서는 Barrel을 통한 import를 직접 import로 바꾸며, Registry는 항목별로 지연시킵니다. 작은 변경이지만 같은 문제의 재발을 막아 줍니다.

## 정리

- `lazy()`나 `next/dynamic` 호출이 있다고 해서 지연된다는 증거는 아닙니다. Module Graph로 확인하십시오.
- Snapshot 비교를 통해 Bundle 증가가 막연한 느낌이 아니라 측정 가능한 사건이 됩니다. 지금부터 Baseline을 저장하십시오.
- Optimizer Skill은 아무도 감사하지 않은 Codebase에 대한 첫 점검으로는 적절하지만, 제안마다 동작 변화에 대한 사람의 검토가 필요합니다.
- 개선을 유지하려면 CI에서 First Load Budget을 강제하십시오.

App Router로 이전한 뒤 프로파일링한 적이 없는 사이트라면 `next analyze`에 한 시간만 써도 무언가 발견될 가능성이 높습니다.
