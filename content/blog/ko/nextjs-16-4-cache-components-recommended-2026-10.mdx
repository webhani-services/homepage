Next.js 16.4가 10월 초에 Stable로 출시되었습니다. 2차 보도를 바탕으로 한 내용이므로(공식 Release Note를 한 줄씩 확인한 것은 아닙니다. 실제 적용 전에 GitHub의 v16.4.0 Tag를 확인해 주십시오), 핵심은 방침의 변화입니다. Cache Components가 모든 앱에 권장되는 모델이 되었고, `create-next-app`은 신규 Project에서 이를 활성화합니다. 이 밖에 React 19.3 통합, Zstandard 압축을 통한 Turbopack Disk Cache 약 20~25% 감소, Bundle Analyzer의 Route별 요약 화면이 보고되었습니다. `ensureStatic`과 더 세밀한 Prefetch 제어, Coding Agent를 겨냥한 `next upgrade --agent`도 언급됩니다.

저희가 보는 주간 Digest는 Stable 릴리스 자체는 대부분 점진적인 변경이라고 평가했습니다. 코드 측면에서는 저희도 같은 생각입니다. 중요한 것은 방향성입니다. Framework가 나아갈 방향을 알려 주고 있으며, Next.js 17에서는 Cache Components가 기본값이 될 것으로 전해집니다.

## 기존 앱에게 "권장"이 의미하는 것

권장은 강제 전환이 아니므로 업그레이드 때문에 깨지지는 않습니다. 다만 실무에서는 두 가지가 영향을 줍니다.

첫째, 문서, 예제, Tooling이 명시적 Caching 모델을 전제로 하는 방향으로 바뀝니다. 새 팀원과 Coding Agent는 기본적으로 `use cache` 코드를 작성하게 되고, 암묵적 `fetch` Caching에 의존하는 기존 App Router 코드는 그 옆에서 낯설어 보입니다.

둘째, 암묵적 모델에 머무는 기간이 길수록 결국의 Migration 규모가 커집니다. 수십 개 Route에 걸쳐 암묵적으로 정해진 Caching 동작은 나중에 목록으로 정리하기 어렵습니다.

## 예제 하나로 보는 모델

Cache Components는 "Framework가 캐시 가능 여부를 추측하는" 방식을 명시적 Directive로 바꿉니다.

```tsx
// app/products/page.tsx
import { Suspense } from "react";
import { cacheLife } from "next/cache";

async function getCategories() {
  "use cache";
  cacheLife("hours");
  const res = await fetch("https://api.example.com/categories");
  return res.json();
}

export default async function ProductsPage() {
  const categories = await getCategories();
  return (
    <main>
      <h1>Products</h1>
      <ul>
        {categories.map((c: { id: string; name: string }) => (
          <li key={c.id}>{c.name}</li>
        ))}
      </ul>
      <Suspense fallback={<p>Loading stock…</p>}>
        <LiveStock />
      </Suspense>
    </main>
  );
}

async function LiveStock() {
  // 캐시하지 않음: Request 시점 데이터를 Suspense 안에서 Streaming
  const res = await fetch("https://api.example.com/stock", { cache: "no-store" });
  const stock = await res.json();
  return <p>{stock.available} in stock</p>;
}
```

캐시된 Category 목록을 포함한 Static Shell은 Prerendering할 수 있습니다. 동적인 부분은 `Suspense` 안에서 Streaming됩니다. 무엇이 캐시되는지는 추측이 아니라 코드를 보면 알 수 있습니다.

## 단계적 도입 계획

큰 앱에서 PR 하나로 설정을 한꺼번에 바꾸는 것은 권하지 않습니다. 저희 Project에서 효과가 있었던 순서는 다음과 같습니다.

1. **기존 설정 그대로 16.4로 올립니다.** Test와 Production Build를 통과시킵니다. 단순한 Version Bump로 취급합니다.
2. **데이터 접근을 정리합니다.** Route와 그곳에서 수행하는 fetch를 목록으로 만들고, 정적, 시간 기반 재검증, 사용자별, Request별로 분류합니다. 실수로 캐시되기 쉬운 것은 사용자별 데이터이므로 이 부분은 엄격하게 봅니다.
3. **Branch에서 Cache Components를 활성화합니다.** Request 시점 데이터를 `Suspense` 경계 밖에서 읽는 Route가 지적됩니다. 이는 Noise가 아니라 실제 설계 문제이므로 가장 먼저 고칩니다.
4. **효과가 큰 곳부터 `use cache`를 붙입니다.** Category, Navigation, 요금표 같은 공유 참조 데이터가 좋은 출발점입니다. 기본값에 의존하지 말고 `cacheLife`를 명시합니다.
5. **Route Group 단위로 확대합니다.** 마케팅 페이지가 먼저, 인증이 필요한 영역은 마지막입니다.
6. **dev가 아니라 Production 동작으로 검증합니다.** `next dev`와 `next start`는 Caching 동작이 다릅니다. Response Header를 확인하고, 가능하면 Deploy 후 Cache Hit 비율도 살펴봅니다.

## 주의해야 할 위험

- **개인화된 콘텐츠의 캐시.** Cookie, Header, Session에서 파생된 값은 캐시 범위 안에 두면 안 됩니다. 서로 다른 두 사용자가 서로 다른 출력을 받는지 확인하는 Test를 추가하십시오.
- **데이터 신선도에 대한 기대 차이.** 값이 얼마나 오래되어도 되는지는 Product 및 사업 담당자와 합의해야 합니다. `cacheLife`를 시간 단위로 두는 것은 기술적 결정인 동시에 비즈니스 결정입니다.
- **Canary와 Stable의 차이.** 한 보고서에 따르면 Canary Build에서 `forbidden()`과 `unauthorized()`의 안정화가 되돌려졌습니다. 이 API를 사용한다면 Stable에 고정하고 Release Note로 확인하십시오.
- **Agent에 맡기는 업그레이드.** `next upgrade --agent`는 편리하지만, 큰 Repository에 Codemod를 적용하더라도 Caching 의미론은 사람이 Review해야 합니다. 계획하실 때 이전 글 "[Review 용량](/blog/ai-agents-more-code-same-output-review-bottleneck-2026-10)"도 참고해 주십시오.

## 정리

점진적 개선을 위해 16.4로 올리되, Cache Components는 "켜기만 하면 되는 설정"이 아니라 계획된 Migration으로 다루십시오. 데이터 접근을 정리하고, 공유 참조 데이터부터 시작하며, Production 동작으로 검증합니다. App Router Codebase를 유지보수하고 있고 Migration 계획에 대한 두 번째 의견이 필요하시다면 webhani가 Review를 도와드릴 수 있습니다.
