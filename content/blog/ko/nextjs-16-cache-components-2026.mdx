## 암묵적인 fetch Caching에서 명시적인 Model로

Next.js 16은 Partial Pre-Rendering(PPR)과 명시적인 `use cache` Directive를 결합한 새로운 Caching Model, Cache Components를 도입했습니다. 기존 Framework의 기본 동작 — `fetch()` 호출을 자동으로, 그리고 경험적 규칙에 따라 Caching하던 방식 — 을 대체하고, Component나 함수 단위로 Source Code에 명시적으로 Caching을 선언하는 Model로 전환합니다.

이 한 문장만으로는 실무에 얼마나 큰 변화를 가져오는지 와닿지 않을 수 있습니다. 기존 Model에서는 어떤 Page가 정적으로 생성되는지, Caching되는지, 완전히 동적으로 렌더링되는지가 어떤 Data Fetching API를 어떤 순서로 호출했는지에 좌우되었습니다. 공식 문서는 이 규칙을 꼼꼼히 설명했지만, 실제로는 많은 Team이 예기치 못한 재검증(Revalidation)을 겪은 뒤에야 그 규칙을 하나씩 학습하곤 했습니다. Cache Components는 이 경계를 명시적이고 지역적인 것으로 만듭니다. 어떤 함수가 Caching되는 이유는 그렇게 선언되어 있기 때문이며, 암묵적인 규칙 묶음이 "그래야 한다"고 판단한 결과가 아닙니다.

## use cache가 실제로 하는 일

이 Directive는 File 최상단, 함수, Component 어디에든 붙일 수 있습니다. Directive가 붙은 대상은 Caching 가능한 단위가 되며, Next.js는 입력값을 Key로 삼아 그 출력을 저장하고 재사용합니다.

```tsx
// app/lib/pricing.ts
async function getPricingTiers(region: string) {
  "use cache";

  const res = await fetch(`https://api.example.com/pricing?region=${region}`);
  return res.json();
}

export default getPricingTiers;
```

반대로, 의도적으로 동적인 상태를 유지해야 하는 Server Component — 예를 들어 Cookie를 읽어 표시 내용을 결정하는 경우 — 와 비교해 보겠습니다.

```tsx
// app/dashboard/account-banner.tsx
import { cookies } from "next/headers";

export default async function AccountBanner() {
  const store = await cookies();
  const plan = store.get("plan")?.value ?? "free";

  return <Banner plan={plan} />;
}
```

`AccountBanner`는 `cookies()`를 읽기 때문에 Caching 가능한 경계 밖에 놓입니다. Partial Pre-Rendering이 있다면 이는 문제가 되지 않습니다. Navigation, Footer, Marketing Section 같은 Page의 나머지 부분은 Caching된 Shell에서 그대로 제공되고, `AccountBanner`만 `Suspense` 경계 안에서 Request마다 렌더링됩니다. Component 하나가 Live Data를 필요로 한다고 해서 Route 전체가 완전히 동적인 렌더링으로 떨어지는 대신, 대부분 정적인 HTML 안에 동적인 "구멍" 하나가 뚫리는 형태가 됩니다.

## Marketing + App 형태 Site에 갖는 의미

Webhani가 만드는 Site 대부분은 "완전히 정적인 Marketing Site"와 "완전히 동적인 Web App"의 중간 어딘가에 위치합니다. 개인화된 요소를 몇 개 가진 공개 Site이거나, 대부분 정적인 설정 화면으로 구성된 App Shell 같은 경우입니다. 기존 fetch Caching Model에서는 Layout 안의 동적 API 호출 하나가, 실제 Data 의존 관계가 요구하는 것보다 더 많은 Route를 동적 렌더링 쪽으로 밀어내곤 했습니다. Cache Components는 이 영향 범위를 좁혀줍니다. 진짜로 Request마다 달라져야 하는 부분만 그렇게 동작하면 됩니다.

구체적으로는 다음과 같은 효과가 있습니다.

- **User마다 달라지지 않는 Content의 Navigation이 빨라집니다**: `use cache`가 붙은 가격 Page, Blog 목록, Marketing Section은 같은 Page 안의 로그인 Banner가 무엇을 필요로 하든 상관없이 Cache에서 제공됩니다.
- **Code Review에서 짚어낼 수 있는 Caching 경계가 생깁니다**: "이 Route는 왜 동적인가"라는 질문은 예전에는 fetch Graph 전체를 추론해야 답할 수 있었습니다. 이제는 `use cache`가 없으면서 동적 API를 호출하는 Component를 찾으면 됩니다.
- **Chunking 제어와 함께 효과가 커집니다**: Next.js 16은 Code를 어떻게 분할·공유할지 조정할 수 있는 실험적 Chunking 제어 기능도 함께 제공합니다. Caching 경계와 동적 경계가 명시적이 된 만큼, Route 경계가 아니라 실제 렌더링 경계에 맞춰 Chunk 크기를 정할 수 있게 됩니다.

## 마이그레이션하는 Team에 전하고 싶은 것

실제 Next.js 15 Codebase에 이 Model을 대입해 보면서 확인한 실무적인 Point입니다.

1. **먼저 의도치 않은 동적화를 찾습니다**: `use cache`를 추가하기 전에, 필요하지도 않은데 `cookies()`나 `headers()`를 호출하거나 `searchParams`를 읽는 Component를 찾습니다. 대부분 Copy-paste의 흔적이지 실제 요구사항이 아닙니다. 이것만 제거해도 Caching을 건드리기 전에 동적 범위를 줄일 수 있습니다.
2. **Page 단위가 아니라 함수 단위로 Caching합니다**: `getPricingTiers`처럼 공유되는 Data Fetching 함수에 `use cache` 하나를 붙이면, 그 함수를 import하는 모든 Page가 혜택을 받습니다. Route 전체에 표시를 붙이려는 것보다 이쪽이 더 나은 Caching 단위가 되는 경우가 많습니다.
3. **Cache Key를 의도적으로 다룹니다**: Caching이 명시적이 된 만큼, Caching된 출력을 무엇이 변화시키는지 — Region, Locale, Feature Flag 등 — 도 똑같이 명시적으로 다뤄야 합니다. Caching되는 함수 안에서 암묵적인 Context를 읽기보다, 함수의 인자로 전달하는 편이 낫습니다.

## Webhani의 시각

Cache Components는 메커니즘을 명시적으로 만드는 대가로 처음에는 Directive를 작성하는 수고가 조금 늘지만, 그만큼 나중의 Debugging 시간을 크게 되돌려받는 사례입니다. 기존의 자동 fetch Caching은 잘 작동하는 동안에는 편리했지만, 어떤 Route가 예기치 않게 완전히 동적으로 바뀌거나(혹은 그러지 말아야 할 때 계속 Caching되어 있거나) 하는 순간, 원인을 추적하려면 Next.js의 내부 규칙을 다시 되짚어야 했습니다. 명시적인 `use cache` 경계가 있으면 답은 항상 지금 보고 있는 File 안에 있습니다.

이미 Next.js 16을 운영 중인 Team에게 드리는 권장 사항은, 이 마이그레이션을 기계적인 찾기-바꾸기 작업이 아니라 감사(Audit)의 기회로 다루라는 것입니다. 가치는 `use cache`를 여기저기 뿌리는 데 있는 것이 아니라, 실제 Data 요구사항보다 더 넓게 동적 렌더링이 새어 나가고 있던 지점을 찾는 데 이 작업을 활용하는 데 있습니다.
