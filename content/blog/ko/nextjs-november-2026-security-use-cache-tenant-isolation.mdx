11월 3일, Next.js의 정기 Security Release로 v16.4.5(Active LTS)와 v15.5.29(Maintenance LTS)가 배포되었습니다. 공식 Blog 기준으로 수정은 7건이며 High 1건, 나머지는 Medium입니다. 건수보다 눈여겨볼 부분은 7건 중 4건이 **Cache Components와 `use cache`의 Cache 식별자 계산** 에 관한 문제라는 점입니다.

`use cache`는 무엇을 Cache Key로 삼을지를 Framework에 맡기는 구조입니다. 편리하지만, Framework가 Key를 잘못 계산하면 Multi-tenant 환경에서는 곧바로 다른 Tenant의 Data 노출로 이어집니다. 이번 Release는 "지금 Patch하기"와 "Cache 함수 설계 점검하기" 두 가지 작업으로 나누어 대응하는 것이 좋습니다.

## 먼저 Version을 올립니다

```bash
# 16.x
npm install next@16.4.5

# 15.5.x
npm install next@15.5.29
```

지난주 16.4.4로 올린 Project도 16.4.5로 다시 Update해야 합니다. CI에서 최소 Version을 강제해 두면 오래 유지되는 Branch를 통해 구 Version이 다시 섞여 들어오는 일을 막을 수 있습니다.

```js
// scripts/check-next-version.mjs
import { createRequire } from "node:module";
const require = createRequire(import.meta.url);
const { version } = require("next/package.json");

const [major, minor, patch] = version.split(".").map(Number);
const ok =
  (major === 16 && (minor > 4 || (minor === 4 && patch >= 5))) ||
  (major === 15 && minor === 5 && patch >= 29) ||
  major > 16;

if (!ok) {
  console.error(`next@${version} 에는 2026년 11월 Security 수정이 포함되어 있지 않습니다`);
  process.exit(1);
}
```

## 수정 내용 정리

공식 Advisory를 바탕으로 영향받는 구성별로 묶으면 다음과 같습니다.

| 분류 | 내용 | 영향받는 구성 |
| --- | --- | --- |
| Cache 식별자 | `unstable_cache`와 `use cache`를 함께 쓰면 Tenant 간 결과가 섞임 (High) | Cache Components 활성화 + root parameter를 읽는 함수 |
| Cache 식별자 | 중첩된 `use cache`에서 내부 함수의 root parameter 의존성이 기록되기 전에 외부 Entry가 저장됨 | 내부 함수가 빠른 값과 느린 비동기 값을 함께 반환 |
| Cache 식별자 | 서로 다른 Binary 인자가 같은 Cache 식별자가 됨 | Binary 인자로 User를 구분하는 경우 |
| Cache Poisoning | Self-hosted 환경의 공유 Shell 오염 | `next start` + Partial Prefetching 비활성/미설정 |
| HTTP | 압축 Response의 Framing Header 불일치로 Response가 다른 Client에 전달됨 | fetch한 `Response`를 그대로 반환 + HTTP/1.1 Proxy |
| Cookie | Edge Route에서 `HttpOnly` Cookie 값이 내부 Header로 노출 | Edge에서 `NextResponse.cookies.set()` 사용 |
| Image | `dangerouslyAllowSVG: false` 우회 | SVG를 Decode할 수 있는 Native Backend |

위의 3건은 Vercel이든 Self-hosted든 관계없이 해당됩니다. Cache Components를 켠 Multi-tenant SaaS라면 우선순위를 높게 잡아야 합니다.

## 암묵적인 Key에 기대지 않는 작성법

High 취약점은 Cache 함수가 내부에서 root parameter(예: `[tenant]` Segment)를 읽고, 그 값이 자동으로 Cache Key에 포함된다는 전제 위에서 발생했습니다. Framework 쪽은 Patch로 고쳐졌지만, 저희는 설계 차원에서 **Tenant ID를 명시적인 인자로 전달하는 방식** 을 권장합니다.

```ts
// lib/dashboard.ts
import { cacheTag, cacheLife } from "next/cache";

export async function getTenantDashboard(tenantId: string) {
  "use cache";
  cacheTag(`tenant:${tenantId}:dashboard`);
  cacheLife("minutes");

  return db.dashboardWidget.findMany({
    where: { tenantId },
    orderBy: { position: "asc" },
  });
}
```

```tsx
// app/[tenant]/dashboard/page.tsx
export default async function Page({
  params,
}: {
  params: Promise<{ tenant: string }>;
}) {
  const { tenant } = await params;
  const tenantId = await resolveTenantId(tenant); // 인가 Check 포함
  const widgets = await getTenantDashboard(tenantId);
  return <Dashboard widgets={widgets} />;
}
```

함수 Signature에 Tenant ID가 있으면 Code Review에서 "이 Cache는 Tenant별로 분리되어 있는가"를 바로 확인할 수 있습니다. Framework 내부 동작을 추측할 필요가 없어집니다.

함께 점검할 항목입니다.

- **`unstable_cache` 안에서 `use cache` 함수를 호출하지 않습니다.** 새 Code는 `use cache`로 작성하고, 남은 `unstable_cache`는 단계적으로 교체합니다.
- **Binary Data를 Key로 쓰지 않습니다.** `Uint8Array` 인자는 문자열 ID로 바꿉니다.
- **중첩된 Cache 함수가 await하지 않은 Promise를 포함한 객체를 반환하는지** 확인합니다. 두 번째 Advisory가 설명하는 형태입니다.

## 외부 API Response를 그대로 반환하지 않기

Self-hosted 환경에서 외부 API를 Proxy하는 Route Handler가 fetch한 `Response`를 그대로 `return`하면, Body와 맞지 않는 Framing Header가 함께 전달될 수 있습니다. Header를 다시 구성하는 것만으로 충분히 예방됩니다.

```ts
// app/api/upstream/route.ts
const HOP_BY_HOP = ["content-encoding", "content-length", "transfer-encoding", "connection"];

export async function GET() {
  const upstream = await fetch("https://api.example.com/data");
  const headers = new Headers(upstream.headers);
  for (const h of HOP_BY_HOP) headers.delete(h);

  return new Response(upstream.body, {
    status: upstream.status,
    headers,
  });
}
```

Edge Route에서 Cookie를 설정하고 있다면 이번 기회에 Node.js Runtime으로 옮기고 `cookies().set()`을 사용하는 형태로 정리하는 것이 깔끔합니다. Edge Runtime은 Vercel에서도 이미 Deprecated 상태입니다.

## Tenant 분리를 Test로 보장하기

Patch는 이번 Bug를 고칠 뿐이고, 다음 Bug는 Test가 잡아냅니다. Cold Cache 상태에서 서로 다른 Tenant에 동시에 Request를 보내 결과가 섞이지 않는지 확인하는 것만으로도 효과가 있습니다.

```ts
// e2e/tenant-isolation.spec.ts
import { test, expect } from "@playwright/test";

test("동시 Request에서 Tenant Data가 섞이지 않는다", async ({ request }) => {
  const tenants = ["acme", "globex", "initech"];
  const results = await Promise.all(
    tenants.map((t) => request.get(`/${t}/api/dashboard`)),
  );

  for (const [i, res] of results.entries()) {
    const body = await res.json();
    expect(body.tenant).toBe(tenants[i]);
  }
});
```

Deploy 직후나 Cache 삭제 후처럼 Entry가 처음 채워지는 시점에 실행하면 Cold Fill 동작을 확인할 수 있습니다.

## webhani의 견해

`use cache`는 Cache 관련 Code를 크게 줄여 주지만, 그만큼 Cache Key에 무엇이 들어가는지가 잘 보이지 않게 됩니다. 이번 수정의 대부분은 Framework 측 Bug이지만, Tenant ID를 명시적으로 다루는 Team은 영향 범위 조사를 훨씬 빨리 끝낼 수 있습니다.

권장 대응 순서는 다음과 같습니다.

1. 16.4.5 / 15.5.29로 Update하고 CI에서 최소 Version을 강제합니다.
2. 내부에서 root parameter를 읽는 `use cache` 함수를 찾아 Tenant ID를 인자로 옮깁니다.
3. `unstable_cache`로 `use cache` 함수를 감싸는 부분을 제거합니다.
4. Tenant 분리 E2E Test를 추가합니다.

Next.js Security Release는 이제 거의 매달 나옵니다. "Patch → 검증 → Test" 절차를 짧은 Runbook으로 정리해 두면 매번 당황하지 않고 처리할 수 있습니다.
