10월 27일, Next.js 팀은 2026년 11월 3일(화)에 정기 보안 릴리스를 진행한다고 예고했습니다. 공지에 따르면 대상은 Medium 등급 취약점 7건이며, 상세 Advisory는 릴리스와 함께 공개됩니다. 사전에 공개되는 정보는 이것뿐입니다. 사전 공지의 목적은 상세 내용이 공개되기 전에 팀이 준비할 시간을 주는 데 있습니다.

운영 환경에서 Next.js를 사용한다면, Framework 패치를 배포하기까지 얼마나 걸리는지 점검하기에 좋은 시점입니다. 9월 이후 Next.js 블로그를 보면 패치 릴리스가 잦았습니다.

- **9월 22일:** 업스트림의 Critical 문제에 대한 긴급 업데이트(16.3.6 및 15.5.26).
- **9월 30일:** 9월 정기 보안 릴리스.
- **10월 14일:** 업스트림 Dependency의 Critical 2건과 High 1건에 대한 긴급 업데이트.
- **11월 3일:** 10월 27일에 공지된 11월 정기 릴리스.

팀은 7월에 공식 보안 릴리스 프로세스로 전환했고, 각 릴리스 전에 사전 공지를 합니다. 계획을 세우기는 쉬워졌지만, 패치 대응이 가끔 일어나는 일이 아니라 Next.js 앱 운영에 상시 포함된 작업이 되었다는 뜻이기도 합니다.

## "준비되었다"는 상태

목표는 11월 3일에 패치 적용이 하루 종일 걸리는 조사가 아니라 평범한 Pull Request로 끝나는 것입니다. 이를 좌우하는 요소를 정리합니다.

### 1. 실제로 실행 중인 버전을 파악합니다

`package.json`에 적힌 내용이 아니라 실제로 설치된 버전에서 시작합니다.

```bash
npm ls next react react-dom
```

여러 앱을 관리한다면 모두 실행해서 결과를 한곳에 모읍니다. 흔한 실패는 릴리스 당일에야 잊고 있던 사내 Tool이 마이너 버전 두 단계 뒤처져 있고, 수정이 들어오지 않는 Branch에 고정되어 있음을 알게 되는 것입니다.

어느 릴리스 Line을 쓰고 있는지도 확인합니다. Next.js 15 Line은 Backport(9월의 15.5.26)를 받아 왔지만, 지원이 종료된 Line은 더 이상 받지 못합니다. 짐작하지 말고 공식 지원 정책을 확인하고, 긴급 패치가 필요해지기 전에 현행 Line(블로그 기준 현재 16.4)으로의 업그레이드를 계획하십시오.

### 2. 업그레이드를 한 줄 변경으로 만듭니다

패치 업그레이드는 버전 번호만 건드려야 합니다. 패치 업데이트를 허용하는 범위 지정을 사용하고 재현성은 lockfile에 맡깁니다.

```json
{
  "dependencies": {
    "next": "~16.4.0"
  }
}
```

`~`를 쓰면 다음 패치 버전으로의 상승은 lockfile 갱신으로 끝납니다. Renovate나 Dependabot 같은 자동화 Tool이 Pull Request를 대신 만들어 줄 수 있으며, 보안 업데이트를 높은 우선순위로 두고 Framework 관련 Package(`next`, `eslint-config-next`, React Package)를 한 Group으로 묶어 두십시오.

### 3. 화요일에 믿을 수 있는 Test Suite를 갖춥니다

보안 패치는 빠르게 배포할 수 있을 때 가치가 있고, 그것은 CI에 대한 신뢰에 달려 있습니다. 최소한 다음이 필요합니다.

- 타입 오류와 lint 오류에서 Build가 실패할 것.
- 중요한 페이지에 대한 Smoke Test: 최상위 페이지, 로그인, Form 제출, 동적 Route 하나.
- 보안 수정은 Request 처리에 손을 대는 경우가 많으므로 Middleware와 Route Handler가 기대대로 응답하는지 확인.

전체 Coverage는 필요 없습니다. Pipeline이 통과하면 당일 배포할 수 있다고 느낄 정도의 확신이면 충분합니다.

### 4. 배포 경로와 Rollback 방법을 알아 둡니다

패치가 운영 환경에 도달하는 절차와 되돌리는 절차를 Repository에 적어 둡니다. 즉시 Rollback이 가능한 Platform이라면 그렇게 적고, Container 운영이라면 마지막으로 정상이었던 Image Tag를 기록합니다. 이를 확인할 시점은 장애 대응 도중이 아닙니다.

Self-hosted 구성이라면 Node.js 쪽도 확인하십시오. Node 20은 EOL이 지나 보안 수정이 제공되지 않습니다. 지원되지 않는 Runtime 위에서 Next.js만 패치해서는 문제의 일부만 해결됩니다. 이전 방법은 Node 20 Runbook에서 다루었습니다.

### 5. 담당자를 정합니다

릴리스 당일 Next.js 블로그와 보안 Advisory를 확인할 담당자 한 명, Pull Request를 승인할 Reviewer 한 명을 정해 둡니다. 릴리스 공지는 Sprint 일정과 상관없이 도착합니다. 담당자가 없는 화요일 릴리스는 목요일 배포가 되기 쉽습니다.

## 릴리스 당일과 이후

Advisory가 공개되면 다음 순서로 진행합니다.

1. **우리 구성에 비추어 Advisory를 읽습니다.** Medium 등급 문제는 특정 Middleware 패턴, 이미지 최적화 설정, Server Actions 같은 특정 기능에 의존하는 경우가 많습니다. 영향 여부는 조사하되, "아마 해당 없음"을 기다릴 이유로 삼지 말고 업데이트는 진행하십시오.
2. **Preview 환경을 먼저 업그레이드하고** Smoke Test를 실행한 뒤 승격합니다.
3. **전이 Dependency도 확인합니다.** 10월 14일 업데이트는 업스트림 Dependency 취약점에 대한 것이었습니다. 수정은 `next`를 통해 도착하더라도 문제는 다른 곳에 있을 수 있습니다. 업그레이드 후 `npm audit`로 남은 항목을 확인합니다.
4. **수행한 내용을 기록합니다.** 업그레이드 전후 버전과 날짜를 changelog나 Ticket에 짧게 남기십시오. 고객이나 감사 담당자가 언젠가 묻는 질문에 대한 답이 됩니다.

## 짚어 둘 Trade-off

정확한 고정(`"next": "16.4.0"`)은 가장 예측 가능한 Build를 만들지만 패치마다 수동 편집이 필요하고, 경험상 패치가 뒤로 밀립니다. 마이너 범위를 열어 두면(`^16.4.0`) 수정이 자동으로 들어오지만 검토하지 않은 동작 변경도 함께 들어올 수 있습니다. 틸데 범위는 그 절충안으로, 패치 릴리스만 허용하고 반영 시점은 lockfile과 CI가 결정합니다.

이는 11월 3일에만 해당하는 이야기가 아닙니다. 다음 Advisory도 우리가 통제할 수 없는 일정으로 도착합니다. 침착하게 대응하는 팀은 급하지 않을 때 Pipeline을 정비해 둔 팀입니다. 업그레이드 경로에 대해 외부의 시각이 필요하시다면 짧은 기간의 지원으로 가능하며, 비용 대비 효과를 설명하기도 쉬운 작업입니다.
