Next.js Team이 2026년 8월 26일 Scheduled Security Release를 예고했습니다. 대상은 Next.js 16.3 계열과 15.5 계열이며, Critical Severity 취약점 1건을 포함한 수정이 예정되어 있습니다. 2026년 들어 Next.js는 월 단위 Security Release를 지속해왔고 이번도 그 흐름의 일부지만, "Critical"이라는 등급이 사전에 공개된 점은 그냥 넘길 수 없습니다.

취약점의 세부 내용은 관례상 Patch 공개와 동시에, 혹은 그 이후에 공개됩니다. 따라서 지금 시점에서 CVE 내용을 추측해 대응책을 논하는 것은 의미가 없습니다. 반대로 말하면, "세부 내용을 모르는 지금이기 때문에 준비해둘 수 있는 것들"이 있습니다. 이번 글에서는 Critical 취약점이 공개되는 당일 팀이 당황하지 않도록 준비할 사항을 정리합니다.

## 왜 "예고" 단계에서 움직여야 하는가

Next.js 같은 Framework 수준의 취약점은 수정 대상이 Application Code가 아니라 Framework 자체이기 때문에, Patch 적용 외에는 근본적인 대응책이 없는 경우가 많은 것이 현실입니다. Middleware나 App Router 내부 처리에서 비롯된 취약점의 경우, WAF Rule 같은 완화책만으로는 완전히 막기 어려웠던 사례도 과거에 있었습니다.

따라서 "취약점 내용을 기다렸다가 움직인다"가 아니라, "공개되는 순간 최단 시간에 Patch를 적용할 수 있는 상태를 지금 만들어둔다"가 사실상 유일하게 유효한 대비책입니다.

## 지금 할 수 있는 준비

### 1. 의존성 Pin 상태를 확인한다

`package.json`에서 Next.js Version을 어떻게 고정하고 있는지 확인하세요. Caret(`^`) 지정을 그대로 두면 의도치 않은 Minor Version 갱신이 발생하거나, 반대로 lockfile이 오래된 채 갱신이 멈춰 있을 수 있습니다.

```bash
# 현재 Next.js Version과 lockfile 정합성 확인
npm ls next
npm outdated next
```

### 2. Security Advisory 구독 경로를 확보한다

GitHub에서 `vercel/next.js` Repository의 Security Advisory 알림을 받도록 Watch 설정을 해두면, 공식 Blog 확인을 기다리지 않고 1차 정보에 접근할 수 있습니다.

### 3. Deploy Pipeline 소요 시간을 파악해둔다

Critical 취약점은 "인지 시점부터 Deploy 완료까지"의 시간이 실질적인 Risk 노출 시간이 됩니다. CI/CD의 Build~Deploy 표준 소요 시간을 파악하고, 긴급 Patch 적용 시 승인 절차를 단축할 수 있는 운영 규칙(예: Security Patch에 한해 Pair Review로 즉시 Merge 가능 등)을 미리 정해두면 당일 판단이 빨라집니다.

```yaml
# .github/workflows/security-patch.yml (예시)
name: security-patch-fast-track
on:
  workflow_dispatch:
    inputs:
      next_version:
        description: "적용할 Next.js Version"
        required: true
jobs:
  patch:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - run: npm install next@${{ github.event.inputs.next_version }} --save-exact
      - run: npm run build
      - run: npm test
```

### 4. LTS Branch 운영 방침을 확인한다

16.3 계열과 15.5 계열이 모두 대상이라는 것은, 최신 Version뿐 아니라 이전 Major 계열을 사용하는 Project도 영향을 받을 수 있다는 의미입니다. 여러 Project를 운영하고 있다면 각 Project가 어느 계열을 따르고 있는지 지금 점검해두세요.

## webhani의 권장 사항

1. **8월 26일 전후로 Deploy 담당자 일정을 비워둔다**: Critical 취약점의 경우 당일~익영업일 내 대응이 바람직하다
2. **운영 환경과 동일한 Version의 Staging 환경을 유지한다**: Patch 적용 후 동작 확인을 운영 반영 전에 신속히 할 수 있는 체계를 유지한다
3. **middleware와 App Router의 Custom 구현을 미리 파악해둔다**: 과거 유사 취약점에서 middleware 영역이 영향 범위였던 사례가 있어, 자사 Custom 구현의 영향 여부를 빠르게 판단할 수 있도록 준비해두면 대응이 빨라진다
4. **Client 대상 영향 설명 Template을 준비해둔다**: 수탁 개발 현장에서는 취약점 공표 이후 Client에게 상황을 설명해야 하는 경우가 많다. 정형화된 Format을 미리 준비해두면 당일 부담이 줄어든다

Critical 취약점의 세부 내용은 공개되기 전까지 알 수 없지만, "대응 속도를 결정하는 것은 사전 준비의 양"이라는 점은 매번 달라지지 않습니다. webhani는 Next.js를 채택한 Project의 Security Release 대응 Process 구축도 함께 지원하고 있습니다.
