Node.js 프로젝트는 Node.js 27부터 새로운 Release Schedule을 적용하여 Major Release를 연 1회로 줄인다고 발표했습니다. Node.js 26은 연 2회 Major Release라는 기존 방식의 마지막 Line이 됩니다. 프로젝트 측은 이 Schedule을 잠정적이며 변경될 수 있다고 밝히고 있으므로, 아래 내용은 확정된 약속이 아니라 현재 계획으로 받아들이시기 바랍니다.

많은 팀에는 "최신 LTS를 쓰고, 다음 LTS가 나오면 올린다"는 경험칙이 있습니다. 이 규칙은 여전히 유효하지만 전제가 몇 가지 달라집니다. 이 글에서는 새 Schedule의 내용과, 각 팀의 정책에서 손봐야 할 부분을 정리합니다.

## 새 Schedule의 내용

프로젝트 발표에 따르면 다음과 같습니다.

- **Major Release는 연 1회**, 4월에 나오고 10월에 LTS로 승격됩니다.
- **Version 번호는 첫 Current Release가 나온 연도를 따릅니다.** Node.js 27.0.0은 2027년, 28.0.0은 2028년에 나옵니다.
- **약 6개월의 Alpha 단계**(10월~3월)가 Current 앞에 추가됩니다. Alpha 중에도 semver-major 변경이 허용되며, Node.js 27의 Alpha Channel은 2026년 10월에 열립니다.
- **Current**는 약 6개월(4월~10월)이며 안정화 기간입니다.
- **LTS**는 30개월입니다. Node.js 27의 계획은 2027년 10월 LTS 시작, 2030년 4월 EOL입니다.

실무적으로는 추적할 Line이 연 2개에서 1개로 줄고, 홀수 Version이라는 별도 범주가 사라지며, 번호만 봐도 처음 나온 연도를 알 수 있다는 뜻입니다.

## 달라지지 않는 것

Production Workload가 있어야 할 곳은 여전히 LTS입니다. Release 다음 해 상반기에는 해당 Line이 Current 상태이며 Production용이 아닙니다. LTS 기간이 길기 때문에 두 개의 LTS Line이 동시에 지원되는 시기가 자주 생기고, Migration을 위한 겹치는 기간도 충분합니다.

이미 EOL에 도달한 Line을 쓰고 있다면 이 이야기는 아직 해당되지 않습니다. 그쪽을 먼저 해결하십시오. 이 경우의 절차는 [Node 20 EOL Upgrade Runbook](/blog/node-20-eol-upgrade-runbook-docker-ci-2026-10)에 정리해 두었습니다.

## 정책에서 점검할 부분

### 1. Upgrade 주기를 LTS 날짜로 정의합니다

"새 Version이 나오면 올린다"가 아니라 달력에 묶인 규칙으로 적어 둡니다. 예를 들어 "새 LTS는 LTS에 진입한 분기에 평가하고, 이전 LTS가 Maintenance 전용 단계에 들어가기 전에 전환을 마친다"와 같은 방식입니다. 연 1회 Release라면 즉흥적인 대응 대신 예측 가능한 연간 Project로 만들 수 있습니다.

### 2. Version 고정 위치를 한 곳으로 모읍니다

Local, CI, Production 사이에 차이가 생기는 흔한 원인은 Version 문자열이 여기저기 흩어져 있기 때문입니다. 기준이 되는 곳을 하나로 정하고 나머지는 거기서 가져오게 합니다.

```text
# .nvmrc
26
```

```json
{
  "engines": {
    "node": ">=26 <27"
  }
}
```

```dockerfile
ARG NODE_VERSION=26
FROM node:${NODE_VERSION}-slim AS base
```

```yaml
# .github/workflows/ci.yml (발췌)
- uses: actions/setup-node@v4
  with:
    node-version-file: ".nvmrc"
```

`node-version-file`을 쓰면 Version 변경이 한 줄 수정으로 끝나고, CI와 Local 개발 환경이 같은 값을 참조합니다. 고정하는 Major는 실제로 운영하는 Line에 맞게 조정하십시오.

### 3. 다음 Line은 일찍 시험하되, Blocking Job으로 만들지 않습니다

Alpha 단계는 Release가 확정되기 전에 하위 Project들이 문제를 찾을 수 있도록 마련된 것입니다. Commit마다 전체 Test Suite를 돌릴 필요는 없습니다. 실패를 허용하는 정기 실행 Job 하나면 중요한 문제를 충분히 잡아낼 수 있습니다.

```yaml
name: node-next
on:
  schedule:
    - cron: "0 3 * * 1"   # 주 1회
jobs:
  test-next:
    runs-on: ubuntu-latest
    continue-on-error: true
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: "27.0.0-alpha"   # 프로젝트가 공개하는 식별자에 맞추세요
      - run: npm ci
      - run: npm test
```

Pre-release Build의 정확한 Version 문자열은 프로젝트의 배포 방식에 따라 다릅니다. 위의 Placeholder를 믿기 전에 Download 페이지나 `nvm ls-remote`로 확인하십시오. 실패는 Blocker가 아니라 추적할 정보로 다룹니다.

### 4. Native Addon과 Build Tooling을 재점검합니다

Major Upgrade의 비용은 자사 코드보다 새 ABI용 Prebuilt Binary가 필요한 Native Module, Lockfile 변동, Base Image에서 발생하는 경우가 많습니다. 연 1회 주기라면 이런 비용을 1년에 한 번 묶어서 처리할 수 있습니다. Native Code를 Compile하는 Dependency를 파악하고, 새 Line용 Binary가 제공되는지 일정을 확정하기 전에 확인하십시오.

### 5. Docker와 Runtime Image를 맞춥니다

Image Tag에는 `latest` 대신 Major를 고정하고, Line 안의 Patch가 반영되도록 정기적으로 다시 Build합니다. 보안 수정은 Point Release로 들어옵니다. Major를 잘못 고른 경우보다, Major는 맞는데 Patch가 몇 달 뒤처져 있는 경우가 실제로는 더 흔합니다.

## Trade-off

연 1회 주기는 Churn을 줄이지만 변경을 한곳으로 모읍니다. 각 Major가 6개월이 아니라 1년 치 semver-major 변경을 담게 되므로, 개별 Upgrade가 다소 커질 수 있습니다. Alpha 단계가 이에 대한 프로젝트의 답이지만, 우리 쪽에서 누군가 실제로 시험해 봐야 효과가 있습니다.

연도 기준 Version 번호도 작은 가독성 개선입니다. "Node 28"이라고 하면 처음 나온 시기를 대략 알 수 있어서, Runtime이 얼마나 오래되었는지에 관한 감사 논의가 조금 쉬워집니다.

## webhani의 권장 사항

대부분의 고객 Project에서는 다음과 같이 진행합니다.

1. LTS만 사용하고, 새 LTS를 채택해야 하는 기한을 날짜로 문서화합니다.
2. Version 고정(`.nvmrc` 등)을 한 곳에 모으고 CI와 Docker가 그것을 따르게 합니다.
3. 다음 Line의 Alpha Build가 나오면 주 단위의 Non-blocking Job을 추가합니다.
4. Release마다 반응하는 대신, 새 Line이 LTS에 진입하는 시기에 맞춰 연 1회의 Upgrade 기간을 확보합니다.

어느 것도 Node.js 27을 기다릴 필요가 없습니다. 지금 시작할 가치가 있습니다. 같은 구조가 현재의 Upgrade 비용도 낮춰 주기 때문입니다.
