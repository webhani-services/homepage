Node.js 22.18부터는 `.ts` 파일을 실행하는 데 `ts-node`도 `tsx`도 Build Step도 필요 없습니다. Type Stripping(타입 주석을 제거하고 나머지를 그대로 실행하는 방식)이 기본으로 활성화되어 있어, `node app.ts`가 그대로 동작합니다. 사소한 변화처럼 보이지만, 새로운 Backend Service나 CLI Tool, Script를 오늘 어떻게 Setup할지에는 실질적인 변화입니다.

여기서는 정확히 짚고 넘어갈 필요가 있습니다. "Node.js가 TypeScript를 지원한다"는 표현은 다소 과장된 것이고, 실제 동작과 이 표현 사이의 차이가 바로 CI에서 발목을 잡는 지점이기 때문입니다.

## Type Stripping이 실제로 하는 일

Node.js는 SWC Engine을 감싼 `amaro`라는 Module을 사용해, 소거 가능한 TypeScript 문법(타입 주석, Interface, Type-only Import)을 제거하고 남은 JavaScript를 그대로 실행합니다. 중요한 점은 **타입 Check는 전혀 하지 않는다**는 것입니다. 진단 Pass가 없고, `string`을 넣어야 할 자리에 `number`를 넣어도 Error가 나지 않습니다. 전통적인 의미의 Compiler가 아니라 문법 Transform입니다.

```ts
// greet.ts
interface Greeting {
  name: string;
  times: number;
}

function greet({ name, times }: Greeting): void {
  for (let i = 0; i < times; i++) {
    console.log(`Hello, ${name}`);
  }
}

greet({ name: "webhani", times: 2 });
```

```bash
node greet.ts
# Hello, webhani
# Hello, webhani
```

이걸 실행하는 데 Config도 Flag도 `tsconfig.json`도 필요 없습니다. Node는 `: Greeting`이나 `: void`를 제거하고 Stack Trace의 줄 번호가 어긋나지 않도록 공백으로 치환한 뒤, 나머지를 순수한 JS로 실행합니다.

## 의도적으로 지원하지 않는 것들

Type Stripping은 실행 시 동작을 바꾸지 않고 소거할 수 있는 문법에만 적용됩니다. 구체적으로 다음은 대상에서 제외됩니다.

- **Enum** — `enum Status { Active, Inactive }`는 단순한 타입이 아니라 실제 Runtime Code로 Compile됩니다.
- **Parameter Properties** — `constructor(private name: string)`는 Class Field 대입을 생성하므로 소거할 수 없습니다.
- **Runtime 값을 갖는 Namespace** — 예전 방식의 `namespace Foo { export const x = 1 }`는 실제 Object를 생성합니다.
- **Decorator** — 아직 TC39 Stage 3 Proposal 단계이며, 사용한다면 본격적인 Transform이 필요합니다.
- **JSX** — `.tsx`는 Stripping 대상이 아닙니다. JSX 문법은 어딘가에서 실제 `React.createElement` 호출로 변환되어야 합니다.

이런 경우에는 더 넓은 범위의 Transform을 적용하는 `--experimental-transform-types`로 Fallback하거나, 기존처럼 `tsc`, `SWC`, `esbuild`를 Loop에 남겨둬야 합니다. 바로 이 지점에서 신중해야 하는데, "일부 File은 Native Stripping으로 돌고, 일부는 Flag가 필요하고, 일부는 Bundler가 필요한" 상태를 명확한 Rule 없이 섞어 두면, 애초에 Build Step을 정당화했던 것과 같은 종류의 불일치가 다시 생깁니다.

## 실무에서 실제로 바뀌는 것

Enum이나 Decorator에 의존하지 않는 Script, CLI Tool, 소규모 Backend Service라면 Build Step은 말 그대로 사라집니다. 이는 사소한 편의가 아니라, "로컬에서는 되는데 Docker Image에서는 Build Step을 안 돌려서 안 되는" Category의 실패를 통째로 없앤다는 뜻이고, 그냥 실행만 하고 싶은 사람 입장에서는 `.ts` File이 `.js` File처럼 동작한다는 의미입니다.

더 큰 Application에 대해 솔직하게 말하면, **Type Stripping이 대체하는 것은 "실행" Step이지 "타입 Check" Step이 아닙니다.** CI에서는 여전히 Merge 전에 `tsc --noEmit`(또는 Editor의 Language Server)을 돌려야 합니다. Node가 그 File을 정상적으로 실행했다는 사실은 타입의 정확성에 대해 아무것도 보장하지 않기 때문입니다. "Node.js가 이제 TypeScript를 실행할 수 있으니까"라는 이유로 CI에서 `tsc --noEmit`을 빼버리는 것은, Build Step을 잘못된 안전감과 맞바꾸는 것에 불과합니다.

현실적인 Setup은 다음과 같습니다.

```json
{
  "scripts": {
    "dev": "node --watch src/index.ts",
    "typecheck": "tsc --noEmit",
    "start": "node src/index.ts"
  }
}
```

Development와 Production 모두 Source를 직접 실행합니다. `typecheck`는 CI에서 필수인 별도 Step으로 남겨둡니다. Browser로 배포하거나 단일 File Artifact가 필요한 경우가 아니라면 Bundler는 Loop에 넣지 않습니다.

## 그래도 정식 Compiler가 필요한 경우

NestJS 스타일의 Dependency Injection처럼 Decorator를 사용하는 Project, TypeScript Enum을 Domain Model의 일부로 쓰는 Project, 특정 Runtime 제약 때문에 예전 JavaScript Target으로 출력해야 하는 Project라면 Native Stripping은 아직 맞는 선택지가 아닙니다. 이는 Team의 취향이 아니라 Framework의 선택이 결정할 문제이므로, Build Step을 통째로 없앨 수 있다고 단정하기 전에 사용 중인 Framework의 Idiom이 소거 가능한 범위 안에 들어오는지 먼저 확인해야 합니다.

그 외의 경우 — API Service, 사내 Tooling, Script, Lambda 성격의 Function 등 — 라면 지금 도입할 가치가 있습니다. 마이그레이션 비용의 본질은 Code 변경이 아니라, Build Step이 암묵적으로 담당하던 타입 Check가 Build Step의 소멸과 함께 같이 사라지지 않았는지 CI에서 확인하는 것입니다.
