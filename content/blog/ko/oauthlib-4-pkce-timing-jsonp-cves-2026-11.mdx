`oauthlib`를 직접 설치한 기억은 없어도 프로젝트에 들어 있는 경우가 많습니다. `requests-oauthlib`를 통해 Kubernetes Python Client, 각종 SaaS SDK, Django·Flask의 OAuth 확장 등이 이 Library에 의존합니다. 이번에 oauthlib에 대한 CVE 2건이 공개되었고, 수정 버전인 4.0.0이 출시되었습니다.

문제는 "버전만 올리면 끝"이 되기 어렵다는 점입니다. 수정은 Major Release인 4.0.0에만 포함되어 있고, 3.x 계열로의 Backport는 없습니다.

## 두 취약점의 내용

### CVE-2026-49265: PKCE `code_verifier` 비교의 Timing Attack

PKCE에서 Client는 Authorization Request 때 `code_challenge`를 보내고, Token Request 때 원래의 `code_verifier`를 제시합니다. Authorization Server는 둘이 일치하는지 검증합니다.

oauthlib 3.0.0 이상 4.0.0 미만은 이 비교를 일반 문자열 비교로 처리했습니다. 일반 비교는 다른 문자를 만나는 순간 종료되므로, 이론상 처리 시간의 차이로 정답에 가까워질 수 있습니다. 4.0.0에서는 `hmac.compare_digest`를 사용한 상수 시간 비교로 바뀌었습니다. GitLab Advisory Database 기준 CVSS는 6.8(Medium)입니다.

실제 위험도는 낮은 편입니다. Advisory의 PoC에서 관측된 시간 차이는 1,000만 번 반복에 약 0.037초에 불과하고, 공격하려면 한 번만 쓸 수 있는 Authorization Code를 먼저 가로채야 합니다. Splunk의 분석도 이를 Authorization Server의 다층 방어 관점 문제로 봅니다. 급하지는 않지만 방치할 이유도 없습니다.

### CVE-2026-49264: RevocationEndpoint의 JSONP Callback Injection

0.6.1 이상 4.0.0 미만에서는 Token Revocation Endpoint에 `enable_jsonp=True`를 설정한 경우, `callback` Parameter가 검증 없이 Response Body에 삽입됩니다. 그 결과 임의의 JavaScript가 담긴 Response를 만들어 낼 수 있습니다.

JSONP는 기본값이 비활성화입니다. 명시적으로 켠 Deployment만 영향을 받으며, 2026년에 JSONP를 써야 할 이유는 거의 없습니다.

## 우리 서비스는 영향을 받는가

먼저 oauthlib를 **Server(Provider) 쪽**에서 쓰는지, **Client 쪽**에서 쓰는지 구분해야 합니다.

- **oauthlib로 Authorization Server를 구현한 경우**(oauthlib의 Provider Class를 직접 쓰거나 django-oauth-toolkit 같은 Library를 사용) → 두 CVE 모두 해당됩니다. 우선순위를 높여야 합니다.
- **외부 API를 호출하는 Client로만 쓰는 경우**(`requests-oauthlib`로 Token을 받는 등) → 두 취약점 모두 Server 쪽 처리이므로 직접적인 영향은 제한적입니다. 다만 취약점 Scanner에는 검출되므로 대응 방침은 정해 두어야 합니다.

의존 경로는 다음과 같이 확인할 수 있습니다.

```bash
# uv 프로젝트
uv tree --invert --package oauthlib

# pip 환경
pip install pipdeptree
pipdeptree --reverse --packages oauthlib
```

JSONP 활성화 여부는 Code 검색으로 확인합니다.

```bash
grep -rn "enable_jsonp" --include="*.py" .
```

## 4.0.0으로 올리기

4.0.0의 Breaking Change는 주로 Provider 쪽 Interface에 있으며, Client 쪽 Interface는 바뀌지 않은 것으로 알려져 있습니다. Client 용도라면 업그레이드 위험은 비교적 낮습니다.

주의할 점은 `requests-oauthlib`가 `oauthlib>=3.0.0`만 선언하고 있다는 것입니다. Resolver 상황에 따라 취약한 3.x가 설치될 수 있습니다. Kubernetes Python Client에서도 같은 이유로 `oauthlib>=4.0.0`을 명시하는 Issue와 PR이 올라와 있습니다. 우리 프로젝트에서도 하한을 명시합니다.

```toml
# pyproject.toml
[project]
dependencies = [
  "requests-oauthlib>=2.0",
  "oauthlib>=4.0.0",  # CVE-2026-49264 / CVE-2026-49265
]
```

## 4.0.0으로 올릴 수 없을 때

까다로운 경우는 다른 의존 Library가 `oauthlib<4.0.0`으로 상한을 걸어 둔 상황입니다. oauthlib Repository에 3.x 수정 Release를 요청하는 Issue가 있지만, 이 글을 쓰는 시점까지 Maintainer의 대응은 없습니다. 선택지는 다음과 같습니다.

1. **영향을 판단하고 기록합니다.** Client 용도이고 JSONP도 쓰지 않는다면 실질적인 영향은 없습니다. Scanner 검출은 이유와 재검토 날짜를 붙여 예외로 등록합니다.
2. **직접 구현한 비교 로직은 스스로 보호합니다.** 자체 PKCE 검증 Code가 있다면, Library와 상관없이 그 부분은 상수 시간 비교로 작성합니다.

```python
import base64
import hashlib
import hmac


def verify_pkce_s256(code_verifier: str, code_challenge: str) -> bool:
    digest = hashlib.sha256(code_verifier.encode("ascii")).digest()
    expected = base64.urlsafe_b64encode(digest).rstrip(b"=").decode("ascii")
    # == 대신 상수 시간 비교
    return hmac.compare_digest(expected, code_challenge)
```

3. **Upstream에 PR을 보냅니다.** 상한이 단지 보수적으로 잡혀 있는 경우가 많아, `<5.0.0`으로 완화하고 Test가 통과하면 금방 해결되기도 합니다.

## CI에서 지속적으로 검출하기

간접 의존성의 CVE는 Code Review로는 알아챌 수 없습니다. `pip-audit`를 CI에 넣어 두면 Pull Request 단계에서 검출할 수 있습니다.

```yaml
# .github/workflows/audit.yml
name: dependency-audit
on: [pull_request]
jobs:
  pip-audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<full-commit-sha>
      - uses: actions/setup-python@<full-commit-sha>
        with:
          python-version: "3.13"
      - run: pip install pip-audit
      - run: pip-audit -r requirements.txt
```

예외로 처리한 CVE는 `--ignore-vuln`으로 명시하고, 이유와 기한을 Comment로 남겨 두면 반년 뒤에도 판단 근거를 추적할 수 있습니다.

## webhani의 관점

두 CVE 모두 단독으로는 심각도가 높지 않습니다. 그럼에도 다루는 이유는 Python 의존성 관리에서 자주 겪는 구조가 그대로 드러나기 때문입니다.

- 수정이 Major Release에만 있다
- 간접 의존성이라 버전을 직접 정한 적이 없다
- 중간 Library가 상한을 걸어 두어 올리고 싶어도 올릴 수 없다

이럴 때 필요한 것은 "일단 올리기"도 "심각도가 낮으니 무시"도 아닌, **실제 사용 방식에 비추어 영향을 판단하고 그 판단을 기록하는 것**입니다. OAuth Server를 구현하고 있다면 4.0.0 전환을 우선하고, Client 용도라면 하한 고정과 예외 등록으로 충분한 경우가 많습니다.

이번 주 할 일은 세 가지입니다.

1. `uv tree --invert`나 `pipdeptree`로 oauthlib를 끌어오는 경로를 확인합니다.
2. Server 용도인지 Client 용도인지, `enable_jsonp`를 켜 두지 않았는지 확인합니다.
3. 가능하면 `oauthlib>=4.0.0`을 명시하고, 어렵다면 이유와 함께 예외로 등록합니다.

인증 관련 Library는 쓰고 있다는 인식이 약할수록 업데이트가 늦어집니다. 이번 기회에 의존성 Tree 안의 인증 관련 Package를 한 번 점검해 보시기 바랍니다.
