대부분의 팀은 Observability Platform에 매달 얼마를 지불하는지 정확히 알고 있습니다. 하지만 그 Dashboard 중 지난 분기에 실제로 누군가 열어본 것이 몇 개인지, 매주 울리지만 아무도 조사하지 않고 넘기는 Alert가 어떤 것인지 대답할 수 있는 팀은 훨씬 적습니다. 이 간극이 바로 "Telemetry Debt"입니다. 수년에 걸쳐 쌓인 Metrics, Logs, Traces instrumentation을 아무도 되돌아보지 않고 방치한 상태를 말합니다.

이는 기술 부채(Technical Debt)와 같은 구조를 가지지만, 이자는 Monitoring 청구서와 On-call 엔지니어의 주의력 두 곳 모두에 붙습니다. 방치하면 비용만 늘어나는 것이 아니라, 실제 장애 대응 시 필요한 Signal이 아무도 정리하지 않은 Noise 아래 묻혀버려 Incident 대응 자체를 저하시킵니다.

## Telemetry Debt는 실제로 어떻게 쌓이는가

한 번의 잘못된 결정으로 발생하지 않습니다. 개별적으로는 합리적으로 보이는 작은 결정들이 쌓인 결과입니다.

- **즉흥적인 Alert 설계**: Incident가 발생할 때마다 "다시는 이런 일이 없도록" Alert를 추가하고, 근본 원인이 해결된 뒤에도 그 Alert는 그대로 남습니다. 2년 뒤에는 누가 왜 그 threshold를 정했는지 아무도 기억 못하는 채로 매달 울립니다.
- **주인 없는 Dashboard**: 특정 프로젝트나 Migration, 혹은 지금은 원래 형태로 존재하지 않는 팀을 위해 만들어진 Dashboard가 공유 폴더에 그대로 남습니다. 누군가 Tool을 열 때마다 Query 부하가 발생하고 Seat와 API 예산을 계속 소비합니다.
- **제한 없는 Custom Metric Cardinality**: `user_id`, `order_id`, 혹은 정규화하지 않은 Request Path를 그대로 Label로 붙이는 경우입니다. 값의 고유 조합마다 새로운 Time Series가 생성되기 때문에, Traffic이 많은 Service에서는 Metric 정의 하나가 수백만 개의 Series로 불어날 수 있습니다. 대부분의 Observability Vendor가 Active Series 수 기준으로 과금하기 때문에 이는 곧바로 비용으로 이어집니다.
- **프로덕션에 남은 Debug Level Logging**: 버그를 추적하려고 추가한 상세 Log가 프로덕션에 그대로 배포되고 다시 낮춰지지 않습니다. Service와 Deploy 수만큼 곱해지면서 Log 수집량과 비용이 눈치채지 못하는 사이 몇 배로 늘어납니다.

이 각각은 단독으로 보면 누구의 실수도 아닙니다. 문제는 "이게 아직 필요한가"를 주기적으로 되묻는 프로세스 자체가 없다는 점입니다.

## 실전 감사 방법

Client에게 개선안을 제시하기 전, webhani는 다음 세 가지 축으로 감사를 진행합니다.

**1. Dashboard 사용 현황**: Grafana, Datadog, New Relic 등 대부분의 최신 Observability Platform은 Dashboard 단위 조회 이력을 UI나 API로 제공합니다. 최근 90일 조회 수를 가져와서, 정기 Export나 Synthetic Check가 아닌 실제 사용자에 의한 조회가 0에 가까운 Dashboard를 삭제나 Archive 후보로 분류합니다.

**2. Alert의 "울리기만 하고 무시됨" 비율**: Alert 발생 이력을 Incident/Ticket 이력과 대조합니다. 한 분기에 40번 울렸는데 실제 Incident 개설로 이어진 건 두 번뿐인 Alert는 아무도 보호하지 못하고 있는 것입니다. On-call 담당자에게 Slack 알림을 무시하는 습관만 학습시킬 뿐입니다. 발생 빈도는 높은데 실제 대응 조치로 이어진 비율은 낮은 Alert를 집중적으로 찾아냅니다.

**3. Cardinality Cost Driver**: 대부분의 Vendor는 Active Series 수나 수집량 기준으로 Metric 순위를 보여주는 기능을 제공합니다. Prometheus를 직접 운영 중이라면 다음과 같은 Query로 바로 확인할 수 있습니다.

```promql
# Active Time Series 수가 많은 Metric 이름 상위 10개
topk(10, count by (__name__)({__name__=~".+"}))
```

```promql
# 특정 Metric의 Cardinality를 밀어올리는 Label 찾기
count by (label_name) (
  count by (label_name, __name__) (http_requests_total)
)
```

실제로는 `user_id`, `session_id`, 혹은 제한 없는 Path Label을 가진 소수의 Metric이 전체 Series 수의 대부분을 차지하는 경우가 많습니다. Metric 정의 서너 개만 고쳐도 청구서를 눈에 띄게 움직일 수 있는 경우가 흔합니다.

## 개선을 위한 기술적 Playbook

### OpenTelemetry Sampling 전략

OpenTelemetry는 Traces, Metrics, Logs instrumentation의 사실상 표준(de facto standard)이 되었지만, Trace 양에 가장 크게 영향을 미치는 레버는 Sampling 전략입니다.

- **Head-based Sampling**은 Trace가 시작되는 시점에 고정 확률로 유지 여부를 결정합니다. 저렴하고 단순하지만, 정작 조사가 필요한 느린 Trace나 에러가 포함된 Trace를 놓칠 수 있습니다.
- **Tail-based Sampling**은 Trace가 완료될 때까지 기다린 뒤 실제 결과를 기준으로 판단합니다. 에러와 지연된 Trace는 모두 보존하고, 정상적이고 빠른 Trace는 일부만 Sample합니다. Span을 일시적으로 버퍼링하고 판단을 후단에서 내리는 Collector가 필요해 비용은 더 들지만, 정작 중요한 Trace를 놓치지 않습니다.

OpenTelemetry Collector에서 단순화한 Tail Sampling 설정 예시입니다.

```yaml
processors:
  tail_sampling:
    decision_wait: 10s
    policies:
      - name: keep-errors
        type: status_code
        status_code:
          status_codes: [ERROR]
      - name: keep-slow-requests
        type: latency
        latency:
          threshold_ms: 500
      - name: sample-the-rest
        type: probabilistic
        probabilistic:
          sampling_percentage: 5
```

이는 어디까지나 예시입니다. 실제 운영에서는 Policy 종류와 조합 로직을 Tuning해야 하지만, "에러와 이상치는 반드시 남기고 일반 Traffic은 적극적으로 걸러낸다"는 기본 원칙은 그대로 유지됩니다.

### Log Level 정책과 구조화 Logging 원칙

명확한 정책을 세우세요. `debug` Level은 로컬과 Staging 환경 전용으로 제한하고, 프로덕션에 남은 `debug` Log는 삭제하거나 Feature Flag로 제어하도록 요구하는 Follow-up Ticket을 필수화합니다. 여기에 JSON 같은 구조화 Logging을 함께 사용하면 자유 Text를 grep하는 대신 Field 단위로 필터링·집계할 수 있고, "혹시 몰라서" 과도하게 Log를 남기려는 동기 자체를 줄일 수 있습니다.

### SLO에 연결된 Alert 통합

CPU, Memory, Queue Depth, Disk 같은 개별 Infrastructure 증상마다 낮은 Signal의 Alert를 여러 개 두는 대신, 가용성·Latency·Error Rate 같은 소수의 SLO를 정의하고 Error Budget 소진 속도(Burn Rate)를 기준으로 Alert를 겁니다. 잘 Tuning된 Burn Rate Alert 하나가 Noise 많은 threshold Alert 여러 개를 대체하며, Resource의 사소한 변화가 아니라 실제 사용자 영향을 직접 반영합니다.

### Retention 계층화

모든 Telemetry가 같은 해상도와 보존 기간을 필요로 하지는 않습니다. 대략적인 기준으로는, Full Resolution의 Metrics/Traces는 15~30일간 Hot하게 보관하고, 추이 분석용으로 Downsample된 집계 데이터는 6~13개월 보존하며, Incident 조사에 쓰이는 고 Cardinality Raw Data는 조사 기간이 끝나면 폐기하는 구성이 현실적입니다. 대부분의 Platform이 이를 기본 기능으로 지원하며, 직접 운영하는 경우 Prometheus의 Recording Rules와 장기 저장용 Backend 조합으로 같은 효과를 낼 수 있습니다.

## 운영 체계와 실행 주기

Telemetry Debt가 쌓이는 이유는 "추가하는 사람"은 있어도 "삭제하는 사람"은 없기 때문입니다. webhani는 다음 두 가지를 함께 권장합니다.

1. **분기별 Observability 감사**: Security Review와 같은 수준의 진지함으로 다루며, Dashboard 사용 현황 Report, Alert 발생·무시 비율 Report, Cardinality Top-N Report를 SRE/Platform 팀과 각 Service 팀 대표가 함께 검토합니다.
2. **발생 지점에서의 Ownership**: Alert나 Dashboard를 만든 팀이 삭제까지 포함한 Lifecycle 전체의 Owner입니다. SRE/Platform 팀은 감사 프로세스와 Tooling을 Owner하지만, 다른 팀의 instrumentation을 일방적으로 삭제하지 않고 삭제 후보를 제시해 승인을 요청합니다. 이렇게 하면 갈등 없이 프로세스를 빠르게 돌릴 수 있습니다.

## Checklist

- [ ] 최근 90일 Dashboard 조회 이력을 가져와서 사용되지 않는 것을 Archive한다
- [ ] Alert 발생 횟수를 Incident Ticket과 대조해 무시되는 Alert를 통합·삭제한다
- [ ] Active Series 수 기준으로 Metric 순위를 매겨 Cardinality 주범 Metric부터 수정한다
- [ ] 프로덕션 환경에서 Debug Level Logging이 기본적으로 비활성화되어 있는지 확인한다
- [ ] 에러·Latency 가시성이 중요한 구간에는 Tail-based Sampling을 도입한다
- [ ] 증상 기반 threshold Alert를 SLO 기반 Burn Rate Alert로 대체한다
- [ ] Hot / Downsample / 폐기의 Retention 계층을 설정한다
- [ ] 감사 Owner(SRE/Platform)와 instrumentation Owner(발생 팀)를 명확히 지정한다
- [ ] 이번 감사를 마무리하기 전에 다음 분기 감사 일정을 확정한다

Telemetry Debt는 장애처럼 요란하게 자신을 드러내지 않습니다. 갱신할 때마다 조금씩 불어나는 청구서와, Monitoring을 무시하는 법을 서서히 배워가는 On-call 로테이션으로 조용히 나타납니다. 정리를 한 번의 대청소가 아니라 반복되는 습관으로 다루는 것만이 이 문제가 다시 쌓이지 않게 하는 유일한 방법입니다.
