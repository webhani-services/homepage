## Agent 구현에서 가장 시간을 잡아먹는 부분

LLM Agent를 실제 Production까지 배포해본 팀에 "가장 오래 걸린 부분이 어디였냐"고 물으면, Prompt가 아니라 "배관 작업"이라는 답이 자주 나옵니다. 대화가 길어질수록 Context를 Model의 Window 안에 맞추는 작업, 무엇을 요약하고 무엇을 남길지 판단하는 작업, 부모 Agent의 Context를 오염시키지 않으면서 Sub-task를 다른 Agent에게 위임하는 구조, Tool 호출 도중 오래 실행되던 Job이 죽었을 때의 복구, 그리고 이번 턴에 쓰지 않을 Tool의 Schema까지 Token을 낭비하지 않도록 지연 로딩하는 것 — 이 중 새로운 기술은 하나도 없습니다. 단지 지루하고, 자체 구현하면 미묘하게 틀리기 쉬운 부분일 뿐입니다.

지금까지는 순수 Chat Completion API 위에 Agent를 쌓아 올리는 모든 팀이 이 배관 작업을 직접 작성해야 했습니다. 2026년 9월 10일, OpenAI는 이 문제에 대한 자체 답을 Public API로 공개했습니다. Codex 계열 Coding Agent를 구동하는 것과 동일한 Harness를 외부에서 호출할 수 있는 Agents API, Public Beta입니다.

## 실제로 대신 처리해주는 것들

Agents API는 agent, environment, session, events라는 4가지 개념을 축으로 구성되어 있고, 핵심 가치는 이 4가지와 관련된 어려운 부분을 OpenAI가 관리해준다는 데 있습니다.

- **Session Orchestration** — 여러 턴과 Tool 호출에 걸친 Session을 매번 전체 History를 다시 보내지 않고도 유지
- **Context Compaction** — Session이 Context 한도에 가까워지면 이전 대화를 자동으로 압축. 직접 요약 로직을 작성할 필요 없이 Root Agent와 각 Subagent에서 독립적으로 처리
- **Sub-agent Coordination** — Root Agent가 작업을 나눠 Subagent에게 위임하면, 각 Subagent는 독립된 Context를 유지하며 병렬로 동작하고 결과를 Root에 반환
- **Tool 지연 로딩** — Tool Schema는 작업이 실제로 필요로 하는 시점에만 Context에 로드됨
- **Crash Recovery** — 오래 실행되는 Session이 중간 단계에서 실패해도 그 이전 상태를 잃지 않음

실행은 OpenAI가 Hosting하는 Sandbox 또는 직접 지정한 Compute 환경에서 이루어지고, 과금은 Model Token, Tool 사용량, Hosted Sandbox 실행 시간뿐이며 별도의 Platform 이용료는 없습니다.

## 감을 잡기 위한 예시 코드 (Spec을 그대로 옮긴 것이 아닌 개념 설명용)

정확한 Request/Response Schema는 Beta 기간 동안 계속 바뀔 예정이므로, 아래는 그대로 복사해 쓸 수 있는 Reference가 아니라 패턴을 보여주는 예시로 봐주세요.

```python
from openai import OpenAI

client = OpenAI()

session = client.agents.sessions.create(
    agent="repo-maintainer",
    environment={"sandbox": "hosted"},
    tools=["read_file", "run_tests", "open_pull_request"],
)

client.agents.sessions.send(
    session_id=session.id,
    input="payment_service에서 실패하는 Test를 찾아 수정하고 PR을 열어줘.",
)

for event in client.agents.sessions.stream(session_id=session.id):
    if event.type == "subagent.spawned":
        print(f"위임된 Subagent: {event.subagent_id}")
    if event.type == "session.compacted":
        print("Context가 압축되었습니다. 회수한 Token 수:", event.tokens_reclaimed)
```

여기서 흥미로운 부분은 `session.compacted` 이벤트입니다. 대부분의 팀이 직접 구현할 경우 제대로 처리하지 못하거나 아예 구현조차 하지 않는 부분이 바로 여기입니다.

## 대체되는 것과 대체되지 않는 것

지금 구조가 Chat Completion 위에 손수 짠 Loop — 수동 History Trimming, 자체 Retry 로직, 임시방편으로 만든 Sub-task 생성 — 라면, Agents API는 상당한 양의 Infrastructure Code를 없애줍니다. 첫 Agent를 동작시키기까지의 시간을 확실히 줄여줍니다.

반면 얼마나 많은 통제권을 넘길 것인가에 대한 판단은 여전히 남습니다. Managed Harness는 OpenAI의 기준으로 "무엇을 버려도 안전한지" 판단해 Context를 압축하고, OpenAI의 실행 Model 위에서 동작하며, Orchestration 로직을 해당 Platform에 고정시킵니다. 이미 Claude Agent SDK나 LangGraph, 혹은 여러 Model Provider에 대응해야 하는 자체 Harness에 투자한 팀이라면 이 편의성이 Lock-in을 상쇄하지 못할 수 있습니다.

## 실무에서는 어디에 쓸 것인가

Client 프로젝트에서 판단할 때 핵심은 두 가지입니다. 여러 Provider에 대한 유연성이 필요한가, 그리고 Agent가 맡을 작업이 직접 Orchestration을 구현할 만큼의 가치가 있는가입니다.

- **적합한 경우**: OpenAI를 Model로 받아들이는 신규 사내 Tool이나 MVP, 대규모 Codebase Migration이나 여러 File에 걸친 Refactor처럼 Sub-agent 병렬 처리가 실제로 효과를 내는 작업, Harness 구현에 몇 주를 쓰고 싶지 않은 경우
- **적합하지 않은 경우**: Client가 이미 Anthropic으로 표준화했거나, 비용이나 성능에 따라 Provider를 바꿔야 하거나, Session Data와 Sandbox 실행 위치에 Compliance 제약이 있는 경우

## webhani의 견해

Agents API는 "Agent를 만드는 대부분의 팀은 Orchestration 계층을 직접 소유하고 싶은 게 아니라, Agent의 동작만 통제하고 Context 관리는 다른 곳에 맡기고 싶어한다"는 데 건 Bet입니다. 사내 Tool이나 Prototype 상당수에는 합리적인 선택입니다. 다만 여러 해 동안 유지해야 하는 Customer 대상 Service라면, Context Compaction의 동작 방식이나 Subagent 연동 방식은 한 번 의존하면 걷어내기 어려운 부분이므로, Managed Harness로의 이전 비용과 Open한 구성이 주는 유연성을 미리 비교해보길 권합니다.

도입을 검토 중이라면 PR 1차 Triage나 문서 동기화 같은, Customer에게 직접 노출되지 않는 사내 Workflow부터 시작하는 것이 안전합니다.
