11월 4일, OpenAI가 Pierre Computer Company 인수 계획을 발표했습니다. Pierre는 사람이 아닌 AI 플랫폼을 위해 만든 hosted Git Service인 Code Storage, 그리고 Codex 앱의 파일 탐색과 변경 사항 리뷰에 이미 쓰이고 있는 오픈소스 Library Trees·Diffs를 만든 회사입니다. 인수 금액은 공개되지 않았고 규제 당국 승인을 기다리는 단계입니다. OpenAI는 Pierre의 오픈소스 프로젝트를 계속 오픈소스로 유지하겠다고 밝혔습니다.

대부분의 기사는 "OpenAI가 GitHub에 도전한다"는 관점으로 다룹니다. 그 의미는 몇 년 뒤에나 드러날 수 있습니다. 지금 Coding Agent를 쓰는 팀에게 더 실질적인 질문은 따로 있습니다. **AI 회사가 왜 자체 Git 인프라까지 필요로 할까요?**

## Agent는 사람과 다른 방식으로 Git을 씁니다

기존 Git hosting은 사람의 작업 리듬에 맞춰 설계되었습니다. 하루에 몇 번 push하고, Pull Request를 열고, 리뷰를 기다리는 흐름입니다. Coding Agent는 이 전제를 꽤 예측 가능한 방식으로 깨뜨립니다.

- **Branch 수**: 한 작업에 세 가지 접근을 시도하는 Agent는 Branch를 세 개 만듭니다. Agent 여러 개가 동시에 돌면 수천 개가 되고, 대부분 한 시간 안에 버려집니다
- **Commit 빈도**: 잘못된 단계를 되돌리기 위해 tool 호출마다 checkpoint commit을 남기기도 합니다
- **코드 읽는 방식**: clone보다 grep, glob, blame이 압도적으로 많습니다. "이 함수 어디서 호출하지?"를 알기 위해 대형 monorepo를 통째로 clone하는 건 느리고 낭비입니다
- **Latency 민감도**: 사람은 2초짜리 push를 거의 의식하지 못하지만, push를 200번 반복하는 Agent loop에서는 큰 차이가 납니다

Code Storage의 공개 문서에도 이런 경향이 그대로 드러납니다. API 레벨 grep, glob 기반 archive 다운로드, 파일 streaming, Git namespace로 구현한 ephemeral branch, TypeScript·Python·Go SDK, MCP Server가 나열되어 있습니다. 인수 결과와 상관없이, 이 기능 목록은 Agent가 Repository에 무엇을 요구하는지 보여 주는 좋은 지도입니다.

## Vendor를 바꾸지 않아도 같은 발상을 적용할 수 있습니다

webhani가 지원하는 팀 대부분은 GitHub나 GitLab 위에서 Coding Agent를 운영하고 있고, 이번 소식 때문에 hosting을 옮길 가능성은 낮습니다. 그래도 설계 아이디어는 가져올 수 있습니다.

### 시행착오는 로컬 worktree 안에서 끝냅니다

공유 remote에 `agent/*` Branch가 수백 개 쌓이면 목록이 지저분해지고, CI와 webhook도 불필요하게 돌아갑니다. 탐색은 로컬 worktree에서 하고, 채택한 결과만 push합니다.

```bash
#!/usr/bin/env bash
# Agent 시도 N회를 독립된 worktree에서 실행하고, 채택한 것만 push
set -euo pipefail

TASK_ID="$1"
ATTEMPTS="${2:-3}"
BASE="origin/main"

git fetch --quiet origin main

for i in $(seq 1 "$ATTEMPTS"); do
  dir=".agent-work/${TASK_ID}-${i}"
  git worktree add --quiet -b "scratch/${TASK_ID}-${i}" "$dir" "$BASE"
  # 여기서 "$dir"을 Agent Runner에 전달
done

echo "평가 후 채택한 시도만 push:"
echo "  git push origin scratch/${TASK_ID}-<n>:agent/${TASK_ID}"
echo "  git worktree remove .agent-work/${TASK_ID}-<n>"
```

remote에는 채택된 하나만 `agent/<task>`라는 고정된 이름으로 올라가므로, Branch 보호 규칙과 CI 설정도 이 이름을 기준으로 작성할 수 있습니다.

### clone 대신 검색 API를 제공합니다

Agent가 주로 코드를 검색한다면 전체 checkout보다 검색 tool을 주는 편이 낫습니다. 공유 bare mirror에 대한 `git grep` wrapper 정도면 대부분 충분합니다.

```typescript
import { execFile } from "node:child_process";
import { promisify } from "node:util";

const run = promisify(execFile);

// cron으로 git fetch해 최신 상태를 유지하는 읽기 전용 mirror
const MIRROR = "/srv/mirrors/app.git";

export async function grepAtRef(pattern: string, ref = "origin/main") {
  // execFile로 shell injection 방지, -F로 고정 문자열 검색
  const { stdout } = await run(
    "git",
    ["--git-dir", MIRROR, "grep", "-n", "-F", "-e", pattern, ref, "--"],
    { maxBuffer: 10 * 1024 * 1024 },
  ).catch((err) => {
    // 일치 결과가 없으면 git grep은 exit 1
    if (err.code === 1) return { stdout: "" };
    throw err;
  });

  return stdout
    .split("\n")
    .filter(Boolean)
    .map((line) => {
      // 형식: <ref>:<path>:<line>:<content>
      const [, path, lineNo, ...rest] = line.split(":");
      return { path, line: Number(lineNo), text: rest.join(":") };
    });
}
```

이를 MCP 같은 tool로 노출하면 대형 Repository에서 Agent 시작 시간이 크게 줄고, 실제로 쓰기가 필요해질 때까지 Agent를 읽기 전용으로 둘 수 있습니다.

### Storage를 Interface 뒤에 둡니다

이번 인수는 Agent tooling 시장이 빠르게 통합되고 있다는 신호이기도 합니다. Agent 플랫폼 곳곳에서 Git hosting API를 직접 호출하고 있다면 나중에 교체하기가 매우 어렵습니다. Agent에게 필요한 연산만 정의하고 구현은 갈아 끼울 수 있게 만듭니다.

```typescript
export interface AgentRepoStore {
  createEphemeralBranch(task: string, base: string): Promise<string>;
  commit(branch: string, files: Record<string, string>, message: string): Promise<string>;
  grep(pattern: string, ref: string): Promise<{ path: string; line: number; text: string }[]>;
  promote(branch: string, target: string): Promise<void>; // 예: PR 생성
  discard(branch: string): Promise<void>;
}
```

첫 구현은 로컬 worktree와 GitHub API로 충분합니다. 나중에 전용 Service를 도입하더라도 Adapter 하나만 교체하면 되고 Agent 로직은 손대지 않아도 됩니다.

## 오픈소스 의존성에 대해

자사 제품에서 Trees나 Diffs를 쓰는 팀은 오픈소스를 유지하겠다는 OpenAI의 설명을 그대로 받아들여도 무방하다고 봅니다. 다만 평소의 관리 원칙은 유지하십시오. 버전을 고정하고, 인수 완료 후 라이선스나 거버넌스 변경이 없는지 Repository를 지켜보고, 실제로 의존하는 기능이 무엇인지 파악해 둡니다. 관리 주체가 바뀌는 Library라면 어디에나 권장하는 수준의 점검이지, 당장 걷어낼 이유는 아닙니다.

## webhani의 시각

이번 소식의 핵심은 OpenAI 대 GitHub 구도가 아닙니다. **Repository가 Agent 인프라가 되어 가고 있다**는 점입니다. 그리고 Agent에게 중요한 접근 패턴, 즉 저렴한 ephemeral branch, Server 측 검색, 낮은 latency의 commit은 사람 중심 Git hosting이 최적화해 온 방향과 다릅니다.

대부분의 조직에서 지금 할 일은 크지 않습니다.

1. Agent 탐색은 로컬 worktree나 namespace에서 하고 결과만 push합니다
2. Agent에 검색 tool을 제공해 매번 전체 clone하지 않게 합니다
3. Agent orchestration과 Git hosting 사이에 Interface를 둡니다
4. Agent의 push·branch·clone 횟수를 측정합니다. 빠르게 늘고 있다면 hosting의 rate limit에 걸리기 전에 대비합니다

어느 것도 인수 완료를 기다릴 필요가 없습니다. Agent를 여러 개 운영하는 팀이라면 지금 정비해 둘 만한 설계입니다.
