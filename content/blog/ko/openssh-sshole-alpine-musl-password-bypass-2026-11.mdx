11월 5일, Alpine Linux와 OpenSSH 프로젝트가 sshd의 비밀번호 인증 우회 취약점에 대한 advisory를 발표했습니다. CVE-2026-123158로 등록되었고 'sshole'이라는 별칭으로 불립니다. CVSS 3.1 기준 점수는 8.1(High)입니다.

이 취약점이 까다로운 이유는 **애초에 비밀번호 로그인을 쓰지 않는 계정이 오히려 공격 대상**이 된다는 점입니다. Key 인증만 쓰는 사용자, 비밀번호가 잠긴(locked) 계정이 여기에 해당합니다.

## 영향 조건

공개된 advisory를 기준으로 정리하면, 다음 조건을 모두 만족할 때 영향을 받습니다.

- **musl libc로 빌드되고 PAM을 사용하지 않는 OpenSSH**. Alpine의 기본 `openssh-server` Package가 이에 해당합니다
- `PasswordAuthentication`이 활성화되어 있음 (OpenSSH 기본값은 `yes`)
- 대상 계정에 사용 가능한 비밀번호가 설정되어 있지 않음

이 조건에서 비정상적으로 긴 비밀번호를 조작해 보내면, 원래 비밀번호로는 들어갈 수 없어야 할 계정에 로그인이 된다고 알려져 있습니다. Dropbear 등 OpenSSH가 아닌 Server는 영향이 없다는 분석도 나와 있습니다.

수정 버전은 11월 5일 릴리스된 OpenSSH 10.6p2이고, Alpine은 edge와 3.16 이후 모든 stable branch에 패치된 Package를 배포했습니다. 11월 6일 시점에 공개된 재현 코드는 있지만 실제 악용 사례는 확인되지 않았고, CISA KEV에도 등록되지 않았습니다. 다만 재현 코드가 이미 공개된 이상, 악용까지 남은 시간은 길지 않다고 봐야 합니다.

## 먼저 Alpine sshd가 어디 있는지 찾습니다

Debian, Ubuntu, RHEL은 glibc 기반이라 이번 조건에 해당하지 않습니다. 그래서 실제 작업의 핵심은 범위를 좁히는 것입니다. webhani가 고객 환경을 점검할 때 보면, Alpine sshd는 자산 목록에 잘 드러나지 않는 곳에 남아 있는 경우가 많습니다.

- 작은 VM이나 Container로 띄운 bastion(점프 Server)
- CI에서 쓰는 SFTP 수신 지점, Git mirror
- 개발용 `docker compose`에 들어 있는 "SSH 접속 가능한 Container"
- 내부적으로 Alpine을 쓰는 벤더 appliance

Host에서는 다음 스크립트로 판별할 수 있습니다.

```bash
#!/bin/sh
# CVE-2026-123158 영향 여부 간이 점검
set -eu

[ -f /etc/alpine-release ] && echo "distro: alpine $(cat /etc/alpine-release)"

if ldd "$(command -v sshd)" 2>/dev/null | grep -q musl; then
  echo "libc: musl"
fi

# Include된 drop-in 파일까지 반영된 실제 설정값
sshd -T 2>/dev/null | grep -Ei '^(passwordauthentication|usepam) '

sshd -V 2>&1 | head -1 || ssh -V 2>&1
```

`sshd_config`를 grep하지 말고 `sshd -T`로 **실제 적용되는 설정값**을 확인하는 것이 중요합니다. `Include`로 불러오는 drop-in 파일이 메인 설정을 덮어쓰는 경우가 흔하기 때문입니다.

Container Image는 다음과 같이 일괄 점검합니다.

```bash
for img in $(docker images --format '{{.Repository}}:{{.Tag}}' | grep -v '<none>'); do
  if docker run --rm --entrypoint sh "$img" -c \
      'test -f /etc/alpine-release && apk info -e openssh-server' >/dev/null 2>&1; then
    echo "CANDIDATE: $img"
  fi
done
```

운영 환경에서는 Trivy나 Grype 같은 SBOM 기반 Scanner로 CVE ID를 지정해 검색하는 편이 더 확실합니다. 다만 취약점 Database에 새 CVE가 반영되기까지 시간이 걸리므로, 반영 전까지는 위와 같은 직접 점검을 병행합니다.

## 대응 절차

### 1. Package 업데이트 후 sshd 재시작

```bash
apk update
apk upgrade openssh-server openssh
rc-service sshd restart   # OpenRC 기준
```

Alpine advisory에서도 강조하듯이, **Package를 업데이트해도 실행 중인 sshd는 이전 binary 그대로**입니다. 반드시 재시작하고, Process 시작 시각이 업데이트 이후인지 확인합니다.

```bash
ps -o pid,lstart,args -C sshd 2>/dev/null || ps -ef | grep '[s]shd'
```

### 2. 바로 패치할 수 없는 경우

비밀번호 인증 자체를 끄면 이번 공격 경로는 막힙니다.

```text
# /etc/ssh/sshd_config.d/00-disable-password.conf
PasswordAuthentication no
KbdInteractiveAuthentication no
```

파일명을 `00-`으로 시작하는 데는 이유가 있습니다. sshd는 대부분의 키워드에서 **처음 나온 값을 우선**하기 때문에, 뒤쪽 파일에 `no`를 써도 앞에 `yes`가 있으면 적용되지 않습니다. `sshd -t`로 문법을 검증하고, `sshd -T`로 실제 값이 `no`인지 확인한 뒤 reload합니다.

### 3. Container는 내부 패치가 아니라 재빌드

Container 안에서 `apk upgrade`를 실행하지 말고, Base Image를 갱신해 재빌드하고 다시 Deploy합니다.

```dockerfile
FROM alpine:3.24
RUN apk add --no-cache --upgrade openssh-server
COPY sshd_config.d/ /etc/ssh/sshd_config.d/
```

`--upgrade`를 붙이면 Cache된 오래된 Base layer를 쓰더라도 Package는 최신 버전으로 맞춰집니다.

## 로그 확인

이 취약점의 흔적은 "비밀번호가 없는 계정에 대한 password 인증 성공"입니다. 비밀번호 로그인을 전혀 운영하지 않는 환경이라면 아래 결과가 나오는 것 자체가 이상 신호입니다.

```bash
grep -E 'Accepted password for' /var/log/messages /var/log/auth.log 2>/dev/null
```

해당 기록이 있다면 그 Host는 침해된 것으로 간주하고, 보관된 Key를 교체한 뒤 그 자리에서 정리하기보다 재구축하는 쪽을 검토하십시오.

## webhani의 시각

이번 건에서 다시 확인해야 할 것은 "Key 인증만 쓰니까 괜찮다"는 전제가 **설정이 아니라 운영 습관에 대한 믿음**일 뿐인 경우가 많다는 점입니다. 아무도 비밀번호로 로그인하지 않는데 `PasswordAuthentication`은 기본값 `yes`로 남아 있는 Host를 저희는 자주 발견합니다.

webhani가 권장하는 방침은 다음과 같습니다.

- SSH를 받는 모든 Host에 `PasswordAuthentication no`를 명시합니다. 쓰지 않는 기능은 닫아 둡니다
- 설정 파일을 믿기보다 `sshd -T` 출력을 CI나 구성 관리 도구에서 검증합니다
- Bastion은 가능하면 SSM Session Manager나 IAP처럼 SSH Port를 외부에 열지 않는 방식으로 옮깁니다
- sshd가 들어 있는 Container Image는 정말 필요한지 다시 검토합니다

패치는 반나절이면 끝납니다. 하지만 SSH 진입점이 어디에 몇 개 있는지 파악해 두어야 다음 advisory도 반나절 안에 대응할 수 있습니다.
