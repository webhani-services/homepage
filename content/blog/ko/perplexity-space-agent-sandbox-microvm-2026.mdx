Perplexity는 10월 15일 SPACE(Sandboxed Platform for Agentic Code Execution)를 오픈소스로 공개했습니다. 자사 Computer Agent의 모든 Session을 구동하는 Sandbox 계층이라고 하며, 라이선스는 Apache 2.0, 구현 언어는 Rust이고 E2B Python SDK와 호환되는 Wrapper도 포함합니다. 아래 수치는 언론 보도와 Perplexity의 발표에 근거한 것이므로 Vendor가 공개한 값으로 보셔야 합니다.

수치보다 주목할 부분은 설계입니다. "모델이 작성한 코드는 어디에서 실행해야 하는가"라는, 지금 많은 팀이 마주한 질문에 대해 실서비스 수준의 답을 보여 주기 때문입니다.

## 핵심 설계

보도에 따르면 SPACE의 설계는 네 가지로 요약됩니다.

1. **Task당 microVM 하나**: 각 Agent Task에 전용 Firecracker microVM을 할당하고, Task가 끝나면 VM을 폐기합니다.
2. **Credential은 Sandbox 밖에 둠**: Secret을 Sandbox 안에 두지 않습니다. Sandbox는 작업을 "요청"만 하고, 실제 실행은 바깥의 신뢰할 수 있는 계층이 수행합니다.
3. **Egress는 Node 단에서 제어**: 외부로 나가는 Traffic을 Guest 설정이 아닌 Host에서 제한하므로, VM 안의 코드가 스스로 규칙을 완화할 수 없습니다.
4. **상태를 명시적으로 관리**: 일시 중지, 재개, Branch가 가능하며 Rolling Snapshot은 제한된 기간 동안만 보관합니다.

Perplexity는 Sandbox 생성 시간의 중앙값을 약 60ms로 보고했습니다. 정확한 값과 무관하게, 신뢰할 수 없는 코드를 견디는 격리가 더 이상 수 초의 시작 비용을 요구하지 않게 되었다는 점이 중요합니다.

## Container만으로 부족한 이유

Agent 코드를 일반 Docker Container에서 실행하는 팀이 많습니다. 자사의 신뢰할 수 있는 Service라면 합리적인 선택입니다. 하지만 신뢰할 수 없는 입력이 섞일 수 있는 Prompt로 생성된 코드에는 약한 선택입니다. Container는 Host의 Kernel을 공유하기 때문에, Kernel Bug나 Capability 설정 실수가 곧바로 Host 침해로 이어질 수 있습니다.

microVM은 Guest와 Host 사이에 Hypervisor 경계를 둡니다. Memory와 시작 시간 비용이 조금 늘어나는 대신, 잘못 생성된 Script의 영향 범위가 일회용 VM 하나로 제한됩니다.

이미 E2B나 Cloud Vendor의 Managed Sandbox를 사용 중이라면 이 경계는 확보된 것입니다. SPACE 공개의 의미는 추측이 아니라 프로덕션급 구현을 직접 읽어 볼 수 있게 되었다는 점입니다.

## 보안 검증 결과는 신중하게 읽어야 합니다

Perplexity의 적대적 Test 결과는 보도마다 수치가 다릅니다. 약 118회 시도에서 Escape가 없었다는 보도가 있는 반면, 108회 시도에서 9개 Model이 Host에 도달하지 못했지만 4개가 일부 Network 제한을 우회했다고 전하는 보도도 있습니다(Perplexity는 이를 수정하고 재검증했다고 밝혔습니다).

어느 쪽이 정확하든 두 가지 교훈이 있습니다.

- Host 경계는 유지되었지만 Model이 빈틈을 찾은 곳은 **Network Policy**였습니다. Egress 규칙은 Sandbox에서 미묘한 오류가 가장 잘 생기는 부분입니다.
- 고성능 Model을 이용한 Red-teaming은 이제 실용적인 기법입니다. 직접 Sandbox를 만든다면 Model에게 공격을 시키고, 우회된 지점을 Bug로 관리하는 것이 좋습니다.

## Perplexity 규모가 아니어도 적용할 수 있는 것

대부분의 고객사는 하루 수백만 개의 Sandbox를 운영하지 않습니다. 그래도 설계 원칙은 작은 구성에 적용할 수 있습니다.

**Credential을 실행 환경 밖에 둡니다.** 비용 대비 효과가 가장 큰 조치입니다. API Key를 Sandbox에 주입하는 대신, 검증 로직이 있는 좁은 Proxy를 통해 호출하게 합니다.

```ts
// Host 측: Agent는 작업을 요청하고, Secret은 Host가 보관한다
type ToolCall = { name: "create_issue"; args: { title: string; body: string } };

async function handleToolCall(call: ToolCall) {
  switch (call.name) {
    case "create_issue":
      // 실제 API를 호출하기 전에 Schema로 인자를 검증한다
      return githubClient.issues.create({
        owner: "example-org",
        repo: "example-repo",
        title: call.args.title.slice(0, 200),
        body: call.args.body,
      });
    default:
      throw new Error(`Tool not allowed: ${call.name}`);
  }
}
```

Sandbox는 Token을 전혀 보지 못합니다. 생성된 코드가 Prompt Injection으로 탈취되더라도, 할 수 있는 일은 허용된 작업을 검증된 인자로 요청하는 것뿐입니다.

**Egress는 기본 차단으로 시작합니다.** 외부 Network 접근이 없는 상태에서 시작해, 허용 Host를 검토를 거친 목록으로 추가합니다. 강제는 Guest 바깥에서 수행합니다.

**Sandbox를 일회용으로 만듭니다.** Task 또는 Session마다 생성하고 종료 후 폐기합니다. 수명이 긴 Sandbox를 여러 사용자나 Task가 재사용하면 상태 유출이 Tenant 간 문제가 됩니다.

**무엇을 남길지 정합니다.** Snapshot은 오래 실행되는 Agent에 편리하지만, 보존된 Snapshot은 모두 분류·만료·보호가 필요한 데이터입니다. 보존 기간은 의도적으로 정하십시오.

## 주의할 점

- **운영 부담**: Firecracker를 직접 운영하려면 KVM을 지원하는 Host, Image 관리, Network 설계가 필요합니다. 소규모 팀에는 Managed Service가 보통 더 경제적입니다.
- **성숙도**: SPACE는 공개된 지 며칠밖에 되지 않았습니다. 도입 전에 Issue Tracker와 Security Policy를 확인하고, 거친 부분이 있을 것을 전제로 하십시오.
- **Sandbox는 방어 계층 중 하나입니다**: 피해를 제한할 뿐, 허용된 권한 안에서 Agent가 유해한 행동을 하는 것까지 막지는 못합니다. Tool 권한을 좁히고, 되돌릴 수 없는 작업에는 사람의 승인을 두십시오.

## 정리

- Model이 생성한 코드는 신뢰할 수 없는 것으로 취급하고, 위험도에 따라 Hypervisor 경계 안에서 실행합니다.
- Secret은 Sandbox 밖에 두고, 검증이 있는 Tool 계층을 통해서만 접근하게 합니다.
- Network Policy는 Host에서 기본 차단으로 강제하고 적대적으로 Test합니다.
- 대부분의 팀은 Managed Sandbox를 먼저 도입하고, SPACE는 좋은 구현의 참고 자료로 읽는 것이 현실적입니다.
