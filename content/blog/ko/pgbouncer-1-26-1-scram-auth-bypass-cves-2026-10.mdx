PgBouncer 1.26.1이 2026년 10월 14일에 릴리스되어 CVE 3건이 수정되었습니다. 그중 하나가 인증 우회이므로, PostgreSQL 앞단에 PgBouncer를 두고 있다면 일반적인 Patch Release로 취급하기 어렵습니다. 아래 내용은 PostgreSQL 프로젝트의 공지와 Debian Security Tracker를 근거로 합니다. 취합 사이트마다 CVE 번호 표기가 달랐으므로, 실제 적용 시에는 사용 중인 Vendor의 Advisory와 대조하시기 바랍니다.

## 세 가지 취약점

**CVE-2026-107350: 인증 우회.** 한 SCRAM 사용자의 Password를 아는 Client가 admin과 Backend superuser 계정을 포함한 다른 SCRAM 사용자로 로그인할 수 있습니다. 대상 Database가 존재하지 않을 때 SCRAM 인증 중 들어오는 두 번째 startup 메시지의 처리 방식에 문제가 있습니다. 가장 먼저 대응해야 할 항목입니다.

**CVE-2026-107349: 인증 전 DoS.** startup options에 빈 옵션 이름이 있으면 무한 루프가 발생합니다. `ignore_startup_parameters`가 설정되어 있고 `options`를 포함하지 않는 경우의 1.20.0~1.26.0이 대상입니다.

**CVE-2026-107348: 인증 전 DoS.** Packet Buffer 확장 로직의 Integer Overflow로 무한 루프가 발생할 수 있습니다. `max_packet_size`를 기본값보다 크게 올린 경우에만 해당합니다.

직전 릴리스인 1.26.0에서도 다른 CVE 3건이 수정되었으므로, 1.26.0에 머무는 것도 안전하지 않습니다.

## 누가 영향을 받는가

DoS 2건은 설정에 좌우됩니다. 우려가 큰 쪽은 인증 우회입니다. 전제 조건이 낮기 때문입니다. Pooler에서 SCRAM 사용자 한 명의 유효한 인증 정보만 있으면 됩니다. Tenant마다 DB Role이 있거나 여러 Application Service가 PgBouncer 하나를 공유하는 구성에서는 "유효한 사용자가 한 명 있다"는 조건이 쉽게 충족됩니다. 영향 범위는 공격자가 도달한 계정의 권한이며, Pooler를 통해 접근 가능하다면 superuser도 포함됩니다.

먼저 실제로 무엇이 동작 중인지 확인합니다.

```bash
# Admin Console에서 Version 확인
psql -h pgbouncer.internal -p 6432 -U pgbouncer pgbouncer -c 'SHOW VERSION;'

# DoS와 관련된 설정 확인
psql -h pgbouncer.internal -p 6432 -U pgbouncer pgbouncer -c 'SHOW CONFIG;' \
  | grep -E 'ignore_startup_parameters|max_packet_size|auth_type'
```

Container Image와 배포판 Package도 확인하십시오. Debian은 1.26.1-1을 unstable에서 수정된 버전으로 표시하고 이전 Package는 여전히 취약한 것으로 분류합니다. Package Manager가 따라오지 못했다면 "정기적으로 업데이트한다"고 해도 노출이 남습니다.

## 미리 알아 둘 동작 변경

1.26.1에서는 `ignore_startup_parameters`와 추적 대상 Parameter의 우선순위도 바뀌어 전자가 우선합니다. 1.26.0에서는 `search_path`가 추적되었지만, 이번 버전부터는 `ignore_startup_parameters`에 나열하면 1.25처럼 무시됩니다.

```ini
; pgbouncer.ini
[pgbouncer]
ignore_startup_parameters = extra_float_digits,search_path
```

Application이 Connection Option으로 `search_path`(예: Tenant별 Schema)를 지정한다면 중요합니다. PgBouncer가 추적하게 할지, 무시하게 할지 의도적으로 정하고, 실제 Client Library 설정으로 Staging에서 검증하십시오. 보안 Rollout 도중에 차이를 발견하는 상황은 피하는 편이 좋습니다.

## Patch 외에 노출을 줄이는 방법

수정은 업그레이드로 이루어지지만, 이런 유형의 버그로 인한 피해를 줄이는 방법도 있습니다.

1. **PgBouncer를 넓게 공개하지 않습니다.** Application Subnet에서만 접근 가능하도록 하고 Security Group과 Network Policy에 반영하여, "인증 전" 버그에 인터넷에서 도달하지 못하게 합니다.
2. **superuser를 Pooler에 통과시키지 않습니다.** `auth_query`와 `auth_user`는 신중하게 다루고, superuser Role이 PgBouncer를 통해 인증되지 않도록 합니다. 관리 작업은 Bastion에서 PostgreSQL에 직접 접속하고 `pg_hba.conf`로 제한합니다.
3. **신뢰 경계별로 Pooler를 분리합니다.** 모든 Tenant와 Service가 Pooler 하나를 공유하면 인증 버그의 영향 범위가 커집니다. 환경이나 민감도에 따라 나누는 비용은 크지 않습니다.
4. **비정상 로그인을 감지합니다.** 제시된 사용자와 접근한 Database를 대조합니다. Application이 쓰지 않는 Role로의 로그인은 알림 대상으로 삼을 만합니다.
5. **`max_packet_size`를 점검합니다.** 큰 Payload 때문에 올렸다면 낮추거나, Patch 전까지 위험을 감수한다는 판단이 필요합니다.

## 업그레이드 진행 방법

PgBouncer는 Online Restart를 지원하지만, Connection Drain에는 주의가 필요합니다.

```bash
# 새 Process를 시작하고 Listening Socket을 인계받음
pgbouncer -R /etc/pgbouncer/pgbouncer.ini
```

Kubernetes에서는 Pooler Port에 대한 Readiness Probe를 둔 일반적인 Rolling Update로 대체로 충분합니다. 단, Client가 연결 오류 시 재시도한다는 전제가 필요합니다. 먼저 Staging에서 `search_path` 동작을 확인한 뒤 Production을 소규모 단위로 진행하십시오.

## 정리

- 1.26.1(또는 배포판의 수정된 Package)로 업그레이드하십시오. 1.26.0은 충분하지 않습니다.
- SCRAM 우회는 유효한 사용자 한 명만으로 성립하므로 공유 Pooler의 우선순위를 높게 잡으십시오.
- `ignore_startup_parameters`를 확인하고 Rollout 전에 `search_path` 처리를 테스트하십시오.
- Pooler로의 Network 접근을 제한하고 superuser 접근은 통과시키지 마십시오.
- CVE 참조가 출처마다 달랐으므로 사용 중인 Vendor의 Advisory로 확인하십시오.
