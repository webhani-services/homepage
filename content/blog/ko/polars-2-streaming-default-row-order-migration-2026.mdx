Polars 2.0에서는 `LazyFrame` Query를 실행하는 Engine이 바뀌어, Streaming Engine이 기본값이 되었습니다. Polars 팀의 발표는 전체적으로 몇 배 빨라질 것으로 기대한다고 밝히고 있습니다. 초기 보도에 따르면 정식 Release는 10월 6일에 공개되었고, out-of-core(디스크 Spill) 기능도 초기 수준으로 포함되었다고 합니다. Release 날짜는 제3자 기사 한 곳에서만 확인했으므로, 계획에 반영하기 전에 pola.rs에서 확인하시기 바랍니다.

헤드라인은 속도이지만, 실제로 문제가 되기 쉬운 부분은 다른 곳에 있습니다. **Streaming Engine은 일부 연산에서 행 순서를 보장하지 않습니다.** 보도에서는 join, group_by, unpivot이 언급됩니다. 기존 in-memory Engine의 순서에 우연히 의존하던 코드는 같은 행을 다른 순서로 반환할 수 있습니다.

## 행 순서가 문제가 되는 이유

대부분의 Pipeline은 순서에 의존하려는 의도가 없습니다. 우연히 의존하고 있을 뿐입니다.

- 그룹 집계 결과의 앞 N행을 출력하고, 후속 처리가 이를 상위 N건이라고 가정합니다.
- Test에서 `assert_frame_equal`을 정렬 없이 사용합니다.
- join 결과를 CSV로 저장하는데, diff 기반 검사가 매 실행마다 "변경됨"으로 판정합니다.
- 정렬하지 않은 결과에 `.head()`를 "샘플"처럼 사용합니다.

이전 Engine에서는 우연히 안정적이었습니다. 새 Engine에서는 실행마다, 또는 Version마다 달라질 수 있습니다. 오류는 나지 않고 값의 위치만 바뀝니다.

## 순서를 명시합니다

해결 방법은 비용이 적고 코드도 더 정직해집니다. 순서가 필요한 곳에서 정렬하십시오.

```python
import polars as pl

orders = pl.scan_parquet("orders/*.parquet")
customers = pl.scan_parquet("customers.parquet")

result = (
    orders
    .join(customers, on="customer_id", how="left")
    .group_by("region")
    .agg(pl.col("amount").sum().alias("revenue"))
    .sort("revenue", descending=True)   # 우연이 아니라 명시적으로
    .collect()
)
```

join이나 group_by에서 입력 순서를 유지해야 한다면 `maintain_order` 인자를 사용합니다. 메서드마다 허용하는 값이 다르므로 2.0 API Reference에서 확인하십시오.

```python
grouped = orders.group_by("customer_id", maintain_order=True).agg(
    pl.col("amount").sum()
)
```

`maintain_order`는 Streaming의 속도 향상을 일부 희생합니다. 순서가 계약의 일부인 곳에만 사용하고, 그 밖에는 업무 Key로 정렬하는 것이 기본입니다.

## 마이그레이션 중 Opt-out

시간이 필요하다면 `collect` 시점에 기존 in-memory Engine을 명시적으로 지정할 수 있습니다. 최근 Polars에서는 대략 다음과 같은 형태입니다.

```python
df = lazy_query.collect(engine="in-memory")
```

Engine 지정 방식은 Minor Version마다 바뀌어 왔고, 기존 Engine을 기본값으로 되돌리는 engine affinity 설정을 언급한 기사도 있습니다. 현재 형태는 2.0 Documentation에서 확인하십시오. 이것은 목적지가 아니라 다리일 뿐이며, 실질적으로 in-memory Engine은 점차 물러나는 방향이라고 보는 편이 안전합니다.

## 마이그레이션 체크리스트

1. **Branch에서 단독으로 Upgrade합니다.** 2.0만 올려서 전체 Test Suite를 실행합니다.
2. **순서에 민감한 Test를 찾습니다.** `assert_frame_equal`을 grep하여, 순서가 사양이 아닌 곳에는 `check_row_order=False`를, 사양인 곳에는 명시적 정렬을 추가합니다.
3. **신·구 출력을 비교합니다.** 운영 Query를 샘플 Data로 두 Engine에서 실행하고 정렬한 결과를 diff합니다. 정렬 후에도 차이가 있다면 순서 문제가 아닌 실제 Bug입니다.
4. **`head()`, `first()`, `unique()`, `limit`을 점검합니다.** 정렬되지 않은 Data가 "답"으로 노출되기 쉬운 전형적인 위치입니다.
5. **자사 Workload로 다시 측정합니다.** 전체적인 속도 주장이 개별 Pipeline에 그대로 들어맞는 경우는 드뭅니다. 효과는 메모리를 넘어서는 Data에 대한 Scan, Filter, 집계에서 가장 큽니다.
6. **Spill 활성화 시 메모리를 모니터링합니다.** out-of-core 지원은 초기 단계로 설명됩니다. 운영에서 의존하기 전에 RAM보다 큰 Dataset으로 테스트하십시오.

Test에 바로 넣을 수 있는 간단한 동등성 검사입니다.

```python
def assert_same_rows(a: pl.DataFrame, b: pl.DataFrame, key: list[str]) -> None:
    a_sorted = a.sort(key)
    b_sorted = b.sort(key)
    assert a_sorted.equals(b_sorted), "행 순서 외에도 결과가 다릅니다"
```

## webhani의 시각

좋은 기본값이라고 생각합니다. Streaming 실행은 대부분의 팀이 실제로 다루는 Data 규모에 잘 맞으며, 빠른 경로를 기본으로 삼는 것은 합리적인 판단입니다. 그 대가로 "Engine이 편한 순서로 행을 돌려줄 것"이라는 숨은 가정이 드러났습니다. 이는 오히려 반길 일입니다. 명시적으로 정렬하는 Pipeline은 이해하기 쉽고, 테스트하기 쉬우며, Engine이 바뀌어도 이식할 수 있습니다.

Polars로 Data Pipeline을 운영 중이라면, 단순한 Dependency 업데이트가 아니라 출력 diff 단계를 포함한 작은 프로젝트로 Upgrade를 계획하십시오. 마이그레이션 검토가 필요하시면 webhani가 도와드리겠습니다.
