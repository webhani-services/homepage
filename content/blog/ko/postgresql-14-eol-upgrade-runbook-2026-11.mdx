PostgreSQL 14는 11월 12일 예정된 마지막 Minor Release를 끝으로 지원이 종료됩니다. PostgreSQL Project는 5년 지원 정책을 따르고 있으며, 5월 Update 공지에서도 이 날짜가 명시되었습니다. 12일 이후 발견되는 취약점은 14 계열에서는 Community가 수정하지 않습니다.

연장 지원을 제공하는 HeroDevs의 집계에 따르면 올해 공개된 PostgreSQL CVE는 이미 44건입니다. 집계 방식에 따라 숫자는 달라질 수 있지만, "EOL이 지나도 잘 돌아가니 당분간 그대로 두자"는 판단이 예전보다 위험해진 것은 분명합니다. 이 글에서는 남은 며칠 동안 해야 할 일과 그 이후의 Migration 진행 방법을 정리합니다.

## 먼저 현황을 파악합니다

첫 작업은 14가 어디에 남아 있는지 확인하는 것입니다. Production뿐 아니라 Staging, 분석용 Replica, CI의 Service Container, 개발자의 docker-compose까지 포함합니다.

```sql
-- 각 Instance에서 실행
SELECT version();

-- Migration에 영향을 주는 Extension 확인
SELECT extname, extversion FROM pg_extension ORDER BY extname;

-- Database별 크기 (Migration 방식 판단용)
SELECT datname, pg_size_pretty(pg_database_size(datname))
FROM pg_database
WHERE datistemplate = false
ORDER BY pg_database_size(datname) DESC;
```

Repository 쪽에서는 Image Tag와 Engine Version이 고정된 곳을 검색하면 누락을 줄일 수 있습니다.

```bash
grep -rnE "postgres(ql)?:14|POSTGRES_VERSION=14|engine_version.*\"14" \
  --include="*.yml" --include="*.yaml" --include="*.tf" --include="Dockerfile*" .
```

## 이전 대상은 18을 기본으로

후보는 18과 19입니다. 저희는 대부분의 경우 **18** 을 권장합니다. Release 후 1년이 지나 주요 Extension과 Managed Service 지원이 충분히 갖춰져 있기 때문입니다. 19는 신규 Project이거나, 사용하는 Extension의 지원 여부를 모두 확인한 환경에서 검토하면 됩니다.

14에서 18로 옮길 때 주의할 변경 사항입니다.

- **initdb에서 Data Checksum이 기본 활성화.** 14 Cluster를 Checksum 없이 만들었다면 `pg_upgrade`가 그대로는 진행되지 않습니다. 새 Cluster를 `--no-data-checksums`로 만들거나, 기존 Cluster에서 먼저 Checksum을 활성화합니다.
- **MD5 Password 인증 Deprecated.** 18에서는 MD5 사용 시 경고가 출력됩니다. 별도 작업으로 미루지 말고 Migration과 함께 `scram-sha-256`으로 전환하는 것이 효율적입니다.
- **pg_upgrade가 통계 정보를 유지.** 18부터 Upgrade 후에도 Planner 통계가 보존되어, Migration 직후의 성능 저하가 줄어듭니다.

## Migration 방식 선택

| 방식 | Downtime | 적합한 경우 |
| --- | --- | --- |
| `pg_dump` / `pg_restore` | 김 | 수십 GB 이하, Maintenance 시간 확보 가능 |
| `pg_upgrade --link` | 수 분 | 같은 Host에서 In-place Upgrade |
| 논리 Replication | 전환 시점만 | 대규모 DB, Downtime을 거의 허용할 수 없음 |

`pg_upgrade`를 사용할 때는 반드시 `--check`부터 실행합니다.

```bash
/usr/lib/postgresql/18/bin/pg_upgrade \
  --old-bindir=/usr/lib/postgresql/14/bin \
  --new-bindir=/usr/lib/postgresql/18/bin \
  --old-datadir=/var/lib/postgresql/14/main \
  --new-datadir=/var/lib/postgresql/18/main \
  --link --check
```

Downtime을 최소화하려면 논리 Replication을 사용합니다. 14에서 Publication을 만들고 18에서 Subscribe합니다.

```sql
-- 기존 Cluster (14)
CREATE PUBLICATION upgrade_pub FOR ALL TABLES;

-- 새 Cluster (18): 먼저 pg_dump --schema-only로 Schema를 생성해 둡니다
CREATE SUBSCRIPTION upgrade_sub
  CONNECTION 'host=old-db port=5432 dbname=app user=replicator'
  PUBLICATION upgrade_pub;
```

논리 Replication은 Sequence 값을 복제하지 않는다는 점에 주의해야 합니다. 전환 직전에 기존 Cluster의 값을 새 Cluster에 반영하는 단계를 Runbook에 넣어 둡니다.

```sql
-- 기존 Cluster에서 새 Cluster용 setval 문을 생성
SELECT format('SELECT setval(%L, %s, true);',
              schemaname || '.' || sequencename, last_value)
FROM pg_sequences
WHERE last_value IS NOT NULL;
```

전환 후에는 `vacuumdb --all --analyze-in-stages`를 실행하고, 주요 Query의 실행 계획을 Migration 전과 비교합니다.

## Managed Service를 쓰는 경우

Amazon RDS / Aurora, Cloud SQL, Azure Database for PostgreSQL은 EOL이 된 Major Version을 유료 연장 지원에 자동으로 등록합니다. 계속 동작은 하지만 vCPU 단위 추가 요금이 붙고, Migration을 미룰수록 비용이 늘어납니다.

AWS는 11월 3일자로 Community CVE 수정을 Backport한 Aurora PostgreSQL 새 Minor Version을 공개했습니다. 14 계열을 당분간 계속 써야 한다면 최소한 Minor Version은 최신으로 유지하시기 바랍니다.

Managed Service에서 Major Upgrade를 할 때는 Blue/Green Deployment 기능을 활용하면 Rollback이 훨씬 쉬워집니다. Production에서 바로 실행하지 말고 Snapshot으로 복원한 환경에서 먼저 Rehearsal합니다.

## webhani의 견해

Database Major Upgrade는 Application Library Update와 달리 뒤로 미루기 쉬운 작업입니다. 하지만 EOL이 지난 Database는 새 취약점이 발견되어도 스스로 고칠 수 없는 상태가 됩니다.

앞으로 한 달 동안의 진행 계획을 정리합니다.

1. **이번 주:** 14가 동작 중인 환경을 모두 찾아 최신 Minor Version으로 Update합니다.
2. **이번 달:** Extension 지원 여부와 Migration 방식을 정하고 Staging에서 Rehearsal합니다.
3. **연내:** Production Migration을 마치고 Managed Service의 연장 지원 과금을 멈춥니다.
4. **지속:** 다음 EOL(PostgreSQL 15, 2027년 11월)을 Calendar에 등록하고 1년 전부터 계획합니다.

PostgreSQL의 EOL은 매년 같은 시기에 찾아옵니다. 이번 Migration에서 만든 Runbook을 남겨 두면 내년 15 계열 Migration은 훨씬 수월해집니다.
