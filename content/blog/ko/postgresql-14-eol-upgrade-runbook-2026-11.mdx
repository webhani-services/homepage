PostgreSQL 버전 정책 페이지에 따르면 PostgreSQL 14의 마지막 Release는 **2026년 11월 12일**입니다. 이후로는 14 라인에 대한 Bug 수정이나 Security 수정이 Community에서 나오지 않습니다. 현재 Minor 버전은 14.24이고 첫 Release가 2021년 9월이었으니, 예정대로 5년간의 지원이 끝나는 것입니다.

아직 14가 어딘가에서 돌고 있다고 해서 11월 13일에 당장 문제가 생기지는 않습니다. 다만 앞으로 발견되는 모든 CVE는 "Patch할 수 없는 취약점"이 됩니다. 이 글에서는 webhani가 이런 업그레이드에 사용하는 Runbook을 소개합니다.

## 1단계: 14.x Instance 모두 찾기

눈에 띄는 Production Database만 있는 경우는 드뭅니다. Container, CI, Local 개발 환경까지 확인합니다.

```bash
# Container Image와 compose 파일
grep -RnE "postgres(ql)?:14|postgres:14" --include="*.yml" --include="*.yaml" --include="Dockerfile*" .

# CI Service Container
grep -RnE "image:\s*postgres" .github/workflows/ 2>/dev/null

# Terraform / IaC
grep -RnE "engine_version\s*=\s*\"14" --include="*.tf" .
```

운영 중인 Server에서는 README에 적힌 버전이 아니라 실제 버전을 확인합니다.

```sql
SELECT version();
SHOW server_version_num;  -- 14xxxx이면 14.x
```

Amazon RDS나 Aurora 같은 Managed Service는 Community EOL 이후에도 유료 Extended Support를 제공하는 경우가 일반적입니다. 시간을 벌 수는 있지만 이는 비용 항목이지 계획이 아닙니다. 사용 중인 Service의 기한과 요금을 확인하고, 그것을 마감일로 다루시기 바랍니다.

## 2단계: 대상 버전 정하기

현재 지원되는 버전은 15부터 18까지입니다. Extension이나 Managed Service 제약이 없다면 **18**(현재 18.6, 2030년 11월까지 지원)로 바로 올리는 것을 권장합니다. 14에서 15로 올리면 지원 기간이 1년밖에 늘어나지 않습니다.

PostgreSQL 19는 Release Candidate 단계입니다. Production 업그레이드 대상을 19.0으로 잡기보다는, Minor Release가 몇 번 나와 안정될 때까지 기다리는 편이 안전합니다.

14에서 18로 올릴 때 특히 알아 둘 점입니다.

- **18에서는 initdb 시 Data Checksum이 기본으로 켜져 있습니다.** `pg_upgrade`는 기존 Cluster와 새 Cluster의 설정이 같아야 합니다. 14 Cluster를 Checksum 없이 만들었다면 새 Cluster를 `--no-data-checksums`로 초기화하거나, 미리 기존 Cluster에서 `pg_checksums`로(중지 상태에서) Checksum을 켭니다.
- **MD5 Password 인증은 Deprecated**되어 경고가 출력됩니다. 이번 기회에 SCRAM-SHA-256으로 옮깁니다.
- **`pg_upgrade`가 Planner 통계를 이어받습니다**(Extended Statistics 제외). 업그레이드 직후 Query가 느려지는 기간이 짧아집니다.

15, 16, 17, 18의 Release Note에는 각각 "Incompatibilities" 섹션이 있습니다. Major 버전 네 개를 건너뛴다면 네 개 모두 읽어야 합니다.

## 3단계: 무엇보다 먼저 Extension 확인

업그레이드가 실패하는 원인은 대부분 Extension입니다.

```sql
SELECT extname, extversion FROM pg_extension ORDER BY extname;
```

각 Extension에 대해 대상 버전용 Build가 있는지 확인합니다. PostGIS, pgvector, TimescaleDB, `pg_partman` 등은 `pg_upgrade` 전에 새 Cluster 쪽에 대응 Package를 설치해 두어야 합니다.

## 4a단계: pg_upgrade로 In-place 업그레이드

Self-managed Server라면 대부분 `pg_upgrade`가 가장 간단합니다. 반드시 Check Mode부터 실행합니다.

```bash
# 설정을 맞춰 새 Cluster 초기화
/usr/lib/postgresql/18/bin/initdb -D /var/lib/postgresql/18/main \
  --no-data-checksums --encoding=UTF8 --locale=C.UTF-8

# Dry Run: 아무것도 바꾸지 않고 비호환 항목만 보고
/usr/lib/postgresql/18/bin/pg_upgrade \
  --old-bindir=/usr/lib/postgresql/14/bin \
  --new-bindir=/usr/lib/postgresql/18/bin \
  --old-datadir=/var/lib/postgresql/14/main \
  --new-datadir=/var/lib/postgresql/18/main \
  --check
```

`--check`가 깨끗하게 통과하면 Backup을 받고 기존 Server를 중지한 뒤, `--check` 없이 같은 명령을 실행합니다. `--link`를 붙이면 복사 대신 Hard Link를 쓰기 때문에 큰 Database도 빠르게 끝납니다. 다만 새 Cluster를 한 번 기동하면 기존 Cluster는 안전하게 기동할 수 없습니다. 사용하기 전에 복원까지 검증한 Backup을 준비해 두십시오.

업그레이드 후에는 다음을 실행합니다.

```bash
# 이어받지 못한 통계 정보 보완
vacuumdb --all --analyze-in-stages --missing-stats-only
```

## 4b단계: Logical Replication으로 거의 무중단 이전

Downtime을 초 단위로 줄여야 한다면, 새 버전을 Logical Replication Subscriber로 구성하고 따라잡은 시점에 Application 접속 대상을 전환합니다.

```sql
-- 14.x(Publisher) 쪽
CREATE PUBLICATION upgrade_pub FOR ALL TABLES;

-- 18.x(Subscriber) 쪽. 먼저 pg_dump --schema-only로 Schema를 생성해 둠
CREATE SUBSCRIPTION upgrade_sub
  CONNECTION 'host=old-db dbname=app user=replicator'
  PUBLICATION upgrade_pub;
```

한계도 알아 두어야 합니다. Logical Replication은 Sequence와 DDL을 복제하지 않습니다. 전환 전에 쓰기를 멈추고 `setval`로 Sequence 값을 맞추며, 이전 기간 동안에는 Schema 변경을 동결합니다. Primary Key가 없는 Table에서 UPDATE와 DELETE를 복제하려면 `REPLICA IDENTITY` 설정이 필요합니다.

## 5단계: Container와 CI

compose 파일의 `postgres:14`를 `postgres:18`로 바꾼다고 Data가 업그레이드되지는 않습니다. 새 Major 버전은 기존 Data Directory로 기동하지 못합니다. Local 개발 환경이라면 Volume을 새로 만들고 Seed를 다시 넣는 것이 가장 간단합니다. 또한 공식 Docker Image는 18부터 기본 Data Directory 구성이 바뀌었으므로, 기존 Volume Mount 경로를 그대로 쓰기 전에 Image 문서를 확인하십시오.

CI Service Container도 함께 갱신해서 Production과 같은 버전으로 Test가 돌도록 합니다.

## 정리

- PostgreSQL 14의 마지막 Community 수정은 2026년 11월 12일입니다.
- Docker, CI, IaC까지 포함해 모든 14.x Instance를 찾습니다.
- 특별한 제약이 없다면 18을 대상으로 하고, 건너뛰는 Major 버전의 비호환 항목을 모두 확인합니다.
- Extension을 먼저 확인하고, `pg_upgrade --check`를 실행하고, 검증된 Backup을 준비합니다.
- Downtime을 최소화해야 한다면 Logical Replication을 쓰고, Sequence 동기화를 잊지 않습니다.
- Managed Service의 Extended Support는 해결책이 아니라 유료 유예 기간으로 봅니다.

webhani는 Self-managed PostgreSQL과 AWS RDS/Aurora 양쪽에서 Database 업그레이드를 지원하고 있으며, 실제 전환 전에 Production 규모의 복제본으로 리허설하는 과정까지 함께 진행합니다.
