## 하루에 5개 Version 동시 Release

2026년 8월 13일, PostgreSQL Project는 18.6·17.11·16.15·15.19·14.24를 동시에 Release하며 Security 취약점 28건과, 그동안 쌓인 Bug 보고 100건 이상을 함께 수정했습니다. 같은 날 PostgreSQL 19 Beta 3도 함께 나왔고, 공개된 Roadmap대로 2026년 9월 General Availability를 향해 순조롭게 진행 중입니다.

"왜 5개 Version이나 동시에?"라고 생각할 수 있지만, 이는 PostgreSQL Project의 구조 자체입니다. PostgreSQL은 항상 5개의 Major Version을 동시에 지원하며, 최신 Version에서 발견된 Security 수정 사항은 지원 대상인 모든 Branch에 Backport됩니다. 이는 Project가 내세우는 장기 지원 약속이 실제로 작동하고 있다는 증거이면서, 동시에 어떤 Major Version을 쓰고 있든 거의 모든 운영 중인 PostgreSQL 환경이 이번 대응을 필요로 한다는 뜻이기도 합니다.

## "Patch"가 실제로 의미하는 것

이번 것은 Major Version Upgrade가 아니라 Minor Version 갱신입니다. 이 차이는 운영 측면에서 매우 중요합니다. 같은 Major Version 안에서의 Minor Upgrade（예: 17.10 → 17.11）는 Binary 호환이 유지되므로 `pg_upgrade`도, Dump & Restore도, Data Directory 이관도 필요 없습니다. 새 Binary를 설치하고 Server를 재시작하면 끝입니다. Version 변경 자체로 Data File이 바뀌지는 않습니다.

그렇다고 위험이 전혀 없는 것은 아닙니다. 재시작은 재시작입니다. 다만 Major Upgrade에 비하면 작업 규모가 명확히 작고, Security 수정이 걸려 있는 이상 미루는 것을 합리화하기는 어렵습니다.

## 실무 Patch 적용 Checklist

1. **현재 Version을 확인하고 대상 Branch인지 확인한다**

   ```bash
   psql -c "SELECT version();"
   ```

2. **건수만 볼 게 아니라 해당 CVE 내용을 Release Note에서 확인한다**. 특정 Extension이나 인증 방식, Replication 구성을 쓸 때만 영향을 받는 수정도 있습니다. 실제로 해당되는지에 따라 대응의 시급성이 달라집니다.

3. **가능하면 실제 Production Traffic 패턴에 가까운 형태로 Staging 환경에서 검증한다**. 특히 PostGIS·pgvector·자체 C Native Extension 등을 쓴다면, 새 Minor Version에 맞춰 다시 Build해야 하는 경우가 있습니다.

4. **재시작 시점을 계획한다**. 단일 Instance라면 짧은 예정된 유지보수 시간이면 충분합니다. Replication 구성이라면 Replica에 먼저 Patch를 적용해 검증한 뒤 Failover하고, 이전 Primary에 Patch를 적용하는 방식으로 Downtime을 거의 0에 가깝게 만들 수 있습니다.

5. **Patch 적용 후에는 Version을 Infrastructure as Code에 반영한다**. 반영하지 않으면 다음 Terraform/Ansible 적용 시 모르는 사이에 수정 사항이 되돌아갈 수 있습니다.

RDS나 Aurora, Cloud SQL 같은 Managed Service를 쓴다면, 대부분 유지보수 시간에 새 Minor Version이 자동으로 적용되도록 되어 있는지 확인하거나, Policy상 명시적 승인이 필요하다면 수동으로 Trigger하는 방식으로 대응하면 됩니다.

## PG19 Beta 3이 보여주는 것

Security Patch 일괄 Release와 같은 날 PG19가 Beta 3에 도달했다는 사실은, Beta Cycle이 이미 상당히 진행됐고 2026년 9월 GA 목표가 순조롭다는 신호입니다. 지금이 바로 Sandbox 환경에서 PG19을 평가해 보기 시작할 시점입니다. 무언가를 실제로 옮기기 위해서가 아니라, 자체 Test Suite와 의존하는 Extension을 Beta에 대해 돌려보면서 GA 직후에 호환성 문제를 발견하는 상황을 피하기 위해서입니다. Beta는 지금 Test하고, Major Upgrade는 나중에 계획한다 — 이 두 가지를 스스로도, 이해관계자에게 설명할 때도 분명히 구분해 두는 것이 표준적인 접근입니다.

## webhani의 견해

Webhani는 PostgreSQL Minor Version Patch 적용을, 누군가 CVE 발표를 3주 늦게 알아채는 수동 대응이 아니라 정기적인 유지보수 자동화의 일부로 다루기를 권장합니다. Project의 Release Feed를 정기적으로 확인하고, Staging Test를 자동화하고, 사전 승인된 재시작 Window를 미리 마련해 두는 구조가 이상적입니다. EC2나 자체 운영 Kubernetes에서 PostgreSQL을 돌리는 고객이라면, 이번 Release가 이런 자동화를 갖추는 좋은 계기가 될 수 있습니다.

또한 PG19 전환을 고민 중인 고객이라면, 정식 Major Upgrade가 Roadmap에 오르기 전인 지금, 버릴 수 있는 환경에서 Beta에 대한 낮은 Risk의 평가를 시작할 것을 권장합니다. Beta가 Production에 바로 쓸 수 있는 수준이어서가 아니라, Extension이나 Query Plan의 회귀를 일찍 발견할수록 실제 Upgrade 시점의 비용이 작아지기 때문입니다.
