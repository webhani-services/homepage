Table Bloat는 PostgreSQL 운영에서 가장 눈에 띄지 않지만 가장 끈질긴 문제 중 하나입니다. UPDATE나 DELETE가 많은 Workload에서는 Dead Tuple이 남고, 일반 `VACUUM`은 공간을 재사용 가능하게 만들 뿐 OS에 돌려주는 일은 드뭅니다. 기존 해결책은 배타적 Lock을 잡는 `VACUUM FULL`, `CLUSTER`를 쓰거나, 서드파티 Extension인 `pg_repack`을 쓰는 것이었습니다.

PostgreSQL 19는 이 문제를 Core에서 다룹니다. PostgreSQL 19 Release Notes에 따르면, 새 `REPACK` Command는 이름이 혼동스러웠던 `VACUUM FULL`과 `CLUSTER`를 대체하며, `CONCURRENTLY` Option을 사용하면 읽기와 쓰기를 막지 않고 Table을 재구성할 수 있습니다.

먼저 현재 상태를 말씀드립니다. 작성 시점에 확인한 PostgreSQL 19 문서는 Beta 버전 기준이었고, 해당 페이지의 Release 날짜도 정해지지 않은 상태였습니다. GA 전에 사양이 바뀔 수 있습니다. 아래 내용은 운영 반영 일정으로 잡을 사안이 아니라 Test Cluster에서 평가할 대상으로 읽어 주십시오.

## Release Notes가 설명하는 내용

일상 운영에 관련된 변경은 세 가지입니다.

- **`REPACK`**: Table을 다시 쓰는 단일 Command이며, 정렬 기준으로 쓸 Index도 지정할 수 있습니다. 기존 Command는 호환성을 위해 남습니다. `CONCURRENTLY`는 Reader와 Writer의 장시간 Blocking을 피하며, 이를 지원하는 `max_repack_replication_slots` 설정이 추가됩니다.
- **Autovacuum 병렬화**: Autovacuum이 Table의 Index를 병렬 Worker로 Vacuum할 수 있습니다. `autovacuum_max_parallel_workers`와 Table 단위 `autovacuum_parallel_workers` Storage Parameter로 제어합니다. 또한 Vacuum이나 Analyze가 가장 필요한 Table을 우선하는 Scoring 방식도 도입됩니다.
- **`WAIT`**: Standby에서 지정한 LSN까지 반영될 때까지 Session이 기다릴 수 있습니다. Replica에서 Read-your-writes를 구현할 때 유용합니다.

## Core의 REPACK이 유용한 이유

`pg_repack`은 잘 동작하며 많은 팀이 문제없이 사용합니다. 다만 Core 기능이라면 없앨 수 있는 운영 비용이 있습니다.

- Extension이므로 모든 환경에서 사용 가능하고 Version이 맞아야 합니다. Managed Service 중에는 Extension 버전 반영이 늦는 곳도 있습니다.
- 재구성 중 변경을 포착하기 위해 Trigger와 Log Table을 사용하므로, 쓰기 Overhead와 고유한 장애 유형이 생깁니다.
- 마지막에 짧은 배타적 Lock이 필요하고, 새 복사본을 위한 추가 Disk도 필요합니다.

새 설정에서 짐작할 수 있듯, Replication Slot과 연결된 Core 구현이라면 서버 자체의 변경 포착과 더 잘 통합될 것으로 기대합니다. 다만 저희는 Benchmark를 하지 않았으므로 더 빠르다고 단정하지 않겠습니다. 확실한 장점은 구성 요소가 줄어든다는 점입니다.

## 지금 바로 실행할 수 있는 Bloat 점검

어떤 Version을 쓰든, 조치 전에 먼저 측정해야 합니다. `pgstattuple` Extension을 쓰면 정확한 상태를 볼 수 있습니다.

```sql
CREATE EXTENSION IF NOT EXISTS pgstattuple;

SELECT
  relname,
  pg_size_pretty(pg_relation_size(c.oid))          AS size,
  round(s.dead_tuple_percent::numeric, 1)           AS dead_pct,
  round(s.free_percent::numeric, 1)                 AS free_pct
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace,
LATERAL pgstattuple(c.oid) s
WHERE n.nspname = 'public'
  AND c.relkind = 'r'
  AND pg_relation_size(c.oid) > 100 * 1024 * 1024
ORDER BY pg_relation_size(c.oid) DESC
LIMIT 20;
```

`pgstattuple`은 Table 전체를 Scan하므로 Peak 시간대를 피하거나 Replica에서 실행하십시오. 더 가벼운 추정에는 `pg_stat_user_tables.n_dead_tup`을 사용할 수 있습니다.

## PostgreSQL 19에서의 작업 흐름

문서에 기술된 동작을 전제로 하면, 유지보수 작업이 한 문장으로 줄어들 수 있습니다. 정확한 Syntax는 최종 문서에서 확인해야 하지만, 대략 다음과 같은 모습입니다.

```sql
-- Bloat된 Table을 읽기/쓰기 차단 없이 재구성
REPACK (CONCURRENTLY) orders;

-- 재구성하면서 Index 순서로 물리적 정렬
REPACK (CONCURRENTLY) orders USING INDEX orders_created_at_idx;
```

큰 Table에 사용하기 전에 다음을 계획해야 합니다.

1. **Disk 여유 공간.** 재작성에는 Table과 Index의 두 번째 복사본을 담을 공간이 필요합니다.
2. **WAL 발생량.** 전체 재작성은 WAL을 생성합니다. Replica 지연과 Archive 용량을 확인하십시오.
3. **Replication Slot 한도.** `max_repack_replication_slots`와 `max_replication_slots`에 여유가 있는지 확인합니다.
4. **장기 실행 Transaction.** 동시 재구성은 보통 오래된 Transaction의 종료를 기다려야 합니다. `pg_stat_activity`로 모니터링하십시오.

## Autovacuum 병렬화: 눈에 덜 띄지만 중요한 변경

Index가 많은 큰 Table에서는 Index Vacuum이 가장 오래 걸리는 단계인 경우가 많습니다. Autovacuum이 이를 병렬화하면 Table에 Bloat가 쌓이는 시간이 짧아질 것입니다. 쓰기가 많은 대형 Table이 소수라면, 19로 올린 뒤 Table 단위로 조정할 수 있습니다.

```sql
-- Syntax는 19 Release Notes 기준이며 최종 문서에서 확인 필요
ALTER TABLE events SET (autovacuum_parallel_workers = 4);
```

늘릴 때는 신중해야 합니다. Worker가 늘면 Application Traffic과 동시에 발생하는 I/O도 늘어납니다.

## webhani의 권고

1. **이것만을 이유로 업그레이드하지 마십시오.** Bloat는 적절한 Autovacuum Tuning과, 필요 시 `pg_repack`으로 지금도 관리할 수 있습니다.
2. **PostgreSQL 19 Test Cluster를 구성하십시오.** 운영 데이터의 최근 복사본으로 만들고, 가장 Bloat가 심한 Table에서 `REPACK (CONCURRENTLY)`를 시험해 보십시오. 소요 시간, 생성된 WAL, Lock 대기를 측정합니다.
3. **증상만이 아니라 원인을 고치십시오.** 반복해서 Bloat되는 Table은 갱신 패턴, `fillfactor`, HOT Update 적용 조건, Vacuum을 막는 장기 Transaction을 살펴야 합니다.
4. **GA와 Managed Service의 지원을 기다린 뒤** 운영 업그레이드를 계획하십시오. Major Version 업그레이드에는 `pg_upgrade`, Dump/Restore, Logical Replication 중 하나가 필요합니다.

차단 없는 재구성을 기본 기능으로 쓸 수 있게 되는 것은 운영상 실질적인 개선입니다. 안정 버전이 나왔을 때 자사 Workload에 어떤 효과가 있는지 알 수 있도록, 지금 미리 시험해 볼 가치가 있습니다.
