Go 서비스 앞단에 Redis를 두면 많은 팀이 "Redis 자체 처리 속도가 빠르니 지연도 작을 것"이라고 가정합니다. 틀린 말은 아니지만, 부하가 걸린 실제 요청 경로를 들여다보면 병목은 대부분 거기 있지 않습니다. p99 그래프에 실제로 찍히는 비용은 애플리케이션 프로세스와 Redis 서버 사이의 라운드트립이고, 요청 하나가 건드리는 키 개수만큼 이 비용은 그대로 누적됩니다.

2026년 9월에 나온 go-redis 9.22.0은 이 라운드트립 문제를 정면으로 다루는 실험적 기능 두 가지를 추가했습니다. RESP3의 `CLIENT TRACKING`을 활용한 클라이언트 사이드 캐싱, 그리고 자동 파이프라이닝입니다. 지금 당장 도입 여부를 결정하지 않더라도, 클라이언트 계층에서 캐싱이라는 개념이 어떻게 바뀌고 있는지는 알아둘 가치가 있습니다.

## 비용의 정체는 Redis 처리 시간이 아니라 라운드트립

일반적인 Go 웹 서비스가 요청 하나를 처리하면서 사용자 세션, 피처 플래그 3개, 공유 설정값 하나를 필요로 한다고 가정해 봅시다. 단순하게 구현하면 Redis에 `GET`을 다섯 번 호출하게 됩니다. 같은 가용 영역 안에서 잘 튜닝된 네트워크라도 라운드트립 한 번에 0.3ms가 든다면, Redis가 아무 작업도 하지 않은 시점에 이미 1.5ms의 네트워크 비용이 발생한 셈입니다. 부하가 걸리고 커넥션 풀 경쟁과 GC 일시정지까지 겹치면 이 수치는 개선되기는커녕 악화됩니다. 그리고 이 비용은 모든 요청, 모든 레플리카, 매 분마다 그대로 쌓입니다.

Redis 자체는 싱글 스레드로 동작하지만 단순한 키 조회라면 수십 마이크로초 수준으로 매우 빠르게 처리합니다. "Redis 처리는 50마이크로초면 끝난다"와 "라운드트립에는 300마이크로초 이상 걸린다" 사이의 이 간극이 클라이언트 사이드 캐싱이 존재하는 이유입니다. 읽기의 라운드트립 자체를 없앨 수 있다면 지배적인 비용을 제거할 수 있습니다.

## RESP3 CLIENT TRACKING이 바꾸는 것

클라이언트 측에서 Redis 부하를 줄이는 전통적인 방법은 TTL을 둔 로컬 캐시, 즉 애플리케이션 프로세스 안에 `sync.Map`이나 LRU 캐시를 두는 것이었습니다. 이 방식은 동작하지만 불편한 트레이드오프가 있습니다. TTL을 너무 길게 잡으면 쓰기 이후에도 오래된 데이터를 내려줄 위험이 있고, 너무 짧게 잡으면 라운드트립이 거의 줄지 않습니다.

`CLIENT TRACKING`은 RESP3 프로토콜의 일부로, 이 추측 자체를 없애줍니다. 클라이언트가 트래킹을 활성화하면 Redis는 그 클라이언트가 어떤 키를 읽었는지 기억합니다. 다른 클라이언트(혹은 동일 클라이언트)가 해당 키를 변경하면, Redis는 같은 커넥션을 통해 무효화 메시지를 푸시해서 "네가 캐싱한 이 값은 더 이상 유효하지 않다"고 알려줍니다. 클라이언트는 TTL 만료를 기다릴 필요 없이 즉시 로컬 캐시에서 해당 엔트리를 지울 수 있습니다.

이건 본질적인 발상의 전환입니다. 클라이언트가 데이터의 신선도를 "추측"하는 대신, 서버가 신선도가 깨지는 시점을 직접 "알려주는" 것입니다. Go 프로세스 안의 캐시는 Redis 키스페이스 일부를 어림짐작으로 근사하는 것이 아니라, 정확성이 보장된 미러가 됩니다.

## 감을 잡기 위한 예시 코드

아래 코드는 아이디어의 형태를 보여주기 위한 예시적인 Go 코드이며, go-redis API를 그대로 옮긴 것이 아닙니다. 실험적 기능이라 API 형태가 아직 바뀔 수 있으므로, 실제 구현 시에는 go-redis 9.22.0 공식 문서에서 정확한 메서드 이름과 옵션을 확인해야 합니다.

Before — 읽을 때마다 라운드트립 발생:

```go
func GetFeatureFlag(ctx context.Context, rdb *redis.Client, key string) (string, error) {
    // 지난 한 시간 동안 플래그가 바뀌지 않았어도 매번 네트워크를 탄다.
    return rdb.Get(ctx, key).Result()
}
```

After — 클라이언트 사이드 캐싱을 사용한다고 가정했을 때의 개념적인 형태:

```go
// 예시: go-redis 9.22.0은 RESP3 CLIENT TRACKING을 활용한
// 옵트인 방식의 클라이언트 사이드 캐시를 제공할 것으로 보입니다.
// 실제 API 형태는 다를 수 있으므로 상호작용 패턴을 보여주는
// 스케치로만 참고하세요.
type TrackedCache struct {
    rdb   *redis.Client
    local *sync.Map // key -> 캐시된 값, 서버 푸시로 무효화됨
}

func (c *TrackedCache) GetFeatureFlag(ctx context.Context, key string) (string, error) {
    if v, ok := c.local.Load(key); ok {
        return v.(string), nil // 라운드트립 없음
    }

    val, err := c.rdb.Get(ctx, key).Result()
    if err != nil {
        return "", err
    }

    // 이 읽기 자체가 Redis 쪽에 트래킹 대상으로 등록된다.
    // 백그라운드 goroutine이 이 커넥션의 무효화 푸시를 소비하다가
    // Redis가 키 변경을 알리면 c.local.Delete(key)를 호출한다.
    c.local.Store(key, val)
    return val, nil
}
```

중요한 건 정확한 메서드 시그니처가 아니라 이 패턴 자체입니다. 완전히 프로세스 내부에서 끝나는 로컬 읽기 경로와, TTL에 의존하지 않고 로컬 상태의 정확성을 유지해주는 별도 채널(무효화 푸시)이 분리되어 있다는 점입니다.

자동 파이프라이닝은 관련은 있지만 다른 문제를 다룹니다. 캐싱이 없더라도, 짧은 시간 window 안에 여러 독립적인 Redis 커맨드가 발생하면(예: 여러 goroutine이 각자 `GET`을 호출하는 경우), go-redis는 이를 하나의 네트워크 라운드트립으로 투명하게 묶어줄 수 있습니다. `Pipeline`을 직접 구성할 필요가 없습니다. 데이터 신선도 관련 semantics를 전혀 바꾸지 않는 순수한 네트워크 계층 최적화이기 때문에, 클라이언트 사이드 캐싱보다 리스크가 낮은 기능입니다.

## 정확성과 관련된 주의사항

클라이언트 사이드 캐싱은 공짜가 아닙니다. 리스크는 대부분 다음 사항들에 몰려 있습니다.

- **서버 쪽 트래킹 테이블에는 메모리 한계가 있습니다.** Redis는 어떤 클라이언트가 어떤 키를 트래킹하고 있는지 기억해야 무효화 알림을 보낼 수 있고, 이는 Redis 서버 메모리를 소비합니다. 많은 클라이언트 커넥션에 걸쳐 카디널리티가 매우 높은 키 집합을 트래킹하면, 클라이언트 쪽 라운드트립 절감보다 Redis 본체에 가해지는 메모리 압박이 더 커질 수 있습니다.
- **연결 끊김·재연결 시에는 반드시 로컬 캐시를 flush해야 합니다.** 무효화 푸시를 실어 나르던 커넥션이 끊기면, 클라이언트는 그 사이에 무효화 알림을 놓치지 않았다는 보장을 잃습니다. 안전한 동작은 재연결 시 로컬 캐시를 전부 비우고 처음부터 다시 채우는 것뿐입니다. 클라이언트 사이드 캐싱 구현체는 이 부분을 정확히 처리해야 하며, 재연결 이후에도 오래된 엔트리를 조용히 들고 있는 것은 사소한 비효율이 아니라 실제 정확성 버그입니다.
- **핫하고 읽기 빈도가 높으며 쓰기가 드문 키에 효과적입니다.** 피처 플래그, 설정값, 쓰기 한 번에 여러 번 읽히는 세션 조회가 딱 맞는 대상입니다. 절감되는 라운드트립이 받게 되는 무효화 푸시보다 훨씬 많습니다.
- **쓰기가 많은 키에는 효과가 없습니다.** 읽기만큼 자주 쓰기가 일어나는 키라면, 쓰기가 일어날 때마다 트래킹 중인 모든 클라이언트에 무효화 푸시가 전송됩니다. 결과적으로 무효화 채널에서 지불하는 네트워크 비용이 읽기에서 절감한 비용과 비슷하거나 오히려 더 커집니다. 카운터, Rate Limit용 버킷, 자주 갱신되는 큐라면 클라이언트 사이드 캐싱은 거의 순수한 오버헤드에 가깝습니다.

## webhani의 도입 권장사항

기존 캐싱 레이어를 대체하는 것이 아니라 추가 옵션으로 보는 것이 맞다고 생각합니다. 현실적인 도입 절차는 다음과 같습니다.

1. 명확하게 읽기 중심이고 쓰기가 적은 키부터 시작합니다. 피처 플래그나 정적 설정값이 가장 다루기 쉬운 첫 대상이고, 세션 조회는 그다음 단계로 적절합니다.
2. 도입 전후로 무효화 발생 빈도를 계측합니다. 트래킹을 켠 키가 읽기와 비슷한 빈도로 무효화된다면 그 키에는 효과가 없다는 뜻이므로 대상에서 제외합니다.
3. 기존 캐싱 레이어(CDN, 명시적 TTL을 둔 애플리케이션 내 캐시, 읽기 전용 Replica)는 그대로 유지합니다. `CLIENT TRACKING` 기반 클라이언트 사이드 캐싱은 특정 접근 패턴에 맞춰진 좁고 정밀한 도구이지, 기존 캐싱 아키텍처 전체를 대체하는 것이 아닙니다.
4. go-redis 9.22.0에서 두 기능 모두 실험적 기능으로 표시되어 있으므로, 프로덕션 도입 시에는 Feature Flag로 제어하고 대상 키를 확대하기 전에 Redis 쪽 메모리 동작, 특히 트래킹 테이블 크기를 면밀히 모니터링할 것을 권장합니다.

"클라이언트가 TTL로 추측하는 대신 서버가 캐시가 틀렸을 때를 알려준다"는 아이디어 자체는 탄탄합니다. 그 가치는 결국 어떤 키에 적용하느냐에 달려 있습니다.
