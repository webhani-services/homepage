## "거의 같은 질문"에 매번 과금하지 않으려면

LLM 기반 Chatbot이나 Customer Support App을 운영하다 보면, User의 질문 중 상당수가 "문자열은 다르지만 의미적으로는 거의 같은" 경우라는 것을 알게 됩니다. "반품 방법 알려주세요"와 "상품을 반품하고 싶은데 어떻게 해야 하나요"는 일반적인 Key-Value Cache에서는 서로 다른 질문으로 처리되지만, 의미상으로는 같은 질문입니다.

Redis가 제공하는 LangCache는 이러한 "의미적 중복"을 감지해 LLM 호출 자체를 생략하는 Managed Semantic Caching Service입니다. Embedding Vector 기반 유사도 검색을 사용해, 과거에 답변한 질문과 의미적으로 가까운 질문이 들어오면 Cache된 답변을 그대로 반환하고, 일치하지 않을 때만 실제로 LLM을 호출합니다 ([Redis 공식 문서: Redis LangCache](https://redis.io/docs/latest/develop/ai/context-engine/langcache/)).

## 구조: 완전 일치가 아닌 의미적 일치

일반적인 Cache(Redis의 String Key 등)는 완전 일치일 때만 Hit됩니다. Semantic Caching은 질문 문장을 Embedding Vector로 변환하고, Vector 공간에서의 유사도가 임계값을 넘으면 Cache Hit로 판단합니다.

```text
질문 A: "반품 방법 알려주세요"
질문 B: "상품을 반품하고 싶은데 어떻게 해야 하나요"

→ 문자열로는 불일치
→ Embedding Vector 유사도는 높음
→ Semantic Cache에서는 Hit 처리
```

LangCache는 이 Embedding 생성과 Vector 검색을 Managed Service로 제공하며 REST API로 이용할 수 있습니다. 직접 Vector DB와 Cache Layer를 조합해 구축하는 수고를 덜어준다는 점이 도입 문턱을 낮춥니다 ([Redis 공식 Blog: What is semantic caching?](https://redis.io/blog/what-is-semantic-caching/)).

## 구현 예시

Redis가 공개한 RedisVL Library를 사용한 Semantic Caching의 기본 Pattern을, 공식 문서의 방식에 따라 보여드립니다.

```python
from redisvl.extensions.llmcache import SemanticCache

cache = SemanticCache(
    name="support_cache",
    redis_url="redis://localhost:6379",
    distance_threshold=0.15,  # 유사도 임계값
)

def answer_question(question: str) -> str:
    cached = cache.check(prompt=question)
    if cached:
        return cached[0]["response"]

    response = call_llm(question)  # 실제 LLM 호출
    cache.store(prompt=question, response=response)
    return response
```

`distance_threshold` 값이 작을수록 "엄격하게 유사한" 질문만 Hit로 간주하고, 클수록 더 폭넓게 Hit됩니다. 이 값을 얼마나 정교하게 Tuning하느냐가 Semantic Caching 운영의 핵심입니다 ([Redis LangCache 공식 문서](https://redis.io/docs/latest/develop/ai/redisvl/0.6.0/user_guide/llmcache/)).

## 임계값 Tuning의 함정

Semantic Caching의 가장 큰 위험은 "잘못된 Hit"입니다. 임계값을 너무 느슨하게 설정하면, 미묘하게 뉘앙스가 다른 질문("반품하고 싶어요" vs "반품 기한이 지났는데 반품할 수 있나요")이 같은 Cache 답변을 반환하게 되어 User에게 잘못된 정보를 전달할 위험이 있습니다.

운영상 다음과 같은 단계적 접근을 권장합니다.

1. **보수적인 임계값에서 시작합니다.** 처음에는 엄격한 `distance_threshold`로 운영하며 Cache Hit율과 User 불만 사항을 함께 Monitoring합니다.
2. **Category별로 임계값을 다르게 설정합니다.** FAQ 같은 정형화된 질문은 느슨한 임계값도 안전하지만, 가격이나 계약 조건에 관련된 질문은 엄격하게 설정하는 등 질문의 성격에 맞춰 조정합니다.
3. **Cache에 TTL을 설정합니다.** 가격 변경이나 정책 변경이 있을 때 오래된 답변이 계속 Cache되어 나가지 않도록 유효 기간을 둡니다.

## 비용과 지연에 미치는 효과

Semantic Cache가 Hit되면 LLM 호출 자체가 발생하지 않으므로 Token 과금과 지연을 모두 없앨 수 있습니다. FAQ성 질문이 많은 Customer Support 용도에서는 Cache Hit율이 높아지기 쉽고, 절감 효과도 그만큼 커집니다.

다만 Embedding 생성과 Vector 검색 자체에도 비용과 지연이 발생하므로, "LLM 호출보다 Vector 검색이 확실히 가벼운" 상황이 전제되어야 합니다. 질문의 다양성이 매우 크거나 실시간성이 극도로 중요한 Use Case에서는 이 전제가 무너지면서 효과가 옅어질 수 있다는 점에 유의해야 합니다.

## webhani의 관점

webhani가 고객의 AI Chatbot이나 Support 자동화를 설계할 때, Semantic Caching은 "만능 고속화 장치"가 아니라 "질문 분포가 한쪽으로 치우친 Workload를 위한 최적화"로 자리매김합니다. 도입 전 다음을 확인하는 것을 권장합니다.

- 과거 문의 Log를 분석해 실제로 "의미적으로 중복된 질문"이 얼마나 존재하는지 정량화합니다
- 잘못된 Hit가 허용되지 않는 영역(법무·의료·금전 관련 답변 등)에서는 Cache를 사용하지 않거나 사람의 검토 단계를 둡니다
- Cache Hit율과 User 만족도를 함께 Dashboard로 지속적으로 관찰합니다

## 마무리

Redis LangCache 같은 Semantic Caching은 LLM Application의 비용과 지연을 구조적으로 낮추는 수단으로 실용 단계에 들어섰습니다. 다만 효과는 Workload의 질문 분포에 크게 좌우되며, 임계값 Tuning을 잘못하면 오답 Risk를 떠안게 됩니다. webhani는 이러한 Caching 전략의 설계와 검증을 포함한 AI Application 구축을 지원해 나가겠습니다.
