"AI 학습에는 쓰이고 싶지 않지만 검색 결과에서는 빠지고 싶지 않다." 고객사 웹사이트 운영에서 자주 받는 요청입니다. 지금까지의 해법은 `GPTBot`, `ClaudeBot`, `Google-Extended` 같은 Crawler 이름을 하나씩 robots.txt에 추가하는 것이었습니다. 새로운 Crawler가 나올 때마다 목록을 갱신해야 하고, 무엇보다 표현하려는 의도와 맞지 않습니다. 거부하려는 대상은 특정 Crawler가 아니라 "학습"이라는 용도이기 때문입니다.

10월 30일, Anthropic의 Kevin Kelley가 작성한 IETF 개인 Draft `draft-kelley-aipref-training-preference-signal-00`이 공개되었습니다. 이후 보도에 따르면 Google, Microsoft, OpenAI, Anthropic 네 곳이 이 Token을 존중하겠다고 밝혔습니다. 다만 각 사의 1차 발표를 모두 확인하지는 못했으므로, 현재로서는 "보도된" 내용으로 보는 것이 적절합니다.

## 동작 방식

이 Draft는 새로운 Directive나 문법을 추가하지 않습니다. RFC 9309의 Group 구조, Path 매칭, 최장 일치 규칙을 그대로 사용하고, `User-agent` 줄에 쓰는 Policy Token `__usage_ai-training`만 정의합니다. 학습용으로 콘텐츠를 수집하는 Crawler는 이 Group의 규칙을 따르게 됩니다.

"AI Training"의 정의는 IETF AIPREF Working Group의 어휘 Draft에서 가져왔으며, "생성형 AI 모델의 학습된 Parameter를 변경하기 위해 Asset을 사용하는 것"입니다. 검색 Index나 답변 생성 시점의 참조(RAG 등)는 대상이 아닙니다.

```text
User-agent: *
Allow: /

User-agent: __usage_ai-training
Disallow: /
```

Path 단위 지정도 기존 robots.txt와 동일합니다.

```text
User-agent: __usage_ai-training
Disallow: /blog/
Disallow: /docs/
Allow: /press/
```

## 주의할 점: 전체 Disallow는 학습 거부가 아니다

Draft에서 가장 놓치기 쉬운 부분입니다. `User-agent: *`에 `Disallow: /`를 지정한 사이트라도, Draft 기준으로는 AI 학습에 대해 아무런 의사도 밝히지 않은 것으로 취급됩니다. 크롤링 전체 차단과 학습 거부는 별개의 의사 표시입니다. 외부에서 접근 가능한 Staging 환경이나 내부 문서 사이트를 전체 Disallow로만 관리해 왔다면, Token을 명시적으로 추가하는 것이 좋습니다.

## Next.js App Router 적용

Next.js에서는 `app/robots.ts`로 robots.txt를 생성합니다. `rules`에 배열을 넘길 수 있으므로 Group을 하나 추가하면 됩니다. 전환 기간에는 기존 Crawler별 차단도 남겨 둡니다.

```ts
// app/robots.ts
import type { MetadataRoute } from "next";

const AI_TRAINING_TOKEN = "__usage_ai-training";
const LEGACY_AI_CRAWLERS = ["GPTBot", "ClaudeBot", "Google-Extended", "CCBot"];

export default function robots(): MetadataRoute.Robots {
  return {
    rules: [
      { userAgent: "*", allow: "/" },
      { userAgent: AI_TRAINING_TOKEN, disallow: "/" },
      { userAgent: LEGACY_AI_CRAWLERS, disallow: "/" },
    ],
    sitemap: "https://example.com/sitemap.xml",
  };
}
```

Token 앞의 밑줄 두 개(`__`)는 오타가 나기 쉽고 Code Review에서도 잘 보이지 않습니다. Test로 고정해 두는 것을 권장합니다.

```ts
// app/robots.test.ts
import { expect, test } from "vitest";
import robots from "./robots";

test("AI 학습 opt-out Group이 포함되어 있다", () => {
  const { rules } = robots();
  const list = Array.isArray(rules) ? rules : [rules];
  expect(
    list.some((r) => r.userAgent === "__usage_ai-training" && r.disallow === "/"),
  ).toBe(true);
});
```

Build 후에는 `curl -s http://localhost:3000/robots.txt`로 실제 출력도 확인합니다.

## 페이지 단위 지정

2차 정보에 따르면 Microsoft는 IETF Draft에 없는 페이지 단위 지정(`meta` Tag 또는 `X-Robots-Tag` Header)도 지원할 예정입니다. 정확한 값 형식은 1차 자료로 확인하지 못했기 때문에, Bing 공식 문서가 나올 때까지는 robots.txt를 기본으로 삼는 것이 안전합니다.

## webhani의 관점

이 Draft의 장점은 새로운 체계를 만들지 않고 이미 모든 사이트가 가진 robots.txt 위에 얹었다는 점입니다. Crawler 목록을 따라다니는 운영에서 "어떤 용도를 거부하는가"를 밝히는 운영으로 바뀌면, 반복 작업이 줄고 의도도 명확해집니다.

한계도 분명히 알아 두어야 합니다.

1. **강제력이 없습니다.** robots.txt는 접근 제어가 아니라 약속입니다. 이를 무시하는 Scraper 대응은 WAF나 Bot 관리의 영역입니다.
2. **아직 개인 Draft입니다.** 표준화 과정에서 Token 이름이나 의미가 바뀔 수 있습니다.
3. **학습과 검색·답변 인용은 별개입니다.** 학습을 거부해도 AI 검색 답변에 인용되는 것까지 막히지는 않습니다. 미디어나 EC 사이트라면 그 유입이 오히려 중요할 수 있으므로, 두 질문을 분리해서 결정해야 합니다.

## 이번 주 체크리스트

1. robots.txt 또는 `app/robots.ts`에 AI 학습에 대한 명시적인 의사 표시가 있는지 점검합니다.
2. 학습을 거부한다면 `__usage_ai-training` Group을 추가하고, 기존 Crawler별 차단은 당분간 유지합니다.
3. Token 이름을 Unit Test로 고정해 Refactoring 이후에도 유지되게 합니다.
4. "학습은 거부, AI 검색 인용은 허용"처럼 정책을 문서화해 개발팀과 사업 측이 함께 참조할 수 있게 합니다.

작은 파일이지만, 콘텐츠에 대한 회사의 방침이 실제로 드러나는 곳입니다. 이번 기회에 한 번 점검해 보시기 바랍니다.
