DeepSeek이 더 자율적인 Coding Agent의 Open Source Prototype을 공개했습니다. Claude Code에 대한 도전자로 자리매김하고 있지만, 스스로는 성숙한 제품이 아니라 Architecture 탐색이라고 설명하고 있으며, 저희도 Benchmark를 측정하지는 않았습니다. 언론 보도는 구조상의 아이디어 하나를 소개하는데, 시스템이 Router 계층과 여러 Worker Session으로 나뉘어 있다는 것입니다.

여기서 제품 리뷰는 하지 않습니다. 이 분리 자체가 유용한 Pattern이고, 엔지니어에게 익숙한 개념에 대응시킬 수 있기 때문입니다. 이것이 무엇인지, 언제 효과가 있는지, 어디서 문제가 생기기 쉬운지를 정리합니다.

## Pattern 개요

Agent의 단일 Session은 작업하면서 Context를 쌓습니다. 읽은 파일, 실행한 Command, 막다른 길을 탐색한 기록 등입니다. 이 Context는 강점이면서 동시에 한계입니다. Session이 길어지면 느려지고 비용이 늘며, 오래된 세부 정보로 Window가 가득 차면 품질이 떨어지기 쉽습니다.

Router/Worker 분리는 두 가지 역할을 나눕니다.

- **Router:** 전체 목표와 짧은 계획을 가지고 있습니다. 다음에 무엇을 할지 결정하고, 범위가 정해진 Task를 Worker에게 넘기며, 간결한 결과를 받습니다. Code에는 거의 직접 손대지 않습니다.
- **Worker:** 범위가 분명한 하나의 Task, 필요한 파일, 완료 기준을 받은 새로운 Session입니다. 읽기와 수정을 수행하고 요약과 Diff를 반환하며, 그 Context는 폐기됩니다.

Job Queue를 써 보셨다면 익숙한 구조입니다. Router는 Coordinator, Worker는 Stateless Consumer, 요약은 둘 사이의 Message Contract에 해당합니다.

## 장점

- **중요한 곳에서 Context를 작게 유지합니다.** Router는 Worker가 읽은 모든 파일이 아니라 요약만 봅니다. Worker는 Repository 중 자기 담당 부분만 봅니다.
- **병렬화가 가능합니다.** 서로 무관한 세 Module의 Test를 갱신하는 것처럼 독립적인 Task를 별도의 Worker에서 동시에 실행할 수 있습니다.
- **실패가 격리됩니다.** 잘못된 길로 들어선 Worker는 메인 Session을 오염시키지 않고 폐기한 뒤 재시도할 수 있습니다.
- **Review가 쉬워집니다.** 각 Worker가 목적이 분명한 독립된 변경을 만들어 냅니다.

## 최소한의 예시

아래 TypeScript는 제어 흐름을 보여 주기 위해 직접 작성한 예시이며, 특정 벤더의 구현이 아닙니다. `runWorker`는 사용 환경에서 Agent Session을 시작하는 처리를 대신하는 자리 표시자입니다.

```ts
type Task = {
  id: string;
  goal: string;
  files: string[];          // 이 Worker가 수정할 수 있는 범위
  acceptance: string[];     // "완료"를 정의하는 검사 항목
};

type WorkerResult = {
  taskId: string;
  status: "ok" | "failed";
  summary: string;          // Router를 위한 짧은 요약
  changedFiles: string[];
};

// 대체: 하나의 Task로 범위를 좁힌 새 Agent Session을 시작합니다.
declare function runWorker(task: Task): Promise<WorkerResult>;

async function runPlan(tasks: Task[], maxParallel = 3): Promise<WorkerResult[]> {
  const results: WorkerResult[] = [];
  const queue = [...tasks];

  async function lane() {
    for (let task = queue.shift(); task; task = queue.shift()) {
      let result = await runWorker(task);
      if (result.status === "failed") {
        // 실패 요약을 추가 Context로 넘겨 재시도는 한 번만 합니다.
        result = await runWorker({
          ...task,
          goal: `${task.goal}\n\nPrevious attempt failed: ${result.summary}`,
        });
      }
      results.push(result);
    }
  }

  await Promise.all(Array.from({ length: maxParallel }, lane));
  return results;
}
```

Code보다 중요한 점이 두 가지 있습니다. 첫째는 `files` 필드로, Worker는 수정할 수 있는 파일을 선언하거나 지정받아야 합니다. 둘째는 `acceptance`입니다. 객관적인 검사 기준이 없는 Worker는 스스로 성공했다고 믿기 때문에 성공했다고 보고합니다.

## 대비해야 할 실패 유형

**수정 충돌.** 두 Worker가 같은 파일을 수정하면 충돌합니다. 병렬 실행 전에 파일 소유 기준으로 Task를 나누고, 분할이 불분명하면 순차 실행으로 되돌립니다. git에서 병렬 Branch를 다룰 때와 같은 문제이고 해법도 같습니다.

**요약 과정의 정보 손실.** Router는 Worker의 보고를 바탕으로 판단합니다. Worker가 주의 사항을 빠뜨리면 Router는 되찾을 수 없습니다. 자유 서술만 받지 말고, 둔 가정과 실행하지 않은 Test 같은 항목이 명시된 구조화된 요약을 요구하십시오.

**Router의 Drift.** 계속 재계획하는 Router는 반복에 빠질 수 있습니다. 재계획 횟수와 Worker 총 실행 횟수에 상한을 두고, 상한에 도달하면 사람에게 알립니다.

**비용 증가.** 병렬 Worker는 각자 자기 Context 비용을 지불합니다. 이 Pattern은 개별 Session의 비대화를 줄이지만, Task 범위가 나쁘면 총 비용은 오히려 늘 수 있습니다. Session 단위가 아니라 완료된 Task당 Token 수를 측정하십시오.

**확신에 찬 오답.** 자율성이 높을수록 사람이 잘못된 가정을 일찍 알아챌 기회는 줄어듭니다. Agent가 Code를 많이 만들어 낼 때는 [Review 용량이 진짜 병목](/blog/ai-agents-more-code-same-output-review-bottleneck-2026-10)이라고 이전 글에서 썼는데, Worker를 부채꼴로 펼치면 이 점이 더 두드러집니다.

## 다른 Agent에도 적용되는 Guardrail

이것들은 특정 Model이나 벤더에 의존하지 않습니다. 다중 Session 구성에서 저희가 권하는 통제는 다음과 같습니다.

1. **Worker별 최소 권한.** 각 Worker에게 작업 사본이나 Branch를 주고, 인증 정보는 Task 범위로 한정합니다.
2. **결정론적 Gate.** Test, 타입 검사, Linter는 Agent 밖에서 실행되며 결과의 수용 여부를 결정합니다.
3. **Fail-closed Hook.** 정책 검사를 실행할 수 없으면 허용이 아니라 거부해야 합니다. [Fail-closed Hook](/blog/claude-code-hooks-fail-closed-guardrails-2026-10) 글을 참고하십시오.
4. **사람의 확인은 모든 단계가 아니라 Merge 시점에.** 통합된 결과를 Review하고, 각 Worker의 요약과 Diff는 보조 자료로 열람할 수 있게 합니다.
5. **감사 추적.** 어느 Worker가 어떤 Task 설명을 바탕으로 어떤 변경을 만들었는지 기록합니다.

## 지금 도입해야 할까

Sub-agent나 Fork를 지원하는 Agent를 이미 쓰고 있다면 필요한 부품은 갖춰져 있으므로 단계적으로 시도할 수 있습니다. 메인 Session이 Test 생성이나 기계적인 Migration처럼 범위가 분명한 Task를 위임하게 하고, Architecture 결정은 메인 Session에 남겨 둡니다.

막 나온 Prototype을 Production Tooling으로 취급하는 것은 신중해야 합니다. 새 Project는 아이디어를 검증할 수는 있어도, 중요한 Repository에서 무인으로 돌려도 될 만큼 준비된 것은 아닐 수 있습니다. 저희가 권하는 순서는, 버려도 되는 Repository에서 Architecture를 평가하고, 현재의 단일 Session Workflow와 비용 및 Review 부담을 비교한 뒤, 특정 제품을 Toolchain에 넣을지 결정하는 것입니다.
