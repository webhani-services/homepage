Ruby 4.0에 ZJIT(Zero-overhead JIT)라는 Just-In-Time Compiler가 새로 탑재됐습니다. YJIT를 조금 개선한 것이 아니라 후속작으로 처음부터 새로 설계된 것입니다. Rails를 Production에서 운영하는 Team이라면 이것이 Default가 되기 전에 이해해둘 가치가 있습니다. YJIT가 문제가 있어서가 아니라, ZJIT의 설계가 YJIT 자체 Architecture에서 비롯된 특정 Tradeoff를 다루고 있기 때문입니다.

## 왜 YJIT 개선이 아니라 새로운 JIT인가

YJIT는 lazy basic block versioning이라는 기법으로 Ruby Bytecode를 Machine Code로 Compile합니다. 효과적이지만 구조적인 Cost가 있는데, Program의 각 지점에서 관측된 Type을 기반으로 적극적으로 Specialize하기 때문에 생성되는 Machine Code 양이 많아집니다. 실행 시점에는 빠르지만 Memory를 많이 쓰게 되고, 이 Specialization 전략 자체가 큰 재설계 없이는 일부 Optimization을 추가하기 어렵게 만듭니다.

ZJIT는 다른 접근을 취합니다. Ruby Compiler가 Machine Code를 생성하기 전에 분석하고 최적화할 수 있는, 좀 더 전통적인 Intermediate Representation(IR) 중심으로 설계됐습니다. 실무적인 효과로는 시간이 지날수록 Optimization의 여지가 늘어난다는 점과, Workload에 따라 Hot Path에서 동일한 조건의 YJIT보다 Memory Footprint가 작아질 수 있다는 점을 들 수 있습니다.

## 활성화 방법

ZJIT는 4.0에서 YJIT와 함께 제공되지만 아직 Default는 아닙니다. 명시적으로 활성화해야 합니다.

```bash
ruby --zjit app.rb
```

Rails App이라면 Server 실행 Command나 Process Manager가 전달하는 Environment 변수를 통해 설정합니다.

```bash
RUBYOPT="--zjit" bundle exec puma -C config/puma.rb
```

실행 중 활성화 여부는 다음으로 확인할 수 있습니다.

```ruby
RubyVM::ZJIT.enabled? # => true
```

## 실제로 무엇을 측정해야 하는가

JIT Compiler는 Hot하고(자주 실행되고) 오래 실행되는 Code Path에서 효과를 냅니다. Process가 계속 살아있을수록 실제 Input 형태를 기반으로 Specialize할 기회가 늘어나고 효과가 누적되기 때문입니다. 즉 ZJIT를 제대로 평가하려면 몇 초 만에 끝나는 `rails runner` 같은 단발성 Script가 아니라, Production과 유사한 Load 아래에서 검증해야 합니다.

현실적인 평가 방법의 예시입니다.

```ruby
# config/initializers/jit_metrics.rb
if RubyVM::ZJIT.enabled?
  Rails.logger.info("ZJIT stats: #{RubyVM::ZJIT.stats}")
end
```

기존 Load Test Suite(또는 Staging 환경에 대한 Shadow Traffic Replay)를 YJIT와 ZJIT 각각 켠 상태로 실행하고, 시작 직후뿐 아니라 지속적인 구간에서 p50/p95 Response Time과 RSS Memory를 비교하세요. 1분 시점에는 동일해 보이는 JIT라도, 두 Compiler 모두 충분히 Specialize할 시간을 가진 30분 시점에는 의미 있는 차이가 나타날 수 있습니다.

## Rails App에서 특히 의미 있는 부분

Rails Workload는 대개 수치 연산의 Tight Loop가 아니라 ActiveRecord Query 구성, Serialization, View Rendering이 중심입니다. 그래서 연산량이 많은 Ruby Script와는 효과가 나타나는 양상이 다릅니다. 1분에 수천 번씩 같은 Code Path를 타는 Controller Action — Access가 많은 JSON API Endpoint나 자주 Render되는 Partial — 이 JIT Compiler가 Specialize할 기회가 가장 많고 효과도 크게 나타나는 지점입니다. 반대로 거의 Access되지 않는 관리자 Page라면 어느 쪽을 써도 눈에 띄는 차이는 없을 것입니다.

Puma 위에서 여러 Worker Process로 Rails를 돌리고 있다면, 각 Worker가 각자 독립적으로 JIT Compile을 수행한다는 점에 유의하세요. ZJIT가 목표로 하는 Memory 절감 효과는 Worker 수만큼 곱해지므로, 오히려 그 의미가 작아지는 게 아니라 커집니다.

## 도입 절차

이는 Minor Version Up 수준이 아니라 Compiler Backend 자체의 변경이므로, 다른 Runtime 수준의 변경과 동일하게 다루는 것을 권장합니다.

1. 먼저 Staging 환경에서 현실적인 Load 아래 최소 며칠간 활성화합니다.
2. Performance뿐 아니라 Error Rate도 함께 비교합니다. 새로운 Compiler Backend는 Native Extension이나 특이한 Metaprogramming Pattern에 숨어 있던 문제를 드러내기 쉬운 변경입니다.
3. Deployment 구성이 Process 단위 Canary를 지원한다면, 전면 전환 전에 Production Worker 일부에만 먼저 적용합니다.
4. ZJIT가 최소 한 번의 Full Deploy Cycle을 문제없이 통과할 때까지는 `ruby --yjit`를 문서화된 Fallback으로 남겨둡니다.

## 정리

- ZJIT는 YJIT의 단순한 고속판이 아니라, YJIT보다 Optimization 여지가 크고 Memory Footprint도 작도록 처음부터 새로 설계된 JIT Compiler입니다.
- Ruby 4.0에 포함되어 있지만 아직 Default는 아닙니다. `--zjit`로 명시적으로 활성화하고 `RubyVM::ZJIT.enabled?`로 확인하세요.
- 단명하는 Script로는 효과가 드러나지 않으므로, 지속적이고 Production에 가까운 Load 아래에서 평가하세요.
- Rails Workload에서는 API Endpoint나 자주 쓰이는 Partial처럼 Hot한 Code Path에서 효과가 가장 크고, Access가 적은 Page에서는 차이가 크지 않습니다.
- 일반적인 Runtime 변경과 동일하게 다루세요. Staging에서 검증하고, Canary로 배포하고, 실제 Traffic으로 검증될 때까지 YJIT를 Fallback으로 유지하세요.
