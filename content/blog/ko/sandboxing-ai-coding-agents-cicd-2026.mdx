## Pipeline에 등장한 새로운 주체

전통적인 CI/CD 보안 모델은 Build Step을 실행하는 주체가 예측 가능하다는 전제를 깔고 있습니다. Version Control에 등록되어 있고, Merge 전에 Review를 거친 고정된 Script 집합이라는 전제입니다. 이 전제가 무너지고 있습니다. 2026년, Pipeline 내 활동 중 자율 Agent가 주도하는 비중이 늘고 있습니다. Task 설명을 읽고, 어떤 Package를 설치할지 판단하고, 코드를 작성하고, 사람이 각 단계를 승인하지 않은 채 Shell Command를 실행하는 Tool들입니다.

이는 가상의 이야기가 아닙니다. 보안 Vendor들은 이미 이러한 변화를 전제로 한 제품을 내놓고 있습니다. Agent가 설치한 코드가 실행되기 전에 악성 OSS Package를 Endpoint 단에서 차단하는 기능, On-call Engineer를 호출하기 전에 AI가 Production Kubernetes 문제를 진단하고 수정하도록 설계된 Platform 등입니다. 이런 제품들의 완성도를 어떻게 평가하든, 그 밑바탕에 깔린 전제 자체는 타당합니다. Pipeline 안의 Agent는 새로운 신뢰 경계이며, 대부분 팀의 Container 보안 태세는 사람과 정적 Script를 전제로 설계되어 있어, 실행 도중 "이걸 `pip install` 해보자"라고 판단해 실행하는 Process는 상정하지 않았습니다.

## "Container니까 충분하다"가 더 이상 통하지 않는 이유

표준적인 Container 격리(Namespace, cgroups, 제한된 Dockerfile)는 예측 가능한 Workload를 담아두고, 알려진 실패 모드 — 죽은 Process, Resource 누수, 사람이 Diff를 Review한 뒤 Build 시점에 유입된 취약한 의존성 — 로부터의 피해 범위를 제한하도록 설계되었습니다. 자율 Agent는 위협 모델을 세 가지 측면에서 바꿉니다.

1. **실행할 수 있는 Command 집합이 사전에 고정되어 있지 않습니다.** Deploy Script처럼 특정 Shell Command를 Allowlist화할 수 없습니다. Agent의 존재 가치 자체가 Context에 따라 무엇을 실행할지 판단하는 데 있기 때문입니다.
2. **실행 중 스스로 의존성을 설치할 수 있습니다.** Build Step 안에서 실행되는, 오염되었거나 환각(Hallucination)으로 생성된 Package 이름은 사람의 `package.json` 변경이 아니라 Agent 자신이 끌어들이는 Supply Chain Risk입니다.
3. **사람의 Review Loop보다 빠르게 움직입니다.** 사람이 Agent의 예상치 못한 행동을 알아차릴 즈음에는, 이미 몇 Turn을 더 진행했을 수 있습니다.

바로 이 때문에 업계의 논의는 Agent가 실행하는 코드에 대한 "VM급" 격리 쪽으로 옮겨가고 있습니다. Container 자체가 잘못 만들어져서가 아니라, 그 안에서 동작하는 Workload가 더 이상 Container가 상정한 전제에 맞지 않기 때문입니다.

## 실무에서의 VM급 격리

CI/CD 안에서, 또는 운영 중인 Kubernetes Cluster를 대상으로 Agent를 돌리는 팀들 사이에서 몇 가지 패턴이 표준으로 자리잡고 있습니다.

**1. Agent Task마다 일회성 격리 환경을 사용합니다.** Agent가 여러 Task에 걸쳐 재사용하는 장수명 Runner 대신, Task마다 새롭고 격리된 실행 환경을 띄우고 끝나면 폐기합니다. 하나의 잘못된 판단이 일으킬 수 있는 피해를 제한하고, Agent가 여러 실행에 걸쳐 악용할 수 있는 영속 State를 없앱니다.

```yaml
# 단순화한 예시: Agent Task는 공유되는 장수명 CI Runner가 아니라
# 범위가 좁혀진 일회성 Sandbox에서 실행한다.
apiVersion: batch/v1
kind: Job
metadata:
  name: agent-task-run
spec:
  ttlSecondsAfterFinished: 0
  template:
    spec:
      restartPolicy: Never
      automountServiceAccountToken: false
      containers:
        - name: agent-sandbox
          image: agent-runtime:isolated
          resources:
            limits:
              cpu: "1"
              memory: "1Gi"
          securityContext:
            readOnlyRootFilesystem: true
            allowPrivilegeEscalation: false
            runAsNonRoot: true
```

**2. Network Egress는 기본 개방이 아니라 Allowlist로 제한합니다.** 임의의 Host에 접근할 수 있는 Agent는 Data 유출이나 임의 코드 획득이 가능해집니다. Task가 실제로 필요로 하는 특정 Package Registry와 API로 Egress를 좁히고, Allowlist 밖으로의 연결 시도는 경고가 아니라 Incident로 Log에 남겨야 합니다.

**3. 상시 인증정보를 두지 않습니다.** Agent Sandbox는 장수명 Service Account Token을 Mount하는 대신, OIDC 연동 같은 Just-in-time 방식을 통해 해당 Task 전용의 단기·범위 제한된 인증정보를 요청해야 합니다. 실행 중 Agent의 Sandbox가 침해되더라도, 피해 범위는 그 Task 분량의 Access로 한정되며 영속적인 Secret에는 미치지 않습니다.

**4. Production에 닿기 전에 사람의 승인 Gate를 둡니다.** 격리는 실행 중의 피해를 제한할 뿐, Release 전 Review를 대체하지는 않습니다. Infrastructure, Deploy 설정, Production Kubernetes Resource에 대한 Agent발 변경도 사람이 작성한 변경과 동일한 승인 Gate를 거쳐야 합니다 — 실패 모드가 아직 충분히 파악되지 않은 단계라면 오히려 더 엄격한 Gate가 타당합니다.

## Agentic CI/CD를 도입하는 팀에게

Build Pipeline 안이나 운영 중인 Kubernetes Cluster를 대상으로 자율 Agent를 시범 도입 또는 이미 운영하고 있다면, Sandbox 설계를 나중에 덧붙이는 것이 아니라 도입 계획의 1급 요소로 다루세요.

- 현재 CI Runner가 사람 Contributor보다 더 많은 상시 Access를 Agent에게 부여하고 있지는 않은지 점검하세요.
- "Agent가 읽고 제안할 수 있음"과 "Agent가 실행하고 Merge할 수 있음"을 별도의 Permission 등급으로 분리하고, 기본값은 전자로 설정하세요.
- Sandbox Infrastructure(일회성 Compute, 범위 제한된 인증정보, Egress 제어) 비용을, Incident 발생 후 뒤늦게 추가하는 것이 아니라 Agent 도입 비용의 일부로 처음부터 산정하세요.

Pipeline 안의 자율 Agent는 격리 모델이 실제 위협 모델과 맞아떨어질 때 생산성 향상으로 이어집니다. 지금 시점에서 많은 팀은 아직 그렇지 않으며, 이를 방치하면 그 공백이 다음 세대 CI/CD Incident의 발생 지점이 될 것입니다.
