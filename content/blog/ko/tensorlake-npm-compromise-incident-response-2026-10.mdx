10월 초, npm Package `tensorlake`의 0.5.144 버전이 침해되었다고 보도되었습니다. ChainDrop(Shai-Hulud 계열 Worm)으로 불리는 Campaign의 일부입니다. Socket과 The Hacker News가 다루었고, Stingrai가 대응 Checklist를 공개했습니다. 악성 버전의 배포일은 출처에 따라 10월 7일과 8일로 갈리므로 정확한 Timestamp에는 의존하지 않겠습니다.

[Dependency Cooldown과 npm Worm](/blog/dependency-cooldown-policy-npm-pypi-worms-2026)은 이전 글에서 다루었습니다. 이번 글은 이 사건 고유의 교훈, 특히 대응 순서에 집중합니다. 순서를 잘못 잡으면 피해를 키우기 때문입니다.

## 보도된 내용

보도에 따르면 다음과 같습니다.

- 악성 Release는 `preinstall` Hook을 사용했기 때문에 `npm install`만 실행해도 동작합니다. SDK를 import할 필요가 없습니다.
- Hook은 난독화된 Loader를 실행하고, Bun Runtime을 이용해 인증 정보를 탈취하며 스스로 전파되는 Payload를 구동합니다.
- 대상에는 로컬 파일, CI 환경, Kubernetes와 Vault 인증 정보, AI 개발 Tool의 설정이 포함됩니다.
- Stingrai에 따르면 이 Release는 Tensorlake 자체의 Release Workflow를 통해 **유효한 Provenance와 함께** 배포되었습니다.
- Stingrai는 또한 탈취된 GitHub Token이 폐기되면 Home Directory를 삭제하는 Monitor 프로세스가 있다고 보고합니다.

마지막 항목은 신중하게 다뤄야 합니다. 저희가 독자적으로 검증하지는 못했지만, 사실이라면 올바른 작업 순서가 달라집니다.

## Provenance가 증명하는 것은 어디서 만들었는가까지

Provenance(출처 증명)는 특정 Repository의 특정 Workflow에서 Build되었음을 보여 줍니다. 그 Workflow가 신뢰할 수 있는 Code를 실행했는지, 배포용 인증 정보가 악용되지 않았는지는 보증하지 않습니다. 공격자가 Release Pipeline을 장악하면 유효한 증명도 함께 얻게 됩니다.

따라서 Provenance는 판단 근거 중 하나로만 취급합니다. 도난당한 노트북의 Token으로 CI 밖에서 배포하는 경우는 걸러 내지만, CI 자체가 침해된 경우는 걸러 내지 못합니다.

## Install 시점의 실행 줄이기

이 시나리오에서 가장 저렴한 대책은 Lifecycle Script를 기본값으로 실행하지 않는 것입니다.

```bash
# 프로젝트의 .npmrc
ignore-scripts=true
```

그 다음 Native Build처럼 정말 필요한 Package만 명시적으로 허용합니다. 최근 npm과 pnpm은 이 방향으로 가고 있지만, 허용 방법의 구체적인 형태는 사용 중인 버전의 문서에서 확인하시기 바랍니다.

여기에 갓 공개된 버전을 자동으로 설치하지 않는 최소 Release 경과 시간도 설정합니다. 24~72시간 정도의 짧은 Cooldown만 있어도, 악성 버전이 보통 몇 시간 안에 탐지되기 때문에 많은 사고가 아슬아슬한 Near-miss로 끝납니다.

```yaml
# Renovate 예시: 새 버전을 제안하기 전에 대기
{
  "minimumReleaseAge": "3 days"
}
```

## 이미 설치했다면: 대응 순서

1. **영향 범위 파악.** Lockfile과 CI Log에서 해당 버전을 찾습니다.
   ```bash
   grep -rn "tensorlake" package-lock.json pnpm-lock.yaml yarn.lock 2>/dev/null
   ```
   개발자 PC뿐 아니라 해당 기간에 install을 실행한 모든 장비와 CI Runner가 대상입니다.
2. **폐기 전에 격리.** 보고된 Home Directory 삭제 동작이 사실이라면, GitHub Token을 먼저 폐기하는 순간 그것이 발동할 수 있습니다. Host를 Network에서 분리하고, 필요한 데이터를 확보하고, 지속성 메커니즘을 제거한 뒤에 Token을 회수합니다.
3. **접근 가능한 모든 것을 교체.** Cloud Key, GitHub와 npm Token, Kubernetes Service Account Token, Vault Token, 설정 파일에 저장된 AI Tool의 API Key가 해당됩니다.
4. **Audit Log 검토.** 본인이 만들지 않은 Repository, Workflow 변경, Package 배포가 있는지 확인합니다. 자기 복제형 Worm은 피해자 자신의 배포 권한을 이용해 퍼집니다.
5. **정리가 아니라 재구축.** 영향을 받은 Runner와 개발 장비는 가능하면 Image를 새로 만듭니다.

## AI Tooling이 노리기 좋은 대상인 이유

AI 코딩 Tool을 쓰는 개발 장비에는 수명이 긴 API Key가 dotfile과 환경 변수에 여럿 있기 마련입니다. Agent Infrastructure 계열 SDK는 바로 그런 Key가 있는 환경에 설치됩니다. 가능한 범위에서 수명이 짧은 인증 정보나 Secret Manager로 옮기고, CI Runner는 일회용으로 운영해 침해된 설치가 남지 않도록 합니다.

## 정리

- Install Script는 기본적으로 끄고, 예외만 허용 목록에 둡니다.
- 의존성 자동 업데이트에 Release 후 경과 시간 조건을 둡니다.
- 유효한 Provenance를 안전한 Package의 증거로 착각하지 마십시오.
- Worm이 의심되는 Incident에서는 격리를 먼저, 교체는 그 다음에 하고, Token을 건드리기 전에 최신 Advisory를 읽습니다.
