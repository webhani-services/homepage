10월 20일 TypeScript 7.1 Beta가 공개되었습니다. 보도된 일정으로는 RC가 11월 10일, 정식 버전이 11월 24일입니다. 다만 Beta 자체가 약 2주 늦어졌으므로 이후 일정은 잠정적으로 보는 편이 좋습니다. 어느 쪽이든 앞으로 일주일 정도가 실제 Project에서 시험하고 문제를 보고할 수 있는 마지막 기간입니다.

7.1의 핵심은 새로운 언어 기능이 아닙니다. **Ecosystem의 도구들이 TypeScript 7로 넘어올 수 있는 기반**을 마련하는 Release입니다. Go로 다시 작성된 TypeScript 7은 type check가 크게 빨라졌지만, 기존 JavaScript API에 의존하던 typescript-eslint나 Vue·Svelte·Angular의 language tools는 바로 따라오지 못했습니다. 7.1은 이 공백을 메우기 시작하는 Release입니다.

## 주요 변경 사항

### 1. 용도별로 나뉜 preview API

7.1의 API는 하나의 거대한 Module에 모든 기능을 담지 않고, 용도별 entry point로 나뉘어 있습니다. 발표와 후속 보도에서 언급된 것은 다음과 같습니다.

- `typescript/sync`: 동기식 Compiler Client(compiler options, type checker, program API)
- `typescript/async`: 비동기 버전의 Client
- `typescript/fs`: File System 관련
- `typescript/ast`, `typescript/ast/is`, `typescript/ast/factory`: AST 타입, 판별 함수, 생성 함수

설계의 중심은 **snapshot**, 즉 특정 시점의 Compiler 상태를 보여 주는 읽기 전용 View입니다. 새 snapshot을 만들거나 기존 snapshot에서 갱신된 snapshot을 파생해 사용합니다. Editor처럼 상태가 계속 바뀌는 환경에서도 매 질의가 일관된 상태를 전제로 할 수 있도록 하려는 설계로 보입니다.

이 API는 명확히 **preview**입니다. Beta와 정식 버전 사이에도 호환성을 깨는 변경이 있을 수 있고, 전체 Documentation은 7.1 정식 버전에서 공개될 예정입니다. TypeScript API로 사내 도구를 운영하고 있다면 지금은 이전할 때가 아니라 실험해 볼 때입니다.

### 2. 내장 코드를 위한 content mapper

Vue SFC, Svelte Component, Angular template처럼 다른 형식 안에 TypeScript가 들어가는 경우를 위한 plugin 구조입니다. 도구는 파일 안의 TypeScript 부분을 language service에 노출할 수 있습니다.

지금까지는 각 도구가 가상 파일을 생성해 TypeScript에 넘기는 식으로 각자 우회 방법을 만들어 왔습니다. 공식 구조가 생기면서 Vue와 Svelte Project에서도 TypeScript 7의 속도를 누릴 수 있는 현실적인 길이 열렸습니다.

### 3. Ambient module에서 import attributes 선언

Bundler가 import attributes로 CSS나 텍스트를 불러오는 경우, 지금까지는 타입을 구분하기가 번거로웠습니다. 7.1에서는 attribute별로 ambient module을 선언할 수 있습니다.

```ts
// src/types/assets.d.ts
declare module "*" with { type: "css" } {
  const sheet: CSSStyleSheet;
  export default sheet;
}

declare module "*" with { type: "text" } {
  const content: string;
  export default content;
}
```

```ts
import sheet from "./theme.css" with { type: "css" };   // CSSStyleSheet
import readme from "./README.md" with { type: "text" }; // string
```

후속 보도에 따르면 import의 attributes가 선언 쪽 attributes 타입에 할당 가능하면 일치로 판단하고, 여러 선언이 일치하면 더 구체적인 선언이 우선합니다. Attribute 값은 string literal 타입이어야 합니다. 이 선언들은 TypeScript 기본 lib에 포함되지 않으므로 직접 작성하거나 Framework·Bundler가 제공하는 것을 사용합니다. 필요한 attribute 없이 import하면 Error가 나기 때문에 누락도 잡아낼 수 있습니다.

### 4. 정식 target·lib이 된 es2026

`--target es2026`과 `--lib es2026`을 정식으로 사용할 수 있습니다.

```json
{
  "compilerOptions": {
    "target": "es2026",
    "lib": ["es2026", "dom", "dom.iterable"],
    "module": "esnext",
    "moduleResolution": "bundler"
  }
}
```

Target을 올리면 downlevel 변환이 줄어 출력이 깔끔해집니다. 하지만 실행 환경(지원 Browser 범위, Node.js 버전)이 따라오는지는 별도로 확인해야 합니다. Next.js처럼 Bundler가 최종 변환을 맡는 구성에서는 `target`이 주로 type check에 영향을 주는 설정이라고 생각해도 됩니다.

이 밖에 source phase imports 지원도 포함되었습니다.

## RC 전에 해 둘 일

### 의존 도구가 TypeScript API를 쓰는지 파악하기

7.1의 혜택을 얼마나 받을지는 Project가 의존하는 도구가 TypeScript API를 사용하는지에 달려 있습니다.

```bash
# typescript에 의존하는 Package 목록
npm ls typescript --all 2>/dev/null | grep -v "deduped" | head -50

# 자주 문제가 되는 대표 도구
npm ls typescript-eslint vue-tsc @angular/compiler-cli svelte-check 2>/dev/null
```

이 도구들이 7.1 대응 버전을 내기 전까지는 Editor와 Linter는 5.x를 유지하고, CI의 type check만 7.x로 돌리는 구성도 현실적인 선택입니다.

### CI에 필수가 아닌 Beta Job 추가하기

Main Pipeline에 영향을 주지 않으면서 문제를 일찍 발견할 수 있습니다.

```yaml
# .github/workflows/typecheck-ts-next.yml
name: typecheck (typescript@beta)
on:
  pull_request:
  schedule:
    - cron: "0 3 * * 1"

jobs:
  typecheck-beta:
    runs-on: ubuntu-latest
    continue-on-error: true
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with:
          node-version: 24
          cache: npm
      - run: npm ci
      - run: npm install --no-save typescript@beta
      - run: npx tsc --noEmit --extendedDiagnostics
```

`--extendedDiagnostics` 출력을 남겨 두면 버전별 type check 시간과 Memory 사용량도 비교할 수 있습니다.

### Import attributes 사용처 점검하기

이미 `with { type: ... }` 형태의 import를 쓰고 있다면, 지금까지 `any`나 범용 선언으로 넘겨 온 부분을 7.1 선언으로 바꿀 수 있는지 확인합니다.

## webhani의 견해

TypeScript 7의 속도는 분명 매력적입니다. 하지만 저희가 지원하는 Project에서도 이전의 걸림돌은 type checker 자체가 아니라 **주변 도구의 대응 상황**이었습니다. 7.1은 바로 그 부분을 정면으로 다루는 Release이고, 특히 Vue나 Angular를 쓰는 팀에게는 TypeScript 7 이전의 현실적인 출발점이 될 것으로 보입니다.

권장 사항은 다음과 같습니다.

1. 이번 주 안에 필수가 아닌 Beta CI Job을 추가하고, type error 차이와 Build 시간을 기록합니다
2. Toolchain의 7.1 대응 현황을 목록으로 정리해 이전 판단 자료로 씁니다
3. TypeScript API를 사용하는 사내 코드(codegen, custom lint 등)는 API가 안정될 때까지 서둘러 이전하지 않습니다

Preview API는 바뀐다는 전제로 일찍 검증하고, 정식 버전에 반영될 수 있을 때 Feedback을 보내는 것이 좋습니다.
