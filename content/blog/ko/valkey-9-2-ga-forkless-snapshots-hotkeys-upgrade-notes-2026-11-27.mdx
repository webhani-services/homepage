Valkey 9.2가 2026년 11월 19일 GA로 출시되었습니다. RC를 지켜보셨다면 주요 기능은 이미 익숙하실 것입니다. 달라진 점은 이제 운영 환경 업그레이드를 현실적으로 계획할 수 있는 릴리스가 되었다는 것입니다. 이 글에서는 운영에 영향을 주는 변경 사항과, 적용 전에 어떻게 테스트할지를 정리합니다.

아래 내용은 Valkey 릴리스 공지와 2차 자료를 기반으로 합니다. 제3자 비교 글에 나오는 성능 수치(예: Sorted Set 메모리의 큰 폭 절감)는 저희가 직접 검증한 것이 아니므로, 반드시 자체 데이터로 측정하시기 바랍니다.

## 운영에 영향을 주는 변경 사항

**Forkless snapshot (선택형).** RDB Snapshot과 Replica의 Full Sync를 fork한 자식 Process가 아니라 Background Thread에서 실행할 수 있습니다. 중요한 이유는 `fork()`가 copy-on-write 메모리에 의존하기 때문입니다. 데이터셋이 크고 쓰기가 많은 Instance에서는 Snapshot 도중 메모리 사용량이 급증할 수 있고, 이 Spike를 버티려고 RAM을 넉넉히 확보하는 팀이 많습니다. 활성화는 `forkless-infrastructure-enabled`로 하며, 설정 파일에 지정해 시작 시점에 적용해야 합니다. Key당 4바이트가 추가로 든다고 보고되어 있습니다. `prefer-forkless` 정책은 필요할 때 fork 방식으로 되돌아갑니다.

**서버 측 Hot Key 탐지.** `hotkeys-top-k`를 설정하면 `HOTKEYS GET`과 `HOTKEYS RESET` 명령으로 어떤 Key에 트래픽이 몰리는지 서버에 직접 물어볼 수 있습니다. 이전에는 운영 환경에서 비용이 크고 위험한 `MONITOR` 샘플링이나 Client 측 계측이 필요했습니다.

**B+ tree Sorted Set.** Sorted Set이 B+ tree 표현으로 바뀌어 메모리 Overhead가 줄어듭니다. `ZADD` 기반의 Leaderboard, Rate Limiter, 지연 Job Queue가 가장 큰 혜택을 봅니다.

**복제 압축과 ACL Role.** 복제 트래픽을 압축할 수 있으며(LZ4 또는 Zstandard로 보도됨), 전송량 과금이 있는 Availability Zone 간 구성에서 도움이 됩니다. ACL Role로 권한 관리의 반복 작업도 줄어듭니다.

## Forkless snapshot에 가장 주목하는 이유

메모리 여유분은 In-memory Store를 운영할 때 눈에 잘 띄지 않는 비용입니다. fork 시 copy-on-write의 최악 상황에 대비해 큰 여유 메모리를 남겨 두는 것이 일반적인 경험칙이었습니다. 쓰기 패턴에 따라 forkless snapshot이 잘 동작한다면 용량 한계에 더 가깝게 운영하거나, 적어도 Snapshot 순간을 걱정하지 않아도 될 수 있습니다.

선택형인 데에는 이유가 있습니다. Background Thread 방식 Snapshot은 fork 방식과 Latency 특성이 다릅니다. 또한 Key당 4바이트는 Keyspace가 크면 무시할 수 없습니다. Key가 10억 개라면 약 4GB입니다. 무조건 이득이라고 가정하지 말고 테스트하십시오.

## 업그레이드 테스트 계획

릴리스 당일에 운영 환경을 업그레이드하지 마십시오. 현실적인 순서는 다음과 같습니다.

1. **삭제 또는 변경된 동작을 Release Note에서 확인합니다.** 명시적으로 설정한 옵션은 특히 주의합니다.
2. **Staging Primary의 Replica로 새 버전을 띄워** 동기화합니다. 복제 지연과 메모리가 정상 범위인지 확인합니다.
3. **대표적인 트래픽을 재생합니다.** 명령 패턴을 수집해 평균이 아닌 Latency Percentile로 비교합니다.
4. **쓰기 부하 상태에서 Snapshot을 테스트합니다.** forkless 사용 여부별로 Snapshot 중 Peak RSS와 p99 Latency를 기록합니다.
5. **Failover를 확인합니다.** 새 Replica를 승격하고 Client가 재연결되는지 검증합니다.

Snapshot 중 메모리 동작을 빠르게 비교하는 방법입니다.

```bash
# 백그라운드 저장을 시작하고, 쓰기가 계속되는 동안 메모리를 관찰
valkey-cli BGSAVE
while true; do
  valkey-cli INFO memory | rg 'used_memory_rss_human|used_memory_peak_human'
  valkey-cli INFO persistence | rg 'rdb_bgsave_in_progress'
  sleep 1
done
```

동일한 쓰기 부하에서 기본 fork 경로와 forkless 활성화 상태로 각각 한 번씩 실행합니다. Peak RSS의 차이가 알고 싶은 수치입니다.

Hot key 탐지는 첫 확인이 간단합니다.

```bash
# 시작 시 설정 파일에서 활성화: hotkeys-top-k 10
valkey-cli HOTKEYS GET
valkey-cli HOTKEYS RESET
```

명령 인자는 빌드에 따라 2차 자료와 다를 수 있으므로, 정확한 구문은 공식 문서에서 확인하십시오.

## Client와 Managed Service 관련 고려 사항

- **Client Library.** Valkey는 Redis 생태계와 Protocol 호환이므로 대부분의 Client는 그대로 동작합니다. 새 명령에 의존하는 Client 측 기능만 테스트하십시오.
- **Managed Service.** 클라우드의 Managed Valkey를 사용한다면 업그레이드 경로와 forkless snapshot 같은 신기능의 제공 시점은 사업자에 달려 있습니다. 계획 전에 지원 버전을 확인하십시오.
- **보안 패치.** 최근 몇 달간 Valkey 보안 Advisory가 여러 건 나왔습니다. Patch Level이 뒤처져 있다면 신기능과 별개의 이유로 업데이트를 진행해야 합니다.

## webhani의 권장 사항

Valkey를 Cache나 Session Store로 쓰는 일반적인 Web Application이라면 9.2는 급하지 않습니다. 평소 Patch 주기에 맞춰 업데이트하고, 실제로 겪는 문제를 해결하는 기능만 켜십시오.

다음 중 하나라도 해당한다면 우선적으로 테스트할 가치가 있습니다.

- fork를 위해 확보해 둔 메모리 여유분을 회수하고 싶다.
- 원인 모를 Latency Spike가 있고 hot key를 의심한다.
- Sorted Set을 많이 쓰며 메모리가 주된 비용이다.
- Zone이나 Region 간 복제를 하고 있고 전송 비용이 신경 쓰인다.

모두 신기능이 구체적이고 측정 가능한 문제에 대응하는 경우이며, 그것이 도입의 올바른 이유입니다. 먼저 측정하고, 설정은 Instance 하나씩 전환하십시오.
