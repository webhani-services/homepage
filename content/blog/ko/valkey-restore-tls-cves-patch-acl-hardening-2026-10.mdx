늦여름부터 Linux 배포판들이 Valkey 보안 업데이트를 배포하고 있습니다. Red Hat의 Advisory(RHSA-2026:64807)는 RHEL 9와 10을 Valkey 8.0.10으로 Rebase했고, 9월에는 Ubuntu의 USN-8771-1이 뒤따랐습니다. 이 가운데 두 건은 단순히 패치만 적용하기보다 원리를 이해해 둘 가치가 있습니다. 둘 다 여러분이 직접 제어하는 설정으로 영향 범위를 좁힐 수 있기 때문입니다. 아래 내용은 NVD 항목과 배포판 Advisory를 근거로 합니다. 일부 Aggregator 사이트에서 Advisory 번호가 서로 달랐으므로, 사용 중인 Vendor 기준으로 확인해 주십시오.

## 두 가지 문제

**CVE-2026-63639: RESTORE의 비정상 Stream Payload.** 조작된 RDB Stream Payload를 `RESTORE`로 보내면 Memory 손상이 발생할 수 있고, 최악의 경우 원격 코드 실행으로 이어집니다. 공격자가 `RESTORE`를 실행할 수 있어야 합니다. NVD 게시일은 2026-08-18입니다.

**CVE-2026-56684: TLS 보류 데이터의 use-after-free.** TLS 보류 데이터 처리가 올바르지 않아 Server가 Crash하거나 코드 실행이 가능할 수 있습니다. 악용하려면 `CLIENT KILL`을 실행할 수 있는 인증된 Client가 필요합니다.

두 건 모두 7.2.14, 8.0.10, 8.1.9, 9.0.5, 9.1.1에서 수정되었습니다. Ubuntu 공지에는 Cluster Slot 이전과 관련된 서비스 거부(CVE-2026-85522)도 포함되어 있습니다.

두 건 모두 특정 명령 권한을 가진 인증된 Client가 필요합니다. 이 점이 중요합니다. 인증 없이 인터넷에서 공격할 수 있는 종류의 Bug가 아니므로, 패치의 시급성과 패치 전까지 노출을 줄이는 방법이 달라집니다.

## 1단계: 실행 중인 버전 확인

```bash
valkey-cli INFO server | grep -E "valkey_version|redis_version"
```

Staging, CI Service Container, 버전을 직접 제어할 수 없는 Managed Instance까지 모든 환경을 확인합니다. Managed Service라면 짐작하지 말고 제공자의 Status 페이지에서 수정된 Engine 버전을 확인하십시오.

위의 수정 버전 목록과 비교합니다. 8.0 계열이라면 8.0.10, 8.1 계열이라면 8.1.9가 필요합니다. 긴급 패치 중에 Branch를 건너뛰지 마십시오.

## 2단계: ACL로 위험한 명령 제한

많은 환경에서 Default User는 모든 명령을 실행할 수 있습니다. Application 코드가 `RESTORE`나 `CLIENT KILL`을 필요로 하는 경우는 드뭅니다. 최소 권한 User를 만듭니다.

```text
# valkey.conf 또는 ACL File
user default off
user app on >REPLACE_WITH_STRONG_SECRET ~app:* &* +@read +@write +@connection -@dangerous -@admin
user ops on >REPLACE_WITH_OTHER_SECRET ~* &* +@all
```

`-@dangerous`는 `KEYS`, `FLUSHALL`, `DEBUG` 같은 명령을 제외합니다. 의존하기 전에 사용 중인 Server 버전이 각 Category에 무엇을 넣는지 확인하십시오.

```bash
valkey-cli ACL CAT dangerous
valkey-cli ACL DRYRUN app RESTORE app:key 0 payload
valkey-cli ACL DRYRUN app CLIENT KILL ID 1
```

`ACL DRYRUN`은 `app`에게 두 명령 모두 권한이 없다고 보고해야 합니다. Application의 정상 기능이 `RESTORE`를 사용한다면(일부 Migration이나 Cache Warming Tool이 사용합니다), 해당 Tool 전용 User에게만 권한을 부여합니다.

## 3단계: Network 노출 줄이기

- Private Interface에만 Bind하고, Application Host만 접근할 수 있는 Network Segment에 Valkey를 둡니다.
- VPC 내부를 포함해 모든 곳에서 인증을 필수로 합니다. 인증 없이 접근 가능한 Instance는 공격자가 이미 완전한 제어권을 갖고 있으므로 이 CVE들이 의미를 갖기 이전의 상태입니다.
- TLS는 필요한 곳에서만 활성화하고, 활성화한 곳은 신속히 패치합니다. CVE-2026-56684가 TLS 처리와 관련되기 때문입니다.
- 디버깅을 위해 Load Balancer나 Port Forward로 Port를 열어 두고 그대로 방치하지 마십시오.

## 4단계: Rollback 계획을 갖고 패치

Replication 구성에서는 Replica를 먼저 업데이트하고, Failover한 뒤 기존 Primary를 업데이트합니다. 전후로 Replication 상태를 확인합니다.

```bash
valkey-cli INFO replication
```

Cache 전용 Workload에서는 재시작 비용이 작지만, Cold Start 이후 Warm-up 때 Database에 걸리는 부하는 상당할 수 있습니다. 재시작은 시차를 두고 진행하며 Database CPU를 지켜보십시오.

## 5단계: 오용 모니터링

예상치 못한 User의 `RESTORE`나 `CLIENT KILL`을 Log로 남기거나 Alert를 설정합니다. ACL Log가 도움이 됩니다.

```bash
valkey-cli ACL LOG 20
```

Application User에게서 거부가 반복된다면 Bug이거나 탐색 행위라는 뜻입니다.

## Redis에서 마이그레이션 중이라면

Redis를 사용 중이라면 같은 Hardening이 적용됩니다. Red Hat Advisory에는 Redis의 RESTORE 문제(CVE-2026-66373)도 포함되어 있습니다. 올해 초 Redis 고유 Advisory는 이전 글 "[Redis Hardening Checklist](/blog/redis-rce-cve-2026-hardening)"에서 다루었습니다.

## 정리

현재 Branch 안에서 수정된 Point Release로 패치하고, Application User에서 `RESTORE`와 `CLIENT KILL`을 제거하고, 신뢰할 수 없는 Network에서 분리하고, ACL Log를 모니터링하십시오. ACL 변경은 비용이 적고, 다음 명령 수준 취약점에 대한 위험도 낮춰 줍니다. Managed Instance를 포함한 Caching 인프라 감사가 필요하시다면 webhani의 Cloud 컨설팅 업무의 일부로 도와드립니다.
