2026년 11월 10일경부터, 탈취된 수천 개의 GitHub 계정이 인증 정보를 훔치는 스크립트를 다수의 Repository에 밀어 넣고 있습니다. 보안 업체들은 이를 "wfx" 또는 "wfx-loot"라고 부릅니다. 수치는 출처마다 다릅니다. Aikido는 약 4,837개 계정이 약 6만 1천 개 Repository에 탐색용 Pull Request를 열었고, Payload가 실제로 실행된 곳은 2천 개 미만이라고 보고했습니다. 대략적인 규모로만 받아들이시기 바랍니다.

엔지니어링 팀에 중요한 것은 규모가 아닙니다. Endor Labs 등의 분석에 따르면 이 캠페인은 GitHub Actions의 취약점을 악용하지 않습니다. 탈취한 계정 인증 정보와 Token을 사용해, 해당 계정이 원래 가진 권한을 그대로 이용합니다. Workflow 파일이 전달 수단이고, CI Secret이 목표입니다.

## Stealer의 동작 (공개 분석 기준)

1. 탈취한 계정이 접근 가능한 Repository에 탐색용 Pull Request를 열어, Workflow를 주입할 만큼의 쓰기 권한이 있는지 확인합니다.
2. 권한이 있으면 GitHub Actions 안에서 Shell Script를 실행합니다. 이곳에는 Repository Secret, Cloud 인증 정보, Package Registry Token, AI Provider API Key가 모이기 쉽습니다.
3. 스크립트는 찾아낸 정보를 외부로 전송하고, 흔적이 되는 Workflow 실행 기록을 삭제하는 것으로 알려져 있습니다.
4. 이후 Azure Application에 Federated Credential을 등록하거나 AWS Role의 Trust Policy를 수정해 Cloud 쪽에 지속성을 확보합니다.

4번이 "Secret을 Rotation하면 된다"가 불충분한 이유입니다. Token을 교체해도, 공격자의 Principal이 Role을 Assume할 수 있게 해 둔 Trust Policy는 그대로 남습니다.

## 먼저 확인할 것

Cloud에 접근하는 CI를 가진 Repository가 있다면 다음 순서로 점검하십시오.

**1. 작성한 적 없는 Workflow가 있는지.** 최근 이력에서 낯선 Commit이 추가하거나 변경한 Workflow 파일을 찾습니다. 기본 Branch 외의 Branch도 대상입니다.

```bash
# 최근 30일간 Workflow 변경 (작성자 포함)
git log --since="30 days ago" --all \
  --format='%h %an %ad %s' --date=short \
  -- .github/workflows/

# 캠페인 식별자로 보이는 문자열
git grep -n -i "wfx" $(git rev-list --all --since="30 days ago") -- .github 2>/dev/null | head
```

**2. Key뿐 아니라 Cloud 쪽 신뢰 관계를 감사합니다.** AWS에서는 모르는 Principal이나 설정한 적 없는 OIDC Subject를 허용하는 Role을 찾습니다. CloudTrail의 `UpdateAssumeRolePolicy` 이벤트가 출발점입니다.

```bash
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=EventName,AttributeValue=UpdateAssumeRolePolicy \
  --start-time "$(date -u -d '30 days ago' +%FT%TZ)" \
  --query 'Events[].{time:EventTime,user:Username,res:Resources[0].ResourceName}'
```

macOS Shell에서는 `date` 부분을 `date -u -v-30d +%FT%TZ`로 바꾸십시오.

Azure에서는 App Registration의 Federated Credential을 확인합니다. 보고에는 `wfx-ci-` 접두사 항목이 언급되지만, 이름에 의존하지 말고 설명할 수 없는 항목은 모두 검토 대상으로 삼으십시오.

**3. 올바른 순서로 Rotation합니다.** 먼저 낯선 Trust 설정과 Federated Credential을 제거하고, 그다음 Secret을 교체합니다. 순서를 거꾸로 하면 Backdoor를 통해 새 인증 정보를 발급받을 틈이 남습니다.

**4. 사람 쪽도 점검합니다.** 쓰기 권한 보유자 목록 재검토, 오래된 Personal Access Token과 OAuth App 허용 폐기, 조직 단위 2단계 인증 강제를 확인합니다. 보고에 따르면 계정은 Credential Stuffing, Phishing, Infostealer 로그 등으로 탈취되었으며 GitHub 자체가 침해된 것은 아닙니다.

## 피해 범위를 줄이는 Hardening

새로운 내용은 아니지만, 이번 캠페인은 실제로 적용해 두었는지를 시험하는 계기가 됩니다.

**장기 Cloud Key 대신 OIDC Federation을 사용하고 Subject를 제한합니다.** Repository 내 모든 Workflow를 허용하는 Trust Policy는 정적 Key보다 조금 나은 수준입니다. Environment로 고정하십시오.

```json
{
  "Condition": {
    "StringEquals": {
      "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
      "token.actions.githubusercontent.com:sub": "repo:your-org/your-repo:environment:production"
    }
  }
}
```

Reviewer 승인이 필요한 `production` Environment와 함께 쓰면, Feature Branch의 악성 Workflow는 운영 인증 정보를 얻을 수 없습니다.

**기본 권한을 최소화합니다.**

```yaml
permissions:
  contents: read
```

**Workflow를 변경할 수 있는 사람을 제한합니다.** `.github/workflows/`에 CODEOWNERS를 설정하고 소수 인원의 Review를 필수로 합니다. Branch Protection과 Ruleset은 관리자에게도 적용합니다.

**Third-party Action은 전체 Commit SHA로 고정하고**, 신뢰할 수 없는 Pull Request 이벤트에서 실행되는 Job에는 Secret을 전달하지 마십시오.

**Cloud 쪽에 Alert를 설정합니다.** Trust Policy 변경과 신규 Federated Credential 생성은 발생 빈도가 낮아 Alert 비용은 작고 신호는 명확합니다.

## webhani의 시각

고객사 팀들에게 공통으로 해당하는 교훈이 두 가지 있습니다.

첫째, CI는 "외부에서 접근 가능한 Trigger를 가진 인증 정보 저장소"입니다. Application Code는 꼼꼼히 Review하면서 Workflow는 가볍게 다루는 경우가 많지만, Workflow는 가장 강한 권한의 Secret에 접근할 수 있는 임의 코드입니다.

둘째, CI 침해 대응에는 Token Rotation뿐 아니라 Cloud ID 감사가 포함되어야 합니다. 런북이 "Secret Rotation"에서 끝난다면 Trust Policy, Federated Credential, 노출 기간에 생성된 신규 Principal 확인 단계를 추가하십시오.

AI Provider API Key도 표적에 포함됩니다. Pipeline이나 Coding Agent가 보유하고 있다면 Cloud Key와 동일한 범위 제한과 Rotation 원칙을 적용하십시오.

## 정리

- 악용되는 것은 GitHub Actions 취약점이 아니라 탈취된 인증 정보입니다. 계정 위생과 Token 범위 제한이 첫 번째 방어선입니다.
- Workflow 이력과 Cloud 신뢰 관계를 감사하고, Backdoor를 제거한 뒤에 Secret을 Rotation합니다.
- OIDC Subject를 Environment로 제한하고, Workflow 변경 Review를 강제하며, Trust Policy 변경을 모니터링합니다.

세부 내용은 계속 갱신되고 수치도 업체마다 다릅니다. 자체 점검을 마치기 전에 Aikido, Endor Labs, GitHub의 최신 Advisory를 확인하시기 바랍니다.
